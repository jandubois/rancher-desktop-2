## Executive Summary

The PR ports RD1's delete confirmations for the Containers and Volumes pages, the access key on Delete, and the translated Standalone Containers label. The port matches its RD1 source, and the translations pass i18n-report. Two defects need fixing first. The Volumes table keys rows on a `Name` field that RD2's rows lack, so the row menu never opens, and the PR's delete fix cannot run. And a refresh while the dialog is open makes a confirmed context-menu delete do nothing.

I1. **The Volumes row menu never opens, so the row-menu delete fix cannot run** — `pkg/rancher-desktop/pages/Volumes.vue:15` [Claude Opus 5.5, Codex GPT 6 Astra]

```vue
      key-field="Name"
```

SortableTable finds a clicked row by matching its `data-node-id` against `get(row, keyField)`. RD2's volume rows have `metadata` and `status` but no `Name`, so no row gets an id and `nodeForRow` returns nothing. The row menu, row selection and the context menu all stop there, and only select-all reaches `deleteVolume`.

See `pkg/rancher-desktop/components/SortableTable/selection.js:203-225` for the lookup.

The key line predates this PR (2025-07-02). But the PR body and `6a4e6e1ef` say this rewrite fixes deleting a volume from its row menu.

The table also reads `row[keyField]` and matches selections by `_key`, so a dotted `metadata.name` would not be enough.

I2. **A refresh while the dialog is open makes a confirmed context-menu delete do nothing** — `pkg/rancher-desktop/pages/Containers.vue:264` [Codex GPT 6 Astra]

```ts
              const targets = args?.length ? args : [container];

              if (await this.confirmDelete(targets)) {
                await Promise.all(targets.map(target => this.containerDelete({ container: target })));
              }
```

With several rows selected, the right-click menu hands the bulk handler the table's own `selectedRows` array. The toolbar's Delete filters that array into a copy first, so only the context menu is affected.

See `pkg/rancher-desktop/components/SortableTable/selection.js:330-338` and `pkg/rancher-desktop/store/action-menu.js:214-218` for that path.

The container store is watch-driven, so any change in the namespace rebuilds the rows while the dialog waits. The `pagedRows` watcher then splices the stale rows out of that same array. The user confirms, `targets` is empty, and nothing is deleted or reported.

See `pkg/rancher-desktop/components/SortableTable/selection.js:122-136` for the watcher.

Before this PR, the handlers dispatched at once, so the `await` opens the window. `Volumes.vue:161` keeps the same alias. RD1's #11007, not yet ported, refills the selection after a refresh.

## Suggestions

S1. **No test pins the Containers `bulkAction`** — `pkg/rancher-desktop/pages/Containers.vue:360` [Claude Opus 5.5]

```ts
          bulkAction: 'deleteContainer',
```

Deleting this line leaves all 13 `Containers.spec.ts` tests green; I ran that mutation during consolidation. Without the line, the table calls each selected row's handler separately, so a bulk delete opens one "Delete 1 container?" dialog per container, all at once. The specs call `row.deleteContainer(doomed)` directly and never check the delete action's entry.

Fix: assert the entry in the existing `getContainerActions` test, which already builds a stopped container.

```ts
expect(wrapper.vm.getContainerActions(stopped)).toContainEqual(expect.objectContaining({
  action: 'deleteContainer', bulkAction: 'deleteContainer', enabled: true,
}));
```

S2. **A confirmed delete force-removes a container that started while the dialog was open** — `pkg/rancher-desktop/pages/Containers.vue:267` [Claude Opus 5.5]

```ts
                await Promise.all(targets.map(target => this.containerDelete({ container: target })));
```

Delete is offered only for stopped containers (`isStopped`, line 358), checked when the user clicks. Deleting a Container mirror force-removes the engine's container, and containerd kills a running task first. The dialog stretches the gap between that check and the delete from milliseconds to however long the user takes. A container started meanwhile, from the CLI or by compose, gets killed and removed. That is unlikely, but nothing undoes it.

See `rdd/pkg/controllers/app/engine/controllers/docker_watcher.go:503` for the forced removal.

Fix: after the user confirms, delete only the targets whose current state in `this.containers` is still stopped.

S3. **The new `container()` fixture omits the required `status.id`** — `pkg/rancher-desktop/pages/__tests__/Containers.spec.ts:66` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]

```ts

        image:     'scratch',

        path:      '/bin/false',
```

S4. **The port dropped RD1's empty-selection case from the Containers spec** — `pkg/rancher-desktop/pages/__tests__/Containers.spec.ts:212` [Codex GPT 6 Astra, Gemini 3.5 Flash]

## Design Observations

### Concerns

- **(future)** `selection.update()` finds the row to deselect by `_key`, whatever the table's `key-field` (`pkg/rancher-desktop/components/SortableTable/selection.js:444`). Containers rows lack `_key`, so every lookup matches the first selected row. Select rows a and b, uncheck b, and the selection holds b while the checkboxes show a. A bulk action then runs on the row that the user unchecked. A probe run during consolidation left `['b']` with `key-field="id"` and `['a']` with `_key`. RD1 fixed this in #11007, and its port is already tracked. This PR's dialog, which names its targets, is where a user would now notice the wrong row. Found during consolidation; no reviewer raised it.
- **(future)** `components/Images.vue` still builds its own confirmation, without `showDeleteConfirmation` or an access key. The translations README records the exception (line 86). Routing Images through the helper would leave one dialog definition and one access-key rule. [Claude Opus 5.5]
- **(future)** The Volumes header `sort` keys (`Name`, `Driver`, `Mountpoint`, `Created`, `Volumes.vue:114-129`) name RD1 fields that RD2's rows lack, so the column sort compares undefined values. The rows arrive pre-sorted by name, which hides it. [Claude Opus 5.5]

### Strengths

- **(in-scope)** `showDeleteConfirmation` takes the strings the pages resolve, so the `t()` keys stay literal where i18n-report can find them. [Claude Opus 5.5, Codex GPT 6 Astra]
- **(in-scope)** Cancel is both the default and the cancel button, so Esc, Enter and closing the dialog all back out. [Claude Opus 5.5, Codex GPT 6 Astra]
- **(in-scope)** The standalone group keeps its English key for grouping and sorting, and only the header shows the translated label. [Claude Opus 5.5, Codex GPT 6 Astra]
- **(in-scope)** The macOS strip of parenthesized access keys applies only to dialogs that pass `normalizeAccessKeys`. [Claude Opus 5.5, Gemini 3.5 Flash]

## Review Process Notes

### Skill improvements

- When a change inserts an `await` (a dialog, a network call) between receiving a caller-owned collection and using it, check whether the caller can mutate that collection meanwhile, and whether the handler should copy it first. A synchronous handler never exposed that window, so the diff alone does not show the new risk.

### Repo context updates

- [repo] SortableTable finds a clicked row with `get(row, keyField)` and keys `v-for` rows and row expansion with `row[keyField]`. Flag a page whose `key-field` is a dotted path or names a field that its row objects lack, because row clicks, row menus and the context menu then do nothing and nothing reports an error.
- [repo] SortableTable's context menu passes bulk handlers the table's live `selectedRows` array. Every store watch event rebuilds the rows, and the `pagedRows` watcher then splices the stale rows out of that array. So a bulk handler that awaits before using its argument must copy it first.

S2. **Untested empty array bulk deletion in container spec** — `pkg/rancher-desktop/pages/__tests__/Containers.spec.ts:203-210` (suggestion, enhancement)

```typescript
    it('deletes the container once the user confirms', async() => {
      const containerDelete = jest.fn();
      const doomed = container('doomed');
      const row = rowFor(doomed, { containerDelete, confirmDelete: () => Promise.resolve(true) });

      await row.deleteContainer();
      expect(containerDelete).toHaveBeenCalledWith({ container: doomed });
    });
```

In `pkg/rancher-desktop/pages/Containers.vue:264`, `deleteContainer` folds an empty selection back to the row via `args?.length ? args : [container]`. `Containers.spec.ts` only tests `row.deleteContainer()` with no arguments (`undefined`). In contrast, `pkg/rancher-desktop/pages/__tests__/Volumes.spec.ts:106-115` explicitly tests both `[]` and `undefined` using `it.each`. Adding the empty selection case to `Containers.spec.ts` protects against regression where an empty array could delete nothing. Decided by check #3 (how a user sees it: silent no-op).

Fix:

```diff

+    it.each([
+      ['an empty bulk selection', []],
+      ['no selection, as the row menu passes', undefined],
+    ])('deletes the container given %s once the user confirms', async(_, selection) => {
       const containerDelete = jest.fn();
       const doomed = container('doomed');

-      await row.deleteContainer();
```

S3. **Inconsistent fallback for volume name in delete confirmation** — `pkg/rancher-desktop/pages/Volumes.vue:239` (suggestion, enhancement)

```typescript
names:   volumes.map(volume => volume.status?.name ?? ''),
```

In `pkg/rancher-desktop/pages/Containers.vue:314`, container names fall back to `metadata.name` if `status.name` is missing or empty (`container.status?.name || container.metadata?.name || ''`). In `Volumes.vue:239`, volumes fall back to `''`.
