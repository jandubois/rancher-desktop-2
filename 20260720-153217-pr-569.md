## Executive Summary

This PR re-backs the auto-update checkbox onto the daemon's `App.spec`, adds an
immediate-write path for preferences applied outside the Apply/Cancel dialog, and
re-enables the Application pane in the preferences window. Two issues dominate: a
rejected immediate write leaves an optimistic value stuck in the store with no error
surface, and nothing in the main process wires up the updater, so the restored
main-window checkbox never renders.

All four reviewers independently found the failed-write problem (I1), the strongest
signal in this review. Codex and Claude both traced the missing updater wiring (I2);
it predates this PR but bears directly on the PR's stated goal. The remaining twelve
suggestions are mostly comment, dead-code, and typing cleanups. Two Gemini 3.5 Flash
findings failed verification; the retro reconciles both.

## Important Issues

I1. **A failed immediate write leaves a stale value on screen and reports nothing** — `pkg/rancher-desktop/store/preferences.ts:195` [Claude Opus 4.8, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]

```ts
    } else {
      commit('SET_CHANGES', { ...state.changes, [key]: value });
    }

    return commitChanges(this, context, { [key]: value });
```

`writeNow` records the new value in `state.changes` before the patch, and nothing removes it when the patch fails. The `preferences` getter merges `state.changes` over the committed spec, and `RdCheckbox` reads its state from that getter (`RdCheckbox.vue:50`), so the box keeps showing a setting that was never stored.

The store plugin at `preferences.ts:413-418` clears a key only once `app.spec` matches it, which never happens for a rejected write.

`patchApp` records the reason in `errorStatus`, but only `Preferences/Alert.vue:28` and `Preferences/ModalFooter.vue:16` render it, and both live in the preferences window. The main window shows nothing. `RdCheckbox.onUpdate` also discards the boolean `writeNow` returns.

Fix: make `writeNow` async and drop the optimistic entry when the commit fails, so the checkbox snaps back to the committed value.

```ts
    const succeeded = await commitChanges(this, context, { [key]: value });

    if (!succeeded) {
      const { [key]: _rejected, ...reverted } = state.changes;
      commit('SET_CHANGES', reverted);
    }

    return succeeded;
```

Surfacing `errorStatus` in the main window is a larger change; if that is out of scope, leave a TODO.

I2. **Nothing wires the updater into the main process, so the restored main-window checkbox never renders** — `pkg/rancher-desktop/pages/General.vue:64-65` [Codex GPT 5.6 Sol, Claude Opus 4.8] (gap)

```ts
  ipcRenderer.on('update-state', onUpdateState);
  ipcRenderer.send('update-state');
```

No handler answers this request. The `ipcMain.on('update-state', …)` handler at `pkg/rancher-desktop/main/update/index.ts:67` registers as a module side effect, but `background.ts` never imports `@pkg/main/update`. ## Design Observations

### Concerns

- **Two write semantics chosen by a boolean prop on a shared form component** *(future)* [Claude Opus 4.8, Gemini 3.5 Flash] — `RdCheckbox` branches on `immediate` to pick between `preferences/modify` (batched, dry-run validated, applied on Apply) and `preferences/writeNow` (committed at once, no Apply gate). Their failure semantics differ sharply: `modify` reports through the dialog's `Alert` and `ModalFooter`, `writeNow` reports nowhere (I1). As more preferences move to the main window, that asymmetry multiplies. Letting the container supply the write strategy, rather than a boolean on the leaf, would force a container with no error surface to declare one.
- **The preference and its consumer live in different processes** *(in-scope)* [Codex GPT 5.6 Sol] — the renderer's Vuex store persists `application.updates.enabled`, while the updater runs in the Electron main process. Nothing currently bridges them (I2). A main-process watcher on the App resource that owns updater lifecycle and broadcasts `UpdateState` would also pick up preference changes made through the CLI, without renderer-specific IPC.
- **Immediate writes skip the validation round-trip** *(future)* [Claude Opus 4.8] — `modify` sends a `dryRun: 'All'` patch before committing; `writeNow` goes straight to the live patch. That is fine for a boolean. Applied later to a numeric or string preference, the user would get a hard rejection with no inline feedback. Worth documenting on the `immediate` prop.

### Strengths

- Extracting `commitChanges` so `commit` and `writeNow` share one path, including the generation-watch handshake and the `skipResolve` interrupt protocol, is the right factoring; the existing `commit` tests kept passing unmodified. [Claude Opus 4.8]
- Replacing `marked(markdown) as string` with `marked(markdown, { async: false })` removes an unsound cast. I confirmed marked 18.0.5 declares the narrowing overload at `node_modules/marked/lib/marked.d.ts:698-701`. [Claude Opus 4.8]
- Swapping `setData({ applying: true })` for a real `trigger('click')` upgrades that test from poking internal state to exercising `applyUpdate`. [Claude Opus 4.8]
- `preferencesNavItemName` with `as const satisfies` gives the nav a closed type, and the cast in `transientPreferences.ts` is the minimum needed to widen the literal. [Claude Opus 4.8]
- Moving the preference key, value lookup, and lock state into `RdCheckbox` simplifies every parent and gives the ongoing migration one consistent pattern. [Gemini 3.1 Pro, Gemini 3.5 Flash]

## Review Process Notes

### Skill improvements

**Verify typed-API claims against the installed declaration file.** When a finding claims that a call into a typed third-party API fails to compile, or returns a wider type than the surrounding code assumes, open the installed declaration file and read the overloads before reporting it. Library entry points often narrow their return type on a literal option value, so reasoning from the general signature produces a confident, well-cited false positive. Quote the declaration and line that makes the call fail; if you cannot find one, drop the finding.

**Cap severity on findings whose failure requires a change that has not happened.** When the failure mode needs a future refactor, a hypothetical object replacement, or a caller that does not exist, report it as a suggestion rather than a defect, and name both the invariant that currently prevents the failure and the code enforcing it. Reactivity, caching, and identity-comparison findings attract this shape. The observation is often worth making, but stating it as a present bug inflates severity and sends the author hunting for a failure they cannot reproduce.

**Confirm that a producer exists for every event or request a consumer issues.** When reviewing code that subscribes to an event, sends an IPC request, or waits on a channel from another process, verify that something registers the corresponding handler, and that the registering module is reachable from the program's entry point. Registration performed as an import side effect is dead when nothing imports the module, and type-only imports are erased at compile time, so they never trigger it. A consumer wired to an absent producer compiles, passes type checks, and silently does nothing.

### Repo context updates

**[repo] Vue is pinned at 3.5.x, so destructuring `defineProps` in `<script setup>` keeps reactivity.** The compiler rewrites destructured bindings back to prop accesses. Do not flag a destructured prop as a lost-reactivity bug in this repo; check the pinned Vue version in `package.json` before raising that class of finding.

**[repo] Each Electron window runs its own renderer with its own Vuex store.** The preferences dialog is a separate `BrowserWindow` created by `pkg/rancher-desktop/window/preferences.ts`, not a modal inside the main window. Renderer stores share no state across windows; anything that must cross a window boundary goes through IPC or the daemon. Treat any comment or code that assumes one window can observe another's store state as a defect.

**[repo] `background.ts` at the repo root is the sole Electron main-process entry.** Main-process modules register their `ipcMain` handlers as import side effects, so a module missing from that file's imports never registers anything, and its renderer-side callers hang silently. When a finding concerns main-process behavior, check that file's import list first.

## Design Observations

### Concerns

**Two write semantics selected by a boolean prop on a shared form component** *(future)* — `RdCheckbox` now branches on `immediate` (line 54-58) to pick between `preferences/modify` (dialog, batched, validated, applied on Apply) and `preferences/writeNow` (immediate, committed, no Apply gate). These have materially different failure semantics: `modify` surfaces errors through the dialog's `Alert`/`ModalFooter`, `writeNow` has no error surface at all (I1). As more preferences move to the main window this asymmetry will multiply. An alternative worth considering: keep `RdCheckbox` purely declarative and let the *container* supply the write strategy (a `write` prop taking the action name, or an injected `preferencesWriter`), so a container that has no error surface is forced to declare one. This is a future refactor, not a merge blocker.

**Immediate writes bypass the validation round-trip** *(future)* — `modify` sends a `dryRun: 'All'` patch first (line 173) and only then a real commit. `writeNow` goes straight to the live patch. For a boolean that is fine; if `immediate` is later applied to a numeric or string preference, the user gets a hard rejection with no inline feedback. Worth documenting on the `immediate` prop.

### Strengths

- Extracting `commitChanges` (lines 337-398) so `commit` and `writeNow` share one code path — including the generation-watch handshake and the `skipResolve` interrupt protocol — is exactly the right factoring, and it kept the existing `commit` tests passing unmodified because they already bound `this` explicitly.
- Replacing `marked(markdown) as string` with `marked(markdown, { async: false })` (`UpdateStatus.vue:167`) removes an unsound cast and correctly deletes the comment that justified it; marked 18 has the overload.
- `UpdateStatus.spec.ts:130` swapping `setData({ applying: true })` for a real `trigger('click')` upgrades the test from poking internal state to exercising `applyUpdate` — a genuine coverage improvement forced by the `<script setup>` conversion.
- `preferencesNavItemName` (`preferenceConstants.ts:16`) plus the `as const satisfies` on the array gives the nav a real closed type, and the cast at `transientPreferences.ts:17` is the minimum needed to widen the literal without loosening the state type.

##### I2. Missing state rollback on immediate preference write failure — `pkg/rancher-desktop/store/preferences.ts:183-195` (important, regression)

```typescript
  writeNow(context, { key, value }: { key: RecursiveLeafKeys<AppSpec>, value: FieldType<AppSpec, typeof key> }) {

```

When `writeNow` is dispatched (line 183), it eagerly adds the new value to `state.changes` (line 192) so the UI checkbox immediately toggles. It then calls `commitChanges` to persist the preference to the backend. However, if `commitChanges` fails, the change is never rolled back from `state.changes`. Because checkboxes are bound to `preferences/preferences` (which resolves `state.changes` on top of committed preferences), the UI will permanently display the failed state, resulting in a silent and confusing out-of-sync state.
