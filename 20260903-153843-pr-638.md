## Executive Summary

Round 5 closes all four of round 4's Important findings. The deletion finalizer is now best-effort, freshness gates under every strategy, and `api_app.md` describes the split gate. But the comment justifying the `manual` carve-out says a removal can only fail on a block the user corrupted. That is wrong: a permission error fails an intact block and repairs itself, so `rdd set --wait` reports success over a residue the next retry would clear.

Four Important findings survive. I1 and I2 are net-new defects that no prior round reached, both of them cases where the controller reports `Applied` over work it did not finish. I3 is round 4's I3 returning, with the rationale that declined it disproved. I4 is a pair of design docs describing a mechanism the PR did not ship. Seven suggestions that have now run two rounds unaddressed moved to Acknowledged Limitations rather than inflating the list a third time.

## Important Issues

I1. **Two instances racing on one startup file lose each other's block, and both report `Applied`** — `rdd/pkg/util/managedlines/managedlines.go:42` [Codex GPT 5.6 Sol]

```go
	current, err := os.ReadFile(path)
	if err != nil && !os.IsNotExist(err) {
		return err
	}

	target, changed, err := computeTargetContents(string(current), startMarker, endMarker, desired)
```

The suffix-tagged markers exist so separate instances can share one `~/.zshrc`. This read defeats that: `Manage` reads and computes before `atomicfile.Write` takes its per-path mutex (`atomicfile.go:86`), and that mutex is in-process anyway, so two daemons never share it. The later rename writes a target computed from the pre-state and drops the other instance's block. Both reconcilers then write `PathManagementReady=Applied` (`reconciler.go:105`). `manual` on a clean file returns before writing, so reaching this needs at least one instance on `front`/`back`.

```go repro
	for _, s := range []string{"2", "3"} {
		go func(s string) {
			defer wg.Done()
			<-start // release both at the same instant
			_ = Manage(p, "### START "+s, "### END "+s,
				[]string{`export PATH="/home/u/.rd` + s + `/bin:$PATH"`}, true)
		}(s)
	}
```

```text repro-output
first loss: instance2=true instance3=false userContent=true
concurrent Manage, distinct markers: 200/200 trials lost a block, 0 clean
sequential control: instance2=true instance3=true
```

Fix: hold an OS-level lock on the target file across read, compute, and write, so the guarantee the markers promise survives two daemons. The barrier in the probe releases both goroutines together, so 200/200 is the worst case, not the field rate; the sequential control shows the mechanism is the overlap and nothing else.

I3. **The `manual` carve-out names one cause of failure when there are several, and the repairable ones report success** — `rdd/pkg/controllers/app/app/controllers/app_controller.go:712` [Claude Opus 5, Codex GPT 5.6 Sol]

The carve-out treats them as unfixable, so `rdd set application.addPath=manual --wait` reports success over a residue. Fix: give the unparseable-block case a typed error and skip the gate only for that, keeping the gate and the finalizer for I/O errors. Failing that, drop "the only way" from all three copies of the sentence and say which failures the carve-out covers.

S1. **`manual` can promote an empty segment to the front of the Windows `Path`** — `rdd/pkg/controllers/app/pathmanagement/controllers/pathlist.go:62` [Claude Opus 5, Gemini 3.1 Pro, Gemini 3.5 Flash] (round 4 S2 unaddressed)

```go

			// Empty segments just leave stray semicolons; drop them when adding.
			continue
		}
```

Tidying is gated on `adding`, so removing our front entry from `C:\bin;;C:\Windows` yields `;C:\Windows` (measured in round 4). Windows resolves an empty `Path` entry as the current directory, so the removal turns a stray semicolon into a working-directory lookup ahead of every real directory. Codex reads the comment at line 29 as making this deliberate; the comment justifies keeping *existing* empty segments, not creating a leading one.

Fix: drop an empty segment that becomes leading or trailing because we removed our own entry next to it.

S2. **`--controllers=app` does not enable path management** — `rdd/pkg/controllers/app/pathmanagement/controller.go:46` [Codex GPT 5.6 Sol]

```go
func (c *controller) GetAPIGroup() string {

```

`shouldEnableController` matches a selector part against the API group or the controller name (`service.go:637-653`), and `""` matches neither, so `--controllers=app` starts the daemon without PATH management and reports ready. S7. **The generated shell lines interpolate `binDir` without quoting** — `rdd/pkg/controllers/app/pathmanagement/controllers/pathmanagement_unix.go:177` [Codex GPT 5.6 Sol]

```go
func posixPathLine(binDir string, strategy appv1alpha1.AddPathStrategy) string {
	if strategy == appv1alpha1.AddPathBack {
		return fmt.Sprintf(`export PATH="$PATH:%s"`, binDir)
```

`instance.Suffix()` returns `RDD_INSTANCE` verbatim (`instance.go:17`) and `BinDir()` carries it into these lines, so a suffix holding `$(…)`, a backtick, a quote, or a newline writes shell code into the startup file. ## Design Observations

### Concerns

- **Cleanup obligations still come from the desired value alone** `(in-scope)` [Codex GPT 5.6 Sol, Claude Opus 5]. The App records what the user wants and never what was last applied. Round 4 named this as the reason its I3 had no cheap fix; round 5 accepted the trade-off in a comment instead. A `status.appliedAddPath` would separate the `manual` default from an explicit `front`→`manual` switch, tell `Unwind` whether anything needs unwinding, and let the finalizer skip itself when nothing was written. I3 shows the accepted trade-off is broader than the comment claims, which raises the value of that field.
- **A permanent edit failure under `front`/`back` wedges every later `rdd set --wait`** `(in-scope)` [Claude Opus 5]. The author reasoned that gating `manual` on failure "would wedge `Settled` forever". The same wedge exists under `front`/`back`: a `.zshrc` the user broke after we wrote it makes `rdd set memory=8Gi --wait` fail forever for an unrelated reason. The forwarded reason does surface the cause, so it is diagnosable. Gating on failure only while `observedGeneration` matches the generation in which `addPath` itself changed would remove the class, and needs the same provenance field.
- **`%USERPROFILE%`-style entries are invisible to the Windows matcher** `(future)` [Claude Opus 5]. `computeWindowsPath` compares expanded literals, so a user who typed `%USERPROFILE%\.rd2\bin` gets a second literal copy under `front` rather than a move.

### Strengths

- The retargeted gate is correct across the whole cross-product. `reconciler.go:99` stamps the condition with the current generation *before* returning the error, so the freshness arm at line 725 is satisfied even when `apply` fails; without that ordering the split would deadlock. Claude enumerated (strategy × condition status × observedGeneration × enabled) and found no cell reporting a wrong `Settled`, and I re-ran the table suite green. [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]
- `TestReconcileReleasesFinalizerWhenUnwindFails` reproduces round 4's I1 input exactly, a `.zshrc` with a start marker and no end marker, rather than asserting the fix abstractly. [Claude Opus 5, Gemini 3.1 Pro, Gemini 3.5 Flash]
- Marking the first login file `handled` before the write (`pathmanagement_unix.go:94`) so a failure cannot push the block onto a file bash never sources, pinned by `TestApplyPosixFirstLoginFileFailureDoesNotMoveBlock`, remains the sharpest piece of failure handling in the PR. [Claude Opus 5, Codex GPT 5.6 Sol]

## Review Process Notes

### Skill improvements

- When a change ships a feature that documentation elsewhere in the repo already specifies, grep the whole tree for the feature's name and read every hit outside the changed files. A design doc describing an unbuilt plan is harmless; the moment the plan ships with different mechanics, that same doc states the wrong mechanism for shipped behavior, and no diff can show it. Check in particular for a command, flag, or helper the doc says the feature uses, and confirm the code defines it.
- When a design gives each writer its own tag, namespace, prefix, or marker so independent writers can share one resource, verify the read-modify-write around that resource is serialized across the writers, not just within one process. Per-writer tagging makes the writers look independent, which is exactly why the shared read gets no scrutiny. Check whether the lock covers the read or only the write, and whether it is a process-local primitive where the writers are separate processes.
- When a comment justifies skipping a gate by asserting that a failure has only one cause, enumerate the error returns of every function the guarded call reaches. The assertion is a claim about a set, and a single reachable error outside that set inverts the conclusion, because a gate skipped for an unfixable failure is reasonable while the same skip over a self-healing one reports success too early. Treat "the only way X fails" in a comment as a finding waiting to be checked, not as context.
- Treat a reproducer an agent attaches as a claim about the tree, not as evidence. Grep for every identifier its code names, the test function, the helper, the fixture type, before repeating its output. Agents fabricate reproducer blocks whose stated output is consistent with a true underlying claim, so the finding survives verification while the evidence never ran, and a report that quotes it launders a reading of the code into a measurement.
- Before crediting a finding that alleges a resource is about to be removed or invalidated, trace who removes it. Cleanup responsibilities commonly split across two entry points with different scopes, one tearing down a sub-resource and one deleting the parent directory, and a finding that assumes the wider scope reads as sound until the ownership is checked.

### Repo context updates

- `[repo]` `instance.BinDir()` resolves to `instance.ShortDir()/bin` (`~/.rd<suffix>/bin`), and only `service.Delete` removes it, via `os.RemoveAll(instance.ShortDir())`. Deleting the App resource tears down the LimaVM and nothing on disk. A finding premised on the bin directory disappearing must establish which of the two paths is running.
- `[repo]` `pkg/rancher-desktop/pages/FirstRun.vue` and its `openFirstRunDialog` helper in `pkg/rancher-desktop/window/index.ts` are unreachable Rancher Desktop 1 code: nothing calls `openFirstRunDialog`. Settings that page writes, including `application.pathManagementStrategy`, reach no user. Check for a caller before treating anything in that page as live behavior.
- `[repo]` `pkg/util/atomicfile` serializes writes with a `sync.Map` of per-path mutexes. That lock is process-local and is taken inside `Write`, so it does not serialize a caller's read-compute-write sequence and does nothing across two daemon processes. Callers that read a file, compute a new value, and write it back need their own cross-process lock.
- `[repo]` `shouldEnableController` (`rdd/pkg/service/cmd/service.go`) matches each `--controllers` part against the controller's API group or its name. Controllers under the app group that register no CRD of their own return `""` from `GetAPIGroup()`, so `--controllers=app` does not enable them; only the `*` default or their exact name does. This is the established convention, not a per-controller bug, but it does mean a named-group selector silently omits them.

## Design Observations

**Concerns**

- **A permanent edit failure under `front`/`back` wedges every later `rdd set --wait`, and nothing says so** *(in-scope)*. The author reasoned explicitly that gating `manual` on failure "would wedge `Settled` forever" (`app_controller.go:713`) — but the identical wedge exists under `front`/`back`, where a `.zshrc` the user broke after we wrote it makes `rdd set memory=8Gi --wait` exit 4 forever. The forwarded reason and `conditionReporter` do surface the cause, so it is diagnosable; what is missing is the acknowledgement. An alternative that removes the class: gate on failure only while `observedGeneration` equals the generation in which `addPath` itself changed, so the user who asked for the edit sees the failure and unrelated settings are not held hostage. That needs `status.appliedAddPath` provenance, which round 4 already identified as the cost.
- **`effectiveAddPath` and the reconciler's `strategy == ""` fallback are both dead against the CRD** *(future)*. `+kubebuilder:default=manual` (`app_types.go:232`) plus structural defaulting recursing into the parent-level `{updates:{enabled:true}}` default means stored Apps always carry `addPath`. Two independent copies of the same fallback (`reconciler.go:90-93`, `app_controller.go:738-744`) are a drift risk for no current benefit; if kept, a one-line comment saying they exist for objects written before the field landed would explain them.
- **`%USERPROFILE%`-style entries are invisible to the Windows matcher** *(future)*. `computeWindowsPath` compares expanded literals, so a user who typed `%USERPROFILE%\.rd2\bin` gets a second, literal copy added under `front` rather than a move (measured: `changed=false` under `manual` for that input). Expanding both sides before comparison would close it; whether it is worth the `ExpandEnvironmentStrings` call is a judgement for the author.

**Strengths**

- Splitting `writeUserPath` from `apply` so a test can retarget `envSubKey` at a throwaway HKCU key, and keeping `computeWindowsPath` pure so it can be exercised off Windows, is the right seam — it is why the Windows semantics are the best-tested part of the PR.
- Marking the first login file `handled` *before* the write (`pathmanagement_unix.go:94`) so a failure cannot push the block onto a file bash never sources, with `TestApplyPosixFirstLoginFileFailureDoesNotMoveBlock` pinning it, is a subtle failure mode caught early.
- Stamping the condition with the generation that was *applied* rather than the re-`Get`'s generation, with `TestReconcileStampsAppliedGeneration` proving it via an interceptor, is exactly the discipline `Settled` needs.

### Design Observations

#### Concerns

- **Shared host state lacks a shared owner (in-scope).** Each control plane reconciles one App, but shell files and the Windows user Path are per-user global state. A user-scoped coordinator or lock around the platform mutation would give all instances one serialization boundary and eliminate the lost-update class in I1.

#### Strengths

- The applied generation is carried from the strategy read into `PathManagementReady`, preventing a concurrent spec update from being credited prematurely.
- Suffix-specific fences, atomic publication, shell login-file precedence, and best-effort continuation across independent files are sound choices for the normal single-instance path.
- Concurrent App status writers use retry-on-conflict with a re-read, matching the repository’s status ownership contract.
