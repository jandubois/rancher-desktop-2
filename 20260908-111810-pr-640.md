## Important Issues

I1. **The webhook rejects `spec.namespace: moby` whenever the engine is down, and the reconciler never reads the field** — `rdd/pkg/controllers/containers/image/image_pull_request_webhooks.go:53-57` [Claude Opus 5]

```go
		containerNamespace := &v1alpha1.ContainerNamespace{}
		if err := v.reader.Get(ctx, key, containerNamespace); err != nil {
			if apierrors.IsNotFound(err) {
				return nil, fmt.Errorf("spec.namespace %q does not refer to an existing ContainerNamespace in namespace %q", imagePullRequest.Spec.Namespace, imagePullRequest.Namespace)
			}
```

Only the engine watcher's full sync (`sync_namespace.go:20-25`) creates
`ContainerNamespace/moby`, and `cleanupMirrorResources`
(`watch_reconciler.go:383`) deletes it again on app stop, so it is absent for
the whole VM boot and after every stop. Throughout that window this check
rejects the request the design doc's own example writes
(`api_containers.md:326-328`), which is why the new BATS suite waits for the
namespace first (`image-docker.bats:17`).

The reconciler's own path for this case, the `e == nil` wait for the engine
(`image_pull_request_reconciler.go:153-156`), is thereby unreachable for any
request naming the namespace, while a request that omits the optional field is
admitted and queued.

## Suggestions

S1. **The doc's `ImagePullRequest` example shows a settled-successful pull at 10% progress** — `rdd/docs/design/api_containers.md:331-340` [Claude Opus 5]

```yaml
status:
  lastUpdateTime: "2025-11-17T03:14:16Z"
  start: 0
  current: 10
  total: 100
  units: bytes
  conditions:
  - type: Settled
    status: True
    reason: ImagePulled
```

`image_pull_request_reconciler.go:416-417` sets `latest.Status.Current = latest.Status.Total` on the success path, so `current == total` holds for every `Settled=True`/`ImagePulled` object. A front-end written against this example renders a finished pull as a 10% bar.

Fix: set `current: 100`, or make the example the mid-pull state (`Settled: False`, `reason: Pulling`), which is the only state in which those numbers occur.

S2. **`status.lastUpdateTime` is documented as a progress timestamp but stamps every write** — `rdd/docs/design/api_containers.md:347` [Claude Opus 5]

```markdown
- **status.lastUpdateTime**: The last time any progress has been made.
```

The reconciler sets the field on the initial `Pulling` transition (`image_pull_request_reconciler.go:213`), on each throttled progress tick (line 338) and on the terminal update (line 406), including failures where no byte ever moved. The Go doc comment already says the right thing. Line 186 computes the pull timeout from this field, so a reader who believes the doc mis-models when a pull times out.

Fix: `- **status.lastUpdateTime**: The last time the status was updated.`

S3. **The design doc omits the admission rules the new webhook enforces** — `rdd/docs/design/api_containers.md:345-351` [Claude Opus 5]

The field list documents the `ImagePullRequest` fields but none of the four rejections this PR adds: `spec.namespace` and `spec.repoTag` are immutable on update, `spec.namespace` must name an existing `ContainerNamespace` in the same Kubernetes namespace, and `spec.repoTag` must satisfy `reference.ParseNormalizedNamed`. The doc's audience is the front end, which needs the rejection rules most. The list also reads as though `spec.namespace` were required, while `image_types.go:117-118` marks it `+optional` and `image/crd.yaml:58-59` requires only `repoTag`.

Fix: add a short "Validation" paragraph after the field list, and mark `spec.namespace` optional.

S4. **The exported type comment promises deletion the controller deliberately withholds** — `rdd/pkg/apis/containers/v1alpha1/image_types.go:169-171` [Codex GPT 5.6 Sol]

```go
// ImagePullRequest defines a request to pull a new image.
// After an image has been pulled, the ImagePullRequest object will
// be deleted after a short delay.
```

Fix: say that an ownerless request is deleted after a delay, and that one with owner references is retained for its owner to inspect.

## Design Observations

### Concerns

**Throttling the writes also sets the reconcile rate** `(in-scope)` [Claude Opus 5]. The 100 ms ticker caps status writes at ten per second per pull, which round 2 credited as the fix for its I5. Each of those writes is also an update event on `Watches(&containersv1alpha1.ImagePullRequest{}, …)` (`engine_reconciler.go:251`), so the same throttle governs reconciles too. Each is cheap (a cache read, then the early return at `image_pull_request_reconciler.go:196`), and the bulk path at lines 124-133 starts every pending request at once with no concurrency bound.

**`reconcileImagePullRequestTerminalReason` deletes the state entry on a path where it changed nothing** `(future)` [Claude Opus 5]. When `state.desiredReason` is the zero value the closure returns `nil` at lines 401-404, and the caller reads `err == nil` as "applied" and deletes the map entry at lines 437-441, dropping whatever `cancel` a concurrently-started pull had installed. Unreachable today: `MaxConcurrentReconciles` is 1 and the only other caller is the completion goroutine, which starts no pull. The invariant is unwritten, and correctness depends on it.

**`spec.namespace` has no consumer below the API** `(future)` [Gemini 3.1 Pro, Gemini 3.5 Flash]. Both Gemini models raised this as the `pullImage` signature gap: `engine_reconciler.go:102` takes only a repo tag, so a containerd implementation has nowhere to put the namespace. Docker has one global image store, so nothing breaks now. Round 2 filed the same concern from the CRD side; I1 is the client-facing consequence.

### Strengths

**The sentinel is the right shape for the completion signal** [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]. Replacing the shared `progressError` with `errPullSucceeded` in the context cause turns mutable shared state into an immutable value with a guaranteed happens-before edge, and because `progressCtx` is a child of `pullContext` the single `context.Cause(progressCtx)` read subsumes both cancellation sources. A late `onComplete(nil)` after a parent cancel cannot flip the verdict back to success, because the cause is already fixed.

**Terminal reason as queued intent, applied separately** [Claude Opus 5, Codex GPT 5.6 Sol]. `setImagePullRequestTerminalReason` records what should happen and `reconcileImagePullRequestTerminalReason` applies it, which makes the completion goroutine and the reconciler idempotent against each other and lets a failed status write self-heal on the next reconcile instead of losing the outcome.

**The UID-mismatch path cleans up without writing** [Codex GPT 5.6 Sol]. When the object is deleted and recreated mid-pull, the completion goroutine runs on a cancelled context, but the UID check at `image_pull_request_reconciler.go:393` returns before any status update and the stale state entry is removed. Verified by probe; see the retro's reconciliation note.

## Testing Assessment

Executed in the lead worktree at the review SHA: `go build ./pkg/controllers/...`
clean; `go test -race -count=3 ./pkg/controllers/app/engine/controllers/` and
`go test -race ./pkg/controllers/containers/...` both pass. `make

produced one agent's "stale generated helpers" finding. BATS was not run
locally; CI's three `bats-app` jobs passed at the round-2 SHA and the suite is
unchanged since.

Gaps, highest risk first:

1. **Manager shutdown mid-pull.** The case the sentinel exists to prevent has
   no test. One that cancels `watcherCtx` while a pull is in flight and asserts
   the terminal reason is not `Succeeded` would pin it; the probe in the retro
   is a starting point.
2. **Update admission** at both layers (S8), the one dispatch path
   controller-runtime keeps separate.
3. **Pull timeout** (`image_pull_request_reconciler.go:186-195`). No coverage of
   `PullTimeout`, which the design doc now publishes as API.
4. **Request deleted mid-pull** (lines 142-149,
   `imagePullRequestFailedReasonDeleted`), and the ticker-detected UID
   replacement.
5. **The new `alreadySettled` branch**, which no test drives through a
   status-update conflict followed by `Settled=True`.
6. **`Settled` reasons** (S9), and the bulk path's `RequeueAfter` fold and
   `errors.Join` at lines 118-134.
7. **Timing-dependent assertions.** Lines 441 and 513 sleep rather than
   synchronise; they passed 50 consecutive race-enabled runs, so the risk is a
   flake, not a failure. Raised in round 2 and unaddressed; see Acknowledged
   Limitations.

One style note: `image-docker.bats:12` captures with `RDD_NAMESPACE=$(rdd ctl get …)`
where the repo's rule is `run -0` plus `${output}`. Under `load.bash`'s
`errexit` the assignment does fail on a non-zero exit, so the only gain would be
that the failure report includes the command's output. The line is also copied
verbatim from `engine-docker.bats:48`, so changing it here alone would split the
convention.

## Documentation Assessment

where it matters most: both condition types, all five `Failed` reasons with
spellings that match the code, the owner-reference exemption (doc:36 against

  those sections would warn the reader without restoring the banner.

The `pullImage` interface comment (`engine_reconciler.go:101-102`) still does
not state when `onComplete` runs (round-2 S9, declined).

## Review Process Notes

### Skill improvements

- [ ] When an agent's own review reports running a build, generate, or format step against the worktree, re-run that step with the toolchain the project pins (the `go`/`node`/`python` version in its manifest) before accepting a "generated files are stale" or "verification fails" finding. Generators embed their toolchain's version in their output, so a newer local toolchain produces drift in files the change never touched, and that drift is indistinguishable in a diff from a missed regeneration.
- [ ] Before recording a reviewer's claim that a cancelled context caused a write to fail, check whether the client in that path reads through a cache. A cached read that discards its context returns a valid object where the reviewer assumed an error, which usually moves the failure to a later line or removes it entirely. The symptom the reviewer describes is often real on a different trigger they did not examine.
- [ ] Treat an agent that runs the project's own CLI, service, or daemon binaries as having acted outside its worktree, whatever its review says. A worktree left clean by `git restore` proves nothing about state the binary owns elsewhere on the machine. Check for such invocations in the agent's transcript, not only for a dirty worktree, and record them in the retro.

### Repo context updates

- [ ] [repo] `make verify-generate` passes only under the Go toolchain `rdd/go.mod` pins. Run it as `GOTOOLCHAIN=go1.26.0 make verify-generate`; a newer toolchain's `applyconfiguration-gen` inserts blank `//` lines into every generated `applyconfiguration/` file, which looks exactly like a missed regeneration. Do not report generated-code drift without re-running under the pinned toolchain first.
- [ ] [repo] `ContainerNamespace/moby` exists only while the engine watcher is connected: the watcher's full sync applies it, and `cleanupMirrorResources` deletes it on app stop along with the Container, Image and Volume mirrors. Any webhook or controller that requires the object to exist is unreachable for the whole VM-boot window and after every stop, so treat a validation rule keyed on it as a client-facing failure mode, not a safety check.
- [ ] [repo] controller-runtime's cached client discards the context on `Get` (`CacheReader.Get` takes it as `_`), while `Status().Update` fails immediately on a cancelled context. A goroutine that runs on past cancellation therefore reads a valid object and only then fails to write, so reason about where a cancelled-context path actually stops rather than assuming the first API call errors.
- [ ] [repo] The `rdd` engine reconciler is registered with `builder.TypedControllerManagedBy[engineRequest]` and no `.For(...)`, so controller-runtime's default log constructor adds neither kind nor object name to any line this controller emits. Log sites in that package must include `namespace` and `name` themselves; a bare `logf.FromContext(ctx).Error(...)` there is unattributable, and so is any error returned from `Reconcile`.

## Design Observations

### Concerns

- **`reconcileImagePullRequestTerminalReason` deletes the state entry on a path where it changed nothing** `(future)`. When `state.desiredReason` is the zero value the closure returns `nil` at line 401-404, and the caller treats `err == nil` as "applied" and deletes the map entry at lines 437-441 — dropping whatever `cancel` a concurrently-started pull had installed. Today this is unreachable: `MaxConcurrentReconciles` is 1 and the only other goroutine that calls this function (the completion goroutine, line 304) never starts a pull, so no one can install a fresh `cancel` while a `reconcileImagePullRequestTerminalReason` is in flight. The invariant is load-bearing and undocumented; a comment at line 437 naming it would keep a future concurrency bump from turning it into an orphaned pull.

- **`engineRequest` multiplexes two unrelated reconcile domains through one controller** `(future)`. `Reconcile` (`engine_reconciler.go:168-188`) switches on `req.Kind` to route between the watcher lifecycle and image-pull handling, and the two share the workqueue, the single-concurrency budget and (per I2) the log context. A second `TypedControllerManagedBy[…]` named `image-pull-reconciler` sharing the same `EngineReconciler` receiver would give each domain its own queue and its own `LogConstructor`, and would remove the `default:` arm at line 178-186 that exists only because the request type cannot express "one of two kinds".

### Strengths

- The `errPullSucceeded` sentinel is the right shape for the problem: it turns a shared mutable variable into an immutable value carried by the context itself, and because `progressCtx` is a child of `pullContext` the single `context.Cause(progressCtx)` read subsumes both cancellation sources without a second lookup.
- Layering the terminal reason as *queued intent* (`setImagePullRequestTerminalReason`) plus *apply* (`reconcileImagePullRequestTerminalReason`) makes the completion goroutine and the reconciler idempotent against each other, and lets a failed status write self-heal on the next reconcile rather than losing the outcome.
- `startWatcherAndSync` firing `enqueueReconcile(r.reconcileImagePullRequestChan)()` (`watch_reconciler.go:191`) closes the "created while the engine was down" gap that the `e == nil` early returns at lines 113-116 and 153-156 would otherwise leave open.
