## Executive Summary

The PR shows Preferences › Application › Environment on every platform and rebuilds `PathManagementSelector` to write `application.addPath` (`front`, `back`, `manual`) through `preferences/modify`, taking the real bin directory from a new `get-paths` IPC handler. The wiring works and its tests pass. But only `en-us.yaml` changed, so the eight other locales tell users to add RD1's `$HOME/.rd/bin`, and the descriptions leave out the Windows and Docker-plugin wording that #1049, which this PR closes, asked for.

None.

## Important Issues

I1. **The other eight locales still name RD1's `$HOME/.rd/bin` and lack the new keys** — `pkg/rancher-desktop/assets/translations/de.yaml:1042-1043` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]

```yaml
      # @source Rancher Desktop does not change your PATH configuration; add <code>$HOME/.rd/bin</code> to your path manually.
      description: Rancher Desktop ändert Ihre PATH-Konfiguration nicht; fügen Sie <code>$HOME/.rd/bin</code> manuell zu Ihrem PATH hinzu.
```

The PR adds `{binDir}` to `pathManagement.tooltip` and `options.manual.description` in `en-us.yaml` only. The selected locale's string wins over English (`store/i18n.ts:68-72`), and these contain no `{`, so the getter returns them unchanged. A user in any of the eight other locales who opens the newly visible tab is told to add RD1's directory, and sees the `front` and `back` options in English.

The repo's `i18n-report` flags it too. At the merge-base `de` has no drifted or stale `pathManagement` keys; at the head, `drift` adds the two keys above, `stale` adds both `rcFiles` keys, and `validate --locale=de` reports the missing `{binDir}`.

The patch ran `i18n-report remove` on those four keys, then restored `en-us.yaml`, which pipe mode also edits.

I2. **The descriptions leave out what #1049 asked for, and the PR closes #1049** — `pkg/rancher-desktop/assets/translations/en-us.yaml:481` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro]

```yaml
    front:
      label: Add to front
      # @no-translate Rancher Desktop
      description: Rancher Desktop will add '<code>'{binDir}'</code>' to the front of your PATH.  Restart any open shells for changes to take effect.
```

On Windows, where the tab now also shows, rdd edits the user Path (`pathmanagement_windows.go:116-127`), which Windows places after the system Path. So `front` cannot put the bundled `docker` ahead of Docker Desktop's.

The Manual text (line 489) omits that `manual` also takes the bundled plugins directory out of docker's `cliPluginsExtraDirs` (`dockerplugins.go:49-54`). Then `docker compose` stops finding the bundled plugin, and PATH can't help, because Docker never looks for plugins there (`rdd/docs/design/api_app.md:45`). The default `unset` behaves the same.

#1049 specifies these texts, and "Closes #1049" drops them from the open list on merge.

Unproven: the system Path's precedence is Windows behaviour, and this review had no Windows host.

## Review Process Notes

### Skill improvements

- When staging installed dependencies for agents, also run the install steps that a package defers to its first import, such as a binary it downloads, before staging the tree. An install that skips build scripts leaves such a package to fetch on first use, so each agent's test run downloads it again, and a test that imports it can time out mid-download and read as a failure.

### Repo context updates

- [repo] Changing an `en-us.yaml` string's text or placeholders leaves every other locale on its old translation, and the renderer's `t` prefers the selected locale's string, ignoring arguments that string lacks. Each locale key records the English it was translated from in a `# @source` comment. To see what a PR does to the locales, build `src/go/i18n-report` in its module directory, then run `drift`, `stale` and `validate --locale=<code>` from the repo root at the merge-base and at the head, and flag any key that the head adds. Check `.github/workflows` for an `i18n-report check --locale` step before assuming CI catches this.
- [repo] A value returned through `ipcMainProxy.handle` crosses Electron's structured clone: own enumerable getters are evaluated and copied, but a `Proxy` throws "could not be cloned" and the renderer's `invoke` rejects. `getPaths()` returns such a Proxy when `rdd service paths` fails. Reject a fix that wraps an IPC return value in a Proxy.
- [repo] A Preferences tab component may read `preferences/preferences` without optional chaining: `pages/Preferences.vue` renders the tabs only once the committed App spec has keys, and the CRD defaults each top-level spec section. Rate a missing-`?.` finding in such a component as latent unless it has a caller outside that page.
- [repo] UPDATE the entry on `pages/FirstRun.vue` and `addPath` once the Environment tab writes `application.addPath` on the default branch: its claims that the tab is commented out and that no app code writes `addPath` then stop holding.

###### Design Observations

###### Concerns
- **Coupling of `PathManagementSelector` to Vuex store** `(in-scope)`: In RD1, `PathManagementSelector.vue` was a pure presentational component accepting `value`, `isLocked`, and emitting `input`. This PR converts it into a store-coupled component reading and modifying `preferences/modify`. While this aligns with `ApplicationGeneral.vue`, it breaks compatibility with `pages/FirstRun.vue` (lines 73-77), which still attempts to bind `:value="pathManagementStrategy"` and `@input="setPathManagementStrategy"`. If `FirstRun` is re-enabled in the future, it will fail to bind properly unless updated to match the store-driven API.

###### Strengths
- **Accessibility and ARIA compliance**: Removing the invalid nested `<label>` in `RadioButton.vue` and linking `:aria-describedby` dynamically to the description block using `hasDescription` significantly improves screen-reader compatibility.
- **Store-driven preferences integration**: Re-backing `application.addPath` through `preferences/modify` cleanly adopts RDD's server-side apply validation and pending changes store.

###### Testing Assessment

- **I1 (Unchecked `preferences.application.addPath`)**: Required under Testing check #3 (crashes Preferences UI upon navigation when `App` spec lacks `application`). An existing test does not catch this because `PathManagementSelector.spec.ts` mocks a fully populated `preferences.application` store state.
- **I2 (`getPathsForScreenshots` Proxy flattening)**: Required under Testing check #3 (silent breakage of `paths` fallback during test/headless executions). `paths.spec.ts` only invokes `getPaths()`, leaving `export default` and `getPathsForScreenshots()` unexercised.
- **I3 (Missing tooltip `{ binDir }` parameter)**: Required under Testing check #3 (causes runtime `MissingValueError` logs and corrupts tooltip formatting).
- **Missing component test for `ApplicationEnvironment.vue`**: Required under Issue #1049 acceptance criteria ("Add a Jest test that the Environment tab writes `application.addPath`"). Only `PathManagementSelector` has a spec; `ApplicationEnvironment` is unexercised.

###### Documentation Assessment

- `config/help.ts:22` uncommented `'application/environment': 'ui/preferences/application/environment'`, which restores help routing for the Environment tab.
- Issue #1049 noted that Windows descriptions should clarify user Path vs. system Path precedence and compose/buildx plugin implications under manual mode. Currently, `en-us.yaml` uses a single generic string across all platforms ("Restart any open shells...").

###### Commit Structure

Commit `f3a6ad4f7` (`RDA: Prefs: Enable path management, convert to composition API`) explicitly states in its message:
> "Note that these are intentionally not working correctly; it will be fixed in a follow-up commit."

Commits `f3a6ad4f7`, `8b548fe1b`, and `53ebe309b` contain interdependent changes that leave intermediate commits in a broken state, violating bisectability. They should be squashed into a single coherent commit before merging to `main`.
