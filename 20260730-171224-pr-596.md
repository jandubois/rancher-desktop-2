## Review Process Notes

### Skill improvements

- When the review target is a merge commit, derive the files to review by replaying the merge (`git merge --no-commit --no-ff <other-parent>` from the first parent) and classifying every conflict as take-one-side, hand-merged, or modify/delete. Take-one-side resolutions silently discard the other parent's change to that file, and hand-merged files are where a hunk gets half-applied. Tell agents to spend their budget there and to treat the rest of the merge-base diff as already-reviewed upstream work. Without this, the agents each re-review the whole import and converge on the same handful of shallow findings.
- On a merge, classify each merged blob against both parents (identical to parent A, identical to parent B, or differs from both) and give agents the classification. A blob identical to a parent needs no review; only the third class is new work. This turns an unreviewable diff into a bounded file list.
- The merge itself authored any rename or type change that appears in neither parent, so nothing upstream reviewed it. Flag such changes to agents as the highest-yield place to look for stranded call sites, because nothing outside the resolved file changed to match.
- Before accepting a finding that traces a call chain to a defect, check that the chain's entry point can execute. A handler is latent when the only way in is a constant-false template branch, a commented-out block, or an unregistered route, and the severity must say so. Reviewers reconstruct chains bottom-up from the defect and routinely miss that the top of the chain is disabled two lines above the code they quoted.
- When a reviewer proves a type error with a synthetic reproduction rather than the real declaration, re-run the check with the actual file imported through the project's own tsconfig, before repeating the claim. A hand-written stand-in can encode the union the reviewer expected instead of the one the code declares.
- Where a change alters what a shared helper returns for a missing input (a placeholder string instead of `undefined`, an empty collection instead of null), grep every caller for `??`, `||` and truthiness guards on that return. A caller written against the old contract keeps compiling and silently loses its fallback branch.

### Repo context updates

- [repo] The check-spelling configuration under `.github/actions/spelling/` is inert. The `spelling` job in `.github/workflows/lint.yaml` is commented out, and no `spelling.yml` workflow exists. A word missing from `allow.txt` or `expect/*.txt` cannot fail CI; it surfaces only through a manual `make spelling`. Rate such findings as suggestions, not CI breakage.

- [repo] `yarn lint:typescript:nofix` runs eslint, not `tsc`, and Playwright uses its own transpiler. Only the production `package` build type-checks bundled files. ### Design Observations

**Concerns**

- **The i18n gate and the i18n code arrived separately.** (in-scope) Every finding above except C1 and I5 is something `i18n-report check --locale=all` reports mechanically: I3's dead channel shows as a `locale.*` mismatch only indirectly, but I4 surfaces as five unused keys, S2 as 14 missing plus one drifted. Landing the tool without its CI job inverts the design: the repo now carries a 3,500-line checker that nothing runs. Re-enabling it (I1 + I2) subsumes S2 and would have caught I4 automatically.
- **The renderer and the main process disagree about `appName` injection.** (in-scope) `store/i18n.js:95-98` merges `{ vendor, appName }` into every format call; `main/i18n.ts:90` formats only the caller's args. A key written for one side silently misbehaves on the other — I7 is one instance, and `tray.ts`, `mainmenu.ts`, `window/dashboard.ts` and `window/preferences.ts` all call the main-process `t()`. Injecting the same two values in `main/i18n.ts` would remove the asymmetry and let `tray.tooltip` become `{appName}`.
- **RD1 components are being adopted whole while RD2's prop APIs have moved on.** (future) C1 is the visible case: `RdCheckbox` migrated from `value`/`is-locked`/`update:value` to a store-backed `preference` prop, and an RD1 component dropped in unchanged compiles, mounts, and does nothing. The store-typing gap (`typings/store.d.ts` keeps vuex's `(type: string, payload?: any)` overload) means I6's class of defect is equally invisible. A short checklist for "adopting an RD1 component" — check `form/` prop APIs, check every `dispatch` string against the module, check every `ipcRenderer.invoke` channel has a handler — would catch all three.

- The `.golangci.yaml` resolution is exemplary: it drops every `src/go/rdctl|wsl-helper|nerdctl-stub` exclusion for trees RD2 deleted while keeping RD1's new `ignore-string-values` entry, with the reason spelled out in the comment.

return {

### [Gemini 3.5 Flash]

### Executive Summary

PR #596 successfully merges RD1 upstream branch changes into RD2, but introduces a major schema drift and visual localization regression. The transition from RD1's local JSON settings to RD2's daemon-backed architecture leaves the new `application.locale` preference completely missing from the daemon's `AppSpec` Custom Resource definition, causing validation failures on preference save. Additionally, a localization-fallback bug in the rewritten `Alert.vue` will display ugly visible placeholders instead of raw error messages to users when validation fails. Resolving these issues, along with minor spelling allowlist omissions, will ensure a stable merge.

---

### Findings

#### Critical Issues

C1. **Settings Schema Drift: Missing `locale` Field in Daemon's `AppSpec` API** — `rdd/pkg/apis/app/v1alpha1/app_types.go:175` (critical, regression)

```go
type ApplicationSpec struct {
	// updates specifies application update settings.
	// +optional
	// +kubebuilder:default={enabled:true}
	Updates ApplicationUpdatesSpec `json:"updates,omitempty"`
}
```

In RD1, the newly added `application.locale` preference was stored in a local `settings.json` file. In RD2, preferences are synced to the `App` Custom Resource managed by Rancher Desktop Daemon (RDD). Since RDD's `ApplicationSpec` schema lacks a `locale` field, any attempt to modify or save language preferences generates an invalid JSON patch path (`/spec/application/locale`), which is rejected by the Kubernetes API server and crashes preference saving.

**Traced Path:**
1. Trigger: `pkg/rancher-desktop/components/Preferences/ApplicationGeneral.vue:22` calls `store.dispatch('preferences/modify')`.
2. Action: `pkg/rancher-desktop/store/preferences.ts:153` triggers validation and patching.
3. Patch Gen: `pkg/rancher-desktop/store/preferences.ts:241` outputs path `/spec/application/locale`.
4. Impact: Rejected by Kubernetes API server due to schema definition at `rdd/pkg/apis/app/v1alpha1/app_types.go:175`.

Fix: Add the `locale` field to the `ApplicationSpec` struct in Go, then regenerate the client deepcopy code and models.

```go
type ApplicationSpec struct {
	// updates specifies application update settings.
	// +optional
	// +kubebuilder:default={enabled:true}
	Updates ApplicationUpdatesSpec `json:"updates,omitempty"`
	// locale is the user's preferred application locale (e.g., "en-us", "de").
	// +optional
	// +kubebuilder:default="en-us"
	Locale string `json:"locale,omitempty"`
}
```

#### Important Issues

I1. **`Alert.vue` Fallback Bug Displays Visible Placeholders** — `pkg/rancher-desktop/components/Preferences/Alert.vue:62` (important, regression)

```typescript
  const localized = store.getters['i18n/t'](key, { current, message: cause.message });

  return localized ?? `${ cause.field }: ${ cause.message }`;
```

When a settings validation failure occurs for fields lacking a dedicated translation (e.g., custom versions/CPUs), `errorString` tries to translate the error key. Because `store.getters['i18n/t']` returns a visible debug placeholder (e.g., `%preferences.validation.kubernetes.version.FieldValueNotSupported%`) on miss, `localized` is always non-empty and truthy. The nullish coalescing operator never falls back to the raw server message, displaying the ugly placeholder string to the user.

Fix: Verify the key exists in translation files using the store's `exists` getter before attempting a translation.

```diff
-  const localized = store.getters['i18n/t'](key, { current, message: cause.message });
+  const localized = store.getters['i18n/exists'](key) ? store.getters['i18n/t'](key, { current, message: cause.message }) : undefined;
```
