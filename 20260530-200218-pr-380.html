Executive Summary ¶

The PR gates computeSettledCondition on templateUpToDate — the template ConfigMap's resourceVersion versus the LimaVM's ObservedTemplateResourceVersion — so Settled stays False (reason ApplyingTemplate) until the VM restarts into a rewritten template, closing the premature-settle window in issue #378. All three reviewers found the fix correct with no Critical or Important issues; an independent cross-controller trace confirmed convergence with no hang. Remaining items are a design-doc table omission and a BATS-style nit.

All three reviewers (Claude, Codex, Gemini) agreed the core logic is sound. The only inter-reviewer disagreement was the severity and validity of the local-inside-@test style point (S2), resolved below against the actual file.

  `Running=True` means the Lima guest has finished booting and SSH is reachable. It says nothing about the container engine socket; consumers that depend on the engine (container/image/volume mirrors, `docker` against the forwarded socket) must also check `ContainerEngineReady`, which flips to `True` only after the engine controller has connected to the socket and completed its initial full sync.

  The `Created` and `Running` conditions are mirrored from LimaVM, so their `lastTransitionTime` reflects the LimaVM transition rather than the copy — the timestamp is meaningful for staleness checks. The engine reconciler stamps `ContainerEngineReady.observedGeneration` with the App's `metadata.generation` at the time it writes the condition; if the App's generation advances between the reconciler's read and write, the stamp reflects the write-time generation rather than the observed one. The App reconciler computes `Settled` from the mirrored `Running`, the engine-written `ContainerEngineReady`, and the Kubernetes-written `KubernetesReady` (the last only when `spec.kubernetes.enabled` is true), and stamps its own `observedGeneration` with the `metadata.generation` observed when it computed the condition, not the generation at write time. The retry-on-conflict loop re-reads on 409, so a successful write always carries the current generation. `rdd set` waits for `Settled.status=True` with `observedGeneration >= post-patch metadata.generation`, so stale snapshots cannot prematurely satisfy the wait.

RDD has no public release, so this is doc drift, not a contract break.

Design Observations ¶

Strengths ¶

  • Generic, change-agnostic gate Claude — The gate unsettles on any template-rewriting spec change (containerEngine.name, kubernetes.version, kubernetes.enabled) without inspecting what changed, and correctly makes a version-aware KubernetesReady probe unnecessary — matching the direction @mook-as argued for in the issue. (in-scope)
  • Reuses existing deferral instead of new synchronization Claude Codex — The fix leans on the already-correct ObservedTemplateResourceVersion deferral in limavm_controller.go:handleTemplateUpdate (the version is withheld while RestartNeeded is set, lines 420-423). Both sides of the comparison are reads of the same <name>-template ConfigMap, so the resourceVersion match is exact. (in-scope)
  • Graceful degradation on boot failure Gemini — Because ApplyingTemplate holds only until the LimaVM writes the new template, a VM that then fails to boot surfaces the real failure (Starting/Failed) rather than masking it behind ApplyingTemplate indefinitely.
  • Test improvements Claude Gemini — The rename "without stopping VM" → "restarts the VM" corrects a pre-existing misnomer, and the before/after snapshot of lastTransitionTime + observedTemplateResourceVersion directly catches a premature-settle regression. The templateOutOfDate bool + !tt.templateOutOfDate extension covers the new branch without touching the 20+ existing table cases.

Testing Assessment ¶

The unit test (app_controller_test.go, "stale template holds Settled false despite ready conditions") is meaningful: it was confirmed to fail (True != False) with the gate disabled and pass when restored, and go test ./pkg/controllers/app/app/controllers passes. The BATS test validates the end-to-end fix via lastTransitionTime/observedTemplateResourceVersion deltas after a blocking rdd set.

Untested scenarios, ranked by risk:

  1. kubernetes.version=X at the integration level — the issue's headline reproducer. Both the unit and BATS tests exercise containerEngine.name; the version-change path is not pinned. Since the gate is template-generic and both fields rewrite the same ConfigMap, coverage is adequate, but the exact reported bug is not directly reproduced in CI.
  2. Combined running=false + template change — no test asserts the gate does not strand Settled when a template change races a stop. Traced manually: the stopped-phase branch in handleTemplateUpdate records the new resourceVersion immediately, so Settled reaches True with no hang. Low risk, but it is the one untested interaction between the new gate and the !desiredRunning arms.
  3. No reconciler-level test proving templateUpToDate is derived from ConfigMap resourceVersion vs LimaVM.status.observedTemplateResourceVersion; only the pure computeSettledCondition function is unit-tested.

Documentation Assessment ¶

One gap, captured as S1: the new ApplyingTemplate reason is absent from the authoritative Settled reason table (api_app.md:122-128), the design-doc prose (api_app.md:132), and the waitForDesiredState comment (set.go:467-473). Code-level doc comments (app_types.go:80-83, app_controller.go:382-385, 504-507) are accurate and complete, and the ObservedTemplateResourceVersion field doc the fix relies on is already documented.

Commit Structure ¶

Single commit with a message that accurately describes the change and its rationale. History and scope are clean.

Acknowledged Limitations ¶

  • Code comment — "ConfigMaps are not watched, so requeue to let the reconciler evaluate remaining spec fields" (app_controller.go:411-415). The change makes this limitation less likely to cause premature success: the follow-up reconcile now holds Settled=False until the LimaVM reports the current template resourceVersion, rather than relying on LimaVM to set restartNeeded before a racing rdd set observes Settled=True.
