Executive Summary ¶

PR #390 adds rdd run COMMAND [ARGS...], which starts Rancher Desktop and runs a child process wired to the instance's Docker and Kubernetes contexts through PATH, DOCKER_CONTEXT, and a throwaway KUBECONFIG. The wiring is clean and copied credentials stay 0600. Two UX defects hit common inputs: a non-zero child exit prints a blank level=error line, and rdd run --help boots the VM before failing instead of showing help.

All three reviewers independently flagged the blank error line and the --help defect; both were reproduced live. The remaining findings — a documentation contract that overstates kubeconfig isolation, a Docker/Kubernetes coupling on kubeconfig load, and signal/cleanup gaps — each came from a single reviewer and verify against the code.

S3. Ctrl+C leaks the throwaway kubeconfig and skips cleanup Gemini¶ 
 command.Stderr = os.Stderr
+signal.Ignore(os.Interrupt)
 err := command.Run()

rdd installs no signal handler, and the child shares its foreground process group, so Ctrl+C delivers SIGINT to both. rdd dies on the default disposition before the deferred os.Remove(kubeconfig) runs (run.go:75), leaving a 0600 throwaway kubeconfig in $TMPDIR until reboot. Ending a long rdd run kubectl logs -f or exec -it with Ctrl+C is the common case, so these files accumulate. The author already notes signal handling is deferred (run.go:186-188, see Acknowledged Limitations), but that comment covers context cancellation, not the cleanup leak.

Fix: ignore os.Interrupt before command.Run(). rdd then waits for the child, runs its defers, and propagates the child's exit code; the child still receives the signal directly.

// getAppKubeClient returns a controller-runtime client with the App scheme
// registered, and the raw REST config for creating other clients.
func getAppKubeClient(ctx context.Context) (client.Client, *rest.Config, error) {
	if err := ensureServiceRunning(ctx); err != nil {
		return nil, nil, err
	}
	config, err := service.GetKubeRestConfig()
	if err != nil {
		return nil, nil, fmt.Errorf("failed to get kubeconfig: %w", err)
	}
	runtimeScheme := runtime.NewScheme()
	if err := appv1alpha1.AddToScheme(runtimeScheme); err != nil {

	if err != nil {
		return nil, nil, fmt.Errorf("failed to create client: %w", err)
	}
	return c, config, nil
}

Design Observations ¶

Concerns ¶

  • rdd run reuses the persistent global-context publication path (future) Codex — I3 and S1 share one root: the one-shot command relies on App startup to publish Docker and Kubernetes contexts into the user's global config, then reads back from it. Building ephemeral Docker and kube configs straight from the instance endpoints would make the command's isolation local and testable, and would free it from the health of the user's existing config.
  • TOCTOU between the App existence check and the patch (future) Claude — ensureAppRunning decides whether to add kubernetes.enabled=true from a Get that returns NotFound (run.go:99-103), but setAction re-fetches and patches. If another process creates the App without Kubernetes in that window, setAction patches kubernetes.enabled=true onto the existing App, contradicting the documented "an existing App is only started, never reconfigured." Irrelevant for a single-user CLI today; deciding enablement from one shared read (S4) closes it.
  • Every rdd run issues running=true and waits for Settled (in-scope) Claude — even rdd run docker context show runs the full set-and-wait path. When the App is already settled the patch is a no-op and the wait returns quickly, so the cost is one apiserver round-trip. Acceptable, and it matches the documented "starts first if not already running."

Strengths ¶

  • The code handles the environment-precedence traps correctly: clearing DOCKER_HOST lets DOCKER_CONTEXT win, and setting KUBECONFIG at the environment level overrides ~/.kube/config. Claude Gemini
  • The throwaway kubeconfig is 0600 and copies only the instance context, cluster, and user — not the whole config — so credentials stay protected. Claude
  • Missing-~/.kube/config and missing-instance-context cases degrade gracefully to a clear "context does not exist" error. Claude
  • writeRunKubeconfig runs before setupRunEnv, so it reads the user's real KUBECONFIG rather than the throwaway it installs. Claude
  • Relying on the App defaulter for the Kubernetes version, instead of hardcoding kubernetes.version=stable as the issue sketched, keeps one source of truth. Claude

Review Process Notes ¶

Repo context update [repo]: A CLI command that documents leaving the user's global Docker or Kubernetes configuration "unchanged" must be checked against the App-startup reconcilers, not only its own code. manageKubeContext (pkg/controllers/app/kubernetes/controllers/kube_reconciler.go) unconditionally merges the instance context into ~/.kube/config once k3s is healthy, and the engine reconciler creates the Docker context and sets currentContext when the existing one is unhealthy. Any command that triggers an App start — through rdd set running=true, ensureAppRunning, or ensureServiceRunning — inherits these global side effects regardless of its own isolation. Flag isolation claims that ignore the startup path.

Skill improvement: When a command loads or parses configuration for one subsystem on a code path shared with commands that do not use that subsystem, a malformed or unreadable config fails the unrelated commands too. Flag an unconditional config load that gates execution of subsystem-agnostic commands, and recommend deferring the load until a command that needs it runs — or tolerating the failure for the commands that do not.
