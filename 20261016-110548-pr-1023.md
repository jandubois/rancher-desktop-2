## Important Issues

I1. **Dropping the MSI's plugin PATH entries breaks standalone `docker-compose` on Windows** — `build/wix/main.wxs:89-94` [Claude Opus 5.5]

```xml
      <Environment Id="PathWindowsUserBin" Name="PATH"
        Action="set" Part="last" System="no" Permanent="no"
        Value="[APPLICATIONFOLDER]resources\windows\bin\" />
      <Environment Id="PathLinuxUserBin" Name="PATH"
        Action="set" Part="last" System="no" Permanent="no"
        Value="[APPLICATIONFOLDER]resources\linux\bin\" />
```

Only these `bin` entries remain; the PR removes the four that put `resources\windows\docker-cli-plugins` and `resources\linux\docker-cli-plugins` on PATH. Commit 3900234c6 added them so users could run the plugins directly, and `docker-compose` and `docker-buildx` ship only in those directories (`scripts/dependencies/tools.ts:112,150`).

The replacement, copies in `~/.rd2/bin`, reaches PATH only under `front` or `back`. No app code writes `application.addPath`, so every MSI install stays on the default `manual`, and both stop resolving in Windows shells and in WSL distros that append the Windows PATH. The field doc's claim that the GUI sends "front" when the user opts in (`app_types.go:222-223`) predates this PR and is false.

Unproven: the effect is in an installed MSI's PATH, which no in-process test can create.

Fix: keep the four entries until the app can set `addPath`. Docker ignores PATH when it looks for plugins, so they do not conflict with `cliPluginsExtraDirs`. The commit message then has to drop "dead".

I2. **An unparseable `config.json` under `manual` with the marker reports `Failed` and wedges Settled** — `rdd/pkg/controllers/app/pathmanagement/controllers/reconciler.go:249` [Claude Opus 5.5]

```go

```

## Review Process Notes

### Skill improvements

- **Replacement reachable only by opt-in**: when a change removes a working delivery path (a PATH entry, an installer step, a default) and replaces it with a mechanism that the user must opt into, check that the default configuration and every UI surface can reach that opt-in. A replacement that only some users can enable is a regression for the rest, and reviewing the replacement's correctness does not show it.

### Repo context updates

- [repo] No app code writes `spec.application.addPath` (as of 2026-10-16), so app installs run with the default `manual`. Before crediting a feature that `addPath=front|back` enables, grep `pkg/rancher-desktop` for a writer of `application.addPath`; when none exists, the feature is unreachable for app users, and removing an older path to the same capability is a regression for them.
- [repo] UPDATE the pending round-1 rule about the path-management reconciler under `manual`: `permanentPathError` decides the reason, and only causes that it recognizes map to the non-gating `Malformed`. Flag any new file that reconcile parses unless its parse failures are classified permanent, even when the step has work to do, since a marker can keep the step running under `manual`. **Shutdown and cancellation audit — reasoned**

- The other production config-edit callers are `setCurrentDockerContext` and `applyDockerPlugins`. The former receives `watcherCtx`; the latter receives the reconcile or service-deletion context. Cancellation aborts their lock wait rather than performing unwanted new work.

###### Design Observations

###### Concerns

1. **Dual lock acquisition in `apply`** (`in-scope`): `apply` (`reconciler.go:217`) acquires the PATH lock, then synchronously calls `applyDockerPlugins`, which acquires the `dockerconfig` lock. While lock ordering is consistent across controllers (precluding deadlocks), a slow or contested `dockerconfig` lock holds the PATH lock for up to `lockTimeout` (30s), blocking unrelated instances from performing PATH updates.

###### Strengths

1. **`errors.Join` with cause-walking error classifier**: `reconciler.go:224` runs both PATH and Docker plugin edits independently and returns `errors.Join(pathErr, pluginErr)`. `permanentPathError` properly inspects `err.(interface{ Unwrap() []error })` to ensure that any transient failure (such as a lock timeout) keeps retrying within the unwind grace window.
2. **Pre-mutation ownership markers**: Writing `.docker-plugins-managed` prior to updating `config.json` guarantees that if the process terminates mid-operation, subsequent runs under `manual` safely clean up residual entries.
3. **Hardlinked forwarders on Windows**: Reusing the shared `rdd-forwarder.exe` binary in the instance `docker-cli-plugins` directory via NTFS hardlinks eliminates duplicate executables while keeping shims co-located with their targets.
