## Suggestions

S1. **The icon title says "Loading" while an image builds** — `pkg/rancher-desktop/components/LoadingIndicator.vue:8` [Claude Opus 5.5]

```vue
        <title>{{ t('loadingIndicator.title') }}</title>
```

Every `LoadingIndicator` gets this title as its hover text and accessible name. "Loading" fits the logs, the volume files and an image pull.

But the Add Image page's Build tab shows the same icon beside "Building image..." (`components/ImagesOutputWindow.vue:135-137`), so the icon's name says "Loading" during a build.

The scan page does the same beside "Scanning '…'" (`pages/images/scans/_image-name.vue:14-16`).

So do the extension cards, beside "Installing...", "Removing..." and "Upgrading..." (`components/MarketplaceCard.vue:75`).

The installed-extensions table shows the icon with no text while it removes or upgrades an extension (`pages/extensions/installed.vue:242`), so "Loading" is all a screen reader gets there. The nav does not show the Extensions pages today, so these two callers wait until it does.

Fix: pick a word that fits every caller, such as "Working", and reword the en-us `@context` to match. Or give `LoadingIndicator` a `title` prop that defaults to that word, so callers that load can keep "Loading".

###### Suggestions

S1. **"Loading" is the hover text and accessible name for every spinner, including ones that are not loading** — `pkg/rancher-desktop/components/LoadingIndicator.vue:8` (suggestion, regression)

```vue
        <title>{{ t('loadingIndicator.title') }}</title>
```

`LoadingIndicator` sits beside several kinds of progress text:
- `ImagesOutputWindow.vue:135-137` shows `images.add.loadingText` (`'{action} image...'`, for example "Building image...").
- `pages/images/scans/_image-name.vue:14-16` shows "Scanning 'x'".
- `ContainerLogs.vue` and `volumes/files/_name.vue` show actual loading text.

Hovering over the spinner, or reading it with a screen reader, gives "Loading" next to "Building image..." or "Scanning 'x'". The commit body says the new title tells "a user ... what is happening". That holds for the logs and volume-file spinners but not for the image build, pull or scan spinners. The key was just added to all nine locales, so a wording change now costs less than one made after the translations drift.

Fix: use a word that fits every caller, such as "Working" or "In progress", and reword the en-us `@context` to match. Alternatively, let callers pass a `title` prop that defaults to that word.

S2. **Volume Files formats sizes in English units and the decimal style of the en-us locale** — `pkg/rancher-desktop/pages/volumes/files/_name.vue:399-402` (suggestion, gap)

```ts
      if (bytes === 0) return '0 B';
      const sizes = ['B', 'KB', 'MB', 'GB', 'TB'];
      const i = Math.floor(Math.log(bytes) / Math.log(1024));
      return Math.round(bytes / Math.pow(1024, i) * 100) / 100 + ' ' + sizes[i];
```

This is user-visible text on the page this PR touches, and neither #985 nor #1205 lists it.
- **Units:** French shows "Ko" and "Mo" for these units.
- **Decimals:** the number is joined with `+`, so de, fr, es, it, pt-br and vi readers see "1.5" where they expect "1,5".
- **Dates:** `formatDate` (line 405) calls `toLocaleString()`, which follows the OS locale. The app never sets Chromium's `--lang`, so dates do not follow the app's language either.

`git blame` dates these lines to commits d994a675f and f4031ecfe, so they predate this PR. `ContainerStats.vue:396` `formatBytes` has the same problem.

Fix: add these lines to #1205, or open a follow-up issue for number, unit and date formatting that follows the app's locale (`Intl.NumberFormat` and `Intl.DateTimeFormat` with the store's locale).
