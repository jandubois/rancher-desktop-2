Executive Summary ¶

The PR lets a developer-mode rdd running from a checkout publish the checkout's resources/<goos> tools and Docker CLI plugins, the way a packaged app does. The approach is sound, and the bats file passes on a live instance with and without an assembled checkout. Two things need fixing first. On Windows, a checkout without rdd-forwarder.exe now fails to publish anything, even rdd's own links. And a fixture comment claims developer-mode detection that the mock never triggers.

# Create a new file with the provided path; the contents of standard input will
# be written to that file.  Analogous to `cat >$1`.  Will create any parent
# directories.
create_file() {
    local dest=$1
    # On WSL, avoid creating files from within the Linux side; this leads to
    # issues where the WSL view of the filesystem is desynchronized from the
    # Windows view, so we end up having ghost files that can't be deleted from
    # Windows. MSYS2 writes directly to the Windows filesystem, so it's safe.
    if ! is_windows || is_msys; then
        mkdir -p "$(dirname "${dest}")"
        cat >"${dest}"
        return
    fi

    local contents # Base64 encoded file contents
    contents="$(base64)"

    local winParent
    local winDest
    winParent="$(wslpath -w "$(dirname "${dest}")")"
    winDest="$(wslpath -w "${dest}")"
    PowerShell.exe -NoProfile -NoLogo -NonInteractive -Command "New-Item -ItemType Directory -ErrorAction SilentlyContinue '${winParent}'" || true
    if [[ -z "${contents}" ]]; then
        PowerShell.exe -NoProfile -NoLogo -NonInteractive -Command "New-Item -ItemType File -Force '${winDest}'"
    else
        local command="[IO.File]::WriteAllBytes('${winDest}', \$([System.Convert]::FromBase64String('${contents}')))"
        PowerShell.exe -NoProfile -NoLogo -NonInteractive -Command "${command}"
    fi
}

### Docker CLI plugins

The bundle ships Docker CLI plugins (`buildx`, `compose`, …) in a `docker-cli-plugins` directory beside its `bin` directory.
In developer mode, running from a checkout, `rdd` instead reads them from the checkout's `resources/<goos>/docker-cli-plugins` (`yarn`'s postinstall download target), rather than from a packaged bundle.
Docker never discovers plugins via `PATH`.
It searches the directories listed in `cliPluginsExtraDirs` in `~/.docker/config.json` first, then `~/.docker/cli-plugins`, then its system plugin directories.
So the daemon mirrors the bundled plugins into a per-instance directory (`~/.rd2/docker-cli-plugins`) and registers that directory in `cliPluginsExtraDirs`.

This registration is driven by [`spec.application.addPath`](#app-object), the same setting that manages `PATH`: `front`/`back` add the directory (prepended or appended), and `manual` removes it. Because `config.json`'s array has no fence to mark our entry (just like the Windows `Path`), the controller keeps a separate marker file in the short directory so, under `manual`, it only removes an entry it added and leaves a user-added one alone. Both the engine controller (which edits `currentContext`) and this one serialize their `config.json` read-modify-writes behind a cross-process lock so neither drops the other's edit. Docker searches every `cliPluginsExtraDirs` entry before `~/.docker/cli-plugins`, so even under `back` our plugins win over the user's own copies there; `back` yields only to other tools' entries in `cliPluginsExtraDirs`.
