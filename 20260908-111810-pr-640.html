rdd/docs/design/api_containers.md
namespaces are not supported and we always use `moby` as the value for that label.

For the `*Request` resources, they use the `Settled` and `Failed` conditions to
express state.  `Settled` will become `True` when the request object has reached
a terminal state (it will not produce any more actions).  Once a request object
has reached such a terminal state, unless it has an owning reference set, it
will be automatically removed after some timeout.  This will be at least one
minute (so the caller can read any data), but the precise timing is unspecified.
If the `Settled` condition is set to `True` but it is not successful, then the
`Failed` condition will exist and set to `True`, with the reason and message
describing what the error is.

Fix: say that an ownerless request is deleted after a delay, and that one with owner references is retained for its owner to inspect.

Design Observations ¶

Concerns ¶

Throttling the writes also sets the reconcile rate (in-scope) Claude Opus 5. The 100 ms ticker caps status writes at ten per second per pull, which round 2 credited as the fix for its I5. Each of those writes is also an update event on Watches(&containersv1alpha1.ImagePullRequest{}, …) (engine_reconciler.go:251), so the same throttle governs reconciles too. Each is cheap (a cache read, then the early return at image_pull_request_reconciler.go:196), and the bulk path at lines 124-133 starts every pending request at once with no concurrency bound.

reconcileImagePullRequestTerminalReason deletes the state entry on a path where it changed nothing (future) Claude Opus 5. When state.desiredReason is the zero value the closure returns nil at lines 401-404, and the caller reads err == nil as "applied" and deletes the map entry at lines 437-441, dropping whatever cancel a concurrently-started pull had installed. Unreachable today: MaxConcurrentReconciles is 1 and the only other caller is the completion goroutine, which starts no pull. The invariant is unwritten, and correctness depends on it.

spec.namespace has no consumer below the API (future) Gemini 3.1 Pro Gemini 3.5 Flash. Both Gemini models raised this as the pullImage signature gap: engine_reconciler.go:102 takes only a repo tag, so a containerd implementation has nowhere to put the namespace. Docker has one global image store, so nothing breaks now. Round 2 filed the same concern from the CRD side; I1 is the client-facing consequence.

Strengths ¶

The sentinel is the right shape for the completion signal Claude Opus 5 Codex GPT 5.6 Sol Gemini 3.1 Pro Gemini 3.5 Flash. Replacing the shared progressError with errPullSucceeded in the context cause turns mutable shared state into an immutable value with a guaranteed happens-before edge, and because progressCtx is a child of pullContext the single context.Cause(progressCtx) read subsumes both cancellation sources. A late onComplete(nil) after a parent cancel cannot flip the verdict back to success, because the cause is already fixed.

Terminal reason as queued intent, applied separately Claude Opus 5 Codex GPT 5.6 Sol. setImagePullRequestTerminalReason records what should happen and reconcileImagePullRequestTerminalReason applies it, which makes the completion goroutine and the reconciler idempotent against each other and lets a failed status write self-heal on the next reconcile instead of losing the outcome.

The UID-mismatch path cleans up without writing Codex GPT 5.6 Sol. When the object is deleted and recreated mid-pull, the completion goroutine runs on a cancelled context, but the UID check at image_pull_request_reconciler.go:393 returns before any status update and the stale state entry is removed. Verified by probe; see the retro's reconciliation note.

Review Process Notes ¶

Skill improvements ¶

  • [ ] When an agent's own review reports running a build, generate, or format step against the worktree, re-run that step with the toolchain the project pins (the go/node/python version in its manifest) before accepting a "generated files are stale" or "verification fails" finding. Generators embed their toolchain's version in their output, so a newer local toolchain produces drift in files the change never touched, and that drift is indistinguishable in a diff from a missed regeneration.
  • [ ] Before recording a reviewer's claim that a cancelled context caused a write to fail, check whether the client in that path reads through a cache. A cached read that discards its context returns a valid object where the reviewer assumed an error, which usually moves the failure to a later line or removes it entirely. The symptom the reviewer describes is often real on a different trigger they did not examine.
  • [ ] Treat an agent that runs the project's own CLI, service, or daemon binaries as having acted outside its worktree, whatever its review says. A worktree left clean by git restore proves nothing about state the binary owns elsewhere on the machine. Check for such invocations in the agent's transcript, not only for a dirty worktree, and record them in the retro.

Repo context updates ¶

  • [ ] [repo] make verify-generate passes only under the Go toolchain rdd/go.mod pins. Run it as GOTOOLCHAIN=go1.26.0 make verify-generate; a newer toolchain's applyconfiguration-gen inserts blank // lines into every generated applyconfiguration/ file, which looks exactly like a missed regeneration. Do not report generated-code drift without re-running under the pinned toolchain first.
  • [ ] [repo] ContainerNamespace/moby exists only while the engine watcher is connected: the watcher's full sync applies it, and cleanupMirrorResources deletes it on app stop along with the Container, Image and Volume mirrors. Any webhook or controller that requires the object to exist is unreachable for the whole VM-boot window and after every stop, so treat a validation rule keyed on it as a client-facing failure mode, not a safety check.
  • [ ] [repo] controller-runtime's cached client discards the context on Get (CacheReader.Get takes it as _), while Status().Update fails immediately on a cancelled context. A goroutine that runs on past cancellation therefore reads a valid object and only then fails to write, so reason about where a cancelled-context path actually stops rather than assuming the first API call errors.
  • [ ] [repo] The rdd engine reconciler is registered with builder.TypedControllerManagedBy[engineRequest] and no .For(...), so controller-runtime's default log constructor adds neither kind nor object name to any line this controller emits. Log sites in that package must include namespace and name themselves; a bare logf.FromContext(ctx).Error(...) there is unattributable, and so is any error returned from Reconcile.
