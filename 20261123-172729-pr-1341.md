## Design Observations

### Concerns

- **(in-scope)** When a hidden first window's page fails to load, the splash keeps spinning until the user quits (`window/index.ts:96-98`), and the maintainers haven't ruled on whether that should change. On macOS the dock icon can quit the app. On Windows and Linux the splash is frameless and RD2 doesn't show a tray yet (`background.ts:168`), so the user can only close the splash, from the taskbar or with Alt+F4. That leaves the app running with no visible window (reasoned, not run). The reviewers raised two alternatives: close the splash, which leaves the screen empty as at the merge-base, or show an error box, which is #463's unfinished half. [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]

**Outcome:** addressed in #1349, which is stacked on this PR. #1349 makes the app hide the splash, show an error box and quit when the first window's page fails to load.

### Strengths

- **(in-scope)** `hideSplash()` and `closeSplash()` divide along the measured `window-all-closed` behaviour, and `splash.ts:126-131` gives the reason. [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]
- **(in-scope)** `openSplash()` runs before the startup `try` (`background.ts:107`), so its own try/catch keeps a failed `BrowserWindow` constructor from stopping startup. [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]
- **(in-scope)** The theme listener looks up the current main window, and calling `off` before `on` keeps one listener across reopens, as `updateViewBackground` already does. [Codex GPT 6 Astra, Claude Opus 5.5]
- **(in-scope)** `index.spec.ts` pins each trigger on a visible first window and both exclusions (a sub-frame failure, a hidden window's failure). Claude deleted three of them one at a time (the sub-frame guard, the crash trigger and the `closed` listener), and each deletion failed one test. [Claude Opus 5.5]

###### Design Observations

###### Concerns

- **Indefinite splash spinner on hidden first window load failure** `(in-scope)`: In `window/index.ts:98-106`, when `options.show === false` (used by modal dialogs such as FirstRun), `did-fail-load` is intentionally not handled so that the splash stays on screen. However, because the modal dialog page never sends `dialog/ready` when it fails to load, the dialog remains hidden forever while the frameless, unclosable splash spinner runs indefinitely. Showing an error box (such as `showErrorDialog`) on load failure would hide the splash and inform the user why the app failed to start.

###### Strengths

- **Graceful fallback in `openSplash()`**: Wrapping the `BrowserWindow` constructor in a try/catch prevents display or compositor initialization errors from halting the application startup.
- **Renderer crash hook (`render-process-gone`)**: Ending startup on `render-process-gone` for visible windows ensures a crashed main window is visible to the user rather than hidden behind the splash.
- **Splash hiding before native error dialogs**: Calling `hideSplash()` instead of `closeSplash()` preserves macOS application activation and Dock state, preventing error dialogs from opening in the background.
