## Executive Summary

The round-2 fixes hold. Every refusal reproduces against real images, and both backends agree on the payload this tool writes. Two defects remain. The tarball backend accepts a file where the overlay just created a directory, exits 0, and emits an archive `tar` cannot extract, while the image backend refuses the same manifest. And the default in-place tar path has no test that the overlay reaches the distro at all.

Codex GPT 5.6 Sol and Claude Opus 5 found the tarball defect independently, from opposite ends: Codex through a CLI probe, Claude by reading the guard against its own rationale. Codex raised the in-place test gap as a finding, and Claude found its permission half in its own Testing Assessment. Both Geminis returned clean. The consolidator reproduced every finding below, found that the collision runs in both directions, and widened the fix accordingly.

## Important Issues

I1. **A file where the overlay just made a directory produces a tarball nobody can extract** — `rdd/pkg/overlay/tar.go:184` [Codex GPT 5.6 Sol, Claude Opus 5]

```go
// checkNotBaseDir refuses to put a file or symlink where the base has a
// directory, since the base entries under it would stay in the tar, orphaned.
func (t *tarDistro) checkNotBaseDir(p string) error {
	if t.base[tarClean(p)] == tar.TypeDir {
		return fmt.Errorf("%s is a directory in the base", p)
	}
	return nil
}
```

The rationale in the comment covers any directory, but the check reads only `t.base`. A directory `plannedDirs` created earlier is invisible to it, so a file entry naming a path a tree copy walks as a directory passes, and the archive ends up with both `etc/app/sub/` and `etc/app/sub`. The collision runs both ways. Writing a file first, then an entry whose parent chain names it, emits the pair in the other order through `EnsureDir`. The image backend refuses both, so "one manifest drives both forms" (`README.md:75`) does not hold.

## Suggestions

S1. **The source containment check misses a symlink in any parent component** — `rdd/pkg/overlay/overlay.go:265` [Codex GPT 5.6 Sol]

```go
	if info, err := os.Lstat(srcPath); err != nil {
		return fmt.Errorf("opening source for %s: %w", dest, err)
	} else if info.Mode()&os.ModeSymlink != 0 {
		return fmt.Errorf("%s: a source may not be a symlink; add symlinks as symlink entries", srcPath)
	}
```

`Lstat` sees only the final component, so `source: escape/secret` with `escape` a symlink out of the source directory passes the guard and `os.Open` follows it. `manifest.go:133` promises the source is "within the source directory"; this is the half that enforces it. Measured: a source directory holding `escape -> ../outside` packaged `outside/secret` as `HOST SECRET`, exit 0. `walkTree` has the same gap at its root. The manifest and the source tree are both in-repo and author-controlled, and the real asset tree holds no symlinks, so nothing is exposed today.

Fix: resolve each candidate against a canonicalized source root with `filepath.EvalSymlinks` and reject any result outside it.

S2. **The `--output` cleanup fires when the tool has written nothing, and not when it has** — `rdd/cmd/distro-overlay/main.go:96-98` [Claude Opus 5, Codex GPT 5.6 Sol]

```go
		if err := copyTo(input, output); err != nil {
			return emptyOutput(output, err)
		}
```

`README.md:16` says a failed run empties the output, and the tool gets it wrong at both ends. `copyTo` fails at its own `os.Open(input)`, so an unreadable distro truncates an `--output` the tool never wrote to: measured, a pre-existing 19-byte output came back at 0 bytes while the error named the input. In the other direction, a failure before either format path, from `LoadManifest` or `detectFormat`, returns without any cleanup: measured, a malformed manifest exited 1 and left a 5-byte output untouched. The tar path has no early window, since it opens the input before creating the output.

Fix: open the input before `copyTo` on the raw path, and move the cleanup to one place in `run` that covers manifest loading and format detection.

S3. **A fifo or device source hangs the tool with no output** — `rdd/pkg/overlay/overlay.go:265` [Claude Opus 5]

The guard above tests `ModeSymlink` alone, although it already holds the whole `FileInfo`. `walkTree` rejects every non-regular member at `overlay.go:240-242`, so a tree copy is safe, but a plain file entry naming a fifo reaches `os.Open` and blocks with nothing printed and no timeout. Measured: `timeout 10 distro-overlay ... --format tar` exited 124. A directory source fails loudly instead, so only fifos and device nodes hang. `manifest.example.yaml` tells the reader that sockets, fifos and device nodes are rejected, which is the behavior this guard is one word away from.

Fix: test `!info.Mode().IsRegular()` and name the offending type in the message.

S4. **The two backends give a symlink different owners** — `rdd/pkg/overlay/tar.go:171` [Claude Opus 5]

```go
	return t.tw.WriteHeader(&tar.Header{
		Typeflag: tar.TypeSymlink,
		Name:     tarClean(link),
		Linkname: target,
		Mode:     0o777,
		Uid:      uid,
		Gid:      gid,
		ModTime:  mtime,
```

Validation now forces a symlink entry's uid and gid to 0 (`manifest.go:125-127`), so the tarball always stamps `root:root`. The image backend ignores them by signature (`image.go:235`) and go-diskfs gives the new link its parent directory's owner (`ext4.go:985`: `owner: parentInode.owner`). A symlink inside a `uid: 472` directory therefore comes out root-owned in the tarball and 472-owned in the image. `manifest.example.yaml` documents only the image half. This is the residual of round 1's S2 and S4. The fix removed the knob and left the divergence.

Fix: document both halves in `manifest.example.yaml`, or drop the now-always-zero `uid, gid` parameters from `Distro.Symlink`.

S5. **The raw `--output` copy inflates a sparse image to its full size** — `rdd/cmd/distro-overlay/main.go:147-151` [Codex GPT 5.6 Sol]

```go
	out, err := os.Create(dst)
	if err != nil {
		return err
	}
	if _, err := io.Copy(out, in); err != nil {
```

`io.Copy` writes every zero range, which undoes the sparseness `pkg/xz/xz.go` goes out of its way to produce. Its `sparseWriter` skips each zero block and punches a hole, because "writing every byte would allocate a disk image's free space along with its data". The distro image is mostly reserved free space, so the copy is exactly the case that comment describes. Codex measured a 64 MiB sparse file going from 16 KiB allocated to 64 MiB on APFS. Nothing calls the tool yet, so this costs disk in no build today.

Fix: reuse the xz sparse writer for the copy, or clone the file where the platform supports it and fall back to a zero-skipping copy.

S6. **`Apply` and `ApplyTar` never validate the manifest** — `rdd/pkg/overlay/overlay.go:45` [Claude Opus 5]

Round 2 added the duplicate-path, uid-range and symlink-owner rules, and all three run only in `LoadManifest` (`manifest.go:69`). Both `Apply` and `ApplyTar` are exported from a package whose purpose is that the two backends behave alike, and `ownedByTree`'s comment already concedes the gap: "Apply also runs on manifests that never went through validate". Today `cmd/distro-overlay` is the only caller and it goes through `LoadManifest`, so nothing is broken; the next caller inherits the divergence these rules exist to prevent.

Fix: call `m.validate()` at the top of both entry points, or state the precondition in both doc comments.

S7. **`checkGroupsInitialized` performs a second, unrelated refusal** — `rdd/pkg/overlay/image.go:129` [Claude Opus 5]

The name and the first line of the doc comment describe the `BLOCK_UNINIT` check, but the function also rejects a filesystem without the 64bit feature, which has nothing to do with group initialization. That test guards `groupdescriptors.go:264`, where go-diskfs slices 64 bytes out of a 32-byte descriptor on every write. `README.md:66-73` presents them correctly as two kinds of refused image, so only the code disagrees with itself.

Fix: rename the function to cover both, or split the 64bit test out, and extend the doc comment.

S8. **The README's remedy for a full image leads into a refusal it does not mention** — `rdd/cmd/distro-overlay/README.md:32` [Claude Opus 5]

Line 32 tells a builder whose overlay does not fit to "raise the reserve and rebuild". Lines 66-73 then explain that `mke2fs` leaves a `BLOCK_UNINIT` group "in any filesystem from about 768 MiB up", which the tool refuses, and offer only that "the fix belongs in the distro build". Following the first instruction past 768 MiB therefore produces an image the tool will not open, with no named way out. Claude measured the escape routes at 768 MiB: neither `-O ^uninit_bg` nor `-E lazy_itable_init=0` suppresses the group, and only dropping `metadata_csum` clears it, which this image cannot do.

Fix: say in the `BLOCK_UNINIT` paragraph that no `mke2fs` option avoids it on a `metadata_csum` filesystem, and name the lever that does work.

S9. **The `e2fsprogs` test helper is duplicated byte for byte across two packages** — `rdd/pkg/overlay/overlay_test.go:688-705` [Claude Opus 5]

`cmd/distro-overlay/main_test.go:279-296` is identical to it (`diff` of the two ranges reports no difference). The `RDD_REQUIRE_E2FSPROGS` contract that stops CI from silently skipping the e2fsck-backed tests is in both copies, so a change to it has to be made twice and can be made inconsistently. `rdd/pkg` has no shared test-helper package today, so the fix costs a new one.

Fix: leave it until a third caller appears, but as a decision rather than an accident.

S10. **`sortedKeys` hand-rolls `slices.Sorted(maps.Keys(...))`** — `rdd/pkg/overlay/overlay.go:190` [Claude Opus 5]

`rdd/go.mod` declares `go 1.27.0` and the repo already uses the idiom in `cmd/rdd/service_paths.go:64` and two other places, so the whole function is one line. The hard-link scan at `tar.go:63-72` builds and sorts a slice only to report its first element, which the same idiom reduces to iterating in order and returning on the first hit.

## Design Observations

### Concerns

- **The two backends share a manifest but not a refusal set, and nothing enforces the overlap** (in-scope) [Claude Opus 5, Consolidator]. `Distro` gives the implementations one interface, but each guard lives inside one of them: the image refuses hard links, holes, shrinks, symlink replacement and htree parents; the tarball refuses hard links and base directories. I1 and S4 are both instances of the shape. A table of manifests applied to both backends, asserting the same accept-or-reject verdict from each, would have caught I1 in both directions before any reviewer probed for it.
- **`Distro.WriteFile` takes an `io.Reader` that both implementations immediately drain** (future) [Claude Opus 5]. `image.go:198` and `tar.go:143` both call `io.ReadAll`. The image backend needs the whole buffer, since one `Write` is what keeps a file to a single extent, but the reader hides from every call site that nothing streams and that a large asset is held in memory twice.
- **Check every entry before writing any** (future) [Claude Opus 5, round 1]. Round 1 raised this and the round-2 refusals make it sharper: `Apply` still interleaves refusals with writes, so a manifest with three conflicting entries takes three runs to clean up. Carried forward unaddressed, and now in its second round.

### Strengths

- Every refusal names the go-diskfs defect that motivates it, in a comment beside the check. Each one the reviewers traced was accurate at v1.9.4, which is what let this round verify the delta instead of re-deriving it [Claude Opus 5].
- `ownedByTree` (`overlay.go:177-186`) makes nested-tree ownership order-independent in six lines, and `overridePaths` reuses the same predicate, so the tarball drops exactly the base paths the overlay rewrites [Claude Opus 5, Codex GPT 5.6 Sol].
- Closing the distro from a `defer` in `Apply` fixes the Windows deletion failure at the one place both backends pass through, rather than at each call site [Gemini 3.1 Pro, Gemini 3.5 Flash].
- `TestImageWritesPassFsck` and `TestImageRefusesIndexedDirectory` validate with `e2fsck`, the only oracle that checks the `metadata_csum` checksums go-diskfs's own reader skips, and `RDD_REQUIRE_E2FSPROGS` stops them skipping silently in CI [Claude Opus 5].

## Acknowledged Limitations

Each round-1 limitation was re-checked this round rather than inherited.

- **ctime**: confirmed, with a correction to the mechanism. `Chtimes`'s third argument becomes ext4's crtime, not the inode change time, which go-diskfs writes only from `time.Now()` at creation. So `setMeta` cannot set it and the raw image is not bit-reproducible, exactly as recorded. Held not to matter while rdd embeds the image.

## Review Process Notes

**Skill improvements**

- When a change adds a guard whose stated rationale is broader than its implementation, test the rationale rather than the code. A comment that says "where the base has a directory" while the code reads one map is a complete specification of the missing case, and one reproducer reaches it.
- When two implementations share one interface and each has its own validation, enumerate the guards on both sides and diff the sets before reviewing either. A rule one side enforces and the other does not is invisible in a diff that touches both, and it produces a defect whose severity depends on which implementation the user reaches.
- When a finding proposes a fix, apply it and re-run the reproducer in the direction the finding did not consider. A patch that makes the supplied reproducer pass can still leave the mechanism live from the other side, and the author will take a verified-looking patch at face value.

## Design Observations

### Concerns

**The two backends share a manifest but not a refusal set, and nothing enforces the overlap** *(future)*. `Distro` gives the two implementations one interface, but the guards live inside each one: the image refuses hard links, holes, shrinks, symlink replacement and htree parents; the tarball refuses hard links and base directories. I1 and S2 are both instances of the same shape — a rule one backend enforces and the other does not, discovered only by reading both. A table-driven test that applies one manifest corpus to both backends and asserts *the same* accept/reject verdict would turn each divergence into a failing case instead of a reviewer's grep. My probe does this by hand for one manifest and found the symlink-owner split immediately; as a test it would have caught I1 as well.

**`Distro.WriteFile` takes an `io.Reader` that both implementations immediately drain** *(future)*. `image.go:198` and `tar.go:143` both call `io.ReadAll`. The image backend genuinely needs the whole buffer — one `Write` is what keeps a file to a single extent (`image.go:194-196`) — but the tar backend needs only the size up front, and the reader abstraction hides that neither streams. Taking `[]byte` (or a `*os.File` plus size) would make the memory cost of a large asset visible at the call site rather than at two `ReadAll`s.

### Strengths

- Every refusal carries the go-diskfs defect that motivates it in a comment next to the check, and each one I traced was accurate at the pinned version. That is what let this review verify the delta instead of re-deriving it.
- `ownedByTree` (`overlay.go:177-186`) makes nested-tree ownership order-independent with six lines and no bookkeeping, and `overridePaths` reuses the same predicate so the tarball drops exactly the base paths the overlay rewrites.
- Closing the distro from a `defer` in `Apply` (`overlay.go:46-50`) fixes the Windows deletion failure at the one place both backends pass through, rather than at each call site.
- `TestImageWritesPassFsck` and `TestImageRefusesIndexedDirectory` validate with `e2fsck`, which checks the `metadata_csum` checksums go-diskfs's own reader skips — the only oracle that could have caught the bug this PR's second commit fixes.

#### S1. Platform-dependent limit on UIDs and GIDs due to `int` representation — `rdd/pkg/overlay/manifest.go:50-51` (suggestion, gap)

```go
	// UID and GID own the entry; both default to 0 (root).
	UID int `json:"uid,omitempty"`
	GID int `json:"gid,omitempty"`
```

The fields `UID` and `GID` in the `Entry` struct are represented as standard `int` types, which are platform-dependent (32-bit vs 64-bit). In Linux and ext4, UIDs and GIDs are unsigned 32-bit integers (`uint32`), which can range from `0` to `4294967295`. On a 32-bit build host, Go's `int` is signed 32-bit with a maximum value of `2147483647`. Thus, any UID or GID larger than `2147483647` would cause parsing/overflow failures during manifest unmarshaling on 32-bit systems, despite being valid under the `maxID` check.

Fix: Represent `UID` and `GID` as `uint32` (or `int64`) to ensure absolute platform independence and align precisely with the underlying ext4 and Linux standards.

```diff
type Entry struct {
...
-	UID int `json:"uid,omitempty"`
-	GID int `json:"gid,omitempty"`
+	UID uint32 `json:"uid,omitempty"`
+	GID uint32 `json:"gid,omitempty"`
```
*(Note: If changed, signatures receiving these variables in the `Distro` interface should also be updated to accept `uint32` or converted accordingly.)*
