## Executive Summary

distro-overlay handles the common case: representative overlays onto clones of the real v0.2.8 image pass e2fsck. Five Important defects remain, each with a verified patch. Overriding a hard-linked file rewrites every name on its inode. A failed `Apply` leaves the image open, which turns the Windows unit-test job red. A refused raw write leaves the input corrupt, and `--output` is ignored for raw. Nested trees depend on manifest order. `--output` naming the input empties the tarball.

Claude Opus 5 raised four of the five Important findings and every Suggestion, and probed each on a clone of the real image. Codex GPT 5.6 Sol was stopped by its provider's content filter partway through; the two defects its log shows it had formed carry its name. The consolidator found the nested-tree defect, ran every reproducer below against `b8d01e24e`, and checked each patch against its probe, the test suite, and golangci-lint, singly and all five together.

`WriteFile` rewrites an existing file's inode in place (line 130), and `checkOverride` never reads `st.Nlink`, so every other name on that inode gets the new bytes while the tool exits 0 and e2fsck stays clean. A walk of v0.2.8 found 141 hard-linked regular files, none under `/etc` or `/usr/local`. Busybox alone has 125 names in `/usr/bin` and `/usr/sbin`, and Claude showed that replacing `/usr/bin/which` rewrites `/usr/bin/patch`.

The tarball backend drops the overridden entry (`tar.go:44-46`), so later `TypeLink` entries naming it point at a missing file and extraction fails. The WSL tarball holds 1,299 hard links.

```go repro
// danglingLinks lists the TypeLink entries whose target no earlier entry names.
func danglingLinks(t *testing.T, data []byte) []string {
	seen, dangling := map[string]bool{}, []string{}
	tr := tar.NewReader(bytes.NewReader(data))
	for {
		hdr, err := tr.Next()
		if errors.Is(err, io.EOF) {
			return dangling
		}
		assert.NilError(t, err)
		if hdr.Typeflag == tar.TypeLink && !seen[hdr.Linkname] {
			dangling = append(dangling, hdr.Name+" -> "+hdr.Linkname)
		}
		seen[hdr.Name] = true
	}
}
```

The raw path hands `<distro>` itself to `OpenImage` and never reads `output`. `--output new.raw d.raw` exits 0, modifies `d.raw`, and creates no `new.raw`.

The extent-tree refusal (`image.go:148-151`) fires after go-diskfs has written the unchecksummed tree block, so it leaves the input corrupt (Claude reproduced this on v0.2.8 with a 130 MiB file), and any other refusal leaves the earlier entries written. No test reaches it: with lines 148-151 deleted, the suite stays green.

`README.md:36-37` promises that the tool "refuses them instead of producing a broken image".

## Suggestions

S1. **The refusals miss two go-diskfs defects that corrupt silently; the v0.2.8 image happens to avoid both** — `rdd/pkg/overlay/image.go:240-241` [Claude Opus 5, Consolidator]

```go
	data := (info.Size() + i.blockSize - 1) / i.blockSize * i.blockSize
	return int64(st.Blocks)*unit > data
```

A destination with holes passes `checkOverride`, which tests only for extra blocks, and go-diskfs then starts the write before the file's first block. On an mke2fs image, overriding a file with a 16-block leading hole put 61,444 bytes of the new contents inside a neighbouring file while `Apply` returned nil.

go-diskfs also never clears a group's `BLOCK_UNINIT` flag when it allocates there, so e2fsck (exit 4 in Claude's probe) and the kernel still count those blocks free.

v0.2.8 has neither: no sparse file among the 3,585 walked, and none of its 12 groups is `BLOCK_UNINIT`. Check the reserved image too.

Fix: refuse destinations whose blocks fall short of their size, and images with a `BLOCK_UNINIT` group, or state both preconditions in the README.

S2. **A symlink entry at an existing image path fails, and the image ignores a symlink's uid and gid** — `rdd/pkg/overlay/image.go:155-162` [Claude Opus 5, Gemini 3.5 Flash, Consolidator]

```go
func (i *imageDistro) Symlink(link, target string, _, _ int, mtime time.Time) error {
	r := rel(link)
	if err := i.checkParentIndex(r); err != nil {
		return err
	}
	if err := i.fs.Symlink(target, r); err != nil {
		return err
	}
```

go-diskfs's `Symlink` refuses a name that exists, so replacing a base symlink (a systemd `.wants` link, say) fails on the raw image after the earlier entries were written, while the tarball replaces it. The README's four raw-image limits and the example's "Overwrites win" leave this case out.

The image also gives a new link its parent directory's owner, since `Chown` would follow the link, while the tarball writes the entry's `uid`/`gid`. In a probe the same entry came out 7:7 in the image and 5:5 in the tar. `Entry.validate` accepts `uid` on a symlink without comment. Flash's design note puts the image's default at 0:0; it is the parent's owner.

Fix: stat the path first and refuse with a message naming the limit, list it in the README, and either reject `uid`/`gid` on symlink entries or document that the image ignores them.

S3. **The "raise the reserve" advice cannot help a file over about 127 MiB** — `rdd/cmd/distro-overlay/README.md:39-44` [Claude Opus 5]

```markdown
- **Files needing an extent tree.** go-diskfs writes extent-tree blocks without
  their `metadata_csum` checksum. The tool writes each file in one piece, which
  gets it a single extent when the image has a contiguous free run at least as
  large as the file. Otherwise go-diskfs splits the file across several runs,
  and if the file then needs a tree, the tool fails and asks for a larger
  reserve.
```

go-diskfs gives a file one extent only when one free run inside a single block group holds it, at most 32,768 blocks. A larger file goes to a fallback allocator that takes every free run in group 0 first. v0.2.8's group 0 has four, so any such file needs a fifth extent and a tree, however large the reserve. The largest single-group run in v0.2.8 is 32,594 blocks, 127.3 MiB (`dumpe2fs`).

The error at `image.go:149-150` sends the user to the reserve as well.

Fix: state the per-file limit (one block group, 128 MiB at 4 KiB blocks) in the README and the error, and word the error differently for a file larger than a group.

S4. **Manifest validation lets the backends diverge** — `rdd/pkg/overlay/manifest.go:112-114` [Claude Opus 5, Gemini 3.5 Flash, Consolidator]

## Design Observations

### Concerns

- **Check every entry before writing any** (in-scope) [Claude Opus 5]. `Apply` interleaves refusals with writes, so the user learns of one conflicting entry per run. The htree, symlink, shrink and hard-link refusals depend only on the base image, so a first pass could stat every destination and its parent and report them all at once. With I3's copy the input survives a refusal either way.
- **go-diskfs defects keep surfacing** (future) [Claude Opus 5]. The PR works around four; this review found hard links, holes, `BLOCK_UNINIT` groups, and one more: `inode.toBytes` zero-fills everything past offset 0x98, so every inode go-diskfs rewrites loses its in-inode xattrs. That covers each file written and each directory that gains an entry or gets metadata; v0.2.8 directories carry none. Claude suggests a backend that drives e2fsprogs' `debugfs -w`, which handles all of these and can set ctime, making the image reproducible. ## Review Process Notes

**Skill improvements**

- Broaden the comment-claim rule in `instructions.md`: a comment or doc that claims a property for every input ("in any order", "never duplicated", "always wins") needs the inputs its tests skip, such as two instances of the same kind that overlap or the same key twice, built and run before the claim is credited. Tests encode the pairing the author had in mind, and a reviewer who reads them inherits the same blind spot.
- Add a dimension for in-place writes: when code writes into an existing object instead of replacing it (a file's inode, a record, an output path that may equal the input), list everything else that refers to that object (hard links, aliases, the caller's own input stream) and check that each still sees the intended content. S3. **The "raise the distro's free-space reserve" advice cannot help a file over 128 MiB** — `rdd/cmd/distro-overlay/README.md:39-44` (suggestion, gap)


go-diskfs only gives a file a single extent when it fits in 32768 blocks (`maxBlocksPerExtent`, ext4.go:46, used at 2209) and inside one free run within a single block group. ### Design Observations

**Concerns**

- **Validate before writing** (in-scope). `Apply` interleaves checks with writes (`overlay.go:52-83`). The htree, symlink, shrink and hard-link refusals depend only on the image as it was before the overlay. A first pass could `Stat` every destination and its parent before any write. Combined with I2's copy, every refusal except the allocator-dependent extent-tree one would then leave the input untouched. The user would also get every conflicting entry in one error instead of only the first.
- **Growing list of go-diskfs workarounds** (future). This PR works around four go-diskfs defects. This review found four more: hard links, `BLOCK_UNINIT` groups, sparse destinations, and in-inode xattrs. On the last: `inode.toBytes` (inode.go:402) zero-fills the inode from offset 0x98 on, so every existing inode the tool rewrites loses its in-inode xattrs. That covers each parent directory that gains an entry and each directory given metadata. v0.2.8 directories carry no xattrs, so nothing is lost today.

  An alternative backend: generate a script for e2fsprogs' `debugfs -w` (`mkdir`, `write`, `symlink`, `unlink`, and `set_inode_field` for uid, gid, mode, mtime and ctime). It goes through libext2fs, which handles htree directories, checksummed extent trees, uninitialized groups and hard links. Setting ctime would also make the raw image bit-reproducible, which removes the acknowledged ctime limitation. The cost is an e2fsprogs dependency on macOS and Linux build hosts; CI already installs it for the tests.
- **File capabilities are lost on replacement** (future). Replacing a file drops its file capabilities in both backends. I verified that `/usr/bin/newuidmap` loses its `security.capability` xattr in the raw image, and the tar entry carries no xattrs. If the overlay ever replaces such a binary, the manifest will need a capability field.

**Strengths**

- One `Distro` interface drives both backends, and `plannedDirs` settles directory ownership before any write. An explicit entry therefore overrides a tree in any manifest order, and both backends test both orders.
- The e2fsck-backed tests, together with `RDD_REQUIRE_E2FSPROGS` in CI, cannot skip silently on Linux or macOS. On a clone of the real v0.2.8 image, `e2fsck -fn` passes after a representative overlay: a 40 MiB binary, a tree, a short and an 89-character symlink, and a directory owned by uid 472. ### Design Observations

#### Concerns

*   **Asymmetrical symlink ownership support across backends:**
    The `tarDistro` backend correctly writes the `UID` and `GID` specified in the manifest for symlinks (`tar.go:102`). However, the `imageDistro` backend ignores the ownership fields and leaves them at the go-diskfs default (`0:0` root) because calling `Chown` on a symlink follows it to its target in go-diskfs (`image.go:164`). While this is documented in comments and is an upstream limitation, this silent divergence between backends is worth noting.

#### Strengths

*   **Platform-independent file permissions:**
    By ignoring host permissions for tree members and using static file/directory modes (`treeFileMode`/`treeDirMode`), the tool guarantees reproducible and clean file modes regardless of whether the build runs on a Windows, macOS, or Linux host.
*   **Checksum/HTree/Truncate safety checks:**
    The thorough and precise validation guards (e.g. `checkParentIndex`, `checkOverride`, `hasExtentTree`) are exceptionally well-engineered. They prevent silent ext4 filesystem corruption or half-written file states by loudly rejecting unsupported go-diskfs writes.

### Acknowledged Limitations

*   **Non-reproducible raw images:**
    The raw ext4 image is not bit-reproducible because `go-diskfs` updates each inode's change time (`ctime`) to the current time, which cannot be overridden without upstream changes. This is documented as a known, accepted limitation in the PR.
*   **go-diskfs write limitations (refusal guards):**
    `imageDistro` refuses to shrink files, overwrite symlinks, add to htree-indexed directories, or write files requiring extent trees. These limitations are intentionally enforced to dodge go-diskfs bugs that would otherwise silently corrupt the filesystem.
*   **Host symlink limits on Windows:**
    Trees copied via `dir` source cannot contain symlinks because Windows checkouts can turn symlinks into plain files. Symlinks must be listed explicitly as `symlink` entries.
*   **No automated partition resizing:**
    The ext4 partition size is static and filled in-place. If the overlay exceeds the reserved space, the tool reports `ENOSPC`.
