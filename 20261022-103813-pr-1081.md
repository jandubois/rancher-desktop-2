## Executive Summary

PR #1081 adds an `unset` value for `spec.application.addPath`, makes it the default, blocks a return to it with a CEL rule, and has `rdd set` write `manual` for CLI-created Apps. The Go, CRD and CEL work matches issue #1052 and behaves as documented against a real API server. Three gaps remain. The TypeScript client was not regenerated, so CI's `Verify generated files` fails. Several docs still call `manual` the default, and no test covers an existing `unset` App.

## Suggestions

S1. **`rdd set` decides the pin from a read that its patch does not condition on** — `rdd/cmd/rdd/set.go:462` [Claude Opus 5.5]

```go
	if err := c.Patch(ctx, app, client.RawPatch(types.MergePatchType, patchBytes), opts...); err != nil {
```

The pin depends on the `Get` at line 300, but `patchApp` sends an unconditional merge patch with no `resourceVersion`. If the first-run dialog writes `front` between the two calls, `rdd set` overwrites it with `manual`, which the CEL rule allows. The `AlreadyExists` branch (lines 381-387) re-reads the App but reuses the `specMap` built for a missing App, so it pins `manual` over whatever the concurrent creator stored. Hitting either window takes the GUI and the CLI writing the App within milliseconds of each other.

Fix: when the pin is added, send the `Get`'s `resourceVersion` with the patch and retry on conflict, recomputing the pin after each read.

## Design Observations

### Concerns

- **`rdd stop` pins `manual` too** (in-scope) [Claude Opus 5.5]: the pin is in `setAction`, which `rdd start`, `rdd stop` and `rdd run` all call (`rdd/cmd/rdd/app.go:43`, `rdd/cmd/rdd/app.go:105`, `rdd/cmd/rdd/run.go:110`). Issue #1052 covers instances started from the CLI. But `rdd stop` against a GUI-created App whose dialog was never answered also writes `manual`, and the dialog then never returns. Passing the pin as a `setAction` option that `stopAction` leaves off would make each command's behavior visible at its call site. Whether `rdd stop` should pin at all is a design decision, not a defect.

### Strengths

- **One predicate for every PATH decision** (in-scope) [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]: `IsAdding()` replaces six comparisons. Two of them, the `!= manual` tests in `applyPosix` and in the Settled check, would have treated `unset` like `front`.
- **The one-way rule holds in the API server** (in-scope) [Claude Opus 5.5, Codex GPT 6 Astra]: the CEL rule binds every client, and it also rejects deleting the field or the whole `application` object, because defaulting brings `unset` back.

## Acknowledged Limitations

- **No path back to `unset`:** nothing in the API returns an App to `unset`, so restoring the first-run state takes deleting the App or `rdd svc delete`, which RD2 requires between versions anyway. #1052 intends this; a future reviewer should not re-suggest a reset path.
- **`rdd set --dry-run` creates a real App:** on a missing App the dry-run create is real, because the dry-run patch needs an object to validate against, and `set.bats:190` pins that behavior. The created App keeps the default `unset`, since only the dry-run patch carries the `manual` pin. A future reviewer should not re-suggest `DryRunAll` on that create.

###### Design Observations

###### Concerns

- **Single-direction CEL transition allows no programmatic reset** `(future)`: The rule `self != 'unset' || oldSelf == 'unset'` permanently forbids returning to `unset`. This satisfies the requirement to distinguish first-run state from an intentional `manual` setting. However, if a future factory-reset command or testing scenario needs to restore the first-run state on an existing instance without deleting the App resource, it will require dropping and recreating the App rather than patching `addPath`. This tradeoff aligns with the issue specification and avoids complex multi-field state machines.

###### Strengths

- Consolidating the strategy checks under `AddPathStrategy.IsAdding()` cleanly isolates the semantics of `front` and `back` from non-adding states (`manual` and `unset`), eliminating dual checks across Unix, Windows, Docker plugin, and Settled condition logic.
- Removing dead helpers (`effectiveAddPath` and `strategy == ""`) leaves the path management reconciler simpler and ensures strategy evaluation is uniform across all platforms.
