// Running reports whether the service process is alive.
func Running() bool {

IsOurProcess(pid, "service", "serve") confirms the PID runs a control plane, not this instance's. The service serve command line carries only --secure-port <6443+index> per instance (no instance name), and the guard ignores it. If two instances run concurrently and instance A's stale PID file holds a PID recycled to instance B's live service serve, PID() adopts B: Running() reports A as up, rdd svc start refuses to start, and StopWithWait could signal B's control plane. Single-instance use is safe — a recycled PID is never another rdd service serve — so the residual is the concurrent multi-instance / BATS case. The guard remains a clear gain over the prior "any live PID" trust.

Fix: append a per-instance token to the serve argv (the instance name, or the per-instance --secure-port) and require it in the check.

S2. IsOurProcess matches on image alone when called with no substrings Claude¶
pkg/util/process/process_windows.go
//
// Each substring is matched with strings.Contains, not as a whole argument, so a
// discriminator must be specific enough that it cannot appear in an unrelated
// process's command line. An instance name that is a prefix of another (e.g.
// "vm" and "vm2") matches both; pass a name distinct enough to avoid that.
func IsOurProcess(pid int, cmdlineSubstrings ...string) bool {
	self, err := os.Executable()
	if err != nil {
		return false
	}
	handle, err := windows.OpenProcess(
		windows.PROCESS_QUERY_LIMITED_INFORMATION|windows.PROCESS_VM_READ, false, uint32(pid))
	if err != nil {
		return false
	}
	defer func() { _ = windows.CloseHandle(handle) }()

	image, err := processImagePath(handle)
	if err != nil || !strings.EqualFold(filepath.Clean(image), filepath.Clean(self)) {
		return false
	}
	cmdline, err := processCommandLine(handle)
	if err != nil {
		return false
	}
	for _, s := range cmdlineSubstrings {
		if !strings.Contains(cmdline, s) {
			return false
		}
	}
	return true
}

// processImagePath returns the full path to the executable backing the process.
// QueryFullProcessImageName does not report the size it needs on failure, so on
// ERROR_INSUFFICIENT_BUFFER this doubles the buffer and retries, up to the
// Windows extended-path ceiling of 32767 characters.

The docstring frames substring matching as integral, but IsOurProcess(pid) succeeds on an image-path match alone. Every production caller passes a discriminator, so this is latent: the variadic signature invites a future caller to omit one and silently get image-only matching, which a recycled PID running another rdd subprocess (e.g. rdd ctl) would satisfy. The risk stays low because the image must still be the rdd binary.

Fix: no code change required; document that a zero-substring call checks the image only, and that callers should always pass a discriminator.

Design Observations ¶

Concerns ¶

  • handleDeletion's force-stop relies on the StatusRunning proxy (future) Codex — handleDeletion force-stops only StatusRunning instances (limavm_lifecycle.go:55) and skips the new IsOurProcess guard, and Reconcile dispatches a deleting object straight to it on a controller restart (limavm_controller.go:175) before killOrphanedHostagent can run. Codex read this as a recycled-PID force-kill. In practice Lima's store.Inspect connects to the hostagent socket and downgrades a recycled HostAgentPID to StatusBroken (lima store/instance.go:71-88), which this path does not force-stop and then PID-clears before Delete. The residual is a driver-status override leaving StatusRunning over a recycled HostAgentPID, plus the always-deferred DriverPID. Low risk, but the "StatusRunning means ours" premise is implicit; an IsOurProcess scrub would make it explicit.
  • Hostagent startup refuses to start on a recycled PID (future) Claude — hostagentAction rejects startup when store.ReadPIDFile returns a nonzero PID (pkg/hostagent/command.go:55). On Windows ReadPIDFile treats any live PID as valid and never cleans the file, so a recycled PID makes a fresh hostagent fail with "another hostagent may already be running." This is the inverse of the signal hazard — a false "running," not a wrong-target kill — and is pre-existing (uses Lima's helper). Validate the read PID with IsOurProcess(pid, "hostagent", name) before refusing, or clear a non-matching file.
  • Service-PID false-negative orphans a live control plane (future) Claude — IsOurProcess compares the target image to os.Executable(). After an in-place binary upgrade to a different path, or a transient PEB read failure, the live service reads as "not ours," PID() removes the file (service.go:166), and Running() reports the control plane down. The author documents exactly this in the longPath comment ("for the service PID a false 'not ours' would orphan a live control plane") and mitigates the short-path form with normalization; the moved-binary form remains. Self-healing on the next reconcile and implausible pre-release.

Strengths ¶

  • The PEB walk is correct against x/sys@v0.43.0: the PROCESS_BASIC_INFORMATION → PEB → RTL_USER_PROCESS_PARAMETERS → CommandLine chain, the byte-counted NTUnicodeString.Length (divided by 2 for UTF-16), and the full-read check all hold. Claude Codex
  • longPath degrades to lexical filepath.Clean on resolution failure rather than a guaranteed mismatch, biasing toward keeping a live service. Codex
  • The handle-vs-PID split — procExited for in-memory *exec.Cmd paths, IsOurProcess for on-disk PIDs — keeps the common path simple and answers @mook-as's feedback precisely. Claude Codex

Review Process Notes ¶

Skill improvements ¶

  • When a finding alleges that a library's force-stop, kill, or delete-with-force call reaches the wrong process, trace that library's platform-specific termination primitive before assigning severity. The same cross-platform API can map to a bounded per-process kill on one OS and a process-group or console-wide broadcast on another (for example a Windows GenerateConsoleCtrlEvent that escapes to the shared console and kills the calling service). The blast radius — contained kill versus session-wide crash — decides the severity, so the primitive must be read, not assumed from the API name.

Repo context updates ¶

  • [repo] On Windows, Lima's instance.Delete(force=true) → StopForcibly → osutil.SysKill sends GenerateConsoleCtrlEvent(CTRL_BREAK) to both DriverPID and HostAgentPID taken from on-disk state (lima/pkg/osutil/osutil_windows.go), ignoring the requested signal even for SIGKILL. Any rdd caller that hands a Lima instance to Delete/StopForcibly without zeroing its PIDs on Windows can broadcast CTRL_BREAK to a recycled PID and crash the rdd service. handleDeletion clears both PIDs first; audit every other limainstance.Delete caller for the same scrub.
  • [repo] Lima's store.Inspect sets StatusRunning only after connecting to the hostagent socket and calling Info() (lima/pkg/store/instance.go:71-88); a recycled HostAgentPID not listening on that socket downgrades to StatusBroken. So Status == StatusRunning is a reliable "this HostAgentPID is genuinely ours" signal, but no such check backs DriverPID. When reviewing PID-trust decisions gated on Lima status, treat StatusRunning as identity evidence for HostAgentPID only.
