## Consolidated Review

### Executive Summary

This Windows-only PR heals orphaned WSL2 distro registrations (re-import on start) and prevents new ones (unregister on `svc delete`). The mechanism is sound and matches Lima's WSL2 driver. One Important defect: `instanceDistroNames` enumerates every directory under LimaHome, so Lima's reserved `_config`/`_disks` dirs become phantom `lima-_config` distros that emit a spurious warning on every Windows delete — and a unit test masks it by creating `_config` as a file.

Two cloud reviewers ran (Codex, Claude); Gemini dropped on an authentication error. Both reviewers independently raised the enumeration bug. They split on the start-time heal path: Codex rated the missing terminate-before-unregister step Important, Claude rated it a Suggestion. This report adjudicates it as a Suggestion — the triggering state (a diskless distro still running) is unlikely, but the one-line fix restores parity with the two sibling cleanup sites.

## Important Issues

I1. **`instanceDistroNames` enumerates Lima's reserved `_`-dirs as distros — spurious Windows warning on every `svc delete`** — `rdd/pkg/service/cmd/service.go:613-628` [Codex GPT 5.5, Claude Opus 4.8]

```go
for _, entry := range entries {
	if entry.IsDir() {
		names = append(names, "lima-"+entry.Name())
	}
}
```

`instanceDistroNames` returns a `lima-<name>` distro for every directory under LimaHome, checking only `entry.IsDir()`. LimaHome also holds Lima's reserved directories — `_config`, `_disks`, `_networks` — and Lima creates `_config` (the shared SSH key) as soon as any instance exists (`ssh_keys_windows.go:21-26`). So `unregisterInstanceDistros` runs `wsl --unregister lima-_config`, which fails and logs at `warn` (`service.go:605`): "Failed to unregister WSL2 distro; a stale registration may remain." On the CLI path (logrus, default level `warn`) this false alarm reaches the user's terminal on every Windows delete. Lima's own `store.Instances()` skips `.`/`_`-prefixed entries (`store.go:67`); this hand-rolled copy dropped that filter.

The unit test masks the bug: it creates `_config` as a *file* (`service_test.go:22`), so the real directory case never runs. Update that test to create `_config` with `os.Mkdir` and it fails until the filter is restored.

Fix: skip reserved and dotfile entries, mirroring `store.Instances()`.

```diff
-		if entry.IsDir() {
-			names = append(names, "lima-"+entry.Name())
-		}
+		name := entry.Name()
+		// Skip Lima's reserved dirs (_config, _disks, ...), as store.Instances does.
+		if !entry.IsDir() || strings.HasPrefix(name, "_") || strings.HasPrefix(name, ".") {
+			continue
+		}
+		names = append(names, "lima-"+name)
```

## Suggestions

S1. **Heal path skips the terminate-before-unregister guard its two siblings apply** — `rdd/pkg/controllers/lima/limavm/controllers/limavm_lifecycle.go:387-391` [Codex GPT 5.5, Claude Opus 4.8]

```go
if wsl2RegistrationIsOrphaned(inst) {
	logger.Info("WSL2 distro is registered but its root disk is missing; unregistering to force re-import", ...)
	unregisterWSL2Distro(ctx, logger, limaVM.Name)
}
```

The heal path calls `unregisterWSL2Distro` without first calling `terminateWSL2Distro`. Both sibling cleanup sites terminate first — `removeStaleInstance` (`limavm_lifecycle.go:844-845`) and `unregisterInstanceDistros` (`service.go:591-592`) — because `wsl --unregister` can deadlock on a distro that still holds kernel state (documented at `limavm_lifecycle.go:841-843`; recovery needs `taskkill /F /IM wslservice.exe`). The 30s context timeout bounds the `wsl.exe` call, not the underlying wslservice deadlock.

Codex rated this Important; Claude and this report rate it a Suggestion, because a diskless distro is rarely Running — a running distro holds its `ext4.vhdx` open, which usually blocks the deletion that creates the orphan. The fix is one line and restores parity with the other two sites.

Fix:
```diff
+	terminateWSL2Distro(ctx, logger, limaVM.Name)
 	unregisterWSL2Distro(ctx, logger, limaVM.Name)
```

S2. **Heal-path unregister failure logs only at `V(1)`, yet its failure perpetuates the loop being fixed** — `rdd/pkg/controllers/lima/limavm/controllers/limavm_lifecycle.go:830-832` [Claude Opus 4.8]

When the heal-path `unregisterWSL2Distro` fails, it logs only at `V(1)` (`limavm_lifecycle.go:831`), and `startInstance` proceeds to boot the diskless distro into the `ERROR_FILE_NOT_FOUND` loop this PR exists to break. The next reconcile's Lima `Start` failure surfaces a louder error, so the condition self-retries and stays observable — but the heal log alone shows only "unregistering to force re-import" with no signal that it failed. Consider logging the heal-path failure at a higher level, or returning a distinct error so the requeue reason is explicit.
