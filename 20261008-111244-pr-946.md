## Executive Summary

The PR adds per-OS process spawning for `docker compose`, the deletion path that runs `down` for a ComposeProject, the ComposeUpRequest reconciler, and BATS tests. The structure holds up, but the lifecycle edges do not. A spec edit during `up` is reported as applied without running, three deletion paths retry `down` forever, macOS `kill` never delivers SIGHUP, Linux `kill` needs kernel 6.9, and a `docker` that cannot start leaves a request unsettled.

## Important Issues

I1. **A spec update during a running `up` is reported as applied but never runs** — `rdd/pkg/controllers/containers/compose/compose_up_request_reconciler.go:90-95` [Claude Opus 5.5, Codex GPT 6 Astra]

```go

		// The process has finished; record the outcome.

```

The webhook lets `spec.workingDir` and `spec.configs` change (`compose_webhooks.go:80-84`), and `api_containers.md:815-816` promises that reaping waits until `up` has completed for the updated spec. When the spec changes while `up` runs, line 90 returns early. Once the old run finishes, `completeUp` stamps `ObservedGeneration` from the current object (lines 180 and 188), so Settled claims the new generation succeeded, and the settled case at line 72 never reruns `up`. `processState` records only the resource version, which the reconciler's own status writes also bump, so nothing tells which spec a process ran.

I2. **Deletion never resolves `HasMembers=Unknown`, so a failing `down` retries forever and a finished one runs twice** — `rdd/pkg/controllers/containers/compose/compose_reconciler.go:209-212` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]

```go
	case hasState, apimeta.IsStatusConditionFalse(project.Status.Conditions, v1alpha1.ComposeProjectConditionHasMembers):
		// Either `docker compose down` has finished, or the containers were removed
		// externally (e.g. because the engine shut down).  Remove the tracked state,
		// and remove the finalizer so the object can be deleted.
```

`removeComposeMembership` sets `HasMembers=Unknown` when a member disappears (line 392), and only the non-deleting branch turns Unknown into False (line 143). So once deletion starts, this case never sees an empty project, although its comment says engine-removed containers reach it. If the engine stops while `down` fails, the reconciler logs each failed `down` at Error (line 197) and requeues after 1 s, indefinitely. If `down` exits while members are still listed, line 207 drops the state, the members go Unknown, and `down` runs a second time.

S1. **Cancelling the tracker's context marks a process finished before it exits, and `output()` then panics** — `rdd/pkg/controllers/containers/compose/compose_process.go:163-166` [Codex GPT 6 Astra]

```go
		state.err = state.cmd.wait(ctx)

```

`wait` returns `ctx.Err()` as soon as its context is cancelled (`command.go:73-74`), and line 165 then marks the state finished. A reconcile that reads that state calls `output()` (`compose_reconciler.go:199`, `compose_up_request_reconciler.go:168`), which panics because the process has not exited. The context is the manager's, so this happens only at shutdown, and controller-runtime recovers reconcile panics.

Fix: on cancellation, leave the state unfinished or skip `onComplete`, so that only a real exit publishes a result.

## Design Observations

### Concerns

- **The process tracker keys a run by resource version** (in-scope). The reconcilers' own status writes bump the resource version, so it cannot say which spec a process ran; the object's generation can. I1 is the visible consequence, and a future caller of `run` could kill a healthy process on its own status write. [Claude Opus 5.5]
- **The temporary-directory fallback exists three times** (in-scope). Each `spawn` starts the process, matches an OS-specific error and retries in a temporary directory, and the Windows copy has already drifted (I3). Deciding the working directory once before spawning would remove the error matching from all three. [Claude Opus 5.5]
- **`docker compose` runs from the daemon's PATH** (future). `rdd run` prepends the instance's `bin` directory instead (`cmd/rdd/run.go:125`), so a user whose shell finds `docker` may still see I5's failure under the daemon. [Claude Opus 5.5, Gemini 3.5 Flash]
- **nerdctl compose projects are never detected** (future). The pinned nerdctl 2.1.2 does not set `com.docker.compose.config-hash` (its `pkg/labels/labels.go` gained `ComposeConfigHash` in 2.2.0), and `reconcileContainer` drops containers without it. That check predates this PR, and PR #882's bump to nerdctl 2.2.x is the tracked fix. [Gemini 3.5 Flash]

### Strengths

- **Each platform's kill-on-parent-exit mechanism fits its OS.** It uses Pdeathsig on a locked thread on Linux, a PTY session on macOS, and a job object on Windows. [Claude Opus 5.5, Gemini 3.5 Flash]
- **Only the current run publishes a result.** `onComplete` fires only when `current.cmd == state.cmd`, so a superseded process never reports completion. [Claude Opus 5.5]
- **The executor is injectable.** The fake command makes `kill` unblock `wait`, so the lifecycle tests run without Docker or a VM. [Codex GPT 6 Astra, Claude Opus 5.5]
- **Membership removal checks the container UID**, so a delayed deletion event for a container recreated under the same name cannot remove the new one. [Gemini 3.1 Pro]

## Acknowledged Limitations

- **nerdctl:** `compose_process.go:93` says "TODO: Support nerdctl here." On the containerd engine, deleting a project therefore runs `docker compose down`, which fails and, until I2 and S7 are fixed, retries every second.
- **Windows job assignment:** `command_windows.go:21-29` assigns the process to its job only after it starts, until Go supports assignment at creation. A grandchild started in that window escapes `KILL_ON_JOB_CLOSE`. Assignment also fails if the process has already exited, but the window is microseconds against the startup of a Go binary, so do not re-suggest it without a measured exit inside it.
- **Docker discovery:** `compose-docker.bats:17-20` skips the suite when the compose plugin is missing, pending a reliable way for the reconciler to find it.
- **Do not re-suggest:** stripping `DOCKER_CONTEXT` before appending it (`os/exec` keeps the last duplicate); making the Linux `cleanup` idempotent (its only caller runs once); passing the caller's context to the darwin `forceKill` (the spawn context is the manager's, and once it is cancelled `exec.CommandContext` has already killed the child); fixing I2 by testing `len(status.containers) == 0` alone (it breaks two existing deletion tests).

## Review Process Notes

### Skill improvements

- When a finding depends on state a process or connection reaches only after running for a while (a reader blocked in a system call, a lease expired, a cache warmed), reproduce it after that state is reached. An existing test that acts immediately after setup can pass on the defective code, so neither its pass nor a timing quoted from it confirms or refutes the finding.
- When the consolidator writes fix patches for several findings against one review SHA, apply them in sequence before publishing and name the pairs that overlap. Authors apply review patches one after another, and an unannounced conflict looks to the author like a broken patch.

### Repo context updates

- [repo] rdd's host-side `*_linux.go` code runs on the user's desktop distribution kernel, not the guest VM's or WSL's; rdd on Windows uses the `*_windows.go` files. Rate a kernel-version requirement in host code against desktop distributions' GA kernels (Ubuntu 24.04 ships 6.8), and note that CI's ubuntu-latest runner has a newer kernel, so a passing Linux job proves nothing about older ones.
- [repo] Many rdd objects have deterministic names derived with `api.MirrorName`, so a delete-and-recreate under the same name is routine. A reconciler that tracks work per object must key it by UID and, after a successful `Get`, compare the fetched UID with the request's; flag cleanup that runs only on NotFound.

S1. **The process-group flag needs Linux 6.9, and the comment's reasoning for that floor is wrong** — `rdd/pkg/controllers/containers/compose/command_linux.go:19-22` (suggestion, gap)

Kernels before 6.9 reject any non-zero flags with EINVAL. That 6.9 itself is end-of-life says nothing about older kernels still in use: Ubuntu 24.04's GA kernel is 6.8, and the 6.1 and 6.6 LTS lines are maintained. On such a host, `kill` (line 105) returns EINVAL:

- The stale-process kill in `run` turns into a Reconcile error.
- `abort` logs at V(1) only and leaves `docker compose up` running for a deleted request.

###### Design Observations

**Concerns**

- **The process identity key is wrong (in-scope).** `processTracker` deduplicates and supersedes by `resourceVersion`, but the reconcilers' own status writes bump the version. Keying on `metadata.generation` (spec changes only) would remove a class of bugs: I2, plus a latent risk that a future caller of `run` kills a healthy process on its own status write.
- **The temp-dir fallback is implemented three times (in-scope).** Each `spawn` re-implements "start, check an OS-specific error, retry in a temp dir", and Windows already drifted (I4). If `defaultCommandExecutor` or `initiateProjectDown` stat `workingDir` once and pass `""` when it is missing, each `spawn` shrinks to "start in dir, or in a fresh temp dir when dir is empty", with no error-code matching.

**Strengths**

- Each platform's kill-on-parent-exit mechanism is chosen with care: Pdeathsig on a locked thread for Linux, the PTY session for darwin, and a job object for Windows.
- The fake-command test double performs a real teardown: `kill` unblocks `wait`.
- Gating `onComplete` on `current.cmd == state.cmd` correctly suppresses completion events from superseded runs.

###### Testing Assessment

1. **Required: spec update while `up` runs** (I2). Failures that depend on reconciler ordering and state are required, and no existing test changes the generation mid-run.
2. **Required: deletion with `down` failing and no members** (I3). The result is a 1 s retry loop that no test bounds. `TestReconcileCompose_Delete/keeps the finalizer and retries…` pins the fixed `RequeueAfter` and does not cover the loop.
3. **Required: macOS kill delivers SIGHUP promptly** (I1). The opaque-behavior check makes it required: `TestDefaultCommandExecutorKill` passes on the SIGKILL fallback.
4. **Required: spawn failure records a status** (I5). The user sees a hang, which is opaque.
5. **Required: missing workingDir with stale configs makes `down` succeed** (I4). Windows needs a unit test that uses a nonexistent subdirectory of `t.TempDir()`. The BATS deletion test covers only an empty `workingDir`.
6. **Optional:** `TestDefaultCommandExecutor` asserts exit 0 and empty output, which a helper that never runs would also satisfy. The capture-stderr test does prove the child runs.

###### Documentation Assessment

- `api_containers.md` promises that a spec update reruns `up` for the new spec. The code breaks that promise (I2). Fix the code, not the doc.
- These comments describe paths that do not behave as written:
  - `command_darwin.go:147-148` and `compose_reconciler.go:210-211` (I1, I3).
  - `command.go:44-46`: the `commandImpl.spawn` contract says a missing directory falls back to a temp dir, which Windows violates (I4).
- `command_linux.go:20-21` overstates the kernel floor's justification (S1).

###### Acknowledged Limitations

- **nerdctl.** `compose_process.go:93`, "`// TODO: Support nerdctl here.`" On the containerd engine, deleting a nerdctl compose project runs `docker compose down`, which fails. This PR makes that a 1 s retry loop with Error logs (I3), so the limitation now costs more.
- **Windows job assignment.** `command_windows.go:21-29` says the process is assigned to the job only after it starts, until Go supports pre-start assignment. A grandchild spawned in that window escapes `KILL_ON_JOB_CLOSE`. The change neither worsens nor improves this.
- **Docker discovery.** `compose-docker.bats:17-19`, "this needs to go away once we can ensure the reconciler can find `docker compose` correctly". The reconciler resolves `docker` through the daemon's frozen PATH, not `instance.BinDir()` as `rdd run` does (`cmd/rdd/run.go:124-135`). I5 is the user-visible consequence of that unresolved lookup.
- **Obsolete Linux.** `command_linux.go:115-116` says `os.ErrNoHandle` on obsolete Linux is simply returned.

###### Executive Summary

This PR implements the remaining ComposeProject reconciler functionality, including `docker compose down` execution on deletion, the `ComposeUpRequest` reconciler, and BATS test coverage. While the concurrency architecture and state machine logic are remarkably robust against delayed watch events, two cross-platform process management bugs will cause `docker compose` commands to fail or leak on Windows and WSL.

###### Findings

###### Critical Issues

C1. **WSL process leak via `PidfdSendSignal` on older kernels** — `rdd/pkg/controllers/containers/compose/command_linux.go:94-96` (critical, regression)

The Linux executor sends `SIGTERM` to the process group using `unix.PidfdSendSignal` with the `PidfdSignalProcessGroup` flag (`4`). While the author notes this was introduced in Linux 6.9 and claims it covers WSL, the default kernels for WSL2 on Windows 10 and 11 are still on LTS branches (e.g., 5.15 and 6.6). On these prevalent kernels, `PidfdSendSignal` with this flag returns `EINVAL`, which is propagated out of `kill()`. The process group is never terminated, silently leaking the `docker compose` processes on teardown.

Fix: Add a fallback in `kill()`: if `unix.PidfdSendSignal` returns `unix.EINVAL` or `unix.ENOSYS`, fall back to `unix.Kill(-process.Pid, syscall.SIGTERM)` (which targets the process group since `Setpgid: true` was used during spawn) so older kernels can still terminate the process.

###### Important Issues

I1. **Sporadic `docker compose` failures on Windows due to job assignment race** — `rdd/pkg/controllers/containers/compose/command_windows.go:121-126` (important, gap)

After spawning the command, the Windows executor assigns the running process to a Job Object. If the command executes and exits extremely quickly (e.g., an empty compose project, or a fast `up --detach`), the process may terminate before `windows.AssignProcessToJobObject` is called. Per MSDN, calling this on a terminating or terminated process fails with `ERROR_ACCESS_DENIED`. The reconciler treats this as a fatal start failure and aborts the request, masking the successful execution and potentially triggering infinite retry loops in `ComposeUpRequest`.

Fix: If `AssignProcessToJobObject` fails with `ERROR_ACCESS_DENIED`, check if the process has already exited (e.g., using `windows.GetExitCodeProcess` returning anything other than `STILL_ACTIVE`). If it has, the job object cleanup is no longer needed—ignore the error and proceed.

I2. **Test race condition due to asynchronous finalizer application** — `rdd/bats/tests/34-containers-controllers/compose-docker.bats:136-141` (important, regression)

The test "deleting a Compose runs docker compose down for its resources" waits for the `ComposeProject` to be created (`wait --for=create`) and then immediately deletes it. `wait --for=create` is satisfied the moment the apiserver records the object, but before `reconcileCompose` has asynchronously added the `mirrorFinalizer`. ###### Executive Summary

PR #946 implements the ComposeProject reconciler, member tracking from container labels, process spawning for `docker compose`, `ComposeUpRequest` execution, and BATS integration tests. The core process abstraction is well-architected across platforms, but two critical issues must be resolved before merge: process killing on Linux unconditionally passes an unsupported flag (`PidfdSignalProcessGroup = 4`) that fails with `EINVAL` on Linux kernels prior to 6.9 (including all supported enterprise distributions and WSL), and reaping uninitialized ComposeProjects causes an infinite 1-second reconcile loop.

###### Findings

###### Critical Issues

C1. **`PidfdSignalProcessGroup` flag in `unix.PidfdSendSignal` fails with `EINVAL` on Linux < 6.9** — `rdd/pkg/controllers/containers/compose/command_linux.go:19` (critical, regression)

```go
// PidfdSignalProcessGroup is the flag for [unix.PidfdSendSignal] to send the
// signal to the process group.  Introduced in Linux 6.9, released in (and EOLed
// in) 2024; that covers all kernels we want to support, include SLES 16 and WSL.
const PidfdSignalProcessGroup = 4
```

`unix.PidfdSendSignal` passes `PidfdSignalProcessGroup` (value 4) at lines 103 and 110 of `command_linux.go`. Linux kernels reject non-zero flags with `EINVAL` prior to Linux 6.9 (`PIDFD_SIGNAL_PGID`). Contrary to the comment at line 17, current enterprise distributions and WSL run earlier kernels (Ubuntu 24.04 runs 6.8; Ubuntu 22.04 and WSL run 5.15/6.6 LTS; SLES 15 SP6 runs 6.4). On these kernels, `unix.PidfdSendSignal` returns `EINVAL` without delivering signals. At line 115, `kill()` returns `EINVAL`, leaving the process running. Callers at `compose_process.go:70` (`abort`), `compose_process.go:121` (`run`), and `compose_reconciler.go:106` fail to kill existing commands, leaking processes and stalling execution.

Fix: Fall back to direct process or group signaling when `PidfdSendSignal` returns `EINVAL` or `ENOSYS`, or if `process.WithHandle` returns `os.ErrNoHandle`:

```diff
 	err := process.WithHandle(func(handle uintptr) {
 		innerErr = unix.PidfdSendSignal(int(handle), syscall.SIGTERM, nil, PidfdSignalProcessGroup)
+		if errors.Is(innerErr, unix.EINVAL) || errors.Is(innerErr, unix.ENOSYS) {
+			innerErr = unix.Kill(-process.Pid, syscall.SIGTERM)
+		}
 		if innerErr != nil {
 			return
 		}
 		select {
 		case <-c.done:
 		case <-killCtx.Done():
 			innerErr = unix.PidfdSendSignal(int(handle), syscall.SIGKILL, nil, PidfdSignalProcessGroup)
+			if errors.Is(innerErr, unix.EINVAL) || errors.Is(innerErr, unix.ENOSYS) {
+				innerErr = unix.Kill(-process.Pid, syscall.SIGKILL)
+			}
 		}
 	})
+	if errors.Is(err, os.ErrNoHandle) {
+		err = unix.Kill(-process.Pid, syscall.SIGTERM)
+	}
```

###### Design Observations

###### Concerns

1. **Host-bound Docker command execution (`in-scope`)**: `compose_process.go:87-160` executes `docker compose` directly on the host. In environments where the host does not have `docker` CLI or Docker Compose plugin installed, compose reconciliation cannot function even though Docker is running inside the VM. Long-term, routing compose commands through the guest or embedded CLI will improve consistency across installation configurations.

###### Strengths

1. **Process tracking with generation and version fencing**: `processTracker` in `compose_process.go` cleanly fences duplicate reconcile requests, manages concurrency races, and properly aborts stale commands when resource versions advance.
2. **Platform-native lifecycle binding**: The use of macOS PTY master SIGHUP propagation (`command_darwin.go`), Linux `Pdeathsig` (`command_linux.go`), and Windows Job Objects with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` (`command_windows.go`) ensures orphaned child processes are reliably cleaned up if the parent daemon crashes.
