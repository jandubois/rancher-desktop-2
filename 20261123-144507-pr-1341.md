## Executive Summary

The PR logs named startup timing points and shows a static, sandboxed splash from Electron's `ready` until the first app window is visible. The design is sound. The one Important finding: the "Incompatible RDD Service" box, the startup error that #463 describes, comes up over the still-spinning splash, and the obvious fix of closing the splash first deactivates the box on macOS. Hiding the splash fixes both. The five suggestions are optional.

## Important Issues

I1. **The splash stays up behind the "Incompatible RDD Service" startup error** — `pkg/rancher-desktop/main/rdd-ctl.ts:114` [Codex GPT 6 Astra, Claude Opus 5.5]

```ts

        Electron.dialog.showErrorBox('Incompatible RDD Service', message);
```

The splash commit says it closes "before showing a startup error", but only `showErrorDialog` (`background.ts:441`) does, and only the `before-quit` failure path reaches it. `setupNetworking()` fires `rdd/kube-config` without waiting, and an incompatible service triggers this box, #463's startup error, before any app window opens. ## Suggestions

S1. **A first window that fails to load or closes early leaves the splash up** — `pkg/rancher-desktop/window/index.ts:99` [Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]

```ts
    if (options.show === false) {
      window.once('show', () => onFirstWindowVisible('first-window-shown'));
    } else {
      window.webContents.once('did-finish-load', () => onFirstWindowVisible('first-window-loaded'));
    }
```

Only the first window that `createWindow()` builds can close the splash, and only when that window shows or finishes loading. If that window's page fails to load, or the user closes the main window before its page finishes loading, no later window takes over. The splash then stays on screen until the app quits, and the timing line never reaches the log. A harness that loads the real modules against a stand-in Electron reproduced the second case. A reopened main window finished loading with the splash still open. A packaged build loads a local `app://` page, so both triggers are rare.

Fix: also close the splash from the first window's `closed` event and from a main-frame `did-fail-load` (check `isMainFrame`).

S2. **A failed splash load isn't logged, and a constructor throw stops startup** — `pkg/rancher-desktop/window/splash.ts:99` [Gemini 3.1 Pro, Codex GPT 6 Astra, Claude Opus 5.5, Gemini 3.5 Flash]

```ts
  splash.loadURL(`data:text/html;charset=utf-8,${ encodeURIComponent(html) }`, { baseURLForDataURL: baseURL })
    .catch(() => closeSplash());
```

A failed load closes the splash without writing anything to the logs. The repo asks every `BrowserWindow` built outside `createWindow()` for a `did-fail-load` listener that logs, as `window/dashboard.ts:74` has. Separately, `openSplash()` runs before the `try` at `background.ts:108`, so a throw from the `BrowserWindow` constructor rejects the `whenReady` callback and startup stops, with only the `unhandledRejection` line in the log. Both failures are unlikely, because a static data URL and a stock constructor rarely fail.

Fix: log the error code and description from a `did-fail-load` listener, then call `hideSplash()` from I1's patch, since `closeSplash()` on the only window hides the dock icon. Wrap `openSplash()` in a `try`/`catch` that logs and continues.

S3. **The matched colours don't prevent a white flash on the main-window path** — `pkg/rancher-desktop/window/splash.ts:9` [Claude Opus 5.5, Gemini 3.5 Flash]

```ts
// Body background and text colors from the app's light and dark themes
// (assets/styles/themes), so the switch to the first app window does not
// flash a different color.
```

`openMain()` (`window/index.ts:139`) creates a visible window without setting `backgroundColor`, whose default the Electron typings give as white (`#FFF`), and that window opens on top of the splash before its page paints. In dark mode, a launch that skips first run therefore goes from the dark splash to a white window and then to the dark app. The first-run dialog stays hidden until `dialog/ready`, so the comment holds on that path. Not run; read from the code and the typings.

Fix: export the two background constants and pass `backgroundColor: nativeTheme.shouldUseDarkColors ? darkBackground : lightBackground` from `openMain()`, or limit the comment to the dialog path.

S4. **A launch that fails before its first window doesn't log its timing** — `pkg/rancher-desktop/window/index.ts:72` [Gemini 3.5 Flash]

```ts
function onFirstWindowVisible(mark: string) {
  markStartup(mark);
  reportStartup(Logging.background);
  closeSplash();
}
```

`reportStartup()` has this one caller, so the marks reach the log only once a window shows. A launch that ends at I1's box, at `showErrorDialog`, or in the `whenReady` catch that quits never writes its marks, and a user who reports that launch sends a log without the line.

Fix: also call `reportStartup(Logging.background)` from a `will-quit` handler. It writes only once, so a launch that reached a window keeps its report unchanged. Not run.

S5. **The PR doesn't test `startupTiming` or the first-window hook** — `pkg/rancher-desktop/utils/startupTiming.ts:41` [Claude Opus 5.5, Gemini 3.5 Flash]

```ts
  const creationTime = process.getCreationTime();
  const origin = creationTime ?? marks[0]?.time ?? 0;
```

The PR doesn't test the one-shot report, marks made after it, the fallback when `process.getCreationTime()` returns `null`, or the `createWindow()` hook that closes the splash, and the e2e specs skip the splash. A unit test has to stub `process.getCreationTime`, which only Electron defines. Under Jest's Node, `reportStartup()` throws `TypeError: process.getCreationTime is not a function`; the shipped code is safe only because its one caller runs in Electron's main process. The tests are optional, since a regression shows on every launch. A test of the hook can follow `window/__tests__/dashboard.spec.ts`, which drives `createWindow()` with a mocked Electron.

## Design Observations

### Concerns

- **(future)** When `startInBackground` comes to RD2 (`e2e/start-in-background.e2e.spec.ts` is `fixme`), `openSplash()` has to check it, or a background launch leaves the splash open for good. [Claude Opus 5.5]
- **(future)** While the app is starting, `second-instance` and macOS `activate` do nothing (`background.ts:88`, `background.ts:285`). If those handlers raised the splash, a second launch would bring a covered splash to the front. [Claude Opus 5.5]
- **(future)** If `isFirstRunNeeded()` hangs, the user now sees a spinner without a close button where they used to see nothing. The PR body leaves #463's error half for later. [Claude Opus 5.5]

### Strengths

- **(in-scope)** The splash page is a static data URL in a sandboxed window with `default-src 'none'`. It escapes the name and version and doesn't wait for the renderer bundle. [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]
- **(in-scope)** `startupTiming.ts` imports only types from `logging` and `paths`, so it stays out of their import cycle, and its one-shot flag makes late marks harmless. [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]
- **(in-scope)** The first-window hook waits for `show` on a window created hidden and for the first page load on the visible main window, which matches when each one appears. [Claude Opus 5.5]

## Review Process Notes

### Repo context updates

- [repo] Two native error boxes can appear during startup. Only the `before-quit` failure path reaches `showErrorDialog` in `background.ts`. The "Incompatible RDD Service" box in `main/rdd-ctl.ts` can appear before any app window opens, because `setupNetworking()` fires `rdd/kube-config` without waiting for it. A change that must act before "a startup error", such as removing a window or flushing a log, has to cover the second one.

- [repo] A `BrowserWindow` whose page lacks a `<title>`, and that doesn't set the `title` option, takes `app.name` as its title, which is "Rancher Desktop 2" in dev and packaged builds. Do not flag a missing title as showing "Electron" or the page URL.

###### Design Observations

###### Concerns

- **Splash window does not set `alwaysOnTop: true` while main window starts visible** `(in-scope)`:
  Because `openMain()` creates the main window with `show: true` (Electron's default) while `splash` has `alwaysOnTop` unset, the 1280x720 main window immediately appears on top of the splash window as soon as `openMain()` runs, obscuring the splash while the main window is still rendering a blank document before `did-finish-load`. Setting `alwaysOnTop: true` on `splash` (or delaying main window display until `ready-to-show`) would keep the splash screen visible throughout the transition.

###### Strengths

- The static data-URL splash page with embedded CSS avoids loading the renderer bundle or initializing an extra Nuxt/Vue instance, keeping splash display instantaneous (~150 ms) without incurring additional memory overhead.
- `startupTiming.ts` imports only types from `@pkg/utils/paths` and `@pkg/utils/logging`, avoiding circular module dependencies while recording high-resolution startup milestones.
