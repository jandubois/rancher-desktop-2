## Executive Summary

The PR splits `status.name` and `status.labels` across two field managers, so a failed label fetch can no longer erase stored labels. The split works, and an empty label set from containerd still clears them. Nothing pins that behavior. Revert the fix and the package suite stays green. A mirror written by the merge-base build still loses its labels once, but only on code that merged today and has shipped in no release.

I1. **Nothing pins the field-ownership split the fix rests on** — `rdd/pkg/controllers/app/engine/controllers/sync_namespace_containerd.go:110` [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.5 Flash]

```go
	applyConfig.WithStatus(containersv1alpha1apply.ContainerNamespaceStatus().
		WithLabels(labels))
	return w.k8s.Status().Apply(ctx, applyConfig,
```

The remedy rests on how the API server merges two field managers writing one status subresource. No Go test names `applyNamespace` or `syncNamespaces`. The BATS case at `engine-containerd.bats:243-264` sets a label, changes its value, and waits for each, so it stays green even if the labels apply reuses the single owner, because the second apply rewrites the labels either way. The suite cannot tell this fix from the bug it replaces.

That matters more than a usual test gap, because `status.labels` has no consumer yet. A future regression here corrupts stored status, and nothing reports it.

For a namespace that is gone, containerd returns an empty map and a nil error, never `NotFound`. `namespaceStore.Labels` returns `(labels, nil)` when `getNamespaceLabelsBucket` finds no bucket, and `getBucket` returns nil as soon as any level of the path is missing. So this branch cannot fire for the case the comment names.

The merge-base said so and kept the branch anyway, because the containerd API promises nothing about the error and the behavior can change. Replacing that with a comment about logging drops the reasoning, so the next reviewer re-raises it. One did this round, recommending removal, the change the author already declined on PR #772.

Fix: append a sentence naming the reason, for example that containerd's namespace store currently returns an empty label set rather than NotFound, but the API does not promise that.

S3. **The labels field owner is spelled inline** — `rdd/pkg/controllers/app/engine/controllers/sync_namespace_containerd.go:110` [Claude Opus 5]

```go

```

A field manager name is persisted state, stored in `metadata.managedFields`. Only an apply that includes `status.labels` may use this one, and nothing in the code says so. Spelling the name inline keeps that rule away from `controllerName` (`engine_reconciler.go:38`), where the next reader looks.

Fix: declare it beside `controllerName` as `labelsFieldOwner = controllerName + "-labels"`, with a comment saying that every apply using it must include `status.labels`.

## Design Observations

### Concerns

- `applyNamespace` now costs three API round trips instead of two, and it runs on every `ContainerCreate` and `ImageCreate` event, not only during a full sync (`containerd_watcher.go:197` and `:236`). Each is a no-op apply after the first, so the extra cost is one request per event over the local socket, but it scales with image pulls into `k8s.io`. `(future)` [Claude Opus 5, Gemini 3.5 Flash]
- Only the containerd path writes `engine-controller-labels`. The Docker path's `syncContainerNamespace` still applies `status.name` under `engine-controller` alone (`sync_namespace.go:32-38`), so nothing there would clear containerd-era labels off a `moby` mirror. `cleanupMirrorResources` deletes every mirror on an engine change within one process, which covers it today. `(future)` [Claude Opus 5]

### Strengths

- Applying `status.name` before the labels fetch, rather than after, keeps the selectable field fresh even when the fetch fails. That ordering is deliberate and any fix for S1 should preserve it. `(in-scope)` [Claude Opus 5]
- The `len(entries) > 0` guard in `WithLabels` that caused the original bug now works in the PR's favor: an empty map produces a `status:{}` body, which removes exactly the keys that owner wrote. Scenario 4 of the S1 probe confirms it. `(in-scope)` [Codex GPT 5.6 Sol, Gemini 3.1 Pro, Claude Opus 5]
- The PR drops stale label keys from a migrated mirror correctly, which the simpler alternative fix does not. Scenario 7 of the S1 probe shows both. `(in-scope)`

### Executive Summary

PR #786 attempts to fix a label-erasure bug in containerd namespace mirroring by splitting status ownership between two field managers (`engine-controller` and `engine-controller-labels`). However, this remedy fails to protect existing labels during daemon upgrades (transition period). The initial name-only status apply under `"engine-controller"` relinquishes and deletes existing labels before the containerd label fetch is even executed. Fetching labels first and using a single combined status apply under `"engine-controller"` avoids this transition bug, preserves existing state, and reduces API server/SQLite write transactions by 33%.

Under Kubernetes Server-Side Apply (SSA), when a field manager applies a status omitting a field they previously owned, they relinquish ownership and that field is deleted from the live resource. On daemon upgrade, existing `ContainerNamespace` mirrors in the database are owned by `"engine-controller"`, which owns both `status.name` and `status.labels`. 

When `applyNamespace` runs under the new code, line 90 status-applies with ONLY `WithName(ns)` under `"engine-controller"`. If the subsequent `Labels()` call on line 96 then fails, the function returns `nil` at line 104 without executing the labels apply on line 109. Consequently, existing labels are permanently deleted on retrieval failure during transition.

Splitting status field ownership into two separate managers (`engine-controller` for status name and `engine-controller-labels` for status labels) results in **three** separate API server calls (one Apply for metadata/spec, two separate Status Apply calls for name and labels) during every sync or apply of a namespace mirror. 

In Rancher Desktop's embedded single-user context using SQLite/Kine, performing multiple sequential write transactions is highly inefficient and increases DB lock contention and latency.

Fix: Revert back to a single field owner (`engine-controller`) and combine name and labels in a single status apply by fetching the labels *first* before making any status modifications (as detailed in the fix for `I1`). This reduces write transactions from 3 to 2, increasing database efficiency by 33%.

### Design Observations

#### Concerns

*   **Transition-Period Edge Cases `(in-scope)`**: Relying on separate field managers to prevent field erasure assumes that separate field manager ownership has already been established on the resource. On transition/upgrade from older daemon versions, the existing resources are still fully owned by the old field manager, making the transition period highly vulnerable to state loss.
*   **Database Write Amplification `(in-scope)`**: Splitting a single status update into two sequential HTTP requests and DB transactions adds unnecessary write amplification to the single-user embedded SQLite database. Minimizing API calls keeps DB contention low and performance predictable.

#### Strengths

*   **Graceful Disappearance Handling**: Swallowing `NotFound` errors when calling `Labels()` on deleted namespaces prevents spurious error logs and avoids polluting logs during normal namespace deletions.
