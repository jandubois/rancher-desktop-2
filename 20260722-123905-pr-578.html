Executive Summary ¶

Moving the host-switch into the per-VM hostagent is the right ownership model: it deletes six teardown call sites, a mutex, and an atomic.Bool, and replaces them with OS reclamation that no future shutdown path can forget. Three issues survive verification, all in the seam between the new host and the moved code: a cancellation contract that never fires, lost error severity, and a doc guarantee the retry loop does not implement.

Gemini 3.1 Pro hit an exhausted quota and produced no output. The findings below come from Claude, Codex, and Gemini 3.5 Flash. I verified each one against the worktree at the review SHA.

### Bridge Failure Recovery

If the bridge dies on its own while the VM keeps running (for example the vsock data plane wedges), the guest loses DHCP/DNS/NAT. `hostswitch.Run` detects the unexpected exit and restarts the bridge internally, rate-limited to one attempt per 15 seconds. The VM and hostagent keep running; the reconciler is not involved.

### Crash Recovery

If the hostagent crashes, its host-switch goroutine dies with it and the OS reclaims the host resources. The watcher detects the exit and triggers a reconcile; the reconciler relaunches the hostagent, which starts a fresh host-switch.

The named example is the one case not covered. vn.AcceptStdio errors are logged and the accept loop continues (hostswitch_windows.go:225-251); even the relayDropWarnThreshold escalation only emits diagnostics. runOnce returns solely on an ln.Accept() failure, so a wedged data plane behind a live listener never engages the supervisor.

Concerns ¶

  1. The Docker named pipe is still unscoped, and the socketbridge error is still swallowed (in-scope) Codex GPT 5.6 Sol Gemini 3.5 Flash

socketbridge.NewDockerHostBridge binds the well-known \\.\pipe\docker_engine, which Docker Desktop also owns, and the errgroup goroutine at hostswitch_windows.go:202-208 logs the failure then returns nil, so the new supervisor never retries it. The engine controller dials the same path and accepts any successful ping, so Docker Desktop's daemon can be mirrored and its containers force-removed.

This code moved verbatim; the PR neither introduces nor worsens it, and deep-review-context.md already records it. Raising it here only because the move is the natural moment to scope the pipe to the instance.

  1. Bridge failure lost its structured signal (future) Claude Opus 4.8

The old path emitted a HostSwitchRestarted Warning event and set a failed flag the reconciler could read. networking.md:141 documents the new arrangement as deliberate, but a permanently wedged bridge is now invisible to rdd ctl describe limavm and to App-level readiness. The hostagent could emit a lima events.Event with Status.Errors on stdout, which hostagent_watcher.go:97 already parses, letting the reconciler surface a condition without owning the restart.

  1. Restarts accumulate gvisor stacks (future) Claude Opus 4.8

virtualnetwork.VirtualNetwork exposes no Close in gvisor-tap-vsock v0.8.9, so each pass through runOnce leaves the previous netstack and its goroutines behind. The old design had the same property at the same 15s rate, so this is a gap rather than a regression, but a hostagent surviving a long crash loop now accumulates them for the VM's whole life.

Testing Assessment ¶

No test accompanies the move, and the retry loop is the one piece of new logic (S2). Beyond that seam, four gaps stand out:

  1. Clean-shutdown classification. Nothing distinguishes a cancelled stop from a failure, which is exactly the distinction I1 shows is currently impossible to reach.
  2. The non-WSL2 early return. hostswitch_other.go:22 and the VMType guard at hostswitch_windows.go:120-122 are the only protection against the host-switch firing on a vz/qemu instance; neither is asserted.
  3. Hostagent startup with store.Inspect failing. The new fatal path at command.go:173-175 has no coverage (S1).
  4. Windows lifecycle. Hostagent exit releasing the pipe, vsock, and forwarded ports is untested, as is the engine controller refusing a foreign Docker daemon.

BATS adds nothing here, and the Windows path is untestable in the current matrix. A non-Windows assertion that rdd limavm start/stop still works would at least cover the new pre-boot inspect on macOS and Linux.

Review Process Notes ¶

Skill improvements ¶

  • [ ] When a finding depends on a context's cancellation semantics, trace the context to its origin before accepting or rejecting it. A ctx obtained from a framework accessor (cmd.Context(), a request context, an injected field) may be a background context that is never cancelled, which silently converts every <-ctx.Done() branch and every ctx.Err() check into dead code while the surrounding comments and design docs continue to describe cancellation as the shutdown path. Verify the entry point actually installs a cancellable context rather than assuming the accessor implies one.
  • [ ] Treat a design document's own example as a claim to verify, not as context. When a doc names a specific failure mode as the one a recovery mechanism handles, trace that exact scenario through the code. Illustrative examples are written from intent and are the most likely part of a document to outrun the implementation, particularly when the mechanism recovers from a different, coarser class of failure than the example describes.
  • [ ] When a PR moves code between processes or ownership domains, diff the logging path as carefully as the logic. An adapter inserted at the new boundary (a logr sink, a writer wrapper, a formatter callback) can silently drop severity, redirect a stream to a file nothing propagates, or change which log the operator actually reads. Verify that an error raised in the moved code still reaches an operator at error level, and name the file it lands in.

Repo context updates ¶

  • [ ] [repo] The rdd CLI reaches cobra through cli.RunNoErrOutput (k8s.io/component-base/cli) → cmd.Execute(), never ExecuteContext, and nothing calls SetContext. So cmd.Context() inside any subcommand's RunE is context.Background() and is never cancelled, on any platform. Subcommands that need shutdown propagation must derive their own cancellable context and cancel it explicitly; on Windows the shutdown request arrives through the named interrupt event registered by process.RegisterInterruptHandler, not through a signal, so signal.NotifyContext alone is not sufficient. Reject findings that assume cmd.Context() cancels on SIGTERM, and flag new code whose cleanup depends on it.
  • [ ] [repo] RDD calls lima's hostagentevents.Watch with propagateStderr=false (rdd/pkg/controllers/lima/limavm/controllers/hostagent_watcher.go), so anything the hostagent writes to stderr stays in that instance's ha.stderr.log and never reaches the daemon log. Only lima events on hostagent stdout drive reconciler behavior. When reviewing code that logs from inside the hostagent process, do not treat a log call as operator-visible in rdd.stderr.log, and check whether a failure needs a lima events.Event (which the watcher parses) rather than a log line.
  • [ ] [repo] store.Inspect called from inside the hostagent process is not free and not equivalent to calling it from the reconciler. The hostagent writes its own PID file early, so Inspect takes the HostAgentPID != 0 branch and makes a 3s-capped HTTP round-trip to the hostagent's own API socket; on Windows the WSL2 driver's InspectStatus also shells out to wsl.exe --list --verbose. Flag a synchronous Inspect on the hostagent's pre-boot path, especially under a context that is never cancelled.
  • [ ] [repo] virtualnetwork.VirtualNetwork (gvisor-tap-vsock v0.8.9) exposes no Close, so every host-switch restart leaks the previous netstack and its goroutines. Treat "restart the bridge" designs as accumulating, and judge a restart loop by whether it bounds attempts or documents the leak, not by whether it tears the old network down.
