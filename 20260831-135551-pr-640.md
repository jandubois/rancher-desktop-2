## Executive Summary

This PR adds an `ImagePullRequest` reconciler, a validating webhook, progress
status fields, and a moby-backed `pullImage`, alongside a `Complete`→`Settled`
condition rename and a reconciler split. The state machine is careful and
unusually well unit-tested. Five Important defects survived verification: the
bulk reconcile path discards every requeue, two documented failure reasons are
unreachable, a stale progress callback writes onto a recreated request, the
refactor lost workqueue coalescing, and progress writes are unthrottled.

Four reviewers ran. Codex timed out without emitting a review, but the probe
tests it left in `.scratch/` were recovered, executed, and contributed two
findings no other reviewer raised (I3, S2). Findings marked *reproduced* or
*measured* are backed by the programs under Reproductions below, each executed
against the review SHA; `go build` and `go test -race` are otherwise clean on
every changed package.

## Important Issues

I1. **Bulk reconcile discards every `ctrl.Result`, stranding requests** — `rdd/pkg/controllers/app/engine/controllers/image_pull_request_reconciler.go:105` [Claude Opus 5, Codex GPT 5.6 Sol]

```go
		for _, imagePullRequest := range imagePullRequestList.Items {
			if _, err := r.reconcileSingleImagePullRequest(ctx, e, &imagePullRequest); err != nil {
```

`reconcileSingleImagePullRequest` returns its `RequeueAfter` through the first
slot and the loop throws it away, returning `ctrl.Result{}` at line 112.

Reproduced: a request persisted as `Settled=False/Pulling` with a stale
`LastUpdateTime` and no in-memory state (post-restart), driven through the
engine-became-available branch, queues `desiredReason="PullTimeout"` in memory,
returns `RequeueAfter:0`, and stays `Settled=False/Pulling` — nothing ever
applies the terminal reason. A pull started from this path likewise loses its
30s requeue, so the timeout never fires.

Applying the fix below makes that probe pass and makes
`TestEngineImagePullRequestReconcileBulkProcessesPendingRequests` fail at
`image_pull_request_reconciler_test.go:174` — it asserts `ctrl.Result{}` and so
pins the bug as correct. That assertion must change with the fix.

Fix: accumulate the smallest non-zero `RequeueAfter` across the loop and return it.

Reproduction: [Reproductions → I1](#i1-bulk-reconcile-strands-a-request).

I2. **`Unauthorized` and `InvalidArgument` are unreachable in production** — `rdd/pkg/controllers/app/engine/controllers/image_pull_request_reconciler.go:292` [Claude Opus 5]

```go
		cancel := r.setImagePullRequestTerminalReason(
			imagePullRequest,
			failedConditionReasonPullFailed,
```

Both documented reasons require `cerrdefs` classification, and neither path
delivers it. Streamed pull errors reach `docker_watcher.go:497` with
`Code == 0`, because moby's `FormatError` wraps a non-`*jsonstream.Error` as
`&jsonstream.Error{Message: err.Error()}` and leaves `Code` unset
(`moby/v2@v2.0.0-beta.18/daemon/internal/streamformatter/streamformatter.go:37`;
only the builder ever sets a code). So `pullImage` always takes the `Code == 0`
branch and emits a bare `errors.New`, defeating the switch in `onComplete`.

Synchronous failures *are* classified — the client maps the HTTP status through
`errhttp.ToNative` (`client@v0.5.1/errors.go:98`) — but they arrive at line 290
and are hardcoded to `PullFailed`, discarding it. `api_containers.md` documents
two reasons the code cannot produce.

Fix: extract the classification switch into a helper and apply it at line 292 as well as in `onComplete`.

I3. **Stale progress callback writes onto a recreated request** — `rdd/pkg/controllers/app/engine/controllers/image_pull_request_reconciler.go:211` [Codex GPT 5.6 Sol]

```go
			err := r.Client.Get(pullContext, client.ObjectKeyFromObject(imagePullRequest), &request)
```

`onProgress` re-fetches by name/namespace with no UID check, so an in-flight
pull keeps writing after its request is deleted and a new one is created under
the same name. The guard exists elsewhere in the same file —
`reconcileImagePullRequestTerminalReason:320` checks `latest.UID !=
imagePullRequest.UID` with the comment "The request was deleted and recreated;
don't apply the reason" — but the progress path never got it.

Reproduced: an `alpine:latest` pull's progress callback, fired after the request
was replaced by a `busybox:latest` one of the same name, wrote
`Start:1 Current:2 Total:3` and a `Settled=False/Pulling` condition onto the new
object. Requests named deterministically by the caller (or recreated after the
TTL sweep) hit this directly.

Fix: carry the UID into `onProgress` and skip the update when it does not match, mirroring line 320.

Reproduction: [Reproductions → I3, S2](#i3-s2-codex-s-recovered-probes).

I4. **Refactor lost workqueue coalescing for mirror events** — `rdd/pkg/controllers/app/engine/controllers/engine_reconciler.go:220` [Claude Opus 5]

```go
			return []engineRequest{{
				Kind:           kind,
				NamespacedName: client.ObjectKeyFromObject(obj),
				UID:            obj.GetUID(),
			}}
```

At the merge-base every Container/Image/Volume/ContainerNamespace event mapped
to the single request `{Name: "app"}`, which the workqueue's dirty set collapsed
into one item. Each object now yields a distinct key, but `Reconcile` ignores
`Name`/`UID` for all five non-`ImagePullRequest` kinds and runs the same
object-independent `reconcileWatcher`.

Measured with the two key schemes and 500 mirror events: merge-base reaches
queue depth **1**, this PR reaches **500**. Each of those reconciles runs two
List passes — `watch_reconciler.go:135-141` already calls the cost "O(N) per
child event" — so a fullSync burst goes from O(N) to O(N²).

Fix: return a constant key for every kind except `ImagePullRequestKind`.

Measurement: [Reproductions → I4](#i4-lost-workqueue-coalescing).

I5. **Progress writes are unthrottled against the embedded control plane** — `rdd/pkg/controllers/app/engine/controllers/image_pull_request_reconciler.go:219` [Gemini 3.1 Pro, Claude Opus 5]

```go
			request.Status.LastUpdateTime = metav1.Now()
			request.Status.Start = start
			request.Status.Current = current
```

Every progress callback commits a `Status().Update` to kine/sqlite, bumps
`resourceVersion`, broadcasts to watchers, and re-enqueues this reconciler
through the `ImagePullRequest` watch — so each progress message also costs a
full reconcile pass.

Moby does throttle upstream, contrary to how this was first reported: a 512 KB
(or 1%-of-layer) byte gate plus a `rate.Every(100 * time.Millisecond)` limiter
(`client@v0.5.1/pkg/progress/progressreader.go:30,37-47`) caps it at ten
messages per second per layer. With docker's default of three concurrent layer
downloads that is roughly 30 writes/second sustained for the length of the pull.
That bound is read off the moby constants, not measured against a running daemon.

Fix: skip the write when the stored `LastUpdateTime` is under ~1s old and `total` has not been reached; the 60s timeout check tolerates coarse timestamps.

## Suggestions

S1. **`context.AfterFunc` stop function discarded, one registration leaked per pull** — `rdd/pkg/controllers/app/engine/controllers/image_pull_request_reconciler.go:201` [Claude Opus 5, Gemini 3.1 Pro, Gemini 3.5 Flash]

```go
	context.AfterFunc(r.watcherCtx, func() { pullCancel(r.watcherCtx.Err()) })
```

`AfterFunc` registers a child on `r.watcherCtx` via `propagateCancel`
(`GOROOT/src/context/context.go:326-330`); the entry is removed only by the
returned `stop` or by the parent's cancellation. Cancelling `pullContext` does
not unregister it, and `watcherCtx` lives for the whole manager, so every pull
adds a permanent entry.

Measured: 100,000 registrations retain 27,511,160 bytes — about 275 bytes per
pull, never reclaimed. Calling `stop()` retains nothing. Small in absolute terms
but unbounded, which is why it sits here rather than under Important; all three
reviewers that raised it rated it higher.

Fix: keep the returned stop function and call it once the pull terminates, alongside the `defer cancel()` in `onComplete`.

Measurement: [Reproductions → S1](#s1-context-afterfunc-retention).

S2. **Deleting a request while the engine is down never cancels the pull** — `rdd/pkg/controllers/app/engine/controllers/image_pull_request_reconciler.go:91` [Codex GPT 5.6 Sol]

```go
	if e == nil {
		// The engine is not ready yet; ignore the reconcile request, it will get
		// triggered again when the engine is connected.
		return ctrl.Result{}, nil
	}
```

The early return precedes the delete-detection branch at lines 116-129, so when
the engine disconnects mid-pull and the user then deletes the request, the
in-flight pull is never cancelled and its `imagePullRequestState` entry is never
removed. `onComplete` later takes the `IsNotFound` path and returns without
touching the map, so the entry leaks permanently.

Reproduced: with `r.engine == nil` and a live cancel func in the state map,
reconciling a deleted request leaves `context.Cause(pullCtx) == nil`.

Fix: move the `e == nil` check below the deletion and settled branches — neither needs an engine.

Reproduction: [Reproductions → I3, S2](#i3-s2-codex-s-recovered-probes).

S3. **`status.start` can never be populated by the moby backend** — `rdd/pkg/apis/containers/v1alpha1/image_types.go:128` [orchestrator]

```go
	// Start is the initial progress of the image pull request.
	//
	// +optional
	Start int64 `json:"start,omitempty"`
```

The daemon builds its progress payload from `Current`/`Total`/`HideCounts`/`Units`
only (`moby/v2@v2.0.0-beta.18/daemon/internal/streamformatter/streamformatter.go:99-104`),
and its internal `progress.Progress` has no `Start` field at all
(`daemon/internal/progress/progress.go:8-28`). So `msg.Progress.Start` is always
zero and this field is permanently zero in practice.

The documented meaning also conflicts with upstream: where moby *does* consume
`Progress.Start` it treats it as a Unix timestamp for ETA
(`client@v0.5.1/pkg/jsonmessage/jsonmessage.go:91`, `time.Unix(p.Start, 0)`), not
a value in `Units`.

Fix: drop `Start` from the API and from `api_containers.md` until a backend populates it, per YAGNI.

S4. **`r.apiNamespace` read from the event goroutine without synchronisation** — `rdd/pkg/controllers/app/engine/controllers/engine_reconciler.go:231` [Claude Opus 5]

```go
				NamespacedName: types.NamespacedName{Namespace: r.apiNamespace},
```

`enqueueRawRequest`'s map function runs on the source's event goroutine while
`watch_reconciler.go:34` writes the field from the reconcile worker. The
merge-base handler returned a constant and read no reconciler state, so this
read is new. `App.spec.namespace` is immutable, so the observed value is always
correct and the practical risk is low — but it is a genuine unsynchronised
read/write that `-race` would flag once a test drives a live manager.
`container_passthrough.go:72` already reads the same field from the HTTP handler
goroutine, so this widens an existing gap rather than introducing one.

Fix: resolve the namespace inside `Reconcile` from the `App` it already fetches, or guard the field.

S5. **Condition reasons are bare string literals** — `rdd/pkg/controllers/app/engine/controllers/image_pull_request_reconciler.go:340` [Claude Opus 5, Gemini 3.1 Pro]

```go
		settledReason := "ImagePulled"
		failedStatus := metav1.ConditionFalse
		failedReason := "Succeeded"
```

The `Failed` reasons have typed constants, but `"Pulling"`, `"ImagePulled"`,
`"Errored"` and `"Succeeded"` are literals — and line 157 compares
`settledCondition.Reason == "Pulling"` by string. `api_containers.md` and
`image-docker.bats:34-36` are now external consumers of those exact spellings, so
a typo breaks the BATS wait with no compile error.

Fix: export them from `image_types.go` beside `ImagePullRequestConditionSettled`.

S6. **Documented `Failed` reason table omits the success case** — `rdd/docs/design/api_containers.md:361` [Claude Opus 5]

Every settled request carries a `Failed` condition, and on success it is
`Status=False, Reason=Succeeded` (`image_pull_request_reconciler.go:341-342`,
asserted by `image-docker.bats:36`). The table lists only the four `True` reasons
and reads as exhaustive.

Fix: add a `Succeeded / False` row and bump the `rowspan` to 5. Note also that markdown inside the raw `<table>` block is not processed, so the `` `message` `` backticks render literally — use `<code>message</code>`.

S7. **Progress fields cleared on settle, contradicting the documented example** — `rdd/pkg/controllers/app/engine/controllers/image_pull_request_reconciler.go:333` [Claude Opus 5]

```go
		// Clear the progress fields, so a retry doesn't abort early.
		latest.Status.LastUpdateTime = metav1.Time{}
		latest.Status.Start = 0
		latest.Status.Current = 0
```

No path takes a request out of the settled state: line 139 routes every
`Settled=True` object to the terminal handler, and the webhook makes `spec`
immutable, so the "retry" this guards against does not exist. Meanwhile
`api_containers.md:331-341` shows a settled request with `lastUpdateTime`,
`current`, `total` and `units` all populated, and documents `lastUpdateTime` as
"the last time any progress has been made". A client reading final byte counts
after settle finds zeros.

Fix: drop the five assignments, or amend the doc example and field list to say the fields are cleared on settle.

S8. **New BATS suite forces a VM boot it does not need** — `rdd/bats/tests/32-app-controllers/image-docker.bats:11` [Claude Opus 5]

```bash
    setup_rdd_control_plane

```

`setup_rdd_control_plane` runs an unconditional `rdd svc delete` before create,
so the suite pays a full VM boot. `start_docker_engine`
(`rdd/bats/helpers/docker.bash:14-19`) exists for exactly this case: its
`load_var DOCKER_ENGINE_BOOTED` guard reuses a VM booted by an earlier file in

S9. **Negative BATS assertion is weak, and prefers a non-idiomatic form** — `rdd/bats/tests/32-app-controllers/image-docker.bats:61` [Claude Opus 5, Gemini 3.1 Pro]

```bash
    assert_output ""
```

Two points. No `Image` mirror could exist for a registry that never resolves, so
this passes whether or not the reconciler behaves correctly — it would also pass
against a typo in the field selector, leaving the preceding
`Failed reason PullFailed` check carrying the test. Separately, `refute_output`
with no argument is the repo's idiom for the empty case (see
`assert_single_mirror` in `engine-docker.bats`).

Fix: assert positively on something only the failure produces — that the `Failed` condition's message names the repo tag — and keep the absence check as secondary, written as `refute_output`.

S10. **WSL probe misses `WSLInterop-late` (latent)** — `rdd/bats/helpers/os.bash:14` [Claude Opus 5]

```bash
    if [[ -e /proc/sys/fs/binfmt_misc/WSLInterop ]]; then
```

WSL registers the interop binfmt entry as `WSLInterop-late` when systemd is
enabled, and it can disappear entirely on distro teardown
([microsoft/WSL#13449](https://github.com/microsoft/WSL/issues/13449),
[rancher-sandbox/rancher-desktop#10049](https://github.com/rancher-sandbox/rancher-desktop/issues/10049)).
The merge-base check on `/proc/sys/kernel/osrelease` was immune to this.

This is latent, not a live break: RD2 runs BATS under MSYS2, where `uname`
yields `MINGW*` and line 20 wins, and running BATS inside WSL is not supported
because restarting WSL kills the run. CI never reaches this branch.

Fix: since the suite does not want to run in WSL at all, failing fast with an explanatory message fits the constraint better than detecting WSL more accurately.

S11. **"Concept stage" caution removed while four of five request types are unimplemented** — `rdd/docs/design/api_containers.md:1` [Claude Opus 5]

The PR deletes the `> [!CAUTION] … still in the concept stage` banner.
`ImagePullRequest` is now real, but `ContainerCreateRequest`, `ImagePushRequest`,
`ImageScanRequest` and `VolumeCreateRequest` appear only in `crd.yaml` files —
no Go controller exists for any of them — and the document still contains
"#### Build image — Not sure; do something with the `Resource` API maybe?".
A reader now takes the whole document as an implemented contract.

Fix: keep a scoped caution noting that only `ImagePullRequest` is implemented, and only for the moby backend.

S12. **`RequeueAfter: time.Microsecond` as an immediate-requeue idiom** — `rdd/pkg/controllers/app/engine/controllers/image_pull_request_reconciler.go:166` [Claude Opus 5]

```go
			return ctrl.Result{RequeueAfter: time.Microsecond}, nil
```

The intent is "requeue now", but a sub-tick duration reads as an arbitrary
constant, the test pins the literal
(`image_pull_request_reconciler_test.go:317`), and nothing else in the package
uses this shape.

Fix: apply the terminal reason inline as `onComplete` already does at line 280, or name the constant and say why a zero `RequeueAfter` will not do.

## Design Observations

### Concerns

**The webhook makes the reconciler's "engine not ready" path nearly unreachable** `(in-scope)` [Claude Opus 5]. `imagePullRequestValidator.validate` rejects a request whose `spec.namespace` names a `ContainerNamespace` that does not exist, and `ContainerNamespace/moby` is created by the engine controller's fullSync and swept by `cleanupMirrorResources` when the app stops. So a client cannot queue a pull while the engine is down — yet `reconcileImagePullRequest:91-95` is built around exactly that case, and the whole `req.UID == ""` bulk-scan branch exists to serve it. The two mechanisms encode opposite assumptions about who waits. Worth settling explicitly: either relax the webhook so requests can be queued ahead of the engine, or drop the queue-for-later machinery.

**A daemon restart mid-pull surfaces as `PullTimeout`, never a resume** `(future)` [Claude Opus 5]. Once `Settled=False/Pulling` is persisted, nothing re-enters `e.pullImage` for that object; the reconciler only waits out the clock and settles as timed out. After a restart the pull is provably dead, so the wait buys nothing and the reason misleads. Treating a `Pulling` request with no in-memory state as orphaned and restarting it would be both faster and more accurate.

**`Failed=False, Reason=Succeeded` is an awkward encoding** `(future)` [Claude Opus 5]. A condition named `Failed` carrying the reason `Succeeded` reads oddly in `kubectl` output and in the BATS test name. `Settled` already distinguishes `ImagePulled` from `Errored`, so `Failed` is redundant on the success path.

**No private-registry authentication** `(future)` [Gemini 3.5 Flash]. `ImagePullRequestSpec` carries only `repoTag`, with no credential or secret reference, so only public images can be pulled. Worth stating as a known limitation in the design doc rather than leaving it implicit.

### Strengths

**Cancel-cause plumbing** [Claude Opus 5]. Making `imagePullRequestReason` an `error` so it can ride `context.CancelCauseFunc`, then testing it with `errors.AsType` in `onComplete`, cleanly separates "we already decided the outcome" from "something else cancelled us."

**Settled re-checks inside the retry closure** [Claude Opus 5]. Every status write re-checks `IsStatusConditionTrue(Settled)` inside its `RetryOnConflict` body, so a late progress callback cannot resurrect a settled request even if it wins the initial read — the conflict forces a re-read that sees the terminal state.

**Refactor ordering and mechanics** [Claude Opus 5]. Splitting `watch_reconciler.go` out before adding the second reconcile path is the right sequence, and a function-set diff against the merge-base confirms the move is mechanical apart from the `reconcileWatcher` extraction and the `watcher`→`engine` rename.

**`newDockerWatcher` takes a plain `enqueue func()`** [Claude Opus 5]. Replacing the `chan<- event.GenericEvent` parameter puts the buffering policy with the reconciler that owns the channel.

**Referential-integrity webhook** [Gemini 3.5 Flash]. Validating that the referenced `ContainerNamespace` exists before admission prevents a class of invalid requests reaching the reconciler at all — see the first concern for the tension this creates.

## Testing Assessment

Unit coverage of the new reconciler is unusually thorough: 17 test functions
covering engine-not-ready, UID mismatch, bulk processing, both terminal reasons,
timeout, progress, immediate pull error, TTL delete and owner-reference
retention, plus three webhook tests and a stream-error classification test.
`go build ./...` (clean apart from the pre-existing `pkg/guestagent` embed of a
build artifact) and `go test -race -count=1` on both changed package trees pass —
executed against the review SHA, not inferred.

The error-classification test is load-bearing, contrary to what its
compare-two-derived-booleans shape suggests: removing the `errhttp.ToNative`
wrapping from `pullImage` fails both the invalid-argument and unauthorized
subtests at `docker_watcher_test.go:95-96`.

Gaps, highest risk first:

1. **The bulk path's dropped result (I1).** `TestEngineImagePullRequestReconcileBulkProcessesPendingRequests:174` asserts `ctrl.Result{}`, pinning the bug. Fixing I1 requires changing that assertion.
2. **Delete/recreate under the same name (I3).** No test covers a progress or completion callback outliving its object; the UID guard that exists at line 320 has no counterpart test.
3. **Real moby error classification (I2).** The stream test fabricates an `errorDetail.code` the daemon never sends, and nothing covers the synchronous `ImagePull` error path where errdefs sentinels actually arrive.
4. **Restart recovery.** Nothing exercises a request surviving a process restart with empty `imagePullRequestState`.
5. **Callback concurrency.** Every test invokes `pullImageHook` synchronously on the reconcile goroutine, so the real callback-on-another-goroutine ordering is never exercised.
6. **BATS timing.** `wait_for_resource_condition` caps at `try --max 30 --delay 1`; the success test must pull `registry.suse.com/bci/bci-nano:latest` inside 30s on a cold VM across three runners. Worth watching for flakes.

## Documentation Assessment

`api_containers.md` is a genuine deliverable here and is mostly accurate — the
condition tables match the implementation, and the new status fields are
documented individually. The defects are S3 (`start` cannot be populated), S6
(missing `Succeeded` row), S7 (example shows fields the code clears), S11
(caution removed prematurely), and I2 (two documented reasons the code cannot
produce). Two further gaps: `spec.repoTag`/`spec.namespace` immutability is now
enforced by the webhook but appears nowhere in the doc, and the TTL is documented
as "at least one minute" while the code uses ten — accurate but unhelpful for a
client deciding how long it may read results.

Godoc coverage on the new Go code is complete, including the new `*Kind` and
condition constants.

## Review Process Notes

### Skill improvements

- [ ] When an agent hits its deadline without emitting a review, inspect its `.scratch/` directory before recording it as failed. An agent that spends its budget writing and running probe programs leaves reproductions behind that are stronger evidence than the prose review would have been; execute them against the lead worktree and attribute the resulting findings to that agent. Only after that comes up empty should the retry budget be spent.
- [ ] When a finding asserts that an external system emits events at some rate, locate the emitter's own throttling before accepting the rate. Producers of progress or event streams commonly rate-limit at the source, so a claim of "unthrottled" or "N per second" usually rests on the reviewer's intuition rather than the emitter's code; the corrected bound often changes the severity without changing the underlying concern.
- [ ] When a finding says a value returned by an inner call is discarded, check whether any other path can supply that value before rating it. A dropped error is usually cosmetic because the operation retries, but a dropped scheduling or continuation token often has no alternative producer, which turns a tidiness nit into stranded state — and the difference is only visible by looking for the second producer.
- [ ] When a guard against a hazard appears at one call site, grep for the other call sites that share the hazard. A comment explaining why a check exists is evidence the author knew about the failure mode; its absence at a sibling site is more likely an oversight than a deliberate exemption, and this asymmetry localises real bugs faster than reading either site alone.

### Repo context updates

- [ ] [repo] On Windows this repo runs its BATS suite under MSYS2, not inside WSL: CI invokes `C:\msys64\usr\bin\bash.exe`, so `uname` reports `MINGW*`/`MSYS*`. Running BATS inside WSL is unsupported because restarting WSL kills the test process. The WSL-detection branch in `rdd/bats/helpers/os.bash` is therefore latent — treat defects in it as latent rather than as live regressions.
- [ ] [repo] The engine reconciler is a cluster-scoped singleton whose `reconcileWatcher` pass is object-independent and issues several List calls per invocation. When reviewing changes to its event handlers, check whether mirror-resource events still map to a single constant workqueue key: giving each object its own key defeats the workqueue's dedup and turns a fullSync burst from O(N) into O(N²).
- [ ] [repo] `*Request` CRDs in this repo use paired `Settled` and `Failed` conditions, where `Settled=True` marks any terminal state and `Failed` distinguishes the outcome; a successful request carries `Failed=False, Reason=Succeeded`. Only `ImagePullRequest` has a controller — the other `*Request` types exist as CRD schema with no reconciler, so a finding that one of them "does nothing" is expected, not a defect.

```go
	"context"
	"fmt"
```

```go
	context.AfterFunc(r.watcherCtx, func() { pullCancel(r.watcherCtx.Err()) })
```

`AfterFunc` registers a child on `r.watcherCtx` and returns a `stop` function; discarding it leaves the registration in `watcherCtx`'s children map until manager shutdown. Cancelling `pullContext` does not unregister it. `watcherCtx` lives for the whole daemon, so every image pull adds a permanent entry. Small in absolute terms, but unbounded.

Fix: keep the stop function and call it once the pull terminates.

```diff
-	context.AfterFunc(r.watcherCtx, func() { pullCancel(r.watcherCtx.Err()) })
+	stopShutdownHook := context.AfterFunc(r.watcherCtx, func() { pullCancel(r.watcherCtx.Err()) })
```

then call `stopShutdownHook()` alongside the `defer cancel()` in `onComplete` (line ~278) and after the `e.pullImage` error at line 298.

## Design Observations

### Concerns

**The webhook makes the reconciler's "engine not ready" path nearly unreachable.** `imagePullRequestValidator.validate` (`rdd/pkg/controllers/containers/image/image_pull_request_webhooks.go:50-64`) rejects a request whose `spec.namespace` names a `ContainerNamespace` that does not exist, and `ContainerNamespace/moby` is created by the engine controller's fullSync and swept by `cleanupMirrorResources` (`watch_reconciler.go:384-386`) whenever the app stops. So a client cannot queue a pull while the engine is down — yet `reconcileImagePullRequest:91-95` is built around exactly that case ("it will get triggered again when the engine is connected"), and the whole `req.UID == ""` bulk-scan branch exists to serve it. The two mechanisms encode opposite assumptions about who waits. Worth settling explicitly: either the webhook should not require the `ContainerNamespace` to exist yet (leaving the reconciler to hold the request), or the queue-for-later machinery is dead weight for the moby backend. `(in-scope)`

**A daemon restart mid-pull surfaces as `PullTimeout`, never a resume.** Once `Settled=False/Pulling` is persisted, no path re-enters `e.pullImage` for that object — `reconcileSingleImagePullRequest:157-171` only waits out the clock and then settles as timed out. After a restart the pull is provably dead, so the one-minute wait buys nothing and the user gets a misleading reason. A cheap improvement: on the bulk scan, treat a `Pulling` request with no in-memory `imagePullRequestState` entry as orphaned and restart the pull rather than waiting for it to age out. `(future)`

**`Failed=False, Reason=Succeeded` is an awkward encoding.** A condition named `Failed` carrying the reason `Succeeded` reads oddly in `kubectl` output and in the BATS test name ("succeeds and sets Failed reason to Succeeded"). `Settled`'s own reason already distinguishes `ImagePulled` from `Errored`, so `Failed` is redundant on the success path. Consider omitting the `Failed` condition entirely when the pull succeeds, which is closer to Kubernetes convention. `(future)`

### Strengths

- The cancel-cause plumbing is genuinely good: making `imagePullRequestReason` an `error` so it can ride `context.CancelCauseFunc`, then testing it with `errors.AsType` in `onComplete`, cleanly separates "we already decided the outcome" from "something else cancelled us."
- Every status write re-checks `IsStatusConditionTrue(Settled)` inside the `RetryOnConflict` closure, so a late progress callback cannot resurrect a settled request even if it wins the initial read — the conflict forces a re-read that sees the terminal state.
- Splitting `watch_reconciler.go` out of `engine_reconciler.go` before adding the second reconcile path is the right order of operations, and the move is genuinely mechanical (a function-list diff shows only `reconcileWatcher`'s extraction and the `watcher`→`engine` rename).
- `newDockerWatcher` taking a plain `enqueue func()` instead of a `chan<- event.GenericEvent` is a clear improvement: the buffering policy now lives with the reconciler that owns the channel.

### [Gemini 3.1 Pro]

### Executive Summary

This PR successfully introduces an `ImagePullRequest` reconciler and correctly plumbs it to the Moby container engine. However, it ships with a critical scaling hazard: progress events from the Docker API are forwarded to the embedded K8s API server unthrottled, creating massive CPU/disk I/O spikes. There is also an important memory leak caused by an unstopped `context.AfterFunc` registration on the long-lived watcher context.

### Findings

#### Critical Issues

C1. **Unthrottled K8s API updates on Image Pull Progress** — `rdd/pkg/controllers/app/engine/controllers/image_pull_request_reconciler.go:208-228` (critical, regression)

```go
	onProgress := func(start, current, total int64, units string) {
		err := retry.RetryOnConflict(retry.DefaultRetry, func() error {
			var request containersv1alpha1.ImagePullRequest
			err := r.Client.Get(pullContext, client.ObjectKeyFromObject(imagePullRequest), &request)
// ... updates request and calls r.Client.Status().Update ...
```

Docker emits progress messages very rapidly during image layer downloads (often dozens per second). `onProgress` performs a `Client.Get` and `Status().Update` against the embedded kine/sqlite backend for every single progress message. This will cause massive CPU/disk I/O spikes, lock contention, and rapid database bloat in the single-user K8s daemon, especially on large images or fast connections.

Fix: Throttle the K8s API updates by tracking the time of the last update in the closure and only calling `Status().Update` if enough time has passed (e.g., 1–3 seconds), while guaranteeing a final sync on completion.

#### Important Issues

I1. **Context leak via unstopped `context.AfterFunc`** — `rdd/pkg/controllers/app/engine/controllers/image_pull_request_reconciler.go:201-204` (important, regression)

```go
	// Cancel the context on shutdown
	context.AfterFunc(r.watcherCtx, func() { pullCancel(r.watcherCtx.Err()) })
	r.imagePullRequestMu.Lock()
	r.imagePullRequestState[imagePullRequest.UID] = imagePullRequestState{
		cancel: pullCancel,
	}
```

The `stop` function returned by `context.AfterFunc` is discarded. In Go 1.21+, the associated closure and context node are attached to the parent context (`r.watcherCtx`) and remain there until the parent is canceled. Because `r.watcherCtx` lives for the entire uptime of the daemon, the controller permanently leaks an `AfterFunc` node for every `ImagePullRequest` it ever processes.

Fix: Capture the `stop` function and ensure it executes inside the cancel function you store in the state map.

```diff
-	context.AfterFunc(r.watcherCtx, func() { pullCancel(r.watcherCtx.Err()) })
+	stopAfterFunc := context.AfterFunc(r.watcherCtx, func() { pullCancel(r.watcherCtx.Err()) })
+	originalCancel := pullCancel
+	pullCancel = func(cause error) {
+		stopAfterFunc()
+		originalCancel(cause)
+	}
```

##### I1. **Docker image pull stream connection leak** — `rdd/pkg/controllers/app/engine/controllers/docker_watcher.go:482-514` (important, regression)

```go
func (w *dockerWatcher) pullImage(
	ctx context.Context,
	repoTag string,
	onProgress func(start, current, total int64, units string),
	onComplete func(err error),
) error {
	stream, err := w.cli.ImagePull(ctx, repoTag, mobyclient.ImagePullOptions{})
```

At line 482, the reconciler calls the Docker engine's `ImagePull` API, which returns an `io.ReadCloser` stream. A separate goroutine is spawned at line 487 to decode JSON messages from this stream. However, `stream.Close()` is never called, which leaks the underlying network connection and associated file descriptor on every image pull request.

```diff
 	go func() {
+		defer stream.Close()
 		if onComplete == nil {
 			onComplete = func(error) {}
 		}
```

##### I2. **Memory leak of AfterFunc closures on long-lived watcher context** — `rdd/pkg/controllers/app/engine/controllers/image_pull_request_reconciler.go:201` (important, regression)

```go
	// Cancel the context on shutdown
	context.AfterFunc(r.watcherCtx, func() { pullCancel(r.watcherCtx.Err()) })
```

At line 201, `context.AfterFunc` registers a callback on `r.watcherCtx` to cancel `pullContext` when the manager shuts down. Since `r.watcherCtx` is a long-lived context that persists for the entire lifecycle of the daemon, and the returned `stop` function is never called when the pull request finishes, these registered callbacks (and their captured closures/contexts) accumulate in memory for every `ImagePullRequest` processed.

Fix: Declare a `stop` handle and call it inside `onComplete` to unregister the callback upon pull completion.

```diff
-	// Cancel the context on shutdown
-	context.AfterFunc(r.watcherCtx, func() { pullCancel(r.watcherCtx.Err()) })
+	var stopAfterFunc func() bool
+	// Cancel the context on shutdown
+	stopAfterFunc = context.AfterFunc(r.watcherCtx, func() { pullCancel(r.watcherCtx.Err()) })
...
 	onComplete := func(err error) {
+		if stopAfterFunc != nil {
+			stopAfterFunc()
+		}
 		r.imagePullRequestMu.Lock()
```
