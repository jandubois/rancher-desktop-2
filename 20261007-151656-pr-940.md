## Executive Summary

The PR vendors ScoopInstaller/Shim's C++ shim as `rdd-forwarder` and changes its launch so a multicall `rdd` sees the forwarder's name as `argv[0]`. That two-line change matches the README and #931's `.shim` contract. But `scripts/dependencies/rdd.ts` tests `goPlatform === 'win32'`, which never holds, so no build compiles the forwarder and Windows packages ship without it. Once it builds, three more gaps matter. It links the runtime dynamically, it lacks a signing entry, and its error message no longer names the missing target.

## Critical Issues

C1. **No build compiles the forwarder, so Windows packages ship without it** — `scripts/dependencies/rdd.ts:14-16` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]

```ts
    if (context.goPlatform === 'win32') {
      targets.push('build-forwarder');
    }
```

`goPlatform` is a `GoPlatform`, `'linux' | 'darwin' | 'windows'` (`scripts/lib/dependencies.ts:18`), and `scripts/postinstall.ts:192` maps a `win32` host to `'windows'`; line 22 passes the same value as `GOOS`. So `build-forwarder` never joins the targets, nothing else builds it, and electron-builder's filter at `packaging/electron-builder.yml:56` copies nothing without complaint.

The head commit's `windows-11-arm` package job shows it. Postinstall's `make` built only `rdd.exe` and `mock-controller.exe`, the log does not mention `clang++` or `shim.cpp`, and the job passed. After #931 merges, its `linkForwarders` returns `locate forwarder` before publishing anything, and the service only logs that, so Windows installs do not get any tools in `~/.rd2/bin`. `tsc` rejects the comparison (TS2367), but no CI job type-checks `scripts/`.

## Important Issues

I1. **The build links the MinGW runtime dynamically, but the forwarder must be static** — `rdd/Makefile:269-273` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]

```make
FORWARDER_CXXFLAGS := -std=c++20 -O2 -municode -fno-exceptions -fno-rtti \
	-ffunction-sections -Wl,--gc-sections -s

bin/rdd-forwarder.exe: $(FORWARDER_SRC)
	$(FORWARDER_CXX) $(FORWARDER_CXXFLAGS) $< -lshell32 -o $@
```

The forwarder has to be a static binary with no DLL dependencies (@jandubois, during this review). Upstream builds it that way: its `shim.vcxproj:102` sets `<RuntimeLibrary>MultiThreaded</RuntimeLibrary>`, and its `cpp/README.md` promises "statically linked, zero runtime dependencies". MinGW-w64 `g++`, which the Makefile picks for x86_64, links `libstdc++-6.dll` and `libgcc_s_seh-1.dll` dynamically unless told otherwise, and the shim uses `std::wstring` and `std::vector`. A runner has MinGW's `bin` on `PATH`, so the forwarder would start there. On a user's machine, every forwarded tool would fail at load with a missing-DLL error, before the shim can print a word.

Unproven: the review host lacks a Windows-targeting C++ toolchain, and CI has never compiled the recipe (C1). After C1's fix, `objdump -p rdd/bin/rdd-forwarder.exe | grep 'DLL Name'` in a Windows package job settles it.

Fix: add `-static`, then check both architectures' imports, since the arm64 `clang++` may target MSVC or MinGW.

```diff
-FORWARDER_CXXFLAGS := -std=c++20 -O2 -municode -fno-exceptions -fno-rtti \
+FORWARDER_CXXFLAGS := -std=c++20 -O2 -municode -static -fno-exceptions -fno-rtti \
```

## Suggestions

S1. **`make build-forwarder` fails on a fresh tree** — `rdd/Makefile:272-273` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]

```make
bin/rdd-forwarder.exe: $(FORWARDER_SRC)
	$(FORWARDER_CXX) $(FORWARDER_CXXFLAGS) $< -lshell32 -o $@
```

`rdd/bin` is gitignored (`rdd/.gitignore:1`) and only `go build` creates it, so the standalone `make build-forwarder` the README documents fails with `No such file or directory` unless `build-rdd` ran first. Postinstall runs `build-rdd` first, which hides it. A stand-in compiler in place of `g++` reproduces the failure.

Fix:

```diff
 bin/rdd-forwarder.exe: $(FORWARDER_SRC)
+	@mkdir -p $(@D)
 	$(FORWARDER_CXX) $(FORWARDER_CXXFLAGS) $< -lshell32 -o $@
```

S2. **The RDD change alters more than the `args =` line its comment names** — `rdd/src/rdd-forwarder/shim.cpp:747-751` [Claude Opus 5.5, Gemini 3.1 Pro]

```cpp
    std::wstring cmd = GetCommandLineW();

    // Params are only consumed by ShellExecuteExW; not built on the normal CreateProcessW path.
    if (info.elevate) [[unlikely]]
        return LaunchElevated(path, BuildParams(info.args), cwd, jobHandle);
```

The comment and the README say the change drops only upstream's `args =` injection. But both elevated launches, line 751 and the `ERROR_ELEVATION_REQUIRED` retry at line 786, keep upstream's behaviour. `ShellExecuteExW` makes the target its own `argv[0]` and still appends `args =`, so an elevated `kubectl.exe` would run `rdd`'s own CLI. And `lpApplicationName` resolves a relative `path =` against the current directory instead of the forwarder's own, and does not append `.exe`. None of this is reachable today. #931 writes absolute `.exe` paths and no `elevate` line, and nothing under `rdd/` sets an elevation manifest.

Fix: list these in the README's change description, or have `GetShimInfo` reject `elevate`, `args` and relative paths.

S3. **The README leaves out the MIT half of upstream's dual license** — `rdd/src/rdd-forwarder/README.md:12-13` [Claude Opus 5.5]

```markdown
Imported from [ScoopInstaller/Shim](https://github.com/ScoopInstaller/Shim)
under its **Unlicense** (public-domain dedication) — that is how the upstream
```

Upstream's top-level README says the project "is dual-licensed under the Unlicense or the MIT License", and the `shim.cpp` header this PR replaced read `SPDX-License-Identifier: MIT`. Taking the Unlicense is a valid choice, and it is what permits the Apache-2.0 relicensing. But an auditor comparing against upstream sees an MIT tag removed with no explanation.

Fix: say that upstream offers MIT or the Unlicense, and that Rancher Desktop takes it under the Unlicense.

## Design Observations

### Concerns

- **The first compile on either architecture comes after C1's fix** (in-scope) [Claude Opus 5.5, Codex GPT 6 Astra]. CI has never run the recipe. The `windows-11-arm` image ships LLVM 22.1.8 (runner-images `Windows11-Arm64-Readme.md`), and whether its `clang++` accepts `-municode`, `-Wl,--gc-sections` and `-s` depends on whether it targets MSVC or MinGW; a Clang driver probe accepted `-municode` for an MSVC target. Watch the first package run of both architectures after the fix.
- **`rdd-forwarder.exe` is installed in a directory on `PATH`** (future) [Claude Opus 5.5]. The MSI adds `resources\windows\bin` to `PATH` (`build/wix/main.wxs:91`, `:116`), and `main`'s `linkBinaries` links every file there into `~/.rd2/bin` (`rdd/pkg/binlinks/binlinks.go:99-108`). Until #931 skips it and #448 drops that `PATH` entry, `rdd-forwarder` is a command that fails with `Cannot open shim file`. Staging it in `resources/internal` would keep it off `PATH`.
- **No CI job type-checks `scripts/`** (future) [Claude Opus 5.5, Gemini 3.1 Pro]. Lint runs ESLint only, `tsx` runs `scripts/` without type-checking, and the production build type-checks only the files its bundles include (`scripts/lib/build-utils.ts:333`), so TS2367 in C1 passed CI. A full `tsc --noEmit` at the review SHA, run with the main checkout's `node_modules` linked in, reports 131 errors, so adding the check means clearing those first.

### Strengths

- **The upstream delta is small and marked** [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]. A diff against upstream's `cpp/shim.cpp` at `1877f4ab` shows the license header and the two `MakeProcess` lines the README lists, both tagged `RDD change`. `.clang-format` is byte-identical.
- **`lpApplicationName` keeps the child's identity** [Claude Opus 5.5]. The child's image is the real `rdd.exe`, so `os.Executable()` and `inAppBundle` still see the bundle.
- **The shim matches #931's contract** [Claude Opus 5.5, Codex GPT 6 Astra]. #931 writes `<tool>.shim` holding `path = <absolute path>\r\n`. The shim derives that name by overwriting `exe` with `shim`, and trims the trailing `\r` (`shim.cpp:606`).

## Review Process Notes

### Skill improvements

- When a PR vendors or ports code from an upstream project, stage the upstream tree at the recorded commit and inline the upstream-to-vendored diff in the prompt, and tell agents to compare the build recipe and flags against upstream's own build files as well as the source. A vendored file reviews clean against itself; the defects sit where the local build departs from how upstream builds it (runtime linkage, resources, manifests).
- Before calling a packaging change verified, read the CI log of a job that ran it for the step that produces the new artifact, not only the job's conclusion. A packager that filters a list of files skips a missing one silently, so a green package job proves nothing about whether the new file shipped.

### Repo context updates

- [repo] CI does not type-check `scripts/`. Lint runs ESLint only, `tsx` runs scripts without type-checking, and the production build type-checks only the files its bundles include. A full `tsc --noEmit` reports over a hundred pre-existing errors. When a diff compares or assigns a typed value in TypeScript, check the type by hand or run `tsc` on that file, because a comparison TypeScript would reject still passes CI.
- [repo] In `scripts/`, `DownloadContext.goPlatform` holds Go's names (`linux`, `darwin`, `windows`) and is passed as `GOOS`; `DownloadContext.platform` holds Node's (`win32`). Flag any comparison that mixes the two spellings.
- [repo] Every unsigned `.exe`, `.dll` or `.ps1` in the Windows package must appear in `build/signing-config-win.yaml`, signed or explicitly skipped, or the `sign-win` job, which runs on pushes to `main`, `release-*` and tags, throws. A diff that adds a Windows executable to the package without touching that file breaks `main`'s signing, and PR CI never runs the job.

### [Claude Opus 5.5]

#### PR #940 review: vendor the rdd-forwarder shim for Windows bin links

##### Executive Summary

This PR vendors ScoopInstaller/Shim's C++ shim as `rdd-forwarder`. It changes the launch so a multi-call target sees the shim's own name as `argv[0]`, adds a Makefile target and stages the binary for packaging. The main problem: `scripts/dependencies/rdd.ts` compares `goPlatform` (`linux`, `darwin` or `windows`) with `'win32'`. That comparison is never true, so no build ever compiles the forwarder, and every Windows package silently ships without it. Even once it builds, the binary would not be statically linked and would not be signed.

##### Findings

###### Critical Issues

C1. **The forwarder is never built, so no Windows package ships it** — `scripts/dependencies/rdd.ts:14` (critical, gap)

```ts
    if (context.goPlatform === 'win32') {
      targets.push('build-forwarder');
    }
```

`goPlatform` has type `GoPlatform = 'linux' | 'darwin' | 'windows'` (`scripts/lib/dependencies.ts:18`), and `postinstall.ts:192` sets it to `'windows'`. Line 14 is therefore never true, and `build-forwarder` never runs. I2. **Elevated fallback drops `argv[0]` and breaks multicall dispatch** — `rdd/src/rdd-forwarder/shim.cpp:859-861`

```cpp
        // Target manifest requires elevation: retry through ShellExecuteExW.
        if (err == ERROR_ELEVATION_REQUIRED)
            return LaunchElevated(path, BuildParams(info.args), cwd, jobHandle);
```

The PR authors correctly modified `CreateProcessW` to pass the raw command line (preserving the shim's name as `argv[0]` for `rdd`'s multicall dispatch), but left the `LaunchElevated` fallback untouched. `BuildParams(info.args)` drops `argv[0]` (it joins only the trailing arguments `userArgv[1...]`). If a bundled tool ever triggers `ERROR_ELEVATION_REQUIRED`, `ShellExecuteExW` will launch `rdd.exe` with its own name as `argv[0]`, bypassing the multicall dispatch entirely and running the `rdd` daemon instead of the intended tool.

If elevation is never required for bundled tools, this code is unreachable and can be removed; otherwise, `info.args` must be prefixed with the tool's subcommand name (e.g., `kubectl`) so `rdd` parses it correctly.

#### Executive Summary

I2. **Missing `-static` flag leaves runtime DLL dependencies on MinGW DLLs** — `rdd/Makefile:269-270` (important, regression)

```makefile
FORWARDER_CXXFLAGS := -std=c++20 -O2 -municode -fno-exceptions -fno-rtti \
	-ffunction-sections -Wl,--gc-sections -s
```

MinGW-w64 `g++` dynamically links `libstdc++-6.dll` and `libgcc_s_seh-1.dll` by default. Because `shim.cpp` uses C++ standard library types (`std::wstring`, `std::vector`, `std::optional`, `std::unique_ptr`), building without `-static` produces a binary requiring MinGW runtime DLLs that do not exist in standard Windows environments (`C:\Windows\System32`). When users run hardlinked forwarders (`kubectl.exe`), the OS loader fails with missing DLL errors. Both upstream ScoopInstaller/Shim (`build.zig`, `shim.vcxproj`) and issue #448 specify a zero-runtime-dependency static binary.

Unproven: requires running a MinGW-built binary on a clean Windows machine lacking MinGW on `PATH`.

Fix: Add `-static` to `FORWARDER_CXXFLAGS`.

```diff
--- rdd/Makefile
+++ rdd/Makefile
@@ -269,2 +269,2 @@
-FORWARDER_CXXFLAGS := -std=c++20 -O2 -municode -fno-exceptions -fno-rtti \
+FORWARDER_CXXFLAGS := -std=c++20 -O2 -municode -static -fno-exceptions -fno-rtti \
 	-ffunction-sections -Wl,--gc-sections -s
```

S1. **`bin/rdd-forwarder.exe` target does not ensure output directory exists** — `rdd/Makefile:272-273` (suggestion, enhancement)

S2. **Spawn failure error message omits the target binary path** — `rdd/src/rdd-forwarder/shim.cpp:783-786` (suggestion, enhancement)

```cpp
        std::wstring msg = L"Shim: Could not create process with command '";
```
