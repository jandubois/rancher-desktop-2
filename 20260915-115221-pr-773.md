## Executive Summary

This PR adds the `ComposeProject` and `ComposeUpRequest` API types, a webhook that checks request names, and a context parameter on `RegisterWithManager`. The fields and naming rule follow the design doc, and the build, lint, generated-file, and race checks pass. A probe shows the new context stays live after the manager fails. Three API comments, which `kubectl explain` prints, contradict the code or the spec, and the naming test takes its expected value from the function it tests.

Four reviewers ran. Gemini 3.1 Pro's first run stopped mid-review, and its one retry completed. I ran a reproducer for every Important finding in the lead worktree, two of them envtest probes against a real kube-apiserver, and each fix comes with a patch I tested. The findings fall into four groups: the context contract (I1), API text that the code or the spec contradicts (I2, I4, I5), the naming test (I3), and admission gaps (S1 to S3).

## Important Issues

I1. **The context passed to `RegisterWithManager` stays live after the manager stops** — `rdd/pkg/service/controllers/manager.go:225-227` [Claude Opus 5, Codex GPT 5.6 Sol]

```go
		if err := registration.RegisterWithManager(ctx, mgr); err != nil {
			return fmt.Errorf("failed to register controller %s: %w", registration.GetName(), err)
		}
```

The interface comment added in `011117602` says the context "must be cancelled to signal controller shut down" (`rdd/pkg/controllers/base/controller.go:34-36`).

`Start` passes its caller's context and creates the manager's own context only at line 274. So when a Runnable fails, `mgr.Start` returns and every controller stops, but the registration context stays live. A webhook-setup failure (line 261) leaves it live too.

The embedded daemon then logs the error and blocks on its own context (`rdd/pkg/service/cmd/service.go:934-940`), so a future `docker compose up` started under it keeps running until the daemon exits. External controllers exit the process instead.

No implementor runs long work under the context yet, so nothing leaks today; the compose reconciler would be the first.

## Suggestions

S1. **The schema admits project names that `docker compose` rejects, the empty string included** — `rdd/pkg/apis/containers/v1alpha1/compose_types.go:178-182` [Claude Opus 5, Codex GPT 5.6 Sol]

```go
	// Name is the compose project name.  Immutable once created.
	//
	// +required
	// +kubebuilder:validation:XValidation:rule="self == oldSelf",message="spec.name is immutable"
	Name string `json:"name"`
```

A `+required` string still admits the empty string. The validator admitted both agents' probes, one with empty `spec.namespace` and `spec.name` (named `cmp-cdb4ee2a…`) and the other with an absolute `configs` entry, which the spec defines as relative to `workingDir`.

compose-go rejects an empty project name (compose-go v2.12.1 `loader/loader.go:577-578` in the module cache) and accepts only lowercase letters, digits, `-`, and `_`, starting with a letter or digit (`InvalidProjectNameErr`, line 665). containerd namespaces may contain dots, so `("k8s.io", "foo")` and `("k8s", "io.foo")` both map to `k8s.io.foo`. Compose's grammar has no dots, so enforcing it would make the join unambiguous.

Fix: add `+kubebuilder:validation:Pattern=^[a-z0-9][a-z0-9_-]*$` to `spec.name` and `+kubebuilder:validation:MinLength=1` to `spec.namespace` and `spec.workingDir`; schema rules run before the webhook.

S2. **`workingDir` is called both absolute and "relative to where the RDD process runs"** — `rdd/pkg/apis/containers/v1alpha1/compose_types.go:183-184` [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]

```go
	// WorkingDir is the compose project directory on the host (i.e. relative
	// to where the RDD process runs).  Used to look up any files needed.
```

The phrase means "on the machine that runs RDD", but a reader can also take it as a relative path, resolved against the daemon's working directory. `ComposeProjectStatus.WorkingDir` puts "absolute path" and "relative to where the RDD process runs" in one sentence (lines 93-94).

The spec repeats the wording (`rdd/docs/design/api_containers.md:766-767`), and nothing rejects a relative `workingDir`.

Fix: write "an absolute path on the host that runs the RDD daemon" in the types and the spec, and reject `!filepath.IsAbs(request.Spec.WorkingDir)` in `ValidateCreate` and `ValidateUpdate`, since the field is mutable.

S3. **The webhook intercepts UPDATE only to admit it** — `rdd/pkg/controllers/containers/compose/compose_controller.go:77-82` [Claude Opus 5]

## Design Observations

### Concerns

- **The tree already has a manager-lifetime context that ends on every stop path** (in-scope) [Claude Opus 5]. The engine reconciler derives `watcherCtx` from `context.Background()` and cancels it from a `manager.RunnableFunc` (`rdd/pkg/controllers/app/engine/controllers/engine_reconciler.go:209-225`), and `ImagePullRequest` runs its long pulls under it (`image_pull_request_reconciler.go:257`). controller-runtime cancels a Runnable's context whenever the manager stops, and waits up to the 10 s `GracefulShutdownTimeout` for it to return. A compose reconciler could use the same pattern, which would make `011117602`'s parameter unnecessary. Of its 17 implementors, 16 ignore it, and the 17th, the mock, uses it only during setup. If the parameter stays, apply I1's fix.
- **Deterministic request names allow one `ComposeUpRequest` per project at a time** (future) [Claude Opus 5]. A settled request stays for at least a minute (`api_containers.md:36-38`), so a second `up` in that window fails with AlreadyExists, and an update with an unchanged spec bumps no generation. The spec should say how a client runs `up` again.
- **Reaping can run `docker compose down` on containers the user never deleted** (future) [Claude Opus 5]. `cleanupMirrorResources` deletes every `Container` mirror when the App stops (`watch_reconciler.go:449-466`), so every `ComposeProject` will fall to `HasMembers=False` and be reaped. Deleting a project runs `docker compose down --remove-orphans`, which "may be retried later" (`api_containers.md:720-731`); a retry after the next start removes the project's containers. The spec should say that a project deleted while `HasMembers=False` drops its finalizer without running `down`.

### Strengths

- **The name rule is in a webhook because CEL cannot hash** (in-scope) [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.5 Flash]. CEL transition rules keep `spec.namespace` and `spec.name` immutable, so the name stays consistent with the spec across updates.
- **`+listType=map` keyed on `name`** (in-scope) [Claude Opus 5] makes the API server enforce the spec's rule that each `status.containers` name is unique.
- **The validator does not require the `ContainerNamespace` to exist** (in-scope) [Claude Opus 5], so it avoids the boot-window rejections the `ImagePullRequest` webhook produces.
- **Both binaries register the compose controller** (in-scope) [Claude Opus 5, Codex GPT 5.6 Sol]. The `containers` aggregator's blank import pulls it into `cmd/containers-controller` and the embedded service.

## Review Process Notes

**Skill improvements**

- Quote the liveness monitor's glob. The Monitor tool runs its command in the user's shell, and zsh expands an unquoted `$HOME/.gemini/tmp/review-gemini-pass-1-*/chats/*.jsonl` once, at launch. When stale session directories from earlier reviews match the pattern, the list holds only their files, the new session never counts, and a Gemini run longer than one interval reports STALLED. Single-quote the pattern in Step 4's command and table so `agent-liveness.sh` expands it on every sample, as its header comment assumes.
- Treat a review that lacks its Coverage Summary, or that ends inside a finding, as truncated even when all three severity headings are present. Read the last record of the agent's session log; an empty or zero-token final message is a dropped stream, and the transient-error retry applies.
- Check each agent's executed commands with a parser for its session format (Claude's `tool_use` `input.command`, Codex's function and custom tool-call arguments, and Gemini's `toolCalls[].args.command`). A regex over the raw JSONL misses commands with escaped quotes and matches the prompt's own text, so a zero count from it proves nothing.
- When a change adds a mechanism (a parameter, hook, context, or registry entry) for a feature a later change will build, search the tree for an existing mechanism that serves the same need and compare the two on every exit path, failure paths included. The existing reuse dimension names only the stdlib and installed dependencies.

**Repo context updates**

- [repo] UPDATE: the "Live verification setup" section and the live-verification bullet under "Build, test environment, and CI" invite review agents to build `rdd` and run `rdd svc start`. Review agents must not start services, VMs, or containers on the reviewer's machine, and an override later in the prompt does not stop an agent from following these entries. Replace both: tell agents to judge live behavior from the code and leave live checks to the consolidator.
- [repo] `SharedControllerManager` can run real controllers, with their CRDs and admission webhooks, against envtest (`envtest.Environment{DownloadBinaryAssets: true}`, as `pkg/service/controllers/manager_test.go` does) in about ten seconds. S1. **The schema accepts project names that `docker compose` rejects, and the dot separator can collide** — `rdd/pkg/apis/containers/v1alpha1/compose_types.go:175-182` (suggestion, gap)

### Design Observations

**Concerns**

- **The tree already has a lifetime context that fires on every stop path (in-scope).**
  - The engine reconciler derives `watcherCtx` from `context.Background()` and cancels it from a `manager.RunnableFunc` (`rdd/pkg/controllers/app/engine/controllers/engine_reconciler.go:209-225`). `ImagePullRequest` runs its long pull under that context (`image_pull_request_reconciler.go:255-257`).
  - controller-runtime cancels every Runnable's context on any manager stop, and waits up to `GracefulShutdownTimeout` for it to return (v0.24.1 `pkg/manager/internal.go:499-528`; rdd sets 10 s at `manager.go:152`). So this pattern avoids I1, and shutdown waits for `docker compose up` to wind down.
  - The `compose` package, like `image`, registers only a CRD and a webhook. A reconciler that runs `docker compose` needs the engine connection, so it probably belongs beside `ImagePullRequest`, where `watcherCtx` is already available.
  - Dropping 011117602 would spare 18 implementors a parameter that 17 of them ignore. If the parameter stays, apply I1's fix.
- **Deterministic request names allow only one `ComposeUpRequest` per project (future).** The spec keeps a settled request for at least a minute (`api_containers.md:35-38`), and a second `up` in that window fails with AlreadyExists. An update with an unchanged spec does not bump the generation, so it cannot trigger a rerun either. The spec should say how a client reruns `up`: delete and recreate, an annotation, or a spec field.
- **Reaping collides with the delete finalizer on every App stop (future).**
  - `cleanupMirrorResources` deletes every `Container` mirror when the App stops (`watch_reconciler.go:449-466`), so every `ComposeProject` will drop to `HasMembers=False` and be reaped.
  - Deleting a `ComposeProject` runs `docker compose down --remove-orphans`, and that "may be retried later" (`api_containers.md:722-731`).
  - A retry after the next start would remove the user's containers. The spec should state that a delete seen while `HasMembers=False` removes the finalizer without running `down`.

**Strengths**

- The name rule is in a webhook because CEL cannot hash. CEL transition rules keep `spec.namespace` and `spec.name` immutable, so the name stays consistent with the spec across updates.
- `+listType=map` keyed on `name` makes the API server enforce the spec's "each `name` must be unique" rule for `status.containers`.
- The reason strings are exported constants in the API package, so the reconciler and clients compare against one definition.
- The validator does not require the `ContainerNamespace` to exist, so it avoids the boot-window rejections the `ImagePullRequest` webhook produces.
