Executive Summary ¶

This PR trades an infinite startup wait for a fast, explicit failure: the daemon returns a new exit code 5 for an incompatible control plane, and the Electron main process shows an error dialog and quits. The Go exit-code plumbing and the TS/Go field-name contract are correct end-to-end. The gaps are narrow: the twice-regressed JSONL message parser has no tests, and a handful of error-path items degrade diagnostics rather than break behavior.

Codex and Claude reviewed independently; Gemini failed to produce output on two attempts (see the retro). The two reviews converged on the empty-msg JSON log line and the stderr-drain race, and each surfaced one unique correctness item. The orchestrator dropped one Codex finding — a claimed spawnFile type-check failure — after running the real type-checker disproved it.

S1. stderr can be truncated when spawnFile rejects, hiding the version-specific message Codex Claude¶

spawnFile rejects the instant the child's exit event fires; the stderr end promise sits in the same Promise.all and is abandoned on the first rejection. The catch then reads the stderr closure, which may still be missing the final chunk — the exit-code:5 line that main.go logs immediately before exiting. When that line is absent, the parser falls back to the generic "Unsupported RDD service version" text. This is the fallback @mook-as observed (r3476447447); the loop fix addressed multi-line output, not this exit-versus-drain race.

Design Observations ¶

Concerns ¶

  • The fatal quit trusts the numeric exit code, not a confirmed signal (future) Claude — rdd-ctl.ts:95 quits on err.code === CodeIncompatibleServer, while rdd run (run.go:177) propagates arbitrary child exit codes including 5. This is safe today only because the TS spawns rdd service config, whose sole source of exit 5 is checkSupportedVersion. Gating the quit on a parsed exit-code:5 record — which the loop already finds — would make the decision robust to future callers.
  • The Latch hangs silently if rdd-ctl is not imported before networking (in-scope) Claude — await certificateCallback resolves only once something emits rdd/certificate-callback. background.ts:21 imports @pkg/main/rdd-ctl (registering the listener) before setupNetworking runs at line 90, so the order holds. A setupNetworking throw before the emit quits the app (background.ts:93-97), so this cannot wedge a running app either. The dependency is real but implicit — worth a one-line comment.

Strengths ¶

  • Callback-before-return guarantees certificates precede any config consumer (in-scope) Claude — fetchConfigWithoutCache invokes the cert callback before returning, and fetchConfig memoizes the promise, so every caller — including the renderer's independent invoke('rdd/kube-config') — receives a kubeconfig only after certificate handling is installed. This is safer than consuming the invoke return value directly, which would let the renderer race the cert setup.
  • Exit-code plumbing is correct end-to-end (in-scope) Codex Claude — checkSupportedVersion → Wait → Classify → main.go → os.Exit(5); the JSON exit-code/msg field names match the TS parser exactly; Wait stops polling only on code 5 and keeps retrying transient errors; and no references to the removed errorServerVersionUnsupported type remain.

Review Process Notes ¶

Skill improvements ¶

  • When an agent claims code fails to compile or type-check — a TypeScript overload mismatch, a missing symbol, a broken build — treat the claim as empirically verifiable. Run the compiler or type-checker on the exact construct, or confirm the project's build even type-checks that file, before rating it. Overload resolution and type assignability are easy to misread from signatures alone, and many build setups transpile without type-checking in development, so a hand-derived "this will not build" is often wrong. Rate such a claim only after the tool agrees.
  • Flag callback arguments that pass an object method by bare reference — .then(obj.method), .catch(logger.error), arr.forEach(this.handle) — when the method body uses this. The detached call loses its receiver and throws at runtime, usually on an error path where the resulting TypeError buries the original failure. The safe form wraps the call in an arrow: ex => logger.error(ex).
  • When code reads a child process's stdout or stderr after the process rejects or exits, verify the read waits for stream drain (the close event), not just exit. A process can emit exit before its stdio pipes flush, so a post-exit read of a captured buffer can miss the final chunk — often the exact line the caller needs. Flag error-path parsing that reads a subprocess-output buffer filled by a drain path separate from the one that triggered the throw.

Repo context updates ¶

  • [repo] Lint TypeScript in CI runs eslint (scripts/lint-typescript.ts), not tsc, and yarn dev builds with transpileOnly: true — only the production package build (yarn package, transpileOnly: false) type-checks bundled files. To verify a TypeScript type- or compile-error claim, run tsc --noEmit or check the package job, not the lint or dev output.
  • [repo] The Logging module's Log methods (Logging.<topic>.error, .log, and siblings) are unbound and use this internally. Passing one by bare reference to a callback (.catch(console.error)) loses the receiver and throws a TypeError; the repo's safe idiom wraps it in an arrow (ex => console.error(ex), see utils/backgroundProcess.ts:140). Flag bare-reference Log-method callbacks.
  • [repo] spawnFile (pkg/rancher-desktop/utils/childProcess.ts) accepts a stream.Writable in the stdio tuple (the encoding path routes it to the child pipe), and it rejects on the child's exit event before the stdout/stderr end promises resolve. A caller that reads a stderr closure filled by that stream inside its catch can observe a truncated buffer missing the final line. Trace the drain-versus-reject ordering when reviewing subprocess error parsing here.
  • [repo] UPDATE: the exit-codes context entry (CodeRejected=3, CodeTimeout=4 in pkg/cli/exit/exit.go) should add CodeIncompatibleServer=5 — the running daemon is incompatible with the client; documented in cmd_app.md and surfaced to the Electron UI as a fatal error dialog.
