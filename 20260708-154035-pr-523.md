## Important Issues

I1. **Webhook accepts negative `cpus`, then silently ignores it** — `rdd/pkg/controllers/app/app/controllers/app_webhook.go:72-77` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro]

```go
if vm.CPUs != 0 {
    if v.hostInfo.CPUs > 0 && vm.CPUs > v.hostInfo.CPUs {
        return fmt.Errorf("spec.virtualMachine.cpus %d exceeds the host CPU count of %d", vm.CPUs, v.hostInfo.CPUs)
    }
}
```

Issue #498 requires `cpus >= 1`, with `0` as the reset sentinel. A negative value (`cpus: -4`) satisfies `!= 0` but passes the upper-bound test, and the CRD declares `cpus` as an unconstrained integer (no `minimum`), so admission stores it.

`applyVMResources` (`app_controller.go:133-148`) then skips both the `cpus == 0` env-fallback branch and the `cpus > 0` rewrite branch, so the value is silently discarded — the VM uses the template default and `RDD_VM_CPUS` is suppressed.

Fix: reject negatives in the webhook and gate the upper-bound check on `> 0`.

```go
if vm.CPUs < 0 {
    return fmt.Errorf("spec.virtualMachine.cpus %d must not be negative", vm.CPUs)
}
if vm.CPUs > 0 { /* existing upper-bound check */ }
```

I2. **`rdd set virtualMachine.cpus=0` stores `0` instead of clearing; the reset test fails** — `rdd/cmd/rdd/set.go:740-745` [Codex GPT 5.5]

```go
case "integer":
    v, err := strconv.ParseInt(raw, 10, 64)
    if err != nil {
        return nil, errors.New("expected integer")
    }
    return v, nil
```

The generic integer coercion returns `int64(0)`, and `patchApp` sends a JSON merge patch `{"cpus":0}`, which stores `0` (merge-patch removal requires `null`). Running the suite confirms the assertion at `virtual-machine.bats:92-96` fails: expected empty, actual `0`. Unlike `memory` (an `XIntOrString` whose empty string yields a null patch), an integer field cannot be cleared — `cpus=` errors with "expected integer" and `cpus=0` persists `0`.

Fix: decide the contract. Either special-case `virtualMachine.cpus` so `0`/empty emits a `nil` (null patch) that clears the field, or keep `0` as the stored sentinel and change the test to assert `0` and document it.

I3. **The new BATS suite starts a control plane without the `rdd` group; 4 tests fail** — `rdd/bats/tests/32-app-controllers/virtual-machine.bats:19` [Codex GPT 5.5]

```bash
local_setup_file() {
    setup_rdd_control_plane "app"
```

`--controllers="app"` enables only the app API group plus builtins. The HostInfo controller is registered in the `rdd` group (`controller.go:26-27`), so `hostinfo` is never served. Running the suite, tests 1–3 and 9 fail with `the server doesn't have a resource type "hostinfo"`. Both the orchestrator's and Codex's live runs reproduced this.

Fix: enable both groups — `setup_rdd_control_plane "app,rdd"`.

I4. **HostInfo singleton has no recovery path, and a comment claims one exists** — `rdd/pkg/controllers/rdd/hostinfo/controllers/hostinfo_controller.go:64-72` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro]

```go
if err := r.Create(ctx, hi); err != nil && !apierrors.IsAlreadyExists(err) {
    // Non-fatal: log and continue. The next reconcile will retry.
    logf.FromContext(ctx).Error(err, "Failed to bootstrap HostInfo singleton")
}
return nil
```

If the one-shot `Start` create fails, no object exists; `Reconcile` fires only on `For(&HostInfo{})` events and the informer's initial list is empty, so no reconcile ever runs — the "next reconcile will retry" comment is false. A runtime `delete hostinfo system` likewise leaves a permanent gap (`Reconcile` returns `IgnoreNotFound`). Impact is limited — the embedded apiserver makes the create reliable, and the webhook detects host limits directly rather than reading the CRD — but the GUI's range query breaks until restart, and the comment misleads.

Fix: extract `ensureSingleton(ctx)`, call it from `Start` and the singleton-NotFound branch of `Reconcile`; return/retry the bootstrap error, or correct the comment.

## Design Observations

### Concerns

- **Host detection is duplicated across two packages and two `HostInfo` types** `(in-scope)` [Claude Opus 4.8]. `DetectHostInfo()` (app package) feeds the webhook, while `HostInfoReconciler.Reconcile` (rdd package) independently calls `goruntime.NumCPU()` + `memory.TotalMemory()` to populate the CRD; two Go types are both named `HostInfo`. Keeping detection out of the webhook is reasonable (a webhook read of the CRD would introduce a cross-group startup-ordering hazard), but the detection *logic* could live in one shared helper. Today the two paths agree only because both call `NumCPU()`; a future divergence (cgroup/affinity awareness in one path) would make the webhook and the GUI-visible range disagree silently.
- **Memory ceiling is 100% of host RAM** `(future)` [Claude Opus 4.8]. The webhook allows `memory == hostInfo.Memory` (`app_webhook.go:85`), matching issue #498, but allocating all host RAM to the guest can starve the host OS. Worth revisiting whether a headroom margin belongs here.

### Strengths

- **HostInfo CRD placement** `(in-scope)` [Codex GPT 5.5]. Moving host limits into a cluster-scoped `HostInfo` CRD in the `rdd` group (per Jan's review feedback) leaves room for future host diagnostics without overloading App.
- **CPU precedence chain** `(in-scope)` [Claude Opus 4.8]. spec → `RDD_VM_CPUS` → template default is expressed cleanly, and an invalid env value errors loudly so a CI typo cannot silently change VM sizing.
- **Template-change requeue contract** `(in-scope)` [Codex GPT 5.5]. The App reconciler updates the Lima template ConfigMap and explicitly requeues after the unwatched ConfigMap write, preserving the existing Settled/resourceVersion gating for applied changes.

## Review Process Notes

### Skill improvements

- **When a change adds or modifies a test suite, run that suite before concluding it passes; do not infer pass/fail by reading the test source.** Source-only review produces false negatives — a test whose setup wires the wrong dependencies, or whose assertion contradicts the code's actual output, reads as correct on the page and fails on execution. If the suite cannot be run in the review environment, state that and lower confidence on any "tests pass" claim rather than asserting it.
- **When a validating webhook treats a sentinel value as "unset / use default" and skips validation for it (e.g. `if x != 0 { … }`), verify that out-of-range values on the other side of the sentinel are still rejected.** A guard that excludes the sentinel and then checks only an upper bound silently admits negatives; if the schema declares the field as an unconstrained integer, the webhook is the only gate. Confirm the CRD `minimum`/`maximum` and the webhook together cover the full invalid range.

### Repo context updates

- **[repo]** BATS tests that query a custom resource must enable that resource's API group in `setup_rdd_control_plane`'s argument — the helper forwards it verbatim to `rdd svc create --controllers=`. Groups are `app`, `rdd`, `containers`, `lima`. A missing group surfaces as `the server doesn't have a resource type "X"` at test time, not as a clear setup error. When a test references a resource type, check that the enabled groups include the one that serves it (e.g. `HostInfo` is in `rdd`, `App` in `app`).
- **[repo]** In `rdd set`, an empty value clears string and quantity (`XIntOrString`) fields by emitting a null merge patch, but an integer field cannot be cleared this way: `field=` fails coercion ("expected integer") and `field=0` stores `0` (a JSON merge patch keeps a zero; only `null` removes). When reviewing a new optional integer spec field documented with a "0 means default / reset" contract, verify reset-to-unset is actually achievable — and that any test asserting the field becomes empty reflects real behavior.
