I1. **No test drives the list wrapper through a watch restart** — `pkg/rancher-desktop/store/rddConnection.ts:578` [Claude Opus 5.5]

```ts
    const listFn = async() => {
      const list = await this.#listFn();

      if (Object.is(watcher, this.#watcher)) {
        this.onChange();
      }

      return list;

```

The wrapper does two things that only a restart reaches. When a restarted watch's list comes back empty, for instance after the App was deleted while the watch was down, the new `ListWatch` starts with an empty cache and emits nothing. When a replaced watcher's list comes back late, the identity check stops it from committing the new watcher's still-empty cache, which would send `{}` and stop Steve.

But on a 410, `doneHandler` relists into the same `ListWatch` and its populated cache (`pkg/rdd-client/cache.ts:170`).

## Design Observations

### Concerns

- **(future) Every window reports, and the last report wins.** [Claude Opus 5.5] Each window's store sends its own reports, and `followAppStatus` acts on whichever arrives last, so a window whose watch lags can stop Steve after another window started it. That predates this PR, which now also closes the dashboard in that case. One App watch in the main process, or reports from the main window only, would remove the race.
- **(future) A `ListWatch` stopped during its list still opens a watch.** [Claude Opus 5.5] `doneHandler` checks `stopped` before the list but not after it (`pkg/rdd-client/cache.ts:177`), and `Watcher.close()` keeps `#watcher`, so a late list from a closed watcher still counts as current. The wrapper adds one more commit from such a watcher, an empty late list after `close()`. The gap predates this PR and is tracked outside it.

**Outcome:** both left as they are. They predate the PR and are tracked outside it.

### Strengths

- **(in-scope) The renderer now tells "not listed yet" from "no App".** [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash] `resourceState` starts every list at `null` and nothing resets it (`pkg/rancher-desktop/store/rddConnection.ts:228`). So the plugin's `null` check holds for the window's lifetime, and the main process can treat every report that is not ready as a stop again.
- **(in-scope) The watcher change helps every resource.** [Claude Opus 5.5, Codex GPT 6 Astra] A slow list no longer blanks a table after 1 s. The old rows stay until the new list arrives, which the stale-data comment in `rewatchResources` already accepts (`pkg/rancher-desktop/store/rddConnection.ts:504`).
- **(in-scope) Nothing in rdd removes `KubernetesReady`.** [Claude Opus 5.5, Codex GPT 6 Astra] A tolerated ambiguous probe leaves it True (`rdd/pkg/controllers/app/kubernetes/controllers/kube_reconciler.go:283`), and every write goes through `SetStatusCondition`. So while Steve runs, a report without the condition means that the App is gone.

### Repo context updates

- [repo] UPDATE the unprocessed suggestion from `20261107-213500-pr-1178` that says to treat a missing condition as unknown; the reworked fix makes it false, so replace it with this rule. Every renderer window that loads the Vuex store sends its own `backend/app-status-changed` report on each change to the App, so a main-process handler runs once per window per change and must be idempotent.
