## Executive Summary

Round 3 is the cleanest so far. Every round-2 fix does what it claims, and I found no defect the fixes introduced. Two defects sit elsewhere in the PR. One is a regression against the merge-base: selecting containerd stops removing the instance Docker context. The other is a gap: an image pulled for a platform other than the host's gets no mirror at all, and says so in the log on every sync.

I proved both with probes run against this tree, each including the neighbouring case that behaves correctly. The two Gemini models share a family, so where they agree it counts once; this round they produced one usable suggestion each and no overlap.

## Important Issues

I1. **Selecting containerd stops removing the instance Docker context** — `rdd/pkg/controllers/app/engine/controllers/engine_reconciler.go:230` [Claude Opus 5]

```go
	wantWatcher := running && engineSupported
```

At the merge-base this read `running && engineIsDocker`, so containerd always fell into the `!wantWatcher` arm, which calls `removeDockerContext` on every reconcile. Now containerd is a supported backend, so the reconciler takes the watcher path and never touches the context. A live moby-to-containerd switch still sweeps it through `previousEngine`, but `watcherEngine` is in-memory: a daemon that starts with containerd already selected leaves the `rancher-desktop-<N>` context in place, pointing at a socket nothing serves. `removeDockerContext` also clears `currentContext` in `~/.docker/config.json`, so what survives can be the user's own selected context.

I2. **An image pulled for another platform gets no `Image` mirror at all** — `rdd/pkg/controllers/app/engine/controllers/sync_images_containerd.go:132` [Claude Opus 5]

```go
	size, err := img.Size(nsCtx)
	if err != nil {
		return fmt.Errorf("failed to get image size %s: %w", name, err)
	}
```

`img.Size` is `usage.CalculateImageUsage(..., WithManifestLimit(i.platform, 1), ...)`, and `newContainerdWatcher` builds its client with no platform option, so `i.platform` is `platforms.Default()`, the platform the daemon itself runs on. A non-nil platform sets `mustExist` in the calculator, so a `NotFound` from the children walk aborts instead of counting zero. After `nerdctl pull --platform=linux/amd64` on an arm64 Mac, the index lists an arm64 manifest whose content was never fetched, and that is the one the host matcher prefers.

The record then errors on every sync. `syncAllImages` logs and skips (`:86-88`), so the image stays absent from the API, where moby would list it.

```go repro
func probeBlob(t *testing.T, cs content.Store, mt string, v any) ocispec.Descriptor {
	t.Helper()
	b, err := json.Marshal(v)
	assert.NilError(t, err)
	d := digest.FromBytes(b)
	desc := ocispec.Descriptor{MediaType: mt, Digest: d, Size: int64(len(b))}
	assert.NilError(t, content.WriteBlob(context.Background(), cs, d.String(), bytes.NewReader(b), desc))
	return desc
}

	cs, err := local.NewStore(t.TempDir())
	assert.NilError(t, err)

	// The platform the host matcher does NOT prefer is the one that was pulled.
	pulled := ocispec.Platform{OS: "linux", Architecture: "amd64"}
	if platforms.Default().Match(pulled) {
		pulled = ocispec.Platform{OS: "linux", Architecture: "arm64"}

	preferred := ocispec.Platform{OS: "linux", Architecture: "arm64"}
	if pulled.Architecture == "arm64" {
		preferred.Architecture = "amd64"

		MediaType: ocispec.MediaTypeImageManifest, Config: cfg,
		Layers: []ocispec.Descriptor{layer},

		assert.NilError(t, err)
```

## Suggestions

S1. **The post-SIGKILL wait has no deadline of its own** — `rdd/pkg/controllers/app/engine/controllers/container_actions_containerd.go:330-335` [Claude Opus 5]

```go
	select {
	case status := <-exitCh:
		return status.Error()
	case <-nsCtx.Done():
		return nsCtx.Err()
	}
```

`nsCtx` derives from Reconcile's context, which nothing cancels short of manager shutdown. A task that survives SIGKILL, a process wedged in uninterruptible sleep on a guest mount, parks the engine reconciler here for good, and the App is a cluster-scoped singleton, so no finalizer pass and no `ContainerEngineReady` update runs again. A broken gRPC connection does unblock it through `exitCh`, which is why this is a suggestion.

Fix: add `case <-time.After(defaultStopTimeout):` returning an error naming the container, so the action records `Failed` and the reconciler moves on.

**Commented.** A deadline aborted restart and left the same unbounded wait at `task.Delete`; the comment now records both sites.

S2. **A stop-timeout label above the `Duration` ceiling wraps negative and kills immediately** — `rdd/pkg/controllers/app/engine/controllers/container_actions_containerd.go:632` [Gemini 3.5 Flash]

```go
	return time.Duration(seconds) * time.Second
```

The guard above rejects a non-numeric or non-positive label but not one past `time.Duration`'s ~292-year ceiling, and the multiply wraps. I measured `10000000000` producing `-2346317h47m53.709551616s` and `9223372036854775807` producing `-1s`, against `30` producing `30s`. A negative argument makes `time.After` fire at once, so the container is SIGKILLed with no grace period. I did not check whether nerdctl caps its own `--stop-timeout`, which is the only path that writes the label in normal use.

Fix: reject anything above a sane bound in the same guard, say `seconds > 86400`.

**Fixed**, bounded at the real overflow point so no previously honored value changes behaviour.

S3. **A deleted `ContainerNamespace` mirror is not recreated in steady state** — `rdd/pkg/controllers/app/engine/controllers/sync_namespace_containerd.go:71` [Codex GPT 5.6 Sol, Claude Opus 5]

`applyNamespace` runs from `fullSync` and from the `ContainerCreate`/`ImageCreate` event arms. `SetupWithManager` does watch `ContainerNamespace` (`engine_reconciler.go:939`), but steady-state `Reconcile` only runs `reconcileContainerActions` and `processFinalizers`, so a `kubectl delete` of a mirror leaves it gone until the next container or image is created in that namespace, or the watcher restarts.

The moby side has the same shape and is worse, since `syncContainerNamespace` has no event path at all, and both the watch and the fullSync-only call predate this PR, so this is a gap rather than a regression. Codex rated it Important; I downgraded it because the delete is unsupported by design and containerd self-heals on the next namespace event.

Fix: re-apply namespaces from the watch that already wakes the reconciler.

**Commented.** Pre-existing on the moby path; the comment records every caller of `applyNamespace`.

## Design Observations

### Concerns

- **User-visible mirror fields diverge between the two engines** *(future)* [Claude Opus 5]. The same image is `busybox:latest` under moby and `docker.io/library/busybox:latest` under containerd; `status.id` is the config digest on one and the manifest digest on the other; and `api_containers.md` now documents `status.size` as uncompressed on moby and a compressed-blob sum on containerd. Each is defensible and each is documented, but together they mean a GUI list and any client keying on `repoTag` behave differently per backend, which is what the repo's parity principle exists to prevent. Worth settling before the renderer is wired up.
- **Windows will serve the well-known containerd pipe name** *(future)* [Claude Opus 5]. `instance.ContainerdSocket()` returns `\\.\pipe\containerd-containerd` on Windows, and `app_controller.go:163` writes it into every Lima template regardless of platform or selected engine. Windows containerd is out of scope here, but the name is global rather than instance-scoped, the same collision it would have with Docker Desktop's `\\.\pipe\docker_engine`. Scoping it before anything serves it is cheaper than after.
- **A mirror kind created only by `fullSync` can drift permanently** *(in-scope)* [Codex GPT 5.6 Sol]. S3 is the instance; the general form is that ordinary reconciliation is authoritative for containers, images and volumes but not for namespaces.

### Strengths

## Review Process Notes

### Skill improvements

- When a finding proposes a fix, place the reproducer's assertion where it can distinguish the proposed placement from a correct one. A patch that guards a side effect behind a success path passes any probe whose setup reaches that path, and fails one whose setup does not; running the reproducer against the patch is what separates them, and the placement is often the whole finding.
- A library call that selects data by the running process's platform is a defect candidate wherever the process and the resource it describes are on different machines. Check every default a client library derives from its own host (platform, architecture, path separators, signal numbers, locale) against where the object it is describing actually lives.

### Repo context updates

- [repo] `run -0` followed by a `${output}` capture is the established form for `rdd ctl` and `rdd svc` calls in this bats suite, including inside `try` predicates; `assert_single_mirror`, `assert_action_consumed` and `assert_docker_context` all use it. Do not flag a nested `run` inside a retry predicate as a style violation. The separate `run_e` rule applies to commands with a debug path that writes to stderr, not to every capture.
- [repo] The daemon builds its containerd client with `containerdclient.New(instance.ContainerdSocket())` and no platform option, so the client carries `platforms.Default()`, which is the host's platform and not the guest's. Any containerd API whose behaviour depends on the client platform (image size, config resolution, manifest selection) therefore asks about the machine the daemon runs on. On an arm64 Mac this happens to match a linux/arm64 guest, which hides the mismatch in ordinary use.

## Design Observations

### Concerns

**User-visible mirror fields diverge between the two engines** *(future)*. `sync_images_containerd.go:155-159` reports the containerd record name verbatim, so the same image is `busybox:latest` under moby and `docker.io/library/busybox:latest` under containerd; `applyImageMirror` reports the manifest digest as `status.id` where moby reports the config digest; and `api_containers.md` now documents that `status.size` is uncompressed on moby and compressed-blob-sum on containerd. Each is defensible on its own and each is documented, but together they mean a GUI list and any client keying on `repoTag` behave differently per backend — the exact thing the repo's "moby/containerd parity beats nerdctl parity" principle exists to prevent. Worth deciding explicitly, before the GUI is wired up, whether the mirror normalises (familiar-name shortening for a `docker.io/library/` reference; a size the two engines measure the same way) or whether the divergence is the contract.

**A deleted `ContainerNamespace` mirror is never recreated** *(in-scope)*. `applyNamespace` (`sync_namespace_containerd.go:71`) runs only from `fullSync` and from `ContainerCreate`/`ImageCreate` events. `SetupWithManager` does `Watches(&containersv1alpha1.ContainerNamespace{}, enqueueApp)`, so a manual `kubectl delete` does wake the reconciler — but `Reconcile` only runs `reconcileContainerActions` and `processFinalizers`, neither of which re-applies namespaces. The mirror stays gone until the watcher restarts. The moby `ContainerNamespace/moby` has had the same shape since before this PR, so the containerd side inherits rather than introduces it; the cheap fix is to re-apply from the existing watch instead of documenting it.

**Windows will serve the well-known containerd pipe name** *(future)*. `instance.ContainerdSocket()` returns `\\.\pipe\containerd-containerd` on Windows and `app_controller.go:163` writes it into every Lima template regardless of platform or selected engine. Windows containerd is explicitly out of scope for this PR, but the name is global rather than instance-scoped — the same shape as the `\\.\pipe\docker_engine` collision with Docker Desktop. Scoping it to the instance before anything serves it is much cheaper than after.

- The `watcherEngine` state machine is genuinely well thought through: putting the backend-switch arm ahead of the liveness arm, keeping `watcherEngine` alive across `stopWatcher`, and clearing it only after the sweep owns the work all survive the state enumerations I traced (switch while dead, switch while stopped, switch whose watcher start then fails).

- `containerdImageRefs` puts the digest check ahead of the reference parse and says why — the `sha256`-as-a-repository trap is exactly the kind of thing a later refactor reorders.

##### S1. Prevent Potential Multiplication Overflow in stopTimeout — `container_actions_containerd.go:626-634`

```go
	seconds, err := strconv.Atoi(raw)
	if err != nil || seconds <= 0 {
		log.V(1).Info("Ignoring unusable stop timeout label",
			"id", ctr.ID(), "value", raw)
		return defaultStopTimeout
	}
	return time.Duration(seconds) * time.Second
```

If a user or a third-party tool writes an extremely large integer to the `nerdctl/stop-timeout` label, multiplying a valid 64-bit integer by `time.Second` ($10^9$) can overflow `time.Duration` (max ~292 years), leading to a wrapped negative duration or immediate timeout.

Fix: Clamp the parsed seconds to a sensible upper bound (such as 1 day or 86,400 seconds) before conversion.

```diff
-	seconds, err := strconv.Atoi(raw)

+	seconds, err := strconv.Atoi(raw)
+	if err != nil || seconds <= 0 || seconds > 86400 {
 		log.V(1).Info("Ignoring unusable stop timeout label",
 			"id", ctr.ID(), "value", raw)
 		return defaultStopTimeout
 	}
```
