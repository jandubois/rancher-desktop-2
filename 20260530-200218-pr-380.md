## Executive Summary

The PR gates `computeSettledCondition` on `templateUpToDate` — the template ConfigMap's `resourceVersion` versus the LimaVM's `ObservedTemplateResourceVersion` — so `Settled` stays False (reason `ApplyingTemplate`) until the VM restarts into a rewritten template, closing the premature-settle window in issue #378. All three reviewers found the fix correct with no Critical or Important issues; an independent cross-controller trace confirmed convergence with no hang. Remaining items are a design-doc table omission and a BATS-style nit.

All three reviewers (Claude, Codex, Gemini) agreed the core logic is sound. The only inter-reviewer disagreement was the severity and validity of the `local`-inside-`@test` style point (S2), resolved below against the actual file.

S3. **`templateUpToDate` computed from the outer `app` read, applied against re-Get'd `latest`** — `app_controller.go:386,459` [Claude Opus 4.8] (suggestion, gap)

```go
settled := computeSettledCondition(latest, engineEnabled, kubernetesEnabled, templateUpToDate)
```

`templateUpToDate` (finalized at line 421) is derived from the outer `app.Spec`/`limaVM` reads, but `computeSettledCondition` runs against `latest` (re-Get'd at line 442-443), which can carry a higher generation if a new `rdd set` lands mid-loop. The stamped `Settled.ObservedGeneration` would then be the newer generation while the flag reflects the prior spec. This self-heals — the newer generation triggers another reconcile that re-derives the template and finds it stale — and mirrors the existing pattern for `engineEnabled`/`kubernetesEnabled` (computed once at lines 439-440; the loop's staleness is already noted in the comment at lines 433-438). Benign.

Fix: add a one-line comment near line 459 noting `templateUpToDate`, like the enabled flags, is evaluated against the outer read and self-corrects on the next generation. Recomputing from `latest` inside the loop is heavier and not warranted.

## Design Observations

### Strengths

- **Generic, change-agnostic gate** [Claude Opus 4.8] — The gate unsettles on *any* template-rewriting spec change (`containerEngine.name`, `kubernetes.version`, `kubernetes.enabled`) without inspecting what changed, and correctly makes a version-aware `KubernetesReady` probe unnecessary — matching the direction `@mook-as` argued for in the issue. (in-scope)
- **Reuses existing deferral instead of new synchronization** [Claude Opus 4.8, Codex GPT 5.5] — The fix leans on the already-correct `ObservedTemplateResourceVersion` deferral in `limavm_controller.go:handleTemplateUpdate` (the version is withheld while `RestartNeeded` is set, lines 420-423). Both sides of the comparison are reads of the same `<name>-template` ConfigMap, so the `resourceVersion` match is exact. (in-scope)
- **Graceful degradation on boot failure** [Gemini 3.1 Pro] — Because `ApplyingTemplate` holds only until the LimaVM writes the new template, a VM that then fails to boot surfaces the real failure (`Starting`/`Failed`) rather than masking it behind `ApplyingTemplate` indefinitely.
- **Test improvements** [Claude Opus 4.8, Gemini 3.1 Pro] — The rename "without stopping VM" → "restarts the VM" corrects a pre-existing misnomer, and the before/after snapshot of `lastTransitionTime` + `observedTemplateResourceVersion` directly catches a premature-settle regression. The `templateOutOfDate bool` + `!tt.templateOutOfDate` extension covers the new branch without touching the 20+ existing table cases.
