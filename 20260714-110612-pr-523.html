func defaultVMCPUCount(vm *v1alpha1.VirtualMachineSpec, hostInfo HostInfo) error {

		return nil

Design Observations ¶

Concerns ¶

  • The webhooks read their own Detect() snapshot rather than HostInfo.Status (in-scope) Claude Codex Gemini. Issue #498 asks that "validation will use these saved values"; the validator instead snapshots hostinfo.Detect() at setup (app/controller.go:124), leaving HostInfo a resource nothing in-tree reads. The Round-4 drift hazard is genuinely gone — one Detect() now backs both contracts, and the package doc says so — and keeping the app webhook free of a cross-group dependency on rdd is the cheaper trade. Both agents who raised this rated it Important; it is demoted here because no divergence can occur and the reduced scope is documented in code. What remains is a contract to write down, not code to rework (I1).
  • Raising cpus or memory on a running VM reboots it (in-scope) Claude. applySpecToTemplate re-renders the template ConfigMap, and LimaVMReconciler.handleTemplateUpdate (rdd/pkg/controllers/lima/limavm/controllers/limavm_controller.go:497) then writes the new template to the on-disk lima.yaml and sets Status.RestartNeeded whenever the instance is running or starting. The change therefore does reach the VM — after a restart, which costs minutes.

Claude reported the opposite: that Lima reads the template only at instance creation, so the user "sees no effect and no warning." The orchestrator published that without tracing the lima controller. Jan caught it. The real consequence is the inverse of the one reported: not a silent no-op, but an unannounced restart. A rdd set virtualMachine.cpus in a bats file whose VM is running adds minutes to CI, which matters because bats-app already fails its timeout on the macOS Intel runners.

Strengths ¶

  • The Round-4 critical is fixed correctly (in-scope) Claude Codex Gemini. Start now retries bootstrapSingleton under wait.PollUntilContextCancel and swallows the cancellation, so it never returns a non-nil error. Verified against controller-runtime v0.24.1: runnable_group.go:244-251 signals readiness from a goroutine separate from Start, so a blocking retry cannot stall manager startup, and a nil return never reaches errChan. The doc comment explains why the function must never fail — the comment that stops someone reintroducing the bug.
  • Host detection is centralized (in-scope) Claude Codex Gemini. pkg/hostinfo.Detect() is now the single computation behind both the CRD Status and the admission ceilings.
  • The defaulter stays self-consistent with its own validator (in-scope) Claude. Clamping the CPU default to the host count and returning a distinct error on a sub-2Gi host, rather than writing a value the validator would reject, forecloses the un-admittable-object class outright.

That literal is the fallback, not the default. RD1 computes the default in getDefaultMemory() (settingsImpl.ts:166), and it is Math.min(6, Math.round(totalMemoryInGB / 4.0)) — the same quarter-of-host rule, with the same 6 GB cap. Claude never made this claim; it is charged to the orchestrator, not the agent.

The second: the orchestrator published Claude's design observation that a cpus/memory change never reaches a running VM, without reading the lima controller. It does reach the VM, via a restart (see Design Observations). Here the agent supplied the false claim and the orchestrator failed to check it.

One failure produced both. Verifying a finding against a single file that plausibly contains the answer is not verification: the grep that lands on a static literal has to be followed by the grep that finds what overrides it, and a claim about what a controller does has to be read in that controller. The checks that were run this round — the C1 retry against controller-runtime's runnable group, the S8 admission ordering — both held up. The difference is that those were traced to the mechanism; these two were not.

Review Process Notes ¶

Skill improvements ¶

  • When a change deletes a hard-coded default and replaces it with a computed one, compute both values for the machines that will actually run the code, and compare them. A diff that removes a constant and adds a formula reads as a refactor, and every reviewer's attention lands on whether the formula is correct rather than on whether it returns what the constant did. State the old value, the new value on a typical developer machine, and the new value on each CI runner. Flag any silent reduction in a resource the software depends on — memory, timeouts, retries, disk — even when the new rule is defensible in isolation, because nothing in the diff announces the regression and no test will.
  • Before calling a comment's cited rationale false, find the code that computes the value — not the code that declares it. A comment of the form "following X's default" is a citation, and checking it means locating X's effective default. A static literal in a settings or config file is frequently a fallback that a helper overrides at runtime, so a grep that lands on the literal and stops will contradict a comment that is in fact correct. Search for the function that derives the value (getDefaultX, a factory, an initializer) before concluding the citation is wrong. An accusation that a comment lies is a strong claim; hold it to a stronger standard of proof than the finding it supports, because a reviewer who "corrects" an accurate comment sends the author to change working code.
