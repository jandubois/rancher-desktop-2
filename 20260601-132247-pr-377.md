## Important Issues

I1. **`StopWithWait` can pass pid 0 to `Interrupt`, broadcasting `CTRL_BREAK` to the caller's console** — `pkg/service/cmd/service.go:404-420` [Codex GPT 5.5] (important, gap)

```go
if !Running() {            // PID() read #1
    return fmt.Errorf("%q control plane is not running", instance.Name())
}
pid := PID()               // read #2: PIDNotFound (0) if state changed
if err := process.Interrupt(pid); err != nil {
```

`Running()` calls `PID()` (line 404); `StopWithWait` then reads `PID()` again (line 408). The new identity guard makes `PID()` return `PIDNotFound` (== 0, line 137) and delete the file whenever `IsOurProcess` fails. If the service exits or its PID recycles between the two reads, `pid` is 0, and `process.Interrupt(0)` runs `GenerateConsoleCtrlEvent(CTRL_BREAK, 0)` (`process_windows.go:36-38`) — group 0 signals every process sharing the caller's console, killing the `rdd` CLI and terminal. The post-crash recycled-PID case is already caught (`Running()` returns false), so the live trigger is a narrow TOCTOU; the blast radius is the `STATUS_CONTROL_C_EXIT` this PR exists to prevent.

Fix: guard `Interrupt` against `pid <= 0` (this forecloses the class for every caller), and read the PID once in `StopWithWait`.

```diff
 func Interrupt(pid int) error {
+	if pid <= 0 {
+		return fmt.Errorf("refusing to signal invalid pid %d", pid)
+	}
 	return windows.GenerateConsoleCtrlEvent(windows.CTRL_BREAK_EVENT, uint32(pid))
 }
```

## Suggestions

S1. **Create/prepare-failure `Delete` calls miss the new WSL2-hang timeout** — `pkg/controllers/lima/limavm/controllers/limavm_controller.go:318,331` [Gemini 3.1 Pro] (suggestion, gap)

```go
if delErr := limainstance.Delete(ctx, inst, true); delErr != nil {
    logger.Error(delErr, "Failed to clean up instance after sentinel creation failure")
}
```

This round wrapped `limainstance.Delete` in `context.WithTimeout(ctx, time.Minute)` at the leftover path (line 221) and in `handleDeletion` (`limavm_lifecycle.go:55`), because Lima's WSL2 driver calls `wsl.exe --unregister`, which can hang when the WSL subsystem is degraded. The two create/prepare-failure cleanups at lines 318 and 331 call the identical `Delete(ctx, inst, true)` with no timeout, so the same degraded-WSL hang wedges the reconcile worker (controller-runtime applies no per-reconcile deadline). The instance is never-started, so its distro is usually unregistered — yet a degraded WSL hangs any `wsl.exe` call regardless. Low likelihood, but the author just established this guard at the siblings.

Fix: wrap both calls in the same 1-minute timeout context.

```diff
-		if delErr := limainstance.Delete(ctx, inst, true); delErr != nil {
+		deleteCtx, deleteCancel := context.WithTimeout(ctx, time.Minute)
+		delErr := limainstance.Delete(deleteCtx, inst, true)
+		deleteCancel()
+		if delErr != nil {
```

S2. **`PID()` opens the target process twice on Windows** — `pkg/service/cmd/service.go:147-169` [Claude Opus 4.8] (suggestion, enhancement)

```go
proc, err = os.FindProcess(pid)   // opens a handle on Windows
_ = proc.Release()                // closes it
if err == nil && !process.IsOurProcess(pid, "service", "serve") {  // opens again
```

`os.FindProcess` opens a process handle on Windows, released at line 155; `IsOurProcess` then opens the process a second time. The double round-trip is harmless, and the non-Windows path still needs the `FindProcess` + `Signal(0)` liveness check, so this is not a defect. A one-line comment marking the double-open as deliberate would stop a future reader from collapsing the two and breaking the Unix liveness path.

Fix: note the intent inline, or leave as is.

S3. **`signalHostagent` reads set-once `cmd`/`procExited` outside `state.mu`** — `pkg/controllers/lima/limavm/controllers/hostagent_watcher.go:209-222` [Claude Opus 4.8] (suggestion, enhancement)

```go
return process.Interrupt(state.cmd.Process.Pid) == nil  // read without state.mu
```

`signalHostagent` reads `state.cmd` and `state.procExited` without holding `state.mu`. Both fields are written once in `startWatcher` and never reassigned, so the read is race-free today, and `shutdownAllHostagents` (`limavm_controller.go:524-532`) reads them the same way. The hazard is latent: a future change that reassigns either field under the lock would introduce a data race here with no compiler warning.

Fix: document on the `instanceState` definition that `cmd` and `procExited` are set once at construction and safe to read without the lock.

S4. **`processCommandLine`'s empty-command-line branch is untested** — `pkg/util/process/process_windows.go:177-180` [Claude Opus 4.8] (suggestion, gap)

`processCommandLine` returns `"", nil` when `params.CommandLine.Length == 0`. No test reaches that branch — the running test process always carries a non-empty command line. Fix: optional; no production caller depends on the branch.

## Review Process Notes

### Skill improvements

- When a function signals or terminates a process by numeric PID, check whether the underlying OS primitive treats `0` or a negative value as a broadcast or process-group wildcard rather than a single target. POSIX `kill(0, ...)` and `kill(-1, ...)` reach the caller's process group or every permitted process, and Windows `GenerateConsoleCtrlEvent(evt, 0)` signals every process sharing the caller's console. Trace every path that supplies the PID, including "not found" sentinels: when the sentinel equals `0` (or another wildcard), a lookup miss silently becomes a broadcast that can kill the caller and its console. Flag any signal or kill wrapper that forwards an externally derived PID without rejecting non-positive values.

### Executive Summary

This PR correctly introduces a process identity check (`process.IsOurProcess`) on Windows to defend against PID reuse when reading a stale PID file. However, the `IsOurProcess` implementation relies on substring matching and the callers pass raw instance names, creating a prefix-matching vulnerability where one instance's hostagent can be killed in place of another. Additionally, two cleanup paths miss the new timeout protection against `wsl.exe` deadlocks. 

**Verdict:** Merge after addressing the prefix match and missing timeouts.

#### Important Issues

I1. **Prefix matching in `IsOurProcess` usage** — `pkg/controllers/lima/limavm/controllers/limavm_lifecycle.go:210` (important, regression)

```go
			if inst.HostAgentPID > 0 && !process.IsOurProcess(inst.HostAgentPID, "hostagent", inst.Name) {
```

The `IsOurProcess` helper explicitly warns that `"vm"` matches `"vm2"` and requires callers to pass a distinct name. However, `limavm_lifecycle.go` (and several other call sites) simply passes `inst.Name`. If a user names a VM `default` and another `default-test`, `IsOurProcess` invoked for `default` will return true against the command line of `default-test` (`rdd ... hostagent default-test`), causing `stopInstanceForcibly` to wrongfully kill the `default-test` hostagent.

Fix: Parse the command line into exact arguments instead of using `strings.Contains`.

```go
	cmdline16, err := windows.UTF16FromString(cmdline)
	if err != nil {
		return false
	}
	var argc int32
	argv, err := windows.CommandLineToArgv(&cmdline16[0], &argc)
	if err != nil {
		return false
	}
	defer windows.LocalFree(windows.Handle(unsafe.Pointer(argv)))

	ptrSlice := unsafe.Slice(argv, argc)
	for _, expected := range cmdlineSubstrings {
		found := false
		for _, ptr := range ptrSlice {
			if windows.UTF16PtrToString(ptr) == expected {
				found = true
				break
			}
		}
		if !found {
			return false
		}
	}
	return true
```

I2. **Missing `context.WithTimeout` on cleanup `limainstance.Delete`** — `pkg/controllers/lima/limavm/controllers/limavm_controller.go:318`, `331` (important, gap)

```go
	if err := createSentinel(limaVM.Name); err != nil {
		logger.Error(err, "Failed to create sentinel file")
		if delErr := limainstance.Delete(ctx, inst, true); delErr != nil {

The PR correctly wraps `limainstance.Delete` with `context.WithTimeout` in `forceStopForDeletion` and `handleDeletion` because `wsl.exe --unregister` can hang indefinitely if the subsystem is degraded.  		}
```
