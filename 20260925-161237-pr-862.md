## Executive Summary

The PR ships the containerd socket-permissions drop-in in the distro image, and moves `VM_SWITCH_LOG` and `NETWORK_SETUP_EXTRA_ARGS` into `/etc/sysconfig/rancher-desktop`, which `network-setup.service` now reads through `EnvironmentFile=`. The mechanics work. On systemd 255 a log path containing a space stays one argument, and the extra flags split into two. But the move left stale comments in three files, and one tells readers to set the flags with a drop-in that the new file overrides.

I2. **`network-setup.service` tells readers to use a drop-in that the new file overrides** — `rdd/overlay/root/usr/local/lib/systemd/system/network-setup.service:11-19` [Claude Opus 5.5, Gemini 3.5 Flash]

```ini

# replacing the ExecStart below. Empty by default; the unquoted
```

systemd merges `EnvironmentFile=` values after every `Environment=` setting, drop-ins included. On systemd main, `src/core/exec-invoke.c` calls `strv_env_merge(..., context->environment, params->files_env)`. Lines 17-18 credit line order for the file winning, but the probe's third case moves `EnvironmentFile=` above the defaults and the file still wins.

## Design Observations

### Concerns

- **On WSL the file reaches `network-setup.service` one boot late** (future) [Gemini 3.5 Flash, Claude Opus 5.5]. `lima-init.service.d/network-namespace.conf` orders lima-init, which writes the file, after `network-setup.service`. The provision script's `rancher-desktop.target` restart leaves network-setup running, because the unit has no `StopPropagatedFrom=`. So a new WSL instance's first boot logs vm-switch inside the guest and ignores the `RDD_KEEP_LOGS` flags, and later boots read the previous boot's file. The old drop-ins had the same timing, so this PR does not regress it. Restarting network-setup from the script would also restart lima-init, which `Requires=` it.
- **Closing #807 drops its engine-switch idea** (future) [Claude Opus 5.5]. #807 hands the journal-capture and k3s rows to #445 and #502, but its idea of a distro unit keyed on `CONTAINER_ENGINE` for the engine switch appears in neither. `Fixes: #807` closes the issue on merge, so record that idea elsewhere first if it is still wanted.

### Strengths

- **The file avoids systemd's specifier expansion** (in-scope) [Claude Opus 5.5, Gemini 3.1 Pro]. The old `Environment="VM_SWITCH_LOG=…"` line went through `%` specifier expansion, so a Windows user name containing `%` would have mangled the path. I2's probe shows the new form keeps a path with a space as one argument while the extra flags split.
- **`permissions.conf` now loads at boot** (in-scope) [Claude Opus 5.5, Gemini 3.5 Flash], beside its docker sibling, instead of depending on the provision script's reload. `engine-containerd.bats` still asserts the socket mode.

S1. **Stale provisioning drop-ins override new sysconfig values on upgrade** — `rdd/pkg/controllers/app/app/lima-template.yaml:50-51` (suggestion, gap)

Systemd parses drop-in files after the main unit file, meaning `Environment=` declarations in a drop-in override `EnvironmentFile=` declarations in the main unit. Because Lima preserves the guest disk across daemon restarts and upgrades, users updating from an older version will still have the old `/etc/systemd/system/network-setup.service.d/extra-args.conf` and `log-path.conf` files in their VM. These stale drop-ins will override the fresh values written to `/etc/sysconfig/rancher-desktop` by the new code, permanently pinning `NETWORK_SETUP_EXTRA_ARGS` and `VM_SWITCH_LOG` to their values from the previous boot and ignoring any new toggles (e.g., turning on packet tracing).

While data migration is not a primary concern before a stable release, adding a system-mode provision script to sweep the old drop-ins prevents this configuration trap for current alpha testers without requiring a factory reset.

#### Design Observations

##### Concerns

- **WSL startup ordering between `network-setup.service` and `lima-init.service`** `(in-scope)`: Under WSL, `lima-init.service.d/network-namespace.conf` sets `Requires=network-setup.service` and `After=network-setup.service`, forcing `network-setup.service` to start before `lima-init.service`.
