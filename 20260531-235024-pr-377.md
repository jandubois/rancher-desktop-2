## Important Issues

I1. **Leftover-instance `Delete` sends `CTRL_BREAK` to un-scrubbed recycled PIDs** — `pkg/controllers/lima/limavm/controllers/limavm_controller.go:218` [Claude Opus 4.8] (important, gap)

```go
existingInst, err := store.Inspect(ctx, limaVM.Name)
if err == nil && existingInst != nil {
    logger.Info("Deleting leftover Lima instance", "instance", limaVM.Name)
    if err := limainstance.Delete(ctx, existingInst, true); err != nil {
```

When the create path finds a leftover Lima instance from a failed prior deletion (line 215), it calls `limainstance.Delete(force=true)` with the PIDs intact. Lima's `Delete` → `StopForcibly` → `osutil.SysKill`, which on Windows is `GenerateConsoleCtrlEvent(CTRL_BREAK_EVENT)` (lima `osutil_windows.go:39`), targeting `HostAgentPID` (always populated by `store.Inspect`) and `DriverPID`. The leftover instance was not started by this service, so those PIDs are stale; a recycled PID sharing the console makes `CTRL_BREAK` escape and kill the rdd service and terminal — the exact `STATUS_CONTROL_C_EXIT` failure this PR exists to prevent. `handleDeletion` zeroes both PIDs on Windows before its own `Delete` (lines 63-77); this path does not. The sibling `Delete` calls at lines 312/325 are safe (instance created/prepared this reconcile, PIDs zero).

Fix: zero the PIDs on Windows before the leftover `Delete`, matching `handleDeletion`.

```diff
 if err == nil && existingInst != nil {
     logger.Info("Deleting leftover Lima instance", "instance", limaVM.Name)
+    if runtime.GOOS == "windows" {
+        existingInst.DriverPID = 0
+        existingInst.HostAgentPID = 0
+    }
     if err := limainstance.Delete(ctx, existingInst, true); err != nil {
```

## Suggestions

S1. **Service PID guard cannot distinguish one control plane from another** — `pkg/service/cmd/service.go:161` [Gemini 3.1 Pro, Codex GPT 5.5] (suggestion, gap)

```go
if err == nil && !process.IsOurProcess(pid, "service", "serve") {
    err = fmt.Errorf("pid %d is not our control plane", pid)
}
```

`IsOurProcess(pid, "service", "serve")` confirms the PID runs *a* control plane, not *this* instance's. The `service serve` command line carries only `--secure-port <6443+index>` per instance (no instance name), and the guard ignores it. If two instances run concurrently and instance A's stale PID file holds a PID recycled to instance B's live `service serve`, `PID()` adopts B: `Running()` reports A as up, `rdd svc start` refuses to start, and `StopWithWait` could signal B's control plane. Single-instance use is safe — a recycled PID is never another `rdd service serve` — so the residual is the concurrent multi-instance / BATS case. The guard remains a clear gain over the prior "any live PID" trust.

Fix: append a per-instance token to the serve argv (the instance name, or the per-instance `--secure-port`) and require it in the check.

S2. **`IsOurProcess` matches on image alone when called with no substrings** — `pkg/util/process/process_windows.go:59-85` [Claude Opus 4.8] (suggestion, enhancement)

```go
func IsOurProcess(pid int, cmdlineSubstrings ...string) bool {
```

The docstring frames substring matching as integral, but `IsOurProcess(pid)` succeeds on an image-path match alone. Every production caller passes a discriminator, so this is latent: the variadic signature invites a future caller to omit one and silently get image-only matching, which a recycled PID running another rdd subprocess (e.g. `rdd ctl`) would satisfy. The risk stays low because the image must still be the rdd binary.

Fix: no code change required; document that a zero-substring call checks the image only, and that callers should always pass a discriminator.

S3. **`resolveLongPath` doubles its buffer instead of using the size `GetLongPathName` returns** — `pkg/util/process/process_windows.go:116-126` [Gemini 3.1 Pro] (suggestion, enhancement)

```go
for bufSize := uint32(1024); bufSize <= 32768; bufSize *= 2 {
    buf := make([]uint16, bufSize)
    n, err := windows.GetLongPathName(p16, &buf[0], bufSize)
```

Unlike `QueryFullProcessImageName`, `GetLongPathName` returns the exact required length in `n` when the buffer is too small, so the doubling loop can take up to six iterations where one regrow would do. The code is correct — the symmetry with `processImagePath` is deliberate — so this is a minor efficiency note, not a defect.

Fix: optional; size the second allocation to `n` and call once more, or keep the symmetry.

## Design Observations

### Concerns

- **`handleDeletion`'s force-stop relies on the `StatusRunning` proxy (future)** [Codex GPT 5.5] — `handleDeletion` force-stops only `StatusRunning` instances (`limavm_lifecycle.go:55`) and skips the new `IsOurProcess` guard, and `Reconcile` dispatches a deleting object straight to it on a controller restart (`limavm_controller.go:175`) before `killOrphanedHostagent` can run. Codex read this as a recycled-PID force-kill. In practice Lima's `store.Inspect` connects to the hostagent socket and downgrades a recycled `HostAgentPID` to `StatusBroken` (lima `store/instance.go:71-88`), which this path does not force-stop and then PID-clears before `Delete`. The residual is a driver-status override leaving `StatusRunning` over a recycled `HostAgentPID`, plus the always-deferred `DriverPID`. Low risk, but the "StatusRunning means ours" premise is implicit; an `IsOurProcess` scrub would make it explicit.

- **Hostagent startup refuses to start on a recycled PID (future)** [Claude Opus 4.8] — `hostagentAction` rejects startup when `store.ReadPIDFile` returns a nonzero PID (`pkg/hostagent/command.go:55`). On Windows `ReadPIDFile` treats any live PID as valid and never cleans the file, so a recycled PID makes a fresh hostagent fail with "another hostagent may already be running." This is the inverse of the signal hazard — a false "running," not a wrong-target kill — and is pre-existing (uses Lima's helper). Validate the read PID with `IsOurProcess(pid, "hostagent", name)` before refusing, or clear a non-matching file.

- **Service-PID false-negative orphans a live control plane (future)** [Claude Opus 4.8] — `IsOurProcess` compares the target image to `os.Executable()`. After an in-place binary upgrade to a different path, or a transient PEB read failure, the live service reads as "not ours," `PID()` removes the file (`service.go:166`), and `Running()` reports the control plane down. The author documents exactly this in the `longPath` comment ("for the service PID a false 'not ours' would orphan a live control plane") and mitigates the short-path form with normalization; the moved-binary form remains. Self-healing on the next reconcile and implausible pre-release.

### Strengths

- The PEB walk is correct against `x/sys@v0.43.0`: the `PROCESS_BASIC_INFORMATION → PEB → RTL_USER_PROCESS_PARAMETERS → CommandLine` chain, the byte-counted `NTUnicodeString.Length` (divided by 2 for UTF-16), and the full-read check all hold. [Claude Opus 4.8, Codex GPT 5.5]
- `longPath` degrades to lexical `filepath.Clean` on resolution failure rather than a guaranteed mismatch, biasing toward keeping a live service. [Codex GPT 5.5]
- The handle-vs-PID split — `procExited` for in-memory `*exec.Cmd` paths, `IsOurProcess` for on-disk PIDs — keeps the common path simple and answers @mook-as's feedback precisely. [Claude Opus 4.8, Codex GPT 5.5]

## Review Process Notes

### Skill improvements

- When a finding alleges that a library's force-stop, kill, or delete-with-force call reaches the wrong process, trace that library's platform-specific termination primitive before assigning severity. The same cross-platform API can map to a bounded per-process kill on one OS and a process-group or console-wide broadcast on another (for example a Windows `GenerateConsoleCtrlEvent` that escapes to the shared console and kills the calling service). The blast radius — contained kill versus session-wide crash — decides the severity, so the primitive must be read, not assumed from the API name.

### Repo context updates

- [repo] On Windows, Lima's `instance.Delete(force=true)` → `StopForcibly` → `osutil.SysKill` sends `GenerateConsoleCtrlEvent(CTRL_BREAK)` to both `DriverPID` and `HostAgentPID` taken from on-disk state (`lima/pkg/osutil/osutil_windows.go`), ignoring the requested signal even for SIGKILL. Any rdd caller that hands a Lima instance to `Delete`/`StopForcibly` without zeroing its PIDs on Windows can broadcast CTRL_BREAK to a recycled PID and crash the rdd service. `handleDeletion` clears both PIDs first; audit every other `limainstance.Delete` caller for the same scrub.
- [repo] Lima's `store.Inspect` sets `StatusRunning` only after connecting to the hostagent socket and calling `Info()` (`lima/pkg/store/instance.go:71-88`); a recycled `HostAgentPID` not listening on that socket downgrades to `StatusBroken`. So `Status == StatusRunning` is a reliable "this `HostAgentPID` is genuinely ours" signal, but no such check backs `DriverPID`. When reviewing PID-trust decisions gated on Lima status, treat StatusRunning as identity evidence for HostAgentPID only.

### Executive Summary

This PR adds `process.IsOurProcess` (a Windows PEB-walk image+command-line check) and applies it before any graceful `CTRL_BREAK`/`taskkill` driven by an on-disk PID, plus guards the service PID file against recycled PIDs. ### Findings

#### Critical Issues

None.

#### Important Issues

**I1. `IsOurProcess` requires `PROCESS_VM_READ`, so an elevation/integrity-level mismatch makes a live control plane read as not-running** — `pkg/util/process/process_windows.go:64-65`, `pkg/service/cmd/service.go:161-163` (IMPORTANT, regression)

```go
handle, err := windows.OpenProcess(
    windows.PROCESS_QUERY_LIMITED_INFORMATION|windows.PROCESS_VM_READ, false, uint32(pid))
if err != nil {
    return false
}
```

`PID()` previously treated any live PID (via `os.FindProcess`, which needs only `PROCESS_QUERY_INFORMATION`) as our control plane on Windows. The new guard calls `IsOurProcess`, which opens with `PROCESS_VM_READ` (needed for the PEB command-line read). If the CLI runs at a different integrity level than the running `service serve` process (service started elevated, CLI not, or vice versa), `OpenProcess(PROCESS_VM_READ)` is denied, `IsOurProcess` returns false, `PID()` deletes the live PID file (service.go:166) and reports `PIDNotFound`. `Running()` then returns false for a healthy control plane, so `rdd svc start` tries to start a second instance and `StopWithWait` cannot find the process to signal.

In RDD's normal flow CLI and service share integrity level (CLI spawns the service), so this is an edge case, not a routine failure — hence IMPORTANT, not CRITICAL.

Fix: short-circuit before the VM read — if `processImagePath` already matches `self`, the image-path check (which needs only `PROCESS_QUERY_LIMITED_INFORMATION`) is strong evidence on its own; consider opening with `PROCESS_QUERY_LIMITED_INFORMATION` first for the image check and only escalating to `PROCESS_VM_READ` for the command-line read, treating a `PROCESS_VM_READ` denial on an image-matched process as "ours". Alternatively document that CLI and service must run at the same integrity level.

#### Suggestions

**S1. `IsOurProcess` returns true on image-match alone when called with no substrings, but the docstring describes substring matching as integral** — `pkg/util/process/process_windows.go:59-85` (SUGGESTION, enhancement)

```go

```

The risk is low because the image must still be the rdd binary.

Fix: no code change required; consider a docstring note that calling with zero substrings checks the image only, and that production callers should always pass a discriminator.

### [Gemini] — Pass 1

### Executive Summary

This PR implements process identity verification on Windows to prevent `CTRL_BREAK` or `taskkill` from reaching unrelated processes when a stale PID is recycled. While the PEB-walking mechanism correctly identifies the running executable, the unanchored command-line matching risks false positives across control-plane instances, and the `service serve` verification lacks an instance discriminator entirely. Additionally, the Unix fallback incorrectly assumes orphaned PIDs are immune to recycling, leaving a pre-existing gap where stale PID files can cause cross-process termination on Linux and macOS.

### Findings

#### Critical Issues
None.

#### Important Issues

I1. **Unanchored substring matching risks cross-instance termination** — `pkg/util/process/process_windows.go:79-83`

```go
	for _, s := range cmdlineSubstrings {
		if !strings.Contains(cmdline, s) {
			return false
		}
	}
```

`IsOurProcess` uses unanchored substring matching on the raw PEB command line, which typically includes the full executable path. If the `rdd` binary resides in a directory whose name matches the target instance (e.g., `C:\rancher-default\rdd.exe`), `strings.Contains(cmdline, "default")` will evaluate to `true` for *any* instance's hostagent running from that path. This causes `IsOurProcess(pid, "hostagent", "default")` to falsely confirm a recycled PID belongs to the `default` instance even if it actually runs `other-vm`, defeating the identity guard and risking termination of the wrong hostagent.

**Fix**: Use `windows.CommandLineToArgv` to parse the raw command line string into an array of discrete arguments. Perform exact string matching on the parsed arguments (or substring matching pinned to specific argument indices) rather than searching the entire unanchored string.

I2. **Missing instance discriminator for `service serve`** — `pkg/service/cmd/service.go:161`

```go
		// not-running. IsOurProcess is a no-op (true) on other platforms.
		if err == nil && !process.IsOurProcess(pid, "service", "serve") {
			err = fmt.Errorf("pid %d is not our control plane", pid)
		}
```

The `service serve` invocation does not include an instance name in its command line. Consequently, `IsOurProcess` only confirms the PID is running *a* control plane, not the *target* control plane. If multiple `rdd` instances run concurrently (e.g., isolated environments or rapid start/stop BATS tests) and a stale PID is recycled to another instance's `service serve`, `PID()` will incorrectly adopt it. This causes `rdd svc start` to hang waiting on the wrong API server port, or allows `StopWithWait` to signal a different instance's control plane.

**Fix**: Add a hidden, ignored flag (e.g., `--instance-id`) to the `serve` command definition in Cobra. Append `--instance-id=` + `instance.Name()` to `cmdArgs` when spawning `service serve`, and require this exact argument in the `IsOurProcess` check.

I3. **Unix implementation falsely assumes orphaned PIDs are not recycled** — `pkg/util/process/process_unix.go:30-33`

```go
// ... On Unix it is always true: PIDs are not recycled within a
// daemon's lifetime the way they are on Windows, and Interrupt (SIGINT) to a
// stale PID is a harmless no-op, so callers need no identity guard. ...
func IsOurProcess(_ int, _ ...string) bool {
	return true
}
```

While PIDs are not recycled while a parent holds a zombie child, `killOrphanedHostagent` and `PID()` read stale PIDs from on-disk files written by *previous* daemon runs. These PIDs can be hours or days old, giving the OS ample time to wrap around and recycle the PID to a new process owned by the same user. Returning `true` unconditionally bypasses the identity guard, and sending `SIGINT` to that recycled PID is not a "harmless no-op"—it will likely terminate the unrelated process. 

**Fix**: Implement `IsOurProcess` for Unix by verifying process identity (e.g., reading `/proc/<pid>/cmdline` on Linux or using `sysctl` `KERN_PROCARGS2` on macOS) to ensure the target process is still `rdd`.

#### Suggestions

S1. **Avoid unnecessary buffer doubling in `resolveLongPath`** — `pkg/util/process/process_windows.go:116-126`

```go
	for bufSize := uint32(1024); bufSize <= 32768; bufSize *= 2 {
		buf := make([]uint16, bufSize)
		n, err := windows.GetLongPathName(p16, &buf[0], bufSize)
        // ...
		// n >= bufSize: the buffer was too small and n is the required size; grow.
	}
```

Unlike `QueryFullProcessImageName`, `GetLongPathName` returns the exact required buffer size in `n` when it fails with `ERROR_INSUFFICIENT_BUFFER`. The `for bufSize *= 2` loop ignores this specific capacity signal and blindly doubles the buffer up to 32768, taking up to 6 iterations.

**Fix**: Remove the loop. Allocate a 1024-element buffer initially; if `n > 1024`, immediately reallocate a buffer of size `n` and call `GetLongPathName` exactly once more.
