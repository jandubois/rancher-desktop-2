Executive Summary ¶

This PR replaces Windows' console-event interrupt and PEB/command-line identity check with a per-process named event, Local\rdd-interrupt-<key>-<pid>. Delivery no longer needs a shared console, identity becomes a path-independent, recycle-PID-safe OpenEvent, and ~200 lines of cross-process memory reading disappear. Both reviewers found no critical issues and converged on one Important regression: the daemon writes its PID file before registering the event, so PID() reads it as "not ours" during a startup window the old check never had.

Two reviewers ran (Claude Opus 4.8, Codex GPT 5.5); Gemini was dropped after an authentication failure. Both independently raised the same I1 and agree on severity.

S2. Hostagent writes its PID file before registering its interrupt event Claude¶

The same ordering as I1, far lower risk: only runtime.LockOSThread and signal.Notify run between the PID write (line 61) and registration (line 93), and the controller checks that consult IsOurProcess(HostagentInterruptKey, ...) S3. Local\ namespace limits the event to the interactive session Claude¶

The doc comment already notes that Local\ scopes the event to the current session and that a session-0 Windows service would need Global\. The choice is right for the GUI-app-in-interactive-session model, but it is a hard dependency for any future packaging that runs the daemon as a service: Interrupt would silently fail and fall back to a hard Kill, skipping the controller-manager drain. If Windows-service packaging is on the roadmap, record this in docs/design/ rather than only in code.

Design Observations ¶

Concerns ¶

  • Identity gated on registration timing (in-scope) Claude — I1 and S2 share one root: identity is proven by an event created partway through startup, not at process creation, as the old command-line check was. Registering the event as the first startup action closes the window for both roles.

Strengths ¶

  • Named-event mechanism replaces cross-process memory reading (in-scope) Claude Codex — the change deletes the entire PEB/ReadProcessMemory/image-path path (~200 lines) in favor of one OpenEvent. Identity becomes path-independent (any rdd binary is recognised) and recycle-PID-safe, fixing the app-bundle-vs-standalone mismatch the old image-path compare suffered.
  • Delete db-first guard (in-scope) Claude Codex — removing db/ before the rest of the directory probes the one resource a live daemon locks. On Windows the lock makes RemoveAll fail deterministically and aborts the delete; on Unix the earlier StopWithWait already guarantees the daemon is gone. It even catches a live pre-fix daemon that PID() cannot confirm.
  • RegisterInterruptHandler lifecycle is correct (in-scope) Claude — the manual-reset event latches the signal so the watcher cannot miss a racing SetEvent; the release event plus sync.Once closure waits on <-done before closing handles, so no use-after-close; onInterrupt fires only on WAIT_OBJECT_0.

Acknowledged Limitations ¶

  • Local\ session scope (process_windows.go:36-38) — the event does not reach a session-0 service; correct for the current GUI-app model, surfaced as S3 only to suggest doc placement.
  • Unix recycled-PID residual risk (process_unix.go:48-54) — IsOurProcess is a deliberate no-op, so a recycled on-disk PID could be signalled; accepted because Unix reuses PIDs far less aggressively, and this PR does not worsen it.
  • ServeInterruptKey carries no instance (service.go:166-168) — a PID recycled to a different instance's control plane would pass; needs concurrent instances (dev/test only).
  • Sequential hostagent shutdown wait (limavm_controller.go:657) — existing TODO, N × gracefulShutdownTimeout worst case; unchanged here.
  • DriverPID not screened by IsOurProcess (limavm_lifecycle.go:680-686) — the qemu/wsl driver registers no event, so a recycled DriverPID is still taskkilled; existing TODO proposes a Windows Job Object. The comment was correctly updated to the event-based rationale.

Review Process Notes ¶

Skill improvements ¶

  • When a change moves how a process proves its identity or liveness — from an attribute fixed at process creation (argv, executable path) to a resource created during startup (a registered event or handler, a named object, a bound socket, a lock file) — check the ordering of startup steps. Any interval between the point the process becomes discoverable to peers (writes its PID file, takes a lock) and the point its identity becomes confirmable (creates that resource) is a window in which liveness or identity probes read the process as absent or not-ours. Flag a discoverability step that precedes the identity-establishing step, and recommend establishing identity first.

Repo context updates ¶

  • [repo] On Windows, a process proves its identity and receives graceful-interrupt requests through a per-process named event, Local\rdd-interrupt-<key>-<pid>, created by process.RegisterInterruptHandler at startup. process.Interrupt, process.IsOurProcess, and process.IsAlive (pkg/util/process) are the canonical primitives, and Interrupt/IsOurProcess/RegisterInterruptHandler take a role key (ServeInterruptKey, HostagentInterruptKey). The earlier PEB/command-line/image-path identity check (IsOurProcessWithArg) was removed. When reviewing Windows process-lifecycle code, expect identity via the named event, not via image-path or command-line comparison, and check that any process which can be an Interrupt target registers its event before it writes its PID file.
