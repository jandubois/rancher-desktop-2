Executive Summary ¶

PR #383 adds process.IsOurProcess to verify a Windows PID still runs rdd's own executable before signalling or taskkilling it, guards service.PID() against recycled PIDs, and makes shutdownAllHostagents reclaim leftover PID files and WSL2 distros after every graceful shutdown. The hardening is careful and thoroughly commented. The one gap: killOrphanedHostagent verifies identity before its 30-second graceful wait but not before the forceStop that follows — unlike its sibling shutdownHostagent, which re-checks.

Three cloud reviewers ran. Codex found nothing to fix; Claude raised robustness and documentation suggestions; Gemini surfaced the one Important gap (I1) and the underlying lifecycle design concern.

S1. Anchor the instance-name discriminator passed to IsOurProcess Gemini Claude¶

Callers pass the raw inst.Name as the command-line discriminator, which IsOurProcess matches with strings.Contains. Its docstring warns that "vm" matches a hostagent for "vm2" and tells callers to "pass a name distinct enough" — but the callers pass the bare name. With concurrent prefix-named instances (dev/test only) plus PID recycling, the cleanup for "vm" could verify and taskkill "vm2"'s live hostagent. The hostagent command line ends with the name as its final argument, so a whole-token match closes the gap. (suggestion, gap)

Fix: pass " "+inst.Name (anchoring the leading space), or pass the per-instance pidfile path, which cannot collide.

S2. resolveLongPath need not double the buffer Gemini¶
pkg/util/process/process_windows.go
func resolveLongPath(p string) (string, error) {
	p16, err := windows.UTF16PtrFromString(p)
	if err != nil {
		return "", err
	}
	for bufSize := uint32(1024); bufSize <= 32768; bufSize *= 2 {
		buf := make([]uint16, bufSize)
		n, err := windows.GetLongPathName(p16, &buf[0], bufSize)
		if err != nil {
			return "", err
		}
		if n < bufSize {
			return windows.UTF16ToString(buf[:n]), nil
		}
		// n >= bufSize: the buffer was too small and n is the required size; grow.
	}
	return "", windows.ERROR_INSUFFICIENT_BUFFER
}

// processImagePath returns the full path to the executable backing the process.

GetLongPathName returns the exact required size in n when the buffer is too small, so the doubling loop issues extra syscalls for very long paths instead of allocating n directly. processImagePath must double because QueryFullProcessImageName does not report its needed size — but resolveLongPath has the size and can skip the loop. The code is correct as written; the parallel structure with processImagePath is deliberate, so this is optional. (suggestion, enhancement)

Fix: allocate 1024, and on n >= len(buf) reallocate to exactly n once.

// readProcessMemory copies size bytes at addr in the target process into dest,
// erroring unless the full range was read.
func readProcessMemory(handle windows.Handle, addr uintptr, dest unsafe.Pointer, size uintptr) error {

readProcessMemory errors unless the full unsafe.Sizeof(params) range is read, yet the only field used (CommandLine) sits near the front of the struct. The read works in practice: ntdll allocates ProcessParameters as one block (the struct plus its string buffers plus the environment), so the trailing bytes are mapped, and TestProcessCommandLineReadsOwnCommandLine confirms it on CI. The cost is coupling to x/sys's full struct layout, not a live failure. (suggestion, enhancement)

Fix: read only through CommandLine (its offset plus size), or document why a full-struct read is safe on supported Windows.

Design Observations ¶

Concerns

  • exec.CommandContext hard-kills the hostagent before it can self-clean (future) Gemini — startInstance spawns the hostagent with exec.CommandContext(ctx, …) and leaves Cmd.Cancel/Cmd.WaitDelay unset (limavm_lifecycle.go:431), so a manager-context cancel hard-kills it (TerminateProcess on Windows, SIGKILL on Unix) before it runs its own teardown. The PR compensates by reclaiming the leftovers externally — stopInstanceForcibly after the wait — which is sound. A cleaner structure sets haCmd.Cancel to send process.Interrupt and haCmd.WaitDelay to bound the grace period (Go 1.20+, and go.mod declares 1.25.7), letting the hostagent run its own shutdown (driver termination, distro cleanup, tmp removal) instead of relying on external reclaim.
  • The recycled-PID guard is copied at five sites (future) Claude — the pattern safeInst := *inst; if safeInst.HostAgentPID > 0 && !process.IsOurProcess(…) { safeInst.HostAgentPID = 0 }; stopInstanceForcibly(…, &safeInst) now appears at limavm_lifecycle.go:209,546,600,665 and limavm_controller.go:566. I1 is the site that forgot the guard. A stopInstanceForciblyVerified(ctx, logger, inst) that clears a recycled HostAgentPID internally would make the guard impossible to omit at the next call site.
  • PID identity is validate-then-use (future) Codex — IsOurProcess validates a PID and a later call acts on it, leaving the validate-then-use race (I1) and the unchecked DriverPID the comments flag. Tracking hostagent and driver processes through a Windows Job Object rather than on-disk PID files would remove both, because the kernel terminates the job's members regardless of PID reuse. The code already names Job Objects as the proper fix.

Strengths

  • The procExited gate (hostagent_watcher.go:213-217, limavm_controller.go:519-523) separates the in-memory *exec.Cmd paths — handle held, PID cannot recycle — from the on-disk-PID paths that need IsOurProcess. Claude
  • Extracting forceStopForDeletion deduplicates the force-stop logic and applies it to the previously-unguarded leftover-instance path (limavm_controller.go:218). Claude
  • IsOurProcess returns false, never an error, for any unconfirmable state, so callers safely treat "unknown" as "not ours." Claude Codex
  • The identity check lives in pkg/util/process with a Unix no-op that keeps the signature. Codex
  • The command line is read from the PEB natively, avoiding WMI or external tools, and long-path normalization handles 8.3 short-path launches. Gemini

Review Process Notes ¶

Skill improvement — Correctness dimension: guard staleness across a wait. When a destructive action (kill, delete, overwrite, unlock, free) is gated by an identity, ownership, or existence check, and a blocking wait or long-running call separates the check from the action, flag the absence of a re-check immediately before the action. The guarded entity can change identity during the wait — a recycled process ID, a replaced file, a released lock, an expired lease — so a check that passed before the wait need not hold after it. When one call path re-checks after the wait and a sibling path does not, the sibling is the likely bug. (This dimension would have surfaced the one Important finding, which only one of three reviewers caught.)

[repo] Repo context — Windows force-stop guard placement. On Windows, every force-stop path that taskkills an on-disk HostAgentPID must screen it with process.IsOurProcess immediately before the kill, because Windows recycles PIDs and a stale PID may resolve to an unrelated process. A check made only at an earlier signal decision is insufficient when a graceful wait separates it from the kill — re-screen after the wait. When reviewing a new or changed force-stop path, confirm the guard sits at the point of the taskkill, not just upstream.
