Executive Summary ¶

The stager is well built: content-addressed verification at both hops, atomic publication, and an error taxonomy that puts the retry decision where the knowledge is. Two gaps matter. The download carries no deadline, so a stalled server hangs make build-rdd forever and never reaches the retry loop. And nothing tests that a cache entry is verified rather than trusted: replacing that check with a bare os.Stat leaves the whole suite green.

PR #711 is stacked on unmerged #511, so this round scopes findings to febd11736's seven files; S8 belongs to #511 and is attributed there. Three reviewers reached I1 independently. go test, go vet and golangci-lint were run from the review SHA and are all clean.

Design Observations ¶

Concerns ¶

  • The fetched body is bounded in neither size nor time (future) Claude Opus 5. I1 covers time. On size, io.Copy at stage.go:167 writes until the server stops and the checksum can only reject afterwards, so an endless stream fills the build machine's disk before anything notices. The manifest records a checksum but no length, so the cheap guard is a hard ceiling via io.LimitReader. Low likelihood, since the URL is a pinned GitHub release from a checked-in file, but the guard removes the class in three lines.
  • make clean will not reset a staged asset (future, #708) Claude Opus 5. rdd/Makefile:196-199 removes bin and the guest agent only (verified). Once pkg/embedded/distro.raw.xz is a build input, a developer who suspects a bad stage has no make verb to drop it.
  • EMBEDDED_SOURCES will not see the staged image (future, #708) Claude Opus 5. rdd/Makefile:69 globs only *.yaml and *.json under ./cmd and ./pkg (verified). When #708 adds the //go:embed, a re-staged image will not by itself trigger a rebuild of bin/rdd.
  • The dependency list is hard-coded in the downloader (future) Gemini 3.5 Flash. stagedDeps names distro in a Go literal. That is right for one dependency; as the embedded set grows, deriving it from a manifest field would stop the two sides drifting.
  • A checksum mismatch is classified as permanently fatal (in-scope, no change recommended) Claude Opus 5. stage.go:168-171 marks it fatalError and TestStageRejectsUnexpectedBytes pins requests == 1. Over HTTPS an in-flight corruption is effectively impossible, and re-downloading 207 MiB three times to learn the manifest is stale is the worse trade. Recorded so a later round does not re-litigate it.

Strengths ¶

  • The three-state design (cache, staged copy, both verified by content and not by timestamp) is the right shape, and every behaviour the PR description claims held under test Claude Opus 5 Codex GPT 5.6 Sol.
  • createTemp always opens the temp file in the destination's own directory, so os.Rename never crosses a device boundary Gemini 3.1 Pro Gemini 3.5 Flash.
  • The fatal-versus-retryable split puts the retry decision where the knowledge is, instead of leaving the caller to pattern-match error strings Claude Opus 5.
  • Select requires exactly one match (manifest.go:171) rather than taking the first, so a manifest that grows an overlapping asset fails the build instead of silently changing what ships Claude Opus 5 Codex GPT 5.6 Sol.
  • --os/--arch as flags rather than GOOS/GOARCH, with the cross-compilation rationale written down at main.go:8-12. That is the kind of decision that gets silently "simplified" later once the comment is gone Claude Opus 5 Codex GPT 5.6 Sol.
  • The Go reader is strictly narrower than the TypeScript writer on every axis compared (https-only vs any parseable URL; lowercase-only hex vs case-normalised). Nothing the writer emits is rejected and nothing the reader accepts is looser, which is the safe direction for a two-parser grammar Claude Opus 5.

Testing Assessment ¶

The suite is good: eleven tests across the two packages, a fake asset server that counts requests, and TestStagedDepsResolveAgainstTheManifest, which catches a renamed or dropped asset in rdd/dependencies.yaml at make test rather than in a build. go test, go vet and golangci-lint run on both new packages were executed from the review SHA and are clean.

Gaps, highest risk first:

  1. A cache entry present but not matching the checksum. I2 proves this cell is uncovered and that its regression is silent.
  2. Four consecutive failures. TestStageRetriesATransientFailure covers two failures then success; nothing exercises four consecutive failures, so neither downloadAttempts = 4 nor the final error wrapper at stage.go:127 is pinned.
  3. Context cancellation mid-download. main.go:39 promises an interrupt will "abort it and clean up", but no test cancels during a transfer and asserts no temp file survives.
  4. A failed copy into the destination directory. assertNoTempFiles (stage_test.go:89) globs only under cacheDir, so copyFile's cleanup path is never observed.
  5. assertNoTempFiles is itself fragile. Its glob hard-codes two directory levels below cacheDir (stage_test.go:91). Any change to cachePath's layout makes it match nothing and pass vacuously.
  6. DefaultCacheDir and run have no tests at all, including the os.UserCacheDir error path that main.go:55 propagates.

Review Process Notes ¶

Skill improvements ¶

  • When a reviewer's proposed fix would add work that no code consumes yet, treat the finding as documentation drift rather than a missing feature. A comment describing intended future behaviour is evidence about a plan, not about a defect; implementing it to satisfy the comment inverts the direction of the fix. Verify that a consumer exists before accepting any finding whose remedy is "add the missing call".
  • When a finding rests on platform behaviour the review host cannot exercise, settle the mechanism against the toolchain's own source before assigning a severity. Language runtimes make specific, checkable choices (file share modes, rename primitives, signal numbers), and reading the pinned source turns an untestable guess into a citable claim, or refutes it. Record the file and line as the finding's evidence and mark it Unproven: for the reproduction, not for the mechanism.

Repo context updates ¶

  • [repo] The TypeScript downloader in scripts/lib/download.ts is the house reference for download behaviour: it checks the destination's checksum before fetching, and retries with exponential backoff capped at a ceiling. When reviewing a new downloader in any language, compare it against that file before rating a retry schedule or a cache-reuse decision as adequate.
  • [repo] rdd/Makefile defines EMBEDDED_SOURCES by globbing only *.yaml and *.json under ./cmd and ./pkg. A change that adds a new //go:embed of any other file type creates a build input that is not a prerequisite of bin/rdd, so the binary will not rebuild when that file changes. Flag it.
