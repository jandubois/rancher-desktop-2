I2. StopWithWait can pass PIDNotFound (0) to process.Interrupt Codex¶
pkg/service/cmd/service.go

// StopWithWait sends a shutdown signal to the service. When wait is true, it
// blocks until the process exits, ctx is cancelled, or timeout elapses; pass
// timeout 0 to wait indefinitely (bounded only by ctx).
func StopWithWait(ctx context.Context, wait bool, timeout time.Duration) error {
	if !Running() {
		return fmt.Errorf("%q control plane is not running", instance.Name())
	}

	pid := PID()
	// Try graceful shutdown first. On Unix, Kill already sends SIGTERM which
	// triggers the Go signal handler. On Windows, Kill uses TerminateProcess
	// which bypasses all handlers, so we send Interrupt (CTRL_BREAK_EVENT)
	// first to let the service run its shutdown path (shutdownAllHostagents).
	//
	// On Unix, Interrupt (SIGINT) always succeeds for a valid PID, so the
	// Kill fallback never fires. On Windows, Interrupt uses
	// GenerateConsoleCtrlEvent, which fails when caller and target lack a
	// shared console; Kill (TerminateProcess) then bypasses graceful shutdown.
	// Hostagents survive in their own process groups and self-heal on the
	// next service start via killOrphanedHostagent.
	if err := process.Interrupt(pid); err != nil {
		if err := process.Kill(pid); err != nil {
			return fmt.Errorf("failed to stop %q control plane with pid %d: %w", instance.Name(), pid, err)
		}
	}

Running() calls PID(), then line 468 calls it again without rejecting PIDNotFound. If the daemon exits, a concurrent stop removes the file, or a transient identity check fails between the two reads, the second PID() returns 0. Interrupt(0) is GenerateConsoleCtrlEvent(CTRL_BREAK, 0) — every process sharing the console — on Windows, and kill(0, SIGINT) — the caller's whole group — on Unix. The double-read is pre-existing (identical at merge-base); this PR's new IsOurProcess path adds a fresh way for read #2 to return 0. Likelihood is low; the consequence is the exact broadcast hazard the PR targets. Distinct from the Round 2 declined "transient false-negative removes the PID file," which concerned file removal, not signalling 0.

Fix: read PID() once, return early on PIDNotFound, then signal.

S3. resolveLongPath could size the buffer in one retry instead of doubling Gemini¶

GetLongPathName returns the exact required length when the buffer is too small, so a single resize would suffice; the loop doubles instead. The practical cost is nil — an executable path fits 1024 units on the first call — and the doubling mirrors processImagePath, which must double because QueryFullProcessImageName does not report its required size. Keeping both helpers on one idiom is a defensible reason to leave this unchanged.

Fix (optional): allocate n and retry once; or keep the loop for consistency with processImagePath.

Design Observations ¶

Concerns

  • exec.CommandContext force-kills the hostagent on manager shutdown, bypassing graceful signalling (in-scope) Gemini — startInstance binds haCmd to the manager context (limavm_lifecycle.go:431). waitForShutdown blocks on that same context's Done() and only then runs shutdownAllHostagents (limavm_controller.go:520-522), so on Windows Go's exec has already called TerminateProcess: procExited closes promptly, the Interrupt loop skips the dead PID, and taskkill /T cannot reach orphaned children. This is deliberate — commit ba400557's "always reclaim" exists to clean up after the force-kill, and KillTree documents the orphaned forwarders as harmless. Gemini's alternative (exec.Command, no context) would enable signal-based teardown but loses the guaranteed-cleanup safety net and relies on a console-bound CTRL_BREAK a detached service cannot deliver. The current design is defensible; recorded as an observation, not a defect.
  • DriverPID is force-killed without an identity check (future) Claude Codex — IsOurProcess matches the rdd image, not qemu/wsl, so the restart paths taskkill a stored DriverPID unverified (limavm_lifecycle.go:201-206). The PR scopes itself to the HostAgentPID/CTRL_BREAK hazard and names Job Objects, tracking the hostagent+driver tree, as the class fix. On Windows RDD uses WSL2, where DriverPID is typically 0, so the live exposure is small. Worth a tracked follow-up rather than more PID-file patching.
  • Reconcile's sentinel cleanup path removes the directory without unregistering the distro (future) [orchestrator, carried from Round 4] — the sentinel branch (limavm_controller.go:205) uses a bare os.RemoveAll, unlike the leftover-instance and stale-directory paths that now terminate/unregister. This is pre-existing/PR #392 code, outside PR #383's diff; restated for continuity.

Strengths

  • The procExited-gated skip in signalHostagent (hostagent_watcher.go:213-219) and shutdownAllHostagents (limavm_controller.go:550-554) ties "safe to signal" to the OS handle still being held — the real invariant — rather than to on-disk state. (in-scope) Claude
  • The force-stop paths re-check HostAgentPID immediately before each destructive use, so a stored PID is never trusted once time has passed. (in-scope) Codex
  • hostAgentPIDFile is the exact --pidfile value passed at launch (limavm_lifecycle.go:646), an unambiguous per-instance discriminator that cannot match a sibling whose name is a prefix. (in-scope) Claude Codex
  • processCommandLine guards the zero/odd-length case before &buf[0], sizes the read to the buffer rather than to Length, and errors on a short read — careful unsafe code backed by a struct-offset regression test. (in-scope) Claude
  • removeStaleInstance now terminates the WSL2 distro before unregistering and drops the redundant GOOS guard, landing the Round 4 design observation. (in-scope) [orchestrator]

  • DriverPID killed unchecked on Windows — limavm_lifecycle.go:201-206, 596-599. IsOurProcess matches the rdd image, not qemu/wsl; Job Objects named as the proper fix. The orphaned driver must die, so a restart cannot zero it.
  • Handle-release vs. procExited-close window — hostagent_watcher.go:212-216, limavm_controller.go:539-545. cmd.Wait() releases the OS handle just before closing the channel; the window is a few instructions.

Declined in prior rounds (Round 2 Resolution, Commented; surrounding code unchanged):

  • PID() removes the PID file on a transient identity-check failure — service.go. Near-impossible for a same-user process holding only query rights. (I2 is separate: it concerns signalling 0, not file removal.)

Review Process Notes ¶

Skill improvement — Correctness dimension: a substring identity check against a full command line is defeated by the shared image path. When code identifies a process by testing whether its command line contains a discriminator substring, remember that the command line begins with argv[0] — the image path — which is identical for every invocation of the same binary. A discriminator that can also appear in the install path (a username, a parent directory, an unrelated subcommand argument) matches every invocation and collapses the check to the image-path test alone. Recognize the pattern as strings.Contains(commandLine, token) (or equivalent) used for identity; flag it and recommend matching a parsed argv token, because argv[0] is shared across a binary's invocations.

[repo] The control-plane daemon has two launch spellings; service-PID identity must accept both. RDD starts the daemon by self-spawning the canonical service serve and also accepts the svc serve alias, so an identity check on the service PID must recognize either invocation. Because every rdd process shares the same argv[0] (the install path), a strings.Contains discriminator on the full command line can be silently defeated by an install path containing the token. When reviewing changes to service.PID() or its discriminator, verify it matches a command token rather than a raw substring, and that it accepts both launch spellings.
