## Executive Summary

PR #390 adds `rdd run COMMAND [ARGS...]`, which starts Rancher Desktop and runs a child process wired to the instance's Docker and Kubernetes contexts through `PATH`, `DOCKER_CONTEXT`, and a throwaway `KUBECONFIG`. The wiring is clean and copied credentials stay 0600. Two UX defects hit common inputs: a non-zero child exit prints a blank `level=error` line, and `rdd run --help` boots the VM before failing instead of showing help.

All three reviewers independently flagged the blank error line and the `--help` defect; both were reproduced live. The remaining findings — a documentation contract that overstates kubeconfig isolation, a Docker/Kubernetes coupling on kubeconfig load, and signal/cleanup gaps — each came from a single reviewer and verify against the code.

## Important Issues

I1. **Non-zero child exit prints a blank `level=error` line** — `cmd/rdd/run.go:196-199` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro]

```go
var exitErr *exec.ExitError
if errors.As(err, &exitErr) {
	return &cliexit.Error{Code: exitErr.ExitCode()}
}
```

`execCommand` builds `cliexit.Error` with a nil `Err`, so its `Error()` returns `""` (`pkg/cli/exit/exit.go:31-33`). `main.go:173-176` matches the error, calls `logrus.Error(err)`, then exits. The empty message emits a bare `level=error` line after the child's own stderr. Error level always reaches the terminal (default `warn`), so this fires on every non-zero child exit — a `grep` no-match, a false `test`, any failing `docker`/`kubectl`. Reproduced live. The other producers (`Rejected`, `Timeout`) always wrap a real error, so only this new site regresses.

Fix: guard the log on a non-empty message.

```diff
 if errors.As(err, &exitErr) {
-    logrus.Error(err)
+    if exitErr.Err != nil {
+        logrus.Error(err)
+    }
     os.Exit(exitErr.Code)
 }
```

I2. **`rdd run --help` boots the VM, then fails instead of showing help** — `cmd/rdd/run.go:54-56` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro]

```go
Args:               cobra.MinimumNArgs(1),
DisableFlagParsing: true,
RunE:               runAction,
```

`DisableFlagParsing: true` stops cobra from intercepting `--help`/`-h`. `runAction` strips only a leading `--`, so `rdd run --help` satisfies `MinimumNArgs(1)`, runs `ensureAppRunning` (a full App start and settle wait), then tries to exec `--help` as a binary. Run live, it booted the App and ended with `exec: "--help": executable file not found in $PATH`. A user reaching for `--help` to discover the command instead starts a VM and meets a confusing error; only `rdd help run` works today.

Fix: handle the help flags before `ensureAppRunning`.

```go
if args[0] == "-h" || args[0] == "--help" {
    return cmd.Help()
}
```

I3. **Help text and design doc overstate kubeconfig isolation** — `cmd/rdd/run.go:36-42`, `docs/design/cmd_app.md:77` [Codex GPT 5.5]

Both the long help and the design doc state the user's `~/.kube/config` is "left untouched." `rdd run` itself honors that — it writes a throwaway file. But `runAction` calls `ensureAppRunning` first (run.go:74), and starting the App merges the instance context into `~/.kube/config` once k3s is healthy (`kube_reconciler.go:353` → `createReplaceKubeContext`, no path-management gate).

The project's own `docs/design/api_app.md:39` confirms it: "When the `App` is starting it creates the Docker context and sets up the kubeconfig in `~/.kube/config`." The throwaway file protects the user's *selected* context, not the file contents.

Fix: say `rdd run` does not change the *selected* context, and note that startup adds the instance entry to `~/.kube/config` as usual. Reconcile the stale `~/.rd2/kube.config` references in `api_app.md:43` and `bootstrap.md:97`.

## Suggestions

S1. **A malformed `~/.kube/config` breaks Docker-only `rdd run` commands** — `cmd/rdd/run.go:150-153` [Codex GPT 5.5]

```go
src, err := clientcmd.NewDefaultClientConfigLoadingRules().Load()
if err != nil {
	return "", fmt.Errorf("load kubeconfig: %w", err)
}
```

`runAction` calls `writeRunKubeconfig` unconditionally (run.go:74), and `Load()` aggregates and returns parse errors for any file in the precedence chain (`client-go` `loader.go:40,85`). So a single corrupt kubeconfig fails `rdd run docker ps` with `load kubeconfig: ...` before Docker ever runs, coupling a Docker-only command to unrelated Kubernetes state. A missing file is fine — `Load()` skips it — so only a malformed file triggers this.

Fix: for non-kube commands, tolerate a load failure by falling back to the empty-config path the missing-context case already uses (write only `CurrentContext`), or defer kubeconfig creation until a kube command needs it.

S2. **`isKubeCommand` misses the `rdd kubectl` / `rdd helm` alias on a cold start** — `cmd/rdd/run.go:91-94` [Gemini 3.1 Pro]

```go
func isKubeCommand(name string) bool {
	base := strings.TrimSuffix(filepath.Base(name), ".exe")
	return base == "kubectl" || base == "helm"
}
```

`ensureAppRunning` auto-enables Kubernetes only when `isKubeCommand(args[0])` is true. For `rdd run rdd kubectl get nodes`, `args[0]` is `rdd`, so the auto-enable branch is skipped; against a fresh App, Kubernetes never starts and the command fails. The new BATS test uses exactly this `rdd run rdd kubectl` form (`kube-context.bats`), but only after the suite already enabled Kubernetes, so it passes. The heuristic is best-effort and cannot see through `sh -c`, `env`, or `sudo` either.

Fix: also detect the `rdd <kubectl|helm>` alias and cover it in `TestIsKubeCommand`; note the heuristic's limits in the help text.

S3. **Ctrl+C leaks the throwaway kubeconfig and skips cleanup** — `cmd/rdd/run.go:197` [Gemini 3.1 Pro]

```diff
 command.Stderr = os.Stderr
+signal.Ignore(os.Interrupt)
 err := command.Run()
```

`rdd` installs no signal handler, and the child shares its foreground process group, so Ctrl+C delivers SIGINT to both. `rdd` dies on the default disposition before the deferred `os.Remove(kubeconfig)` runs (run.go:75), leaving a 0600 throwaway kubeconfig in `$TMPDIR` until reboot. Ending a long `rdd run kubectl logs -f` or `exec -it` with Ctrl+C is the common case, so these files accumulate. The author already notes signal handling is deferred (run.go:186-188, see Acknowledged Limitations), but that comment covers context cancellation, not the cleanup leak.

Fix: ignore `os.Interrupt` before `command.Run()`. `rdd` then waits for the child, runs its defers, and propagates the child's exit code; the child still receives the signal directly.

S4. **`ensureAppRunning` and `setAction` each build a client and ready the service** — `cmd/rdd/run.go:92,108` [Claude Opus 4.8]

`ensureAppRunning` calls `getAppKubeClient` to read the App (run.go:92), then `setAction` calls `getAppKubeClient` again and re-fetches the App (`set.go:269`). Each `getAppKubeClient` re-runs `ensureServiceRunning`, builds a fresh scheme, and dials a new client (`set.go:612-628`). For a single-user CLI the cost is negligible, but the second read also widens the window in which the App can change between the existence check and the patch (see Design Observations).

Fix: optional. If simplified later, thread the App and client fetched in `ensureAppRunning` into `setAction` so the read and the enablement decision share one snapshot.

## Design Observations

### Concerns

- **`rdd run` reuses the persistent global-context publication path** `(future)` [Codex GPT 5.5] — I3 and S1 share one root: the one-shot command relies on App startup to publish Docker and Kubernetes contexts into the user's global config, then reads back from it. Building ephemeral Docker and kube configs straight from the instance endpoints would make the command's isolation local and testable, and would free it from the health of the user's existing config.
- **TOCTOU between the App existence check and the patch** `(future)` [Claude Opus 4.8] — `ensureAppRunning` decides whether to add `kubernetes.enabled=true` from a `Get` that returns NotFound (run.go:99-103), but `setAction` re-fetches and patches. If another process creates the App without Kubernetes in that window, `setAction` patches `kubernetes.enabled=true` onto the existing App, contradicting the documented "an existing App is only started, never reconfigured." Irrelevant for a single-user CLI today; deciding enablement from one shared read (S4) closes it.
- **Every `rdd run` issues `running=true` and waits for Settled** `(in-scope)` [Claude Opus 4.8] — even `rdd run docker context show` runs the full set-and-wait path. When the App is already settled the patch is a no-op and the wait returns quickly, so the cost is one apiserver round-trip. Acceptable, and it matches the documented "starts first if not already running."

### Strengths

- The code handles the environment-precedence traps correctly: clearing `DOCKER_HOST` lets `DOCKER_CONTEXT` win, and setting `KUBECONFIG` at the environment level overrides `~/.kube/config`. [Claude Opus 4.8, Gemini 3.1 Pro]
- The throwaway kubeconfig is 0600 and copies only the instance context, cluster, and user — not the whole config — so credentials stay protected. [Claude Opus 4.8]
- Missing-`~/.kube/config` and missing-instance-context cases degrade gracefully to a clear "context does not exist" error. [Claude Opus 4.8]
- `writeRunKubeconfig` runs before `setupRunEnv`, so it reads the user's real `KUBECONFIG` rather than the throwaway it installs. [Claude Opus 4.8]
- Relying on the App defaulter for the Kubernetes version, instead of hardcoding `kubernetes.version=stable` as the issue sketched, keeps one source of truth. [Claude Opus 4.8]

## Review Process Notes

**Repo context update [repo]:** A CLI command that documents leaving the user's global Docker or Kubernetes configuration "unchanged" must be checked against the App-startup reconcilers, not only its own code. `manageKubeContext` (`pkg/controllers/app/kubernetes/controllers/kube_reconciler.go`) unconditionally merges the instance context into `~/.kube/config` once k3s is healthy, and the engine reconciler creates the Docker context and sets `currentContext` when the existing one is unhealthy. Any command that triggers an App start — through `rdd set running=true`, `ensureAppRunning`, or `ensureServiceRunning` — inherits these global side effects regardless of its own isolation. Flag isolation claims that ignore the startup path.

**Skill improvement:** When a command loads or parses configuration for one subsystem on a code path shared with commands that do not use that subsystem, a malformed or unreadable config fails the unrelated commands too. Flag an unconditional config load that gates execution of subsystem-agnostic commands, and recommend deferring the load until a command that needs it runs — or tolerating the failure for the commands that do not.

Startup triggers the existing controllers: Docker may write `currentContext` (`pkg/controllers/app/engine/controllers/engine_reconciler.go:397`), and Kubernetes always merges into the user kubeconfig before it may set current-context (`pkg/controllers/app/kubernetes/controllers/kube_reconciler.go:353`, `:401`).

Fix: make `rdd run` use ephemeral Docker/Kubernetes configs, or add an explicit startup mode that suppresses global context publication before waiting for readiness.

I2. **Docker-only commands fail on unrelated kubeconfig errors** — `cmd/rdd/run.go:151-153` (important, regression)

```go
src, err := clientcmd.NewDefaultClientConfigLoadingRules().Load()
if err != nil {
	return "", fmt.Errorf("load kubeconfig: %w", err)
}
```

`runAction` calls `writeRunKubeconfig` unconditionally at `cmd/rdd/run.go:74`, so `rdd run docker ps` fails before running Docker if the user’s kubeconfig is malformed or contains an unreadable referenced file. That makes Docker wiring depend on unrelated Kubernetes client state, even though the child command may never use Kubernetes.

Fix: pass whether the requested command is Kubernetes-facing into kubeconfig setup. For non-kube commands, tolerate source-load failure by writing an empty throwaway config with `CurrentContext` set, or defer kubeconfig creation until it is needed.

I3. **Child failures are not transparent** — `cmd/rdd/run.go:195-198` (important, regression)

```go
err := command.Run()
var exitErr *exec.ExitError
if errors.As(err, &exitErr) {
	return &cliexit.Error{Code: exitErr.ExitCode()}
}
```

The child’s non-zero exit is wrapped in `cliexit.Error` without `Err` at line 198. `main` logs every `cliexit.Error` before exiting (`cmd/rdd/main.go:173-176`), while `Error()` returns an empty string when `Err` is nil (`pkg/cli/exit/exit.go:31-33`), so normal failures like `rdd run false` emit an extra blank rdd error. For signal exits, `ExitCode()` can be `-1`, which is not the shell-compatible `128+signal` status.

Fix: add a silent child-exit path in `main`, or return a typed child-exit error that `main` handles without logging and with explicit signal-status mapping.

S1. **`rdd run --help` is treated as a child command** — `cmd/rdd/run.go:54-56` (suggestion, regression)


Because flag parsing is disabled at line 55, Cobra does not consume `--help` for the `run` command. `rdd run --help` satisfies `MinimumNArgs` at line 54 and then tries to start Rancher Desktop and execute a program literally named `--help`, making the new command’s help discoverable only via `rdd help run`.

### Executive Summary

This PR introduces the `rdd run` command, which allows users to execute commands against the instance's Docker and Kubernetes contexts without modifying their global environment. The implementation is conceptually sound, but it lacks signal handling for SIGINT (which leaks the throwaway kubeconfig on Ctrl+C) and logs an empty error line to the terminal whenever the wrapped command fails.

I1. **`main.go` logs an empty error on child process failure** — `cmd/rdd/run.go:199-200`, `cmd/rdd/main.go:174-177` (important, regression)

```go
	var exitErr *exec.ExitError
	if errors.As(err, &exitErr) {
		return &cliexit.Error{Code: exitErr.ExitCode()}
	}
```

When a wrapped command exits with a non-zero status, `execCommand` returns a `*cliexit.Error` with the correct exit code but leaves the `Err` field `nil`. The global error handler in `cmd/rdd/main.go` unconditionally calls `logrus.Error(err)`. Since the error string is empty, it emits a blank `ERRO[0000]` line after the child process finishes printing its own stderr, breaking `rdd run`'s transparency as a wrapper.

Fix: Update `main.go` to skip logging if the wrapped error is `nil`:
```diff
 		var exitErr *cliexit.Error
 		if errors.As(err, &exitErr) {
-			logrus.Error(err)
+			if exitErr.Err != nil {
+				logrus.Error(err)
+			}
 			os.Exit(exitErr.Code)
 		}
```

I2. **`rdd run --help` tries to execute `--help`** — `cmd/rdd/run.go:61` (important, gap)

```go
	if err := ensureAppRunning(cmd.Context(), args[0]); err != nil {

	}
```

I3. **`isKubeCommand` misses `rdd kubectl` alias** — `cmd/rdd/run.go:111`, `cmd/rdd/run.go:91` (important, gap)

```go
func isKubeCommand(name string) bool {
	base := strings.TrimSuffix(filepath.Base(name), ".exe")
	return base == "kubectl" || base == "helm"
}
```

If a user or the test suite (as in `kube-context.bats:110`) invokes `rdd run rdd kubectl ...`, `args[0]` is `"rdd"`. `isKubeCommand` checks only `args[0]` and returns `false`, failing to append `kubernetes.enabled=true` to `props`. If the `App` is being created, it will start without Kubernetes enabled, and the command will fail to connect.

```diff
-func isKubeCommand(name string) bool {
-	base := strings.TrimSuffix(filepath.Base(name), ".exe")
-	return base == "kubectl" || base == "helm"
+func isKubeCommand(args []string) bool {

+		return false
+	}

+		return true
+	}
```

I4. **`rdd run` does not trap SIGINT, leaking kubeconfig and swallowing exit code** — `cmd/rdd/run.go:197-198` (important, correctness)

```go
	command.Stdout = os.Stdout
	command.Stderr = os.Stderr

	err := command.Run()
```

When the user presses `Ctrl+C` while a command is running, the terminal sends SIGINT to the foreground process group (both `rdd` and the child). By default, the Go runtime terminates the parent `rdd` process immediately. The deferred `os.Remove(kubeconfig)` does not execute, leaking the throwaway kubeconfig file in `/tmp`, and `rdd` exits with status 2 instead of propagating the child's `130` exit code.

Fix: Import `os/signal` and ignore `os.Interrupt` in the parent process before calling `command.Run()`. The child still receives the signal, but `rdd` waits for the child to exit, runs its cleanup defers, and propagates the correct exit code.
```diff
 	command.Stdout = os.Stdout
 	command.Stderr = os.Stderr
 
+	signal.Ignore(os.Interrupt)
 	err := command.Run()
 	var exitErr *exec.ExitError
```
