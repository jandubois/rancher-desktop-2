## Executive Summary

The round-4 delta closes every round-3 Important finding. But both new mechanisms, the deletion finalizer and the `manual` carve-out on `Settled`, reopen the failure mode round 3 identified: a hand-edited dotfile now strands App deletion forever instead of blocking `Settled`, and the carve-out is broad enough that `rdd set --wait` reports success over an unfinished removal.

## Important Issues

I1. **A dotfile with one marker strands App deletion forever** — `rdd/pkg/controllers/app/pathmanagement/controllers/reconciler.go:69` [Claude Opus 5, Codex GPT 5.6 Sol]

```go
		if err := r.apply(ctx, appv1alpha1.AddPathManual, false); err != nil {
			log.Error(err, "Failed to unwind PATH management before App deletion")
			return ctrl.Result{}, err
		}
		controllerutil.RemoveFinalizer(&app, pathManagementFinalizer)
```

The finalizer added for round 3's I3 gates deletion on an unwind that has permanent failure modes. `managedlines.Manage` errors when only one marker survives (`managedlines.go:90`), and `applyPosix` joins every file's error (`pathmanagement_unix.go:160`), so one hand-edited `.zshrc` fails every retry and the App stays `Terminating` with no recovery short of patching the finalizer out by hand. `service.Delete` treats the identical call as best-effort (`service.go:544`); the reconciler does not. BATS `32-app-controllers` runs `rdd ctl delete app` with `--for=delete` waits in five files.

```go repro
func TestProbeA_HandEditedDotfileStrandsDeletion(t *testing.T) {
	home := t.TempDir()
	r := &PathManagementReconciler{BinDir: filepath.Join(home, ".rd2", "bin"), Suffix: "2"}
	// The user deleted the END marker line while tidying their ~/.zshrc.
	assert.NilError(t, os.WriteFile(filepath.Join(home, ".zshrc"),
		[]byte("# mine\n"+r.startMarker()+"\nexport PATH=\"x:$PATH\"\n"), 0o644))
	stuck, err := deleteApp(t, home) // reconciles a terminating App carrying our finalizer
	t.Logf("hand-edited .zshrc: reconcile err = %v", err)
	t.Logf("hand-edited .zshrc: finalizer still present (deletion stuck) = %v", stuck)
}
```

```text repro-output
hand-edited .zshrc: reconcile err = …/.zshrc: exactly one of the delimiter lines is present
hand-edited .zshrc: finalizer still present (deletion stuck) = true
clean .zshrc:       reconcile err = <nil>
clean .zshrc:       finalizer still present (deletion stuck) = false
```

Fix: log the unwind failure and release the finalizer anyway, matching `service.Delete`. Deletion must not depend on a file the user broke.

I2. **`rdd set application.addPath=manual --wait` returns before the removal runs** — `rdd/pkg/controllers/app/app/controllers/app_controller.go:706` [Claude Opus 5]

```go

```

The comment above these lines justifies ignoring a PATH *failure* under `manual`. The guard also skips the `pathCond == nil` and `ObservedGeneration < Generation` arms, so a switch from `front` to `manual` settles while `PathManagementReady` still describes the previous generation, before the reconciler has attempted the removal at all. The user is told the setting took effect while the block is still in their startup files.

```go repro

	front := computeSettledCondition(probeApp(v1alpha1.AddPathFront), in)
	// probeApp: Generation 2, PathManagementReady=Applied stamped at generation 1.
```

```text repro-output

addPath=front,  PATH edit not yet applied: Settled=False reason=PathManagementStale
```

Fix: gate on freshness always, and on `Status` only when the user opted in. Drop `&& pathManaged` from the `if`, and add it to the `pathCond.Status != metav1.ConditionTrue` case. Applied to the tree, this turns the manual/stale case `False`/`PathManagementStale`, leaves the manual/failure case `True` so round 3's I5 stays fixed, and the shipped `app/app/controllers` suite stays green.

I3. **An explicit switch to `manual` hides a removal that permanently failed** — `rdd/pkg/controllers/app/app/controllers/app_controller.go:706` [Codex GPT 5.6 Sol]

```go
	pathManaged := effectiveAddPath(app) != v1alpha1.AddPathManual
	if settled.Status == metav1.ConditionTrue && in.pathManagementEnabled && pathManaged {
```

The same guard conflates two different states: the `manual` default, where the user never asked us to touch anything, and an explicit `front`→`manual` request, which *is* a request to edit files. Round 3's I5 argued the first must not block `Settled`; the fix took both. A user who asks for the block to be removed, and whose removal fails permanently, is told the change succeeded. I2's narrower fix does not reach this case, because it keeps `pathManaged` on the `Status` arm by design.

```go repro
	// Generation 2, PathManagementReady=Failed stamped at the current generation 2.
	failed := computeSettledCondition(probeApp2(v1alpha1.AddPathManual, 2,
		metav1.ConditionFalse, v1alpha1.PathManagementReasonFailed), in)
```

```text repro-output
manual, failure at gen 2 : Settled=True  reason=Settled
front,  failure at gen 2 : Settled=False reason=Failed
```

Fix: distinguishing the two states needs provenance the App does not currently carry. Record the last successfully applied strategy (a status field, or a small state file next to the bin directory) and ignore a `manual` failure only when nothing was ever applied.


Delta item 5 added the `manual` carve-out; this bullet still states the gate is unconditional. Fix: if I2 and I3 are fixed, narrow line 176 to say the gate covers freshness always and failures only under `front`/`back`. If the current behavior is intentional, say so explicitly. Either way, add `PathManagementReady` to the row at line 166.

## Design Observations

### Concerns

- **Empty startup files RD2 created are now permanent** `(in-scope)` [Claude Opus 5]. The round-4 fix for R3-I2 stops deleting a file the user may have owned, which is right. But `applyPosix` also creates `~/.bashrc`, `~/.zshrc`, `~/.cshrc`, and `~/.config/fish/config.fish` unconditionally under `front`/`back`, and `TestApplyPosixManualEmptiesFilesWeCreated` pins all of them surviving as zero-byte files after a switch back to `manual`. `applyPosix` already stats the login files, so it has the information to tell a file it created from one it found. The narrow case that bites: on a home with no login file at all, `applyPosix` creates `~/.bash_profile`, and an empty `~/.bash_profile` shadows a `~/.profile` the user writes later, because bash reads only the first of the three.
- **One unusable shell's dotfile holds `Settled` under `front`/`back`** `(future)` [Claude Opus 5]. `applyPosix` joins errors across every shell it manages, so a root-owned `~/.cshrc` fails the whole apply and `Settled` never reaches `True`. Every later `rdd set --wait`, including `rdd set running=true`, then fails for a reason unrelated to what the user asked. The escape hatch (switch to `manual`) exists but is undiscoverable. Gating on the login-file chain plus `$SHELL`'s rc file, and reporting csh and fish failures on the condition message only, would keep the diagnosis without the blockage.
- **Cleanup obligations are derived from the desired value alone** `(in-scope)` [Codex GPT 5.6 Sol]. The App records what the user wants, never what was last applied, which is why I3 has no cheap fix. A `status.appliedAddPath` would settle I3, tell `Unwind` whether there is anything to unwind, and let the finalizer skip itself when nothing was written.

### Strengths

- The `handled`/`blockInfo` restructuring in `applyPosix` (lines 78 to 107) fixes R3-I6 on both sides: marking the file handled before the write stops the block migrating on a write failure, and breaking rather than continuing on a re-stat failure stops it being written twice. Both are pinned by tests. [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro]
- `setCondition`'s generation threading, with the comment at `reconciler.go:108` explaining why the applied generation rather than the re-`Get`'s is stamped, records a subtle invariant where the next reader will find it. [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]
- `normalizeWindowsPathEntry` with its comment on why `filepath.Clean` is unusable off Windows keeps `computeWindowsPath` testable on the platforms CI actually runs. [Claude Opus 5]

## Review Process Notes

### Skill improvements

- When a round adds a finalizer, a lock, or any other gate that blocks a lifecycle operation until a cleanup succeeds, enumerate the cleanup's permanent failure modes separately from its transient ones. A retry loop converges only on transient failures; a gate placed in front of a cleanup that can fail deterministically converts a recoverable error into an unrecoverable state. Check whether a sibling call site of the same cleanup already treats it as best-effort, and treat the asymmetry as the finding.
- When a fix narrows a gate to exempt a case, check every arm the gate contained, not just the arm the fix was written for. A guard hoisted into the enclosing condition exempts the whole gate, while the rationale in the comment above it usually justifies exempting one arm. Read the comment as a specification and test each arm against it.
- When a fix introduces a position-dependent or index-dependent rule over a list, apply the function to its own output and check it converges in one pass. Indices computed once against the input describe a different list after elements are dropped, so the second-pass result reveals whether "applied" means "finished".

### Repo context updates

- `[repo]` The `--controllers` flag defaults to `*` (`rdd/cmd/rdd/service.go`), which matches every registered controller regardless of the group it reports. A controller returning `""` from `GetAPIGroup()` is following the established convention for controllers that add no CRD of their own, not silently disabling itself; `pkg/controllers/app/kubernetes` has done this since before PATH management existed. Findings that a controller is "silently dropped" because of an empty API group must first check the flag's default and the sibling controllers.
- `[repo]` `rdd/cmd/app-controller/main.go` is a development-only binary that blank-imports a deliberately partial set of app controllers; it already omits `engine` and `kubernetes`. A new app controller's absence from that file is not a defect on its own.
- `[repo]` `managedlines.Manage` returns early when `computeTargetContents` reports no change, and a file with no marker pair produces no change whatever its contents. Any finding about `Manage`'s post-computation guards must first establish that the file has a managed block, or the guard is unreachable.
- `[repo]` The App's `Settled` condition gates on three separate controller conditions, each stamped with `observedGeneration`. A change that exempts one condition from the gate must state whether it exempts staleness, failure, or both: `rdd set --wait` waits on `Settled` plus a generation floor, so exempting staleness makes `--wait` return before the controller has acted, while exempting failure makes it return over a permanent error. The two need separate justification.

## Design Observations

### Concerns

**One unusable shell's dotfile holds `Settled` at `False` under `front`/`back`** `(future)` — `applyPosix` joins errors across every shell it manages (`pathmanagement_unix.go:160`), so a root-owned `~/.cshrc` or a `~/.config` the daemon cannot create fails the whole apply, `PathManagementReady` goes `False`, and — by the deliberate design at `app_controller.go:707` — `Settled` never reaches `True`. Every later `rdd set --wait`, including `rdd set running=true`, then fails for a reason unrelated to what the user asked for. The escape hatch exists (`rdd set application.addPath=manual` clears the gate), but it is undiscoverable. An alternative: gate `Settled` on the shells the user plausibly uses — the login-file chain plus `$SHELL`'s rc file — and report csh/fish failures on the condition message only. The author's comment documents the `manual` half of this tradeoff but not the `front`/`back` half, so I raise it here rather than as a finding.

**Empty startup files RD2 created are now permanent** `(future)` — the round-4 fix for R3-I2 correctly stops deleting a file the user may have owned, but `applyPosix` also *creates* `~/.bashrc`, `~/.zshrc`, `~/.cshrc`, and `~/.config/fish/config.fish` unconditionally under `front`/`back` (`pathmanagement_unix.go:125-158`), and `TestApplyPosixManualEmptiesFilesWeCreated` shows all four surviving as zero-byte files after switching back to `manual`. The information needed to distinguish them exists at write time — `applyPosix` already stats the login files — so passing a "we created this" flag through to `Manage` would let removal delete exactly what RD2 made and empty everything else. Creating `~/.zshrc` in particular has a side effect the `Manage` doc comment itself names: it suppresses zsh's new-user setup wizard.

### Strengths

- The `handled`/`blockInfo` restructuring in `applyPosix` (lines 78-107) is a careful fix: marking the file handled *before* the write, and `break`ing rather than continuing when the re-stat fails, close both ways the block could have migrated to a file bash never sources. `TestApplyPosixFirstLoginFileFailureDoesNotMoveBlock` and `TestApplyPosixSymlinkedLoginFile` pin both.
- `normalizeWindowsPathEntry` (`pathlist.go:85-91`) with the comment explaining why `filepath.Clean` is unusable off Windows is the right call — it keeps `computeWindowsPath` testable on the platforms CI actually runs.
- `setCondition`'s generation-threading, and the comment at `reconciler.go:108-117` explaining why the applied generation rather than the re-`Get`'s is stamped, is a genuinely subtle invariant recorded where the next reader will find it.

```diff
+	}
+	startIdx := slices.Index(trimmed, startMarker)
```
