## Important Issues

I1. **`service.PID()` `serve` discriminator over-matches the shared image path** — `pkg/service/cmd/service.go:182` [Codex GPT 5.5]

```go
if err == nil && !process.IsOurProcess(pid, "serve") {
```

`IsOurProcess` runs `strings.Contains(cmdline, "serve")` (`process_windows.go:83`), and the command line begins with argv[0] — the install path, identical for every rdd process. On a path that contains `serve` (a username like `observer`, a `webserver` directory), the substring matches any rdd CLI process, not just the daemon, so the discriminator silently stops discriminating: `Running()` reports a recycled `rdd ctl` PID as the control plane, and `StopWithWait` then signals it. On a path without `serve` the guard works. This is the Round 4 `service serve`→`serve` fix overshooting — too narrow became too broad (gap, not a regression: merge-base `PID()` had no identity check at all).

Fix: match a parsed argv token, not a raw substring — require `serve` as a standalone word after the image-path check.

I2. **`StopWithWait` can pass `PIDNotFound` (0) to `process.Interrupt`** — `pkg/service/cmd/service.go:464-480` [Codex GPT 5.5]

```go
if !Running() { ... }   // PID() call #1
pid := PID()            // call #2 — not checked for PIDNotFound
if err := process.Interrupt(pid); err != nil {
```

`Running()` calls `PID()`, then line 468 calls it again without rejecting `PIDNotFound`. If the daemon exits, a concurrent stop removes the file, or a transient identity check fails between the two reads, the second `PID()` returns 0. `Interrupt(0)` is `GenerateConsoleCtrlEvent(CTRL_BREAK, 0)` — every process sharing the console — on Windows, and `kill(0, SIGINT)` — the caller's whole group — on Unix. The double-read is pre-existing (identical at merge-base); this PR's new `IsOurProcess` path adds a fresh way for read #2 to return 0. Likelihood is low; the consequence is the exact broadcast hazard the PR targets. Distinct from the Round 2 declined "transient false-negative removes the PID file," which concerned file removal, not signalling 0.

Fix: read `PID()` once, return early on `PIDNotFound`, then signal.

## Suggestions

S1. **PID-guard "clear unless ours" logic duplicated across five sites** — `pkg/controllers/lima/limavm/controllers/limavm_lifecycle.go:210, 547, 618, 679`, `limavm_controller.go:588` [Claude Opus 4.8]

```go
if inst.HostAgentPID > 0 && !process.IsOurProcess(inst.HostAgentPID, "hostagent", hostAgentPIDFile(inst)) {
    inst.HostAgentPID = 0
}
```

The negated "clear the recycled HostAgentPID before taskkill" block, with its ~10-line comment, repeats at five force-stop sites; the sites also differ in whether they copy (`forceInst := *inst`) or mutate in place. Each is correct, but a future change to the discriminator or the zeroing rule must touch all five. A helper consolidates the rule and the comment.

Fix:
```go
func clearRecycledHostAgentPID(inst *limatype.Instance) {
    if inst.HostAgentPID > 0 && !process.IsOurProcess(inst.HostAgentPID, "hostagent", hostAgentPIDFile(inst)) {
        inst.HostAgentPID = 0
    }
}
```

S2. **`cmd.Wait` timeout comment cites an impossible inherited-pipe block** — `pkg/controllers/lima/limavm/controllers/limavm_controller.go:592-595` [Codex GPT 5.5]

```go
// Without a timeout, cmd.Wait can block indefinitely if a child process
// survives KillTree and holds an inherited pipe.
```

The hostagent's stdout/stderr are `*os.File` log handles (`limavm_lifecycle.go:433-434`; `logfile.Create` returns `*os.File`). When stdio is an `*os.File`, `os/exec` passes the fd directly and runs no I/O-copy goroutine, so `cmd.Wait()` cannot block on an inherited pipe — and an inherited regular-file handle never blocks `Wait()` either. The timeout stays a sound defensive bound; only the rationale misleads. The wording is pre-existing, reworded here.

Fix: describe the actual invariant — the wait returns at once when the watcher already reaped the process, and bounds shutdown otherwise.

S3. **`resolveLongPath` could size the buffer in one retry instead of doubling** — `pkg/util/process/process_windows.go:120-130` [Gemini 3.1 Pro]

`GetLongPathName` returns the exact required length when the buffer is too small, so a single resize would suffice; the loop doubles instead. The practical cost is nil — an executable path fits 1024 units on the first call — and the doubling mirrors `processImagePath`, which must double because `QueryFullProcessImageName` does not report its required size. Keeping both helpers on one idiom is a defensible reason to leave this unchanged.

Fix (optional): allocate `n` and retry once; or keep the loop for consistency with `processImagePath`.

## Design Observations

**Concerns**

- **`exec.CommandContext` force-kills the hostagent on manager shutdown, bypassing graceful signalling** `(in-scope)` [Gemini 3.1 Pro] — `startInstance` binds `haCmd` to the manager context (`limavm_lifecycle.go:431`). `waitForShutdown` blocks on that same context's `Done()` and only then runs `shutdownAllHostagents` (`limavm_controller.go:520-522`), so on Windows Go's `exec` has already called `TerminateProcess`: `procExited` closes promptly, the `Interrupt` loop skips the dead PID, and `taskkill /T` cannot reach orphaned children. This is deliberate — commit `ba400557`'s "always reclaim" exists to clean up after the force-kill, and `KillTree` documents the orphaned forwarders as harmless. Gemini's alternative (`exec.Command`, no context) would enable signal-based teardown but loses the guaranteed-cleanup safety net and relies on a console-bound `CTRL_BREAK` a detached service cannot deliver. The current design is defensible; recorded as an observation, not a defect.
- **DriverPID is force-killed without an identity check** `(future)` [Claude Opus 4.8, Codex GPT 5.5] — `IsOurProcess` matches the rdd image, not qemu/wsl, so the restart paths taskkill a stored DriverPID unverified (`limavm_lifecycle.go:201-206`). The PR scopes itself to the HostAgentPID/CTRL_BREAK hazard and names Job Objects, tracking the hostagent+driver tree, as the class fix. On Windows RDD uses WSL2, where DriverPID is typically 0, so the live exposure is small. Worth a tracked follow-up rather than more PID-file patching.
- **`Reconcile`'s sentinel cleanup path removes the directory without unregistering the distro** `(future)` [orchestrator, carried from Round 4] — the sentinel branch (`limavm_controller.go:205`) uses a bare `os.RemoveAll`, unlike the leftover-instance and stale-directory paths that now terminate/unregister. This is pre-existing/PR #392 code, outside PR #383's diff; restated for continuity.

**Strengths**

- The `procExited`-gated skip in `signalHostagent` (`hostagent_watcher.go:213-219`) and `shutdownAllHostagents` (`limavm_controller.go:550-554`) ties "safe to signal" to the OS handle still being held — the real invariant — rather than to on-disk state. `(in-scope)` [Claude Opus 4.8]
- The force-stop paths re-check `HostAgentPID` immediately before each destructive use, so a stored PID is never trusted once time has passed. `(in-scope)` [Codex GPT 5.5]
- `hostAgentPIDFile` is the exact `--pidfile` value passed at launch (`limavm_lifecycle.go:646`), an unambiguous per-instance discriminator that cannot match a sibling whose name is a prefix. `(in-scope)` [Claude Opus 4.8, Codex GPT 5.5]
- `processCommandLine` guards the zero/odd-length case before `&buf[0]`, sizes the read to the buffer rather than to `Length`, and errors on a short read — careful unsafe code backed by a struct-offset regression test. `(in-scope)` [Claude Opus 4.8]
- `removeStaleInstance` now terminates the WSL2 distro before unregistering and drops the redundant GOOS guard, landing the Round 4 design observation. `(in-scope)` [orchestrator]

## Review Process Notes

**Skill improvement — Correctness dimension: a substring identity check against a full command line is defeated by the shared image path.** When code identifies a process by testing whether its command line contains a discriminator substring, remember that the command line begins with argv[0] — the image path — which is identical for every invocation of the same binary. A discriminator that can also appear in the install path (a username, a parent directory, an unrelated subcommand argument) matches every invocation and collapses the check to the image-path test alone. Recognize the pattern as `strings.Contains(commandLine, token)` (or equivalent) used for identity; flag it and recommend matching a parsed argv token, because argv[0] is shared across a binary's invocations.

**[repo] The control-plane daemon has two launch spellings; service-PID identity must accept both.** RDD starts the daemon by self-spawning the canonical `service serve` and also accepts the `svc serve` alias, so an identity check on the service PID must recognize either invocation. Because every rdd process shares the same argv[0] (the install path), a `strings.Contains` discriminator on the full command line can be silently defeated by an install path containing the token. When reviewing changes to `service.PID()` or its discriminator, verify it matches a command token rather than a raw substring, and that it accepts both launch spellings.

### [Gemini 3.1 Pro]

**Executive Summary**

This PR strengthens Windows process handling by adding `process.IsOurProcess`, which walks a target's PEB to confirm it runs our executable and command line. This guards against Windows' aggressive PID recycling, ensuring that graceful shutdown signals and force-stop routines do not hit unrelated processes that reused an old PID. The PR also improves shutdown logic to unconditionally reclaim hostagent resources. The headline finding is a critical gap where `exec.CommandContext` prematurely kills the hostagent during manager shutdown, defeating the newly hardened cleanup.

---

### Critical Issues

**C1. Manager cancellation defeats graceful shutdown and orphans child processes** — `pkg/controllers/lima/limavm/controllers/limavm_lifecycle.go:431` (critical, gap)

```go
	haCmd := exec.CommandContext(ctx, rddPath, args...)
```

Because `ctx` is tied to the manager context, stopping the service cancels `ctx` and causes Go's `exec` to immediately kill the hostagent via `Process.Kill()` (which calls `TerminateProcess` on Windows). This preempts the graceful shutdown sequence in `shutdownAllHostagents`: the hostagent dies before it can receive `process.Interrupt` or perform its own teardown.

Furthermore, because the parent hostagent is already dead when `shutdownAllHostagents` runs, `process.KillTree` (`taskkill /T`) fails with exit code 128 and cannot traverse the process tree. This permanently orphans any child processes (like SSH port forwarders) spawned by the hostagent on Windows.

Fix: Use `exec.Command` without a context so the hostagent's lifecycle is managed entirely by `shutdownAllHostagents`. This ensures `process.Interrupt` and `KillTree` operate on a live process tree.

```diff
-	haCmd := exec.CommandContext(ctx, rddPath, args...)
+	haCmd := exec.Command(rddPath, args...)
```

None.

### Suggestions

**S1. Inefficient buffer resizing loop** — `pkg/util/process/process_windows.go:120-130` (suggestion, enhancement)

```go

		buf := make([]uint16, bufSize)
		n, err := windows.GetLongPathName(p16, &buf[0], bufSize)
```

`GetLongPathName` returns the exact required buffer size (including the null terminator) when the provided buffer is too small (`n >= bufSize`). The current implementation doubles the buffer in a loop, which performs unnecessary intermediate allocations and API calls for deeply nested paths.

```diff
-		}

-		}
-		// n >= bufSize: the buffer was too small and n is the required size; grow.
-	}
-	return "", windows.ERROR_INSUFFICIENT_BUFFER
```
