// processImagePath returns the full path to the executable backing the process.
func processImagePath(handle windows.Handle) (string, error) {
	buf := make([]uint16, 1024)
	size := uint32(len(buf))
	if err := windows.QueryFullProcessImageName(handle, 0, &buf[0], &size); err != nil {
		return "", err
	}
	return windows.UTF16ToString(buf[:size]), nil
}

// processCommandLine reads the target process's command line out of its PEB.

Design Observations ¶

Concerns ¶

  • A handle-pinned helper would close the residual races (in-scope) Codex Gemini — IsOurProcess verifies identity, then closes the handle before the caller signals or kills by PID, leaving a check-to-signal window. A Windows-only InterruptIfOurProcess / KillTreeIfOurProcess that holds the handle across the PID operation would close both that window and the procExited brief window (Round 1 S2) at once. Gemini rated the window Critical (C1); it is practically unhittable — the just-verified live hostagent would have to exit and have its PID reassigned within microseconds — so it does not gate the merge.
  • Force paths still trust persisted DriverPID (future) Gemini Claude — the structural root of S2. stopInstanceForcibly taskkills DriverPID from on-disk state, which IsOurProcess cannot verify (the driver is qemu/wsl, not rdd). A Job-Object or supervisor model would remove PID-based signalling of unrelated processes entirely. Out of scope for this fix.
  • Image-path equality assumes a stable binary location across restarts (future) Claude — IsOurProcess compares the target's image to os.Executable(). A service restart running rdd from a moved or upgraded path rejects a genuinely-ours hostagent, so killOrphanedHostagent skips both signal and taskkill and relies on DriverPID alone. Self-healing on the next reconcile and implausible pre-release, but unstated.
  • Unix no-op leaves a cross-reboot residual (future) Gemini — HostAgentPID read from on-disk state can outlive a reboot and resolve to a recycled live process, which the Unix no-op signals. Lima's ReadPIDFile auto-cleans dead PIDs on Unix (so HostAgentPID reads 0 for a dead process) and SIGINT carries a smaller blast radius than CTRL_BREAK, which is why Round 1 logged this as a doc note. Gemini re-escalated it to Critical (C3); the code is unchanged since.

Strengths ¶

  • The handle-vs-PID split is the right model: rely on the held os.Process handle for in-memory paths, IsOurProcess only for on-disk PIDs from a prior service. Verified against Go os/exec_windows.go — handle release precedes the watcher's close(procExited), matching the documented "brief window." Claude Codex
  • The PEB walk is correct against x/sys@v0.43.0: NTUnicodeString.Length is bytes, so length/2 code units and the full-read check are right. Claude Gemini
  • IsOurProcess fails closed — every uncertain path returns false, and callers treat false as "fall back to forced stop." Codex

Repo context updates ¶

  • [repo] The lima controller sets the hostagent's stdout/stderr to *os.File handles from logfile.Create (pkg/util/logfile, which returns *os.File), not pipes. Go's os/exec passes those descriptors to the child directly and spawns no I/O-copy goroutine, so cmd.Wait() returns promptly once the process is reaped and the watcher closes procExited immediately after. Reject claims that cmd.Wait() blocks indefinitely on inherited pipes for these processes, or that procExited lags handle release by an exploitable margin — the residual window is a few instructions, not unbounded. (This entry was recommended after Round 1 of PR #377 and never applied; its absence caused the same false positive to recur in Round 2.)
