clientOnlySubcommands omits kuberc, so kuberc view and kuberc set probe the cluster like any cluster-bound command. Against a server at 1.34 or older, the resolver then runs a cached kubectl of the server's minor or the next one, or downloads one of the server's minor, and kubectl releases before 1.36 do not have a kuberc command (part 2 of the probe). So a command that only reads or edits the user's kuberc file reaches a kubectl that does not know it, or fails on a download error first. At the merge-base, the embedded kubectl ran it, and cmd_other.md still promises that client-only commands run the embedded kubectl.

Suggestions ¶

S1. Plugin arguments are read as kubectl connection flags Claude Opus 5.5 Codex GPT 6 Astra¶
rdd/docs/design/cmd_other.md

1. The embedded kubectl.
2. The highest version in the download cache (`rdd svc paths kubectl_cache`).
3. A fresh download of the latest patch release of the server's minor version, looked up via the mirror's `stable-<major>.<minor>.txt` marker (e.g. `stable-1.34.txt` → `v1.34.9`), sha512-verified, and stored in the cache.

The probe parses the command line through kubectl's own command tree, so it contacts the cluster that kubectl will contact and applies the user's kuberc, both its defaults and its credential plugin policy. A separate flag parser in rdd would get attached shorthand values such as `-ojson` wrong and would not see kuberc. In exchange, `rdd kubectl` stops on a kuberc that the embedded kubectl rejects, even when the kubectl it would run is older and ignores kuberc.

When the cluster is unreachable, and for client-only commands (`kubectl config`, `completion`, ...), the embedded kubectl runs. It is also the final fallback when nothing acceptable is cached and the version marker cannot be fetched within 5 seconds (offline, or a pre-GA minor with no marker yet): rdd warns and runs it anyway, since rdd embeds a recent kubectl and Kubernetes rarely breaks backward compatibility. Once the marker has named a version, a failed or corrupted download aborts the command rather than hiding the problem. [rdd ctl](cmd_service.md#rdd-ctl) skips the probe entirely: the embedded apiserver always matches the embedded kubectl.

`RDD_KUBECTL_MIRROR` overrides the release mirror (default `https://dl.k8s.io`) and `RDD_CACHE_DIR` the cache root; see [environment.md](environment.md).

For a kubectl plugin, parseCommandLine parses the plugin's own arguments with the root command's flags (resolver.go:213-218), so a plugin flag that matches a kubectl flag sets the probe's target. For example, myplugin -ojson sets the server to on. kubectl itself does not contact a cluster for a plugin; the plugin decides. The probe then usually fails and the embedded kubectl runs, as at the merge-base, so the harm is small. But this sentence and the commit message promise "the cluster that kubectl will contact", and the parseCommandLine comment does not mention plugin arguments.

Design Observations ¶

Concerns ¶

  • A cluster-bound completion can download a kubectl out of sight (in-scope) Claude Opus 5.5 — With I2's patch, kubectl get pods <TAB> still probes, which is right, because the matching kubectl completes it. But against a skewed cluster with an empty cache, that TAB starts the 50 MB download, and cobra's bash and zsh scripts discard its stderr (2>/dev/null), so the shell hangs with no notice for as long as the download takes. Completion could use only the cache, and fall back to the embedded kubectl on a miss.
  • A credential plugin that calls kubectl runs once more per call (future) Claude Opus 5.5 — This round stopped passing the recursion guard to the cached kubectl's children, as round 2 asked. So when the cached kubectl runs a kubelogin plugin (kubectl oidc-login get-token), that call re-enters rdd kubectl, finds oidc-login unknown, probes, and runs the plugin a third time. Review Process Notes ¶

Skill improvements ¶

  • When code keeps a hand-written list that classifies another component's commands, types or events, enumerate that component's full set at the pinned version and check each member against the list. When the list decides which version of the component handles a member, also check that every version it can route to has that member.
  • When code drives a framework's parser or dispatcher without running it (building a command tree and calling find or parse, but never execute), list what the framework adds only on its execute path, such as completion requests, help commands and alias rewriting, and check how the code treats each.
