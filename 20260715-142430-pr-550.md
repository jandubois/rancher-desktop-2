## Executive Summary

PR #550 moves k3s-version parsing into a shared package, adds a reconciler that force-creates a `k3s-versions` ConfigMap plus a webhook blocking its deletion, and switches webhooks to name-based custom paths so two ConfigMap validators no longer collide. Core mechanics are correct and verified — build and tests are green, and the collision fix holds. The main gaps: a stray `_ "embed"` import papered over with a repo-wide lint exclusion, and no coverage for the new webhook and trigger.

All three reviewers agree the change is sound and low-risk; findings cluster around lint hygiene, test coverage, and documentation drift. Gemini raised two Important lifecycle concerns — creation timing and the deletion-blocking webhook — that Codex and Claude did not. Verification against the code downgrades both: the backend defaulter/validator use the embedded data directly (not the ConfigMap), and nothing in rdd deletes the `rdd-system` namespace, so the deletion guard's whole point is intentional immortality rather than a lifecycle trap.

## Design Observations

### Concerns

- **The `k3s-versions` ConfigMap is intentionally immortal** `(future)` [Gemini 3.1 Pro, Claude Opus 4.8] — nothing ever deletes it: the embedded control plane has no garbage collector, no reconciler cleans it up, and the webhook rejects every delete (`failurePolicy` defaults to `Fail`). This is acceptable given the single-user embedded API server and the pre-stable project stage, but a comment near the validator would tell a future maintainer the ConfigMap is deliberately permanent. Gemini proposed removing the validator to restore standard namespace cleanup; that is rejected here — nothing in rdd deletes the `rdd-system` namespace, and blocking deletion is the feature's stated intent.

### Strengths

- **The custom webhook-path change fixes a real collision, not a theoretical one** `(in-scope)` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro] — lima's `limavm-configmap-validator` and the new `k3s-versions-validator` both mapped to controller-runtime's default `/validate--v1-configmap`, so the second silently dropped. Name-based paths give each a distinct route, and the change is verified safe when only a validator or only a defaulter is present (the absent side's custom-path call is a no-op).
- **Sharing the parsed `K3sVersions` struct keeps admission off the control plane** `(in-scope)` [Codex GPT 5.5, Claude Opus 4.8] — the defaulter and validator reuse the embedded data directly instead of reading the ConfigMap back through the API server.
- **The reconciler self-heals deterministically** `(in-scope)` [Claude Opus 4.8] — it `For`-watches the ConfigMap it manages and marshals sorted `map[string]string` values, so applies converge and the ConfigMap is restored if deleted out-of-band.

## Review Process Notes

### Skill improvements

- When a change adds a linter exclusion, a suppression rule, or an inline `//nolint`-style comment, treat it as a claim to verify rather than a fact to accept: confirm the flagged code cannot simply be fixed, and check the exclusion's scope. A file-wide or repo-wide exclusion added to silence a single occurrence masks every future instance of that class and permanently weakens the linter — flag it and prefer the narrower fix (usually deleting the offending line). Because a suppression hides the very issue review exists to catch, the burden is on the change to justify keeping it.

### Repo context updates

- [repo] All admission webhooks register custom paths of the form `/{validating|mutating}-<config-name>` via `base.GenerateWebhookPath`, not controller-runtime's default GVK-derived path. Multiple webhooks on the same resource type (several ConfigMap validators, for example) coexist only because their config names differ; a duplicate config name recollides on one path and silently drops a handler. When reviewing a new webhook, verify its config name is unique across the shared webhook server.
- [repo] The supported-k3s-versions data ships as a plain core `ConfigMap` named `k3s-versions` in the `rdd-system` namespace (labels `app.kubernetes.io/name=rdd-k3s-versions`), created by the `k3sversions` controller and guarded against deletion by a validating webhook. It is intentionally never garbage-collected. The design doc `docs/design/api_k3sversion.md` describes an older, unimplemented CRD-based design — do not treat it as the contract.

### [Gemini] — Gemini 3.1 Pro (effort: default)

### Executive Summary

This PR creates a `k3s-versions` ConfigMap in the `rdd-system` namespace to expose supported Kubernetes versions and channels to the frontend, and refactors webhook path generation to prevent route collisions. The changes correctly embed and parse the versions payload, but the reconciler only creates the ConfigMap upon `App` creation, creating a catch-22 for the frontend UI which requires this data prior to configuration. Additionally, a new validating webhook unconditionally blocks deletion of the ConfigMap, which creates a lifecycle trap if the parent namespace is ever deleted.

### Findings

#### Critical Issues

None.

#### Important Issues

I1. **ConfigMap creation depends on App existence, creating a catch-22 for UI** — `rdd/pkg/controllers/app/k3sversions/controllers/k3s_versions_reconciler.go:94-104`

```go
		Watches(&v1alpha1.App{},
			// Enqueue a reconcile request for the relevant config map on app change...
			handler.EnqueueRequestsFromMapFunc(func(context.Context, client.Object) []reconcile.Request {
				return []reconcile.Request{{
					NamespacedName: client.ObjectKey{
						Namespace: controllers.RDDSystemNamespace,
						Name:      k3sVersionsConfigMapName,
					},
				}}
			}),
```

The reconciler only enqueues a request to create the `k3s-versions` ConfigMap when an `App` is created or when a matching `ConfigMap` already exists and triggers an event. On a fresh install, neither exists, so the ConfigMap is never created until the first `App` is created. However, the UI uses this ConfigMap to populate the dropdown of supported Kubernetes versions *before* the user can configure and create their first `App`. This creates a chicken-and-egg problem where the frontend will receive a 404 Not Found when trying to present version options.

**Fix:** Enqueue a reconcile request unconditionally when the controller starts. Watching the `rdd-system` Namespace (which is guaranteed to exist early) ensures the ConfigMap is populated before any `App` is created:

```go
		Watches(&v1.Namespace{},
			handler.EnqueueRequestsFromMapFunc(func(ctx context.Context, o client.Object) []reconcile.Request {
				if o.GetName() == controllers.RDDSystemNamespace {
					return []reconcile.Request{{
						NamespacedName: client.ObjectKey{
							Namespace: controllers.RDDSystemNamespace,
							Name:      k3sVersionsConfigMapName,
						},
					}}
				}
				return nil
			}),
		).
```

(important, gap)

I2. **ValidatingWebhook unconditionally blocks ConfigMap deletion, breaking namespace cleanup** — `rdd/pkg/controllers/app/k3sversions/controllers/k3s_versions_validator.go:39-46`

```go
	// We reject all deletes.
	return nil, apierrors.NewForbidden(
		v1.SchemeGroupVersion.WithResource("ConfigMap").GroupResource(),
		obj.Name,
		fmt.Errorf("refusing to delete %T %s/%s", obj, obj.GetNamespace(), obj.GetName()),
	)
```

The `K3sVersionsValidator` unconditionally rejects any deletion of the `k3s-versions` ConfigMap. While this prevents accidental manual deletion, it creates a lifecycle trap for its parent namespace (`rdd-system`). If the namespace is ever deleted (e.g., during environment cleanup or reset), the namespace controller will attempt to delete this ConfigMap and get permanently blocked, leaving the namespace stuck in `Terminating`. Since the `K3sVersionsReconciler` automatically recreates the ConfigMap if it goes missing, preventing its deletion is both unnecessary and actively harmful to standard Kubernetes garbage collection.

**Fix:** Remove the `K3sVersionsValidator` entirely. Rely on the `K3sVersionsReconciler` to restore the ConfigMap if it is deleted, which is the standard, self-healing Kubernetes pattern.
