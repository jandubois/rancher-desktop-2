## Important Issues

I1. **The `cns-` hashed namespace lookup can never resolve, so those namespaces are permanently un-admittable** — `rdd/pkg/controllers/containers/compose/compose_webhooks.go:45-48` [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]

```go
		namespaceName := request.Spec.Namespace
		if len(validation.IsDNS1123Subdomain(namespaceName)) > 0 {
			namespaceName = fmt.Sprintf("cns-%x", sha256.Sum256([]byte(namespaceName)))
		}
```

`api_containers.md:141-144` promises that name, but nothing writes it. The
engine's `applyNamespace` *skips* the mirror for a non-DNS1123 namespace
(`sync_namespace_containerd.go:77-84`) rather than hashing it. A repo-wide grep
for `cns-` returns exactly two hits: the doc line and this one.

containerd accepts identifiers such as `my_project_ns` and `BuildKit` that are
not valid object names, so a `ComposeUpRequest` in one is rejected forever.
Round 1 raised the documentation half as I5; this round made the validator
depend on it.

I2. **The validator reads through the cached client; the sibling webhook uses an uncached reader** — `rdd/pkg/controllers/containers/compose/compose_controller.go:81-82` [Claude Opus 5]

```go
		Validator: &composeUpRequestValidator{
			Client: mgr.GetClient(),
		},
```

`imagePullRequestValidator` takes `reader: mgr.GetAPIReader()` for the same
lookup (`image_controller.go:89`). The difference is not cosmetic.
controller-runtime v0.24.1 starts `runnables.Webhooks` before
`runnables.Caches` (`pkg/manager/internal.go:436-448`), and a cached read before
the cache starts returns `ErrCacheNotStarted`, not `NotFound`
(`pkg/cache/informer_cache.go:73-75`). That error goes to the `else if err != nil`
arm at `compose_webhooks.go:56-58`, so the client gets an internal error rather
than the intended rejection. `SharedControllerManager.Start` exposes the window:
it marks the control plane ready once the webhook server answers, which is
before cache sync. Past startup, the cached read also lags a freshly applied
mirror by a watch round trip.

`os.Root` refuses any path leaving the root, so `../compose.base.yml`, an
absolute path, and a symlink pointing outside are all rejected. All three are
legal `docker compose -f` arguments, and a shared base file one directory up is
an ordinary monorepo layout. `api_containers.md:768-770` says only "Relative to
`spec.workingDir`" — nothing forbids `..`, so the validator is stricter than the
contract it enforces. Every client here is admin-equivalent on a single-user
desktop and can run `docker compose` directly, so the confinement adds no
security; round 1 dismissed a path-traversal framing on those same grounds.

## Suggestions

S1. **The validator's own comments say the fields it now checks need no validation** — `rdd/pkg/controllers/containers/compose/compose_webhooks.go:31-34` [Codex GPT 5.6 Sol, Claude Opus 5]

```go
// spec.namespace and spec.name are immutable, enforced via CEL.  The other
// parts of the spec are mutable, and do not require validation.
type composeUpRequestValidator struct {
	client.Client
```

The other parts of the spec are `workingDir` and `configs`, and this round added
`validateSpec` to check exactly those from both `ValidateCreate` and
`ValidateUpdate`. The same file then calls that function "checks the mutable
fields of the ComposeUpRequest spec", so the two comments contradict each other.
The type comment above also still describes the validator as enforcing only the
`metadata.name` invariant, now one of five checks, and
`setupWebhookWithRuntimeConfig`'s comment (`compose_controller.go:73-74`) says
the webhook enforces naming "on ComposeUpRequest create".

Fix: describe all five checks, say that updates revalidate `workingDir` and
`configs`, and drop the "do not require validation" clause.

S2. **`ValidateUpdate` re-checks host filesystem state and discards the old object** — `rdd/pkg/controllers/containers/compose/compose_webhooks.go:79-83` [Claude Opus 5]

```go

	// spec.namespace and spec.name are enforced via CEL; we only need to validate
```

An update that touches neither `workingDir` nor `configs` is still rejected once
the project directory is deleted or unmounted. Nothing updates a
`ComposeUpRequest` today, so this is latent — but finalizer removal is an UPDATE
on the main resource, so a reconciler adding a finalizer would wedge the object
in `Terminating` whenever the directory has gone. The comment also claims only
`workingDir` is checked, while `configs` is checked too.

Fix: run `validateSpec` only when the fields it inspects changed.

## Design Observations

### Concerns

- **Admission is coupled to transient observed state** (in-scope) [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]. `ContainerNamespace` mirrors exist only while the engine watcher is connected — `cleanupMirrorResources` deletes every one of them on stop (`watch_reconciler.go:463`). During VM boot and after every engine stop, a request for the ordinary namespace `moby` is denied with `namespace "moby" does not exist`. Round 1 credited the absence of this check as a strength for exactly that reason; this round reverses it. Keeping admission syntactic and reporting engine state through `Settled`/`Failed` would avoid the boot window; I1's patch at least stops the message blaming the user's input.
- **The `metadata.name` derivation is a client-side contract with no shareable implementation** (future) [Claude Opus 5]. `composeMirrorName` is unexported, yet `api_containers.md:666-673` requires every client to compute the same name before creating either object. The CLI, the renderer and the future reconciler must each reimplement "join with a dot, else `cmp-` plus SHA-256", and the webhook is the only thing that will tell them they got it wrong.
- **Admission is a weak layer for host filesystem validation** (future) [Claude Opus 5]. `validateSpec` proves the paths existed at admission time; the reconciler must re-check anyway, since the directory can vanish before `docker compose up` runs. The webhook's I/O gains an earlier error at the cost of coupling object mutability to host state (S2) and blocking admission on I/O — `validateSpec` also ignores its `context.Context`, so a hung network mount cannot be cancelled.
- **Pre-existing: `api_containers.md` describes a `ContainerNamespace` the code does not implement** (future) [Claude Opus 5, Codex GPT 5.6 Sol]. The doc shows `status.name` and `status.labels`, but the type declares no status at all, and the `cns-` name is never produced. This predates the PR; I1 is what makes the second half break requests.

### Strengths

- **Reusing `compose-go` for project-name validation** (in-scope) [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.5 Flash]. `loader.NormalizeProjectName` and `loader.InvalidProjectNameErr` mean the API accepts what `docker compose -p` accepts, error text included, and it tracks upstream.
- **The name gate closes round 1's collision concern** (in-scope). `NormalizeProjectName`'s `[a-z0-9_-]` class strips dots, so `spec.name` can never contain one. Since only the namespace may hold dots, `namespace + "." + name` splits unambiguously at the last dot and two distinct pairs cannot collide.
- **`mgrCtx` above the registration loop covers paths the in-tree alternative does not** (in-scope) [Claude Opus 5, Codex GPT 5.6 Sol]. The engine's `manager.RunnableFunc` hook only fires once `mgr.Start` reaches its runnable phase, so a webhook-setup failure — which returns before `mgr.Start` is called — would leave that context uncancelled, while `defer mgrCancel()` always fires.
- **`errors.Join` aggregation** (in-scope) [Claude Opus 5]. Reports every problem in one admission response instead of one round trip per mistake.
- **Condition and reason strings are exported constants in the API package** (in-scope) [Claude Opus 5], unlike the sibling, which hides them in its reconciler package where a cross-package comparison cannot reach them.

## Review Process Notes

**Skill improvements**

- When a round adds a lookup, guard, or existence check against another
  component's state, locate the code that produces that state and confirm it
  produces the exact key being looked up. A check written from a design document
  and a check written from the producing code look identical in a diff, and only
  the second one can succeed.
- When a prior round recorded the absence of a check as a strength, and the
  current round adds that check, re-read the reasoning behind the original credit
  before accepting the addition. A strength removed is as reportable as a defect
  added, and nothing else in the process re-examines a previous round's praise.
- Treat an agent's report of a test run as a claim to verify against its session
  log before repeating it anywhere in the report, including the delta verdicts
  and the testing assessment. Counting the agent's executed commands is cheap,
  and an invented run otherwise enters the record as corroboration for whatever
  it was asserted to support.
- When two agents split on whether one construct is a strength or a defect,
  resolve it by running the construct instead of weighing the arguments. A
  confinement API, a sanitiser, or a normalisation call has behaviour that a
  ten-line probe settles, and the agent praising it has usually not executed it.

**Repo context updates**

- [repo] The engine mirrors a containerd namespace as a `ContainerNamespace`
  object only when the namespace name is itself a valid DNS1123 subdomain;
  `applyNamespace` skips the rest and `syncNamespaces` omits them from its active
  set, so no hashed `cns-`-prefixed object is ever created despite what the design
  document states. containerd accepts uppercase and underscores, which K8s object
  names do not, so any code resolving a container namespace to its mirror must
  handle the no-mirror case rather than deriving a name.
- [repo] `ContainerNamespace`, `Container`, `Volume` and `Image` mirrors exist
  only while the engine watcher is connected; `cleanupMirrorResources` deletes
  every one of them when the engine stops or changes. Flag admission logic that
  requires a mirror to exist: it rejects valid requests for the whole boot window
  and after every engine restart. The `ImagePullRequest` webhook documents this
  trade-off in a comment at its namespace lookup.
- [repo] Admission webhooks in this tree take `mgr.GetAPIReader()`, not
  `mgr.GetClient()`. controller-runtime starts webhook runnables before caches, so
  a cached read during the startup window returns `ErrCacheNotStarted` instead of
  `NotFound`, which turns an intended rejection into an internal error; a cached
  read also lags a freshly applied object by a watch round trip.

### Design Observations

**Concerns**

- **The `metadata.name` derivation is a client-side contract with no shareable implementation** `(in-scope)`. `composeMirrorName` (`compose_utils.go:23-29`) is unexported in the controller package, yet `api_containers.md:666-673` requires every *client* to compute the same name before creating either object. The future `rdd` CLI, the renderer, and the compose reconciler must each reimplement "join with a dot, else `cmp-` plus SHA‑256", and the webhook is the only thing that will tell them they got it wrong. Exporting it from `pkg/apis/containers/v1alpha1` (beside the `Kind` constants already there) gives the Go producers one copy and leaves only the TypeScript side to mirror; that is the split the repo context describes as producer/consumer grammar drift.

- **Admission is a weak layer for host filesystem validation** `(future)`. `validateSpec` proves `workingDir` and each config existed at admission time. The reconciler must re-check anyway — the directory can vanish between admission and `docker compose up` — so the webhook's filesystem work buys an earlier error message at the cost of coupling object mutability to host state (S2) and of blocking the admission path on I/O (S3). Worth deciding now whether the reconciler reporting `Settled=True, Failed=True, Reason=...` is the better channel for these errors.

- **Pre-existing: `api_containers.md` describes a `ContainerNamespace` the code does not implement.** The doc shows `status.name` and `status.labels` (lines 128‑148), but `rdd/pkg/apis/containers/v1alpha1/container_namespace_types.go:20-27` declares no status at all, and the `cns-` hashed name in the doc is never produced (I2). This predates the PR — `git merge-base --is-ancestor e2b85ab89 42694a85b` confirms the doc commit is upstream — but I2 shows the drift is now load-bearing.

- **Pre-existing: `imagePullRequestValidator`'s comment does not match its own code.** `image_pull_request_webhooks.go:51-53` says "We do not need to worry about already existing image pull requests; if it is already known to be valid, we don't care if the engine is not ready yet", yet `ValidateUpdate` (line 39) calls `validate`, which re-runs the `ContainerNamespace` lookup. **Strengths**

- Putting the condition and reason strings in the API package as exported constants (`compose_types.go:18-65`) is better than the sibling, which hides them in the reconciler package where a cross-package `Reason ==` comparison cannot reach them.
- Reusing `loader.NormalizeProjectName` and `loader.InvalidProjectNameErr` rather than hand-rolling a regex means the API accepts exactly what `docker compose -p` accepts, including the error text, and it tracks upstream automatically.
- `mgrCtx` above the registration loop covers early-exit paths the engine's `manager.RunnableFunc` pattern does not: that hook only fires once `mgr.Start` reaches its runnable phase, so a webhook-setup failure (`manager.go:264`, before `mgr.Start` is ever called) or a cache-sync failure leaves `watcherCtx` uncancelled, while `defer mgrCancel()` always fires.

#### Findings

##### Critical Issues

C1. **Validator's `ContainerNamespace` existence check causes permanent rejections and boot-window failures** — `rdd/pkg/controllers/containers/compose/compose_webhooks.go:42-50` (critical, regression)

```go

			Namespace: request.ObjectMeta.Namespace,
			Name:      namespaceName,
		}, &namespace)

			errs = append(errs, fmt.Errorf("namespace %q does not exist", request.Spec.Namespace))
```

Requiring the `ContainerNamespace` mirror to exist creates two severe failure modes:
1. **Boot window rejections**: The engine controller drops all mirror resources during VM boot or engine switch. Requiring the mirror to exist turns this window into a client-facing failure for user requests.
2. **Permanent rejections for non-DNS1123 namespaces**: The engine watcher intentionally skips creating `ContainerNamespace` mirrors for containerd namespaces that aren't valid DNS-1123 subdomains (e.g. ones with underscores) (`sync_namespace_containerd.go:82`). Fix: Remove the `v.Get` check for the mirror object. Validating the namespace string directly with `identifiers.Validate(request.Spec.Namespace)` is sufficient.

##### Important Issues

I1. **`os.OpenRoot` rejects absolute paths and legitimate `../` relative paths in `Configs`** — `rdd/pkg/controllers/containers/compose/compose_webhooks.go:90-95` (important, regression)
