Executive Summary ¶

The branch adds a macOS Cluster API infrastructure provider to rdd. For each LimaMachine that Rancher's Cluster API creates in the App's k3s cluster, rdd boots a node VM from the App's own distro image. The design holds up, and it keeps the registration token out of conditions and errors. One Important defect remains. When rdd's webhooks reject one LimaMachine's LimaVM, every pass aborts there, and the LimaMachines listed after it never get node VMs.

// validateLimaVMUniqueName validates that the LimaVM name is unique across all namespaces.
// This is critical because LimaVM names correspond to actual VM instances on the host system,
// which must be unique.
func validateLimaVMUniqueName(ctx context.Context, c client.Client, limavm *v1alpha1.LimaVM) error {
	// List all LimaVMs across all namespaces
	limavmList := &v1alpha1.LimaVMList{}
	if err := c.List(ctx, limavmList, &client.ListOptions{}); err != nil {
		return fmt.Errorf("failed to list LimaVMs for uniqueness check: %w", err)
	}

	// Check for name conflicts across all namespaces
	for _, existingVM := range limavmList.Items {
		// Skip if it's the same resource (UPDATE operation)
		if existingVM.UID == limavm.UID {
			continue
		}

		// Check if another instance with the same name exists
		if existingVM.Name == limavm.Name {
			return fmt.Errorf("LimaVM name %q is already used in namespace %q; LimaVM names must be unique across all namespaces",
				limavm.Name, existingVM.Namespace)
		}
	}

	return nil
}

### Deletion and garbage collection

RDD adds the finalizer `capi.rancherdesktop.io/limamachine` to a `LimaMachine` once its owner `Machine` exists. When the `LimaMachine` is deleted, RDD deletes its `ConfigMap` and `LimaVM`, waits while the `LimaVM` controller stops the VM and deletes its disk, and then removes the finalizer. CAPI in turn waits for the `LimaMachine` to disappear before it deletes the `Machine`.

Every pass also removes the node `LimaVM` and `ConfigMap` objects that belong to another guest cluster or to a `LimaMachine` that no longer exists. Resetting the App's k3s cluster leaves the objects of the old guest cluster behind, and removing a `LimaMachine`'s finalizer by hand leaves the objects of that `LimaMachine`. The `ConfigMap` objects hold registration tokens, so RDD removes them along with the VMs.

## The registration token

Rancher's bootstrap data includes the token that the node's system agent registers with. The provider's errors and conditions never quote it, and its log lines quote it only in the case at the end of this section. Its errors about the bootstrap data name the field and what it expected, and it drops YAML parse errors, which can quote their input.

The path is latent today. The App controller never recreates the App VM, and the Troubleshooting page's Reset Kubernetes and Factory Reset buttons send k8s-reset and factory-reset, but the main process doesn't handle either message. Deleting the App removes node VMs through DeleteOwnedResources. Once Reset Kubernetes reaches rdd, this becomes Important.

Fix: read the kube-system UID before the Cluster API check and remove node objects labelled with another guest UID there. Keep the cleanup of missing LimaMachines behind a successful LimaMachine list.

Outcome: fixed in 850f9b85e as the Fix proposes. Step c of TestReconcile covers a changed UID with Cluster API absent.

### Readiness

RDD probes a node VM over SSH once its `LimaVM` reports `Running`, and again after every restart. The probe reads the IPv4 address of `lima0`, the vzNAT interface, and checks for the guard's marker. Lima reports a VM as running only after its boot scripts finish. Lima's only sign of a failed boot script is its `Degraded` status, and the `LimaVM` doesn't show that status. So RDD learns from the marker whether the install script succeeded.

Once the probe finds both the address and the marker, RDD sets the `LimaMachine`'s `spec.providerID` to `k3s://lima-<name>`, the ID that k3s gives the `Node`, and puts the `lima0` address and the hostname in `status.addresses`. It then sets `status.initialization.provisioned` and marks the `LimaMachine` ready. RDD never unsets `provisioned`. Without the marker, the `Ready` reason is `BootstrapFailed`, and the install script runs again at the next boot.

The `Ready` condition's reason tells how far a `LimaMachine` has got.

Acknowledged Limitations ¶

  • The provider ignores a paused cluster and the cluster.x-k8s.io/managed-by label (capi-provider.md:188), as ruled.
  • A CRD deleted by hand comes back only after rdd restarts or k3s.yaml changes (capi-provider.md:93).
  • A failed install runs again only at the next boot, and the first boot needs the openSUSE package repositories (capi-provider.md:118-120).
  • The token can reach the host log only if Lima fails to parse a template that it marshalled itself (capi-provider.md:184).
  • New LimaClusters and LimaMachines can wait up to 30 seconds, because the reconciler polls the guest cluster (reconciler.go:62-66).
  • Do not re-suggest a race on os.Setenv("LIMA_HOME") in controller_darwin.go:54. Go guards its environment with syscall.envLock, the lima controller already sets the same variable to the same value, and the line was kept on purpose.
  • Do not re-suggest reading controlPlaneRef.namespace or controlPlaneRef.apiVersion. The provider reads Cluster objects at v1beta2, whose controlPlaneRef has apiGroup and doesn't have a namespace.
  • Do not re-suggest listing rdd's datastore as another place that keeps the token. Kine keeps a deleted -source ConfigMap until compaction, but the <name>-template copy keeps the token in the same datastore for the VM's life, and the doc lists it.
