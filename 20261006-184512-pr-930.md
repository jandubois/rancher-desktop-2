## Executive Summary

The PR moves the Lima instance checks and the ssh command line from `rdd limavm shell` into `rdd/pkg/guestexec`, makes the shell exit with the guest command's status, and starts the Windows shell in the `/mnt/<drive>` path of the host's working directory. The extracted ssh arguments match the merge-base, the bats suite passes on a live VM, and the new exit-code test fails without its fix. This round converged, and the nine Suggestions are optional.

## Suggestions

S1. **`..` in a relative path can climb out of the drive's mount** — `rdd/pkg/guestexec/hostpath.go:41-45` [Codex GPT 6 Astra, Claude Opus 5.5, Gemini 3.5 Flash]

```go
	base, err := TranslateHostPath(cwd)
	if err != nil {
		return "", err
	}
	return path.Join(base, slashed), nil
```

The relative branch translates the working directory first and joins afterwards, so `path.Join` applies `..` to the guest path and can walk past `/mnt/c`. My probe set the working directory to `C:\work`. There `..\..\target` came back as `/mnt/target` and `..\..\..\x\y` as `/x/y`, where Windows stops at `C:\`. `..\sibling` stayed on the drive. Claude's probe found that drive-relative input such as `c:foo` also falls into this branch and resolves against the working directory. No caller reaches the branch yet, because `guestDir` passes only absolute paths, but the commit body says the nerdctl stub (#526) will translate user arguments with it.

Fix: join on the host side and translate once, `return TranslateHostPath(cwd + "/" + slashed)`, so the drive branch's `path.Clean` stops at the root; that passes the existing table and my probe. Reject a drive letter not followed by a slash before the relative branch.

S2. **The PR adds a second translator for the same host-to-guest path mapping** — `rdd/pkg/controllers/app/app/controllers/app_controller.go:211-217` [Consolidator]

```go
	if len(hostPath) >= 2 && hostPath[1] == ':' {
		drive := strings.ToLower(string(hostPath[0]))
		rest := strings.ReplaceAll(hostPath[2:], `\`, `/`)
		// /mnt/ is the mount point for drvfs disks in WSL2, per the default
		// value of `[automount] root=` in `/etc/wsl.conf`.
		return "/mnt/" + drive + rest
	}
```

The app controller's `toLinuxPath` already maps Windows host paths to `/mnt/<drive>` for the template's `HOST_HOME_GUEST`, `HOST_INSTANCE_CONFIG` and `VM_SWITCH_LOG` parameters (lines 164-166) and for the guest log directory (line 200). `TranslateHostPath` is a second implementation of that mapping, and `guestDir` (`limavm_shell.go:154-159`) repeats `toLinuxPath`'s `GOOS` check. Whoever changes the mount root, for example with a `root=` line under `[automount]` in `rdd/overlay/root/etc/wsl.conf`, has to find both.

Fix: keep one gated function, for example `guestexec.GuestPath(hostPath)`, which returns the path unchanged off Windows, and call it from `guestDir`'s callers and `toLinuxPath`'s.

S3. **The `LIMA_HOME` precondition does not hold where the engine controller can run** — `rdd/pkg/guestexec/guestexec.go:8-9` [Claude Opus 5.5, Gemini 3.5 Flash]

```go
// The caller must have set LIMA_HOME: the CLI sets it itself, and the lima
// controller sets it in-process at startup.
```

`store.Inspect` finds instances through Lima's `dirnames.LimaDir()`, which reads `LIMA_HOME` on every call and falls back to `~/.lima`. The engine controller, the next caller that #882 plans, belongs to the `containers` group, so `cmd/containers-controller` runs it without the lima controller, whose `RegisterWithManager` sets the variable (`pkg/controllers/lima/limavm/controller.go:183`). There `Inspect` would fail with `instance "rd" does not exist on disk`, which points away from the cause. The embedded service runs both controllers in one process by default (`--controllers=*`), so production works, but only through another controller's startup, and `--controllers=containers` leaves the lima controller out there too.

Fix: set `LIMA_HOME` from `instance.LimaHome()` inside `guestexec`, the value every rdd process uses, so no caller can forget it, and drop the CLI's own `os.Setenv` at `limavm_shell.go:56`.

S4. **`Inspect` returns a CLI remedy to library callers** — `rdd/pkg/guestexec/guestexec.go:43-44` [Claude Opus 5.5, Gemini 3.5 Flash]

```go
	if inst.Status != limatype.StatusRunning {
		return nil, fmt.Errorf("instance %q is not running (status: %s), use 'rdd lima start %s' first", instanceName, inst.Status, instanceName)
	}
```

The hint names `rdd lima start`, a command hidden outside developer mode (`main.go:159`). When the engine controller hits this error, the hint ends up in its log or in a condition about the App's VM, whose remedy is `rdd start`. The name `Inspect` also suggests a plain wrapper around `store.Inspect`, while this one rejects any instance that is not running.

Fix: return the status error alone, or wrap a sentinel such as `ErrNotRunning`, and let `limavm_shell.go` add the hint. `InspectRunning` would say what the function checks.

S5. **A failed ssh connection now exits 255 silently with OpenSSH before 8.9** — `rdd/cmd/rdd/limavm_shell.go:143-148` [Claude Opus 5.5]

```go
	err = sshCmd.Run()
	// ssh exits with the remote command's exit code, or 255 when ssh itself
	// fails.
	if exitErr := cliexit.ChildExit(err); exitErr != nil {
		return exitErr
	}
```

At the merge-base, every ssh failure reached `logrus.Fatal`, which printed `exit status 255`. `ChildExit` returns an `*Error` without a message, which `main.go:182` does not log. That is right when ssh prints its own error, but `guestexec.Command` sets `LogLevel=QUIET` for OpenSSH older than 8.9 (`guestexec.go:91-94`). Against a closed port, macOS's OpenSSH 10.3 exited 255 and printed nothing at `QUIET`, while at `ERROR` it printed `Connection refused`. So on a host with an older ssh, a broken connection now ends with no message at all.

Fix: log a line for code 255, such as "ssh exited with status 255 (connection failure, or the guest command exited 255)".

S6. **A child killed by a signal still makes rdd exit 255** — `rdd/pkg/cli/exit/exit.go:79-81` [Gemini 3.1 Pro]

```go
	// A signal-killed child has no exit code. ExitCode() returns -1, which
	// os.Exit maps to 255 rather than the shell's 128+signal.
	return &Error{Code: exitErr.ExitCode()}
```

The `*exec.ExitError` holds a `syscall.WaitStatus` that records the signal; Windows has the type too, with `Signaled()` always false. My probe passed `sh -c 'kill -TERM $$'` and `sh -c 'kill -SEGV $$'` through `ChildExit` and got -1 for both, which `os.Exit` turns into 255, where a shell reports 143 and 139. `exit 42` came through as 42. With the change below all three matched, and `go vet` passed for windows and linux. The comment at `run.go:172-173` credits signal handling with the 128+signal behaviour, but the wait status is what records the signal.

Fix: report 128+signal from the wait status, update both comments, and turn the probe into `ChildExit`'s first unit test.

```go
	if status, ok := exitErr.Sys().(syscall.WaitStatus); ok && status.Signaled() {
		return &Error{Code: 128 + int(status.Signal())}
	}
```

S7. **`--workdir` still reaches the guest untranslated on Windows** — `rdd/cmd/rdd/limavm_shell.go:72-73` [Claude Opus 5.5, Gemini 3.5 Flash]

```go
	if workDir != "" {
		changeDirCmd = fmt.Sprintf("cd %s || exit 1", shellescape.Quote(workDir))
```

`rdd lima shell --workdir C:\src rd` sends `cd 'C:\src' || exit 1` to the guest and exits 1 with the `cd` error #466 reports. This predates the PR, which translates only the implicit working and home directories. Passing every value through `TranslateHostPath` would also re-root a guest-relative value such as `--workdir src` against the host's working directory.

Fix: on Windows, translate `workDir` only when it starts with a drive letter and a separator.

S8. **The exit-code test does not check that the old error line is gone** — `rdd/bats/tests/33-lima-controllers/limavm-running.bats:174-176` [Claude Opus 5.5]

```bash
@test "shell propagates the remote exit code" {
    run -42 rdd lima shell "${VM_NAME}" sh -c 'exit 42'
}
```

Rebuilt with the `ChildExit` call reverted, `rdd` exited 1 and printed `level=fatal msg="exit status 42"`, and this test failed, so it catches the exit code. It would not catch that line coming back alongside the right code, which the `rdd run` test at `engine-docker.bats:846-852` guards with `refute_line`. Refute `exit status`, not the broader `level=` Claude proposed. `run` merges stderr, and on Windows the Lima instance loader logs `level=warning` lines (#466 quotes two).

Fix: add `refute_line --partial "exit status"` after the `run`.

S9. **The shell's docs omit the exit status and the Windows working directory** — `rdd/docs/design/cmd_lima.md:59-61` [Claude Opus 5.5, Codex GPT 6 Astra]

```markdown
### `rdd limavm shell NAME CMD`

Runs `CMD` inside a shell in the `NAME` instance, or opens an interactive shell if `CMD` is omitted.
```

The section does not say that the command exits with the guest command's status, or 255 when ssh fails, or that on Windows the shell starts in the `/mnt/<drive>` path of the host's working directory. A guest status of 3, 4 or 5 also collides with the codes `cmd_app.md` reserves for rdd in its exit-code table; `rdd run` has the same overlap and does not document it either.

Fix: add a sentence for each to this section.
