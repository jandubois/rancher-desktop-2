## Executive Summary

The PR uploads an x86_64 and an aarch64 Linux zip for OBS, picks the matching zip per build in the spec and the AppImage recipe, and adds a GitHub Pages upload for testing from a fork. OBS built every package on both architectures from this spec, but the arm64 deb depends on `qemu-system-x86`, because debbuild calls that architecture `arm64`. ## Important Issues

I1. **The arm64 deb depends on `qemu-system-x86`** — `packaging/linux/rancher-desktop.spec:59` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]

```spec
%if 0%{?debian}
Requires: qemu-utils
%ifarch aarch64
Requires: qemu-system-arm
%else
Requires: qemu-system-x86
%endif
```

debbuild turns `%ifarch X` into a comparison with `%{_arch}`, which it takes from `dpkg-architecture -qDEB_HOST_ARCH`, and that prints `arm64` on an arm64 host (debbuild 24.12.0, `debbuild:657-659` and `macros/platform.in:8`). So line 59 never matches in a deb build, and every arm64 deb takes the `%else` branch. Lines 34-40 of this PR map `arm64` to `aarch64` for `Source0` for the same reason. The arm64 deb that OBS built from this spec in the author's branch project lists `Depends: qemu-utils,qemu-system-x86,...`, so installing it on a Debian or Ubuntu arm64 host does not install `qemu-system-aarch64`, and the app cannot start the VM.

The line predates the PR, but this PR is the first to build arm64 debs. Issue #1196 says the spec already requires `qemu-system-arm` on Debian aarch64; it doesn't.

S1. **The Pages test mode fails at this SHA and cannot be re-run** — `.github/workflows/package.yaml:200` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]

```yaml
    - name: Upload Linux artifacts to GitHub Pages
      if: vars.OBS_DEPLOY_VIA_PAGES == 'true'
      uses: actions/upload-pages-artifact@fc324d3547104276b827a68afc52ff2a11cc49c9 # v5.0.0
      with:
        name: Rancher Desktop-linux.github-pages
        path: dist/upload
```

On the author's fork, attempt 1 at this SHA (job 129569952261) and the run at `6ee75445e` sat in `syncing_files` until deploy-pages gave up after 10 minutes, so OBS was never triggered. The re-run (job 129580352369) failed at once with `Multiple artifacts named "Rancher Desktop-linux.github-pages" were unexpectedly found`, because attempt 1's artifact is still part of the same run. The two zips make a 1,054,582,785-byte site, close to the 1 GB that GitHub documents as the limit for a published site. But one deploy of nearly the same size (1,054,577,086 bytes, `652a42b24`) succeeded, so size alone doesn't explain the timeouts. GitHub also times out any deployment after 10 minutes, so raising the action's `timeout` probably won't help. Only forks are affected.

Fix: suffix the artifact name with `${{ github.run_attempt }}` in both steps, and for the size, upload to a release on the fork instead.

S2. **aarch64 packages rely on Recommends for the UEFI firmware** — `packaging/linux/rancher-desktop.spec:60` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]

Issue #1196 asks the spec to require `qemu-efi-aarch64` (Debian), `edk2-aarch64` (Fedora) and `qemu-uefi-aarch64` (openSUSE), and the PR adds none of them. The firmware still arrives by default: Fedora 40's `qemu` requires `qemu-system-aarch64`, and its `qemu-system-aarch64-core` requires `edk2-aarch64`. Debian bullseye's `qemu-system-arm` and openSUSE Leap 15.6's `qemu-arm` only recommend theirs, so an install with recommends turned off does not get the firmware. On Debian even the Recommends do not apply until I1 is fixed, because the arm64 deb does not depend on `qemu-system-arm`.

Fix: add the three Requires under an aarch64 test (`RD_ARCH` on Debian), or record in #1196 that the Recommends are enough.

S3. **The release smoke test would pick the aarch64 AppImage** — `.github/workflows/smoke-test.yaml:149` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]

## Design Observations

### Concerns

- **The OBS cutover is undocumented** (in-scope) [Claude Opus 5.5]. After the merge, `rancher-desktop-2-main` takes its spec from `main` and needs `rancher-desktop-2.x86_64.zip`. But its live `_service` still downloads `rancher-desktop-2-linux-main.zip` and saves it as `rancher-desktop-2.zip`, and CI stops writing that key. Dev main fails to build until OBS changes, as the PR body expects. Stable meets the same change at the first tag that contains this PR, because `linux-release.yaml` runs from the tag, and the release checklist does not include a step to repoint the stable `_service` before publishing.

### Strengths

- One architecture-selected `Source0` (`%{name}.%{RD_ARCH}.zip`) keeps `%setup` unchanged and is simpler than the `Source0`/`Source1` pair that #1196 proposed. OBS built rpm, Fedora, deb and AppImage on both architectures from it. [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]
- `linux-release.yaml` now stops with "Failed to parse version" on a ref that isn't a version tag, where the old `sed` passed a garbage `major_minor` to the later steps. [Claude Opus 5.5]

## Review Process Notes

### Skill improvements

- When a change first sends a new platform, architecture or distribution down an existing code path, review the branches on that path for the new value even where the diff leaves them alone. A conditional that never ran on the new target is untested, and the diff shows only the lines the author thought to change.
- When the artifact that a change produces is built outside CI (a packaging service, an app store), fetch the published metadata of the author's test build, such as a repository index's dependency lists, as well as its build status. A build that succeeds says nothing about what the package declares.

### Repo context updates

- [repo] `packaging/linux/rancher-desktop.spec` is built by rpmbuild and by debbuild on OBS. Under debbuild, `%{_arch}` and `%ifarch` use Debian architecture names (`amd64`, `arm64`), so a test written with rpm names (`x86_64`, `aarch64`) never matches in a deb build. Flag a raw `%ifarch` with rpm names in any branch that the deb build takes; the spec's `RD_ARCH` macro gives rpm names under both tools.
