Executive Summary ¶

PR #523 adds a spec.virtualMachine block (cpus + memory) to the App CRD with webhook bounds, Lima-template rewriting, and a new HostInfo singleton CRD for the GUI. The design is clean, but the new BATS suite fails 5 of 14 tests as written: its control plane omits the rdd controller group, and cpus=0 stores 0 rather than clearing. The webhook also accepts negative cpus. All fixes are small and localized.

All three reviewers agreed there are no critical issues. The findings cluster into three themes: validation (negative cpus accepted and silently ignored), the new test suite (wrong controller group, a failing reset assertion, and BATS-style issues), and HostInfo robustness (no recovery path, plus a comment that claims one exists). The orchestrator built and ran virtual-machine.bats on the review SHA; Codex independently ran the same suite. Both confirmed the two test failures below (I2, I3) empirically — Claude and Gemini, reasoning from the source alone, assumed the reset flow passed.

Design Observations ¶

Concerns ¶

  • Host detection is duplicated across two packages and two HostInfo types (in-scope) Claude. DetectHostInfo() (app package) feeds the webhook, while HostInfoReconciler.Reconcile (rdd package) independently calls goruntime.NumCPU() + memory.TotalMemory() to populate the CRD; two Go types are both named HostInfo. Keeping detection out of the webhook is reasonable (a webhook read of the CRD would introduce a cross-group startup-ordering hazard), but the detection logic could live in one shared helper. Today the two paths agree only because both call NumCPU(); a future divergence (cgroup/affinity awareness in one path) would make the webhook and the GUI-visible range disagree silently.
  • Memory ceiling is 100% of host RAM (future) Claude. The webhook allows memory == hostInfo.Memory (app_webhook.go:85), matching issue #498, but allocating all host RAM to the guest can starve the host OS. Worth revisiting whether a headroom margin belongs here.

Strengths ¶

  • HostInfo CRD placement (in-scope) Codex. Moving host limits into a cluster-scoped HostInfo CRD in the rdd group (per Jan's review feedback) leaves room for future host diagnostics without overloading App.
  • CPU precedence chain (in-scope) Claude. spec → RDD_VM_CPUS → template default is expressed cleanly, and an invalid env value errors loudly so a CI typo cannot silently change VM sizing.
  • Template-change requeue contract (in-scope) Codex. The App reconciler updates the Lima template ConfigMap and explicitly requeues after the unwatched ConfigMap write, preserving the existing Settled/resourceVersion gating for applied changes.

Testing Assessment ¶

The suite is well-structured but does not pass as written (see I2, I3): a live run fails 5 of 14 tests — 4 from the missing rdd controller group, 1 from the cpus=0 reset assertion. Beyond those, coverage gaps:

  • Negative cpus (I1) — no unit or integration test; the untested branch is the actual gap.
  • Webhook create path — validateVirtualMachine has no unit test, and the BATS suite exercises only the update path (patch --dry-run=server). Per the Create+Update webhook contract, an invalid VM spec on create is unverified. A table-driven unit test on AppValidator.validate with an injected HostInfo would cover both paths cheaply and remove the dependence on live host geometry.
  • HostInfo recovery (I4) — the bootstrap-failure and post-delete paths are untested (and, as noted, do not self-heal).
  • applyVMResources memory-missing-line — the cpus-missing-line case is unit-tested; the memory equivalent is not.

The Test_applyVMResources unit test is otherwise solid, covering env/spec precedence, the memory rewrite, and invalid-env errors.

Documentation Assessment ¶

  • rdd/docs/design/api_app.md does not document spec.virtualMachine.cpus, spec.virtualMachine.memory, or the HostInfo resource / valid ranges Codex. It should be updated once the cpus=0 reset contract (I2) is decided.
  • The inaccurate "The next reconcile will retry" comment (I4) should be fixed or removed.
  • Exported symbols are otherwise well documented — VirtualMachineSpec, HostInfo/HostInfoStatus, DetectHostInfo, and the reconciler all carry Godoc.

Review Process Notes ¶

Skill improvements ¶

  • When a change adds or modifies a test suite, run that suite before concluding it passes; do not infer pass/fail by reading the test source. Source-only review produces false negatives — a test whose setup wires the wrong dependencies, or whose assertion contradicts the code's actual output, reads as correct on the page and fails on execution. If the suite cannot be run in the review environment, state that and lower confidence on any "tests pass" claim rather than asserting it.
  • When a validating webhook treats a sentinel value as "unset / use default" and skips validation for it (e.g. if x != 0 { … }), verify that out-of-range values on the other side of the sentinel are still rejected. A guard that excludes the sentinel and then checks only an upper bound silently admits negatives; if the schema declares the field as an unconstrained integer, the webhook is the only gate. Confirm the CRD minimum/maximum and the webhook together cover the full invalid range.

Repo context updates ¶

  • [repo] BATS tests that query a custom resource must enable that resource's API group in setup_rdd_control_plane's argument — the helper forwards it verbatim to rdd svc create --controllers=. Groups are app, rdd, containers, lima. A missing group surfaces as the server doesn't have a resource type "X" at test time, not as a clear setup error. When a test references a resource type, check that the enabled groups include the one that serves it (e.g. HostInfo is in rdd, App in app).
  • [repo] In rdd set, an empty value clears string and quantity (XIntOrString) fields by emitting a null merge patch, but an integer field cannot be cleared this way: field= fails coercion ("expected integer") and field=0 stores 0 (a JSON merge patch keeps a zero; only null removes). When reviewing a new optional integer spec field documented with a "0 means default / reset" contract, verify reset-to-unset is actually achievable — and that any test asserting the field becomes empty reflects real behavior.
