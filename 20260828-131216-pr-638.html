Executive Summary ¶

The managedlines helper is a careful, idempotent port of RD1's manageLinesInFile, and the front/back/manual model is a clean improvement on RD1's boolean. Two dotfile layouts silently defeat the feature: a symlinked bash login file loses the block moments after gaining it, and a ~/.cshrc-only home gets a new ~/.tcshrc that shadows it. On Windows the manual default — documented as leaving PATH alone — rewrites HKCU\Environment\Path.

Findings below were verified by executing probes against the review SHA, not by inspection alone; each says which experiment confirmed it. Four reviewers ran; the two Gemini models share a family, so their agreement counts as one voice.

## `rdd shell-profile`

It prints a list of shell commands to STDOUT to put the `~/.rd2/bin` directory on the `PATH` and load completions for `rdd` and any bundled utilities (`docker`, `helm`, ...).

```console
$ rdd shell-profile bash --path --completions
export PATH="$HOME/.rd2/bin:$PATH"
source <(rdd completion bash)
source <(docker completions bash)
source <(helm completions bash)
...
```

This is also the command the "path management" inserts into the users shell profile, e.g.

```bash
source <(~/.rd2/bin/rdd shell-profile bash --path)
```

bootstrap.md:97 further gates the ~/.kube/config merge on "path-management is enabled", which the implementation does not consult.

rdd/docs/design/bootstrap.md

### Kubernetes Context

If Kubernetes has been enabled, e.g. with `rdd start --kube-version 1.33.2`, then a `rancher-desktop-2` kube context is created in `~/.rd2/kube.config`. If path-management is enabled, then the context will also be merged into `~/.kube/config` and made the current context there[^kubeconfig].

[^kubeconfig]: Setting up a list (like `KUBECONFIG=~/.kube/config:~/.rd2/kube.config` is not practical because the environment variable would need to be updated each time an RDD instance is created or removed.

Design Observations ¶

Concerns ¶

  • Three names now exist for one user setting (in-scope) Claude Opus 5. RD1 and the Electron tree use application.pathManagementStrategy with rcFiles/manual (pkg/rancher-desktop/config/settings.ts:82, pkg/rancher-desktop/components/PathManagementSelector.vue); the daemon now uses application.addPath with front/back/manual. Nothing is wired yet — the environment preferences tab is still commented out — so the cost of choosing now is zero and rises sharply once the key reaches users' deployment profiles. Either keep addPath and plan the migration explicitly, or reuse pathManagementStrategy and add front/back as new values so an RD1 profile carries over with a value rename.
  • Ownership of a PATH entry is inferred from its content (in-scope) Codex GPT 5.6 Sol. On Unix the markers make ownership explicit; on Windows the registry has no equivalent, so manual removes any entry matching the bin directory regardless of who put it there. I3 addresses the concrete defect; the residual ambiguity is inherent to a bare Path string and is not worth persisting ownership metadata to solve.
  • Drift is never repaired until the App changes again (future) Claude Opus 5. Reconcile returns without requeue and the only trigger is an App watch event, so a user who edits the block by hand keeps their edit indefinitely. The code reads as if the block is enforced continuously; a RequeueAfter, or a comment accepting the drift, would make the intent visible.

Review Process Notes ¶

Skill improvements ¶

  • When a finding proposes registering, importing, or wiring a new component into an existing extension point, read the extension point's own validation before repeating the fix. Registries frequently assert an invariant on what they accept — a matching identifier, a non-empty group, a unique name — and a fix that satisfies the finding while violating that assertion turns a silent omission into a startup crash. Verify the proposed wiring against the registry's guard, not only against the sibling entries already listed there.
  • Treat "this matches an existing sibling" as a reason to check the sibling, not as evidence the code is correct. When a reviewer defends a construct by pointing at a neighbour that does the same thing, verify the construct against the contract the neighbour is supposed to satisfy; a convention followed by two files can still be a defect present in both, and framing it as convention removes it from the findings list where it belongs.
  • When reviewing code that writes into a set of files a shell or tool selects by precedence — reading the first that exists and ignoring the rest — check whether the code creates a file that is absent. Creating a higher-precedence file silently disables the lower-precedence one the user is actually using. Flag it wherever the code writes to every member of such a set rather than to the one the tool would read.
  • When a change adds a setting whose documented default is "do nothing", execute the no-op path against realistic inputs rather than reading it. A shared normalisation or cleanup step reached by every branch turns the inert default into a write, and because that default ships to every user, it is the highest-exposure path in the change.

Repo context updates ¶

  • [repo] REMOVE or UPDATE the clause in the controller-review rule stating that both cmd/*/main.go and the embedded service package must blank-import every controller. rdd/pkg/external/main.go panics when a registered controller's GetAPIGroup() differs from the group the standalone binary was launched for, so a controller that returns an empty group cannot be imported into its cmd/*/main.go at all. The rule as written prescribes a change that crashes the binary. State instead: a controller must return its API group, and only then must appear in both import lists; a controller returning an empty group is reachable solely through --controllers=* or its own name, which is a defect to flag rather than a layout to reproduce.
  • [repo] rdd/pkg/util/atomicfile resolves symlinks before writing and replaces the link target, so a symlinked dotfile keeps its link. Code that writes user dotfiles through it preserves symlinks by construction, and findings claiming a symlinked config file is replaced by a regular file should be rejected. The reverse case still needs checking: logic that iterates a list of candidate filenames and treats them as distinct files will operate twice on one inode when two names resolve to the same target.
  • [repo] rdd set waits for the App's Settled condition by default, and computeSettledCondition derives it from exactly three conditions: LimaVM Running, ContainerEngineReady, and KubernetesReady. A controller that reconciles an App spec field without writing a status condition is therefore outside the wait, so the CLI reports success before that field's work happens and keeps reporting success while it fails in a backoff loop. When reviewing a new App-watching controller, check whether it contributes a condition and whether Settled gates on it.
  • [repo] go build ./... under rdd/ fails at HEAD on pkg/guestagent's embed of lima-guestagent.gz unless the guest agent has been built first. This is a build prerequisite, not a defect in the change under review; verify new packages with a targeted go build ./pkg/... ./cmd/... subset or run the guest-agent build first.
  • [repo] make verify-generate currently fails on nine rdd/pkg/apis/containers/v1alpha1/applyconfiguration/ files that no recent change touches — a containers API change landed without regenerating. Treat a verify-generate failure confined to that directory as pre-existing, and confirm the CRDs a change actually touches regenerate byte-identical rather than reading the command's exit status.
