## Executive Summary

This PR re-backs the Vuex preferences store on the RDD `App.spec` through the generated `@rdd-client`, replacing the IPC `Settings` object, and reworks the Vuex typings. The store internals — dry-run validation, JSON-Patch commit, request-abort serialization, and the app watcher — are sound and well-tested. The migration is incomplete: roughly sixteen UI consumers still dispatch the removed actions and read `Settings` fields `AppSpec` cannot represent, so the preferences dialog is inert on this branch.

All three reviewers agreed the internals are well-built. Codex surfaced the consumer break, Gemini the commit patch bug, and Claude the type-safety regressions and design concerns. The findings fall into two themes: migration completeness (I1, I2) and the `modify`/`commit` patch asymmetry (I3, S5).

## Important Issues

I1. **Removed preferences actions/getters still dispatched by the UI — every call silently no-ops** — `pkg/rancher-desktop/store/preferences.ts:110-267` [Codex GPT 5.5, Claude Opus 4.8] (important, regression)

```
pages/Preferences.vue:76        dispatch('preferences/commitPreferences')
components/Preferences/*.vue     dispatch('preferences/updatePreferencesData', …)
store/diagnostics.ts:108         dispatch('preferences/commitPreferences', …)
```

The rewrite deletes `updatePreferencesData`, `commitPreferences`, `proposePreferences`, `fetchPreferences`, `setShowMuted`, `setCanApply`, `updateWslIntegrations`, and the getters `getPreferences`/`isPreferencesDirty`/`canApply`/`showMuted`. Roughly sixteen sites across `components/Preferences/*.vue`, `pages/Preferences.vue`, `pages/Diagnostics.vue`, `DiagnosticsBody.vue`, and `store/diagnostics.ts` still reference them. TypeScript does not catch it: vuex's base `Dispatch(type: string, …)` overload declaration-merges with the strict augmentation in `typings/store.d.ts:41`, so CI stays green. At runtime an unknown action logs `[vuex] unknown action type` and resolves `undefined` — every toggle and Apply becomes a no-op. The new surface has zero consumers, confirming a staged migration; downgraded from critical because there is no public release. `store/diagnostics.ts:108` also breaks outside the dialog.

Fix: migrate the consumers, or land a tracking issue and note that the Preferences UI is intentionally inert until a follow-up.

I2. **`AppSpec` cannot represent most `Settings` fields the UI reads** — `pkg/rancher-desktop/store/preferences.ts:60` [Codex GPT 5.5] (important, regression)

```ts
preferences: {} as Required<RDDClient.IoRancherdesktopAppV1alpha1AppSpec>,
// AppSpec has only: containerEngine, kubernetes, namespace, running
```

The old store held a full `Settings` object; `AppSpec` exposes four top-level fields. Components read paths `AppSpec` lacks — `preferences.application.telemetry.enabled` (`ApplicationGeneral.vue:85`), `getPreferences.application.extensions.allowed.list` (`MarketplaceCatalog.vue:33`) — and `ModalBody.vue:32` still types the prop as `Settings`. Even after the I1 action migration, these reads resolve to `undefined`, and the dry-run patch (`preferences.ts:149`, `fieldValidation: 'Strict'`) would reject unknown fields. The App API must grow to cover these preferences, or the UI must be scoped to the fields `AppSpec` supports.

Fix: do not switch the full dialog to `AppSpec` until the schema covers the surfaced settings, or narrow the UI to the supported fields.

I3. **`commit` JSON-Patch `add` fails when the parent object is absent (enabling Kubernetes)** — `pkg/rancher-desktop/store/preferences.ts:182-191` [Gemini 3.1 Pro] (important, regression)

```ts
const pathParts = ['', 'spec', ...key.split('.')].map(k => k.replaceAll('~', '~0').replaceAll('/', '~1'));
body.push({ op: 'add', path, value }); // e.g. /spec/kubernetes/enabled
```

`commit` emits one JSON-Patch `add` per changed key. Under RFC 6902, `add` to `/spec/kubernetes/enabled` requires `/spec/kubernetes` to already exist. An App created by `rdd set running=true` has no `spec.kubernetes`: `createAndPatchApp`/`fillRequiredFields` (`rdd/cmd/rdd/set.go:359`) fill only the spec-level required `running`, and the CRD gives `kubernetes` no default (unlike `containerEngine`). Enabling Kubernetes from the UI then sends `add` to a missing parent, which the API server rejects with 422. `modify`'s merge-patch dry-run vivifies the parent, so validation passes while the real commit fails. Downgraded from critical: latent until the UI is wired (I1), recoverable via the CLI, and pre-release.

Fix: build `commit` as a merge patch from `changes` (mapping `undefined` to `null`), matching the dry-run path.

## Suggestions

S1. **`MutationsType` loosened globally to admit one non-`SET_` mutation** — `pkg/rancher-desktop/store/ts-helpers.ts:12-14` [Claude Opus 4.8] (suggestion, regression)

```ts
export type MutationsType<T> = {
  [key in keyof T as `SET_${ UpperSnakeCase<key> }`]?: (state: T, payload: T[key]) => any;
} & Record<string, (state: T, payload: any) => any>;
```

The added index signature lets `preferences.ts` declare `UPDATE_PREFERENCE` under a bare `satisfies MutationsType<PreferencesState>`. But it weakens the check for every module using `satisfies MutationsType<…>` alone (`steve.ts`, `container-engine.ts`, `rdd.ts`, `diagnostics.ts`): a misspelled `SET_` name or wrong payload now matches the index signature instead of erroring. The established pattern for extra mutations is `satisfies MutationsType<S> & MutationTree<S>` (see `rddConnection.ts:61`), which the old `preferences.ts` used. `satisfies` preserves the precise `UPDATE_PREFERENCE` typing either way.

Fix: drop the `& Record<…>` and use `satisfies MutationsType<PreferencesState> & MutationTree<PreferencesState>` in `preferences.ts:80`.

S2. **`RecursiveReadonly` not updated to `object` like its siblings** — `pkg/rancher-desktop/utils/typeUtils.ts:16` [Claude Opus 4.8] (suggestion, gap)

```ts
T[P] extends Record<string, unknown> ? RecursiveReadonly<T[P]> :
```

This PR moved `RecursivePartial` and `RecursiveKeys` from `Record<string, unknown>` to `object` because generated `@rdd-client` classes do not extend `Record<string, unknown>` and so were not recursed into. `RecursiveReadonly` kept the old form, yet the PR adds a consumer at `preferences.ts:84` (`Required<RecursiveReadonly<AppSpec>>`) where `AppSpec` is a generated class — so the deep-readonly stops one level in. Type-level only, but an inconsistent trap.

Fix: change line 16 to `T[P] extends object ? RecursiveReadonly<T[P]> :`.

S3. **`state.preferences` typed `Required<AppSpec>` but initialized to `{}`** — `pkg/rancher-desktop/store/preferences.ts:60` [Claude Opus 4.8] (suggestion, gap)

The watcher fills `preferences` only once `rdd/app` resolves with a spec. Before that — at startup, or after the app is deleted — `preferences` is an empty object typed as a fully-populated spec. Once consumers migrate (I1) and read `preferences.kubernetes.enabled`, they hit `undefined`. Initialize from defaults, or read through a getter that tolerates the empty state.

S4. **`commit` can drop a `modify` that interleaves during its await** — `pkg/rancher-desktop/store/preferences.ts:182-205` [Claude Opus 4.8] (suggestion, gap)

`commit` snapshots `body` from `changes`, awaits the patch, then clears all changes unconditionally at line 205. A `modify` that runs during the await adds a key `commit` never sent but then wipes — a lost update. Practically unreachable in the single-user UI, so low severity.

Fix: clear only the keys actually committed, rather than resetting `changes` to `{}`.

S5. **`modify`'s merge-patch dry-run cannot represent a field removal** — `pkg/rancher-desktop/store/preferences.ts:147` [Gemini 3.1 Pro, Claude Opus 4.8] (suggestion, gap)

`modify` validates a JSON Merge Patch of the whole `spec: state.preferences` with `dryRun: 'All'`. When a change sets a field to `undefined` — the `remove` case `commit` handles at line 187 — `JSON.stringify` drops the key, so the merge patch neither validates nor represents the removal. The dry-run passes on a payload that differs from what `commit` sends as a JSON-Patch `remove`, so validation and the real write can disagree. This is the removal-side twin of I3.

Fix: validate the exact patch `commit` will send (see the Design Observation on divergent patch mechanisms).

S6. **Watcher leaves unrelated background updates stale after a revert** — `pkg/rancher-desktop/store/preferences.ts:259` [Gemini 3.1 Pro] (suggestion, gap)

```ts
if (Object.keys(store.state.preferences.changes).length === 0) {
  store.commit('preferences/SET_PREFERENCES', _.cloneDeep(app.spec));
}
```

While `changes` is non-empty, the watcher skips `SET_PREFERENCES`, so a background `App.spec` change (e.g. a CLI edit to an unrelated field) is not reflected. Refusing to clobber in-progress edits is correct — Claude flagged the same guard as a strength — but the watcher keys on `rdd/app` changing, not on `changes` emptying, so after the user reverts their edit it does not re-fire and the unrelated field stays stale until the next app change. Narrow in single-user use.

Fix: re-apply `app.spec` on every change and layer the uncommitted `changes` on top, so unrelated fields stay live without losing edits.

## Design Observations

**Concerns**

- **Two divergent patch mechanisms for one resource** `(in-scope)` [Gemini 3.1 Pro, Claude Opus 4.8] — `modify` validates with a full-spec merge patch while `commit` applies a hand-built JSON patch (`preferences.ts:181-201`). The two exercise different server code paths and fail differently: the merge patch vivifies parents and ignores `undefined`, the JSON patch requires existing parents and encodes explicit `remove`. This split is the root of both I3 and S5. Dry-running the exact JSON patch that `commit` will send — or building `commit` as a merge patch from `changes` — would keep validation and write in lock-step and close both gaps. The hand-rolled RFC 6901 escaping (`replaceAll('~','~0').replaceAll('/','~1')`) is correct and tested; a small patch helper would also cover array indices (the `// TODO: Handle array values` at line 189) uniformly.
- **Dot-notation keys cannot represent map keys or array indices** `(future)` [Claude Opus 4.8] — `Changes` keys are dot-joined paths consumed by `_.get`/`_.set`/`key.split('.')`. Today's `AppSpec` (`running`, `kubernetes.*`, `containerEngine.name`, `namespace`) has no map or array fields, and `RecursiveLeafKeys`/`FieldType` note they do not handle arrays. Worth revisiting before adding map-typed spec fields (WSL integrations, allowed-image patterns) whose keys can contain dots.

**Strengths**

- The `SerializedRequestMiddleware` abort pattern is sound: the renderer's `fetch` rejects with `signal.reason`, so `Object.is(error, requestSerializer.abortError)` reliably distinguishes an intentional supersession from a real error. [Claude Opus 4.8]
- Moving validation to a dry-run `patchApp` against the same API-server contract that will apply the change — rather than a separate client-side validator — is a good direction. [Codex GPT 5.5]
- The `ActionTree`/`moduleName<S>`/`mutationsFor<S>` machinery gives each module's actions a precisely-typed `commit`, and `RootGetters` is cleanly relocated so `store.d.ts` and `ts-helpers.ts` share one definition. [Claude Opus 4.8]

## Review Process Notes

**Skill improvements**

- When a change removes a member from a strongly-typed facade layered over a loosely-typed library API — a Vuex `dispatch`/`commit` augmentation, a typed event emitter, a DI-token map — do not assume the type-checker flags stale consumers. TypeScript interface augmentation merges rather than replaces, so a library's base `(type: string, …)` overload survives alongside the strict one and accepts any string key. Consumers that reference the removed member by string compile cleanly and fail only at runtime. When a PR removes actions, getters, mutations, events, or handlers addressed by a string key, grep the codebase for every consumer of each removed name and confirm it still resolves, rather than trusting a green type-check.
- When reviewing code that builds RFC 6902 JSON Patch operations, flag `add` or `replace` on a nested path whose parent object is not guaranteed present: `add` to `/a/b/c` is rejected when `/a/b` is absent, unlike a JSON Merge Patch, which vivifies parents. Verify the parent is always populated by a schema default, a required field, or explicit creation. Separately, when one path validates a change with a dry-run under one patch strategy and another applies it under a different strategy, trace both — merge patch ignores omitted keys and creates parents, JSON patch encodes explicit `remove` and requires existing parents — so a dry-run can pass on a payload the real write will reject.

**Repo context updates**

- [repo] The Vuex store typings in `pkg/rancher-desktop/typings/store.d.ts` augment vuex's `Dispatch` and `Commit` to type known module actions and mutations, but vuex's base `(type: string, payload?: any)` overload survives declaration merging. Removing or renaming a store action or getter therefore produces no type error; `Lint TypeScript` and `Jest` stay green while `dispatch('module/action')` calls become runtime no-ops (`[vuex] unknown action type`). When reviewing changes to a store module's public surface, grep every `dispatch`/`mapActions`/`mapGetters`/`mapState` consumer directly instead of relying on the type-check.
- [repo] In the App CRD (`rdd/pkg/apis/app/v1alpha1/app_types.go`), `spec.containerEngine` carries a `+kubebuilder:default` but `spec.kubernetes` does not, and only `running` is required at spec level. An App created via `rdd set` without a `kubernetes.*` field is stored with no `spec.kubernetes` object. Code that patches nested `kubernetes.*` fields with a JSON Patch `add` (`/spec/kubernetes/...`) must account for the absent parent, since the API server rejects an `add` whose parent object is missing.
- [repo] PRs touching `pkg/rancher-desktop/` are in the classic Rancher Desktop Electron/Vue 2/Vuex/TypeScript tree, tested with Jest, not the Go daemon under `rdd/`. The "RDA" work re-backs this tree onto the daemon's kube-apiserver `App` resource through the generated `@rdd-client`. Expect staged migrations where a store or service is re-backed before its UI consumers are updated; confirm whether an incomplete-migration state is intended and tracked rather than flagging it as an oversight.

`body` is snapshotted, then after the `await` all changes are cleared unconditionally. A `modify` interleaved during the await adds a key to `changes` that the commit did not send but then wipes at line 205 — a lost update. Practically unreachable in single-user UI flow, so low severity, but note it or clear only the keys that were actually committed.

**S5. `modify`'s merge-patch validation cannot represent field removal** — `pkg/rancher-desktop/store/preferences.ts:147` `(suggestion, gap)`

`modify` validates via a JSON Merge Patch of the whole `spec: state.preferences` with `dryRun: 'All'`. When a change sets a field to `undefined` (the `remove` case that `commit` handles at line 187), `JSON.stringify` drops the key, so the merge patch neither validates nor represents the removal — the dry-run passes on a payload that differs from what `commit` will later send as a JSON-Patch `remove`. The validation and the real write can therefore disagree. Consider validating the removal (e.g. explicit `null`, or a dry-run JSON-Patch mirroring `commit`).

### Design Observations

**Concerns**

- **Two divergent patch mechanisms for the same resource** `(future)` — `modify` uses a full-spec Merge Patch (dry-run) while `commit` uses a hand-built JSON Patch (`preferences.ts:181-201`). This means validation and commit exercise different server code paths and different failure modes (e.g. JSON-Patch `add` to `/spec/kubernetes/enabled` requires `/spec/kubernetes` to already exist per RFC 6902; fine for the currently fully-defaulted spec, but fragile if the defaulter ever leaves a parent unset). A single strategy (dry-run the exact JSON Patch that `commit` will send) would eliminate the S5 gap and keep the two flows in lock-step. The hand-rolled RFC 6901 escaping (`replaceAll('~','~0').replaceAll('/','~1')`) is correct and tested, but a small `fast-json-patch`-style helper would also handle array indices (the `TODO: Handle array values` at line 189) uniformly.
- **Dot-notation keys can't represent map keys/array indices** `(future)` — `Changes` keys are dot-joined paths consumed by `_.get`/`_.set`/`key.split('.')`. The current `AppSpec` (`running`, `kubernetes.{enabled,version}`, `containerEngine.name`, `namespace`) has no map or array fields, so this is safe today, and `RecursiveLeafKeys`/`FieldType` explicitly `@note` they don't handle arrays. Worth keeping in view before adding map-typed spec fields (e.g. WSL integrations, allowed-image patterns) whose keys can contain dots.

### Gemini 3.1 Pro

### Executive Summary

This PR rewrites the Vuex preferences store to manage configurations via the `App.spec` object directly using the API client. The headline finding is a critical mismatch in JSON patch strategies: `commit` will fail with a 422 error when enabling previously omitted optional structs, and `modify` drops removed fields during its validation dry-run, missing invalid state errors.

### Findings

#### Critical Issues

C1. **`commit` and `modify` fail to handle missing parent structs and field removals** — `pkg/rancher-desktop/store/preferences.ts:167-210` (critical, regression)

The Vuex store uses flawed patch strategies for applying and validating preferences:
1. `commit` uses `JsonPatch` and generates leaf-level `add` operations (e.g., `path: '/spec/kubernetes/enabled'`). Under RFC 6902, the parent object (`/spec/kubernetes`) MUST exist. If the K8s API server omitted the `+optional` `Kubernetes` struct because it lacked a default, this patch is rejected with a 422 Unprocessable Entity, permanently blocking the user from enabling Kubernetes.
2. `modify` uses `MergePatch` with the full `state.preferences` for validation. If a user unsets a field (value becomes `undefined`), `JSON.stringify` drops it. In MergePatch, omitted fields are ignored rather than removed, so the API server validates the *old* value, falsely passing the validation.

Fix: Use `PatchStrategy.MergePatch` for **both** operations, and send a partial object constructed only from `state.changes`, mapping `undefined` to `null` to ensure proper removals and parent vivification:

```typescript
    const patch: any = {
      apiVersion: 'app.rancherdesktop.io/v1alpha1',
      kind: 'App',
      metadata: { name: app.metadata.name, namespace: app.metadata.namespace },
      spec: {}
    };
    for (const [key, value] of Object.entries(state.changes)) {
      _.set(patch.spec, key, value === undefined ? null : value);
    }
    // Use this patch object for both client.patchApp calls with PatchStrategy.MergePatch
```
*(Update `__tests__/preferences.spec.ts` accordingly)*

#### Important Issues

I1. **Pending changes permanently block backend updates, causing stale UI** — `pkg/rancher-desktop/store/preferences.ts:246-255` (important, gap)

```typescript
        if (Object.keys(store.state.preferences.changes).length === 0) {
          // If there are no uncommitted changes, update the preferences to match the app's spec.
          store.commit('preferences/SET_PREFERENCES', _.cloneDeep(app.spec));
        }
```

The Vuex watcher drops all state updates from the K8s API server (e.g., CLI preference changes) if the user has *any* uncommitted changes in the UI. If a user edits one field while a background process updates an unrelated field, the UI ignores the background update. Furthermore, if the user then reverts their edit, `changes` becomes empty, but the watcher does not re-fire — leaving the UI permanently stuck displaying stale data for the unrelated fields.

Fix: Always apply the latest `app.spec` to `state.preferences`, but re-apply the user's uncommitted `changes` on top of it. This ensures background updates to unrelated fields are reflected immediately without losing the user's work, and eliminates the state-sync race conditions:

```typescript
      (app) => {
        if (!app?.spec) return;
        const newPrefs = _.cloneDeep(app.spec);
        for (const [key, value] of Object.entries(store.state.preferences.changes)) {
          _.set(newPrefs, key, value);
        }
        store.commit('preferences/SET_PREFERENCES', newPrefs);
      }
```
