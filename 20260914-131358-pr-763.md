+// XFS, and btrfs, the smallest hole any of them can make.
+const sparseBlockSize = 4 << 10
+
+var zeroBlock [sparseBlockSize]byte

+// sparseWriter writes to f, skipping each block of zeros so that the file
+// system leaves a hole there. An xz stream records no holes, so writing
+// every byte would allocate a disk image's free space along with its data.
+type sparseWriter struct {
+	f       *os.File
+	off     int64 // offset in f of the next byte to write
+	dataEnd int64 // offset in f just past the last data written

+
+func (w *sparseWriter) Write(p []byte) (int, error) {
+	for i := 0; i < len(p); {
+		data := w.runEnd(p, i, false)
+		if data > i {
+			if err := w.writeData(p[i:data], w.off+int64(i)); err != nil {
+				return i, err
+			}
+		}
+		i = w.runEnd(p, data, true)
+	}
+	w.off += int64(len(p))
+	return len(p), nil

+
+// writeData writes data at off in f, then punches a hole over the whole
+// blocks of zeros skipped since the previous data.
+func (w *sparseWriter) writeData(data []byte, off int64) error {
+	if _, err := w.f.WriteAt(data, off); err != nil {
+		return err
+	}
+	holeStart := (w.dataEnd + sparseBlockSize - 1) / sparseBlockSize * sparseBlockSize
+	holeEnd := off / sparseBlockSize * sparseBlockSize
+	if holeEnd > holeStart {
+		punchHole(w.f, holeStart, holeEnd-holeStart)
+	}
+	w.dataEnd = off + int64(len(data))
+	return nil

+// holds blocks of zeros if zero is true, and blocks of data otherwise. Blocks
+// end at multiples of sparseBlockSize in f, so a block of zeros split across
+// two Write calls still becomes a hole.
+func (w *sparseWriter) runEnd(p []byte, i int, zero bool) int {
+	for i < len(p) {

+		if bytes.Equal(p[i:end], zeroBlock[:end-i]) != zero {

I2. **The Makefile resolves the target differently from the `go` commands it runs** — `rdd/Makefile:48-49` [Claude Opus 5, Codex GPT 5.6 Sol]

```make
TARGET_OS := $(shell go$(EXE) env GOOS)
TARGET_ARCH := $(shell go$(EXE) env GOARCH)
```

GNU make 3.81, macOS's `/usr/bin/make`, hides command-line variables from `$(shell)` but exports them to recipes. So `make build-rdd GOARCH=amd64` on an arm64 Mac stages the arm64 image, and `go build` (line 104) compiles an amd64 rdd around it. The build succeeds, and that rdd hands its VM an arm64 disk. At the merge-base the same command worked, because Lima picked the arch-matching URL at runtime.

Line 94 fails the other way. With `GOOS` or `GOARCH` empty, `go` falls back to a target saved with `go env -w`, so `go run` can build a tool this machine cannot run, and the comment at line 92 no longer holds. CI and `scripts/dependencies/rdd.ts` set the variables in the environment, so shipped artifacts build correctly.

## Review Process Notes

### Skill improvements

- Expect a liveness monitor to expire. The Monitor tool ends every monitor after 30 minutes, whatever `persistent` says, so a 90-minute deadline needs its monitor re-armed on each expiry with the deadline's remaining seconds. Step 4's claim that `persistent: true` lifts the timeout is wrong and should say this instead.
- In PR mode, check the local branch's reflog as well as its tip before launching agents. A forced `gh pr checkout` resets the branch to the pushed head, so the tip comparison shows no divergence while an unpushed commit that belongs to the PR survives only in the reflog. List any commit a recent reset dropped, and settle which SHA to review.
- When a change sends existing input through a different implementation (a library decoder instead of an external tool, a copy loop instead of a platform copy), compare what the two leave on disk, not only the bytes. Sparseness, permissions, ownership, timestamps and extended attributes differ silently between implementations, and a content-equality test passes either way.

### Repo context updates

- [repo] macOS ships GNU make 3.81, whose `$(shell)` does not see command-line variable assignments while recipes do. - [repo] The rdd Makefile's recipes also run under a WSL-hosted make that invokes `go.exe`, and a variable reaches `go.exe` only when the recipe lists it in `WSLENV`. Check every variable a new recipe passes to a Go command against that recipe's `WSLENV` list.
- [repo] `scripts/postinstall.ts` runs every dependency, `make build-rdd` included, under one ten-minute `InstallTimeout`. A change that adds network work to `make build-rdd` must fit that limit on a cold cache or give the step its own.

During clean builds, if the guest agent or the embedded guest distro image does not exist, the `rm` commands print "No such file or directory" error messages to stderr. While the leading `-` instructs GNU Make to ignore these errors and proceed, the output can be noisy and confusing to developers.

Fix: Add the `-f` flag to the `rm` commands to silence these warnings when files are already deleted.

```diff
 clean:
 	-rm -rf bin
-	-rm $(GUESTAGENT_BINARY) $(GUESTAGENT_GZ)
-	-rm pkg/embedded/distro.*.xz*
+	-rm -f $(GUESTAGENT_BINARY) $(GUESTAGENT_GZ)
+	-rm -f pkg/embedded/distro.*.xz*
```

### Design Observations

#### Concerns

None in-scope. All identified limitations have been explicitly called out and accepted by design.

#### Strengths

- **Elegant Lima Integration**: By decompressing and writing the raw disk image or rootfs tarball to the instance directory before calling `limainstance.Prepare`, `rdd` elegantly triggers Lima's built-in short-circuit optimization. This bypasses the remote downloader without requiring any custom forks or intrusive upstream modifications to core `lima-vm` code.
- **In-Memory Stream Processing**: The custom `DecompressReader` directly decodes the embedded image from the read-only Go memory segment into the destination file. This streaming approach completely avoids writing a temporary multi-hundred-megabyte compressed archive to disk, minimizing local disk wear and I/O overhead.
- **Smart Makefile Incremental Builds**: The Makefile's target for `$(DISTRO_IMAGE)` relies on a `.PHONY` or `FORCE` target to ensure the dependency downloader always checks for updates, but since the downloader leaves an up-to-date file untouched, make intelligently avoids relinking `bin/rdd` when the image has not changed.

### Acknowledged Limitations

- **Binary Size Bloat**: The `rdd` binary size grows significantly due to the embedded compressed distro image (~177 MiB on Windows, ~207 MiB on arm64 macOS, and ~250 MiB on amd64 platforms). This is documented and accepted as a necessary trade-off for air-gapped capability.
- **Decompression CPU overhead**: Decompressing the embedded xz image using the pure-Go decoder takes about 19s (on an M1 Mac), compared to ~2.3s using system xz. This is documented as an acceptable trade-off to support hosts without a pre-installed `xz` tool, while avoiding extra intermediate disk writes.
