## Executive Summary

The branch replaces the byte-for-byte bridge on `\\.\pipe\docker_engine` with RD1's Docker API proxy, so drive-absolute bind sources in `POST /containers/create` reach dockerd as `/mnt/<drive>` paths. The path translation and the raw JSON editing hold up. The defects are in the HTTP relay. A streamed response keeps its backend connection after the client leaves, and a response that the backend cuts short reaches the client as complete. Its comment misstates the standard library's proxy. Nothing has run on Windows yet.

## Important Issues

I1. **A streamed response keeps its backend connection after the client leaves** — `rdd/pkg/dockerproxy/reverse_proxy.go:123-126` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro]

```go
	// Flush while the body streams, so that a long-running response such as
	// `docker logs -f` reaches the client as it arrives.
	fw := newFlushedWriter(ctx, w)
	_, err = io.Copy(fw, backendResponse.Body)
```

The copy reads `backendConn` directly, and the proxy doesn't close that connection when `ctx` ends. So when a user stops an idle `docker events` or `docker logs -f`, the hostagent keeps the goroutine, the vsock connection and dockerd's stream until dockerd writes again. rdd's own Docker event watcher leaks a connection this way each time it stops. Before this branch, `HostBridge.handleConn` closed the vsock connection when the pipe read ended.

The comment at lines 60-61 says that cancelling `ctx` ends the backend request, which it doesn't.

When dockerd, rdd-guest or the vsock connection fails partway through a chunked response, the copy returns an error. The proxy logs it and returns normally, so net/http ends the response with its final chunk, and the client reads a complete body. `docker save -o image.tar` would then exit 0 with a truncated tar file. Before this branch, the byte bridge passed the broken framing through, and the client failed. Go's `httputil.ReverseProxy` aborts the response in this case. The run with both patches, shown under I1, passes this probe too.

I3. **A comment says the standard library's proxy can't relay upgrades or half-closes** — `rdd/pkg/dockerproxy/reverse_proxy.go:28-31` [Codex GPT 6 Astra]

```go
// ReverseProxy forwards each Docker API request to dockerd over a new
// connection. Unlike the standard library's ReverseProxy, it relays the
// connection after an HTTP protocol upgrade, which attach and exec use, and
// passes on a half-close from either side.
```

Go's `httputil.ReverseProxy` does both. Its `handleUpgradeResponse` relays an upgraded connection, and its copier calls `CloseWrite` on each side once the other side's copy ends (`net/http/httputil/reverseproxy.go:905` and `:921` in Go 1.27.4). In the probe below, the standard proxy answers an attach with `101`, the backend reads the client's half-close as EOF, and the client still gets the reply. If the standard proxy dropped the half-close, the probe would print a read error or an empty body. A reader takes this comment as the reason the package can't use the standard proxy, and I1, I2, S1 and S2 show what the hand-written relay costs.

## Suggestions

S1. **An `Expect: 100-continue` request loses dockerd's final response** — `rdd/pkg/dockerproxy/reverse_proxy.go:92` [Codex GPT 6 Astra]

```go
	backendResponse, err := http.ReadResponse(bufferedReader, newReq)
```

The proxy forwards the client's `Expect` header, so dockerd answers `100 Continue` before its final response. The proxy reads and relays only that first response, and net/http then completes the exchange with an empty `200`. Codex's probe through `Serve` turned a `201` with a body into an empty `200`. This stays harmless while clients on the pipe leave `Expect` out; the moby Go client that the Docker CLI uses doesn't set it.

Fix: keep reading while `backendResponse.StatusCode < 200` and the status isn't `101`. With that loop, the probe returns the `201`, and the package tests pass.

S2. **The proxy forwards every request body chunked** — `rdd/pkg/dockerproxy/reverse_proxy.go:73-78` [Claude Opus 5.5, Gemini 3.1 Pro, Gemini 3.5 Flash]

```go
	newReq, err := http.NewRequestWithContext(ctx, r.Method, url, r.Body)
	if err != nil {
		proxy.sendError(w, "failed to create a request for the backend: "+err.Error(), http.StatusInternalServerError)
		return
	}
	newReq.Header = r.Header
```

`NewRequestWithContext` can't know the length of `r.Body`, so `newReq.ContentLength` stays 0 and `Request.Write` sends the body chunked. A probe through `Serve` showed a client's `Content-Length: 2` arriving as `ContentLength=-1` with `Transfer-Encoding: chunked`. dockerd's start handler rejects `-1` as a deprecated non-empty body (`api/server/router/container/container_routes.go:217` in moby v28.5.2). So a client that sends `{}` to `/start` works directly and fails through the proxy. The moby client sends a nil body there.

Fix: `newReq.ContentLength = r.ContentLength` after line 78. The probe then shows `ContentLength=2`, and the package tests pass.

S3. **Extended-length drive paths such as `\\?\C:\src` stay untranslated** — `rdd/pkg/guestexec/hostpath.go:68-70` [Claude Opus 5.5]

```go
func IsDriveAbsolute(hostPath string) bool {
	_, _, ok := splitDrive(strings.ReplaceAll(hostPath, `\`, "/"))
	return ok
```

RD1's `ParseBindString` and `IsAbsolutePath` (`platform/serve_windows.go`) accept a `\\?\` prefix and translate the path. `IsDriveAbsolute` rejects it, `CutVolumeSource` cuts such a bind at `\\?\C`, and `containers_create_test.go:42` pins the pass-through. The spec reaches dockerd unchanged, as it did before this branch, so the port loses an RD1 behavior without breaking anything that worked.

Fix: strip a leading `\\?\` before the drive check in both helpers, or note beside `IsDriveAbsolute` that such paths stay untranslated.

S4. **The backend dial waits for Hyper-V's own timeout** — `rdd/pkg/hostswitch/hostswitch_windows.go:190-191` [Claude Opus 5.5]

```go
			dial := func(context.Context) (net.Conn, error) {
				return socketbridge.DialVsock(vmGUID, socketbridge.VsockForwardPort)
```

The dial closure drops its context, and `DialVsock` calls `hvsock.Dial`, which blocks. RD1's `dialHvsock` gave up after one second, and its comment says that the dial otherwise times out after 30 seconds. While rdd-guest isn't listening, each Docker request waits for Hyper-V to refuse the dial, and a client that gives up leaves its goroutine waiting. The merge-base `HostBridge` dialed the same way, so the port inherits this.

Fix: run the dial in a goroutine and return on `ctx.Done()` or a short timer, as RD1 did.

## Design Observations

### Concerns

- **(future) The hand-written relay has to get right what `net/http/httputil.ReverseProxy` already handles.** I1, I2, S1 and S2 are all in `reverse_proxy.go`, and Go's `ReverseProxy` handled I1, I2 and S1 in Codex's loopback probe, which didn't test S2. I3 covers the upgrade case. Codex also ran an upgrade probe. In it, the standard proxy relayed a client half-close and the response that followed. This review didn't rerun that probe, and neither proxy has run over a message-mode pipe. [Codex GPT 6 Astra]
- **(future) Hijacked connections outlive `Serve`'s shutdown, so a host-switch restart may fail to listen again.** `server.Close` leaves `docker run -it`, `docker exec -it` and BuildKit sessions open, and go-winio creates a pipe's first instance with `FILE_CREATE`. A still-open instance would then make the next `runOnce`'s `ListenPipe` fail; nobody has tested that on Windows. The merge-base bridge left every connection open at shutdown, so this change doesn't make it worse. [Claude Opus 5.5]
- **(future) Attach and exec without an `Upgrade` header lose stdin.** dockerd then answers `200` and streams raw output, and the proxy relays that output but not the client bytes that follow the request. The Docker CLI sends `Upgrade: tcp`. RD1 has the same limitation. [Claude Opus 5.5]
- **(pre-existing) The Docker pipe name is global, and a failed listen leaves the pipe to whoever else holds it.** `hostswitch_windows.go:185-187` logs the `ListenPipe` failure and continues, as the merge-base bridge did. The repo's review context already records this. [Gemini 3.1 Pro]
- **(pre-existing) The pipe gets go-winio's default security descriptor**, as the merge-base bridge's did. A multi-user Windows host would need an SDDL that admits only the current user. [Gemini 3.5 Flash]

### Strengths

- The create munger edits raw JSON, so fields from newer API versions reach dockerd, and a body it doesn't change goes out byte-identical (`TestMungeContainersCreateUnchangedBody`). A body that repeats a key in different case goes through untranslated. [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]
- The message-mode comment at `hostswitch_windows.go:181-184` holds against go-winio v0.6.4: `Accept` returns a connection with `CloseWrite` only in message mode, which RD1's listener also uses. [Claude Opus 5.5]

###### Design Observations

**Concerns**

- **(future) Hijacked connections survive `Serve`'s shutdown, so a host-switch restart may fail to re-listen.** `server.Close()` does not close hijacked connections such as `docker run -it`, `docker exec -it` and BuildKit sessions. `winio.ListenPipe` creates its first handle with `FILE_CREATE` (go-winio v0.6.4 `pipe.go`, `makeServerPipeHandle`). I expect a still-open instance to make the next `runOnce`'s listen fail, but I did not verify that on Windows. The Docker pipe would then stay down until the next restart. The merge-base was worse, because every connection outlived shutdown, so this change makes nothing worse. One sketch: set `BaseContext: func(net.Listener) context.Context { return ctx }` in `Serve`, and close `backendConn` on `ctx` in `handleUpgradedConnection` as well. `Pipe` then unwinds the hijacked client once `Serve` stops. Retrying `ListenPipe` inside `runOnce` would cover the remaining window.
- **(future) The proxy breaks attach and exec without the `Upgrade` header.** In that form dockerd answers `200` and then streams raw. The proxy streams the response but never relays client bytes sent after the request, so stdin is lost. The byte bridge passed these through. The Docker CLI sends `Upgrade: tcp`, and I believe docker-py does too (from memory, unverified). The limitation is inherited from RD1.

###### Critical Issues

C1. **Manual raw I/O ignores request context cancellation, leaking goroutines and connections** (critical, new-feature) — `rdd/pkg/dockerproxy/reverse_proxy.go:66-70`

```go
	backendConn, err := proxy.DialContext(ctx, "", "")
	if err != nil {
		proxy.sendError(w, "failed to connect to the backend: "+err.Error(), http.StatusBadGateway)
		return
	}

```

The proxy bypasses `http.Transport` to handle protocol upgrades manually, performing raw `io.Copy` over `backendConn` inside `forwardRequest` (line 128). If the client disconnects, `r.Context()` is cancelled, but `forwardRequest` does not close `backendConn` on cancellation. Since raw network I/O ignores context cancellation, `io.Copy` blocking on an idle stream (such as `docker logs -f`) will block forever if the backend sends nothing, leaking both the goroutine and the underlying connection until the daemon stops. 

Fix: Call `context.AfterFunc` right after `proxy.DialContext`, bounded by `ctx`, to ensure the blocking I/O is interrupted when the context cancels.

```diff
 	if err != nil {
 		proxy.sendError(w, "failed to connect to the backend: "+err.Error(), http.StatusBadGateway)
 		return
 	}
 	defer backendConn.Close()
+
+	stopConn := context.AfterFunc(ctx, func() {
+		backendConn.Close()
+	})
+	defer stopConn()
```

###### Design Observations

###### Strengths

- **Raw JSON manipulation without schema generation**: Managing only `HostConfig.Binds` and `HostConfig.Mounts` via raw JSON preserves unknown fields, unmapped types, and formatting intact. This eliminates the dependency on `go-swagger` models and allows client/server API version negotiation without artificial overrides.
- **Platform-neutral proxy package**: `dockerproxy` has no OS build tags and parses paths platform-independently, allowing all unit tests to execute on macOS and Linux developer environments without Windows tooling.
- **Case-insensitive duplicate key detection**: `checkDuplicateKeys` proactively prevents ambiguous field overrides caused by Go map deserialization while preserving original payloads when conflicts occur.

###### Concerns

- **Named pipe client authorization** `(future)`: `winio.ListenPipe` uses default Windows security attributes, allowing any local user to connect to `\\.\pipe\docker_engine`. If multi-user isolation on Windows is targeted in the future, passing an SDDL restricting access to the current user token in `winio.PipeConfig.SecurityDescriptor` would enforce user boundary isolation.
