## Suggestions

S1. **The `ErrMalformedBlock` comment lists the malformed shapes differently from the other three descriptions** — `rdd/pkg/util/managedlines/managedlines.go:30-31` [Claude Opus 5.5, Gemini 3.5 Flash]

```go
// parse: an unbalanced marker (a lone or unclosed marker, or a stray one left
// beside a block), or the end marker before the start. It's permanent —
```

This round brought `app_types.go:126-128` and `api_app.md:155` into line with the `splitByMarkers` comment (`managedlines.go:100-102`), and all three now name the parser's three branches. This comment, which the PR also rewrote, still uses its own terms. It does not name a nested start, and it lists "the end marker before the start" as a separate case, though the parser handles it in the same branch as any other end marker with no open block (line 131). No code contradicts the comment, but it is now the one description that differs.

Fix: reuse the three-shape wording: "an unbalanced marker: a start with no matching end, an end with no open start, or a start nested inside another."

S2. **The nested-start message names the second start as the marker that broke the pairing** — `rdd/pkg/util/managedlines/managedlines.go:125` [Claude Opus 5.5]

```go
				return malformed("line %d opens a block before the one opened on line %d is closed", i+1, start+1)
```

For the file `a / START / userline / START / export / END / z`, the message reads "line 4 opens a block before the one opened on line 2 is closed". That frames line 2 as the real block and line 4 as the intruder. A user who deletes line 4 gets a balanced block that holds `userline`, and the next pass deletes that line on removal or overwrites it on add. Either start marker could be the stray one, and the parser cannot tell which.

The PR still improves on the merge-base, which in my run deleted `userline` from that file without an error on both add and remove.

Fix: name both lines without ranking them, for example `"lines %d and %d both open a block with no end marker between them", start+1, i+1`, and update the `nested start` case in `TestManageMalformedNamesTheLine`.

###### Design Observations

###### Concerns

- **Rejection on removal leaves live `export PATH` lines when stray markers exist** `(in-scope)`: Under `present=false` (`pathmanagement.Unwind` in `service.go:546` and `reconciler.go:111`), encountering our block followed by a stray marker now causes `Manage` to reject the file and leave it untouched. As intended by issue #917, this prevents half-edits from stranding invisible stray markers, but means the managed block's `export PATH` line remains active in the file. `service.Delete` logs a warning and proceeds, while reconciler deletion releases the finalizer without retrying.

###### Strengths

- **Unified single-pass parsing**: Consolidating block extraction and duplicate collapsing into one pass through `blocks [][2]int` guarantees that marker pairing is evaluated identically across add, update, and remove passes, eliminating the asymmetry where `stripBlocks` previously ignored markers that `splitByMarkers` rejected.
- **Accurate line-numbered diagnostics**: Reporting the exact line number of unclosed starts (`start+1`), unopened ends (`i+1`), and nested blocks (`i+1` and `start+1`) provides actionable guidance directly to the user in `PathManagementReady` condition messages.

Refusing to edit the file when any unbalanced marker is present is the author's deliberate choice, trading automated cleanup for file integrity and user visibility.
