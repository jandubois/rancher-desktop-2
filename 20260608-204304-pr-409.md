## Executive Summary

The PR adds a pure-Go `pkg/xz` decoder and a `LimaVM` reconcile hook that pre-decompresses the distro image to `<inst.Dir>/image` when no system `xz` is on `PATH`, so base macOS (which ships no `xz`) can provision. The macOS/Linux path is sound: digest verified, temp-file-then-rename keeps Prepare's skip-guard safe, `pkg/xz` well-tested. But the WSL2/Windows half does not work — Lima's WSL2 driver consumes `basedisk`, not `image`, ignoring the pre-decompressed file and still shelling out to `xz`.

The three reviewers agreed the decoder package is solid and converged on the `ensureImageDecompressed` hook as the risk surface. Claude alone traced the WSL2 driver to find the `basedisk` gap (I1) — verified against Lima v2.1.2. The remaining findings (loop fidelity, context cancellation, a CI typo, permissions) are lower-stakes; several are inert under today's image configs but matter for the PR's stated "lift into upstream Lima" goal.

## Important Issues

I1. **WSL2/Windows path still requires system `xz` — the pre-decompressed `image` is never consumed** — `rdd/pkg/controllers/lima/limavm/controllers/limavm_controller.go:410,437` [Claude Opus 4.8]

```go
imagePath := filepath.Join(inst.Dir, filenames.Image)  // "<dir>/image"
...
return xz.DecompressFile(cached, imagePath)
```

The hook writes the decompressed image to `<inst.Dir>/image` and relies on Lima reusing it. That holds for vz/qemu: `Prepare` skips its download block when `image` (or `disk`) exists. But the WSL2 driver consumes a *different* file. `EnsureFs` checks `<inst.Dir>/basedisk` (`filenames.BaseDiskLegacy`) and, on absence, calls `DownloadFile(..., decompress=true)`, which shells out to `xz` (verified in lima v2.1.2 `pkg/driver/wsl2/fs.go:20-31`). rdd never writes `basedisk`, so on a clean Windows the `xz` shell-out still fires and provisioning still fails — the exact case the PR claims to fix. Not a regression (Windows failed before too), but a stated goal that silently does not work.

Fix: also produce `basedisk` (hardlink the decompressed output) when `inst.Config.VMType == limatype.WSL2`, and run the flagged Windows e2e.

I2. **In-process decode ignores context — graceful shutdown blocks on the no-xz provisioning path** — `rdd/pkg/xz/xz.go:21-29` [Claude Opus 4.8, Gemini 3.1 Pro]

```go
func Decompress(in io.Reader, out io.Writer) error {
	r, err := ulikunitz.NewReader(bufio.NewReaderSize(in, bufSize))
	...
	if _, err := io.CopyBuffer(out, r, make([]byte, bufSize)); err != nil {
```

`Decompress`/`DecompressFile` take no `context.Context`, so the single-threaded decode (the PR's own table: 19s–95s+) cannot be cancelled. `ensureImageDecompressed` holds `ctx` and `DownloadFile` honors it, but the decode does not. This is the *primary* path for the feature's target (stock macOS has no `xz`), so every first provision there runs an uninterruptible decode; a concurrent `rdd svc stop` waits on it (bounded by the manager's graceful-shutdown timeout).

Fix: thread `ctx` into `DecompressFile`/`Decompress` and close `in` (or check `ctx.Err()` per chunk) on cancel; pass `ctx` from `ensureImageDecompressed`.

## Suggestions

S1. **`ensureImageDecompressed` does not replicate Lima's `Prepare` image loop** — `rdd/pkg/controllers/lima/limavm/controllers/limavm_controller.go:423-438` [Codex GPT 5.5, Gemini 3.1 Pro, Claude Opus 4.8]

```go
for _, img := range inst.Config.Images {
	if img.File.Arch != arch { continue }
	...
	cached, err := fileutils.DownloadFile(ctx, "", img.File, false, "the image", arch)
	if err != nil { return fmt.Errorf("caching image ...: %w", err) }
	return xz.DecompressFile(cached, imagePath)
}
```

The hook returns on the first matching-arch image, dropping two `Prepare` behaviors: (a) fallback to later same-arch mirrors when one fails, and (b) per-image `Kernel`/`Initrd` sidecar downloads — pre-creating `image` makes `Prepare` skip its whole block (the same skip mechanism behind I1), so sidecars would never download on a no-xz host. Both are inert under today's configs (`lima-images-unix.yaml`/`-wsl2.yaml`: one image per arch, no sidecars), but the PR is explicitly "shaped to lift into upstream Lima," where multi-mirror and sidecars are normal.

Fix: iterate candidates, `continue` on error, and reproduce the sidecar work before returning success.

S2. **`core.longpath` is not a Git config key (should be `core.longpaths`)** — `.github/workflows/lint.yaml:82,118` [Claude Opus 4.8]

```yaml
git config --global --replace-all core.longpath true #spellchecker:ignore
```

The Windows long-path setting is `core.longpaths` (plural); `core.longpath` sets an inert key and has no effect. Pre-existing typo (also at lines 63/155/173/195); this PR adds two more copies. If long-path support is actually needed on these runners, it is silently absent.

Fix: change to `core.longpaths` and sweep the other instances in one pass. Also normalize `#spellchecker:ignore` (no space) vs `# spellchecker:ignore` elsewhere.

S3. **Decompressed `image` is mode `0o600`, vs Lima's `0o644`** — `rdd/pkg/xz/xz.go:47` [Claude Opus 4.8]

`os.CreateTemp` creates the temp at `0o600`, and the rename preserves it, so the produced `image` is owner-only. Lima's `decompressLocal` writes `0o644` (lima `pkg/downloader/downloader.go:547`). Functionally fine — the rdd process owns and reads it — but an unexplained drift from the path it replaces.

Fix: `chmod` the temp to `0o644` before rename, or note why `0o600` is intentional.

S4. **`.xz` detected by suffix only; local image locations break in caching-only mode** — `rdd/pkg/controllers/lima/limavm/controllers/limavm_controller.go:427-431` [Codex GPT 5.5]

`strings.HasSuffix(location, ".xz")` misses xz streams behind query-string URLs or magic-byte detection, handing them back to `Prepare`'s `xz` shell-out. Separately, `DownloadFile(ctx, "", localFile, ...)` returns an empty `CachePath` for `file://` locations (lima `copyLocal` returns early in caching-only mode), so `xz.DecompressFile("", ...)` then opens `""`. Both are inert for today's remote `.raw.xz`/`.tar.xz` configs.

Fix: download the candidate first, then sniff the cached file's xz magic; handle the empty-cache-path case for local files.

S5. **The 4 MB buffer passed to `io.CopyBuffer` is never used** — `rdd/pkg/xz/xz.go:29` [consolidator]

`io.CopyBuffer(out, r, make([]byte, bufSize))` ignores its buffer whenever `out` implements `io.ReaderFrom` — which both callers' destinations do (`*os.File` in `DecompressFile`, `*bytes.Buffer` in the tests). Writes fall back to `io.Copy`'s internal 32 KB buffer. The real speedup comes from the input-side `bufio.NewReaderSize(in, bufSize)`, which absorbs ulikunitz's tiny reads; the output buffer is a dead 4 MB allocation.

Fix: drop the explicit buffer (the input `bufio` is what matters), or wrap `out` in `bufio.NewWriterSize` to realize the intended large writes.

## Review Process Notes

**Skill improvements**

- Add a review dimension for Go's buffer-bypassing I/O helpers. When code passes an explicit buffer to `io.CopyBuffer` (or relies on `io.Copy` for throughput), check whether the destination implements `io.ReaderFrom` or the source implements `io.WriterTo`. If either holds, the helper delegates to `ReadFrom`/`WriteTo` and silently ignores the supplied buffer, so the intended large-buffer behavior never happens — and the common destinations `*os.File` and `*bytes.Buffer` both implement `io.ReaderFrom`. Flag a sized buffer whose only purpose is throughput when the destination or source type defeats it, and be skeptical of a comment that attributes a measured speedup to a buffer that is actually bypassed (the real win usually lives on the other side of the copy).

**Repo context updates**

- [repo] Lima stores the provisioning image under two filenames depending on the driver: `filenames.Image` (`image`) is consumed by the vz/qemu path via `instance.Prepare`, while `filenames.BaseDiskLegacy` (`basedisk`) is consumed by the WSL2 driver via `EnsureFs` at driver Start (after Prepare). Both call `fileutils.DownloadFile(..., decompress=true)`, which shells out to `xz`. Any rdd code that pre-creates one artifact to make Lima skip its own download/decompress must satisfy both consumers — pre-creating only `image` leaves the WSL2 path still downloading and decompressing via `xz`. When reviewing image-provisioning code, verify the destination filename matches the driver that will consume it (key off `inst.Config.VMType`).

### Executive Summary

The PR introduces a pure-Go `.xz` decompression fallback to ensure Lima VM images can be provisioned on hosts lacking a system `xz` binary. The change successfully removes an external dependency requirement. However, the decompression loop breaks Lima's native image fallback logic by exiting on the first download or decompression failure, and the synchronous decompression lacks context cancellation, which can hang graceful shutdown.

### Findings

#### Critical Issues

C1. **`ensureImageDecompressed` breaks Lima's image fallback mechanism** — `rdd/pkg/controllers/lima/limavm/controllers/limavm_controller.go:431-438` (critical, regression)

```go
		cached, err := fileutils.DownloadFile(ctx, "", img.File, false, "the image", arch)
		if err != nil {
			return fmt.Errorf("caching image for in-process decompression: %w", err)
		}
		// ...
		return xz.DecompressFile(cached, imagePath)
```

Lima's configuration supports multiple fallback images per architecture (e.g., primary URL and mirrors). Native `Prepare` iterates through these, falling back to the next image if one fails to download or decompress. `ensureImageDecompressed` breaks this resilience for `.xz` images: if `fileutils.DownloadFile` or `xz.DecompressFile` fails for the first matching image, it returns the error immediately instead of attempting the next fallback. This causes VM creation to fail entirely when a primary URL is unreachable.

Fix: Accumulate or log errors and `continue` to the next image on failure. Return `nil` if the loop exhausts all images so `Prepare` can run, try them, and surface its standard aggregate error.

```diff

 		if err != nil {

+			logger.Error(err, "Failed caching image for in-process decompression", "location", img.File.Location)
+			continue
```

#### Important Issues

I1. **`DecompressFile` ignores context cancellation, blocking shutdown** — `rdd/pkg/xz/xz.go:21-29` (important, regression)

```go
func Decompress(in io.Reader, out io.Writer) error {
	r, err := ulikunitz.NewReader(bufio.NewReaderSize(in, bufSize))
	// ...
	if _, err := io.CopyBuffer(out, r, make([]byte, bufSize)); err != nil {
		return fmt.Errorf("decompressing xz stream: %w", err)
	}
```

Decompressing a multi-hundred-megabyte VM image can take up to 95 seconds on slow hosts. `Decompress` and `DecompressFile` do not accept a `context.Context`, and `io.CopyBuffer` does not monitor cancellation. If the daemon is gracefully stopped or the reconcile is canceled, the controller will block waiting for this synchronous I/O loop to finish, hanging the daemon's shutdown process.

Fix: Pass `context.Context` into `DecompressFile` (and subsequently from `ensureImageDecompressed`). Spin up a goroutine bounded by a derived context that monitors `ctx.Done()` and closes the underlying `in` file descriptor (which cleanly interrupts `io.CopyBuffer` with a closed-file error).

```diff
-func DecompressFile(src, dst string) (err error) {
+func DecompressFile(ctx context.Context, src, dst string) (err error) {
 	in, err := os.Open(src)
 	if err != nil {
 		return err
 	}
 	defer in.Close()
 
+	ctx, cancel := context.WithCancel(ctx)
+	defer cancel()
+	go func() {
+		<-ctx.Done()
+		in.Close() // Interrupts blocking io.CopyBuffer
+	}()
+
 	tmp, err := os.CreateTemp(filepath.Dir(dst), filepath.Base(dst)+".tmp-*")
```

None.

### Design Observations

**Concerns**

**Mixed-compression fallbacks on hosts without xz (in-scope)**: `ensureImageDecompressed` correctly returns `nil` when it encounters a non-`.xz` image to defer to Lima's `Prepare`. However, this means if a `lima.yaml` lists a `.tar.gz` primary and a `.xz` fallback, the fallback will never be pre-decompressed. If `Prepare` fails on the primary, it will try the fallback, shell out to `xz`, and fail. Pre-decompressing fallbacks would require eagerly downloading them, which violates priority order. As an alternative, if `Prepare` fails, the controller could catch the missing-`xz` error and trigger a second pass, but the simplest approach is to ensure Rancher Desktop's bundled templates do not mix compression types.

### Testing Assessment

1. **Context cancellation during decompression**: The in-process decompression can take up to 90+ seconds. There is no integration or unit test verifying that `ctx.Cancel()` cleanly interrupts the `DecompressFile` loop and releases resources without leaving corrupted temp files behind (relates to I1).
2. **Image fallback logic**: There is no test exercising the scenario where the primary `.xz` image URL is a 404 but a secondary `.xz` mirror succeeds (relates to C1).
