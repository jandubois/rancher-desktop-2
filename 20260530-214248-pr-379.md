## Executive Summary

PR #379 makes `shutdownAllHostagents` reclaim each hostagent's PID file, socket, tmp files, and WSL2 distro after every exit, not only after a timeout. This fixes the Windows force-kill case, where `exec.CommandContext` terminates the hostagent before its own teardown runs and the stale PID file misleads the next `rdd svc start`. The change is correct, simplifies the loop, and adds a cross-platform regression test. No blocking issues.

All three reviewers converged on one concern — `stopInstanceForcibly` now kills a stored Windows PID that could be recycled — but split on severity (Gemini critical, Codex important, Claude design observation). Verification against the code resolves it downward: the hazard is pre-existing and documented (`limavm_lifecycle.go:225-233`), and this change *narrows* net exposure rather than widening it. It lands in Design Observations, leaving two minor suggestions.

## Suggestions

S1. **Function doc comment still describes the old timeout-only fallback** — `pkg/controllers/lima/limavm/controllers/limavm_controller.go:499-500` [Codex GPT 5.5]

```go
// shutdownAllHostagents terminates all running hostagents during graceful shutdown.
// It sends a graceful shutdown signal to each hostagent, waits for exit, and falls
// back to process termination after a timeout.
```

The comment says forced termination happens only as a timeout fallback. After this change the cleanup runs after every wait outcome (lines 541-542), graceful or timed-out. The distinction matters most on Windows, where the "graceful" exit is the force-kill path that the cleanup exists to handle, so the stale comment misleads exactly where the code is subtlest.

Fix:

```diff
 // shutdownAllHostagents terminates all running hostagents during graceful shutdown.
-// It sends a graceful shutdown signal to each hostagent, waits for exit, and falls
-// back to process termination after a timeout.
+// It signals each hostagent, waits for it to exit, then reclaims any resources the
+// hostagent left behind — whether it self-stopped or was force-killed on timeout.
```

S2. **Test asserts PID-file removal but not WSL2 distro termination** — `bats/tests/33-lima-controllers/limavm-running.bats:341` [Codex GPT 5.5, Claude Opus 4.8]

```bash
try --max 30 --delay 1 --until-fail -- lima_instance_running "${VM_NAME}"
```

The commit message names two leftovers a force-killed hostagent leaves behind: the PID file *and* the WSL2 distro. `lima_instance_running` checks only `ha.pid`. A regression that stopped terminating the distro (`stopInstanceForcibly` → `terminateWSL2Distro`, `limavm_lifecycle.go:677`) would still pass this test, so half the documented bug is unguarded.

Fix: on the WSL2 path, add an assertion that the distro is gone — e.g. `run wsl.exe --list --running` and `refute_line --partial "lima-${VM_NAME}"`. Guard it with `is_msys`/WSL handling so it runs only where `wsl.exe` exists.

## Design Observations

### Concerns

- **Windows PID-recycle window on the new cleanup path** `(future)` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro] — On Windows, `store.Inspect` returns the PID from a stale `ha.pid` without a liveness check, so `stopInstanceForcibly` → `KillTree` runs `taskkill /F /T /PID` against a PID the OS may have recycled. This change adds one more site that does so, now on the post-`procExited` path. Three facts keep it out of the findings list. The hazard is pre-existing and documented (`limavm_lifecycle.go:225-233`), with the same `Inspect`-then-kill pattern already in `handleUnwatchedState`/`killOrphanedHostagent` and `shutdownHostagent`. The new window is milliseconds — cleanup fires right after the force-kill — versus the seconds-to-minutes window of the next-start path it removes. And by clearing the PID file during shutdown, the change stops `killOrphanedHostagent` from killing an even staler PID at the next `rdd svc start`. Net exposure drops. The documented proper fix — validate process identity before `taskkill`, or adopt Windows Job Objects — would close it everywhere at once.

- **Hostagent lifetime is coupled to the manager context** `(future)` [Codex GPT 5.5, Gemini 3.1 Pro] — `exec.CommandContext(ctx, …)` ties the hostagent to the manager context, so cancellation force-kills it before `shutdownAllHostagents` can run an orderly interrupt-wait-kill sequence. That coupling is the root reason the Windows exit only *looks* graceful and this cleanup is needed at all. Detaching with `context.WithoutCancel(ctx)` (Go 1.21+) would let the hostagent receive the interrupt and self-stop, closing the teardown gap at its source. The tradeoff is real: a hostagent that ignores the interrupt would survive the service exit entirely, so the timeout-and-force-kill path this PR strengthens stays necessary as a backstop. Worth weighing as a separate change, not a defect in this one.

### Strengths

- The refactor collapses the old `if !graceful` branch and its duplicate cleanup-and-wait block into one unconditional path and drops the `graceful` bool — less code, one path to reason about. [Claude Opus 4.8]
- The "no-op when already clean" reasoning holds end to end: on a clean exit the PID file is gone, so `inst.HostAgentPID == 0` and `KillTree` never runs; on the Windows force-kill path `KillTree` returns nil for the dead parent (exit 128, `process_windows.go:84`), so `allKilled` stays true and PID/tmp-file removal and distro termination proceed. [Claude Opus 4.8]
- The `context.Background()` cleanup context is correctly justified — it must outlive the cancelled manager context — and carries an explaining comment. [Codex GPT 5.5, Claude Opus 4.8]

### [Gemini 3.1 Pro]

### Executive Summary

The PR attempts to reclaim hostagent resources during service shutdown by unconditionally calling `stopInstanceForcibly` even after the process has died. However, this introduces a critical TOCTOU PID-recycling vulnerability on Windows and fails to fix the underlying child process leak, because `KillTree` cannot traverse the children of an already-dead parent. The root cause is `exec.CommandContext` prematurely murdering the hostagent upon manager cancellation; detaching the context is required for true graceful shutdown.

### Findings

#### Critical Issues

C1. **Unconditional cleanup introduces TOCTOU PID-recycling vulnerability** — `pkg/controllers/lima/limavm/controllers/limavm_controller.go:539-544` (critical, regression)

```go
		logger := ctrl.Log.WithName("shutdownAllHostagents")
		cleanupCtx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
		if inst, err := store.Inspect(cleanupCtx, name); err == nil && inst != nil {
			stopInstanceForcibly(cleanupCtx, logger, inst)
		}
```

The PR unconditionally calls `stopInstanceForcibly` even after `state.procExited` closes. On Windows, when the manager cancels, `exec.CommandContext` immediately force-kills the hostagent. `haCmd.Wait()` returns (releasing the PID to the OS), and `procExited` closes. 

The code then calls `store.Inspect`, which reads the dead hostagent's stale `ha.pid` file. It passes this stale PID to `stopInstanceForcibly` -> `KillTree`, which blindly runs `taskkill /F /T /PID`. If the OS has recycled the PID, an unrelated process is killed. Furthermore, because the parent is already dead, `taskkill /T` cannot traverse the tree, so child processes (e.g., SSH port forwarders) are permanently leaked anyway.

Fix: Revert `limavm_controller.go` to only call `stopInstanceForcibly` if the timeout expires (`!graceful`), guaranteeing the PID is still owned by the hostagent. To achieve true graceful shutdown, detach `haCmd` from the manager context in `limavm_lifecycle.go`.

```diff
// pkg/controllers/lima/limavm/controllers/limavm_controller.go
+		graceful := true
 		select {
 		case <-state.procExited:
 		case <-time.After(gracefulShutdownTimeout):
+			graceful = false
 		}
 
+		if !graceful {
 			logger := ctrl.Log.WithName("shutdownAllHostagents")
 			cleanupCtx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
 			if inst, err := store.Inspect(cleanupCtx, name); err == nil && inst != nil {
 				stopInstanceForcibly(cleanupCtx, logger, inst)
 			}
 			cancel()
 
 			waitCtx, waitCancel := context.WithTimeout(context.Background(), 10*time.Second)
 			select {
 			case <-state.procExited:
 			case <-waitCtx.Done():
 				logger.Info("Timed out waiting for hostagent to exit after forced kill", "instance", name)
 			}
 			waitCancel()
+		}
```
And address the root cause:
```diff

-	haCmd := exec.CommandContext(ctx, rddPath, args...)
+	haCmd := exec.CommandContext(context.WithoutCancel(ctx), rddPath, args...)
```

### Design Observations

**Concerns**

- **Process lifecycle coupling `(in-scope)`**: Tying `exec.CommandContext` to the manager's context structurally breaks graceful shutdown. On context cancellation, `exec` immediately terminates the process (`TerminateProcess` / `SIGKILL`) before the graceful shutdown hook (`shutdownAllHostagents`) can run or complete its wait. This guarantees resource leaks (especially on Windows where `KillTree` cannot traverse dead parents). Detaching the context via `context.WithoutCancel` (available since Go 1.21) and manually managing termination in the shutdown hook is necessary for a robust process lifecycle.

### Testing Assessment

1. The added test `graceful service stop terminates hostagent` verifies that the PID file is removed (via `lima_instance_running`), but does not verify that the child processes (QEMU, SSH port forwarders) are actually terminated. Since `KillTree` on Windows silently fails to traverse a dead parent (returning 128), the test passes while the child processes are permanently leaked. An assertion using `wmic process` or Windows Job Objects to verify no surviving descendants exist would catch this invariant failure.
