Executive Summary ¶

The PR replaces the provision script's trailing systemctl start with an EXIT trap, so the container engine recovers whatever happens to k3s, and retries the k3s curl | sh install up to 30 times. The core mechanism is sound: the trap fires once, preserves the triggering exit code, and the subshell never re-fires it. Two gaps remain: each curl attempt carries no wall-clock deadline, and a failed k3s upgrade can restart the stale old version.

All three reviewers flagged the missing curl deadline. Codex alone surfaced the stale-upgrade path; its separate claim that the trap masks a target-start failure did not survive verification (set -e stays active inside the trap, so the failure propagates). The bash semantics behind every finding were checked against a live bash 5.3.9.

Critical Issues ¶

None.

The most dangerous candidate — "the EXIT trap masks the provision failure" — is a non-issue. When the subshell runs exit 1 after 30 attempts, set -e aborts the parent, the trap fires with $?=1, runs systemctl start --no-block, and the script still exits 1. Lima records the provision failure while the engine recovers, exactly as intended (verified on bash 5.3.9).

Under pipefail the pipeline fails when either curl or the k3s installer (sh -) returns non-zero. Design Observations ¶

Concerns

  • The engine is down for the entire k3s retry window (in-scope) Claude Codex — systemctl stop at line 59 takes the engine down, and the trap restarts it only when the script exits. Every k3s retry extends the engine outage. For the common transient (a few fast retries) this costs seconds, but it couples engine availability to k3s install time — the opposite of the independence this PR argues for. Bounding each curl attempt (I1) caps the coupling; restarting the engine service directly after the enable/disable block, before the k3s work, would remove it, at the cost of a second restart path.

Strengths

  • The EXIT trap covers every abort path — systemctl stop (line 59), the engine enable/disable (lines 63-66), and the k3s subshell — not just the k3s case, and it is registered (line 57) before the first command that can fail.
  • if (( attempt >= 30 )) avoids a real trap: a bare (( ... )) that evaluates false returns status 1 and would abort under set -e; the if condition is exempt.
  • The ( ... ) subshell resets the EXIT trap to default, so the engine restarts exactly once (verified), not once per subshell exit.
  • curl -fsS surfaces the HTTP error on failure while -s keeps the progress meter out of the log.

Testing Assessment ¶

No automated test covers the change; the author documents this choice (see Acknowledged Limitations). The stated rationale — that a mocked harness would exercise only trap ... EXIT — is broader than the change warrants. A bash-level test that extracts the script with curl and systemctl stubbed on PATH would drive the actual control flow, not just bash internals.

Untested scenarios, highest risk first:

  1. Failure path leaves the engine down — with curl always failing, assert the script invokes systemctl start --no-block rancher-desktop.target and exits non-zero. This is the regression guard for the bug being fixed.
  2. Failed upgrade restarts stale k3s (I2) — with an old k3s.service want present and the reinstall failing, assert the App does not settle against the old version.
  3. Retry-then-succeed — a curl stub that fails N times then succeeds yields one install and no engine-down end state.
  4. Hung network (I1) — a stubbed slow curl confirms each attempt is wall-clock-bounded.

No provision-script test harness exists under bats/ today, so adding one is real work — but the rationale should be narrowed rather than stated as "only basic bash."

The added comments (lines 53-57, 79-82) explain why: the engine's independence from k3s and the early-boot routing race. The --no-block/probe claim at lines 55-56 matches the probe at lines 109-135, and line 107 is an accurate breadcrumb where the old systemctl start lived. Review Process Notes ¶

Skill improvements

  • When a change adds or moves a command into a bash trap '...' EXIT handler, verify the exit-code and option semantics against a live shell before flagging any masking or propagation claim. The trap runs with set -e/pipefail still in effect; the shell exits with the status that triggered the trap unless a command inside the trap itself fails under set -e; and a ( ) subshell resets traps to default, so an exit inside it does not re-fire the parent's EXIT trap. Findings that assert a trap masks, changes, or double-fires an exit status sound high-confidence and are frequently wrong — a two-line bash -c reproduction settles them.

Repo context updates

  • [repo] k3s readiness in the App's kubernetes reconciler is established by a /healthz probe alone; it does not verify the running server version against the requested KUBERNETES_VERSION. The provision script wires k3s into rancher-desktop.target with add-wants, which creates a persistent .wants symlink that survives across boots. When reviewing version-change or reinstall paths, check that a failed in-VM upgrade cannot leave the previous k3s version running and still satisfy readiness — the symlink and the running binary both outlive a failed reinstall.
