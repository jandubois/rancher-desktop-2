## Design Observations

### Concerns

- **Nothing enforces the nil-receiver rule** (future) [Claude Opus 5.5, Gemini 3.5 Flash]. `MirrorName` calls `MirrorPrefix()` on a zero `T` (`rdd/pkg/util/api/mirror_name.go:36-37`). `api.MirrorName[api.MirrorNameType]("My_Vol")` compiles and panics with a nil dereference, and a pointer type whose `MirrorPrefix` has a value receiver would panic the same way. No caller does either today. Claude proposed `func MirrorName[E any, T interface{ *E; MirrorNameType }]` with `T(new(E)).MirrorPrefix()`, so callers write `api.MirrorName[containersv1alpha1.Volume](…)` and `T` is inferred. My probe confirmed that form returns the same name as today and rejects the interface type argument at compile time.
- **`client.Object` in the constraint is more than `MirrorName` uses** (future) [Claude Opus 5.5, Gemini 3.5 Flash]. It gives `pkg/util/api` its first controller-runtime import and makes the test type embed a `ConfigMap`. It also restricts the helper to API objects, which may be the point.

### Strengths

- **Each prefix is on the type it names** (in-scope) [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]. The `"cns"` literals in two webhooks and the mock controller are gone, and so is `composeMirrorName`, the constant PR #831's author wanted to fix.
- **No mirror name changes** (in-scope) [Claude Opus 5.5, Codex GPT 6 Astra]. Every call site keeps its hash inputs, including `(ev.ID, e.Namespace)` for containerd containers, `(id, tag)` for Docker images, and the `ns\x00name` join for containerd images, so mirrors a previous build stored keep their names.

##### Design Observations

**Concerns**

- **The nil-receiver contract is documented, not enforced (future).** `MirrorName` calls `MirrorPrefix()` on a zero `T` (`mirror_name.go:36-37`). Two kinds of `T` panic:
  - `T` is an interface type. `api.MirrorName[api.MirrorNameType]("X_Y")` compiles and panics with a nil dereference; I confirmed this with an overlay probe.
  - `T` is a pointer to a struct whose `MirrorPrefix` has a value receiver. `mirror_name.go:24-25` warns about this case, but nothing enforces it.

  No current caller does either, and all six implementations use pointer receivers.

  An alternative constraint, `func MirrorName[E any, T interface{ *E; MirrorNameType }](name string, extras ...string) string` with `prefix := T(new(E)).MirrorPrefix()`, has two benefits. It rejects both panicking forms at compile time, and it removes the "can be called with nil" rule from the interface. Callers would write `api.MirrorName[containersv1alpha1.Container](...)`, and `T` is inferred.

  Requiring `client.Object` in `MirrorNameType` is also more than `MirrorName` uses. It is why the test type embeds a `ConfigMap`. It does restrict the helper to API types, which appears intentional.

**Strengths**

- Putting each prefix on the API type ties it to the resource it names. A caller can no longer pass a mismatched prefix string. The earlier `"cns"` literals in two webhooks and the mock controller are gone.
- The change is behavior-neutral. Prefixes and hash inputs (`(ev.ID, e.Namespace)`, `(id, tag)`, the containerd `ns\x00name` join) are unchanged at every call site, so already-stored mirror names stay valid.

##### Design Observations

###### Concerns

- **Embedding `client.Object` in `MirrorNameType` adds an unnecessary framework dependency** `(in-scope)`: `MirrorNameType` (`mirror_name.go:21-27`) embeds `client.Object`, but `MirrorName` never invokes any `client.Object` methods (`GetName`, `DeepCopyObject`, etc.). ###### Strengths

- **Compile-time enforcement of mirror prefixes**: Consolidating prefixes (`"ctr"`, `"cns"`, `"img"`, `"vol"`, `"cmp"`) onto resource types and using `api.MirrorName[T]` eliminates scattered private constants and raw string literals (`"cns"` in `image_pull_request_webhooks.go` and `mock/container_namespace_reconciler.go`), ensuring all call sites use canonical prefixes matching their resource schema.

##### Acknowledged Limitations

- **Nil pointer receiver requirement for `MirrorPrefix()`** (`rdd/pkg/util/api/mirror_name.go:23-25,35`):
  > `// Implementations must take a pointer receiver, and can be called with it being nil.`
  > `var t T // Nil T, but MirrorPrefix must support this.`
  The author explicitly notes that `MirrorPrefix()` must be callable on a typed nil pointer receiver `var t T`. Because Go cannot enforce receiver types on interface definitions, an implementation using a value receiver would compile but panic at runtime if invoked on a nil pointer. All production types follow this rule with pointer receivers (`(*Type) MirrorPrefix()`).
