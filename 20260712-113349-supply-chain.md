## Pinned dependencies

### Go modules

Four modules — `rdd/` (436 direct requirements), `src/go/i18n-report`, `src/go/startup-profile`, `src/go/wix-helper` — each with a committed `go.sum`, so the toolchain checks every module download against the recorded hash and the public checksum database. No `go.work`, so no workspace sum file to worry about.

The 36 `replace` directives in `rdd/go.mod` all resolve to concrete versions rather than local paths or floating branches. Two point at forks: `github.com/containerd/ltag` → `github.com/mook-as/ltag` at a pseudo-version, and `github.com/lima-vm/lima/v2` → `github.com/rancher-sandbox/lima/v2` at a pseudo-version pending upstream `lima-vm/lima#4998`. `go.sum` hashes both like any other module; the fork itself is the trust decision, not the pinning.

### Node

A single `yarn.lock` (yarn-berry) covers the root `package.json` plus the two nested manifests (`pkg/rancher-desktop/sudo-prompt`, `pkg/rdd-client/gen`). All 1672 installable descriptors carry a checksum; the 78 skipped entries are platform-conditioned descriptors that never fetch on this platform. `.yarnrc.yml` sets `enableScripts: false`, so package lifecycle scripts never run on install — hardening beyond pinning.

### GitHub Actions

All 85 external `uses:` references carry 40-character commit SHAs, with the version in a trailing comment so Dependabot can still bump them. The remaining 25 references are local (`./.github/actions/...`) composite actions. This is the strongest part of the repo's posture.

### Custom version+digest manifest

`pkg/rancher-desktop/assets/dependencies.yaml` records a version plus a per-artifact `sha256:` map for 9 of its 11 entries (Docker CLI, Buildx, Compose, credential helpers, ECR credential helper, Electron, Helm, Steve, WiX). Every download path in `scripts/dependencies/*.ts` passes the stored digest through `lookupChecksum()` into `download()`, which hashes the received bytes and throws on mismatch (`scripts/lib/download.ts:117-123`); the cache-hit path re-hashes the file on disk rather than trusting its existence. `parseSha256Checksum()` rejects anything other than `sha256:<64 hex>`, so a truncated or malformed digest fails at parse rather than silently skipping verification.

The two entries with `checksums: {}` are genuine no-ops rather than gaps: `golangci-lint` is never downloaded (it runs via `go run …/golangci-lint@v<version>`, which the Go module proxy and checksum database verify), and `check-spelling` delegates to `scripts/spelling.sh` — which is itself an open issue below.

`.github/workflows/rddepman.yaml` keeps the manifest current, and rddepman cross-checks each new artifact against the upstream `sha256sum`/`sha512sum` sidecar before recording a digest (`scripts/lib/dependencies.ts:213-258`), so a bump does not launder whatever bytes the CDN happened to serve.

## Open issues

### Fetch-and-execute (critical)

- `scripts/windows-setup.ps1:49` — `Invoke-WebRequest -Uri 'https://get.scoop.sh' | Invoke-Expression` is the PowerShell form of `curl | bash`: a developer's machine executes whatever bytes that endpoint returns. Download the installer to disk, check it against a digest stored in the repo, then run it (see wiki §3.5).
- `scripts/windows-setup.ps1:74` — the WSL bootstrap fetches four PowerShell scripts from `https://raw.githubusercontent.com/rancher-sandbox/rancher-desktop/main/scripts/windows/$file`, then runs `sudo-install-wsl.ps1` elevated at line 80. Two problems compound: the ref is the moving `main` branch, so anyone with push access to that branch controls the bytes; and the source is the *predecessor* project (`rancher-desktop`, not `rancher-desktop-2`), even though this repo already ships the same four files under `scripts/windows/`. Use the local copies (`$PSScriptRoot/windows/...`) and delete the download.
- `scripts/windows/install-wsl.ps1:39` — `Invoke-WebRequest -Uri https://wslstorestorage.blob.core.windows.net/wslblob/wsl_update_x64.msi -OutFile $wslMsiFile`, followed by `msiexec /i` at line 40, installs an MSI elevated. The URL carries no version, and TLS to the CDN alone vouches for the bytes. Record the expected sha256 and check it before invoking `msiexec`, or verify the MSI's Authenticode signature.

### Container images

- `.github/workflows/smoke-test.yaml:227` — the `smoke-test-installer` matrix names its four job containers by floating tag: `registry.opensuse.org/opensuse/tumbleweed:latest`, `.../leap:latest` (line 228), `debian:latest` (line 229), `fedora:latest` (line 230). Line 233 runs each as a `container:` with `options: --privileged`, and the Rancher Desktop installer executes inside it. Add `@sha256:<digest>` to each matrix entry.
- `.github/workflows/smoke-test.yaml:331` — the `smoke-test-appimage` matrix has the same shape: `registry.opensuse.org/opensuse/tumbleweed:latest` and `rockylinux/rockylinux:9` (line 332), which line 335 runs as a privileged `container:`. `rockylinux:9` is a major-version tag that floats across every point release.
- `e2e/assets/k8s-deploy-sample/nginx-sample-app.yaml:19` — `image: nginx:latest` in the e2e Kubernetes fixture. Pin to `nginx:<tag>@sha256:<digest>` so the e2e run is reproducible and a compromised upstream tag cannot swap what runs in the test cluster.
- The BATS suites leave their test-fixture images unpinned: `rdd/bats/tests/32-app-controllers/engine-docker.bats:135` pulls `alpine:latest`, and the same file uses `busybox:latest` throughout. `rdd/bats/helpers/docker.bash:10` already does the right thing with `IMAGE_BUSYBOX=busybox:1.36` — extend that pattern (ideally to `@sha256:`) and route the raw `busybox:latest`/`alpine:latest` uses through the helper. These run inside the guest VM, so they rank lowest of the image findings — but at test time they still fetch unauthenticated bytes.

### Inline downloads without digest verification

- `.github/actions/setup-environment/action.yaml:45` — `curl --location --output "$bindir/yq.exe" https://github.com/mikefarah/yq/releases/download/v4.43.1/yq_windows_amd64.exe`, then `chmod a+x` and onto `PATH`. The version is pinned, the bytes are not. `yq` publishes `checksums` with each release; store the sha256 and `sha256sum --check` it (wiki §3.5).
- `.github/workflows/rdd-bats.yaml:102` — `wget --output-document=bin/jq https://github.com/jqlang/jq/releases/download/jq-1.8.1/jq-linux-amd64`, then `chmod a+x` and onto `PATH`. Same fix: jq ships a `sha256sum` sidecar with each release.
- `.github/workflows/smoke-test/install-from-repo.sh:25` — the script fetches the OBS repository signing key over HTTPS and dearmors it straight into the keyring that `signed-by=` names at line 28. The signature check then validates packages against whatever key that fetch returned, so the whole chain rests on trust-on-first-use against `download.opensuse.org`. Pin the key by comparing its fingerprint against a constant before installing it (the `gpg --show-keys` + hard-coded fingerprint recipe).
- `.github/workflows/smoke-test/install-from-repo.sh:44` — `zypper --non-interactive --gpg-auto-import-keys install` imports the repository's signing key with no fingerprint check — the zypper form of the same TOFU gap. The `addrepo` at line 43 fetches the `.repo` file over HTTPS unverified as well.

## Retro: dependency types not explicitly covered

**R1. GHA matrix `include:` entries that feed a `container:`/`services:` image are invisible to the image scanner.**

1. **What was seen** — `.github/workflows/smoke-test.yaml:227-230` declares `- { id: debian, image: "debian:latest" }` and three siblings; line 233 consumes them as `container: image: ${{ matrix.image }}` with `--privileged`. The scan bucketed lines 233 and 335 into `templated_image_refs[]` (advisory, "resolve the template to judge pinning") and never surfaced the six floating tags — the summary table reported exactly one container image in the whole repo.
2. **Why current rules missed it** — the `image:` detector matches a YAML key at the start of a line; these are inline flow-mappings (`{ id: …, image: "…" }`) inside a `matrix.include` list, so they never enter `k8s_image_lines[]`/`ci_image_lines[]`. The consuming line is templated, so it lands in the advisory bucket, and Phase 3 explicitly says to skip that bucket.
3. **Proposed skill change** — in `inventory.py`, when a templated `image:` value is exactly `${{ matrix.<key> }}`, resolve `<key>` against the same job's `strategy.matrix.include[]` entries (and any top-level `matrix.<key>` list) and emit one `ci_image_lines[]` entry per literal, anchored at the matrix line rather than the consuming line. Match `image:\s*["']?([^"'\s},]+)` inside flow-mapping entries so the scan reaches inline `{ ... }` syntax. This is a misclassification: the scan reported six unpinned, privileged CI container images as zero.

**R2. PowerShell download-to-disk-then-execute is not treated as a `curl | bash` equivalent.**

1. **What was seen** — `scripts/windows-setup.ps1:76` does `Invoke-WebRequest -UseBasicParsing -Uri $url -OutFile $outFile` in a loop over four script names, and line 80 runs one of them elevated (`& $sudoPath -Step "EnableWSL-01"`). Likewise `scripts/windows/install-wsl.ps1:39` writes an MSI to disk and `msiexec /i` installs it at line 40. The scan recorded both only as `language_source_fetches[]` entries with "verifier ✗" — the same tier as a benign runtime API call — while it correctly promoted the neighbouring `IWR | iex` at line 49 to `curl_bash_equivalents[]`.
2. **Why current rules missed it** — `curl_bash_equivalents[]` matches only the piped shapes (`IWR … | iex`, `iex (IWR …)`). Writing the bytes to a file first and invoking them a few lines later is the same threat with an extra step — and the *more* common shape in real installers.
3. **Proposed skill change** — extend the `curl_bash_equivalents[]` detector: when an `Invoke-WebRequest`/`Invoke-RestMethod`/`curl`/`wget` writes to a path (`-OutFile $x`, `--output $x`, `-o $x`) and a later line within the same file invokes that path (`& $x`, `. $x`, `Start-Process $x`, `msiexec /i $x`, `bash $x`, `sh $x`, or `chmod +x $x` followed by `$x`), promote it to the top tier unless a digest check appears between the two. Track the destination variable, which the existing verifier-scan already parses for the basename match. This is a misclassification: two fetch-and-execute paths landed in an advisory bucket.

**R3. Self-fetch detection only matches this repo's own git remotes, missing predecessor/sibling repos in the same org.**

1. **What was seen** — `scripts/windows-setup.ps1:74` fetches from `https://raw.githubusercontent.com/rancher-sandbox/rancher-desktop/main/scripts/windows/$file` — the `main` branch of the *predecessor* repository. `meta.remotes` contains `rancher-sandbox/rancher-desktop-2`, so the owner matches but the repo name does not, and `self_fetch_unpinned[]` stayed empty.
2. **Why current rules missed it** — the detector compares `(host, owner, repo)` triples against the configured remotes. A moving-ref fetch from a different repo under the same owner is *worse* than a self-fetch: it is code from a project this repo no longer tracks, so nobody reviewing `rancher-desktop-2` ever sees changes to those bytes.
3. **Proposed skill change** — widen the `self_fetch_unpinned[]` match to `(host, owner)` and record the repo name in the finding, with a `same_owner_different_repo: true` flag so the report can say "sibling repo, moving ref" rather than "self-fetch". Keep the tier the same (`moving` vs `tag`). This is a misclassification: a moving-ref fetch-and-execute of org-controlled code went unflagged.

**R4. `go run <pkg>@<version>` invoked from TypeScript/JavaScript is not scanned as a run-from-network command.**

1. **What was seen** — `scripts/lint-go.ts:163-176` builds `['go', 'run', 'github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v' + version]` and spawns it. The version comes from `dependencies.yaml`, so this instance is fine — but the scan never saw it. `run_from_network[]` only found the two shell/workflow call sites.
2. **Why current rules missed it** — the run-from-network scanner reads shell, Makefile, Dockerfile, and workflow files. A command assembled as an argv array in a TS build script is the same fetch-and-execute — and exactly where a `@latest` would hide.
3. **Proposed skill change** — in the existing `language_source_fetches[]` walk (which already reads TS/JS under `scripts/`), also match the run-from-network tool names in string literals and array elements: `go run`/`go install` followed by a `<module-path>@<ref>` token, plus `npx`, `uvx`, `pipx run`, `deno run`. Emit them into `run_from_network[]` with the existing per-tool verification defaults so a floating ref becomes an open issue. This is a new detection: in any repo whose build scripts are TS/JS rather than shell, a whole class of fetch-and-execute call sites stays invisible.

**R5. `zypper --gpg-auto-import-keys` is not in the signature-bypass list.**

1. **What was seen** — `.github/workflows/smoke-test/install-from-repo.sh:44` runs `zypper --non-interactive --gpg-auto-import-keys install libxml2-tools` against the repo added one line earlier. The scan recorded the `addrepo` as a `runtime_repo_cmd` with `disabled: —` (nothing bypassed).
2. **Why current rules missed it** — the `runtime_repo_cmd` detector looks for `--no-gpg-checks`, `--allow-unauthenticated`, `--allow-untrusted`. `--gpg-auto-import-keys` leaves signature checking on, but it removes the human from the key-trust decision: zypper imports whatever key the repo serves, then validates that repo's own packages with it. That is TOFU, and reporting `disabled: —` reads as "signature checking intact".
3. **Proposed skill change** — add `--gpg-auto-import-keys` (zypper) and `--allowerasing`-adjacent auto-import flags to the `package_manager_signature_bypass[]` flag list under a distinct `kind: auto_import_key` so the report can describe it as key-TOFU rather than a disabled check. Same treatment for the shell recipe `curl <key-url> | gpg --dearmor > /etc/apt/keyrings/...` with no fingerprint comparison, which appears at line 25 of the same file. This is a misclassification: the report otherwise calls the repo's signature chain intact while the chain fetches its own root of trust unverified at install time.
