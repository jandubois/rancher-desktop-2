## Executive Summary

The PR moves RD's provision steps from the Lima template into `rancher-desktop-provision.service`, so on WSL the two `boot.sh` runs share one run of the steps inside the network namespace. The deduplication works, and the new tests check it on Windows. But the steps no longer inherit `boot.sh`'s environment, so the k3s download ignores the host's proxy (I1). And on WSL, the CI guest-log capture now starts only if `network-setup.service` succeeds (I2).

## Important Issues

I1. **The provision unit drops Lima's proxy settings, so the k3s download bypasses the host proxy** — `rdd/overlay/root/usr/local/lib/systemd/system/rancher-desktop-provision.service:16` [Claude Opus 5.5, Codex GPT 6 Astra]

```ini
[Service]
Type=oneshot
RemainAfterExit=yes
EnvironmentFile=/etc/sysconfig/rancher-desktop
ExecStart=/usr/local/libexec/rancher-desktop/provision.sh
```

Lima puts the host's proxy settings (the macOS system proxy, and the hostagent's `http_proxy` and `https_proxy`) into cidata's `etc_environment`, and `boot.sh` exports that file before it runs the `provision.system` scripts. So at the merge-base the k3s download went through the proxy. The unit gets only the systemd manager's environment and `/etc/sysconfig/rancher-desktop`. Lima also writes the settings to `/etc/environment`, but systemd doesn't read that file for services. On a network that allows traffic out only through the proxy, all 30 download attempts fail, and Kubernetes never starts.

The probe starts each build with a proxy that never answers, and only the PR's build reaches the k3s installer.

I2. **On WSL, the guest-log capture now waits for `network-setup.service`, so CI loses the journal of a failed network setup** — `rdd/overlay/root/usr/local/libexec/rancher-desktop/provision.sh:17` [Claude Opus 5.5, Codex GPT 6 Astra]

```bash

    if ! systemctl is-active --quiet rdd-journal-capture.service; then
        systemd-run --collect --unit=rdd-journal-capture /bin/sh -c \
```

Under `RDD_KEEP_LOGS`, on by default in bats, the capture copies the guest journal and `lima-init.log` to the host, so CI keeps them after the VM stops. At the merge-base it was a separate template script, and the `wsl.exe` run of `boot.sh` started it at once. Now it runs inside the provision unit, whose WSL drop-in has `Requires=` and `After=network-setup.service`. When network setup fails, the start job fails on that dependency, and the template's `|| true` hides the failure. CI doesn't set `RDD_METRICS_GUEST`, the harness's other journal dump, so nothing else saves the journal of the WSL networking failures that the capture was added for.

The block also runs under `errexit` before the EXIT trap, so a failed `systemd-run` skips provisioning.

## Suggestions

S1. **shfmt wants `==` on two moved lines** — `rdd/overlay/root/usr/local/libexec/rancher-desktop/provision.sh:39-40` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]

```bash
CONTAINERD_ACTION=$([[ ${CONTAINER_ENGINE} = containerd ]] && echo enable || echo disable)
DOCKER_ACTION=$([[ ${CONTAINER_ENGINE} = moby ]] && echo enable || echo disable)
```

Flag-less `shfmt` with the repo's `.editorconfig` (`simplify = true`) rewrites `=` to `==` in these two `[[ ]]` comparisons, and the rest of the file already uses `==`. CI lints shell only under `rdd/bats/`, so it won't flag them.

Fix: use `==` on both lines.

S2. **The test comment claims "both boot.sh runs", but the test checks only the `wsl.exe` run's start** — `rdd/bats/tests/32-app-controllers/engine-docker.bats:96-100` [Claude Opus 5.5]

```bash
# lima-init.log shows that the wsl.exe run reached the start. The script's
# xtrace logs `systemctl stop rancher-desktop.target` once per run, and the
# journal tags the unit's output with the wsl-exec identifier only when the
# drop-in runs it. So one such line under that identifier means that systemd
# ran the steps once, inside the namespace, for both boot.sh runs.
```

Line 108 shows that the `wsl.exe` run reached the start, but the test doesn't check the namespaced `lima-init.service` run. In the PR's Windows CI artifacts, `guest-journal.log` shows the namespaced run logging `+ systemctl start rancher-desktop-provision.service`, and `lima-init.log` shows the `wsl.exe` run logging it, so the claim holds today. The test would still pass, though, if the namespaced run stopped before its start, leaving one start and one run.

Fix: also assert the start line in `journalctl --boot --unit=lima-init.service`, or narrow the comment to the `wsl.exe` run.

## Design Observations

### Concerns

- (future) `RemainAfterExit=yes` keeps the unit active until the distro's systemd stops, so new settings reach the guest only through a boot from a stopped distro. Lima's WSL2 `Start` doesn't terminate a running distro. But rdd force-stops an orphaned instance, and `stopInstanceForcibly` calls `terminateWSL2Distro` (`limavm_lifecycle.go`), so today every start does begin from a stopped distro. A line in the unit's header comment naming that assumption would protect it. [Claude Opus 5.5]

### Strengths

- (in-scope) systemd merges the two WSL starts into one job, and `RemainAfterExit=` turns later starts into no-ops, so the steps run once without a namespace check in each script. The template also shrinks by about 75 lines. [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]
- (in-scope) The WSL drop-in orders the steps after `network-setup.service`, so `rancher-desktop.target` no longer starts before the namespace's network is up, the second effect that #1309 describes. [Codex GPT 6 Astra, Gemini 3.5 Flash]
- (in-scope) After a failed k3s install on WSL, the VM now stays up with the engine running, which ends the restart loop that a comment on #1309 describes. Kubernetes then waits for the next VM start, as it already did on macOS and Linux. Users will see that change, so the release notes could mention it. [Claude Opus 5.5]

## Review Process Notes

### Skill improvements

- **Code moved to another parent process**: when a change moves code to run under a different parent (a script's child becomes a systemd unit, a cron job, a container entrypoint, or a subprocess of another binary), list what the old parent passed implicitly: environment variables, `PATH`, working directory, umask, open descriptors and credentials. Check each value the moved code or its children read against what the new parent provides. A downloader reads proxy variables, for one, and a diff that only moves lines doesn't show any of this.

### Repo context updates

- [repo] A guest process that systemd runs as a service sees only the manager's environment and its own `Environment=` and `EnvironmentFile=` settings. The host proxy settings that Lima propagates through cidata's `etc_environment` reach the children of `boot.sh` and, through `/etc/environment`, login shells, but not services. Flag a guest download that runs under a unit without loading them.
- [repo] Under `RDD_KEEP_LOGS` (the bats default, and set by the smoke test), a capture streams the guest journal and `lima-init.log` to the host log dir. CI does not set `RDD_METRICS_GUEST`, so on WSL that stream is CI's only record of the guest journal. Flag a change that makes starting the capture depend on a unit whose failure it should record, such as `network-setup.service`.

`provision.sh` uses `=` for string equality in the conditional expressions on lines 39 and 40, whereas lines 44 and 85 use `==`. In bash scripts, the repository's `.editorconfig` specifies `simplify = true` for `shfmt`, which simplifies `=` to `==` inside `[[ ... ]]`. Running `shfmt -d` flags these lines.

Fix:
```diff
-CONTAINERD_ACTION=$([[ ${CONTAINER_ENGINE} = containerd ]] && echo enable || echo disable)
-DOCKER_ACTION=$([[ ${CONTAINER_ENGINE} = moby ]] && echo enable || echo disable)
+CONTAINERD_ACTION=$([[ ${CONTAINER_ENGINE} == containerd ]] && echo enable || echo disable)
+DOCKER_ACTION=$([[ ${CONTAINER_ENGINE} == moby ]] && echo enable || echo disable)
```

###### Design Observations

###### Concerns

None.

###### Strengths

- Encapsulating provisioning in a `Type=oneshot` systemd unit with `RemainAfterExit=yes` cleanly leverages systemd job serialization: concurrent activations wait on the in-flight job, subsequent starts become no-ops, and steps run strictly once.
- Using `Requires=network-namespace.service network-setup.service` and `After=network-setup.service` in the WSL drop-in ensures network interface initialization and host-switch routing complete before provisioning steps execute.
- Decoupling Lima's boot completion from provisioning success via `systemctl start rancher-desktop-provision.service || true` ensures transient k3s installation errors do not crash the VM hostagent, preserving container engine availability.
