S1. **The new focus watch runs before OK is enabled, so it never focuses OK** — `pkg/rancher-desktop/pages/FirstRun.vue:76-81` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash] (round 2 S3 unaddressed)

```ts
const unwatchPreferencesLoaded = watch(preferencesLoaded, (newValue) => {
  if (newValue && acceptBtn.value) {
    unwatchPreferencesLoaded();
    acceptBtn.value.focus();
```

Unless a `watch` sets `flush: 'post'`, its callback runs before the component re-renders. S4. **`assert_jq_raw` keeps going after a mismatch** — `rdd/bats/helpers/utils.bash:170-171` [Codex GPT 6 Astra, Claude Opus 5.5, Gemini 3.5 Flash] (round 2 I5's `local` point unaddressed)

```bash
        actual=$(jq --raw-output "${expr} | tostring" <<<"${json}") || return 1

```

`assert_equal` returns 1 on a mismatch, and the loop goes on to the next pair. A direct call still fails the test, because bats runs it under `errexit`. Under `run`, `if` or `||`, though, a later matching pair resets the status, so `run assert_jq_raw` followed by `assert_success` would pass on a mismatch. Every current caller calls it directly or passes a single pair, so no test passes wrongly today.

Line 165 still declares three names in one `local`, the point round 2's I5 raised, and line 158 misspells "interchangeable".

From round 2, confirmed this round:

###### Critical Issues

###### Important Issues

I1. **OK button auto-focus fires pre-flush while button is still disabled** — `pkg/rancher-desktop/pages/FirstRun.vue:70-76` (important, regression)

```ts
// Focus the accept button once preferences are loaded (and the controls are
// enabled).
const unwatchPreferencesLoaded = watch(preferencesLoaded, (newValue) => {
  if (newValue && acceptBtn.value) {
    unwatchPreferencesLoaded();
    acceptBtn.value.focus();
  }
}, { immediate: true });
```

Vue's default `watch` uses `flush: 'pre'`, firing before DOM updates. When `preferencesLoaded` becomes `true`, the `<button>` DOM element still retains `disabled="true"`. Browsers ignore `.focus()` on disabled elements, and `unwatchPreferencesLoaded()` immediately disarms the watcher, leaving the button permanently unfocused.

```ts repro
// .scratch/test_focus.spec.ts (run with Jest)
import { defineComponent, ref, watch, useTemplateRef, nextTick } from 'vue';
import { mount } from '@vue/test-utils';

test('watch defaults to flush pre and drops focus on disabled button', async () => {
  const Comp = defineComponent({
    setup() {
      const enabled = ref(false);
      const btn = useTemplateRef<HTMLButtonElement>('btn');
      watch(enabled, (newVal) => {
        if (newVal && btn.value) {
          btn.value.focus();
        }
      });
      return { enabled, btn };
    },
    template: '<button ref="btn" :disabled="!enabled">OK</button>',
  });
  const wrapper = mount(Comp, { attachTo: document.body });
  wrapper.vm.enabled = true;
  await nextTick();
  expect(document.activeElement).not.toBe(wrapper.find('button').element);
  wrapper.unmount();
});
```

```text repro-output
PASS .scratch/test_focus.spec.ts
  ✓ watch defaults to flush pre and drops focus on disabled button (4 ms)
```

Fix: Use `flush: 'post'` so the watcher runs after the DOM updates:

```diff
-const unwatchPreferencesLoaded = watch(preferencesLoaded, (newValue) => {
+const unwatchPreferencesLoaded = watch(preferencesLoaded, async(newValue) => {
   if (newValue && acceptBtn.value) {
     unwatchPreferencesLoaded();
     acceptBtn.value.focus();
   }
-}, { immediate: true });
```

###### Design Observations

###### Concerns

- **First-run gate keying on App existence vs. settings** `(future)`:
  Currently, first-run detection checks whether the cluster-scoped `App` resource exists. If a user closes the dialog, `ensureAppExists` has already created the `App` object (`spec.running: false`), preventing first-run from triggering on subsequent launches. An alternative mentioned in #1051 is gating on `spec.application.addPath == unset` (or an uncommitted preferences flag).

###### Strengths

- **Component extraction**: Extracting `KubernetesVersionSelector.vue` and making `EngineSelector.vue` self-contained cleanly decouples preferences logic and avoids duplicating template markup between `BodyKubernetes.vue`, `ContainerEngineGeneral.vue`, and `FirstRun.vue`.
- **Structured CLI flags**: Introducing `cliflag.EnumValue` (`rdd/pkg/cli/flag/enum.go`) standardizes enumeration parsing and validation across `service status` and `service paths`.

###### Testing Assessment

Missing tests and test gaps identified in this review:
- **I1** (Required, user would see failure): The unit test in `FirstRun.spec.ts` only tests that the button is not disabled when `commit` fails; no test asserts that the accept button actually receives DOM focus when preferences finish loading.
- **I2** (Required, user would see failure): `FirstRun.spec.ts:110-124` tests that `ensureAppExists` failure leaves the button disabled and asserts that `PreferencesAlert` is absent; a test should verify that creation failures surface user feedback.
- **S5** (Optional, build/test code): `e2e/first-run.e2e.spec.ts:48-54` tests default engine selector attributes but leaves engine switching unexercised.

###### Documentation Assessment

- `rdd/docs/design/cmd_service.md` omits `developer_mode` from the known JSON status keys (see S3).
- `rdd/docs/design/gui.md` omits the initial `rdd service status --output=json` invocation in the startup sequence description (see S4).

###### Commit Structure

The commits are logically ordered and build cleanly:
- Commits `a394ca06a` and `09d9fc5fe` cleanly extract the BATS helper and add unit tests.
- Commit messages accurately reflect their diffs after the round 2 fixes to `cab031ebd` and `0a7b008d7`.

###### Acknowledged Limitations

- **Dialog not shown on subsequent launch after closing**:
  Author comment (2026-10-24): "Closing the first-run dialog still prevents us from showing it on next run, because we need the app to exist to have settings to work with. I don't think that's avoidable."
  The implementation aligns with this by creating the App resource in `FirstRun.vue:onBeforeMount`.
- **Path management omitted**:
  Issue #1051 tracks path management, but the backend is not yet ready. The selector remains intentionally commented out in `FirstRun.vue:24-38`.
- **Preference locking**:
  `isPreferenceLocked` stub returns `false` (`store/preferences.ts`), so locking in the dialog is deferred to #513.
