I1. The template comment says a failed script makes Lima stop the VM, but only the WSL2 driver does that¶
rdd/pkg/controllers/app/app/lima-template.yaml
            "tail -c +0 -F /var/log/lima-init.log >> \"$PARAM_GUEST_LOG_DIR/lima-init.log\""

# Start rancher-desktop-provision.service from the distro overlay. On WSL this
# script runs through wsl.exe in the root namespace, where DNS doesn't
# resolve, so the unit's drop-in runs the steps inside RD's network namespace.
# The start blocks, so Lima sees the VM as ready only after provisioning. A
# failed script makes Lima stop the VM, and a failed k3s install must not stop

Lima's WSL2 driver turns a non-zero boot.sh exit into a driver error, and the hostagent stops the VM (pkg/driver/wsl2/vm_windows.go in Lima). Under vz and qemu, boot.sh runs in lima-init.service, and the driver never sees its exit code. boot.sh still writes /run/lima-boot-done, so the hostagent's last requirement passes, and the VM keeps running with lima-init.service failed. Round 1's text said "a failed script in the wsl.exe run". The rewrite dropped that qualifier, so a reader on macOS or Linux learns a behavior those VMs don't have.

The probe boots the embedded raw distro under vz with one provision script that exits 1; qemu rests on the same hostagent code, unmeasured. The other side of the claim, a WSL VM that stops, is in #1309's CI logs (Driver stopped due to error).

- location: embedded:///distro.raw.xz

  system: false
  user: false

- mode: system

    #!/bin/bash
    exit ${code}"
"${rdd}" ctl create configmap tmpl --namespace "${ns}" --from-literal="template=${template}" >/dev/null
"${rdd}" ctl apply -f - >/dev/null <<EOF
apiVersion: lima.rancherdesktop.io/v1alpha1
kind: LimaVM
metadata: {name: ${vm}, namespace: ${ns}}

At the merge-base, the boot.sh run in the root namespace also ran the provision script, without waiting on network-setup, and its trap started the target, which started network-setup again. Acknowledged Limitations ¶

  • Declined in prior rounds:
  • Round 1's I1 has no test — declined Round 1: a proxy test needs a VM started with a proxy in rdd's environment, which no suite starts.
  • Round 1's I2 capture has no test — declined Round 1: the capture runs only in CI, and a test would need a failing WSL network setup.
  • Rulings on this code (do not re-suggest): VMs from earlier builds need a factory reset, as the PR body says. The template ignores the unit's exit status on purpose. Each WSL distro run's capture repeats earlier runs, and #1324 fixes that. The author tried --boot on the capture in this PR and dropped it, because it didn't stop the repeats. The capture stays outside the provision unit, so it also starts when network-setup fails.
  • network-setup reads /etc/sysconfig/rancher-desktop before boot.sh writes it. In the Windows CI job it started at 06:25:48, and boot.sh copied the file at 06:26:02. So a new WSL instance's first boot runs network-setup with the unit's default VM_SWITCH_LOG and NETWORK_SETUP_EXTRA_ARGS. At the merge-base, lima-init's Requires= started network-setup at boot in the same way, and the author chose to keep the boot-time start through the new multi-user.target want. Do not re-suggest dropping the want in this PR. Lima-init no longer requires network-setup on WSL, so a later change could restart it once the file exists.
  • RemainAfterExit= assumes every VM start begins from a stopped distro (stated in the unit's header comment, rancher-desktop-provision.service:1-4). This round checked that it holds. A spec.params change restarts the instance, Lima's WSL2 stopVM runs wsl.exe --terminate, and the CI journal shows the unit stopping before every new run.
