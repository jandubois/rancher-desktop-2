Executive Summary ¶

This PR restores the preferences VM Hardware tab (CPU/memory sliders) backed by the daemon's App spec and a new HostInfo resource, adds a mock HostInfo reconciler for deterministic e2e data, and generates the preferences nav/tab layout from a single table. The traced paths are correct and CI is fully green. Two real defects sit outside CI's coverage: the memory-quantity conversion crashes or truncates on valid non-whole-GiB values, and one test file no longer type-checks.

Findings converged cleanly across reviewers. The memory-quantity bug was raised by three of four agents (Codex live-reproduced the crash on a real control plane); the type regression was unique to Gemini 3.1 Pro and confirmed here by running the project's own tsc. The two Gemini reviewers share a model family, so treat their overlap as one opinion. Gemini 3.5 Flash's two headline findings (a nil-mutate panic and an infinite reconcile loop) were both refuted against the code and the green e2e run.

Design Observations ¶

Concerns

  • The applicable platform-filter mechanism is half-built (future) Claude Opus 4.8 — navItemEntry.applicable is checked by filterNavItems (item.applicable?.() ?? true), but no live entry sets it, and navItemResult<T> types every T[number]['name'] as present. Once an applicable-gated entry is added, preferencesNavItems['WSL'] is typed as defined while undefined at runtime on non-matching platforms, and a .tabs access throws. Either drop applicable until a consumer exists (YAGNI), or mark gated names optional in the mapped type so callers must null-check.
  • Type machinery is heavy for a three-item static list (in-scope) Claude Opus 4.8 — KebabCase, navItemResult, PreferenceNavTabDefaults, and a filterNavItems whose body destructures through an inline IIFE replace three literal objects. The single-table DRY goal is sound; the question is whether the generated indirection earns its complexity while the nav set stays this small.

Strengths

  • Centralizing nav names, labels, ordering, defaults, and help-key typing in preferenceConstants.ts cuts drift between the main and renderer processes. (in-scope) Codex GPT 5.6 Sol Claude Opus 4.8
  • The mock reconciler feeds deterministic limits (32 CPUs / 12 GiB), so the e2e asserts real data arriving over the watch rather than element presence alone. (in-scope) Codex GPT 5.6 Sol Gemini 3.1 Pro Claude Opus 4.8
  • watchResources/unwatchResources on the Hardware component's mount/unmount ref-counts the HostInfo watch, so it is not held open while the tab is closed. (in-scope) Codex GPT 5.6 Sol Claude Opus 4.8

Review Process Notes ¶

Skill improvements

  • When a reconciler watches a resource it also writes, do not flag an unconditional status or spec update as an infinite reconcile loop without checking whether the written content is identical in steady state. The API server suppresses no-op updates (no resourceVersion bump, no watch event), so a reconciler that writes constant values settles once it first converges. Flag the loop only when the written content varies each pass, such as a timestamp, a regenerated field, or unsorted map iteration.

Repo context updates

  • [repo] The renderer reads Kubernetes Quantity fields from the App spec (for example virtualMachine.memory, a *resource.Quantity surfaced as x-kubernetes-int-or-string) as strings that can carry a decimal coefficient (2.5Gi) or a milli-normalized form (...m), and rdd set stores such strings verbatim. Client code converting a Quantity to a number must handle a non-integer scalar (a bare BigInt(quantityToScalar(x)) throws on a fractional coefficient) and must not floor the unit division (integer BigInt division renders 2560Mi as 2 GiB). Flag BigInt() on a Quantity coefficient and integer-division truncation when reviewing resource-settings UI.
  • [repo] UPDATE the "dormant Body*.vue nav entries" entry: the Virtual Machine nav item and its Hardware tab are live in preferenceConstants.ts, not commented out. Only the Volumes, Network, and Emulation tabs, and the WSL and Container Engine top-level items, remain dormant. Findings in the Virtual Machine Hardware path are live, not latent.
