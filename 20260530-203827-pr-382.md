## Executive Summary

The PR replaces the provision script's trailing `systemctl start` with an EXIT trap, so the container engine recovers whatever happens to k3s, and retries the k3s `curl | sh` install up to 30 times. The core mechanism is sound: the trap fires once, preserves the triggering exit code, and the subshell never re-fires it. Two gaps remain: each curl attempt carries no wall-clock deadline, and a failed k3s upgrade can restart the stale old version.

All three reviewers flagged the missing curl deadline. Codex alone surfaced the stale-upgrade path; its separate claim that the trap masks a target-start failure did not survive verification (`set -e` stays active inside the trap, so the failure propagates). The bash semantics behind every finding were checked against a live bash 5.3.9.

---

## Critical Issues

None.

The most dangerous candidate — "the EXIT trap masks the provision failure" — is a non-issue. When the subshell runs `exit 1` after 30 attempts, `set -e` aborts the parent, the trap fires with `$?`=1, runs `systemctl start --no-block`, and the script still exits 1. Lima records the provision failure while the engine recovers, exactly as intended (verified on bash 5.3.9).

## Important Issues

I1. **Retry loop bounds attempts, not wall-clock — a stalled download hangs the boot** — `pkg/controllers/app/app/lima-template.yaml:84-91` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro] (important, regression)

```bash
until curl -fsSL https://get.k3s.io | sh -; do
    attempt=$((attempt + 1))
    if (( attempt >= 30 )); then
```

The counter advances only when `curl` returns. A connection refused right after restart returns fast, so the count bounds it — the targeted transient. But a half-up host-switch network that completes the handshake then drops packets leaves `curl` waiting with no deadline; one attempt can hang far longer than 30 fast ones. The engine stops at line 59 and restarts only when the script exits (line 57 trap), so a long hang prolongs the very engine-down window this PR shrinks. The repo treats a missing download deadline as an operator-facing hang.

Fix: bound each attempt.

```diff
-                until curl -fsSL https://get.k3s.io | sh -; do
+                until curl -fsSL --connect-timeout 10 --max-time 60 https://get.k3s.io | sh -; do
```

I2. **A failed k3s upgrade restarts the stale old version** — `pkg/controllers/app/app/lima-template.yaml:84-93` [Codex GPT 5.5] (important, regression)

```bash
until curl -fsSL https://get.k3s.io | sh -; do
    ...
    exit 1            # aborts the script; add-wants below never runs
done
)
systemctl add-wants rancher-desktop.target k3s.service
```

On a version change, a persistent install failure exits the subshell, so the script never reaches `add-wants` (line 93) or the kubeconfig removal (line 104). The trap then starts `rancher-desktop.target`, which still carries the `k3s.service` want from the prior install — so the old k3s binary and its stale `k3s.yaml` come back. Readiness probes only `/healthz` (`kube_reconciler.go:250`, no version check), so the App can settle against the wrong version.

Verify whether the provision script's non-zero exit already blocks settling; if it does not, the downgrade is silent. Fix: drop the k3s want before reinstalling and re-add it only on success (e.g. `rm -f /etc/systemd/system/rancher-desktop.target.wants/k3s.service` before the subshell).

## Suggestions

S1. **Retry re-runs the full installer, not just the download** — `pkg/controllers/app/app/lima-template.yaml:84` [Claude Opus 4.8] (suggestion, enhancement)

```bash
until curl -fsSL https://get.k3s.io | sh -; do
```

Under `pipefail` the pipeline fails when either `curl` or the k3s installer (`sh -`) returns non-zero. The comment scopes the retry to the download race, but a deterministic installer failure — bad version, full disk, an `INSTALL_K3S_*` misconfig — re-fetches and re-extracts the binary 30 times before giving up. The installer is idempotent, so this wastes roughly a minute and clutters the log rather than corrupting state.

Fix: download once inside the loop (`curl ... --output /tmp/k3s-install.sh`), then run the installer once outside it, so a real installer error surfaces immediately.

S2. **Comment that `exit 1` deliberately surfaces the failure** — `pkg/controllers/app/app/lima-template.yaml:86-88` [Claude Opus 4.8] (suggestion, enhancement)

```bash
if (( attempt >= 30 )); then
    echo "k3s install failed after ${attempt} attempts" >&2
    exit 1
fi
```

This `exit 1` aborts the subshell, then the parent under `set -e`; the trap restores the engine and the script still exits non-zero. The behavior is correct and deliberate, but since the PR's theme is "engine up even when k3s fails," a one-line note — the non-zero exit reports the failure to Lima while the trap handles recovery — would orient the next reader.

Fix: add that note at line 86.

## Design Observations

**Concerns**

- **The engine is down for the entire k3s retry window** `(in-scope)` [Claude Opus 4.8, Codex GPT 5.5] — `systemctl stop` at line 59 takes the engine down, and the trap restarts it only when the script exits. Every k3s retry extends the engine outage. For the common transient (a few fast retries) this costs seconds, but it couples engine availability to k3s install time — the opposite of the independence this PR argues for. Bounding each curl attempt (I1) caps the coupling; restarting the engine service directly after the enable/disable block, before the k3s work, would remove it, at the cost of a second restart path.

**Strengths**

- The EXIT trap covers every abort path — `systemctl stop` (line 59), the engine enable/disable (lines 63-66), and the k3s subshell — not just the k3s case, and it is registered (line 57) before the first command that can fail.
- `if (( attempt >= 30 ))` avoids a real trap: a bare `(( ... ))` that evaluates false returns status 1 and would abort under `set -e`; the `if` condition is exempt.
- The `( ... )` subshell resets the EXIT trap to default, so the engine restarts exactly once (verified), not once per subshell exit.
- `curl -fsS` surfaces the HTTP error on failure while `-s` keeps the progress meter out of the log.

## Review Process Notes

**Skill improvements**

- When a change adds or moves a command into a bash `trap '...' EXIT` handler, verify the exit-code and option semantics against a live shell before flagging any masking or propagation claim. The trap runs with `set -e`/`pipefail` still in effect; the shell exits with the status that triggered the trap unless a command inside the trap itself fails under `set -e`; and a `( )` subshell resets traps to default, so an `exit` inside it does not re-fire the parent's EXIT trap. Findings that assert a trap masks, changes, or double-fires an exit status sound high-confidence and are frequently wrong — a two-line `bash -c` reproduction settles them.

**Repo context updates**

- [repo] k3s readiness in the App's kubernetes reconciler is established by a `/healthz` probe alone; it does not verify the running server version against the requested `KUBERNETES_VERSION`. The provision script wires k3s into `rancher-desktop.target` with `add-wants`, which creates a persistent `.wants` symlink that survives across boots. When reviewing version-change or reinstall paths, check that a failed in-VM upgrade cannot leave the previous k3s version running and still satisfy readiness — the symlink and the running binary both outlive a failed reinstall.

