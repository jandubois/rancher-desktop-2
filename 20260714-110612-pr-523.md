S1. **`Reconcile` populates a `HostInfo` under any name and logs on every no-op pass** — `rdd/pkg/controllers/rdd/hostinfo/controllers/hostinfo_controller.go:41` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro] (Round 4 S1, unaddressed)

```go

	if err := r.Get(ctx, req.NamespacedName, &hi); err != nil {
		if apierrors.IsNotFound(err) && req.Name == SingletonName {
```

The name guard covers only the NotFound path. A `HostInfo` under any other name still reaches line 60 and gets a fully populated Status, contradicting the type doc ("exactly one instance named `system`"), and `log.Info("Updated HostInfo status", …)` at line 64 fires on every reconcile, including the empty-patch convergence pass that follows each real write.

Fix: return early when `req.Name != SingletonName`, and skip the patch and the log when the Status already matches.

S2. **`RDD_VM_CPUS` is parsed on every admission request, not once at construction** — `rdd/pkg/controllers/app/app/controllers/app_defaulter.go:100` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro] (Round 4 S2, unaddressed)

```go

		n, err := strconv.Atoi(val)
		if err != nil || n < 1 {
			return fmt.Errorf("invalid %s value %q: want a positive integer", vmCPUsEnv, val)
		}
```

`NewAppDefaulter`'s own doc states the convention: parse config once "so that a malformed JSON fixture causes controller startup to fail rather than the first admission request." The daemon's environment is frozen at spawn, so re-reading per request buys nothing, while a typo lets the control plane come up ready and then deny every App write.

Fix: resolve the override once in `NewAppDefaulter` and return the parse error from the constructor.

S3. **The env default is clamped; the spec field is rejected** — `rdd/pkg/controllers/app/app/controllers/app_defaulter.go:107` [Claude Opus 4.8, Gemini 3.1 Pro] (Round 4 S3, unaddressed)

```go
	if hostInfo.CPUs > 0 && cpus > hostInfo.CPUs {
		cpus = hostInfo.CPUs
	}
```

`RDD_VM_CPUS=8` on a four-core host is silently reduced to 4, while `spec.virtualMachine.cpus=8` is rejected outright by the validator. The clamp is deliberate and keeps the mutator from writing a value its own validator would reject, so the asymmetry is defensible — but `environment.md:18` still calls the variable an "override", which is the wrong word for a clamped default.

Fix: clamp only the built-in default and either reject an over-large override or log the reduction; fold the wording into I1.

S4. **The "preserves other fields" test sets no VM property** — `rdd/bats/tests/32-app-controllers/virtual-machine.bats:59` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro] (Round 4 S4, unaddressed)

S5. **`--for=create` returns before the Status is populated** — `rdd/bats/tests/32-app-controllers/virtual-machine.bats:25` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro] (Round 4 S5, unaddressed)

`bootstrapSingleton` creates the object with an empty Status and a follow-up reconcile fills it, so `--for=create` is satisfied by the bare object. The next test reads `.status.cpus` and races that write. The window is small but real.

S6. **A comment describes a Lima fallback the defaulter forecloses** — `rdd/pkg/controllers/app/app/controllers/app_controller.go:128` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro] (Round 4 S6, unaddressed)

```go

	// the spec drives them directly. Lima falls back to its own default when a
	// key is absent, which covers the unset case (cpus 0, memory nil).
```

With `failurePolicy: Fail` and the defaulter registered for Create and Update, no App reaches the reconciler with `cpus == 0` or `memory == nil`. The comment presents the unset case as a supported path; were it ever reached, Lima's own defaults differ from the values the webhook writes, so the VM would be sized differently and silently.

Fix: say that the webhook guarantees both fields, and that the guards cover only the bypassed case.

S7. **`omitempty` on `HostInfoStatus` erases "detected zero" from "not reconciled"** — `rdd/pkg/apis/rdd/v1alpha1/hostinfo_types.go:19` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro] (Round 4 S7, unaddressed)

```go
	CPUs int `json:"cpus,omitempty"`
	// memory is the total host RAM in bytes.
	// +optional
	Memory int64 `json:"memory,omitempty"`
```

Should `Detect()` ever return 0, `.status.memory` is omitted rather than reported as `0`, so a GUI client cannot tell a detection failure from an un-reconciled singleton. Both cases also silently disable the validator's upper bound (`app_webhook.go:84,94`).

Fix: drop `omitempty` on the Status fields, and log a warning when either reading is zero.

S8. **`rdd set virtualMachine.memory=` puts a JSON `null` in the App create body** — `rdd/cmd/rdd/set.go:356` [Claude Opus 4.8]

```go
	createSpec := specMap
	if dryRun {
		// Create with required defaults only; patch carries the real values.
		createSpec = make(map[string]any)
	}
```

`coerceValue` returns `nil` for an empty quantity so the field's null clears it on a patch. On a create, `createSpec` carries that same map, so a first-ever `rdd set virtualMachine.memory=` sends `{"virtualMachine":{"memory":null}}`, which the CRD schema rejects for an int-or-string field. It works today only because the mutating webhook overwrites the null before schema validation runs — the apiserver runs mutating admission first. No test covers this shape; `local_setup_file` always creates the App first.

Fix: prune nil entries from `createSpec` — a create has nothing to clear.

S9. **`HostInfo.Status.Memory` is raw bytes while the App spec field is a Quantity** — `rdd/pkg/apis/rdd/v1alpha1/hostinfo_types.go:22` [Claude Opus 4.8]

The GUI must compare an `int64` ceiling against a `resource.Quantity`, and the printer column renders `16719126528` instead of `15564Mi`.

Fix: make it a `*resource.Quantity` (BinarySI) so both sides speak one representation. K8s API convention also prefers `int32` over `int` for `CPUs`.

S10. **The bats suite hard-codes values the validator bounds by the host** — `rdd/bats/tests/32-app-controllers/virtual-machine.bats:46` [Codex GPT 5.5]

```bash
    rdd set --wait=false virtualMachine.cpus=2
```

`cpus=2` and `memory=4Gi` (line 53) both exceed the validator's ceiling on a small host, so the suite fails there for reasons unrelated to what it tests. CI runners are large enough today.

Fix: use the universally valid minima (`cpus=1`, `memory=2Gi`), or derive the values from `HostInfo`.

S11. **The VM's memory default now tracks the host, so CI silently loses 2 GiB** — `rdd/pkg/controllers/app/app/controllers/app_defaulter.go:129` [Claude Opus 4.8]

```go
	memBytes := hostInfo.Memory / 4
	if memBytes > maxDefaultMemoryBytes {
		memBytes = maxDefaultMemoryBytes
	}
	if memBytes < minMemoryBytes {
		memBytes = minMemoryBytes
	}
```

`lima-template.yaml` hard-coded `memory: "6442450944"` (6 GiB) for every install until this PR deleted it, so the effective default now falls to `min(6 GiB, host/4)` on any host below 24 GiB. This is deliberate: it reproduces RD1's `getDefaultMemory()` (`pkg/rancher-desktop/config/settingsImpl.ts:166`), which returns `Math.min(6, Math.round(totalMemoryInGB / 4.0))`. Aligning with RD1 is the right call, and CI now exercises the size a real user gets.

The consequence still deserves a decision. The bats suites drop from 6 GiB to roughly 4 GiB on the 16 GB runners, and `.github/workflows/rdd-bats.yaml:223,236` pins `RDD_VM_CPUS` with no memory counterpart, so nothing can pin the old size if a suite starts failing. Note also that RD1 returns a flat 2 GB on Windows, where the daemon applies the 25% rule on every platform.

Fix: say so in the commit message, and consider an `RDD_VM_MEMORY` knob mirroring `RDD_VM_CPUS`.

## Design Observations

### Concerns

- **The webhooks read their own `Detect()` snapshot rather than `HostInfo.Status`** `(in-scope)` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro]. Issue #498 asks that "validation will use these saved values"; the validator instead snapshots `hostinfo.Detect()` at setup (`app/controller.go:124`), leaving `HostInfo` a resource nothing in-tree reads. The Round-4 drift hazard is genuinely gone — one `Detect()` now backs both contracts, and the package doc says so — and keeping the `app` webhook free of a cross-group dependency on `rdd` is the cheaper trade. Both agents who raised this rated it Important; it is demoted here because no divergence can occur and the reduced scope is documented in code. What remains is a contract to write down, not code to rework (I1).
- **Raising `cpus` or `memory` on a running VM changes nothing until it is recreated** `(future)` [Claude Opus 4.8]. `applySpecToTemplate` re-renders the template ConfigMap on the drift-correction path, so the ConfigMap tracks the spec, but Lima reads the template only at instance creation. A user who raises `cpus` sees no effect and no warning. A condition on `App.Status`, or a doc note, would close the loop.

### Strengths

- **The Round-4 critical is fixed correctly** `(in-scope)` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro]. `Start` now retries `bootstrapSingleton` under `wait.PollUntilContextCancel` and swallows the cancellation, so it never returns a non-nil error. Verified against controller-runtime v0.24.1: `runnable_group.go:244-251` signals readiness from a goroutine separate from `Start`, so a blocking retry cannot stall manager startup, and a nil return never reaches `errChan`. The doc comment explains *why* the function must never fail — the comment that stops someone reintroducing the bug.
- **Host detection is centralized** `(in-scope)` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro]. `pkg/hostinfo.Detect()` is now the single computation behind both the CRD Status and the admission ceilings.
- **The defaulter stays self-consistent with its own validator** `(in-scope)` [Claude Opus 4.8]. Clamping the CPU default to the host count and returning a distinct error on a sub-2Gi host, rather than writing a value the validator would reject, forecloses the un-admittable-object class outright.

## Review Process Notes

### Skill improvements

- **When a change deletes a hard-coded default and replaces it with a computed one, compute both values for the machines that will actually run the code, and compare them.** A diff that removes a constant and adds a formula reads as a refactor, and every reviewer's attention lands on whether the formula is *correct* rather than on whether it returns what the constant did. State the old value, the new value on a typical developer machine, and the new value on each CI runner. Flag any silent reduction in a resource the software depends on — memory, timeouts, retries, disk — even when the new rule is defensible in isolation, because nothing in the diff announces the regression and no test will.

- **Before calling a comment's cited rationale false, find the code that computes the value — not the code that declares it.** A comment of the form "following X's default" is a citation, and checking it means locating X's *effective* default. A static literal in a settings or config file is frequently a fallback that a helper overrides at runtime, so a grep that lands on the literal and stops will contradict a comment that is in fact correct. Search for the function that derives the value (`getDefaultX`, a factory, an initializer) before concluding the citation is wrong. An accusation that a comment lies is a strong claim; hold it to a stronger standard of proof than the finding it supports, because a reviewer who "corrects" an accurate comment sends the author to change working code.

### Repo context updates

- **[repo]** RD1 and the daemon use the *same* VM memory rule, and it is not the static literal in the settings file. `pkg/rancher-desktop/config/settings.ts` declares `memoryInGB: 2`, but that is only a fallback: RD1's effective default comes from `getDefaultMemory()` in `pkg/rancher-desktop/config/settingsImpl.ts`, which returns `Math.min(6, Math.round(totalMemoryInGB / 4.0))` on macOS and Linux, and 2 GB on Windows. The daemon's `app_defaulter.go` reimplements that rule as `min(6 GiB, host/4)` floored at 2 GiB, on every platform. When reviewing a change to either default, read `getDefaultMemory()` — not `settings.ts` — and note that the daemon applies the 25% rule on Windows too, where RD1 does not. Note also that the daemon's VM defaults live in the admission webhook, not in `lima-template.yaml`, which no longer carries `cpus` or `memory`.

- **[repo]** CI pins `RDD_VM_CPUS` in `.github/workflows/rdd-bats.yaml` but has no memory equivalent, so the bats suites take whatever the defaulter computes from the runner's RAM. A change to the memory default silently changes what every bats suite runs against.

## Design Observations

**Concerns**

- *`HostInfo` is a write-only mirror* `(future)`. Nothing reads it. Its value is entirely prospective (the GUI, plus the future metrics Jan sketched in #498). That is fine, but it means the CRD is untested against a real consumer and the validator's ceiling and the GUI's ceiling are two independent reads of the host. Having `AppValidator` read `HostInfo.Status` through the manager cache would collapse them into one — at the cost of a hard `--controllers=rdd` dependency for the `app` group, which is probably the wrong trade. Worth writing the decision down (S1) rather than reworking.
- *Changing `cpus`/`memory` on a running VM re-renders the ConfigMap but does not resize the VM* `(future)`. `applySpecToTemplate` is called on both the create (app_controller.go:356) and the drift-correction (app_controller.go:443) paths, so the ConfigMap does track the spec — issue #498's literal requirement is met. But Lima reads the template only at instance creation, so a user who raises `cpus` sees no effect and no warning until the VM is recreated. A `VirtualMachineRestartRequired` condition (or a doc note) would close the loop.

**Strengths**

- Making the defaulter *self-consistent with its own validator* — clamping the CPU default to the host count and refusing to write a memory value the validator would reject (`app_defaulter.go:90-138`) — is exactly the right shape, and directly forecloses the "permanently un-admittable object" class the repo context warns about.
- `Start`'s retry loop carries a doc comment (`hostinfo_controller.go:76-80`) explaining *why* it must never return non-nil. That is the comment that stops someone from re-introducing Round-4 C1.

## Testing Assessment

Unit tests pass (`go test ./pkg/controllers/app/... ./pkg/controllers/rdd/...`). Untested scenarios, highest risk first:

1. **`HostInfoReconciler` has no test file at all** — neither the bootstrap-retry loop, the NotFound-recreate branch, nor the Status patch is unit-tested. The retry loop is the fix for a critical finding and is exercised only by the happy path in bats.
2. **The rendered Lima template ConfigMap is never asserted end-to-end.** `Test_applySpecToTemplate_VMResources` checks the string, but no bats test confirms that `rdd set virtualMachine.cpus=N` reaches the template ConfigMap the LimaVM controller consumes — the actual requirement in #498.
3. **The App *create* path with `virtualMachine` values is untested** — every bats case runs against an App that `local_setup_file` already created, so only `ValidateUpdate`/`Default`-on-update is covered. See S9 for the concrete shape this hides.
4. **`pkg/hostinfo` has no test file** (trivially correct, but it is now the single source for two contracts).
5. **The sub-2 GiB host error path** is unit-tested in the defaulter but has no integration coverage; nothing verifies the resulting webhook denial is legible to a user.
6. **Memory sizing under CI** (I1) — no test or assertion pins the guest's memory, so the 6 GiB → 4 GiB drop is invisible until a suite OOMs.

#### Important Issues
I1. **Missing name guard on HostInfo reconcile path** — `rdd/pkg/controllers/rdd/hostinfo/controllers/hostinfo_controller.go:42-63` (important, gap)

```go
	if err := r.Get(ctx, req.NamespacedName, &hi); err != nil {
		if apierrors.IsNotFound(err) && req.Name == SingletonName {
// ...
	info := hostinfo.Detect()

	patch := client.MergeFrom(hi.DeepCopy())

```
The guard `req.Name == SingletonName` only applies to the `IsNotFound` recreate branch. If a user creates a `HostInfo` object with any other name, `Get` succeeds, and the reconciler populates its status with the system host limits and logs `Updated HostInfo status`. Because `Patch` returns `nil` even on an empty patch, this causes spurious log spam on every periodic resync for any rogue objects. (This addresses the prior round's S1).

Fix: Short-circuit early for foreign names:
```diff
 func (r *HostInfoReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
+	if req.Name != SingletonName {
+		return ctrl.Result{}, nil
+	}
 	log := logf.FromContext(ctx)
```

#### Suggestions
S1. **`RDD_VM_CPUS` parsed per admission request** — `rdd/pkg/controllers/app/app/controllers/app_defaulter.go:88-92` (suggestion, gap)
The environment override is parsed on every admission request instead of being snapshotted at construction. A malformed value will deny all App writes at runtime instead of failing controller startup.

S2. **Env override is clamped unlike spec field** — `rdd/pkg/controllers/app/app/controllers/app_defaulter.go:94-96` (suggestion, gap)
The `RDD_VM_CPUS` override is silently clamped to the host CPU count, but an explicit `spec.virtualMachine.cpus` exceeding the host count is rejected by the validating webhook. They should behave consistently.

S3. **BATS test sets no VM property** — `rdd/bats/tests/32-app-controllers/virtual-machine.bats:66-69` (suggestion, gap)
The test "rdd set preserves other fields when setting virtualMachine properties" relies on state from previous tests and never calls `rdd set`. If preceding tests are removed or skipped, this test becomes invalid.

S4. **BATS test races Status write** — `rdd/bats/tests/32-app-controllers/virtual-machine.bats:24-32` (suggestion, gap)
`rdd ctl wait --for=create hostinfo/system` returns as soon as the object is created by `Start`. The immediately following `rdd ctl get` races the `Reconcile` pass that writes `.status.cpus`, which may cause a flaky failure if it reads an empty status.

The comment claims Lima falls back to its own default for unset `cpus 0, memory nil`. This state is unreachable because `AppDefaulter` guarantees both are populated before applying the template.

`omitempty` on `HostInfoStatus.CPUs` and `Memory` erases the difference between an unpopulated status and a detected zero. Both serialize to absent, and both silently bypass the validator's upper bound checks.
