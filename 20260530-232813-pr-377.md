## Design Observations

### Concerns

- **A handle-pinned helper would close the residual races (in-scope)** [Codex GPT 5.5, Gemini 3.1 Pro] — `IsOurProcess` verifies identity, then closes the handle before the caller signals or kills by PID, leaving a check-to-signal window. A Windows-only `InterruptIfOurProcess` / `KillTreeIfOurProcess` that holds the handle across the PID operation would close both that window and the `procExited` brief window (Round 1 S2) at once. Gemini rated the window Critical (C1); it is practically unhittable — the just-verified live hostagent would have to exit and have its PID reassigned within microseconds — so it does not gate the merge.
- **Force paths still trust persisted `DriverPID` (future)** [Gemini 3.1 Pro, Claude Opus 4.8] — the structural root of S2. `stopInstanceForcibly` taskkills `DriverPID` from on-disk state, which `IsOurProcess` cannot verify (the driver is qemu/wsl, not rdd). A Job-Object or supervisor model would remove PID-based signalling of unrelated processes entirely. Out of scope for this fix.
- **Image-path equality assumes a stable binary location across restarts (future)** [Claude Opus 4.8] — `IsOurProcess` compares the target's image to `os.Executable()`. A service restart running rdd from a moved or upgraded path rejects a genuinely-ours hostagent, so `killOrphanedHostagent` skips both signal and taskkill and relies on `DriverPID` alone. Self-healing on the next reconcile and implausible pre-release, but unstated.
- **Unix no-op leaves a cross-reboot residual (future)** [Gemini 3.1 Pro] — `HostAgentPID` read from on-disk state can outlive a reboot and resolve to a recycled live process, which the Unix no-op signals. Lima's `ReadPIDFile` auto-cleans dead PIDs on Unix (so `HostAgentPID` reads 0 for a dead process) and SIGINT carries a smaller blast radius than `CTRL_BREAK`, which is why Round 1 logged this as a doc note. Gemini re-escalated it to Critical (C3); the code is unchanged since.

### Strengths

- The handle-vs-PID split is the right model: rely on the held `os.Process` handle for in-memory paths, `IsOurProcess` only for on-disk PIDs from a prior service. Verified against Go `os/exec_windows.go` — handle release precedes the watcher's `close(procExited)`, matching the documented "brief window." [Claude Opus 4.8, Codex GPT 5.5]
- The PEB walk is correct against `x/sys@v0.43.0`: `NTUnicodeString.Length` is bytes, so `length/2` code units and the full-read check are right. [Claude Opus 4.8, Gemini 3.1 Pro]
- `IsOurProcess` fails closed — every uncertain path returns false, and callers treat false as "fall back to forced stop." [Codex GPT 5.5]

### Repo context updates

- [repo] The lima controller sets the hostagent's stdout/stderr to `*os.File` handles from `logfile.Create` (`pkg/util/logfile`, which returns `*os.File`), not pipes. Go's `os/exec` passes those descriptors to the child directly and spawns no I/O-copy goroutine, so `cmd.Wait()` returns promptly once the process is reaped and the watcher closes `procExited` immediately after. Reject claims that `cmd.Wait()` blocks indefinitely on inherited pipes for these processes, or that `procExited` lags handle release by an exploitable margin — the residual window is a few instructions, not unbounded. ### [Gemini] — Pass 1

### Executive Summary

This PR introduces process identity verification (`IsOurProcess`) to prevent sending `CTRL_BREAK` to recycled PIDs on Windows. However, the implementation introduces a Time-of-Check to Time-of-Use (TOCTOU) race by closing the process handle before signaling, allowing the PID to be recycled in the interim. Additionally, it underestimates a handle-release race in `cmd.Wait()`, uses unbounded substring matching that causes cross-instance prefix collisions, and unconditionally trusts orphaned on-disk PIDs on Unix across OS reboots.

### Findings

#### Critical Issues

**C1. TOCTOU race in PID identity verification allows targeting recycled PIDs** — `pkg/util/process/process_windows.go:28-49`

The `IsOurProcess` function is designed to prevent sending signals to recycled PIDs, but it introduces a Time-of-Check to Time-of-Use (TOCTOU) race. It opens a handle, verifies the command line, and immediately closes the handle upon return (line 33). Once the handle closes, Windows is free to recycle the PID if the target process exits. By the time the caller executes `process.Interrupt` or `stopInstanceForcibly` (e.g., `limavm_lifecycle.go:611-612`), the PID may already belong to an unrelated process. Windows only guarantees a PID will not be reused while there is at least one open handle to the process object.

Fix: `IsOurProcess` must either return the open `windows.Handle` (e.g., as an `io.Closer`) so the caller can hold it across the signal/kill operation, or merge the logic into a new `process.InterruptIfOurs(pid, substrings...)` helper that performs the check and issues the signal before closing the handle. 

**C2. `cmd.Wait()` handle release invalidates `procExited` guard against PID reuse** — `pkg/controllers/lima/limavm/controllers/hostagent_watcher.go:210-218`

The inline comment acknowledges that `cmd.Wait()` releases the process handle, but incorrectly assumes it leaves only a "brief window" before closing the channel (line 213). In Go, `os/exec.Cmd.Wait()` calls `Process.Release()` (closing the OS handle) as soon as the process exits, but it then blocks waiting for stdout/stderr copying goroutines to finish. If a child process (e.g., QEMU or port forwarders) inherited these pipes, `cmd.Wait()` blocks indefinitely. During this entire period, the handle is closed and the PID is freed, but `state.procExited` remains open. The checks in `signalHostagent` (line 215) and `shutdownAllHostagents` will proceed and send `CTRL_BREAK` to a recycled PID.

Fix: Do not rely on `procExited` to guard against PID reuse. Either use a TOCTOU-safe `process.InterruptIfOurs` here, or duplicate the process handle (`windows.DuplicateHandle`) immediately after `cmd.Start()` so the daemon retains its own open handle that prevents PID reuse until the watcher explicitly cleans up.

**C3. Unconditional `true` in `IsOurProcess` on Unix enables cross-boot recycled PID kills** — `pkg/util/process/process_unix.go:30-38`

The author assumes "PIDs are not recycled within a daemon's lifetime" and makes `IsOurProcess` a no-op on Unix (line 35). However, `killOrphanedHostagent` (line 611) reads `HostAgentPID` from the on-disk state file, which persists across daemon restarts and OS reboots. On Linux, the default maximum PID is 32768, meaning PIDs wrap quickly. If a stale PID from a previous boot is reassigned to an unrelated process (e.g., a database or `sshd`), RDD will blindly return `true` and forcefully terminate (`kill -9`) the innocent process.

Fix: Implement process identity verification for Unix. On Linux, parse `/proc/<pid>/cmdline` or `/proc/<pid>/exe`. On macOS, use `sysctl` with `KERN_PROCARGS2`. Until implemented, `IsOurProcess` should conservatively return `false` on Unix if the PID cannot be verified, which safely triggers the fallback to clear `HostAgentPID`.

**C4. Substring matching in `IsOurProcess` allows cross-instance kills via prefix collision** — `pkg/util/process/process_windows.go:43-48`

`IsOurProcess` verifies process identity by checking if `strings.Contains(cmdline, s)` is true for all substrings (line 44). If one instance is named `"vm"` and another is `"vm2"`, `"vm2"`'s command line (e.g., `--name vm2`) will falsely match the substring `"vm"`. If `"vm"`'s PID was recycled to `"vm2"`, `killOrphanedHostagent` (line 611) for `"vm"` will receive `true` and send a `CTRL_BREAK` to `"vm2"`, killing the wrong instance.

Fix: Match arguments exactly or ensure word boundaries. Parse the command line into an array using `windows.CommandLineToArgv` and check for exact element matches, or at minimum pad substrings with spaces (`" " + s + " "`).

#### Important Issues

**I1. `stopInstanceForcibly` fails to traverse children if hostagent exited gracefully** — `pkg/controllers/lima/limavm/controllers/limavm_lifecycle.go:625-627`

When `killOrphanedHostagent` successfully signals the hostagent to gracefully terminate, the hostagent process exits. The function then unconditionally calls `stopInstanceForcibly` (line 626) with the original `HostAgentPID` intact. As noted in the project conventions, Windows `taskkill /F /T /PID` does not traverse children of dead parents and simply returns exit code 128. If the hostagent left orphaned child processes behind, this backstop forceful stop will fail to clean them up.

Fix: If the graceful wait confirms the hostagent exited cleanly, clear `forceInst.HostAgentPID = 0` to skip the failing `taskkill` invocation and rely entirely on `DriverPID` for driver cleanup.

#### Suggestions

**S1. `processImagePath` buffer size may be insufficient for extended paths** — `pkg/util/process/process_windows.go:53`

The fixed `1024` character buffer for `QueryFullProcessImageName` (line 53) will fail with `ERROR_INSUFFICIENT_BUFFER` if the executable path utilizes Windows extended-length paths (up to 32,767 characters). 

Fix: Pre-allocate a buffer of `32768` `uint16`s, or loop and double the buffer size upon `ERROR_INSUFFICIENT_BUFFER`.

### Design Observations

#### Concerns
- **PID-based Lifecycle Management (future)**: Relying on PIDs for lifecycle management on Windows is inherently racy due to rapid OS PID reuse. The architecture relies heavily on signaling and killing by PID rather than utilizing Windows Job Objects. A Job Object allows the daemon to group the hostagent and all its descendants into a single managed unit, which can be cleanly tracked and terminated without PID TOCTOU races or orphaned children escaping `taskkill`.

#### Strengths
- Reading process arguments directly from the PEB is a robust, correct way to identify processes on Windows where typical command-line inspection APIs do not cross process boundaries.

### Testing Assessment

1. **Substring collision in `IsOurProcess`**: Test `IsOurProcess` with a command line containing `--name vm2` and a target substring `"vm"` to verify exact-match behavior. The current suite asserts a complete mismatch (`"substring-that-cannot-appear..."`) but misses prefix overlaps. (High risk)
2. **Handle Release Window (`cmd.Wait`)**: The `hostagent_watcher` integration tests should mock a child process that holds stdout open after exiting to reproduce the prolonged handle-release window.

### Documentation Assessment

The package documentation in `pkg/util/process/process_unix.go` incorrectly claims that PIDs are not recycled within a daemon's lifetime as a justification for skipping identity checks. This must be updated to account for orphaned PIDs persisting across reboots via state files once Unix verification is implemented.

### Acknowledged Limitations

- **Code comment**: `// DriverPID is not covered by IsOurProcess and remains trusted there.` (`limavm_lifecycle.go:228-231`). The change does not implement identity checks for the driver process, leaving it vulnerable to PID reuse kills, but limits the immediate blast radius to the VM driver.
- **PR comment**: @jandubois reverted the `IsOurProcess` check on paths where an open handle is retained (e.g., `signalHostagent`), stating "the cases where we still have an open handle... should be good now." However, as detailed in **C2**, `cmd.Wait()` actively releases the handle before `procExited` is closed, meaning the handle is no longer open and the rationale no longer holds.
