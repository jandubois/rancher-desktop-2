- **spec.namespace**: The namespace where the owned `LimaVM` and its ConfigMaps are created. Defaults to `default`. **Immutable after creation** — changing it would orphan resources in the original namespace.

- **spec.running**: Set to `true` to start the LimaVM, `false` to stop it. The App controller propagates this value to `LimaVM.spec.running` on every reconcile.

**spec.containerEngine.name**: The container engine to use inside the VM. Valid values: `moby` (Docker-compatible, default) and `containerd`. Propagated to the `CONTAINER_ENGINE` Lima template param.

- **spec.kubernetes.enabled**: Whether Kubernetes should be enabled in the VM. Defaults to `false`. Propagated to the `KUBERNETES_ENABLED` Lima template param.

- **spec.kubernetes.version**: The Kubernetes version to use (e.g. `"1.30.2"`). Defaults to `"1.30.2"`. Propagated to the `KUBERNETES_VERSION` Lima template param.

- **status.kubernetesPort**: The host TCP port allocated for the k3s API server (`7441 + instance.Index()` by default). Set by the App reconciler on the first reconcile after `spec.kubernetes.enabled` becomes `true`, and cleared when `spec.kubernetes.enabled` is set back to `false` so that a fresh port is resolved on the next enable. The `KUBERNETES_PORT` Lima template param is set to this value; Lima's identity port-forward rule binds the same port on the host and forwards it to the guest.

- **status.conditions**: Multiple controllers write here. The App controller mirrors `Created` and `Running` from the owned `LimaVM` and computes `Settled`, the engine controller writes `ContainerEngineReady`, and the Kubernetes controller writes `KubernetesReady`. All writers use `retry.RetryOnConflict` with a re-Get so concurrent status updates do not 409.

Design Observations ¶

Concerns ¶

  • A controller in the rdd group can now take down the app, lima, and containers controllers (in-scope) Claude. All of them share one SharedControllerManager, and a Runnable error is manager-fatal. Before this PR no controller could fail the manager after startup. Beyond fixing C1, the rule is worth writing down: a manager.Runnable added by a controller must never return a non-nil error outside shutdown, because the blast radius is every sibling controller.
  • The HostInfo CRD is written but never read by the code that motivated it (in-scope) Claude Codex Gemini. Issue #498 asks that validation use the saved values and that the GUI fetch them from the same place. The GUI half landed; the validation half did not, leaving a rdd-group controller whose only consumer is out-of-tree (see I2). A shared pkg/hostinfo.Detect() is the cheaper fix and keeps the App webhook free of a cross-group dependency; having the webhook read HostInfo.Status is the fuller one and costs an app→rdd dependency. Either is defensible — worth stating the choice in api_app.md.

Strengths ¶

  • The defaulter is now provably self-consistent (in-scope) Claude Codex Gemini. Walking the full input range confirms it: the CPU clamp bounds the default by hostInfo.CPUs; mem/4 is bounded above by host memory and floored at 2Gi, which never exceeds a host that passed the sub-2Gi check; and both clamps are guarded on a positive reading, so a zero HostInfo falls through to values the validator accepts. Returning a distinct "host below the minimum" error rather than writing an un-admittable default is exactly what Round 3 asked for.
  • Defaulting in the mutating webhook (in-scope) Claude Codex. Keeping zero-value handling in admission lets rdd set, the reconciler, and the template writer treat cpus/memory as plain values.
  • Appended YAML replaced the regex rewrite (in-scope) Claude Codex Gemini. This removed applyVMCPUsOverride and its "no cpus line" failure mode outright.

Testing Assessment ¶

The Go unit suite passes (Codex ran it, and go mod tidy -diff is clean). The defaulter's new table cases cover both clamp paths and the sub-2Gi error. Gaps, ranked by risk:

  • HostInfoReconciler has no tests at all. The two behaviors this commit added — the NotFound recreate branch and the error-returning Start — are precisely the code C1 and I1 flag as wrong, and nothing exercises either. A fake-client test asserting that a failing Create does not surface as a manager-fatal error would have caught C1 directly.
  • AppValidator.validateVirtualMachine has no unit test. There is no app_webhook_test.go, so the negative, zero, and host-ceiling boundaries are exercised only through bats against the live host's real CPU count.
  • No test drives the defaulter and validator together. The clamp makes the contradiction structurally impossible now, but nothing pins that invariant against a future edit to either side.
  • ValidateCreate is never exercised. Every bats rejection case patches an existing App (Update).
  • Nothing asserts the defaulted values reach the Lima template — the PR's actual user-visible promise.
  • The bats suite depends on inter-test ordering (S4) and races the Status write (S5).

No agent ran the bats suite this round.

Documentation Assessment ¶

  • environment.md:18 and api_app.md are stale, and cmd_app.md:3 still advertises a --cpus shorthand that the CLI does not implement (I3).
  • No document describes HostInfo, though it is explicitly a GUI-facing contract.
  • Two code comments actively mislead: the Start comment claims a restart that never happens (C1), and the recreate-branch comment claims a recovery path that cannot fire (I1). Both are load-bearing — they are the stated reasons the design is sound.

Review Process Notes ¶

Skill improvements ¶

  • When a fix hands an error to a framework, verify what the framework does with it and what the process does afterwards. Returning an error is a claim about the caller, not the callee. A change that replaces "log and continue" with "return the error so the caller retries/restarts/surfaces it" only improves things if a caller actually retries, restarts, or surfaces it. Read the registration site to learn which callback contract the function satisfies, read the framework's handling of a non-nil return, and read the application's handling of the framework's own return value. Flag any path where the error escalates past the failing component's blast radius — a local degradation converted into a process-wide or subsystem-wide abort is a regression, even when the diff reads as hardening and the commit message calls it a fix.
  • Treat a comment that explains why something is safe to omit as a claim to verify, not as context to accept. Comments that justify an absence — no requeue because "the next reconcile will retry", no lock because "only one goroutine reaches this", no check because "the caller already validated" — are load-bearing: if the justification is false, the omission is the bug. Locate the mechanism the comment names and confirm it exists and can fire on the path described. A rewritten comment that replaces one such claim with another deserves the same scrutiny as the original, because a fix that corrects the code but keeps the reasoning style often just relocates the false claim.
  • When the change under review deletes or renames a construct that checked-in documentation describes, the resulting documentation error is a defect the change introduced, not a pre-existing gap. Rate it as a finding against this change rather than carrying it as a standing docs suggestion, and quote the now-false sentence. Documentation that contradicts shipped behavior misleads more than absent documentation.

Repo context updates ¶

  • [repo] A manager.Runnable registered with mgr.Add() is manager-fatal in this repo. When its Start returns a non-nil error, controller-runtime aborts mgr.Start and stops every controller in the SharedControllerManager — app, lima, containers, rdd. pkg/service/cmd/service.go only logs that error and lets its goroutine return, while rdd svc serve stays blocked on <-ctx.Done(), and MarkControlPlaneReady has already fired by then. The result is a daemon that reports a healthy control plane while running zero reconcilers. Never accept "return the error so the manager retries it" or "so the daemon restarts" as a recovery mechanism here: the manager does not retry Runnables, and nothing restarts the daemon. A bootstrap Runnable must retry internally and return nil.
  • [repo] rdd ctl wait --for=create <resource> is satisfied by the bare object, before any controller populates its .status. A bats test that waits for create and then reads a status field races the reconciler that fills it. Gate on the status instead — rdd ctl wait --for=jsonpath='{.status.<field>}' <resource>.
