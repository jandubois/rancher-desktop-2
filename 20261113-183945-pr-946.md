## Suggestions

S1. **A deleting project with a gone member waits up to 10 minutes for the rescan, and a successful `down` reruns every second meanwhile** — `rdd/pkg/controllers/containers/compose/compose_reconciler.go:281-287` [Claude Opus 5.5, Gemini 3.5 Flash]

```go
	case hasState && len(project.Status.Containers) > 0:
		// `docker compose down` has finished, but there are still members.  Remove
		// the state, and pause for a second; normally, this should be enough time
		// to reconcile the members away.  If there are actual containers remaining,
		// however, the retry will handle that.
		r.procs.delete(project.GetUID())
		return ctrl.Result{RequeueAfter: reconcileRetryDelay}, nil
```

The rescan fixes round 2's I1, since deletion now finishes. Until the first tick, 10 minutes after rdd starts (line 59), both of round 2's variants remain. A successful `down` reaches this case, which requeues after a second, and the next pass starts `down` again. A failed `down` falls back to deleting the member Containers, which are already gone, and returns without a requeue, so the project waits for the tick. The only route found to a gone member is rdd exiting with Container deletions still queued, so such a deletion waits about 10 minutes after rdd restarts.

Fix: call `recalculateContainers` after either outcome, so a project whose members are all gone moves to HasMembers=False at once. With that change, a probe ran `down` once and finished both variants without a rescan, and the suite passed under `-race`. Emitting one rescan at startup also covers the known route.

S2. **A stale cached read can restart the running `docker compose up`** — `rdd/pkg/controllers/containers/compose/compose_up_request_reconciler.go:84` [Codex GPT 6 Astra, Claude Opus 5.5]

```go
	case settled != nil && settled.Status == metav1.ConditionTrue:
		if settled.ObservedGeneration < upReq.Generation {
			// The settled condition is for an older generation; treat it as not settled.
			return ctrl.Result{}, r.initiateUp(ctx, &upReq)
		}
```

After a spec update, this branch starts `up` and writes Settled=False. A reconcile queued meanwhile can read the cached object before that write reaches the informer. It finds the old Settled condition, ignores the tracked process from line 80, and `run` kills the new `up` and starts another. A probe that injects one stale read starts `up` twice, and a fresh read starts it once. Round 2's resourceVersion check in `run` caught only a re-read of the same object version, so after any intervening write, round 2's tree would have restarted `up` the same way. The window is milliseconds, and the restarted `up` converges.

Fix: take this branch only when `!hasState || state.generation < upReq.Generation`. With that guard the probe starts `up` once, and the suite passes under `-race`.

S3. **`recalculateContainers` returns NotFound, so one vanished project fails the whole rescan** — `rdd/pkg/controllers/containers/compose/compose_reconciler.go:331-333` [Claude Opus 5.5, Gemini 3.5 Flash]

```go
		var latest v1alpha1.ComposeProject
		if err := r.Get(ctx, req.NamespacedName, &latest); err != nil {
			return err
		}
```

A project deleted between the `List` at line 500 and this `Get` makes `reconcileRescan` return the joined error. controller-runtime then logs a reconciler error and retries the rescan of every project with backoff. The other `RetryOnConflict` closures in this file return `client.IgnoreNotFound(err)` (lines 156, 212, 261, 295 and 535). I traced this without running it.

Fix: return `client.IgnoreNotFound(err)`.

S4. **The rescan's comment misstates when a tick is dropped, and each tick writes status for every project** — `rdd/pkg/controllers/containers/compose/compose_reconciler.go:624-629` [Claude Opus 5.5, Gemini 3.1 Pro]

```go
			case <-r.rescanTicker.C:
				// No need to emit if an event is already queued.
				select {
				case rescanCh <- event.TypedGenericEvent[any]{}:
				default:
				}
```

`rescanCh` is unbuffered (line 617). controller-runtime v0.24.1's `syncLoop` waits on it and copies each event into a 1024-slot buffer, so the `default` arm drops a tick only while the source is not receiving, which in practice means before it starts. The workqueue already merges duplicate rescan requests. Only this goroutine reads `rescanTicker` (line 80), so it can be a local variable. ## Design Observations

### Concerns

- **The run key is still half migrated** (in-scope). With the de-duplication gone, `processState.resourceVersion` only feeds the race checks at `compose_process.go:145` and `:158`. Each reconciler has its own tracker (`compose_controller.go:79`, `:88`) and one worker, so neither check can fire. Meanwhile the up-request reconciler decides restarts by generation. Comparing the command itself, as the wait goroutine does at `compose_process.go:172`, would leave the generation as the only restart key. [Claude Opus 5.5, Codex GPT 6 Astra]
- **The temporary-directory fallback still exists once per OS, and relative `--file` paths still defeat it** (in-scope, open question). Once `status.workingDir` is gone, `down` from a temporary directory still fails on the missing configs. The maintainers have not ruled on handling missing configs once, before the per-OS spawners. [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]
- **`docker` comes from the daemon's PATH** (future). `compose_process.go:103` runs the first `docker` on the daemon's PATH, not the instance's `bin` directory. [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]
- **nerdctl compose projects are never detected** (future). Membership needs `com.docker.compose.config-hash` (`compose_reconciler.go:420`), and `rdd/dependencies.yaml:56` pins nerdctl 2.1.2, which does not set it. [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]
- **An owned ComposeUpRequest is never reaped** (future). rdd's apiserver does not run a garbage collector, so a request whose owner is deleted first stays forever. One sentence in `api_containers.md` would warn the first client that sets an owner. [Claude Opus 5.5]

### Strengths

- **The spawn-failure path removes and re-adds Settled and Failed** (`compose_up_request_reconciler.go:152-155`), the smallest change that gives a failed rerun a new `LastTransitionTime`. [Claude Opus 5.5, Codex GPT 6 Astra]
- **The Windows fallback matches Go's own check.** With `SysProcAttr` nil, `os.StartProcess` stats `Dir` and reports a missing one as a `*PathError` whose `Op` is `"chdir"` (go1.27.3 `os/exec_posix.go:30-35`). [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]
- **Pruning checks the Container objects themselves**, so recovery no longer depends on a Container event that rdd lost, and the HasMembers=Unknown branch and the rescan share one routine. [Codex GPT 6 Astra, Claude Opus 5.5]

**Concerns**

- (in-scope) **The run key is still half migrated (round 2's observation).** Removing the de-duplication leaves `processState.resourceVersion` with one job: the race guards at `compose_process.go:145` and `:158`. Neither guard can fire. Each reconciler owns its own tracker (`compose_controller.go:79`, `:88`) and runs one worker, and `abort` runs on that same worker. The alternative is to drop `resourceVersion` and make the race token the command's identity, as the wait goroutine already does (`current.cmd == state.cmd`, line 172), or a per-call sequence number. - (future, open question) **Round-2 observations that still hold:**
  - The temporary-directory fallback exists three times: `command_linux.go:40-70`, `command_windows.go:68-99` and `command_darwin.go:113-131`.

I1. **Deletion of a project with no members skips `docker compose down`** — `rdd/pkg/controllers/containers/compose/compose_reconciler.go:288` (important, regression/gap)

```go
	case hasState, apimeta.IsStatusConditionFalse(project.Status.Conditions, v1alpha1.ComposeProjectConditionHasMembers):
		// Either `docker compose down` has finished, or the containers were removed
```

The `switch` matches `case hasState, apimeta.IsStatusConditionFalse(...)`, which acts as an `OR` condition in Go. If `HasMembers` is false (e.g., because containers were manually deleted and `recalculateContainers` updated the status), the case matches even when `hasState` is false. This causes the reconciler to immediately remove the finalizer without ever running `docker compose down`.

Deleting the project skips cleanup of its volumes and networks, stranding them permanently, which violates the contract in `api_containers.md`. The new test `deleting a ComposeProject with no members removes the finalizer without running down` inadvertently pins this resource leak as correct behavior.

Fix: Change the case to require `hasState` so `down` always runs first: `case hasState && apimeta.IsStatusConditionFalse(...)`. To prevent an infinite retry loop when `down` fails, remove the finalizer directly in the error case (line 277) once the fallback manual deletion succeeds, instead of relying on the next reconcile to skip `down`.

**Suggestions**

S1. **Unconditional status update in periodic rescan** — `rdd/pkg/controllers/containers/compose/compose_reconciler.go:366-372`

```go

			Type:    v1alpha1.ComposeProjectConditionHasMembers,

			Reason:  reason,

```

`recalculateContainers` is called for every `ComposeProject` by the 10-minute periodic rescan. It unconditionally calls `r.Status().Update(ctx, &latest)`, even if no containers were removed and `SetStatusCondition` made no changes. While the API server suppresses no-op updates, this still generates an unnecessary cached `Get` and API `Update` round-trip for every project.

Fix: Track whether `latest.Status.Containers` was modified or whether `apimeta.SetStatusCondition` returned `true`, and only call `Update` if something actually changed.

###### Concerns

- **The temporary-directory fallback exists three times, and `--file` defeats it** `(in-scope)`. Once `status.workingDir` is removed on host, config files relative to it are missing, so `down` launched from a temporary working directory still fails and the Container fallback leaves networks behind. Resolving missing directories and dropping unresolvable `--file` arguments in `initiateProjectDown` would allow compose to clean up networks via `--project-name` alone and eliminate the OS-specific error matching across Darwin, Linux, and Windows.
