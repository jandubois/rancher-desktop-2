Executive Summary ¶

This PR makes the main process ignore an app-status report without a KubernetesReady condition, so opening a window no longer restarts Steve under an open dashboard. It closes the dashboard when Kubernetes stops and drops the unused dashboard-close handler. The fix is correct, and its new spec fails against main's check. This round converged. Nothing reached Important, and the two suggestions (a comment and a test case) are optional.

Concerns ¶

  • (future) The dashboard closes on the App's status, not when Steve loses its port. Claude Opus 5.5 When the Steve process exits on its own, its exit handler zeroes the port (pkg/rancher-desktop/backend/steve.ts:131-140), and the next True report starts Steve on a new port while the dashboard stays on the old one. That gap predates this PR. Closing the dashboard wherever the port goes to 0 would cover a crash and a stop with one hook.
  • (future) The guard works around the renderer, which reports before it has listed the App. Claude Opus 5.5 #1180 proposes fixing the renderer's store instead, so that it holds the report until the current watcher's own list has returned. The main process could then treat a missing condition as a stop again.

Acknowledged Limitations ¶

  • A deleted App leaves Steve running and the dashboard open (#1180). The window's report for a deleted App is empty, and the new guard ignores it. #1183 names #1180 as the follow-up. A fix there needs the store to tell an App that it has not listed yet from a deleted one. No GUI path deletes the App. The Troubleshooting page sends factory-reset (pages/Troubleshooting.vue:163), and background.ts doesn't register a handler for it. So only the rdd CLI reaches this case today.
  • StatusConditions keeps an open tuple tail on purpose (pkg/rancher-desktop/main/steveLifecycle.ts:7). Deriving it from IpcMainEvents['backend/app-status-changed'] compiles today, but #1167 widens that event's tuples to three elements, and a derived type would then reject the spec's two-element reports. followAppStatus reads only each condition's first element, so the open tail matches what it needs. Do not re-suggest deriving or tightening it; a one-line comment at the type saying why would stop the next reviewer from trying.

Repo context updates ¶

  • [repo] Every renderer window that loads the Vuex store sends its own backend/app-status-changed report on each change to the App, so a main-process handler runs once per window per change and must be idempotent. A report lacks a condition when the window has not listed the App yet, when a watcher restart committed an empty list, when the controller that owns the condition has not written it, or when the App was deleted. Treat a missing condition as unknown. Only an explicit False or Unknown status means stopped.
