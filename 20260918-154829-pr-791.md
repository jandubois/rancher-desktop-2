S1. **`lint-shell` runs in no CI job** — `Makefile:26` [Gemini 3.1 Pro, Claude Opus 5]

```make
lint: lint-rdd lint-bats lint-shell lint-startup-profile lint-wix-helper
```

Every lint job in `.github/workflows/lint.yaml` invokes one specific target;
nothing runs the root `lint` aggregate, and `package.json:22-23` reaches only
`make lint-go`. The target added at `Makefile:52` therefore fires only when a
developer types it, so the one file it guards, the script `verify-generate`
now depends on, can stop passing shellcheck and shfmt unnoticed. Its four
siblings in that aggregate each have their own job, which makes the omission
look accidental.

```bash repro

# GitHub Actions workflow step can reach it. A target is reachable when some
# workflow runs it directly, or runs an aggregate that lists it.
ci_targets=$(grep -hE '^[^#]*run: make ' .github/workflows/*.yaml \
  | grep -oE 'run: make .*' \
  | sed 's/run: make //' | tr ' ' '\n' \
  | grep -vE '^-|^\$|^\}|^$' | sort -u)

for t in ${aggregate}; do
  if echo "${ci_targets}" | grep -qx "${t}"; then
    verdict="RUNS IN CI (own step)"
  elif echo "${ci_targets}" | grep -qx lint; then
    verdict="RUNS IN CI (via 'make lint')"
  else
    verdict="NEVER RUNS IN CI"

  printf '  %-22s %s\n' "${t}" "${verdict}"
```

S2. **The Windows mount failure is a consequence of the port, not an unrelated issue** — `scripts/generate-rdd-client.sh:172-175` [Gemini 3.1 Pro, Gemini 3.5 Flash]

```bash
    run_docker run --rm \
        --user="${UID:-0}" \
        --volume="${OUT_DIR}:/output_dir" \
        --volume="${TEMPLATE_DIR}:/templates:ro" \
```

The PR description calls the Windows breakage "an unrelated issue with docker
mounts". Bash under MSYS2 is an MSYS2 process, so its exec of a native
`docker.exe` triggers argv path conversion on any argument that looks like a
POSIX path list, while the deleted TypeScript spawned docker from native Node,
with no MSYS2 runtime in between.

The repo already has the remedy: `rdd/bats/helpers/paths.bash:24`'s
`host_path()` runs `cygpath -m` under Windows, and `rdd/bats/helpers/load.bash:8`
exports `MSYS_NO_PATHCONV=1`. The three host paths the script hands docker are
the `--volume` arguments at lines 157, 174 and 175.

Unproven: no Windows or MSYS2 host was available, so the conversion was not
executed.

Fix: route those three paths through a `host_path()` equivalent and set
`MSYS_NO_PATHCONV=1` on the docker calls, matching the bats helpers.

S3. **The `.exe` probe disagrees with the Makefile that builds the binary** — `scripts/generate-rdd-client.sh:20` [Claude Opus 5, Gemini 3.5 Flash]

```bash
IS_MSYS=$(command -v cygpath.exe || true)
RDD_PATH="${SRC_DIR}/rdd/bin/rdd${IS_MSYS:+.exe}"
```

`rdd/Makefile:6` and the root `Makefile:9` both decide the suffix with
`command -v winver.exe`. Under MSYS2 both probes answer yes and the two agree;
under WSL with default interop `winver.exe` resolves from `System32` while
`cygpath.exe` does not, so make would build `bin/rdd.exe` and the script would
look for `bin/rdd`. Round 2 unified the script's two internal detectors; this
is the same problem one level out.

I am holding the severity low on purpose. `bats-runs-in-msys-not-wsl` records
that WSL-hosted tooling is unsupported here and that defects in its branch
should not be rated live, and round 1's equivalent finding was declined as
cosmetic.

Unproven: no WSL host was available, so the divergence was not executed.

Fix: have the Makefile hand the path over, since it already knows `EXE`:
`RDD_PATH='$(abspath $<)' ../scripts/generate-rdd-client.sh`, with the script
falling back to its own computation when the variable is unset.

S4. **A proxy that never answers costs 30 silent seconds and can hang the job** — `scripts/generate-rdd-client.sh:89` [Claude Opus 5]

```bash
    for _ in {1..30}; do
        if curl --fail --silent "http://127.0.0.1:${PORT}/healthz" &>/dev/null; then
            break
        fi
        sleep 1
    done
```

Round 2 drops the `mktemp` log and sends the proxy to `/dev/null` (line 85),
so nothing records why it failed. Round 1 at least wrote the log before
deleting it. The loop never checks that
`proxy_pid` is still alive, and neither curl call passes `--max-time` or
`--connect-timeout`, so a proxy that accepts the connection without answering
blocks indefinitely. `.github/workflows/lint.yaml` sets no `timeout-minutes` on
any job, so the runner would sit until GitHub's 360-minute default.

Fix: add `--max-time` to both curl calls, break the loop on
`! kill -0 "${proxy_pid}"`, and keep the proxy's output in a file the failure
path prints.

S5. **Editing the script forces a full client regeneration** — `scripts/generate-rdd-client.sh:162` [Claude Opus 5]

```bash
    script=$(sha256 "${BASH_SOURCE[0]}")
    api=$(sha256 "${OUT_DIR}/swagger.json")
    echo "${version}-${script}${api}"
```

The published version's first 64 characters are the script's own digest.
`shasum --algorithm 256 scripts/generate-rdd-client.sh` gives
`83dd0aa5…ad9d3`, matching `pkg/rdd-client/gen/package.json`. So any edit to
the script, including a comment or a `make lint-shell-fix` reformat, turns
`verify-generate` red until someone reruns the whole docker pipeline. This PR
already pairs its one script commit with a regeneration commit immediately
after.

The API hash is what makes a stale client visible; the script hash is what
couples unrelated edits to a regeneration.

Fix: hash the inputs that determine the output, the pinned constants and the
generator arguments, or keep the swagger hash alone.

S6. **The failure message names a command that fails where CI shows it** — `rdd/Makefile:197` [Claude Opus 5]

```make
		printf "ERROR: Generated files are out of date. Run '%s' and commit the result.\n" \
			"make generate generate-typescript" >&2; \
```

Round 2 fixed round 1's complaint that `make generate` could not regenerate the
client. The replacement is correct from `rdd/`, but the CI step runs with
`working-directory: rdd` and the log shows only `make verify-generate`, so a
contributor pasting the suggested command at the repo root gets
`No rule to make target 'generate'`, because the root `Makefile` defines no
such target. `pkg/rdd-client/README.md:23` gets this right with `make -C rdd`.

Fix: name the directory, e.g. `make -C rdd generate generate-typescript`.

S7. **`verify-generate`'s two prerequisites can race under `make -j`** — `rdd/Makefile:195` [Claude Opus 5]

```make
verify-generate: generate generate-typescript
```

`generate-crds` rewrites the `crd.yaml` files `bin/rdd` embeds through
`EMBEDDED_SOURCES`, and `generate-deepcopy` rewrites Go sources in
`GOLANG_SOURCES`; `generate-typescript` builds `bin/rdd` from both. Under `-j`
make starts both prerequisites together, so the binary can compile against
half-written generated files. CI runs the target bare, so nothing is broken
today, and the failure would be loud.

Fix: sequence them in the recipe with two `$(MAKE)` lines, which works on the
GNU Make 3.81 that ships with macOS (target-scoped `.NOTPARALLEL` does not).

S8. **`lint-shell-fix` cannot format a file shellcheck rejects** — `Makefile:57` [Claude Opus 5]

```make
lint-shell-fix:
	shellcheck --enable=all $(SHELL_FILES)
	go -C rdd tool shfmt --indent=4 --write $(foreach f,$(SHELL_FILES),../$(f))
```

The fix target repeats the non-fixing shellcheck line from `lint-shell`, and
make aborts on its non-zero exit before `shfmt --write` runs, so the one thing
the target can fix is skipped exactly when the file needs it. `rdd/bats/Makefile:145`
does the same thing, so this copies the house pattern, which is why it comes
last.

Fix: drop the shellcheck line from the fix target, or run the formatter first.

## Design Observations

### Concerns

1. **`run()` still gambles the generated tree on the whole pipeline (in-scope)**
   [Claude Opus 5, Gemini 3.1 Pro, Gemini 3.5 Flash]. Line 199 deletes
   `pkg/rdd-client/gen/` and only line 203 restores it. Moving `build_rdd`
   above the `rm` removed one of the four ways to fail inside that window;
   `get_api`, `process_api` and `generate_models`, covering the control plane,
   the network and docker, all still abort with the tree gutted. Generating into a scratch
   directory and swapping at the end closes it; `pkg/rdd-client/.gitignore`
   is outside `gen/`, so the swap leaves it alone.

2. **The host-docker probe checks liveness, not capability (future)**
   [Claude Opus 5]. `run_docker system info` answering proves only that a
   daemon is reachable. A remote `DOCKER_HOST`, or a runtime without the source
   tree shared, passes the probe and then fails at the first bind mount, with
   no fallback to `rdd run docker` and `gen/` already deleted. Probing with the
   mount the script needs would catch it.

3. **`verify-generate` gained a heavy, network-dependent tail (in-scope)**
   [Codex GPT 5.6 Sol, Claude Opus 5]. Measured through the GitHub API: the
   `Verify generated files` job took 160 s at this SHA (job 105779487254,
   22:14:25→22:17:05) against 56 s at the merge-base itself
   (job 105704316976 at `e2400c61c`) and 49 s on a later main run
   (job 105776836700), about 105 s added per PR. Round 1's 4m17s figure was
   measured before the rebase swapped in the `setup-rdd-go` composite action
   and no longer holds. A developer checking a Go-only generation change now
   needs Docker and network.

4. **`KUBERNETES_BRANCH` trails the embedded apiserver (future, pre-existing)**
   [Claude Opus 5]. Line 12 pins `1.35.0` while `go list -m` reports
   `k8s.io/kubernetes v1.36.4` and `k8s.io/apiserver v0.36.4`. The value is
   copied verbatim from the deleted TypeScript (`generate-rdd-client.ts:33`
   at the merge-base), so the PR inherits it. But the port was the natural
   moment to notice.

### Strengths

1. **CI now proves the generated client matches the CRDs (in-scope)**
   [Claude Opus 5]. Job 105779487254 ran the full pipeline at `489a5837e`
   and found no diff. The committed version's leading 64 characters equal
   `shasum --algorithm 256` of the committed script, and only one commit in the
   series touches the script, with the regeneration immediately after.

2. **Deleting `gen/` before regenerating makes hand edits impossible to keep
   (in-scope)** [Claude Opus 5]. The regeneration commit changed four files,
   which is itself the evidence that no hand edits had accumulated.

3. **A single shell-lint idiom (in-scope)** [Claude Opus 5]. The new
   `lint-shell` and `lint-shell-fix` copy `rdd/bats/Makefile`'s pair in
   structure and flags. Where the bats target blankets four checks through
   `SC_EXCLUDES`, the new script waives its two with inline
   `# shellcheck disable=SC2310` comments that give reasons, which is better.
   Claude confirmed neither suppression is surplus by stripping both from a
   scratch copy and reproducing three SC2310 warnings.

4. **Host-dockerd reuse is intact after the rework (in-scope)**
   [Codex GPT 5.6 Sol, Gemini 3.5 Flash]. Round 1 credited the script for
   probing for a live host daemon instead of always booting a VM. Round 2
   replaced the per-call check with a single probe that redefines `run_docker`,
   so both container steps now bind to one decision. The round-1 inconsistency,
   where the preprocessor ran under RDD and the generator under host docker,
   cannot recur.

## Review Process Notes

### Skill improvements

- When the target's prior round has a maintainer review that triages the
  findings, declaring some important and the rest cosmetic, treat that triage
  as the resolution table the target lacks. Re-raising what the maintainer
  called cosmetic spends the round relitigating a decision already made, and
  the items that remain belong in Acknowledged Limitations, not the findings
  list.
- Cross-check an agent's prior-round status table against the tree before
  repeating any row. A table marking an unfixed item "Fixed" is more damaging
  than a missed finding, because a later reader takes it for verification and
  stops asking; the rows are cheap to spot-check and an
  optimistic one predicts more.
- When a prior round records that a verification was impossible for an
  environmental reason, run the trivial command that tests the excuse before
  inheriting it. A misdiagnosed toolchain is the cheapest thing in a review to
  check and the most expensive to keep, since each later round skips the same
  verification for the same wrong reason.
- When a finding rests on a platform configuration the project does not
  support, say so in the severity, not in the prose alone. The mechanism can be
  entirely real while the severity is not, and a finding that states the
  mechanism without saying the configuration is unsupported looks blocking.

#### Important Issues

I1. **Host `cygpath.exe` PATH leakage causes false MSYS2 detection under WSL** — `scripts/generate-rdd-client.sh:20` (important, regression)

```bash
IS_MSYS=$(command -v cygpath.exe || true)
RDD_PATH="${SRC_DIR}/rdd/bin/rdd${IS_MSYS:+.exe}"
```

On line 20, the script detects MSYS2 by checking `command -v cygpath.exe`. On line 21, this determines whether to append `.exe` to `RDD_PATH`. However, under WSL, the Windows host PATH is appended to the Linux PATH. Because Git for Windows is standard on developer hosts, `cygpath.exe` is found inside WSL (e.g., at `/mnt/c/Program Files/Git/usr/bin/cygpath.exe`), making `IS_MSYS` non-empty. This forces `.exe` to be appended to the path of the native Linux `rdd` binary, resulting in a fatal "No such file or directory" error when the script executes.

Fix: Use the standard project convention (checking `uname -s`) to detect MSYS2:

```diff
-IS_MSYS=$(command -v cygpath.exe || true)
+case "$(uname -s)" in
+    MSYS*|MINGW*) IS_MSYS=true ;;
+    *) IS_MSYS= ;;
+esac
```

I2. **Inconsistent `RDD_DEVELOPER_MODE` environment on obsolete service restart** — `scripts/generate-rdd-client.sh:71` (important, regression)

```bash
start_rdd() {
    RDD_DEVELOPER_MODE=true "${RDD_PATH}" service start
    # Check for obsolete RDD service and restart if necessary.
    if ! "${RDD_PATH}" service config &>/dev/null; then
        # Assume it's because of version mismatch; try deleting the service.
        RDD_DEVELOPER_MODE=true "${RDD_PATH}" service delete
        "${RDD_PATH}" service start
    fi
}
```

On line 66, the script starts RDD with `RDD_DEVELOPER_MODE=true`. If the service configuration is obsolete or mismatched, it deletes the service with `RDD_DEVELOPER_MODE=true` on line 69. However, the subsequent service restart on line 71 runs `"${RDD_PATH}" service start` without the `RDD_DEVELOPER_MODE=true` prefix. Since `export RDD_DEVELOPER_MODE=false` is set globally on line 28, this restart executes in non-developer mode. This inconsistency can cause the restart of a dev-compiled binary to fail or operate under incorrect configuration/paths, breaking obsolete service self-healing.

Fix: Prefix the second `service start` with `RDD_DEVELOPER_MODE=true`:

```diff
-        "${RDD_PATH}" service start
+        RDD_DEVELOPER_MODE=true "${RDD_PATH}" service start
```

#### Suggestions

S1. **Prevent MSYS2 path conversion in Docker volume mounts to fix Windows execution** — `scripts/generate-rdd-client.sh:157,172-173` (suggestion, enhancement)

```bash
    run_docker run --rm --user="${UID:-0}" --volume="${OUT_DIR}:/out:rw" "${python_image_name}"
```

The script currently fails on Windows because MSYS2's automatic path conversion translates container-side paths like `/out` or `/output_dir` in volume arguments into host Windows paths, which causes native Windows `docker.exe` to reject them. This blocker (acknowledged in the PR description) can be resolved by converting the host-side paths using `cygpath -m` under MSYS2 and setting `MSYS_NO_PATHCONV=1` (or `MSYS2_ARG_CONV_EXCL='*'`) when calling `docker` to preserve container-side Linux paths.

Fix: Check for `IS_MSYS`, convert paths if on Windows, and prefix `docker` calls with `MSYS_NO_PATHCONV=1`:

```diff
+if [[ -n "${IS_MSYS}" ]]; then
+    OUT_DIR_WIN=$(cygpath -m "${OUT_DIR}")
+    TEMPLATE_DIR_WIN=$(cygpath -m "${TEMPLATE_DIR}")
+else
+    OUT_DIR_WIN="${OUT_DIR}"
+    TEMPLATE_DIR_WIN="${TEMPLATE_DIR}"
+fi
```

Then update volume mounts to use those variables and set `MSYS_NO_PATHCONV=1`:

```diff
-    run_docker run --rm --user="${UID:-0}" --volume="${OUT_DIR}:/out:rw" "${python_image_name}"
+    MSYS_NO_PATHCONV=1 run_docker run --rm --user="${UID:-0}" --volume="${OUT_DIR_WIN}:/out:rw" "${python_image_name}"
```

and:

```diff
-    run_docker run --rm \
-        --user="${UID:-0}" \
-        --volume="${OUT_DIR}:/output_dir" \
-        --volume="${TEMPLATE_DIR}:/templates:ro" \
+    MSYS_NO_PATHCONV=1 run_docker run --rm \
+        --user="${UID:-0}" \
+        --volume="${OUT_DIR_WIN}:/output_dir" \
+        --volume="${TEMPLATE_DIR_WIN}:/templates:ro" \
```

S2. **Pin `PYTHON_IMAGE_BASE` to prevent future silent tag drifts** — `scripts/generate-rdd-client.sh:22` (suggestion, enhancement)

```bash
PYTHON_IMAGE_BASE='python:3-slim'
```

The script defines `PYTHON_IMAGE_BASE='python:3-slim'` on line 22. Because `3-slim` is a moving tag, upstream updates to the Python base image can cause non-deterministic behavior, different package versions, or build failures on a cold cache, without the script's hash changing. Pinning the base image to a specific minor version or SHA-256 digest ensures perfect reproducible builds.

Fix: Pin to a specific tag:

```diff
-PYTHON_IMAGE_BASE='python:3-slim'
+PYTHON_IMAGE_BASE='python:3.12-slim'
```

S3. **MSYS2 user ID permissions inside Docker containers** — `scripts/generate-rdd-client.sh:157` (suggestion, gap)

```bash
    run_docker run --rm --user="${UID:-0}" --volume="${OUT_DIR}:/out:rw" "${python_image_name}"
```

Under MSYS2, `UID` is set to the Windows/Cygwin user ID (e.g., `197609`), which is passed to Docker using `--user="${UID:-0}"`. Passing an invalid or high numeric UID can cause files in the volume mount to have unexpected owner IDs or trigger permission errors within Linux containers. Since the container runs simple python scripts and writes files back to a host volume, a comment explaining why this is acceptable under MSYS2 or adding a fallback to standard IDs would improve clarity.

Fix: Add a code comment explaining that high numeric Windows UIDs are normal on MSYS2 and safely mapped on host mounts.
