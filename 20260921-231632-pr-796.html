Executive Summary ¶

53d99fad8 makes the parallel path decline every block header the sequential decoder rejects, fail a block whose LZMA2 data ends early, and stream each block instead of copying it onto the heap. The fixes hold. Differential probes over more than 20,000 mutated fixtures found no case where the two paths disagree, and both real images decode to the same bytes as xz -d. No Critical or Important finding remains, so this round converged, and the four suggestions are optional.

ulikunitz's blockReader.Read stops at the first read that passes a block's declared uncompressed size. decodeBlock copies the whole LZMA2 output and only then compares the count, so it writes the excess into the next block's region, or past the end of the file for the last block. A probe halved the first block's size in multiblock-padded-index.xz, in its header and in the index, with both CRC32s recomputed. The sequential path answered wrong uncompressed size for block, and the parallel path block at 0 decoded 65536 bytes, want 32768.

Both paths reject the file, and the temporary file is removed. The only production input is the image rdd embeds at build time, so the overrun wastes work on a decode that fails anyway and cannot corrupt an image.

Fix: copy from io.LimitReader(&ctxReader{ctx: ctx, r: lr}, blk.uncompSize+1). The probe then reports decoded 32769 bytes, want 32768, and go test ./pkg/xz/ passes.

Design Observations ¶

Concerns ¶

  • (future) Round 1's two concerns stand Claude Opus 5 Codex GPT 5.6 Sol. The xz preset still sets decode memory and the number of blocks, and the split is still unmeasured on Windows, where punchHole does nothing. The delta changed neither.

Strengths ¶

  • (in-scope) Every fallback starts from an untouched file Claude Opus 5 Codex GPT 5.6 Sol. parseBlocks is the only source of errNotSplittable, and decompressParallel truncates dst only after it succeeds (parallel.go:315). The sequential path therefore always gets the empty file sparse.NewWriter now requires.
  • (in-scope) The trailing-data check needs no extra buffer Codex GPT 5.6 Sol. ulikunitz's LZMA2 reader reads each chunk through an io.LimitReader bounded by the chunk header's size and never reads ahead (lzma/reader2.go startChunk), so draining the bufio.Reader after EOF finds every leftover byte.
  • (in-scope) Streaming each block lowered peak memory without slowing the decode Claude Opus 5 Gemini 3.5 Flash. On the shipped -9 image, Claude's probe measured 1,095 to 1,257 MiB at this SHA against about 1,900 MiB at eec59f184, with the decode at 5.1 to 5.8 s on both. Round 1's mmap probe measured 1,357 to 1,557 MiB at eec59f184 and 1,138 to 1,271 MiB with the fix, so Claude's harness reads higher only at eec59f184 and overstates the saving.

Acknowledged Limitations ¶

Declined in prior rounds ¶

  • The XZ_OPTIONS comment in rdd/Makefile — declined Round 1: "The Makefile's -1 default matters only for dev and CI builds."
  • Capping workers by dictionary memory — declined Round 1, with I1's other fixes applied.

Carried from round 1, re-checked ¶

  • Streams with a check other than CRC64 fall back by design, because ulikunitz verifies CRC32 and SHA-256 and a CRC64-only split would accept corruption it catches. Do not re-suggest splitting them.
  • Single-block streams fall back by design (parallel.go:202-205).
  • On Windows the zeros stay allocated (rdd/pkg/sparse/punch_other.go). This predates the PR.
  • parseBlocks does not guard against a ReadAt that returns 0, nil. The reason still holds on the new read path. io.SectionReader passes ReadAt's result through unchanged, and only *strings.Reader and *bytes.Reader reach this code. Do not re-suggest.

New this round ¶

  • parseBlocks does not check that the blocks' uncompressed sizes sum below 2^63. ulikunitz v0.5.16 has no such check either, and a file that declares more data than any block can decode fails on both paths. Do not re-suggest.
  • uvarint stops at nine bytes, while ulikunitz accepts a noncanonical ten-byte integer. A stream using one falls back to the sequential decoder, so nothing changes for the user. Do not re-suggest.

Review Process Notes ¶

Skill improvements ¶

  • When a review needs a dependency's source or a staged artifact outside the agents' worktrees, copy it into each worktree's .scratch/ before launch instead of granting read access to its path. A CLI with a path sandbox refuses its own file tools outside the workspace, so the agent either falls back to shell reads or skips the material.

Repo context updates ¶

  • [repo] rdd/pkg/xz decodes only the distro image embedded in the binary at build time (limavm_controller.go), so a finding about crafted input with valid CRCs is hardening, not a security issue. Rate a difference in resource use or error text between the parallel and sequential paths as a Suggestion; an input one path accepts and the other rejects stays Important, because the parallel path promises the sequential path's checks.
