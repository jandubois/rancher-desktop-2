The branch adds a macOS Cluster API infrastructure provider that boots a Lima node VM for each LimaMachine. All six round-1 fixes work. I3. **A BATS comment says that Lima reports Running only after the boot scripts finish** — `rdd/bats/tests/35-capi-controllers/lima-machine.bats:256-258` [Codex GPT 6 Astra]

```bash
    # restartCount counts the times that the node VM reached Running, and Lima
    # reports Running only after the boot scripts finish. So at 2, the
    # restarted VM has finished its boot scripts.
```

Round 1's S3 fix corrected this claim in the design doc (`capi-provider.md:141`) but left the test comment. Lima's hostagent waits for the boot scripts with 200 tries 3 seconds apart (`pkg/hostagent/requirements.go:44-45` in the pinned Lima fork). When that wait fails, `startHostAgentRoutines` returns an error, and the hostagent still reports Running with `Degraded` set (`hostagent.go:549-553`).

rdd's hostagent watcher treats that event as Running, and `limavm_lifecycle.go:176` increments `restartCount`. So a `restartCount` of 2 doesn't prove that the restarted VM finished its boot scripts.

Unproven: reaching the timeout path needs a boot that outlasts Lima's wait for the boot scripts, and the in-process tests can't get there. The evidence is the pinned Lima fork's source, cited above.

Fix: say what the wait guarantees.

## Suggestions

S1. **One LimaMachine's persistent control-plane error slows every LimaMachine's timed passes to one every 16m40s** — `rdd/pkg/controllers/app/capi/reconciler.go:203-204` [Claude Opus 5.5]

```go
		if _, ok := errors.AsType[*controlPlaneError](err); ok {
			return ctrl.Result{}, err
```

Any `controlPlaneError` in the joined result makes `Reconcile` return an error and no `RequeueAfter`. controller-runtime v0.24.1 drops the 5-second requeue and backs the App's key off from 5 ms to 1000 s (`pkg/internal/controller/controller.go:483-494`). Every request uses that key. So while one LimaMachine's create keeps failing, every step that only a timed pass drives slows for all of them. Those steps are noticing a new LimaMachine or its bootstrap Secret, and round 1's repeated probe. LimaVM and App events still start passes.

The probe injects the error from a leftover `<name>-template` ConfigMap. It's a Suggestion because the known persistent causes are rare.

// to one that waits for its bootstrap data. With the failing one present, a

		machineCRD(),
		standInCRD(clusterGVK.Group, clusterGVK.Version, clusterGVK.Kind, "clusters"),
		standInCRD("rke.cattle.io", "v1", "RKEControlPlane", "rkecontrolplanes"),

	assert.NilError(t, corev1.AddToScheme(scheme))
	assert.NilError(t, limav1alpha1.AddToScheme(scheme))

	}))

## Design Observations

### Concerns

- (in-scope) In the same pass, `collectGarbage` repeats from the cache what `removeOtherClusterNodeObjects` already did. A cached LimaVM that still shows its owned finalizer gets a second `Update` from `base.RemoveOwnedFinalizer` (`finalizer.go:84`) with a stale resourceVersion, and the 409 ends the pass before the LimaMachine loop runs. The next pass, 5 ms later, recovers. It takes a change of the guest cluster's UID with Cluster API present, and round 1 found that no user action changes that UID while the App exists. Dropping the other-cluster case from `collectGarbage`'s predicate would give each removal reason one owner. [Claude Opus 5.5]
- (in-scope) Open question: rd-init queues a restart of every unit before READY, the mount units included (`rdd/src/rd-init/main.go:86`, `:93`). The maintainers haven't ruled on restarting every unit versus only the networking ones. [Gemini 3.5 Flash]

**Outcome:** the first concern is fixed in `141c695ed`. `collectGarbage` now leaves another guest cluster's objects to `removeOtherClusterNodeObjects`. `syncNodeVMsRunning` can cause the same conflict, because it patches node VMs earlier in the pass, and pending-work tracks that. The second concern is declined. rd-init tells systemd that it is ready before it waits for any of the restarts, so restarting every unit can't hold up the boot, and a unit that needs a mount waits for that mount.

### Strengths

- (in-scope) Reading the input ConfigMap through `apiReader` covers the one case that the cache gets wrong, the 5 ms retry after a failed create, and the interceptor in `TestReconcileLimaMachinesFailedVM` models that cache. [Claude Opus 5.5, Gemini 3.5 Flash]
- (in-scope) The cross-namespace name check reports the conflict in the LimaMachine's `Ready` condition, where the webhook's rejection would have shown up only in rdd's log. [Claude Opus 5.5]
- (in-scope) Removing another guest cluster's node VMs before the Cluster API check means that a replacement cluster without Cluster API doesn't leave them running. [Codex GPT 6 Astra, Gemini 3.5 Flash]

###### Design Observations

###### Concerns

1. **Unbounded unit restart queuing in rd-init before readiness** `(in-scope)`
   In `rdd/src/rd-init/main.go:78-90`, `rd-init` queues asynchronous `RestartUnitContext` jobs for every unit derived from metadata, user data, and network config (including mount units) before calling `SdNotifyReady`. While this ensures units ordered after `rd-init` wait for queued restarts, restarting all units unconditionally before readiness can delay systemd boot progress if many units are loaded. Documenting or bounding the unit restart list to networking units is worth considering as an architectural refinement.

###### Strengths

- **Cache-Bypass on Template Re-rendering**: Using `r.apiReader` in `createNodeVM` (`limamachine.go:317`) specifically prevents reading a stale cached copy of the input ConfigMap that was deleted moments earlier after a VM creation failure, guaranteeing that spec updates immediately re-render.
- **Selective App Event Filtering**: `appPredicate()` in `reconciler.go:319-340` precisely inspects generation bumps and condition status transitions on `AppConditionRunning` and `AppConditionKubernetesReady`, filtering out noisy status writes from other condition writers (`ContainerEngineReady`, `PathManagementReady`) and preventing unneeded reconcile loops.
- **Robust Error Classification**: Deriving `controlPlaneError` and matching via `errors.AsType[*controlPlaneError]` across joined error trees accurately separates internal control plane errors (which require controller-runtime backoff) from guest cluster errors (which require gentle in-progress polling).

###### Acknowledged Limitations

- **Paused cluster and managed-by label**: The provider ignores a paused cluster and the `cluster.x-k8s.io/managed-by` label (`capi-provider.md:189`), per maintainer ruling.
- **Manual CRD deletion**: A CRD deleted by hand from the guest cluster is re-installed only after daemon restart or `k3s.yaml` change (`capi-provider.md:94`).
- **Install retry on reboot**: A failed install script re-runs only upon VM restart, and first boot requires openSUSE repositories (`capi-provider.md:119-121`).
- **Registration token in logs**: The token can reach the host log only if Lima fails to parse a self-marshalled template (`capi-provider.md:185`).
- **Guest polling interval**: New LimaClusters and LimaMachines wait up to 30 seconds for the next polling pass (`reconciler.go:62-66`).
- **LIMA_HOME environment mutation**: `controller_darwin.go:54` sets `LIMA_HOME` in-process. Go guards its environment with `syscall.envLock`, and the lima controller sets the identical value.
- **ControlPlaneRef schema**: The provider reads CAPI v1beta2 `controlPlaneRef` which uses `apiGroup` and has no namespace.
- **Kine compaction**: Deleted ConfigMaps remain in sqlite until compaction, but `<name>-template` retains the token for VM lifetime regardless.
- **Single worker serial probe**: Probing node VMs sequentially over SSH is tracked separately for future work (`probe_darwin.go:16`).
- **No `--instance` in failure message**: The diagnostic `rdd ctl get limavm` command in `limamachine.go:230` lacks `--instance` (already tracked).
- **BootstrapFailed requeue interval**: `BootstrapFailed` machines remain on the 30-second idle requeue rather than the 5-second in-progress one by maintainer ruling.
