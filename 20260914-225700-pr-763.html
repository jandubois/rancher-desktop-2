rdd/docs/design/api_lima.md

    The `LimaVM` controller will create a new ConfigMap (in `metadata.namespace`) with the `metadata.name` and a `"-template"` suffix to store a copy of the validated template. This name is stored under `status.templateConfigMap`. The original `spec.templateRef` source is never accessed again after this, and can be modified or deleted without affecting the `LimaVM` resource. The `spec.templateRef` is immutable after creation and only serves as documentation.

    The `status.templateConfigMap` can be modified, but must pass Lima validation for the update to succeed. If `spec.running` is `true` and the template has changed, then the instance will be restarted. The `status.templateConfigMap` cannot be deleted, except by deleting the `LimaVM` resource itself, which will clean up owned resources automatically.

    When the first image for the instance's arch has a location starting with `embedded:`, the controller uses the distro image built into the binary that runs it, `rdd` or a standalone `lima-controller`. That image is the raw disk image, or on Windows the rootfs tarball that WSL2 imports. A binary built without the image fails to create such an instance and sets `Created` to `False` with reason `CreateFailed`. Lima downloads and decompresses any other image itself, and needs `xz` on the host for an `.xz` one.

- **spec.params**: Override `spec.params` settings in the template. These values will be merged with the template before validation, and when creating/updating the `lima.yaml` file of the actual instance on disk.

    If the template provisioning scripts are properly parameterized, then the instance settings can be modified by just updating `spec.params`, which is simpler than modifying the `template` inside the ConfigMap. If `spec.running` is `true` then changing `spec.params` will restart the instance.

Acknowledged Limitations ¶

Declined in prior rounds, each re-checked at this SHA:

  • A first yarn install must fit the distro download into postinstall's ten minutes — declined Round 1: the comment at InstallTimeout in scripts/postinstall.ts gives the workaround, and it is still there.
  • The embedded: branch ignores the location's arch and file name — declined Round 1: only a hand-written LimaVM template reaches it. It still ignores both, because usesEmbeddedImage compares the image's arch with the instance's, never with the binary's.
  • WSL2 cannot refetch a missing basedisk from an embedded: location — declined Round 1 with the comment on linkWSL2BaseDisk, which is still accurate.
  • Round 1's skipped gaps: a Makefile target-resolution guard, a bats setup with an external lima manager, rdd/NOTICE, the other controllers' stale build after an arch switch, and Lima's decompressLocal leaving an empty file.
  • Switching only GOOS leaves bin/rdd built for the previous OS — declined Round 2: bin/rdd needs cgo for its target. Its rule sets CGO_ENABLED=1 (rdd/Makefile:116), which github.com/mattn/go-sqlite3 requires.
  • Nothing records which distro the binary embeds — declined Round 2: rdd --version names the commit, and that commit's rdd/dependencies.yaml pins distro 0.2.8.
  • Hosts without xz skip most xz tests — declined Round 2: CI runs them on all three OSes, which the timings in the Testing Assessment support.

Author decisions and accepted costs

  • rdd never looks for a system xz, so a downloaded .xz image needs xz on the host. LookPath("xz") appears only in rdd/pkg/xz/xz_test.go:43 Claude Opus 5 Codex GPT 5.6 Sol.
  • No bats test boots a VM from an image Lima downloads. The https locations left are fixtures, among them the invalid ISO in limavm-instance.bats.
  • The decode holds the LimaVM controller's only worker, because nothing sets MaxConcurrentReconciles. The staged arm64 image took 19.5 to 19.7 s here. Round 2 raised this, and the planned block-parallel decoder would shorten it.
  • The costs #708 accepts: the size of bin/rdd, slower VM creation on hosts with xz, CI cache growth, and one VM restart after the upgrade.
