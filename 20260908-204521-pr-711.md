## Executive Summary

The stager is well built: content-addressed verification at both hops, atomic
publication, and an error taxonomy that puts the retry decision where the
knowledge is. Two gaps matter. The download carries no deadline, so a stalled
server hangs `make build-rdd` forever and never reaches the retry loop. And
nothing tests that a cache entry is verified rather than trusted: replacing
that check with a bare `os.Stat` leaves the whole suite green.

PR #711 is stacked on unmerged #511, so this round scopes findings to
`febd11736`'s seven files; S8 belongs to #511 and is attributed there. Three
reviewers reached I1 independently. `go test`, `go vet` and `golangci-lint`
were run from the review SHA and are all clean.

## Important Issues

I1. **The download has no deadline; a stalled server hangs the build forever** — `rdd/pkg/guestdeps/stage.go:140` [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]

```go
	resp, err := http.DefaultClient.Do(req)
	if err != nil {
		return 0, err
	}
```

`http.DefaultClient` sets no `Timeout`, and `DefaultTransport` bounds only the
dial and the TLS handshake, never the wait for response headers or the body
read at `stage.go:167`. The only cancellation source is `ctx`, which
`rdd/cmd/download-guest-deps/main.go:40` wires to SIGINT alone. A peer that
sends headers and then stops blocks `io.Copy` with no error, so the retry loop
at `stage.go:106` never advances.

The comment at `stage.go:22-25` claims these retries "bound the retries of a
stalled or reset transfer". Reset yes, stalled no. The contrast below shows a
dropped connection recovering in 20 ms while a stall runs unbounded.

I2. **Nothing tests that a cache entry is verified rather than trusted** — `rdd/pkg/guestdeps/stage.go:57` [Claude Opus 5]

```go
	cached, err := fileHasChecksum(cachePath, dep.Asset.Checksum)
	if err != nil {
		return err
	}
```

`Stage`'s doc comment promises it "checksums both the cache entry and destPath
rather than trusting a timestamp". Six tests cover the destPath half and the
cache-*hit* half, but none writes wrong bytes at `cachePath`. Replacing this
check with a bare `os.Stat` existence test leaves the entire suite green, and
that mutant copies the corrupt entry to destPath and returns `nil`, which #708
would then `//go:embed` into a shipped binary. The failure is silent.

The PR description lists "a corrupted cache entry is re-downloaded" among the
behaviours verified by hand. The behaviour is right; nothing keeps it right.

## Suggestions

S1. **A correct staged file still forces a download when the cache is gone** — `rdd/pkg/guestdeps/stage.go:57-74` [Claude Opus 5, Codex GPT 5.6 Sol]

```go
	cached, err := fileHasChecksum(cachePath, dep.Asset.Checksum)
```

`Stage` populates the cache before it ever looks at `destPath` (line 67). When
`destPath` already holds the verified asset but the cache is gone (macOS purges
`~/Library/Caches` under disk pressure, or a tree moves between machines), the
build re-fetches 217 409 580 bytes, measured with `curl --head` against the
v0.2.7 arm64 asset, only to log "is up to date" and throw the work away.
Offline, it fails.

Measured directly: staging, deleting the cache, then staging again with the
staged file untouched issues a second HTTP request; with the staged file removed
too, the fetch is unavoidable. The repo's own TypeScript downloader already
checks its destination first (`scripts/lib/download.ts:140`).

Fix: check `destPath` first and return before touching the cache. The double
hash on the warm path is cheap: two sha256 passes over the real 207 MiB asset
measure 116 ms each here.

S2. **The flat retry schedule makes the 429 carve-out useless** — `rdd/pkg/guestdeps/stage.go:149` [Claude Opus 5]

```go
		if resp.StatusCode >= 400 && resp.StatusCode < 500 && resp.StatusCode != http.StatusTooManyRequests {
			return 0, &fatalError{err}
		}
```

Singling out 429 as retryable says the author expects GitHub's asset CDN to
throttle. But `downloadAttempts = 4` (line 26) at a flat `retryDelay = 2 *
time.Second` (line 28) exhausts all four attempts in six seconds (measured at
6.02 s in I2's shipped-tree run), and `Retry-After` is never read. Any throttle
window longer than that fails the build, so the carve-out buys nothing over
treating 429 as fatal.

Fix: back off exponentially and honour `Retry-After` when present, capped at a
ceiling. `scripts/lib/download.ts:100` already does the exponential half
(`baseDelayMs * 2 ** attempt`, capped at 30 s over 8 retries), so this is
existing house style, not a new mechanism.

S3. **Nothing prunes the cache, and an abandoned transfer strands a full-size temp file** — `rdd/pkg/guestdeps/stage.go:87` [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro]

```go
	return filepath.Join(s.CacheDir, dep.Name, "v"+dep.Version, path.Base(u.Path)), nil
```

Keying by version is deliberate and documented, but nothing ever removes an old
version directory, so every distro bump leaves another ~207 MiB in
`~/Library/Caches/rancher-desktop-2` for good.

Worse, `createTemp` at `stage.go:211` generates a fresh random name per attempt,
so a download killed by anything but SIGINT (SIGTERM, SIGKILL, a crash, a lost
machine) strands a partial `*.tmp-*` beside the target that no later run looks
at. `Stage` only ever stats the exact `cachePath`.

Fix: glob and remove `*.tmp-*` in the version directory at the top of `download`,
and either prune sibling version directories after a successful stage or record
the unbounded growth as a TODO on `cachePath`'s comment.

S4. **Concurrent stagers sharing one cache can collide on Windows** — `rdd/pkg/guestdeps/stage.go:226` [Gemini 3.5 Flash]

```go
	return os.Rename(tmp.Name(), destPath)
```

Sharing one cache across worktrees is the stated design, so two builds staging
the same dependency at once is expected. On POSIX that is safe: each writer
renames its own temp file. On Windows `os.Rename` becomes `MoveFileEx(...,
MOVEFILE_REPLACE_EXISTING)`, which needs delete access to the target, while Go
opens files with `FILE_SHARE_READ|FILE_SHARE_WRITE` and no `FILE_SHARE_DELETE`.
So a process hashing `cachePath` in `fileHasChecksum` (`stage.go:232`) blocks
another process's rename onto it, and the build fails with a sharing violation.

The window is narrow and the failure is loud, so this stays a suggestion. RD2
runs BATS under MSYS2 on Windows, so parallel worktree runs are the likely
trigger.

Unproven: no Windows host was available. The mechanism rests on Go's source at
the version `rdd/go.mod` pins: `syscall_windows.go:395` sets the share mode, and
`internal/syscall/windows/syscall_windows.go:366` calls `MoveFileEx`.

Fix: document the limitation, or take a lock file in the version directory
around the rename.

S5. **Manifest error messages omit the URL, the field most likely to be at fault** — `rdd/pkg/guestdeps/manifest.go:95` [Claude Opus 5]

```go
	if u.Scheme != "https" {
		return fmt.Errorf("asset %s must be downloaded over https", a)
	}
```

`Asset.String()` renders only the selection axes, so this prints `asset [linux]
must be downloaded over https`, confirmed by running `validate` directly. For
the three URL checks at lines 92, 95 and 97 the URL *is* the problem, and the
message never shows it; a maintainer has to open the file and count entries.

Fix: include the URL in those three messages, e.g. `fmt.Errorf("asset %s: url %q
must use https", a, a.URL)`. Leave `String()` as the axis renderer it is; the
axes and the URL answer different questions.

S6. **`validate` rejects legitimate file names containing `..` while `Version` goes unchecked** — `rdd/pkg/guestdeps/manifest.go:97` [Claude Opus 5]

```go
	if base := path.Base(u.Path); base == "." || base == "/" || strings.Contains(base, "..") {
		return fmt.Errorf("asset %s has no file name to download to", a)
	}
```

`path.Base` returns a single path element, so the only traversal shape it can
produce is the exact string `".."`; `strings.Contains` additionally rejects an
innocent `a..b.tar.gz`, and does so with a message claiming the URL has no file
name. Meanwhile `Entry.validate` checks only that `Version` is non-empty, and
`cachePath` interpolates it straight into a path: a `Version` of
`../../../escape` yields `<cache>/escape/distro.raw.xz`, relocating the entry. Both were confirmed by calling the functions directly.

The manifest is generated, so neither is reachable today. The asymmetry is the
thing to fix, since `validate`'s stated job is catching a hand-edited file.

Fix: tighten the base check to `base == ".."` and add a matching guard on
`Version`.

S7. **A multi-minute download reports nothing until it finishes** — `rdd/pkg/guestdeps/stage.go:117` [Claude Opus 5]

```go
		s.logf("Downloading %s to %s", dep.Asset.URL, destPath)
```

Once #708 makes this the first step of `make build-rdd`, the default target
prints one line and then appears frozen for however long 207 MiB takes on the
developer's link. Combined with I1, a wedged transfer looks exactly like a slow
one.

Fix: wrap the `io.MultiWriter` in a counting writer and emit a percentage line
every few seconds when `resp.ContentLength >= 0`. `Log` is already an injectable
`io.Writer`, so the plumbing exists.

S8. **`nerdctl.ts` claims a downloader behaviour `stagedDeps` does not implement** — `scripts/dependencies/nerdctl.ts:16` [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro]

```ts
 * it like any other GitHub dependency; the Go downloader fetches it at build
```

`stagedDeps` (`rdd/cmd/download-guest-deps/main.go:89`) returns only the distro,
and there is no other `guestdeps` caller, so the nerdctl entry in
`rdd/dependencies.yaml` is fetched by nobody. `distro.ts:19` makes the same claim
and becomes true with #708; nerdctl's names no landing PR. The text belongs to
#511 and should be fixed there.

Gemini 3.1 Pro raised this as an Important issue and proposed adding nerdctl to
`stagedDeps`. That is the wrong direction: nothing consumes the archive yet, so
the fix would download 40 MiB per build for no consumer.

Fix: reword to say nerdctl is tracked for the forthcoming overlay work but is not
staged yet, or name the tracking issue.

## Design Observations

### Concerns

- **The fetched body is bounded in neither size nor time** *(future)* [Claude Opus 5]. I1 covers time. On size, `io.Copy` at `stage.go:167` writes until the server stops and the checksum can only reject afterwards, so an endless stream fills the build machine's disk before anything notices. The manifest records a checksum but no length, so the cheap guard is a hard ceiling via `io.LimitReader`. Low likelihood, since the URL is a pinned GitHub release from a checked-in file, but the guard removes the class in three lines.
- **`make clean` will not reset a staged asset** *(future, #708)* [Claude Opus 5]. `rdd/Makefile:196-199` removes `bin` and the guest agent only (verified). Once `pkg/embedded/distro.raw.xz` is a build input, a developer who suspects a bad stage has no `make` verb to drop it.
- **`EMBEDDED_SOURCES` will not see the staged image** *(future, #708)* [Claude Opus 5]. `rdd/Makefile:69` globs only `*.yaml` and `*.json` under `./cmd` and `./pkg` (verified). When #708 adds the `//go:embed`, a re-staged image will not by itself trigger a rebuild of `bin/rdd`.
- **The dependency list is hard-coded in the downloader** *(future)* [Gemini 3.5 Flash]. `stagedDeps` names `distro` in a Go literal. That is right for one dependency; as the embedded set grows, deriving it from a manifest field would stop the two sides drifting.
- **A checksum mismatch is classified as permanently fatal** *(in-scope, no change recommended)* [Claude Opus 5]. `stage.go:168-171` marks it `fatalError` and `TestStageRejectsUnexpectedBytes` pins `requests == 1`. Over HTTPS an in-flight corruption is effectively impossible, and re-downloading 207 MiB three times to learn the manifest is stale is the worse trade. Recorded so a later round does not re-litigate it.

### Strengths

- The three-state design (cache, staged copy, both verified by content and not by timestamp) is the right shape, and every behaviour the PR description claims held under test [Claude Opus 5, Codex GPT 5.6 Sol].
- `createTemp` always opens the temp file in the destination's own directory, so `os.Rename` never crosses a device boundary [Gemini 3.1 Pro, Gemini 3.5 Flash].
- The fatal-versus-retryable split puts the retry decision where the knowledge is, instead of leaving the caller to pattern-match error strings [Claude Opus 5].
- `Select` requires exactly one match (`manifest.go:171`) rather than taking the first, so a manifest that grows an overlapping asset fails the build instead of silently changing what ships [Claude Opus 5, Codex GPT 5.6 Sol].
- `--os`/`--arch` as flags rather than `GOOS`/`GOARCH`, with the cross-compilation rationale written down at `main.go:8-12`. That is the kind of decision that gets silently "simplified" later once the comment is gone [Claude Opus 5, Codex GPT 5.6 Sol].
- The Go reader is strictly narrower than the TypeScript writer on every axis compared (https-only vs any parseable URL; lowercase-only hex vs case-normalised). Nothing the writer emits is rejected and nothing the reader accepts is looser, which is the safe direction for a two-parser grammar [Claude Opus 5].

## Testing Assessment

The suite is good: eleven tests across the two packages, a fake asset
server that counts requests, and `TestStagedDepsResolveAgainstTheManifest`, which
catches a renamed or dropped asset in `rdd/dependencies.yaml` at `make test`
rather than in a build. `go test`, `go vet` and `golangci-lint run` on both new
packages were executed from the review SHA and are clean.

Gaps, highest risk first:

1. **A cache entry present but not matching the checksum.** I2 proves this cell
   is uncovered and that its regression is silent.
2. **Four consecutive failures.** `TestStageRetriesATransientFailure` covers two
   failures then success; nothing exercises four consecutive failures, so neither
   `downloadAttempts = 4` nor the final error wrapper at `stage.go:127` is pinned.
3. **Context cancellation mid-download.** `main.go:39` promises an interrupt will
   "abort it and clean up", but no test cancels during a transfer and asserts no
   temp file survives.
4. **A failed copy into the destination directory.** `assertNoTempFiles`
   (`stage_test.go:89`) globs only under `cacheDir`, so `copyFile`'s cleanup path
   is never observed.
5. **`assertNoTempFiles` is itself fragile.** Its glob hard-codes two directory
   levels below `cacheDir` (`stage_test.go:91`). Any change to `cachePath`'s
   layout makes it match nothing and pass vacuously.
6. **`DefaultCacheDir` and `run` have no tests at all**, including the
   `os.UserCacheDir` error path that `main.go:55` propagates.

## Acknowledged Limitations

- `rdd/pkg/guestdeps/manifest.go:74-76` frames `validate` as a drift detector for
  a hand-edited manifest rather than a trust boundary. That is why S6 is a
  suggestion and not a security finding.
- `rdd/pkg/guestdeps/stage.go:79-81` documents cache accumulation as deliberate.
  S3 asks only that the unbounded growth and the stranded temp files be handled

- `rdd/cmd/download-guest-deps/main.go:8-12` explains why the target comes from
  flags rather than `GOOS`/`GOARCH`. The constraint is real; #708 must remember

## Review Process Notes

### Skill improvements

- When a reviewer's proposed fix would add work that no code consumes yet,
  treat the finding as documentation drift rather than a missing feature. A
  comment describing intended future behaviour is evidence about a plan, not
  about a defect; implementing it to satisfy the comment inverts the direction
  of the fix. Verify that a consumer exists before accepting any finding whose
  remedy is "add the missing call".

- When a finding rests on platform behaviour the review host cannot exercise,
  settle the mechanism against the toolchain's own source before assigning a
  severity. Language runtimes make specific, checkable choices (file share
  modes, rename primitives, signal numbers), and reading the pinned source turns
  an untestable guess into a citable claim, or refutes it. Record the
  file and line as the finding's evidence and mark it `Unproven:` for the
  reproduction, not for the mechanism.

### Repo context updates

- [repo] The TypeScript downloader in `scripts/lib/download.ts` is the house
  reference for download behaviour: it checks the destination's checksum before
  fetching, and retries with exponential backoff capped at a ceiling. When
  reviewing a new downloader in any language, compare it against that file
  before rating a retry schedule or a cache-reuse decision as adequate.

- [repo] `rdd/Makefile` defines `EMBEDDED_SOURCES` by globbing only `*.yaml` and
  `*.json` under `./cmd` and `./pkg`. A change that adds a new `//go:embed` of
  any other file type creates a build input that is not a prerequisite of
  `bin/rdd`, so the binary will not rebuild when that file changes. Flag it.
