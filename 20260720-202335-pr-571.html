Executive Summary ¶

The PR re-enables the Kubernetes version selector, backing it with a new kubernetes Vuex module that watches the daemon's k3s-versions ConfigMap, plus a network module. The plumbing is sound and reuses existing watch infrastructure. Three problems stand out: four catalog versions map to +k3s3 builds provisioning cannot construct, the new E2E test asserts only fieldset visibility against a harness supplying no versions, and the offline label rests on a premise RD2 no longer has.

Findings are grouped by theme: version-identity correctness (I1), test efficacy (I2), and the offline/network subsystem (I3, I4). No reviewer raised a Critical issue.

Design Observations ¶

Concerns

  • The network module has one consumer and a false premise (in-scope) Claude Opus 4.8. A namespaced Vuex module, two window listeners, and a dead IPC channel exist to append seven words to one fieldset legend, and the words are wrong (I3, I4). Deleting store/network.ts and its two lines in entry/store.ts removes all three at once. A genuine "your version list is stale" signal would come from the daemon, via the ConfigMap's own metadata, so the module is not scaffolding for that future either.
  • NetworkStatus.vue already tracks network state (in-scope) Claude Opus 4.8. The component registers the same update-network-status / online / offline handlers the new plugin does, plus a pageshow handler the plugin lacks, whose comment explains it catches changes missed while the preferences window was closed. If the module survives I3, repoint the component at the store so there is one source of truth.
  • Exact artifact identity is lost between catalog and provisioning (in-scope) Codex GPT 5.6 Sol. The ConfigMap models bare version → exact k3s release, but the App and Lima handoff keeps only the bare value. Preserving the exact release internally and deriving the display label separately forecloses I1 structurally, where patching the one template line only fixes today's four entries.
  • Module naming (future) Claude Opus 4.8. store/kubernetes.ts reads as "state of the Kubernetes cluster" but holds one ConfigMap watch and two version getters, while store/rdd.ts already watches ConfigMaps. Low urgency: the name fits once the module holds real cluster state.

Strengths

  • Reusing defineResource/resourceWatchActions inherits reconnect, refcounted start/stop, and namespace-change rewatch for free Claude Opus 4.8 Gemini 3.1 Pro Codex GPT 5.6 Sol.
  • Refcounting the watch to the component's mount lifecycle keeps the ConfigMap stream off the main window entirely Claude Opus 4.8.
  • tryParseJSON returning undefined rather than throwing keeps a malformed ConfigMap from taking down the preferences render Claude Opus 4.8 Gemini 3.5 Flash.

Testing Assessment ¶

Ranked by risk:

  1. ConfigMap → dropdown round trip. Nothing asserts a version reaches the UI, and the harness supplies none (I2). A wrong namespace, stalled watch, or parse failure all ship green.
  2. Version grouping and sorting. recommendedVersions, nonRecommendedVersions, and formatRecommendedVersion have no coverage at any layer (S2).
  3. selectedVersion fallback chain. Five candidate sources, none exercised; the realistic cases each produce a different UI (S3).
  4. Selection writes through to the App spec. No test dispatches preferences/modify with kubernetes.version and confirms the webhook accepts the patch.
  5. Non-+k3s1 catalog entries. No test covers a version whose exact release carries a different suffix. That is the gap that lets I1 exist.

All four reviewers ran without node_modules, so every claim about Jest or tsc outcomes in the source reviews is static tracing, not executed. No reviewer reported running a test suite.

Documentation Assessment ¶

k3sVersions and k3sChannels carry no doc comment stating their shape: bare-version keys mapping to full k3s version strings. Neither the name nor Record<string, string> conveys it. The sibling store/rdd.ts documents its getters, and store/network.ts documents nothing.

Commit Structure ¶

Clean. 1386b2824 is the feature (component plus two stores plus registration), 4616a9abb is the test change; neither patches the other and both messages match their diffs.

Repo context updates

  • [repo] UPDATE — The existing entry stating the k3s-versions ConfigMap lives in the rdd-system namespace is wrong. K3sVersionsReconciler creates it in app.Spec.Namespace (the same namespace the renderer's rdd-connection.namespace resolves to), owned by the App and cleaned up with it. The stale entry misleads: it invites a reviewer to flag correct namespace handling as a bug. Replace with: "The supported-k3s-versions data ships as a core ConfigMap named k3s-versions in the App's own namespace (app.Spec.Namespace), labelled app.kubernetes.io/name=rdd-k3s-versions and created by the k3sversions controller from a //go:embed blob. DesiredLabels() is exported so renderer watches can filter on it. The design doc docs/design/api_k3sversion.md describes an older CRD-based design — do not treat it as the contract."
  • [repo] ADD — The e2e harness starts the daemon with rdd service start --controllers= and runs only the mock controller, so no embedded controller's resources exist during Playwright runs. Any UI backed by a controller-created resource renders empty there, and an assertion that only checks element visibility will pass against that empty state. When reviewing a test for controller-backed UI, verify the harness enables the controller group that serves the resource before crediting the test with covering it.
  • [repo] ADD — spec.kubernetes.version carries a bare semver, and the guest provisioning script rebuilds the full k3s release by appending a hardcoded +k3s1 suffix. The bundled catalog maps each bare version to its exact release, and some entries use a higher suffix. When reviewing code that moves a Kubernetes version between the catalog, the App spec, and the guest, check whether the exact release survives the trip or is reconstructed from the bare value.

Skill improvements

  • When a change adds a UI affordance whose label or behaviour describes a system state (offline, cached, degraded, read-only), verify that state is still reachable in the current architecture rather than only that the code computing it is correct. A rewrite commonly carries a label and its plumbing forward after designing away the condition the label describes, and a reviewer checking only internal consistency will pass it. Trace the state back to the component that produces it and confirm that producer is still wired in.
  • When a finding proposes changing which value a UI control binds to, check the proposed value against the control's rendered option set before accepting the fix. Binding a value with no corresponding option makes a <select> render blank, so a fix framed as "always respect the stored value" can be worse than the divergence it corrects.
