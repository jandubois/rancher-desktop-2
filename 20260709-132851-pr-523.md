## Important Issues

I1. **Webhook accepts and stores negative `cpus`, silently suppressing `RDD_VM_CPUS`** — `rdd/pkg/controllers/app/app/controllers/app_webhook.go:72-77` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro] (round 1 I1 unaddressed)

```go
if vm.CPUs != 0 {
    if v.hostInfo.CPUs > 0 && vm.CPUs > v.hostInfo.CPUs {
        return fmt.Errorf("spec.virtualMachine.cpus %d exceeds the host CPU count of %d", vm.CPUs, v.hostInfo.CPUs)
    }
}
```

Issue #498 requires `cpus >= 1`, with `0` as the reset sentinel. The guard excludes only `0`, then checks the upper bound alone, so a negative value passes. The CRD declares `cpus` as an unconstrained integer, making the webhook the sole gate.

The orchestrator confirmed this on a live control plane: `rdd set virtualMachine.cpus=-4` exits 0 and stores `-4`. `applyVMResources` (`app_controller.go:133-148`) then skips both the `cpus == 0` env-fallback branch and the `cpus > 0` rewrite branch, so the VM takes the template default and `RDD_VM_CPUS` is discarded.

Fix: reject negatives and gate the upper bound on `> 0`. Gemini also proposed a CRD `minimum: 1`; that would break the suite's `webhook accepts cpus=0` test. Use `minimum: 0` if a schema guard is wanted.

```go
if vm.CPUs < 0 {
    return fmt.Errorf("spec.virtualMachine.cpus %d must not be negative", vm.CPUs)
}
if vm.CPUs > 0 { /* existing upper-bound check */ }
```

I2. **`coerceValue` makes `0` delete any integer property, not just `virtualMachine.cpus`** — `rdd/cmd/rdd/set.go:740-748` [Gemini 3.1 Pro; Codex GPT 5.5 and Claude Opus 4.8 rated this a Suggestion]

```go
case "integer":
    v, err := strconv.ParseInt(raw, 10, 64)
    if err != nil {
        return nil, errors.New("expected integer")
    }
    // 0 means "unset / use default": send a null patch so the field is
    // removed from the object (consistent with the int omitempty semantics).
    if v == 0 {
        return nil, nil
    }
```

Round 1's I2 named `virtualMachine.cpus`. The fix landed in the coercion helper shared by every settable property, so `0` now means "delete" for every integer the App schema will ever expose. Today `cpus` is the only settable integer, so nothing breaks — but the next integer field where `0` is legal becomes unsettable, silently.

The change also leaves two artifacts. `coerceValue`'s header comment (`set.go:709-714`) still claims integer types "return a clear error" for a cleared field, which no longer holds for `0`. And sibling fields now reset by opposite syntaxes: `cpus=0` clears while `cpus=` errors; `memory=` clears while `memory=0` is rejected below the 2Gi floor. Nothing documents either.

Fix: scope the behavior to the field rather than the type — pass a `clearZero` flag from the resolved property path — and update the header comment.

I3. **HostInfo singleton has no recovery path, and a comment claims one exists** — `rdd/pkg/controllers/rdd/hostinfo/controllers/hostinfo_controller.go:64-72` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro] (round 1 I4 unaddressed)

```go
if err := r.Create(ctx, hi); err != nil && !apierrors.IsAlreadyExists(err) {
    // Non-fatal: log and continue. The next reconcile will retry.
    logf.FromContext(ctx).Error(err, "Failed to bootstrap HostInfo singleton")
}
return nil
```

If the one-shot `Start` create fails, no object exists. `Reconcile` fires only on `For(&HostInfo{})` events and the informer's initial list is empty, so no reconcile ever runs — the comment is false. A runtime `delete hostinfo system` leaves the same permanent gap, since `Reconcile` returns `IgnoreNotFound` (`:43`).

Impact stays bounded: the embedded apiserver makes the create reliable, and the webhook detects host limits directly rather than reading the CRD. But the GUI's range query breaks until restart, and the comment misleads the next maintainer.

Fix: extract `ensureSingleton(ctx)`, call it from `Start` and from the singleton-NotFound branch of `Reconcile`, and return the bootstrap error instead of swallowing it.

## Design Observations

### Concerns

- **Host detection is duplicated, and the webhook's copy is frozen at startup** `(in-scope)` [Claude Opus 4.8, Codex GPT 5.5]. `controller.go:144` hands the validator a `DetectHostInfo()` snapshot taken once during webhook setup, while `HostInfoReconciler.Reconcile` independently calls `NumCPU()` and `TotalMemory()` on every reconcile to populate the CRD. Two Go types are both named `HostInfo`. Keeping detection out of the webhook is reasonable — reading the CRD would introduce a cross-group startup-ordering hazard — but the detection *logic* belongs in one shared helper. The two paths agree today only because both call `NumCPU()`; a future divergence, or a host whose CPU count changes under the running daemon, would make the webhook's enforced range and the GUI's advertised range disagree silently.
- **Memory ceiling is 100% of host RAM** `(future)` [Claude Opus 4.8, round 1 — unaddressed]. The webhook allows `memory == hostInfo.Memory` (`app_webhook.go:85`), matching issue #498, but handing the guest all host RAM can starve the host OS. Worth revisiting whether a headroom margin belongs here.

### Strengths

- **Pointer-aware deepcopy regenerated correctly** `(in-scope)` [Claude Opus 4.8]. Adding `Memory *resource.Quantity` changed the generated `App.DeepCopyInto` from `out.Spec = in.Spec` to `in.Spec.DeepCopyInto(&out.Spec)`, avoiding a shared-pointer aliasing bug. Preserve this on future regenerations.
- **HostInfo CRD placement** `(in-scope)` [Codex GPT 5.5, Gemini 3.1 Pro]. A cluster-scoped `HostInfo` in the `rdd` group leaves room for future host diagnostics without overloading App, and gives the GUI a typed, discoverable resource.
- **CPU precedence chain** `(in-scope)` [Codex GPT 5.5]. spec → `RDD_VM_CPUS` → template default reads cleanly, and an invalid env value errors loudly so a CI typo cannot silently change VM sizing.

## Review Process Notes

### Skill improvements

- **When a finding claims the API server rejects a value on create or update — a JSON `null`, a zero, a wrong type, an out-of-range number — establish whether a mutating admission webhook runs first.** For custom resources the chain is: decode, mutating webhooks, schema validation, validating webhooks. A defaulter that decodes the request into a typed struct and re-marshals it silently normalizes the object: a JSON `null` for a non-pointer field becomes the zero value, and an `omitempty` tag then drops the key, so the schema validator never sees what the client sent. Verify such a claim against a running API server, or against the whole chain — never against the schema validator alone, which will happily reject a value the object no longer carries.

- **When a fix for a finding that named one field or call site lands in a shared helper, enumerate everything else that helper now treats differently and judge each case.** A fix placed in a generic layer inherits every present and future caller, so a contract that is correct for the field which motivated it can be wrong for its neighbours. Report the widened contract at the severity the worst affected caller warrants, and check whether the helper's own doc comment still describes what it does — a fix that outruns its comment leaves the next maintainer with a false map.

- **State each agent's wall-clock budget in its prompt, and tell it to emit a complete review before the budget expires — a shallower review that lands beats a thorough one that is killed.** When a sibling agent or an earlier attempt has already performed expensive verification (a built binary, an executed test suite, a live environment), record the results in the prompt and forbid re-running them. An agent that spends its whole budget reproducing another agent's work returns nothing at all.

### Repo context updates

- **[repo] UPDATE** the entry beginning "Validating-webhook rules that duplicate a CRD `enum`, `pattern`, `maxLength`, or `required` constraint are unreachable — schema validation runs first in the admission pipeline." That holds for validating webhooks and misleads for mutating ones. Add: mutating webhooks run *before* schema validation, so a defaulter can legitimately add, normalize, or remove values that the schema would reject on the raw request body.

- **[repo]** The App resource registers a mutating defaulter for both Create and Update (`pkg/controllers/app/app/controller.go`), wired through controller-runtime's `NewWebhookManagedBy(...).WithDefaulter(...)`. That handler decodes the request into the typed `App` struct and re-marshals it, so a JSON `null` sent for a non-pointer field is normalized to the zero value and dropped by `omitempty` before the CRD schema validator runs. `rdd set` depends on this: it sends `null` to clear a field, and its create path would otherwise fail schema validation. Account for this round-trip before flagging a null or zero as rejected by the API server.

### Design Observations

**Strengths**
- The approach of separating the `HostInfo` detection into an in-memory struct for the webhook (`controllers.DetectHostInfo()`) and a cluster-scoped CRD for external clients is well designed. It prevents the webhook from making a K8s API call on every admission request while still giving the GUI the information it needs.

### Testing Assessment
1. **Missing negative value boundaries**: The BATS tests should enforce that negative values for CPU and memory limits are correctly rejected, especially once the schema minimum is restored.
2. **Test isolation**: The BATS tests for `virtualMachine` properties lack complete isolation and inadvertently rely on the execution order (I.e., finding S7).

### Documentation Assessment
The code is thoroughly documented, though the CLI usage of `=` vs `=0` for clearing values requires explicit alignment in user-facing documentation if the current asymmetric logic is kept.
