Executive Summary ¶

PR #550 moves k3s-version parsing into a shared package, adds a reconciler that force-creates a k3s-versions ConfigMap plus a webhook blocking its deletion, and switches webhooks to name-based custom paths so two ConfigMap validators no longer collide. Core mechanics are correct and verified — build and tests are green, and the collision fix holds. The main gaps: a stray _ "embed" import papered over with a repo-wide lint exclusion, and no coverage for the new webhook and trigger.

All three reviewers agree the change is sound and low-risk; findings cluster around lint hygiene, test coverage, and documentation drift. Gemini raised two Important lifecycle concerns — creation timing and the deletion-blocking webhook — that Codex and Claude did not. Verification against the code downgrades both: the backend defaulter/validator use the embedded data directly (not the ConfigMap), and nothing in rdd deletes the rdd-system namespace, so the deletion guard's whole point is intentional immortality rather than a lifecycle trap.

Design Observations ¶

Concerns ¶

  • The k3s-versions ConfigMap is intentionally immortal (future) Gemini Claude — nothing ever deletes it: the embedded control plane has no garbage collector, no reconciler cleans it up, and the webhook rejects every delete (failurePolicy defaults to Fail). This is acceptable given the single-user embedded API server and the pre-stable project stage, but a comment near the validator would tell a future maintainer the ConfigMap is deliberately permanent. Gemini proposed removing the validator to restore standard namespace cleanup; that is rejected here — nothing in rdd deletes the rdd-system namespace, and blocking deletion is the feature's stated intent.

Strengths ¶

  • The custom webhook-path change fixes a real collision, not a theoretical one (in-scope) Claude Codex Gemini — lima's limavm-configmap-validator and the new k3s-versions-validator both mapped to controller-runtime's default /validate--v1-configmap, so the second silently dropped. Name-based paths give each a distinct route, and the change is verified safe when only a validator or only a defaulter is present (the absent side's custom-path call is a no-op).
  • Sharing the parsed K3sVersions struct keeps admission off the control plane (in-scope) Codex Claude — the defaulter and validator reuse the embedded data directly instead of reading the ConfigMap back through the API server.
  • The reconciler self-heals deterministically (in-scope) Claude — it For-watches the ConfigMap it manages and marshals sorted map[string]string values, so applies converge and the ConfigMap is restored if deleted out-of-band.

Review Process Notes ¶

Skill improvements ¶

  • When a change adds a linter exclusion, a suppression rule, or an inline //nolint-style comment, treat it as a claim to verify rather than a fact to accept: confirm the flagged code cannot simply be fixed, and check the exclusion's scope. A file-wide or repo-wide exclusion added to silence a single occurrence masks every future instance of that class and permanently weakens the linter — flag it and prefer the narrower fix (usually deleting the offending line). Because a suppression hides the very issue review exists to catch, the burden is on the change to justify keeping it.

Repo context updates ¶

  • [repo] All admission webhooks register custom paths of the form /{validating|mutating}-<config-name> via base.GenerateWebhookPath, not controller-runtime's default GVK-derived path. Multiple webhooks on the same resource type (several ConfigMap validators, for example) coexist only because their config names differ; a duplicate config name recollides on one path and silently drops a handler. When reviewing a new webhook, verify its config name is unique across the shared webhook server.
  • [repo] The supported-k3s-versions data ships as a plain core ConfigMap named k3s-versions in the rdd-system namespace (labels app.kubernetes.io/name=rdd-k3s-versions), created by the k3sversions controller and guarded against deletion by a validating webhook. It is intentionally never garbage-collected. The design doc docs/design/api_k3sversion.md describes an older, unimplemented CRD-based design — do not treat it as the contract.
