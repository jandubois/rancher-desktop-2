## Important Issues

I1. **`toContainText` array form cannot detect extra or unexpected options** — `e2e/preferences.e2e.spec.ts:241` [Claude Opus 4.8, Codex GPT 5.6 Sol]

```ts
      await expect(options).toContainText([...recommendedLabels, ...otherVersions]);
```

Playwright routes the array form of `toContainText` to `to.contain.text.array`, which skips the length check (`lengthShouldMatch = expression !== "to.contain.text.array"`) and then matches the expected items as an *ordered subsequence* of *substrings*. The dropdown may therefore render versions absent from the ConfigMap, render duplicates, or decorate a label (`1.35.2 (unsupported)` still contains `1.35.2`) and line 241 still passes. So the PR's stated goal, comparing expected versions against displayed items, holds in one direction only.

I verified this against the installed bundle (`playwright-core@1.61.1`) and by simulation. The expected array is exactly the 35 rendered labels, in order, so `toHaveText` passes unchanged.

Fix:

```diff
-      await expect(options).toContainText([...recommendedLabels, ...otherVersions]);
+      await expect(options).toHaveText([...recommendedLabels, ...otherVersions]);
```

I2. **The expected labels re-derive the component's presentation logic, and the copies already differ** — `e2e/preferences.e2e.spec.ts:234` [Claude Opus 4.8, Gemini 3.5 Flash]

```ts
        const filteredChannels = channels.filter(c => !/^\d+\.\d+/.test(c));
```

Lines 224–239 restate `recommendedVersions`, `nonRecommendedVersions`, and `formatRecommendedVersion` from `BodyKubernetes.vue`, and three details already diverge. The test filters channels with `/^\d+\.\d+/` while the component uses `/^v?\d+\.\d+/` (`BodyKubernetes.vue:38`). The test sorts channel names at line 231 while the component keeps ConfigMap key order (`BodyKubernetes.vue:34-36`). The test calls `semver.compare` raw at line 225 while the component wraps it with a `localeCompare` fallback (`BodyKubernetes.vue:53-59`).

The copies agree today only because `k3s_versions.go:88` strips the leading `v` from channel keys and Go emits map keys sorted. Either change makes the test fail without a UI bug.

Fix: assert the `<option>` `value` attributes, which are the bare unformatted versions, and cover formatting with one explicit label check per group.

## Suggestions

S1. **`waitForLoad()` is a weaker gate than the `waitForURL` it replaced** — `e2e/preferences.e2e.spec.ts:324` [Claude Opus 4.8]

```ts
      await prefPage.waitForLoad();
```

Both call sites previously waited on `preferencesWindow.waitForURL(/Preferences#/i)`, with a comment naming the hash-route transition. `waitForLoad` (`e2e/pages/preferences/index.ts:26-30`) only waits for `.preferences-nav` to be visible, which can happen before the sub-route settles. Both tests then assert `containerEngine.nav` carries the `active` class, which depends on that route. Latent: the enclosing `Preferences State` group is `test.describe.fixme` (line 268).

Fix: fold the route wait into the shared helper so both conditions hold.

S2. **Unaliased `controllers` import diverges from every other cross-package consumer** — `rdd/pkg/controllers/mock/mock_controller.go:22` [Claude Opus 4.8]

```go
	"github.com/rancher-sandbox/rancher-desktop-daemon/pkg/controllers/app/k3sversions/controllers"
```

`controllers.K3sVersionsReconciler` at line 151 gives no clue which of the repo's many `controllers` packages this is, inside a tree rooted at `pkg/controllers/`. The three other cross-package consumers all alias it `k3sversionscontrollers` (`app/app/controller.go:21`, `app_defaulter.go:18`, `app_webhook.go:16`).

Fix: alias the import `k3sversionscontrollers` and update line 151 to match.

S3. **Mock App deletion leaves the newly owned ConfigMap behind** — `rdd/pkg/controllers/mock/app_reconciler.go:40` [Codex GPT 5.6 Sol]

```go
	if !app.GetDeletionTimestamp().IsZero() {
		// The app is being deleted; nothing to do here yet.
		return ctrl.Result{}, nil
	}
```

The new reconciler creates an App-owned ConfigMap via `SetControllerReference`, and RDD has no garbage collector. Production cleans up (`app_controller.go:259` calls `base.DeleteOwnedResources`, then deletes the namespace); the mock returns early, so a deleted mock App now strands `k3s-versions`. This PR gives the mock App its first owned resource. The practical risk is low, since the suites reset the whole control plane, but App-deletion tests would diverge from production.

Fix: give `appReconciler` a `Manager` and call `base.DeleteOwnedResources` behind the cleanup finalizer, mirroring `app_controller.go`.

S4. **`RDCheckbox` forces only `check`/`uncheck`, leaving `setChecked` and `click` unforced** — `e2e/pages/preferences/checkbox.ts:12` [Claude Opus 4.8]

```ts
      value: function(options?: Parameters<Locator['check']>[0]) {
        return l.check({ ...options, force: true });
      },
```

The helper's contract is "a locator suitable for a `<rd-checkbox>`", but the interception problem it works around applies equally to `setChecked()` and `click()`. A future caller reaching for either gets the unforced path and an opaque pointer-events timeout, with nothing in the type signature flagging the gap.

Fix: add a `setChecked` override alongside the existing two, or narrow the returned type to the supported methods.

S5. **Test name does not describe what the test asserts** — `e2e/preferences.e2e.spec.ts:202` [Claude Opus 4.8]

```ts
    test('Kubernetes enabled checkbox should exist', async() => {
```

The body asserts that toggling the checkbox drives the version dropdown's enabled state (lines 204–208); existence is already covered at line 198. Separately, `let kubernetes` (line 191) is assigned inside the first test, so running a later test alone under `--grep` throws on `undefined`.

Fix: rename to describe the toggle behavior, and read `prefPage.kubernetes` per test. `KubernetesNav` is a pure locator holder, so reading it per test costs nothing.

S6. **`Page` imported as a value, against the sibling page objects' convention** — `e2e/pages/preferences/index.ts:1` [Claude Opus 4.8]

```ts
import { expect, Page } from '@playwright/test';
```

Every other file under `e2e/pages/preferences/` uses a trailing `import type { Page, Locator } from '@playwright/test';` (`application.ts:1`, `wsl.ts:1`, `containerEngine.ts:1`), and this file did too before the change.

Fix: keep `import { expect }` at the top and restore the trailing `import type { Page }`.

S7. **Subprocess output used untrimmed as a CLI flag value** — `e2e/preferences.e2e.spec.ts:217` [Claude Opus 4.8]

```ts
      const namespace = await rdd('ctl', 'get', 'app/app', '--output=jsonpath={.spec.namespace}');
```

`tool()` returns `stdout` verbatim (`e2e/utils/TestUtils.ts:245`), so any trailing newline turns line 219 into `--namespace=rancher-desktop\n` and surfaces as an opaque "namespace not found" instead of pointing at the whitespace. jsonpath output carries no trailing newline today, which is why CI is green. But this is a real process boundary, and trimming costs nothing.

Fix: `const namespace = (await rdd(...)).trim();`, and likewise for the two JSON payloads.

## Design Observations

### Concerns

- **The assertion oracle re-derives the component's transformation (in-scope)** [Claude Opus 4.8]. Beyond the specific divergences in I2, the test builds its expectation by re-running the component's logic over the same input, so it cannot catch a bug in that transformation. It catches only a break in the wiring between ConfigMap and DOM. Asserting on `<option>` `value` attributes tests the wiring without copying the formatter, and one or two hardcoded label assertions then cover the formatting independently.
- **Mock mode registers the reconciler but not the ConfigMap's deletion webhook (future)** [Claude Opus 4.8]. `k3sversions/controller.go:84-103` sets up a `Delete`-operation validating webhook guarding the `k3s-versions` ConfigMap; `mock_controller.go:150-156` wires only the reconciler. This is deliberate per the PR body, and the `Owns(&v1.ConfigMap{})` watch recreates the ConfigMap after a delete, so the gap is benign. A one-line comment in `setupReconciler` would keep a future reader from reading it as an oversight.

### Strengths

- **Reusing the production reconciler keeps the encoding under test (in-scope)** [Codex GPT 5.6 Sol, Claude Opus 4.8]. The ConfigMap's `versions`/`channels` encoding (`k3s_versions.go:47-65`) stays exercised instead of frozen into a test fixture that drifts from what the renderer actually consumes.
- **Deriving expectations from the ConfigMap avoids a stale version list (in-scope)** [Codex GPT 5.6 Sol]. A hardcoded list would need editing on every k3s bump.
- **The ConfigMap read is sequenced after the first dropdown assertion (in-scope)** [Claude Opus 4.8]. The dropdown cannot show a channel label until the renderer has observed the ConfigMap, so the `rdd ctl get` calls at lines 217-222 cannot race the reconciler and hit a hard non-retrying failure through `tool()`.
- **Toggling Kubernetes stays transient (in-scope)** [Gemini 3.5 Flash]. `RdCheckbox` dispatches `preferences/modify` rather than `writeNow` absent an `immediate` prop (`RdCheckbox.vue:52-58`), so the uncheck/check cycle at lines 204-207 never triggers a real backend teardown.
- **The `should finish loading` gate fixes a real failure class (in-scope)** [Claude Opus 4.8]. Quitting while the mock controller is still installing CRDs yields the non-zero exit that `teardown` asserts against, so line 33 addresses the cause instead of masking it with a sleep.

## Testing Assessment

The new tests pass in CI on the review SHA. `e2e-tests` ran `should finish loading`, `should open preferences modal`, and all three Kubernetes tests green in 32.1s.

Untested scenarios, highest risk first:

1. **Extra or duplicated dropdown entries.** Per I1, the assertion permits the dropdown to render versions the ConfigMap does not list. A regression widening the version set would ship green.
2. **A version carrying two non-version channels.** Current data puts `latest` and `stable` on different versions, so `filteredChannels.join(', ')` (line 238) never produces a multi-channel label. That is exactly the case where I2's sort divergence becomes observable.
3. **Selected-version behavior.** `selectedVersion` (`BodyKubernetes.vue:18-29`) implements a four-level fallback chain, and nothing asserts which option loads selected or that a selection persists through `preferences/modify`.
4. **Platform coverage.** `e2e-playwright.yaml:25` pins the job to `ubuntu-latest`, so the new `force: true` checkbox path is validated on one platform while BATS runs on three.
5. **Offline labelling.** `cachedVersionsOnly` (`BodyKubernetes.vue:14`) changes the fieldset legend; no test drives `network.offline`.
6. **Empty or malformed ConfigMap.** The component renders no optgroups when parsing fails; no test covers the resulting empty dropdown.

Pre-existing and out of scope: `kubernetesVersionLockedFields` (`e2e/pages/preferences/kubernetes.ts:19`) is referenced by no test, and its `>` child combinators would need re-verification against the current `RdFieldset`/`RdSelect` DOM before use.

## Review Process Notes

### Skill improvements

- When a finding turns on the semantics of a test-framework assertion (subset versus exact match, ordered versus unordered, substring versus equality, whether element counts must agree), read the matcher's implementation in the version the repo has installed before rating the finding. Matcher names are poor guides to matcher behavior, sibling matchers in the same family often differ on exactly one of these axes, and the semantics change across major versions. State which file and version you read.
- Before reporting that code would throw or fail at runtime, check whether the project's CI already exercises that path on the review SHA, and read the job log if it does. A green job covering the exact call is stronger evidence than static reasoning about the runtime's semantics, and it is usually one command away. This applies with most force to claims about a library's internal behavior, where the reviewer cannot see the implementation.
- Treat a test that computes its expected value by re-implementing the logic under test as a finding in its own right. Recognise it when the test's setup mirrors the production transformation step for step over the same input. Such a test verifies the wiring between input and output but cannot catch an error in the transformation itself, and the two copies drift apart silently. Prefer asserting against the untransformed data the code carries alongside its rendered form, keeping one or two hardcoded expectations to cover the transformation.
- When the review prompt's repo-context section makes a factual claim about a file (that a doc is stale, that a design is unimplemented, that a constant holds a given value), verify the claim against the file before repeating it in a finding. Injected context reads to an agent exactly like a verified observation, so a stale entry propagates into the report with full confidence and no visible provenance.

### Repo context updates

- UPDATE the `k3s-versions` ConfigMap entry. It currently states the ConfigMap lives in the `rdd-system` namespace and that `docs/design/api_k3sversion.md` describes an older, unimplemented CRD-based design. Both halves are wrong as of `e004819b4`: the reconciler creates the ConfigMap in `app.spec.namespace` (`k3s_versions_reconciler.go`), and the design doc accurately documents the shipped ConfigMap, including the `versions` and `channels` encodings and an example. Replace with: the supported-k3s-versions data ships as a core `ConfigMap` named `k3s-versions` in the namespace named by `App.spec.namespace`, created by the `k3sversions` controller from an embedded `k3s-versions.json`, guarded against deletion by a validating webhook, and accurately described by `docs/design/api_k3sversion.md`.
- ADD: the Playwright `e2e-tests` job runs only on `ubuntu-latest` (`.github/workflows/e2e-playwright.yaml`), while BATS runs a macOS/Linux/Windows matrix. When reviewing an e2e change that works around platform-specific rendering or input behavior, treat the workaround as validated on Linux only, and say so rather than crediting the green check with cross-platform coverage.
- ADD: `rdd/pkg/controllers/mock` is blank-imported only by `rdd/cmd/mock-controller/main.go`, never by the embedded service. A controller registered in both the mock and a production controller package therefore never shares a manager with its twin, so identical `Named(...)` registrations do not collide. Reject duplicate-registration findings premised on the two running together.

### Executive Summary

### Findings

#### Critical Issues
None.

#### Important Issues

##### I1. Fragile inheritance on Playwright Locator — `e2e/pages/preferences/checkbox.ts:8-21` (important, regression)

```typescript
export default function RDCheckbox(locator: Locator): Locator {
  const l = locator.locator('input[type="checkbox"]');
  return Object.create(l, {
    // Override `check` to always use force, as Playwright detects that the
    // clicks are handled by a different element.
    check: {
      value: function(options?: Parameters<Locator['check']>[0]) {
        return l.check({ ...options, force: true });
      },
    },
    uncheck: {
      value: function(options?: Parameters<Locator['uncheck']>[0]) {
        return l.uncheck({ ...options, force: true });
      },
    },
  });
}
```

Using `Object.create(l)` on a Playwright `Locator` breaks the `this` context for all inherited methods, which are executed with `this` bound to the returned wrapper instead of the original `Locator` instance. Playwright Locators are complex host/library-provided class instances that can rely on private fields or instance-specific internal state, which would throw a `TypeError` at runtime. It also violates the project's Engineering Standards to prefer delegation and explicit wrapping over prototype-based cloning.

Fix: Safely bind and override `check` and `uncheck` directly on the local `l` instance before returning it.

```diff
 export default function RDCheckbox(locator: Locator): Locator {
   const l = locator.locator('input[type="checkbox"]');
-  return Object.create(l, {
-    // Override `check` to always use force, as Playwright detects that the
-    // clicks are handled by a different element.
-    check: {
-      value: function(options?: Parameters<Locator['check']>[0]) {
-        return l.check({ ...options, force: true });
-      },
-    },
-    uncheck: {
-      value: function(options?: Parameters<Locator['uncheck']>[0]) {
-        return l.uncheck({ ...options, force: true });
-      },
-    },
-  });
+  const originalCheck = l.check.bind(l);
+  const originalUncheck = l.uncheck.bind(l);
+  l.check = (options) => originalCheck({ ...options, force: true });
+  l.uncheck = (options) => originalUncheck({ ...options, force: true });
+  return l;
 }
```

##### S1. Sorting order drift in recommended channel labels — `e2e/preferences.e2e.spec.ts:213` (suggestion, regression)
