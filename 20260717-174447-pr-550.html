Executive Summary ¶

Round 2 recuts PR #550. The k3s-versions ConfigMap now lives in the App's own namespace, is owned by the App, and is swept on App deletion; the deletion-guard validator keys on owner reference and labels. Every Round 1 finding is resolved or superseded except one test gap. Build and unit tests pass. One Important issue remains: the deletion guard is bypassable — an unguarded update can strip the routing label or owner reference, after which the delete succeeds.

Design Observations ¶

Concerns ¶

  • The reconciler races the App controller's namespace creation (future) [orchestrator verification] — the k3s reconciler creates the ConfigMap in app.Spec.Namespace, but the App controller creates that namespace on the same App-create event (app_controller.go:289). If the reconciler runs first, CreateOrUpdate fails with "namespace not found," returns a wrapped error, and requeues with backoff — logging an ERROR each attempt until the namespace appears. It self-heals, and the reconciler already returns a quiet result when app.Spec.Namespace is empty (k3s_versions_reconciler.go:68); it could treat a not-found namespace the same way to keep startup logs clean.
  • Lexical version sort on duplicate builds (future) Gemini 3.5 Flash — slices.Sorted orders k3s builds lexically, so +k3s10 sorts before +k3s2. If the embedded JSON ever held two builds of one bare version, the lexically-last would win and could pick the older build. The static list has no duplicates, so this cannot fire today.

Strengths ¶

  • App-scoped, App-owned ConfigMap fits the no-GC control plane (in-scope) Codex GPT 5.5 Gemini 3.1 Pro Gemini 3.5 Flash — moving the ConfigMap into App.spec.namespace and tying cleanup to App ownership (via DeleteOwnedResources) resolves the Round 1 immortal-ConfigMap and cross-namespace concerns; deletion now cascades correctly. The App is cluster-scoped, so the owner reference on a namespaced ConfigMap is valid, not a cross-namespace violation.
  • The reconciler self-heals deterministically (in-scope) Gemini 3.5 Flash — it owns and watches the ConfigMap and restores data, labels, and owner reference on drift, and it skips recreation while the App is being deleted, so it does not fight cleanup.
  • Custom webhook paths fix a real collision (in-scope) Gemini 3.5 Flash — name-based /{validating|mutating}-<name> paths let multiple ConfigMap validators coexist on one port; verified safe when only a validator or only a defaulter is present, since the nil side registers no configuration.
  • Reused parsed version data keeps admission off the control plane (in-scope) Codex GPT 5.5 Gemini 3.5 Flash — the defaulter, validator, and reconciler share the embedded K3sVersions rather than reading the ConfigMap back through the API server.

Review Process Notes ¶

Skill improvements ¶

  • When an admission webhook filters its targets through an ObjectSelector on mutable labels, or gates its decision on mutable metadata such as owner references, and registers for only some operations (commonly Delete but not Update), check whether an unguarded operation can remove the selector metadata. A client that strips the routing label or owner reference through an unguarded Update, then performs the "guarded" operation, bypasses the webhook — the API server never routes the request to it. Flag such a guard as non-deterministic unless the Update path is also registered and rejects removal of the routing metadata while the guard should hold. A reconciler that restores the metadata narrows the window to a race but does not close it.

Repo context updates ¶

  • [repo] The reference implementation for a deletion-guard webhook keyed on a label ObjectSelector is the Lima ConfigMapValidator (pkg/controllers/lima/limavm/controller.go): it registers Create, Update, and Delete, and its ValidateUpdate rejects removing the routing label while the resource is owned. A new label-selected guard that registers only Delete and allows all updates is bypassable — compare any such guard against this pattern.
  • [repo] The App resource is cluster-scoped (+kubebuilder:resource:scope=Cluster), and its spec.namespace names the namespace holding its namespaced children (the k3s-versions ConfigMap, LimaVM). An App owner reference on a namespaced resource is therefore valid, not a cross-namespace ownership violation; base.DeleteOwnedResources resolves the target namespace through the ResourceNamespace interface (GetResourceNamespace). Do not flag an App-owned namespaced resource as a cross-namespace owner reference.
