## Executive Summary

The PR mirrors the bundled Docker CLI plugins into a per-instance directory, registers it in `cliPluginsExtraDirs` under `addPath`, and serializes `config.json` edits behind a cross-process lock. That lock brings two regressions. Daemon shutdown now leaves `currentContext` naming a deleted Docker context, and the default `manual` setting fails PATH management and keeps Settled False whenever docker/cli cannot load `config.json`. Standalone pruning, edit independence and the documented plugin precedence also miss #918's contracts.

Under `manual` without the marker, `computePluginDirs` can change nothing, yet `Edit` still runs `config.Load`. Load rejects invalid JSON, a malformed `auths[*].auth`, and a file that the user cannot read, such as one that `sudo docker login` left owned by root. `Reconcile` records the error as `PathManagementReasonFailed` (`reconciler.go:149-153`), because only `managedlines.ErrMalformedBlock` maps to `Malformed`. `computeSettledCondition` gates Settled on `Failed` even under `manual` (`app_controller.go:720-725`), so Settled stays False, which `rdd set --wait` waits on, and the reconcile requeues forever. `manual` is the default, and at the merge-base it never read `config.json`.

## Design Observations

### Concerns

- **(in-scope) Windows users on `manual` lose standalone `docker-compose.exe`.** The Windows bundle ships `resources/windows/docker-cli-plugins` (`build/signing-config-win.yaml`), so the removed MSI PATH entries did make `docker-compose.exe` and `docker-buildx.exe` work as commands. After this PR they are on PATH only through `~/.rd2/bin` under `front` or `back`. #918 asks for the removal, but the commit message calls the entries "dead", and release notes should mention the change. [Claude Opus 5.5]
- **(future) Our plugins shadow the user's under both `front` and `back`.** Every extra directory comes before `~/.docker/cli-plugins`, so `back` differs from `front` only against other tools' extra directories. A diagnostic that reports a shadowed copy in `~/.docker/cli-plugins`, as the old doc's open question suggested, would tell users why their compose is not the one that runs. [Claude Opus 5.5]

### Strengths

- **(in-scope)** A plugins-only directory keeps the `docker-credential-*` helpers out of docker's plugin discovery, while the bin-directory copies keep `docker-compose` and `docker-buildx` working as commands. [Codex GPT 6 Astra]
- **(in-scope)** `dockerconfig.Edit` holds the lock across load, change and save, and saves only when the callback reports a change. docker/cli's `Save` writes a temporary file and renames it, follows a symlinked `config.json`, and copies its mode. [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]
- **(in-scope)** The two locks are always taken in the same order, the PATH lock before the `config.json` lock, and the engine takes only the second. [Claude Opus 5.5]
- **(in-scope)** Writing the marker before the `config.json` write means a crash between the two still leaves a marker that a later `manual` pass acts on. [Codex GPT 6 Astra]
- **(in-scope)** Plugin-directory forwarders hardlink to the bin directory's forwarder copy, and docker's Windows candidate filter (`trimExeSuffix`) skips the `.shim` files beside them. [Claude Opus 5.5, Gemini 3.5 Flash]

## Review Process Notes

### Skill improvements

- **Cleanup made cancellable**: when a change passes a context into a call that used to run unconditionally, such as a new lock around a cleanup write, trace each caller to the point where its context is cancelled. Shutdown hooks often cancel first and clean up second, which turns the cleanup into a logged no-op while the steps after it still run.

### Repo context updates

- [repo] The engine reconciler's manager-shutdown hook calls `watcherCancel()` before `stopWatcher()`, so `removeDockerContext` and everything else `stopWatcher` reaches run with `watcherCtx` already cancelled. Flag cleanup on that path that hands `watcherCtx` to anything that checks cancellation, such as a lock wait or an API call; it needs `context.WithoutCancel` or its own bounded context.
- [repo] The path-management reconciler runs under the default `addPath=manual` too. Any error it returns becomes `PathManagementReady` reason `Failed`, which gates Settled even under `manual`; only `managedlines.ErrMalformedBlock` maps to the non-gating `Malformed`. Flag a new step in that reconcile that reads or validates a user file when it has nothing to change, because a file the user broke then holds every `rdd set --wait`.

**Concerns**

I3. **apply holds path lock across docker edit and short-circuits plugin cleanup** — `rdd/pkg/controllers/app/pathmanagement/controllers/reconciler.go:215-224` (important, regression)

```go

	unlock, err := acquirePathLock(ctx)
	if err != nil {
		return err
	}
	defer unlock()
	if err := r.applyPath(ctx, strategy, forceRemove); err != nil {
		return err
	}
	return r.applyDockerPlugins(ctx, strategy, forceRemove)
}
```

`apply` holds `pathManagementLock` while running `applyDockerPlugins` (line 223), which acquires a second cross-process lock (`dockerconfig.lock`). If `dockerconfig.lock` waits, `pathManagementLock` remains blocked for up to 30 seconds across instances. Additionally, line 221 short-circuits: if `applyPath` fails (e.g. malformed shell file), `applyDockerPlugins` is skipped. During `Unwind` (line 206), an `applyPath` error leaves `cliPluginsExtraDirs` orphaned in `config.json` before `service.Delete` deletes the target directory.

-	}

+		unlock, err := acquirePathLock(ctx)

+		}

###### Design Observations

###### Concerns

- **No plugin directory pruning in standalone mode** `(future)`: `ensureSelfLinks` (`binlinks.go:201`) runs when `rdd` is executed standalone (such as after the application bundle is uninstalled). It prunes dangling links and forwarders in `binDir`, but does not inspect or prune `DockerCliPluginsDir()`. On Windows, leftover forwarders in `docker-cli-plugins` will remain regular files after app deletion until `rdd svc delete` is invoked.

###### Strengths

- **Cross-process serialization via `pkg/dockerconfig`**: Centralizing `~/.docker/config.json` access behind `dockerconfig.Edit` with file locking prevents race conditions between the engine controller (`currentContext`) and path-management controller (`cliPluginsExtraDirs`), as well as across concurrent daemon instances.
- **Atomic link management on Windows**: Hardlinking plugin forwarders to the bin directory's master copy (`rdd-forwarder.exe`) avoids redundant forwarder binaries while cleanly isolating CLI plugin discovery.

###### Testing Assessment

- **I2 (required)**: Decided by check 3 ("How would a user see it?"). A user with an existing invalid auth credential in `~/.docker/config.json` running default `addPath: manual` encounters permanent reconcile failure. Verified with reproducer test `TestApplyDockerPluginsManualMalformedConfigNoMarker`.
- **I3 (required)**: Decided by check 3 ("How would a user see it?"). A failure in shell startup file editing aborts `Unwind`, leaving orphaned Docker plugin paths in `config.json`.
- **S1 (optional)**: Decided by check 2 ("Does the code run only for us?"). Internal test helper consistency.
- **S3 (optional)**: Decided by check 1 ("Does an existing test catch it?"). Unit test coverage gap in `reconciler_test.go`.

###### Documentation Assessment

`rdd/docs/design/api_app.md` line 49 reverses the actual plugin search order of Docker CLI (`I1`). The documentation should clarify that `cliPluginsExtraDirs` is evaluated before `~/.docker/cli-plugins`.

###### Commit Structure

Commit `c6c37a58d` bundles backend changes with the TypeScript client regeneration in `pkg/rdd-client/gen/`. By repository convention, client regenerations are typically placed in a dedicated `RDA: rdd-client: regenerate` commit.

###### Acknowledged Limitations

- **Shared config.json ordering between instances**: Issue #918 notes that multiple instances with `front` share `~/.docker/config.json`, so the last writer determines which instance's plugins take precedence.
- **Leftover forwarders on Windows after app uninstall without rdd svc delete**: Issue #918 notes that if an uninstall leaves `~/.rd2` behind, forwarders remain regular files on Windows and Docker reports `unknown command: docker compose` rather than falling through to subsequent search paths.
