Executive Summary ¶

PR #379 makes shutdownAllHostagents reclaim each hostagent's PID file, socket, tmp files, and WSL2 distro after every exit, not only after a timeout. This fixes the Windows force-kill case, where exec.CommandContext terminates the hostagent before its own teardown runs and the stale PID file misleads the next rdd svc start. The change is correct, simplifies the loop, and adds a cross-platform regression test. No blocking issues.

All three reviewers converged on one concern — stopInstanceForcibly now kills a stored Windows PID that could be recycled — but split on severity (Gemini critical, Codex important, Claude design observation). Verification against the code resolves it downward: the hazard is pre-existing and documented (limavm_lifecycle.go:225-233), and this change narrows net exposure rather than widening it. It lands in Design Observations, leaving two minor suggestions.

Design Observations ¶

Concerns ¶

  • Windows PID-recycle window on the new cleanup path (future) Claude Codex Gemini — On Windows, store.Inspect returns the PID from a stale ha.pid without a liveness check, so stopInstanceForcibly → KillTree runs taskkill /F /T /PID against a PID the OS may have recycled. This change adds one more site that does so, now on the post-procExited path. Three facts keep it out of the findings list. The hazard is pre-existing and documented (limavm_lifecycle.go:225-233), with the same Inspect-then-kill pattern already in handleUnwatchedState/killOrphanedHostagent and shutdownHostagent. The new window is milliseconds — cleanup fires right after the force-kill — versus the seconds-to-minutes window of the next-start path it removes. And by clearing the PID file during shutdown, the change stops killOrphanedHostagent from killing an even staler PID at the next rdd svc start. Net exposure drops. The documented proper fix — validate process identity before taskkill, or adopt Windows Job Objects — would close it everywhere at once.
  • Hostagent lifetime is coupled to the manager context (future) Codex Gemini — exec.CommandContext(ctx, …) ties the hostagent to the manager context, so cancellation force-kills it before shutdownAllHostagents can run an orderly interrupt-wait-kill sequence. That coupling is the root reason the Windows exit only looks graceful and this cleanup is needed at all. Detaching with context.WithoutCancel(ctx) (Go 1.21+) would let the hostagent receive the interrupt and self-stop, closing the teardown gap at its source. The tradeoff is real: a hostagent that ignores the interrupt would survive the service exit entirely, so the timeout-and-force-kill path this PR strengthens stays necessary as a backstop. Worth weighing as a separate change, not a defect in this one.

Strengths ¶

  • The refactor collapses the old if !graceful branch and its duplicate cleanup-and-wait block into one unconditional path and drops the graceful bool — less code, one path to reason about. Claude
  • The "no-op when already clean" reasoning holds end to end: on a clean exit the PID file is gone, so inst.HostAgentPID == 0 and KillTree never runs; on the Windows force-kill path KillTree returns nil for the dead parent (exit 128, process_windows.go:84), so allKilled stays true and PID/tmp-file removal and distro termination proceed. Claude
  • The context.Background() cleanup context is correctly justified — it must outlive the cancelled manager context — and carries an explaining comment. Codex Claude

Testing Assessment ¶

The new assertion targets the fix directly and runs where it matters: the CI matrix pairs windows-latest with the bats-lima suite (.github/workflows/bats.yaml:42-54), so the Windows force-kill path — the only platform where the assertion fails pre-fix — is exercised. On Unix the hostagent self-cleans, so the assertion passes with or without the fix; its discriminating power is Windows-only, which is expected for a Windows bug and not a gap.

Untested scenarios, by risk:

  1. WSL2 distro termination after rdd svc stop (see S2) — the test checks the PID file, not the distro, leaving half the documented bug unguarded.
  2. Multiple concurrent instances — shutdownAllHostagents loops over every instance, but the test exercises a single VM, so the per-instance unconditional cleanup is untested under N>1.

Documentation Assessment ¶

In-code documentation is thorough: the comment block at limavm_controller.go:529-538 explains the Windows force-kill rationale and the no-op-on-clean-exit behavior, and the bats comment at lines 335-340 documents the cross-platform intent. The one gap is the now-stale function doc comment (S1). No user-facing docs need updating — this is internal shutdown behavior.

Acknowledged Limitations ¶

  • PID recycling between Inspect and kill — limavm_controller.go:535-536 ("Inspect before killing so PIDs are still valid (not yet recycled)"), with the fuller rationale at limavm_lifecycle.go:225-233. The author accepts the recycle window and mitigates it by inspecting immediately before killing. Covered by the first Design Observation.
  • Orphaned Windows child processes are accepted as harmless — process_windows.go:73-78: when the parent is already dead, taskkill /T cannot traverse the tree, "but this is acceptable: orphaned port forwarders cannot rebind their ports and are harmless." This answers the child-process-leak concern Gemini raised under its critical finding.
  • Sequential per-instance wait — limavm_controller.go:520-521: "TODO: Wait on all hostagents in parallel instead of sequentially." Pre-existing; this change makes it slightly more relevant by adding per-instance cleanup to each sequential pass.
  • Child handles keep the PID visible on Windows — limavm-running.bats:343-345: the test deliberately skips the process-death check on Windows and defers it to the next test, because child wsl.exe handles keep the hostagent PID in the process table after termination.

When a review flags one of these call sites as a PID-recycling bug, place it under Design Observations rather than Critical/Important, and compare the new call site's recycle window against the existing accepted ones — a cleanup that fires milliseconds after a force-kill is narrower than one that fires at the next service start.
