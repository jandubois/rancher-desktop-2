## Suggestions

S1. **`store.Inspect` and the host-switch goroutine run on every platform to feed a Windows-only bridge** — `rdd/pkg/hostagent/command.go:191` [Claude Opus 4.8, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]

```go
	hsLogger := newLogrusLogger("host-switch", hsVerbosity)
	go func() {
		// Inspect inside the goroutine so it neither blocks ha.Run nor aborts
		// the hostagent: its only consumer is host-switch's WSL2 check, and on
		// Windows it can shell out to wsl.exe. A lookup failure degrades only
		// WSL2 networking; the VM and hostagent keep running.
		inst, err := store.Inspect(hsCtx, instName)
```

On macOS and Linux `hostswitch.Run` is a compiled no-op (`hostswitch_other.go:22`) that ignores its instance argument, yet the goroutine and its `store.Inspect` run on every platform. Inside the hostagent, `Inspect` takes the `HostAgentPID != 0` branch and makes a 3s-capped HTTP round-trip to this process's own socket, so the call is pure waste off Windows. An `Inspect` failure there logs `Failed to inspect instance for host-switch; WSL2 guest networking is unavailable`, which is nonsensical on a platform with no WSL2. All four reviewers raised this.

Fix: gate the goroutine on `runtime.GOOS == "windows"` (already imported), or give `Run` the instance name and move `Inspect` into the Windows implementation, where the no-op needs no lookup.

```go
	if runtime.GOOS != "windows" {
		return ha.Run(cmd.Context())
	}
```

S2. **Comment and Normal-Stop diagram overstate that the shutdown goroutine finishes before the process exits** — `rdd/pkg/hostagent/command.go:177` [Claude Opus 4.8, Codex GPT 5.6 Sol]

```go
	// cancelled context lets host-switch take its clean-shutdown path instead of
	// logging a spurious failure as the process exits.
	hsCtx, hsCancel := context.WithCancel(ctx)
	defer hsCancel()
```

The fix reliably suppresses the spurious error. `runOnce` blocks in `ln.Accept()` and returns only when cancellation closes its listener, so `runLoop`'s `ctx.Err()` check (`retry.go:31`) is always true on a stop and the error branch never runs. What the comment and the Normal-Stop diagram (`networking.md:135`) overstate is that the goroutine "exits cleanly" before the process does. The goroutine is fire-and-forget. `hsCancel()` fires as `hostagentAction` returns, then the process unwinds without joining it, so `unexposeAllForwards` and the clean-exit log usually lose the race to process exit. That is harmless, because the OS reclaims the vsock, network, and ports on exit.

Fix: soften the comment and the diagram to say the cancelled context suppresses the spurious error, with cleanup best-effort and OS reclamation the guarantee.

## Design Observations

All three concerns moved into this PR verbatim and are already recorded in `deep-review-context.md`. The PR neither introduces nor worsens them; the move is a natural moment to revisit the first two.

### Concerns

1. **The Docker named pipe is unscoped and the socketbridge bind error is swallowed** `(in-scope)` [Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]

`socketbridge.NewDockerHostBridge` binds the well-known `\\.\pipe\docker_engine`, which Docker Desktop also owns, and the errgroup goroutine at `hostswitch_windows.go:176-182` logs the bind failure then returns nil, so the new supervisor never retries it. The engine controller dials the same path and accepts any successful ping, so Docker Desktop's daemon can be mirrored and its containers removed. Now that each hostagent owns the bridge, two concurrent WSL2 VMs also contend for the one pipe, and the first to bind wins.

2. **Host-switch failures no longer reach the daemon log or the control plane** `(future)` [Claude Opus 4.8, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]

Diagnostics now flow through `logrusSink` to the hostagent's stderr, which lands in the per-instance `ha.stderr.log`. RDD watches lima events with `propagateStderr=false` (`hostagent_watcher.go:130`), so these lines never reach `rdd.stderr.log`, and the removed `HostSwitchRestarted` event means a wedged bridge no longer surfaces on the LimaVM or in App readiness. A structured lima `events.Event` on stdout, which the watcher already parses, would restore a controller-visible signal without making the manager own the restart.

3. **Internal restarts accumulate gvisor netstacks** `(future)` [Claude Opus 4.8, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]

`virtualnetwork.VirtualNetwork` exposes no `Close`, so each pass through `runOnce` leaves the previous netstack and its goroutines behind. The old design had the same property at the same 15s rate, so this is a gap rather than a regression, but a hostagent surviving a long crash loop now accumulates them for the VM's whole life.

### Strengths

1. **The ownership model is the real win** [Claude Opus 4.8, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]

Tying the bridge to the hostagent deletes four `stopHostSwitch` call sites, an `atomic.Bool`, a second mutex, and a reconciler branch, and replaces them with OS reclamation that a new shutdown path cannot forget.

2. **The retry loop is now extracted and genuinely tested** [Claude Opus 4.8, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]

`runLoop` isolates the one piece of new logic, decoupled from `runOnce` and the concrete interval, so `retry_test.go` exercises rate limiting, the `err == nil` hot-loop guard, and cancellation on every platform.

3. **`logrusSink` is a faithful funcr adapter** [Claude Opus 4.8, Codex GPT 5.6 Sol, Gemini 3.1 Pro]

It mirrors funcr's own `fnlogger`: value-receiver `With*` methods return `&l`, and funcr's three-index `AddValues` copy prevents a shared backing array, so derived loggers are safe. It preserves the Info/Error level split the Round 1 callback lost.

## Review Process Notes

### Skill improvements

- When a finding claims a supervised loop logs a spurious error on clean shutdown, or fails to take its clean-shutdown branch, first identify what unblocks the loop's blocking call (an `Accept`, a channel receive, a syscall). Context cancellation does not interrupt most blocking primitives directly. If the loop returns only because a cancellation-triggered close unblocks that primitive, the loop's own cancellation check is satisfied by construction on shutdown and the error branch is unreachable. Trace which event returns the blocking call before rating the claim, because the cancellation-observed-first ordering is a property of the wiring, not of wall-clock timing.

### Repo context updates

- [repo] UPDATE the entry directing reviewers to verify that every shutdown path in the LimaVM controller's lifecycle code calls `stopHostSwitch` alongside `stopWatcher`. The host-switch now runs inside the per-VM hostagent process under `rdd/pkg/hostswitch/`, not the LimaVM controller; the reconciler neither starts nor stops it, and `stopHostSwitch` no longer exists. The OS reclaims the vsock listeners, gvisor network, and host ports when the hostagent exits with the VM, so there is no reconciler-side host-switch teardown to check.
