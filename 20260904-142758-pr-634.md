## Executive Summary

The staging mechanism is correct and faithful to the investigation gist. The pinned SHA-256 matches AMD's release byte-for-byte, the `.deb` extraction handles the real archive's symlinks properly, and marker-last write ordering is crash-safe. The issues below are all variants of one theme — the guest can end up without the bridge, or with a stale one, while the API reports success.

Four Important findings: a `spec.gpu.source` change never reaches the guest, a failed stage is silent and unretried, the design doc's pod contract drops the `hostPath` type guards the gist proved, and the package is described as MIT when the staged library links a proprietary blob. I have grouped the findings by the failure they produce; several span more than one file.

## Critical Issues

None.

## Important Issues

I1. **Changing `spec.gpu.source` restages the host but never reprovisions the guest** — `rdd/pkg/controllers/app/app/controllers/app_controller.go:161` [Codex GPT 5.6 Sol]

```go
		fmt.Sprintf("  GPU_ENABLED: %v", spec.GPU.Enabled && gpuWindowsHostSupported()),
		fmt.Sprintf("  GPU_LIB_SOURCE: %q", toLinuxPath(instance.GPUDir())),
```

`GPU_LIB_SOURCE` is `instance.GPUDir()`, a constant. `spec.GPU.Source` reaches no template parameter, so switching the override from one directory to another re-stages the host files and leaves the rendered template byte-identical. The ConfigMap comparison at `app_controller.go:490` then finds no change, the VM never restarts, and provisioning — which only runs at boot — keeps installing the previous library. `Settled` reports success. A `gpu.Version` bump fails the same way, though it usually ships with a build upgrade that restarts the VM anyway; the `source` case has no such mitigation.

```go repro
	mk := func(src string) string {
		out, _ := applySpecToTemplate("base",
			v1alpha1.AppSpec{GPU: v1alpha1.GPUSpec{Enabled: true, Source: src}}, 0)
		return out
	}
	a, b := mk(`C:\old`), mk(`C:\new`)
	t.Logf("gpu.source C:\\old vs C:\\new -> templates identical: %v", a == b)
	// Control: a field that IS a template input must differ.
	on, _ := applySpecToTemplate("base", v1alpha1.AppSpec{GPU: v1alpha1.GPUSpec{Enabled: true}}, 0)
	off, _ := applySpecToTemplate("base", v1alpha1.AppSpec{GPU: v1alpha1.GPUSpec{Enabled: false}}, 0)
	t.Logf("control: enabled vs disabled  -> templates identical: %v", on == off)
```

```text repro-output
gpu.source C:\old vs C:\new -> templates identical: true
control: enabled vs disabled  -> templates identical: false
```

Fix: derive a digest over the two staged files and emit it as a template param, published only after staging succeeds, so a content change forces exactly one restart.

I2. **A failed stage is invisible, and nothing retries it** — `rdd/pkg/controllers/app/app/controllers/app_controller.go:339` [Claude Opus 5, Gemini 3.1 Pro, Codex GPT 5.6 Sol]

```go
	if err := r.reconcileGPUFiles(ctx, app.Spec); err != nil {
		log.Error(err, "Failed to reconcile GPU support files; continuing without GPU passthrough")
	}
```

The comment documents the non-fatal swallow as intended, and that rationale holds. It does not cover the aftermath. `applySpecToTemplate` still emits `GPU_ENABLED: true`, the guest script warns to stderr and exits 0, no condition records GPU state, so `Settled` flips True and `rdd set gpu.enabled=true` returns 0 with no GPU. `SetupWithManager` (`app_controller.go:723`) registers no periodic requeue, so recovery waits for an unrelated watch event or controller-runtime's 10-hour default resync (`defaultSyncPeriod`, cache.go:45, v0.24.1). GitHub CDN throttling is a known failure mode for this project, which makes the transient case realistic.

```go repro
	stageErr := gpu.Stage(context.Background(), t.TempDir(), "/definitely/not/a/real/dir")
	t.Logf("staging FAILED: %v", stageErr)
	got, _ := applySpecToTemplate("base",
		v1alpha1.AppSpec{GPU: v1alpha1.GPUSpec{Enabled: true, Source: "/definitely/not/a/real/dir"}}, 0)
	off, _ := applySpecToTemplate("base", v1alpha1.AppSpec{GPU: v1alpha1.GPUSpec{Enabled: false}}, 0)
```

```text repro-output
staging FAILED: librocdxg.so not found in /definitely/not/a/real/dir
template still says:  GPU_ENABLED: true
control (gpu.enabled=false) emits:  GPU_ENABLED: false
```

Fix: keep the swallow, but requeue on failure and write a `GPUReady` condition with reasons (`Staged`, `StagingFailed`, `UnsupportedHost`) so the CLI and UI can see it.

I3. **The design doc's "proven contract" drops the `hostPath` type guards the gist and the example both keep** — `rdd/docs/design/gpu_passthrough.md:83` [Gemini 3.1 Pro, Claude Opus 5, Codex GPT 5.6 Sol]

```yaml
  - { name: wsl-lib,   hostPath: { path: /usr/lib/wsl/lib } }
  - { name: librocdxg, hostPath: { path: /opt/rocm/lib/librocdxg.so } }
  - { name: dids,      hostPath: { path: /opt/rocm/share/rocdxg/dids.conf } }
```

The gist's manifest and the shipped `vllm-pod.yaml:44-48` both specify `type: Directory` / `type: File`; the design doc, which is what readers copy, omits them. Kubernetes performs no check for the empty default, so a pod applied while staging is absent — the state I2 makes reachable silently — leaves a *directory* at the library path. Both later paths then misbehave, reproduced against GNU coreutils 9.11:

```sh repro
T=$(mktemp -d); mkdir -p "$T/dst/librocdxg.so" "$T/d"; echo lib > "$T/src"
ginstall -D -m 0755 "$T/src" "$T/dst/librocdxg.so"; echo "install exit=$?"
find "$T/dst" | sed "s|$T||"
rm -f "$T/d"; echo "rm exit=$?"
```

```text repro-output
install exit=0
/dst
/dst/librocdxg.so
/dst/librocdxg.so/src        <- nested inside; the mount target is still a directory
rm: /tmp/.../d: is a directory
rm exit=1                    <- under `set -o errexit` the provision step aborts
```

So the enable path silently no-ops forever while reporting success, and the disable path fails the boot provisioning.

Fix: restore `type: Directory` / `type: File` in the doc, and consider `rm -rf` at `lima-template.yaml:177` to make the disable branch resilient.

I4. **The staged library is described as MIT-licensed but links a proprietary blob, and the required notice is discarded** — `rdd/pkg/gpu/gpu.go:14` [Codex GPT 5.6 Sol]

```go
//   - Fetched (default): download AMD's official, MIT-licensed rocdxg-roct
//     Debian package from the pinned GitHub release, verify its SHA-256, and
```

The same claim appears at `gpu_passthrough.md:35`. The package's own `LICENSE.md` says the MIT grant holds "except where noted otherwise" and carves out `src/thunk_proxy/libthunk_proxy.a` under an AMD proprietary licence — and that blob is statically linked into the very file being staged. That licence permits binary redistribution but requires that "Redistributions must reproduce the above copyright notice, this permission notice, and the following disclaimers"; `extractFromDeb` keeps only the `.so` and `dids.conf`, dropping `LICENSE.md`.

```sh repro

strings -a opt/rocm/lib/librocdxg.so.1.2.2 | grep -m2 thunk_proxy
```

## Suggestions

S1. **The generated TypeScript client has no `gpu` field** — `pkg/rdd-client/gen/models/IoRancherdesktopAppV1alpha1AppSpec.ts:25` [Codex GPT 5.6 Sol]

`AppSpec` gains `GPU`, but the generated client has neither a `gpu` property nor a sibling `…AppSpecGpu.ts` model, while every other nested spec (`…AppSpecKubernetes.ts`, `…AppSpecVirtualMachine.ts`) has one. Typed App responses drop the field. No renderer consumes it yet, so impact is latent.

Fix: run `yarn generate:rdd-client` and commit the result.

S2. **The design doc lists Ollama as confirmed, but nothing confirmed it** — `rdd/docs/design/gpu_passthrough.md:9` [Codex GPT 5.6 Sol]

The doc names "`rocminfo`, raw HIP kernels, `llama.cpp`, and Ollama" and says "This has been confirmed end-to-end". The gist proves `rocminfo`, a HIP vector-add, and llama.cpp; the word "ollama" appears zero times in it, and the second commit adds vLLM, not Ollama.

Fix: drop Ollama from the confirmed list, or mark it expected-but-unvalidated.

S3. **A 2-minute blocking download runs inside the singleton App reconciler** — `rdd/pkg/gpu/gpu.go:185` [Claude Opus 5]

`reconcileGPUFiles` runs at `app_controller.go:339`, ahead of the LimaVM branches. `SetupWithManager` sets no `MaxConcurrentReconciles`, so controller-runtime's default of 1 applies and a first enable parks the whole App loop — condition mirroring, `spec.running` propagation, port resolution — behind a GitHub download for up to `fetchTimeout`.

Fix: stage asynchronously and requeue, or at minimum move the call below the running/LimaVM branches so a stop request is never queued behind it.

S4. **`api_app.md` says the App controller stages into the guest; it stages on the host** — `rdd/docs/design/api_app.md:106` [Claude Opus 5]

The bullet reads "the App controller stages the ROCm-on-WSL bridge files … into the guest's `/opt/rocm`". `reconcileGPUFiles` writes only to `instance.GPUDir()`; Lima provisioning does the guest install. `gpu_passthrough.md:31` gets the split right.

Fix: "…stages the bridge files into a host directory that Lima provisioning then installs into the guest's `/opt/rocm`".

S5. **The version-pin comment states a ROCm targeting claim the evidence does not support** — `rdd/pkg/gpu/gpu.go:41` [Claude Opus 5, Codex GPT 5.6 Sol]

The comment says v1.2.2 "targets the ROCm 7.2.x series". Upstream's compatibility matrix does not list 1.2.2 at all — it maps 1.2.0 to 7.2.x and 1.2.1 to 7.14 — which is what mook-as queried and what remains unanswered. Better evidence exists elsewhere in the PR. The gist found `librocdxg.so.1.2.2` inside a ROCm 7.2.4 install, and `README.md:113` records "host ROCm 7.2.4 + librocdxg 1.2.2 bridged a ROCm 7.13 container fine". The shipped Dockerfile pins a 7.13 image while the doc's contract shows 7.2.4.

Fix: state the tested combination next to the pin rather than a support claim, and cite the README evidence there.

S6. **Shipped docs omit the host prerequisites the gist proved necessary** — `rdd/examples/vllm-gfx1151-repro/README.md:24` [Codex GPT 5.6 Sol]

The gist requires AMD Adrenalin ≥ 26.2.2 and a `wsl --update` + `wsl --shutdown` cycle. The shipped prerequisites ask only for Windows 11 + WSL2 and an already-present `/dev/dxg`; `gpu_passthrough.md` omits them too. Host gating checks only `runtime.GOOS == "windows"`, so an older driver yields a settled App and an unexplained workload failure.

Fix: add a Host Prerequisites section to both documents, linking AMD's matrix.

S7. **`test.ps1` never checks `$LASTEXITCODE`** — `rdd/examples/vllm-gfx1151-repro/test.ps1:11` [Codex GPT 5.6 Sol, Claude Opus 5, Gemini 3.5 Flash]

```powershell

$POD = "vllm-gfx1151"

Write-Host "== Waiting for pod Ready (first run also pulls/loads the model) =="
rdd kubectl wait --for=condition=Ready "pod/$POD" --timeout=1200s
```

`$ErrorActionPreference` governs cmdlets, not native-process exit codes, so a 20-minute wait timeout falls through into `kubectl exec` and surfaces a urllib traceback instead of "pod never became Ready" — and the script can still exit 0.

Fix: throw on non-zero `$LASTEXITCODE` after each `rdd` call, ideally via one helper.

S8. **`findSourceLib` picks the lexicographically last name, not the newest version** — `rdd/pkg/gpu/gpu.go:179` [Gemini 3.5 Flash, Gemini 3.1 Pro, Claude Opus 5]

```go
	sort.Strings(matches)
	return matches[len(matches)-1], nil
```

With both `librocdxg.so.1.2.2` and `librocdxg.so.1.10.0` present, string order puts `1.2.2` last, so the older library wins. The comment claims only determinism, but `api_app.md` presents `spec.gpu.source` as the version-override mechanism, so "highest-sorting" will read as "newest".

Fix: compare the suffix numerically, or reword the comment to say the choice is arbitrary-but-stable.

S9. **The download is bounded in time but not in size, and a negative `ar` size panics** — `rdd/pkg/gpu/gpu.go:200` [Gemini 3.5 Flash, Codex GPT 5.6 Sol, Gemini 3.1 Pro]

```go
	data, err := io.ReadAll(resp.Body)
```

`fetchTimeout` caps duration only; the real asset is 185 KB, so a fast unexpected body can grow the daemon's heap before the checksum runs. Separately, `strconv.Atoi` accepts a negative member size, which reaches `archive[start : start+size]`. Both need an input that also matches the pinned digest, so neither is reachable in practice — this is hardening, not a live defect.

```text repro-output
PANIC confirmed: runtime error: slice bounds out of range [68:63]
```

Fix: wrap the body in `io.LimitReader`, and reject `size < 0` next to the existing `Atoi` error check.

## Design Observations

### Concerns

- **No status surface for GPU state** *(in-scope)* [Claude Opus 5, Codex GPT 5.6 Sol] — `App.Status` gains nothing, so nothing can distinguish "installed" from "enabled but the download failed" from "enabled on macOS, where the toggle is inert". One `GPUReady` condition closes the observability half of I1 and I2 and gives a future preferences checkbox something to bind to.
- **Payload identity lives outside the template** *(in-scope)* [Codex GPT 5.6 Sol] — the template holds a fixed path while the meaningful state is the mutable files behind it. A content-addressed manifest would make restart identity and App settlement derive from the same state, which is the shared root of I1 and I2.
- **`spec.gpu.source` is a daemon-host path in a resource a remote GUI may set** *(future)* [Claude Opus 5] — every other App spec field is host-independent. This cuts against the standing constraint that the GUI and daemon must work over the socket alone and may run on different machines. A pinned URL + digest pair travels; a path does not, and it would fold the air-gapped case into the verified-download path instead of a second unverified one.
- **Runtime acquisition versus shipping the bits** *(future)* [Codex GPT 5.6 Sol, Claude Opus 5] — mook-as's proposal to build librocdxg and bundle it would delete the fetch path and with it I2, I4, S3, S9 and S16. Worth settling before this graduates from experimental, because that path is where nearly every finding clusters.

### Strengths

- **Marker-last write ordering is genuinely crash-safe** *(in-scope)* [Claude Opus 5] — two reviewers drafted a stale-marker finding here and both retracted it after tracing the windows. Every partial state across a version bump leaves the *old* marker, so the next run re-fetches. Worth preserving through any refactor.
- **The fetch is pinned properly** *(in-scope)* [Codex GPT 5.6 Sol, Gemini 3.5 Flash] — an immutable release-tag URL, a SHA-256 checked before any parsing, and the bump instruction in the comment. Extraction only ever touches verified bytes.
- **Enable/disable symmetry is carried end to end** *(in-scope)* [Claude Opus 5] — host `Unstage`, `GPU_ENABLED: false`, and guest `rm -f`, rather than leaving a manual cleanup step.
- **The guest contract matches the proven procedure exactly** *(in-scope)* [Codex GPT 5.6 Sol] — paths, 0755/0644 modes, `/dev/dxg`, `hostIPC`, both env vars, and the native-KFD scope boundary all line up with the gist.
- **`gpuWindowsHostSupported` as a test seam** *(in-scope)* [Claude Opus 5] — lets the enabled path be tested on macOS/Linux CI, which is the only automated coverage this Windows-only feature can get.

## Testing Assessment

Ranked by risk:

1. **The download path has no test at all.** `fetchDeb` is never exercised — not the non-200 branch, not the checksum mismatch, not the timeout. `fetchTimeout` is a `var` rather than a `const`, the shape of a test seam, but no test overrides it. An `httptest.Server` serving a fixture deb, a 404, and a wrong-digest body covers all three cheaply.
2. **Neither I1 nor I2 has a test.** Nothing asserts what the reconciler does when staging fails, and nothing asserts that changing `gpu.source` reprovisions — the two gaps where "reports success but did nothing" lives.
3. **The Lima provision script has no coverage.** `grep -ri gpu rdd/bats/` returns nothing. The disable branch, the missing-files warning, and the `install -D` targets are exercised only by hand on Windows. BATS cannot run this on the CI matrix, but the three branches could be shellcheck'd or driven with a fake `$PARAM_GPU_LIB_SOURCE`.
4. **`arMember` is untested against malformed input** — truncation and a non-numeric size field are unexercised (see S9).
5. **`Unstage`'s partial-failure path is untested** — the case that matters on Windows where a file may be held open.

Executed by the consolidator against the review SHA: `go test -race ./pkg/gpu/... ./pkg/controllers/app/app/controllers/...` passes (1.393s and 2.315s). The pinned asset was downloaded and its SHA-256 matches `DebSHA256` exactly. Its `data.tar.gz` contains `librocdxg.so.1.2.2` as a regular file with `.so` and `.so.1` as symlinks, confirming the `TypeReg` guard is correct. `DT_NEEDED` on the shipped object is exactly `libstdc++.so.6 libm.so.6 libc.so.6 ld-linux-x86-64.so.2 libgcc_s.so.1`, confirming the gist's portability claim; `libhsa-runtime64.so` and `libdxcore.so` appear only as runtime `dlopen` strings, supplied by the container image and WSL respectively.

`make verify-generate` fails, but only by rewriting comments in nine unrelated `containers` apply-configuration files — the known pre-existing drift on `main`, not a PR defect. The new `zz_generated.deepcopy.go` is correct for a value struct of scalars.

## Documentation Assessment

`gpu_passthrough.md` is a good document: it states the scope boundary explicitly, distinguishes what works from what cannot, and does not overclaim past the gist's Day 2 conclusion. Three corrections: the `hostPath` type omission (I3), the MIT characterisation (I4), and the Ollama claim (S2). It also never mentions that a staging failure is non-fatal and unretried, so a reader who hits I2 has no diagnostic path.

`api_app.md` has the host/guest confusion (S4), and its `spec.gpu.source` bullet ends mid-thought ("Could also be used to override the librocdxg's version, by manually installing desired version.").

The example README is strong on the *why* — the amdsmi shim rationale and the socat workaround are both well explained — but see S6 on prerequisites and S12 on prose. Its claim that a `docker build` lands the image "in the k3s containerd store" is imprecise: with the default moby engine the template runs k3s with `--docker`, so the image lands in dockerd, which k3s then reads. The outcome is right, the mechanism described is not.

`rdd/examples/` is a new directory category. Only the `Dockerfile` carries an SPDX header; `amdsmi.py`, `test.ps1`, `vllm-pod.yaml` and `README.md` do not. `make check-ltag` passes because `.ltag/` holds only `bash`, `dockerfile`, `go` and `makefile` templates, so this is a convention question rather than a CI break — worth a decision on whether new non-Go example assets should carry headers.

## Review Process Notes

### Skill improvements

- When a PR description links an external design document, gist, or investigation write-up, fetch it and inline it in the prompt as the specification of record, with an instruction to check the implementation against every concrete contract it states (paths, permissions, environment variables, version requirements) and against every negative result it records. Divergence between a proven manual procedure and the automation that replaces it is a defect class that reading the diff alone cannot surface, because both sides look internally consistent.

- When a change ships both a reference document and a runnable example of the same contract, diff them against each other and against any source procedure. The document is what readers copy and the example is what was actually executed, so a guard present in one and absent in the other marks the document as the untested copy.

- Before accepting a reviewer's claim that a shell command will fail on a given input, run that command against that input. Coreutils tools frequently succeed where a reviewer expects failure, and the difference between a loud failure and a silent wrong result inverts both the severity and the fix.

### Repo context updates

- [repo] Test functions in this repo that mutate a package-level `var` test seam are correct without `t.Parallel()` even when sibling tests in the same file call it: Go runs the sequential portion of every top-level test before resuming any paused parallel one, so a non-parallel mutating test completes, including its `t.Cleanup`, before parallel siblings observe the variable. Do not report this as a data race without first running `go test -race`; report it as latent fragility only.

- [repo] `make verify-generate` fails on `main` by rewriting comments in nine unrelated `containers` apply-configuration files. Treat a failure confined to those files as pre-existing drift, not a PR defect; only a diff touching the CRD or deepcopy files of the package under review is a real finding.

- [repo] The App reconciler registers no `MaxConcurrentReconciles` and no periodic requeue in `SetupWithManager`, so it runs single-threaded and an error swallowed inside `Reconcile` is retried only on the next watch event or controller-runtime's 10-hour default resync. Any blocking I/O added to that path serialises the whole App loop, and any best-effort error swallow needs an explicit requeue to converge.

**I1. A failed stage is silent, never retried, and `rdd set gpu.enabled=true` still reports success** — `rdd/pkg/controllers/app/app/controllers/app_controller.go:339-341` (important, regression)


The comment at lines 215-217 documents the *swallow* as deliberate ("staging is best-effort and must not wedge reconciliation, because provisioning already degrades gracefully when the files are absent") — that rationale holds. What it does not cover is the aftermath. `applySpecToTemplate` still emits `GPU_ENABLED: true` (line 160), the guest script warns to stderr and `exit 0` (`lima-template.yaml:185-187`), `computeSettledCondition` has no GPU input, so `Settled` flips True and the CLI returns 0. `SetupWithManager` (lines 723-727) registers no periodic requeue, so a transient GitHub-CDN failure — a known failure mode for this project — is never retried; and because provisioning only runs at boot, even a later successful stage does not reach the guest until a restart.

**I2. The design doc's "proven contract" drops the `hostPath` `type:` the gist proved and the example keeps** — `rdd/docs/design/gpu_passthrough.md:82-85` (important, regression)

```yaml
  volumes:
  - { name: wsl-lib,   hostPath: { path: /usr/lib/wsl/lib } }
  - { name: librocdxg, hostPath: { path: /opt/rocm/lib/librocdxg.so } }
  - { name: dids,      hostPath: { path: /opt/rocm/share/rocdxg/dids.conf } }
```

The gist's manifest and the shipped `vllm-pod.yaml:44-48` both carry `type: Directory` / `type: File`; the design doc — the contract of record readers will copy — omits them. With `type: ""` Kubernetes performs no check. The default engine is moby (`app_types.go:180`), and moby runs k3s with `--docker` (`lima-template.yaml:150`), so dockerd creates the missing source as a **directory**. That poisons both later paths, which I ran against GNU coreutils:

```text repro-output
$ install -D -m 0755 "$T/src" "$T/dest/librocdxg.so"   # dest is a directory
exit=0
/dest/librocdxg.so/src          # file nested one level down, install reports success

$ rm -f "$T/d"                  # disable path, dest is a directory
rm: cannot remove '.../d': Is a directory
rm exit=1                       # under `set -o errexit` the whole provision step aborts
```

So a pod applied before staging completes leaves a directory that makes the *next* boot's install silently no-op and the disable path fail.

Fix: restore the `type` qualifiers in the doc so they match the gist and the example:

```diff
   volumes:
-  - { name: wsl-lib,   hostPath: { path: /usr/lib/wsl/lib } }
-  - { name: librocdxg, hostPath: { path: /opt/rocm/lib/librocdxg.so } }
-  - { name: dids,      hostPath: { path: /opt/rocm/share/rocdxg/dids.conf } }
+  - { name: wsl-lib,   hostPath: { path: /usr/lib/wsl/lib, type: Directory } }
+  - { name: librocdxg, hostPath: { path: /opt/rocm/lib/librocdxg.so, type: File } }
+  - { name: dids,      hostPath: { path: /opt/rocm/share/rocdxg/dids.conf, type: File } }
```

Consider also hardening `lima-template.yaml:177` and `:190-191` against a directory at those paths (`rm -rf`, or `rm -rf "$LIB_DST"` before `install`).

**I3. A 2-minute blocking network fetch runs inside the singleton App reconciler** — `rdd/pkg/gpu/gpu.go:184-186`, called from `app_controller.go:339` (important, regression)

```go
func fetchDeb(ctx context.Context) ([]byte, error) {
	ctx, cancel := context.WithTimeout(ctx, fetchTimeout)
	defer cancel()
```

`reconcileGPUFiles` runs before every other branch of `Reconcile` (line 339, ahead of the LimaVM `Get` at line 344). controller-runtime gives the App reconciler `MaxConcurrentReconciles=1`, so during a first enable the whole App loop is parked for up to `fetchTimeout` (line 66): LimaVM condition mirroring, `spec.running` propagation, and the Kubernetes-port resolution all queue behind a GitHub download. A user who runs `rdd set running=false` mid-download waits for it. `rdd set gpu.enabled=true` blocking is intended; blocking unrelated App reconciliation is not.

Fix: do the fetch in a goroutine keyed by the pinned `Version`, have `reconcileGPUFiles` return `ErrStagingInProgress`, and requeue — this pairs naturally with the retry and `GPUReady` condition from I1. A cheaper interim fix is to move the call below the LimaVM/running/port branches so a stop request is never stuck behind it.

## Design Observations

### Concerns

**`spec.gpu.source` is a daemon-host filesystem path in a resource a remote GUI may set** *(future)* — Every other App spec field is host-independent; `source` is interpreted by `os.ReadFile` on whatever machine runs the daemon (`gpu.go:137-144`). That cuts against the standing constraint that the GUI and daemon must work over the socket alone and may run on different machines. If the field survives past the experiment, consider expressing the override as a pinned URL + digest pair (which travels) rather than a path (which does not) — that also folds the air-gapped case into the existing verified-download path instead of a second, unverified one.

**No status surface for GPU state** *(in-scope)* — `App.Status` gains nothing from this PR, so neither the CLI nor the UI can distinguish "staged and installed" from "enabled but the download failed" from "enabled on macOS, where the toggle is inert". A single `GPUReady` condition with reasons (`Staged`, `StagingFailed`, `UnsupportedHost`) would close I1's observability half and give the future preferences checkbox something to bind to. It also gives the non-Windows no-op — currently documented only in prose (`gpu_passthrough.md:119-120`) — a visible answer.

**Downloading a binary at reconcile time versus shipping it** *(future)* — See Unresolved Feedback; mook-as's point about baking `librocdxg` into the distro or the overlay would delete the fetch path, the checksum pin, the version marker, the staging directory, and I1 and I3 along with them. Worth settling before this graduates from experimental, because the download path is where every finding above clusters.

### Strengths

- The pinned `Version` + `DebSHA256` pair with the bump instruction in the comment (`gpu.go:39-52`) is exactly the right shape for a fetched binary, and the URL is an immutable release-tag path rather than a branch tip.
- Marker-last write ordering in `Stage` (lines 96-102) is genuinely crash-safe: I traced every crash window across a version bump and each one leaves the *old* marker, so the next run re-fetches. Worth preserving through any refactor.
- `gpuWindowsHostSupported` as a `var` (line 123) with `t.Cleanup` restoration lets the enabled path be tested on macOS/Linux CI, which is the only way this feature gets any automated coverage at all.
- The enable/disable symmetry is carried end to end — host `Unstage`, `GPU_ENABLED: false` in the template, and guest `rm -f` — rather than being left as a manual cleanup step.

### Design Observations

#### Concerns

- **Out-of-band payload state (in-scope):** The template contains a path while the meaningful state lives in mutable files behind that path. A content-addressed staging manifest—origin, version, both hashes—and a `GPUReady` condition would make Lima restart identity and App settlement derive from the same state, eliminating I1 and I2.

- **Runtime acquisition and custom package parsing (in-scope):** Building and bundling a reviewed archive would remove live-network failure from reconciliation, preserve notices, and replace the hand-written ar/deb extraction path. This also makes the shipped bits reproducible and auditable.

#### Strengths

- Platform gating is kept at the App/template boundary, leaving non-Windows hosts unchanged.
- The guest paths, modes, `/dev/dxg` contract, environment variables, and native-KFD scope boundary align with the proven procedure.
- The download uses an immutable versioned URL, a matching SHA-256, and a dedicated timeout; the release asset and expected archive layout were confirmed.

### Executive Summary

This PR successfully implements experimental AMD ROCm GPU passthrough for WSL2 by staging the required `librocdxg` bridge files on the host and injecting them into the guest. The headline finding is a critical cache-corruption vulnerability where non-atomic file writes, combined with an existence-only check, allow an interrupted download to permanently poison the host cache and break GPU workloads. Additional important issues include a missing Kubelet `hostPath` type that can wedge the VM rootfs and a suppressed error that leaves the controller permanently stalled on transient network failures.

### Findings

#### Critical Issues

C1. **Non-atomic file staging causes permanent cache corruption** — `rdd/pkg/gpu/gpu.go:95-102` (critical, regression)

```go repro
func TestStagedChecksExistenceOnly(t *testing.T) {
	dir := t.TempDir()
	
	// Simulate an intact directory from a previous successful run
	os.WriteFile(filepath.Join(dir, ".rocdxg-version"), []byte("1.2.2"), 0644)
	os.WriteFile(filepath.Join(dir, "librocdxg.so"), []byte("OLD_LIB"), 0755)
	os.WriteFile(filepath.Join(dir, "dids.conf"), []byte("OLD_DIDS"), 0644)

	// Simulate a crash during writeFile() of a new download.
	// WriteFile truncates the file in-place.
	os.WriteFile(filepath.Join(dir, "librocdxg.so"), []byte("TRUNCATED"), 0755)
	
	// Next run staged() check
	assert.Assert(t, staged(dir) == true, "staged() falsely passed truncated file")
}
```

```text repro-output
--- PASS: TestStagedChecksExistenceOnly
```

```go

		return err
	}
	if err := writeFile(filepath.Join(dir, DidsName), dids, 0o644); err != nil {
		return err
	}
	return writeFile(filepath.Join(dir, versionMarker), []byte(Version), 0o644)
```

`gpu.Stage` overwrites the library files in-place while leaving the old `versionMarker` intact until the very end. If the daemon crashes or is interrupted during `writeFile(LibName)`, it leaves a truncated `librocdxg.so` alongside the intact `versionMarker`. On the next reconcile, `staged(dir)` reads the marker, verifies both files exist via `os.Stat` (it does not check size or hash), and returns `true`, silently skipping the download.

This permanently poisons the host staging directory with a truncated library. Provisioning will copy the corrupted file into the guest on every boot, breaking GPU workloads until the user manually deletes the cache. The same bug applies to `stageFromSource`, which deletes the marker last.

Fix: Remove `versionMarker` before writing the files, or write to temporary paths and use `os.Rename` to atomically swap them.

```diff
 	if err != nil {
 		return err
 	}
+	os.Remove(filepath.Join(dir, versionMarker))
 	if err := writeFile(filepath.Join(dir, LibName), lib, 0o755); err != nil {
 		return err
 	}
```

### Design Observations

#### Concerns

- **Single-Threaded Reconciler Block on Download**:
  `gpu.Stage` performs a synchronous download using Go's default HTTP client under a 2-minute timeout. Since the `App` reconciler has `MaxConcurrentReconciles=1`, other reconcile requests for the `app` singleton (such as `spec.running = false`) are blocked until the download completes or times out. However, because staging is only performed once (as it is idempotent and relies on version markers) and the `.deb` package is small (3MB), the practical impact is negligible and this synchronous trade-off is reasonable for simplicity.

#### Strengths

- **Verification-First Extraction**:
  The debian archive members are extracted only *after* the entire download is completed and verified against a hardcoded SHA-256 (`DebSHA256`). This mitigates structural extraction vulnerabilities (e.g. zip slips, malicious paths, or infinite member expansions) since the processing source is strictly authenticated.
- **VM Native Mount & Copy Symmetry**:
  Instead of relying on complex drvfs mount permission mapping, the provisioning template copies staged files using `install -m 0755` and `install -m 0644`. This guarantees correct POSIX file permissions in the guest VM's writable native filesystem (`/opt/rocm/...`), completely bypasses Windows host limitations, and degrades gracefully if files are missing.

### Acknowledged Limitations

- **CDI and Device Plugin Limitations**:
  As documented by the author in `gpu_passthrough.md`, the upstream `ROCm/k8s-device-plugin` is `/dev/kfd`-based and cannot run on WSL. Pods must explicitly mount `/dev/dxg` and userspace bridge files, which is documented as a known design limitation.
- **Workload dependencies on `kfd`**:
  AIM-class charts and telemetry tools like `amd-smi` expect `/dev/kfd` topology, which is absent under WSL. This is recognized as an architectural scope boundary.
- **`librocdxg` Source Compilation**:
  As noted by `@mook-as` in comments, compiling `librocdxg` from source and distributing it as a built-in package is a potential future enhancement to avoid on-demand download.
