## Executive Summary

The PR decodes the blocks of an `xz --threads` stream concurrently and falls back to the sequential decoder for anything else. Both real image layouts decode byte-identical to `xz -d` in about 5.5 s instead of 19 to 29 s. On the shipped `-9` layout, peak RSS rises from about 460 MiB to 1.4 to 1.6 GiB, partly through an avoidable copy. Five malformed blocks the sequential decoder rejects still decode, although the commit body claims parity.

`eec59f184` says the split "checks the metadata the sequential decoder checks". It skips five checks that ulikunitz v0.5.16 makes, on reserved block-flag bits (line 146 tests only `0xc3`), nonzero header padding, a property length other than 1 (line 165 discards it), reserved dictionary-size bits (line 171 masks them off), and LZMA2 data that ends before the declared compressed size. ## Design Observations

### Concerns

- **(future) The xz preset now also sets decode memory and parallelism** [Claude Opus 5]. `rdd/Makefile:85-88` and `.github/workflows/package.yaml` justify `XZ_OPTIONS` by image size against build time. With the parallel decoder, `-9`'s 64 MiB dictionary puts a floor of 512 MiB under eight workers even after I1, and its 192 MiB blocks limit the split to eight. `-9 --block-size=64MiB` would give more, smaller blocks with the same dictionary; each option needs an image-size measurement nobody has made.
- **(future) Windows is unmeasured** [Claude Opus 5]. `punchHole` is a no-op there, so after `Truncate(total)` each out-of-order `WriteAt` probably makes NTFS zero-fill up to the highest offset written. That is inferred from NTFS's valid-data-length behavior, not measured; a timing of the decode step on `windows-latest` would settle whether the split helps there.

### Strengths

- **(in-scope) The single-stream check leaves no gap** [Claude Opus 5, Gemini 3.5 Flash]. The forward walk must reach the index exactly where the footer's backward size puts it, so a second stream, stream padding, or trailing data always falls back.
- **(in-scope) Concurrent region writers never punch each other's bytes** [Gemini 3.1 Pro, Claude Opus 5]. Hole boundaries round inward to 4 KiB, so a region boundary inside a block stays safe, as S2's test shows.
- **(in-scope) Only the container parsing is new** [Claude Opus 5]. The codec is ulikunitz's `lzma` package, and anything the parser does not recognise falls back instead of failing.

## Review Process Notes

### Skill improvements

- Read a test's comments against its body as strictly as production comments. When a comment describes an injected fault, a mutation, or a corrupted fixture, confirm the body performs it and the fixture is in the state the comment claims; a comment written for a stronger version of the test overstates coverage.
- When a finding rests on a resource measurement (peak RSS, heap, allocations), make the probe hold its inputs the way production does (embedded data is mapped read-only memory, not heap) and take several alternating samples per arm. A heap-loaded input changes the garbage collector's target and can double or halve a fix's apparent saving.
- When a review asks whether a new parser accepts input a reference implementation rejects, ask agents to derive the missing checks from the reference's source and leave building malformed inputs to the consolidator. Provider content filters can end an agent's run when a prompt asks it to craft malformed input.

### Repo context updates

- [repo] Shipped builds compress the embedded distro with `XZ_OPTIONS: -9 --threads=0` (`.github/workflows/package.yaml`), and dev and CI builds with `-1 --threads=0` (`rdd/Makefile`), so the image's xz layout differs between release and CI: about eight 192 MiB blocks with 64 MiB dictionaries against hundreds of 3 MiB blocks with 1 MiB dictionaries. A decode change measured on CI or a developer build says nothing about the shipped layout's memory or parallelism; measure both, using the published asset from the guest-deps cache for the shipped one.
