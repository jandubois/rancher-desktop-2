## Important Issues

I1. **Mock-controller PID handoff never resolves across `beforeAll`/`afterAll`** — `e2e/utils/TestUtils.ts:349,171-176` [Codex GPT 5.5, Claude Opus 4.8]

```ts
testInfo.attach('mock-controller-pid', { body: `${ controller.pid }`, ... }); // startRancherDesktop (beforeAll)
const attachment = testInfo.attachments.find(a => a.name === 'mock-controller-pid')?.body?.toString(); // teardown (afterAll)
const pid = parseInt(attachment ?? '0', 10);
if (pid) { process.kill(pid); }
```

`startRancherDesktop` (run from `beforeAll`) attaches the PID; `teardown` (run from `afterAll`) reads it. Playwright 1.60 builds a fresh `TestInfo` per test and runs the two hooks against different ones — the first test's and the last test's (verified in `workerProcessEntry.js`). For the six-test `main` suite the attachment is absent in `teardown`, so `pid` is 0 and `process.kill` never runs. The normal path still cleans up — `rdd service delete` drops the control plane and the controller self-exits via `monitorControlPlane` — but when that delete fails (line 164 catch), the `unref()`'d controller leaks. Killing a bare PID also risks a recycled PID, and `testInfo.attach` is unawaited.

Fix: hold the `ChildProcess` in module-scoped state and kill it directly.

```ts
let mockController: childProcess.ChildProcess | undefined;
// startRancherDesktop: mockController = childProcess.spawn(...)
// teardown: if (mockController?.exitCode === null) mockController.kill();
```

I2. **`teardown` skips rdd/mock cleanup when the app fails to launch** — `e2e/utils/TestUtils.ts:154-182` [Claude Opus 4.8]

```ts
export async function teardown(app, testInfo) {
  const context = app.context();   // throws when app is undefined
  await teardownApp(app);          // also throwable
  // rdd 'service delete' + mock-controller kill run only AFTER these
```

`startRancherDesktop` spawns the rdd service and the mock controller before launching Electron. If the launch throws, `electronApp` stays `undefined`; Playwright still runs `afterAll`, and `teardown` throws at `app.context()` before reaching the new cleanup at lines 160-182. Both the daemon and the mock controller then leak. The cleanup is the mock controller's only owner, yet it sits behind two throwable calls.

Fix: move the `rdd service delete` and mock-controller kill into a `finally` block, or guard them to run even when `app` is unusable.

## Suggestions

S1. **`isAppSettled` lost the not-ready tolerance the old poller had** — `e2e/pages/nav-page.ts:49-56` [Claude Opus 4.8]

```ts
const crds = await rdd('ctl', 'get', 'crds', '--output=name');
const rawApps = await rdd('ctl', 'get', 'apps', '--output=json');
```

The old `getBackendState` wrapped its query in `try/catch` and returned a `NOT_READY` sentinel; the new `isAppSettled` calls `rdd()` directly, and `rdd → tool` throws on any non-zero exit. `expect.poll` does not retry through a throw — `pollAgainstDeadline`/`raceAgainstDeadline` carry no catch, so a rejected `actual()` fails the poll immediately (verified in playwright-core). `waitForAppSettled` runs once the first window appears, which can precede apiserver readiness after `service start --wait=false`, so a transient `rdd` failure fails the test instead of polling through the not-ready window.

Fix: wrap the body in `try { ... } catch { return false; }` so the poll keeps retrying.

S2. **`controller.on('error')` catches only spawn failure and asserts in a detached callback** — `e2e/utils/TestUtils.ts:345-347` [Codex GPT 5.5, Gemini 3.1 Pro, Claude Opus 4.8]

```ts
controller.on('error', (err) => {
  expect(err, 'mock controller exited with error').toBeUndefined();
});
```

The `error` event fires only when the process fails to spawn or be killed, not on a non-zero exit. A mock controller that starts and then crashes emits `exit`, so the crash surfaces as a 30 s `waitForAppSettled` timeout with no cause. When the handler does fire, `expect().toBeUndefined()` throws inside a detached `EventEmitter` callback — an uncaught exception attributed to no test, possibly outside any active test context.

Fix: listen on `exit` for a non-zero code, and surface failures through the stored controller handle rather than `expect` inside the listener.

S3. **`lockedFields` still asserts profile state it no longer establishes** — `e2e/lockedFields.e2e.spec.ts:96,107` [Codex GPT 5.5, Claude Opus 4.8]

The suite asserts `patterns` equals `['c','d','f']` and the locked k8s version, but the `setUserProfile` call that established them is gone. The block is `.fixme`, so the assertions are dormant; re-enabling it fails. This is the residual of prior S7 and falls under the author's stated plan to rewrite or drop these suites.

Fix: restore the profile setup through the new configuration path, or update the assertions, when the suite is re-enabled.

S4. **Dead `CURRENT_SETTINGS_VERSION` imports left by the deletions** — `e2e/utils/ProfileUtils.ts:20` (see also `e2e/lockedFields.e2e.spec.ts:34`, `screenshots/screenshots.e2e.spec.ts:20`) [Claude Opus 4.8]

Removing `verifyUserProfile` and the `setUserProfile` calls left `CURRENT_SETTINGS_VERSION` imported but unused in three files. This is not a CI blocker: `eslint.config.mts:177` disables `@typescript-eslint/no-unused-vars` repo-wide during the ESLint transition, and no `unused-imports` rule runs. Drop the three imports as optional cleanup.

## Review Process Notes

**Skill improvements**

- Before trusting the `ROUND` value the lead helper exports, check the reviews branch for an existing review of the same target (`git ls-tree reviews | grep <target>`). When a prior review exists but the helper reports `ROUND=1`, treat this as round N+1 and apply the prior-round gates. The helper's round detection can miss a committed review and silently skip the prior-round reconciliation.
- When a change replaces a hand-rolled polling loop with a framework poll/retry primitive (Playwright `expect.poll`, `toPass`, testing-library `waitFor`), verify the polled function still tolerates the transient errors the old loop swallowed. Many such primitives retry only when an assertion fails, not when the polled function itself throws, so a function that now throws on a transient error fails immediately. Flag a refactor that drops a `try/catch`-to-sentinel guard from a function handed to such a primitive.
- When test cleanup hands a spawned resource's identity (PID, handle, port) from a setup hook to a teardown hook through the test framework's own facilities (attachments, annotations, context), verify the framework shares that state across those hooks. Several frameworks scope per-test state per test, so the setup and teardown hooks see different instances and the handoff silently yields nothing. Prefer module-scoped state for cross-hook resource handles.
- Cleanup that is the sole owner of a spawned process or resource must not sit behind throwable setup or teardown calls. Verify it runs even when an earlier step throws — a `finally` block or an unconditional guard. Flag must-run resource cleanup placed after a call that can throw on a partially-initialized fixture.
- For a review whose assembled prompt embeds a large inlined diff (roughly above 100 KB), budget a longer in-process Claude watchdog than the default 900 s. Thorough review of a large diff routinely exceeds it, and a watchdog kill of a still-progressing agent costs a full retry.

**Repo context updates**

- `[repo]` UPDATE the App.Status SSA convention entry (currently unqualified): the non-SSA / retry-on-conflict requirement applies only to a controller that runs alongside other App-status writers (`AppReconciler`, `EngineReconciler`). A controller started with `--controllers=` — such as the mock — is the sole status writer, so a plain read-modify-write `Status().Update` is correct there and must not be flagged. Reviewers keep flagging the mock under the production-controller rule; the prior round recommended this same update and it was not applied.
- `[repo]` Playwright (the e2e harness) builds a distinct `TestInfo` per test; `beforeAll` and `afterAll` hooks run against different instances — the first test's and the last test's. State attached in `beforeAll` via `testInfo.attach` is not visible in `afterAll`'s `testInfo.attachments`. Flag e2e cleanup that hands process or resource state between hooks through `testInfo` attachments.
- `[repo]` During the ESLint transition, the last block in `eslint.config.mts` has no `files:` restriction and disables several rules repo-wide, including `@typescript-eslint/no-unused-vars`; no `unused-imports` rule runs. Unused imports and variables do not fail CI lint. Do not flag them as CI blockers until that transition block is removed.
- `[repo]` External controllers (mock-controller and siblings) run via `external.RunControllers`, which monitors the control plane and self-exits when `rdd svc stop`/`delete` drops it. A test that deletes the RDD service cleans up the controller on the normal path; a separate kill is only a safety net for the delete-failure path.

#### Important Issues

**I1. Mock-controller cleanup via PID round-trip can silently leak the process — `e2e/utils/TestUtils.ts:349, 171-176`** (important, regression)

```ts
testInfo.attach('mock-controller-pid', { body: `${ controller.pid }`, contentType: 'text/plain' }); // in startRancherDesktop (beforeAll)
...
const attachment = testInfo.attachments.find(a => a.name === 'mock-controller-pid')?.body?.toString(); // in teardown (afterAll)
const pid = parseInt(attachment ?? '0', 10);
if (pid) { process.kill(pid); }
```

The PID is attached in `startRancherDesktop` (called from `beforeAll`, line 14 of `main.e2e.spec.ts`) and read in `teardown` (called from `afterAll`, line 19). Playwright builds a distinct `TestInfo` per test; `beforeAll`/`afterAll` hooks in a multi-test `describe` are not the same test, so `afterAll`'s `testInfo.attachments` may not contain the `beforeAll` attachment. (I could not confirm against the installed Playwright 1.60.0 — node_modules is absent in the review worktree.) If it does not, `pid` is `0`, the `if (pid)` guard skips the kill with no log, and the unref'd mock controller is orphaned (bound to the now-deleted RDD instance). Even if it works, killing a bare PID risks a recycled PID over the multi-minute test window, and `testInfo.attach` is not awaited.

Fix: hold the `ChildProcess` in a module-scoped variable (like the existing `currentTest`) and kill it directly — no round-trip, no recycled-PID hazard:
```ts
let mockController: childProcess.ChildProcess | undefined;
// in startRancherDesktop: mockController = childProcess.spawn(...);
// in teardown: if (mockController && mockController.exitCode === null) mockController.kill('SIGTERM');
```

**I2. New rdd/mock cleanup is skipped when the app fails to launch — `e2e/utils/TestUtils.ts:154-182`** (important, regression)

```ts
export async function teardown(app, testInfo) {
  const context = app.context();          // throws if app is undefined / closed
  ...
  await teardownApp(app);                  // also throwable
  // rdd 'service delete' + mock-controller kill live HERE, after the throwables
```

`startRancherDesktop` spawns the rdd service and the mock controller *before* launching Electron (lines 327-365). If the Electron launch throws, `electronApp` stays `undefined`; Playwright still runs `afterAll`, and `teardown` throws at `app.context()` (line 154) before reaching the new cleanup at lines 160-182. Both the rdd service and the mock controller then leak. The new cleanup is critical (the mock controller has no other owner) but is gated behind the throwable `teardownApp`.

Fix: move the rdd-delete + mock-kill into a `finally`, or guard them so they always run even when `app` is unusable.

### Executive Summary

The PR fixes the E2E startup test by isolating the test environment from the built-in daemon controllers and wiring it to a standalone mock controller. The remaining concerns center on the test harness: the mock controller's crash-detection handler listens to the wrong process event, and its background startup races the asynchronous `rdd service start` initialization.

### Findings

#### Critical Issues

None.

#### Important Issues

I1. **App.Status.Conditions updated without SSA or retry-on-conflict** — `rdd/pkg/controllers/mock/app_reconciler.go:57-60` (important, regression)

```go
	if changed {
		if err := r.Status().Update(ctx, &app); err != nil {
			log.Error(err, "Failed to update App status", "name", req.NamespacedName)
			return ctrl.Result{}, err
		}
	}
```

The repo convention (per `api_app.md` and repository guidelines) requires using SSA (Server-Side Apply) or `retry.RetryOnConflict` when updating `App.Status.Conditions`, as it has multiple concurrent writers (e.g., `AppReconciler`, `EngineReconciler`). Although the mock controller disables the built-in controllers and currently has exclusive access in this test environment, using a plain `Update()` establishes an unsafe pattern that will fail with `Conflict` errors if the mock is extended or environments change.

Fix: Wrap the status update in `retry.RetryOnConflict`, or apply the patch via SSA (`client.Patch` with `client.Apply`).

I2. **Mock controller crash is silently ignored** — `e2e/utils/TestUtils.ts:348-350` (important, regression)

```typescript
  controller.on('error', (err) => {
    expect(err, 'mock controller exited with error').toBeUndefined();
  });
```

In Node.js, `childProcess.spawn` emits the `'error'` event only if the process fails to spawn (e.g., `ENOENT` due to a missing binary or permissions). If the `mock-controller` spawns successfully but then panics or exits with an error code during execution, it emits an `'exit'` event, not an `'error'` event. The test suite will silently swallow the crash and hang until `waitForAppSettled` times out, obscuring the actual failure.

Fix: Listen to the `'exit'` event to catch runtime crashes:
```typescript
  controller.on('exit', (code, signal) => {
    if (code !== 0 && code !== null) {
      console.error(`mock-controller exited unexpectedly with code ${code} signal ${signal}`);
    }
  });
```

I3. **Race condition between `rdd service start` and `mock-controller` startup** — `e2e/utils/TestUtils.ts:341-347` (important, regression)

```typescript
    await spawnFile(
      path.join(topSrcDir, 'rdd', 'bin', exeName('rdd')),
      ['service', 'start', '--controllers=', '--wait=false'],
      { env, stdio: ['ignore', rddLogs, rddLogs] });
    // ...
  const controller = childProcess.spawn(
    path.join(topSrcDir, 'rdd', 'bin', exeName('mock-controller')),
```

Passing `--wait=false` causes `rdd service start` to return as soon as the service is registered with the OS, before the embedded API server has fully started and before its `kubeconfig` file is written. The `mock-controller` is spawned immediately afterward. If the controller initializes and calls `ctrl.GetConfigOrDie()` before the `kubeconfig` is populated by the service, it will panic and exit, leaving the test suite to eventually fail via timeout.

Fix: Add a polling loop to wait for the API server's `kubeconfig` to exist (or wait for `rdd ctl get --raw /healthz` to succeed) before spawning the `mock-controller`.
