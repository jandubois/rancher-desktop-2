## Critical Issues

C1. **A HostInfo bootstrap failure stops every controller, and the daemon keeps reporting ready** — `rdd/pkg/controllers/rdd/hostinfo/controllers/hostinfo_controller.go:73-75` [Claude Opus 4.8]

```go
func (r *HostInfoReconciler) Start(ctx context.Context) error {
	return r.bootstrapSingleton(ctx)
}
```

`Start` is registered as a manager `Runnable` (`SetupWithManager` calls `mgr.Add(r)`). When a Runnable returns a non-nil error, controller-runtime aborts `mgr.Start` and stops **all** runnables — app, lima, containers, rdd. `SharedControllerManager.Start` propagates that error (`manager.go:284`), and `service.go:927` merely logs it and lets the goroutine return while `rdd svc serve` stays blocked on `<-ctx.Done()`. Because `MarkControlPlaneReady` already fired at `manager.go:201`, the CLI and GUI see a healthy control plane with zero reconcilers.

Round 3 traded an empty `HostInfo.Status` for a silent, total control-plane outage. The doc comment's claim that "the daemon exits and is restarted" is false — nothing restarts it.

Fix: retry the bootstrap instead of failing the manager, so this Runnable never returns a non-nil error outside shutdown.

I2. **Host detection is duplicated, and the validator never reads `HostInfo`** — `rdd/pkg/controllers/rdd/hostinfo/controllers/hostinfo_controller.go:52-53` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro]

## Suggestions

S1. **`Reconcile` populates any HostInfo name and logs on every no-op pass** — `rdd/pkg/controllers/rdd/hostinfo/controllers/hostinfo_controller.go:41` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro] (Round 3 S3, unaddressed)

S2. **`RDD_VM_CPUS` is parsed on every admission request, not once at construction** — `rdd/pkg/controllers/app/app/controllers/app_defaulter.go:100-106` [Claude Opus 4.8]

```go

	if val := os.Getenv(vmCPUsEnv); val != "" {
		n, err := strconv.Atoi(val)
		if err != nil || n < 1 {
			return fmt.Errorf("invalid %s value %q: want a positive integer", vmCPUsEnv, val)

```

`NewAppDefaulter`'s own doc states the convention: parse config once "so that a malformed JSON fixture causes controller startup to fail rather than the first admission request." The env read breaks it. The daemon's environment is frozen at spawn, so re-reading per request buys nothing, while a typo lets the control plane come up ready and then deny every App write.

Round 3 assessed this path as acceptable fail-fast for a CI knob and the code has not changed since, so it stays a Suggestion — but the constructor is the right home.

Fix: resolve the override once in `NewAppDefaulter` and return the parse error from the constructor.

S3. **The env override is clamped, so it behaves unlike the spec field it mirrors** — `rdd/pkg/controllers/app/app/controllers/app_defaulter.go:107-109` [Claude Opus 4.8]


Round 3 asked for the built-in default to be clamped; this commit clamps the `RDD_VM_CPUS` override too. The result is asymmetric: `spec.virtualMachine.cpus=8` on a 4-core host is rejected by the validator, while `RDD_VM_CPUS=8` is silently reduced to 4. CI is unaffected — Linux sets `3` and macOS `4` on 4-core runners — so this is a wart, not a break.

Fix: clamp only the built-in default, and either reject an over-large override or clamp it with an explicit log line.

S4. **The "preserves other fields" test sets no VM property** — `rdd/bats/tests/32-app-controllers/virtual-machine.bats:59-62` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro] (Round 3 S7, unaddressed)

S5. **`--for=create` returns before the Status is populated** — `rdd/bats/tests/32-app-controllers/virtual-machine.bats:25` [Claude Opus 4.8]

S6. **A comment describes a fallback the defaulter forecloses** — `rdd/pkg/controllers/app/app/controllers/app_controller.go:128-130` [Claude Opus 4.8]

## Design Observations

### Concerns

- **A controller in the `rdd` group can now take down the `app`, `lima`, and `containers` controllers** `(in-scope)` [Claude Opus 4.8]. All of them share one `SharedControllerManager`, and a `Runnable` error is manager-fatal. Before this PR no controller could fail the manager after startup. Beyond fixing C1, the rule is worth writing down: a `manager.Runnable` added by a controller must never return a non-nil error outside shutdown, because the blast radius is every sibling controller.
- **The `HostInfo` CRD is written but never read by the code that motivated it** `(in-scope)` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro]. Issue #498 asks that validation use the saved values and that the GUI fetch them from the same place. The GUI half landed; the validation half did not, leaving a `rdd`-group controller whose only consumer is out-of-tree (see I2). A shared `pkg/hostinfo.Detect()` is the cheaper fix and keeps the App webhook free of a cross-group dependency; having the webhook read `HostInfo.Status` is the fuller one and costs an `app`→`rdd` dependency. Either is defensible — worth stating the choice in `api_app.md`.

### Strengths

- **The defaulter is now provably self-consistent** `(in-scope)` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro]. Walking the full input range confirms it: the CPU clamp bounds the default by `hostInfo.CPUs`; `mem/4` is bounded above by host memory and floored at 2Gi, which never exceeds a host that passed the sub-2Gi check; and both clamps are guarded on a positive reading, so a zero `HostInfo` falls through to values the validator accepts. Returning a distinct "host below the minimum" error rather than writing an un-admittable default is exactly what Round 3 asked for.
- **Defaulting in the mutating webhook** `(in-scope)` [Claude Opus 4.8, Codex GPT 5.5]. Keeping zero-value handling in admission lets `rdd set`, the reconciler, and the template writer treat cpus/memory as plain values.
- **Appended YAML replaced the regex rewrite** `(in-scope)` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro]. This removed `applyVMCPUsOverride` and its "no cpus line" failure mode outright.

## Review Process Notes

### Skill improvements

- **When a fix hands an error to a framework, verify what the framework does with it and what the process does afterwards. Returning an error is a claim about the caller, not the callee.** A change that replaces "log and continue" with "return the error so the caller retries/restarts/surfaces it" only improves things if a caller actually retries, restarts, or surfaces it. Read the registration site to learn which callback contract the function satisfies, read the framework's handling of a non-nil return, and read the application's handling of the framework's own return value. Flag any path where the error escalates past the failing component's blast radius — a local degradation converted into a process-wide or subsystem-wide abort is a regression, even when the diff reads as hardening and the commit message calls it a fix.

- **Treat a comment that explains why something is safe to omit as a claim to verify, not as context to accept.** Comments that justify an absence — no requeue because "the next reconcile will retry", no lock because "only one goroutine reaches this", no check because "the caller already validated" — are load-bearing: if the justification is false, the omission is the bug. Locate the mechanism the comment names and confirm it exists and can fire on the path described. A rewritten comment that replaces one such claim with another deserves the same scrutiny as the original, because a fix that corrects the code but keeps the reasoning style often just relocates the false claim.

- **When the change under review deletes or renames a construct that checked-in documentation describes, the resulting documentation error is a defect the change introduced, not a pre-existing gap.** Rate it as a finding against this change rather than carrying it as a standing docs suggestion, and quote the now-false sentence. Documentation that contradicts shipped behavior misleads more than absent documentation.

### Repo context updates

- **[repo]** A `manager.Runnable` registered with `mgr.Add()` is manager-fatal in this repo. When its `Start` returns a non-nil error, controller-runtime aborts `mgr.Start` and stops **every** controller in the `SharedControllerManager` — app, lima, containers, rdd. `pkg/service/cmd/service.go` only logs that error and lets its goroutine return, while `rdd svc serve` stays blocked on `<-ctx.Done()`, and `MarkControlPlaneReady` has already fired by then. The result is a daemon that reports a healthy control plane while running zero reconcilers. Never accept "return the error so the manager retries it" or "so the daemon restarts" as a recovery mechanism here: the manager does not retry Runnables, and nothing restarts the daemon. A bootstrap Runnable must retry internally and return nil.

- **[repo]** `rdd ctl wait --for=create <resource>` is satisfied by the bare object, before any controller populates its `.status`. A bats test that waits for create and then reads a status field races the reconciler that fills it. Gate on the status instead — `rdd ctl wait --for=jsonpath='{.status.<field>}' <resource>`.

## Design Observations

### Concerns

- **The `HostInfo` CRD is written but never read by the code that needed it.** `(in-scope)` The stated purpose in #498 is that "Validation will use these saved values, and the GUI can fetch them from there as well." The GUI half landed; the validation half did not. The webhooks snapshot `DetectHostInfo()` at setup and never touch the CRD. The concrete cost is I2's drift risk, plus a `rdd`-group controller whose only consumer is out-of-tree. Two viable shapes: (a) minimal — a shared `pkg/hostinfo.Detect()` both call, keeping the webhook independent of the `rdd` group (no cross-group `--controllers` dependency, which is the property the current code accidentally has and should keep deliberately); or (b) full — the webhook reads `HostInfo.Status` through the manager cache, making the CRD the single source of truth at the cost of a hard `app`→`rdd` group dependency. (a) is the better fit for this codebase; whichever is chosen, say so in `api_app.md`.

- **The `rdd` group's HostInfo controller can now take down the `app`, `lima`, and `containers` controllers.** `(in-scope)` They share one `SharedControllerManager`, and a Runnable error is manager-fatal. Before this PR, no controller in the shared manager could fail the manager after startup. C1's retry restores that property; the general rule worth writing into `docs/design/controllers.md` is that a `manager.Runnable` added by a controller must never return a non-nil error outside of shutdown.

### Strengths

- Moving `cpus`/`memory` out of `lima-template.yaml` and appending them from the spec (the shape Jan sketched in his PR comment) removed `applyVMCPUsOverride`'s regex rewriting entirely, along with its "no cpus line" failure mode.
- Keeping all zero-value handling in the mutating webhook — so `rdd set`, the reconciler, and the template writer all treat `cpus`/`memory` as plain values — is the right layering and directly answers Jan's first review round.
- `defaultVMMemory` returning a *distinct* "host below the minimum" error rather than writing a default the validator would then reject is exactly the fix Round-3 I1 asked for, and the added table-driven cases (`hostCPUs`, `wantErr`) cover the clamp and the floor.

The unit suite passes (`go test ./pkg/controllers/app/app/... ./pkg/controllers/rdd/...`). Untested scenarios, highest risk first:

### Important Issues

I1. **HostInfoReconciler violates singleton contract by populating foreign objects** — `rdd/pkg/controllers/rdd/hostinfo/controllers/hostinfo_controller.go:46-59` (important, gap)

```go
	cpus := goruntime.NumCPU()
	mem := int64(memory.TotalMemory())

	patch := client.MergeFrom(hi.DeepCopy())
	hi.Status.CPUs = cpus
	hi.Status.Memory = mem
```

While the reconciler correctly restricts its `NotFound` recreation path to `req.Name == SingletonName`, it skips this check on the success path. If a user or another controller creates a `HostInfo` object named anything other than `system`, the reconciler fetches it, populates its status with the host metrics, and logs the update. A singleton controller should ignore or actively delete rogue objects. Additionally, the unconditional `log.Info` runs on every reconcile pass (even no-op convergence), creating log spam.

Fix: Short-circuit foreign names early, and gate the patch/log on an actual change:
```diff
 	if err := r.Get(ctx, req.NamespacedName, &hi); err != nil {
 		if apierrors.IsNotFound(err) && req.Name == SingletonName {
 			log.Info("HostInfo singleton missing; recreating it")
 			return ctrl.Result{}, r.bootstrapSingleton(ctx)
 		}
 		return ctrl.Result{}, client.IgnoreNotFound(err)
 	}
+
+	if req.Name != SingletonName {
+		return ctrl.Result{}, nil
+	}
 
 	cpus := goruntime.NumCPU()
 	mem := int64(memory.TotalMemory())
+
+	if hi.Status.CPUs == cpus && hi.Status.Memory == mem {
+		return ctrl.Result{}, nil
+	}
 
 	patch := client.MergeFrom(hi.DeepCopy())
 	hi.Status.CPUs = cpus
```

I2. **Host detection logic remains duplicated across controller boundaries** — `rdd/pkg/controllers/rdd/hostinfo/controllers/hostinfo_controller.go:50-51` (important, gap)

```go
	cpus := goruntime.NumCPU()
	mem := int64(memory.TotalMemory())
```

In an effort to consolidate host limit detection, the author introduced `DetectHostInfo()` in `pkg/controllers/app/app/controllers/hostinfo.go`. However, the `HostInfoReconciler` continues to duplicate the underlying `goruntime.NumCPU()` and `memory.TotalMemory()` calls instead of reusing the helper. This occurred because the helper was placed in the `app` controller's package, making it inaccessible to the `rdd` controller package without introducing an undesirable cross-controller import cycle.

Fix: Extract `DetectHostInfo()` into a shared utility package (e.g., `pkg/util/hostinfo/hostinfo.go`) and update both the App webhook and the HostInfo reconciler to use it.
