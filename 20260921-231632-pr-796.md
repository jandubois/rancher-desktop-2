## Suggestions

S1. **A block that decodes past its declared size writes the excess before failing** — `rdd/pkg/xz/parallel.go:278` [Claude Opus 5, Gemini 3.1 Pro]

```go
	n, err := io.Copy(io.MultiWriter(w, digest), &ctxReader{ctx: ctx, r: lr})
	if err != nil {
		return fmt.Errorf("decompressing block at %d: %w", blk.uncompOff, err)
	}
	if n != blk.uncompSize {
		return fmt.Errorf("block at %d decoded %d bytes, want %d", blk.uncompOff, n, blk.uncompSize)
	}
```

ulikunitz's `blockReader.Read` stops at the first read that passes a block's declared uncompressed size. `decodeBlock` copies the whole LZMA2 output and only then compares the count, so it writes the excess into the next block's region, or past the end of the file for the last block. A probe halved the first block's size in `multiblock-padded-index.xz`, in its header and in the index, with both CRC32s recomputed. The sequential path answered `wrong uncompressed size for block`, and the parallel path `block at 0 decoded 65536 bytes, want 32768`.

Both paths reject the file, and the temporary file is removed. The only production input is the image rdd embeds at build time, so the overrun wastes work on a decode that fails anyway and cannot corrupt an image.

Fix: copy from `io.LimitReader(&ctxReader{ctx: ctx, r: lr}, blk.uncompSize+1)`. The probe then reports `decoded 32769 bytes, want 32768`, and `go test ./pkg/xz/` passes.

S2. **The boundary-block test stays green when a region writer's `Finish` truncates the file** — `rdd/pkg/sparse/sparse_test.go:62` [Claude Opus 5]

```go
	assert.NilError(t, a.Finish())
	b := NewWriterAt(f, int64(len(first)))
	_, err = b.Write(second)
```

The test finishes the lower region first, so if `a.Finish()` shrank the file, `b`'s writes would grow it back. With the `if !w.region` guard at `sparse.go:101` removed, `pkg/sparse` passes. Only `TestParallelMatchesSequential` notices, and only on more than one CPU. Under that mutation it failed 5 of 5 runs at `-cpu 2` and at `-cpu 8`, and passed 5 of 5 at `-cpu 1`, where the blocks finish in order. So a multi-core runner catches the regression, but only through a test whose result depends on scheduling.

Fix: assert the file length right after `a.Finish()`. It passes on the tree and fails under the mutation with `1050480 != 2099960`.

```go
	info, err := f.Stat()
	assert.NilError(t, err)
	assert.Equal(t, info.Size(), int64(len(first)+len(second)), "Finish changed the file's length")
```

S3. **A stream that stops splitting falls back without a log line** — `rdd/pkg/xz/xz.go:82` [Claude Opus 5]

```go
		case errors.Is(err, errNotSplittable):
			err = nil
```

The embedded image splits only when the build compresses it with multi-threaded xz, a CRC64 check, and sizes in every block header. If a build change breaks any of those, `DecompressReader` takes the sequential path. The only trace is a longer duration on the `Decompressed the embedded distro image` line (`limavm_controller.go:443`). Round 1 measured the shipped image at about 5.5 s split and 19.5 s sequential, and nothing in a slow log says which path ran.

Fix: log the fallback through the logger the reconcile context already has, for example `logr.FromContextOrDiscard(ctx).Info(...)`. `go-logr/logr` is already a direct dependency (`rdd/go.mod:19`).

S4. **`parseBlocks`' doc leaves out two valid streams that fall back** — `rdd/pkg/xz/parallel.go:108` [Claude Opus 5]

```go
// parseBlocks walks the block headers of a single-stream xz file and checks
// them against the stream's index and footer. A second stream, stream padding,
// a block header without both sizes, more than one filter, a filter other than
// LZMA2, or a dictionary of 4 GiB - 1 returns errNotSplittable. So does
// damaged metadata, which the sequential decoder then reports.
```

The comment lists the valid streams that fall back and files everything else under damaged metadata. A check other than CRC64 (line 121) and a single block (line 203) also fall back, and neither is damage. The delta added the 4 GiB - 1 entry, and a longer list makes the omission more likely to mislead. `crc64CheckID`'s doc (line 45) does describe the check fallback.

Fix: add "a check other than CRC64, fewer than two blocks" to the list.

## Design Observations

### Concerns

- **(future) Round 1's two concerns stand** [Claude Opus 5, Codex GPT 5.6 Sol]. The xz preset still sets decode memory and the number of blocks, and the split is still unmeasured on Windows, where `punchHole` does nothing. The delta changed neither.

### Strengths

- **(in-scope) Every fallback starts from an untouched file** [Claude Opus 5, Codex GPT 5.6 Sol]. `parseBlocks` is the only source of `errNotSplittable`, and `decompressParallel` truncates `dst` only after it succeeds (`parallel.go:315`). The sequential path therefore always gets the empty file `sparse.NewWriter` now requires.
- **(in-scope) The trailing-data check needs no extra buffer** [Codex GPT 5.6 Sol]. ulikunitz's LZMA2 reader reads each chunk through an `io.LimitReader` bounded by the chunk header's size and never reads ahead (`lzma/reader2.go` `startChunk`), so draining the `bufio.Reader` after EOF finds every leftover byte.
- **(in-scope) Streaming each block lowered peak memory without slowing the decode** [Claude Opus 5, Gemini 3.5 Flash]. On the shipped `-9` image, Claude's probe measured 1,095 to 1,257 MiB at this SHA against about 1,900 MiB at `eec59f184`, with the decode at 5.1 to 5.8 s on both. Round 1's mmap probe measured 1,357 to 1,557 MiB at `eec59f184` and 1,138 to 1,271 MiB with the fix, so Claude's harness reads higher only at `eec59f184` and overstates the saving.

### Skill improvements

- When a review needs a dependency's source or a staged artifact outside the agents' worktrees, copy it into each worktree's `.scratch/` before launch instead of granting read access to its path. A CLI with a path sandbox refuses its own file tools outside the workspace, so the agent either falls back to shell reads or skips the material.

### Repo context updates

- [repo] `rdd/pkg/xz` decodes only the distro image embedded in the binary at build time (`limavm_controller.go`), so a finding about crafted input with valid CRCs is hardening, not a security issue. Rate a difference in resource use or error text between the parallel and sequential paths as a Suggestion; an input one path accepts and the other rejects stays Important, because the parallel path promises the sequential path's checks.

#### Executive Summary

#### Findings

##### Critical Issues

None.

##### Important Issues

I1. **Parallel decoder writes unbound data beyond `uncompSize` before failing** — `rdd/pkg/xz/parallel.go:284-288`

```go
	n, err := io.Copy(io.MultiWriter(w, digest), &ctxReader{ctx: ctx, r: lr})
	if err != nil {
		return fmt.Errorf("decompressing block at %d: %w", blk.uncompOff, err)
	}
	if n != blk.uncompSize {
```

The sequential decoder checks the uncompressed byte count on every `Read` and aborts instantly if it exceeds the block header's `uncompressedSize` (`ulikunitz/xz/reader.go:310`). The parallel decoder streams the entire LZMA2 output through `io.Copy` into the sparse writer, and only checks if `n != blk.uncompSize` after the chunk finishes. If a malicious block's LZMA2 data decompresses to far more bytes than the header's `uncompSize` (but fits within its declared `compSize`), `io.Copy` will write the full expanded data to the temporary file on disk—potentially gigabytes for a decompression bomb—before discarding the result. 

Fix: Wrap the LZMA2 reader in an `io.LimitReader` bounded at `blk.uncompSize + 1`. If `io.Copy` hits the limit, it will safely return `blk.uncompSize + 1` (triggering the mismatch error) or fail early, preventing unbounded writes.

```go
	limitReader := io.LimitReader(&ctxReader{ctx: ctx, r: lr}, blk.uncompSize+1)
	n, err := io.Copy(io.MultiWriter(w, digest), limitReader)
```

(important, gap)

I2. **Missing overflow check for uncompressed size accumulation** — `rdd/pkg/xz/parallel.go:192-194`

```go
		blocks = append(blocks, block{
			// ...
		})
		uncompOff += uncompSize
		off = checkOff + crc64CheckSize
```

The sequential decoder validates that the sum of all block uncompressed sizes does not overflow `int64` (`ulikunitz/xz/reader.go:194`). The parallel decoder's `parseBlocks` accumulates `uncompOff += uncompSize` without checking for overflow. A stream whose blocks declare `uncompSize`s that sum past `math.MaxInt64` wraps `uncompOff` to a negative or small positive value. This bypasses the stream checks, causing `dst.Truncate` or `sparse.NewWriterAt` to receive wrapped offsets and fail with obscure `EINVAL` system errors during decode, rather than cleanly rejecting the file as corrupt during metadata parsing.

Fix: Add an overflow guard before incrementing:

```diff
 		blocks = append(blocks, block{
 			compOffset:   dataOff,
 			compSize:     compSize,
 			uncompOff:    uncompOff,
 			uncompSize:   uncompSize,
 			dictCap:      (2 | (bits & 1)) << (bits/2 + 11),
 			check:        check,
 			unpaddedSize: headerSize + compSize + crc64CheckSize,
 		})
+		if math.MaxInt64 - uncompOff < uncompSize {
+			return nil, errNotSplittable
+		}
 		uncompOff += uncompSize
 		off = checkOff + crc64CheckSize
```
