## Important Issues

I1. **Defaulter emits a cpus/memory value its own validator rejects** — `rdd/pkg/controllers/app/app/controllers/app_defaulter.go:98-125`, `app_webhook.go:78-84` [Claude Opus 4.8, Codex GPT 5.5]

```go
cpus := defaultVMCPUs            // 2, or RDD_VM_CPUS — never clamped to host
if val := os.Getenv(vmCPUsEnv); val != "" { ... cpus = n }
vm.CPUs = cpus
```

The mutating webhook fills an unset `cpus` with `2` (or `RDD_VM_CPUS`); the validating webhook then rejects `cpus > host`. Nothing clamps the default to the host, so on a 1-vCPU host the default `2` fails admission and no App can be created. `defaultVMMemory` has the same shape: it floors at 2Gi, which the validator rejects on a host holding under 2Gi. The orchestrator confirmed the CI values stay in bounds (Linux 3-of-4, macOS 4-of-4 — zero margin, Windows default 2), so CI is green today; a future `RDD_VM_CPUS` bump or a 3-core macOS runner would break every admission.

Fix: pass `hostInfo` into `defaultVMCPUCount` and clamp the built-in default to the host count; for a host below 2Gi, return a distinct "host below the 2Gi minimum" error rather than a confusing "default 2Gi exceeds host memory".

I2. **HostInfo singleton has no recovery path, and a comment claims one** — `rdd/pkg/controllers/rdd/hostinfo/controllers/hostinfo_controller.go:64-72` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro] (R2-I3 re-raised, file unchanged)

```go
if err := r.Create(ctx, hi); err != nil && !apierrors.IsAlreadyExists(err) {
    // Non-fatal: log and continue. The next reconcile will retry.
    logf.FromContext(ctx).Error(err, "Failed to bootstrap HostInfo singleton")
}
return nil
```

`Reconcile` fires only on `For(&HostInfo{})` events. If the one-shot `Create` in `Start` fails before the object exists, no event is ever delivered, so the promised retry never runs and `Status` stays empty until the daemon restarts — and the GUI reads its range from that Status. A runtime `delete hostinfo system` leaves the same gap, since `Reconcile` returns `IgnoreNotFound`. This file is byte-identical to Round 2. Likelihood is low (the embedded apiserver is up before `Start` runs), but the false comment is the stated reason no requeue exists.

Fix: recreate the singleton on the `NotFound` branch of `Reconcile` for `req.Name == SingletonName`, return the bootstrap error from `Start` so the manager retries it, and correct the comment.

## Design Observations

### Concerns

- **Host detection is duplicated; the CRD is not the validation source of truth** `(in-scope)` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro]. Issue #498 says "Validation will use these saved values [in HostInfo]." In practice the webhook snapshots `DetectHostInfo()` at setup while `HostInfoReconciler` independently calls `NumCPU()`/`TotalMemory()` on every reconcile. This round shares one snapshot between the defaulter and the validator — a real improvement — but the reconciler still detects on its own, so the GUI's advertised range and the validator's ceiling can still drift. Reading the CRD at admission is impractical (it may be unpopulated on first admission), so a webhook-local snapshot is fine; extract detection into a neutral package (e.g. `pkg/hostinfo`) that both call.
- **`RDD_VM_CPUS` errors now abort admission, not reconcile** `(future)` [Claude Opus 4.8]. A non-integer `RDD_VM_CPUS` makes `Default()` return an error, failing the mutating webhook for any App whose `cpus` is still unset — including the first admission, which then can never default. Recovery needs a fixed (spawn-frozen) env var and a daemon restart. Acceptable fail-fast for a CI knob, but a one-line comment at `defaultVMCPUCount` should note the blast radius.

### Strengths

- **Mutating-webhook defaulting** `(in-scope)` [Claude Opus 4.8, Codex GPT 5.5]. Resolving defaults in the webhook lets the CLI and reconciler treat cpus/memory as plain values instead of special-casing zero — the shape Round-2 feedback asked for.
- **Appended YAML replaces regex** `(in-scope)` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro]. Appending `cpus:`/`memory:` lines instead of regex-rewriting the template is simpler and robust; the template's own keys were removed (verified: no residual keys, so no duplicate-key risk).
- **Defensive guards retained** `(in-scope)` [Claude Opus 4.8]. The reconciler's `if cpus > 0` / `if mem != nil` guards are not dead code — they cover the admission-bypass path (unit tests build the App directly) and Lima's own fallback.

## Review Process Notes

### Skill improvements

- **When a mutating admission step fills a value that a later validating step bounds-checks, verify the filled value always satisfies the validator across the whole input range.** A defaulter and a validator that read the same limit can still disagree at the boundary: the defaulter can emit a value — a built-in default, an env-var override, or a floor/ceiling clamp — that its own validator then rejects, leaving the object permanently un-admittable. Check the extremes: an empty or zero limit reading, the smallest supported host, and any environment override that can exceed the ceiling. Flag any path where the defaulter's output is not provably inside the validator's accepted range.

- **When a finding's severity depends on a configured value — an environment variable, a tuning constant, a CI runner size — read the config that sets it before assigning severity.** A bug that fires only when a value exceeds a limit is severe if the shipped config sets the value past the limit and latent if the config keeps it within bounds. Do not assume the worst case or the happy case; find where the value is set (workflow YAML, a defaults file, a helper) and calibrate against the actual number, stating the margin.

### Repo context updates

- **[repo] UPDATE — supersedes the reset-semantics entry queued by `20260708-154035-pr-523` and revised by `20260709-132851-pr-523`.** The `rdd set` integer-reset behavior changed again. The `coerceValue` integer-`0`→null branch is removed, so `field=0` now stores `0` (it does not clear). For `spec.virtualMachine.cpus`, the App mutating defaulter then replaces the stored `0` with a concrete count, so `cpus=0` still reads as "reset to default" end to end — via the defaulter, not the CLI. Empty string still clears string and quantity (`XIntOrString`) fields; `field=` on an integer still errors with "expected integer". Re-derive the current reset syntax from `app_defaulter.go` before flagging a zero or empty value.

- **[repo]** The bats CI (`.github/workflows/rdd-bats.yaml`) sets `RDD_VM_CPUS` per OS — Linux `3`, macOS `4`, Windows unset (built-in default `2`) — on 4-core runners, so the configured VM CPU count sits at or under each runner's core count. Calibrate VM-sizing findings against these values: a claim that the VM CPU count can exceed the host is latent under the current tuning but would fire if `RDD_VM_CPUS` is raised above a runner's core count or a runner is downsized.

### Important Issues

**I1. Defaulter emits cpus/memory that its own validator rejects — `app_defaulter.go:94-126`, `app_webhook.go:77-98` (important, gap)**

```go
func defaultVMCPUCount(vm *v1alpha1.VirtualMachineSpec) error {
	if vm.CPUs != 0 { return nil }
	cpus := defaultVMCPUs            // 2, or RDD_VM_CPUS — never clamped to host
	...
	vm.CPUs = cpus
```

The mutating webhook fills a default that the validating webhook then checks against `vm.CPUs > v.hostInfo.CPUs`. On a 1-vCPU host the default `2` exceeds `1`, and every App create/update is rejected — the singleton can never be admitted. The sharper trigger: `RDD_VM_CPUS=4` on a 2-core CI runner defaults to 4, then `4 > 2` fails admission (the pre-rework path just passed it to Lima). Memory has the same shape below 2Gi: `defaultVMMemory` floors at `minMemoryBytes` (2Gi), which then exceeds the host in `memBytes > v.hostInfo.Memory`.

Fix: clamp the CPU default to the host ceiling (pass `hostInfo` to `defaultVMCPUCount` as `defaultVMMemory` already receives it):

```go
	cpus := defaultVMCPUs
	if val := os.Getenv(vmCPUsEnv); val != "" { ... }
	if hostInfo.CPUs > 0 && cpus > hostInfo.CPUs {
		cpus = hostInfo.CPUs
	}
	vm.CPUs = cpus
```

For memory, a host below the 2Gi minimum is genuinely unsupported; surface that as a distinct "host has less than the 2Gi minimum" error rather than a confusing "default 2Gi exceeds host memory of 1.5Gi". No test combines the defaulter and validator, so this class of contradiction is uncovered.

**I2. HostInfo create-failure has no recovery path; comment claims one — `hostinfo_controller.go:64-73` (important, gap) [R2-I3 re-raised, unchanged]**

Fix: requeue the bootstrap on failure — return the error from `Start` (the manager retries Runnables) or add a short-interval `RequeueAfter` guarded by a self-recreating reconcile, and correct the comment.

In practice the webhook snapshots `controllers.DetectHostInfo()` at setup (`controller.go:123`) while the `HostInfo` reconciler independently calls `goruntime.NumCPU()`/`memory.TotalMemory()` (`hostinfo_controller.go:46-47`). They agree today only because both use the same primitives. Round 2's duplication is only *partially* resolved: the defaulter and validator now share one snapshot, but the reconciler still detects on its own. Reading `HostInfo` synchronously at admission is impractical (it may be unpopulated at first admission), so keeping a webhook-local snapshot is pragmatic — but the two detections should share one helper. `DetectHostInfo` lives in the `app` controllers package; the `rdd` reconciler cannot import it without odd layering. Extract detection into a neutral package (e.g. `pkg/hostinfo`) and have both call it, so the GUI's advertised range and the validator's ceiling can never diverge.

- **`RDD_VM_CPUS` errors now abort admission, not reconcile (future).** A non-integer `RDD_VM_CPUS` makes `Default()` return an error, failing the mutating webhook for any App whose `cpus` is still unset — including the first admission, which then can never default. Recovery requires fixing the (spawn-frozen) env var and restarting the daemon. This is acceptable fail-fast for a CI-only knob, but worth a one-line comment at `defaultVMCPUCount` noting the admission-failure blast radius.

**Strengths**

- Moving default resolution into the mutating webhook (so the CLI and reconciler treat `cpus`/`memory` as plain values) is the right call and directly answers the Round-2 review feedback.
- Appending `cpus:`/`memory:` as trailing YAML lines instead of regex-rewriting the template is simpler and robust; the removed template keys (verified: no residual `cpus:`/`memory:` in the base template) mean no duplicate-key risk.
- The reconciler's `if cpus > 0` / `if mem != nil` guards in `applySpecToTemplate` are *not* dead: they correctly cover the admission-bypass path (unit tests construct App directly) and are documented against Lima's own fallback. Keep them.
