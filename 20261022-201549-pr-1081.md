## Executive Summary

Round 3 adds a `pinUnset` parameter so that `rdd stop` and `rdd run` leave an undecided App alone, and it applies round 2's test patch, so every `IsAdding()` site has a test that fails on revert. But an App's settings are final once it starts, so `rdd run` must pin `manual` as `rdd start` does. ## Suggestions

S1. **`cmd_app.md` still says `rdd stop` behaves like `rdd set running=false`** — `rdd/docs/design/cmd_app.md:51` [Codex GPT 6 Astra]

```markdown
Stop Rancher Desktop by setting `running=false` on the App singleton. `rdd stop` returns successfully without creating or starting anything when the instance or the App does not exist, or when the control plane is stopped. On a stopped control plane the App keeps its `running` value, so the next control-plane start resumes it. Otherwise it behaves like `rdd set running=false`, sharing the same `--wait` and `--timeout` flags.
```

Round 3 made the pin depend on the caller, so the two commands now differ for an App that is still `unset`. `rdd set running=false` stores `manual` there, and `rdd stop` keeps `unset` (I1's probe, the `unset` rows). The statement held at the merge-base.

Fix: after "behaves like `rdd set running=false`", add "except that it leaves an `application.addPath` that is still `unset` alone".

S2. **`bootstrap.md` never says how to turn PATH management on** — `rdd/docs/design/bootstrap.md:70` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash] round 2 S3 unaddressed

The page walks through `rdd start`, which stores `manual` on a new App, and line 70 limits automatic PATH edits to `front` and `back`. A reader who follows the page does not get a PATH edit, or any instruction for opting in.

Fix: add "`rdd start` sets it to `manual`; run `rdd set application.addPath=front` to opt in."
