Executive Summary ¶

The author force-pushed a substantial delta since round 2, and it fixes five of that round's seven Important findings. Two survive untouched or half-fixed, and each of the two mechanisms the delta adds has a defect of its own. Six Important findings remain. I ran a reproducer for every one against the review SHA, each paired with a contrasting case that behaves correctly.

Three of the six destroy state the user owns: a Windows Path entry they added by hand, a startup file they already had, and a spurious block in a file bash never reads. Two are the residue of incomplete fixes to round 2's I6 and I7. One is new: the Settled gate the delta introduced lets a single hand-edited dotfile block rdd set --wait forever, under the manual default. Suggestions are grouped after them; most are round-2 items the delta did not reach.

#### Future: Grace Period Support

Similar to pod deletion, `LimaVM` deletion could honor `metadata.deletionGracePeriodSeconds`:

1. `rdd ctl delete limavm foo --grace-period=30` sets the grace period on the resource
2. The reconciler starts a graceful shutdown (similar to SIGTERM for containers)
3. After the grace period expires, the reconciler forces shutdown (similar to SIGKILL)
4. `--grace-period=0` would skip graceful shutdown entirely

A similar mechanism should apply to stopping instances via `spec.running = false`. An annotation like `lima.rancherdesktop.io/stopGracePeriod` could control how long to wait before forcing the stop.

Design Observations ¶

Concerns ¶

  • Ownership of external state is expressed four different ways (in-scope) Codex GPT 5.6 Sol. Unix uses marker fences but guesses file ownership; Windows has no provenance at all; App deletion relies on another controller's finalizer; service deletion reconstructs paths from a fresh environment. I1, I2, I3 and S8 are each a symptom. One suffix-scoped record of what we wrote, consulted by both the reconciler and the unwind, would close all four.
  • Cross-process writes to one startup file are still last-writer-wins (future) Codex GPT 5.6 Sol Gemini 3.5 Flash. Suffix markers separate instances logically, but atomicfile's locks are in-process, so two daemons editing the same file can each replace the other's block. @mook-as accepted the single-process read-then-write window in discussion_r3816165512; this is the same class across processes.
  • The reconciler re-runs the full seven-file sweep on every App status write (future) Claude Opus 5. SetupWithManager uses For(&App{}) with only predicates.WatchEventLogger, which returns true for every event, so each status update during VM boot triggers seven os.ReadFiles and an os.MkdirAll. It converges, so the cost is wasted work, not a loop. A predicate on spec.application.addPath would cut it to once per spec change, but it has to keep stamping the condition for each generation (I4).
  • manual still creates rc files for shells the user does not have (in-scope) Gemini 3.1 Pro Gemini 3.5 Flash. Opting in creates .bashrc, .zshrc, .cshrc and config.fish whatever is installed. This matches RD1 deliberately, and round 3 fixed the one case that was actively harmful (.tcshrc). Recorded rather than raised, since the parity is intentional.

Strengths ¶

  • The os.SameFile login-file loop is the right shape for round 2's I2: it re-stats after the atomic write, so a later name resolving to the same inode is recognised. That is exactly what atomicfile's symlink resolution makes non-obvious Claude Opus 5 Codex GPT 5.6 Sol Gemini 3.1 Pro Gemini 3.5 Flash.
  • errors.Join plus the %s: %w path wrap turned round 2's I5 into a usable diagnostic. The failing file is named, and the remaining files still converge Claude Opus 5 Codex GPT 5.6 Sol.
  • dropEmpty makes manual byte-identical on a Path with stray semicolons while still tidying when we add our entry, and the three new table cases pin that distinction Claude Opus 5 Codex GPT 5.6 Sol.
  • Managing .cshrc always and .tcshrc only when it exists is the correct reading of tcsh's precedence, and the new test pins it Claude Opus 5 Codex GPT 5.6 Sol.

Review Process Notes ¶

Skill improvements ¶

  • When a finding claims a Go pointer-lifetime or escape hazard at a call into another package, open that package's source at the pinned version and look for a compiler directive that already provides the guarantee. The hazard and its remedy are both well known, so several reviewers will reach for it from the call site alone; the directive that settles it is one grep away and never visible in the diff.
  • When a fix replaces a boolean progress flag with a value derived from state (a stat result, a handle, a cached lookup), check every error path that leaves the derived value unset. The flag distinguished "not yet attempted" from "attempted and failed"; the derived value usually cannot, and the failure path then repeats work the flag would have suppressed.
  • When a round adds a gate that makes an existing failure visible, evaluate the gate against the population it now blocks, not just the population it was written for. A diagnostic promoted from a log line to a blocking condition inherits every trigger the log line had, including the ones nobody minded when they were silent.

Repo context updates ¶

  • [repo] rdd svc delete (rdd/pkg/service/cmd/service.go) stops the daemon before it removes anything, so no reconciler is running by the time its cleanup code executes. Host-side cleanup placed there runs in the CLI process with the CLI's environment, not the daemon's — a controller that resolved HOME, XDG_CONFIG_HOME or any other environment variable when it wrote host state cannot rely on getting the same answer during deletion.
  • [repo] rdd ctl is a full kubectl passthrough against the RDD control plane, and the design docs use rdd ctl delete <resource> as a supported operation. A controller that writes host state needs its own finalizer: deleting the App resource alone is reachable, and the App controller's cleanup finalizer does not unwind other controllers' host-side edits.
  • [repo] A controller writing an observedGeneration-stamped condition on the App must stamp the generation from the read its decision came from, not from the re-Get inside the conflict-retry loop. engine_reconciler.go documents why its own copy of this pattern is safe (another gate holds Settled until it re-reconciles) and states that a new spec field without such a gate would break it. Check for that second gate before accepting the pattern as correct.
