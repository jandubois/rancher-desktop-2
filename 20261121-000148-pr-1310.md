## Important Issues

I1. **The template comment says a failed script makes Lima stop the VM, but only the WSL2 driver does that** — `rdd/pkg/controllers/app/app/lima-template.yaml:97-99`

```yaml
# The start blocks, so Lima sees the VM as ready only after provisioning. A
# failed script makes Lima stop the VM, and a failed k3s install must not stop
# the container engine, so the script ignores the unit's exit status.
```

Lima's WSL2 driver turns a non-zero `boot.sh` exit into a driver error, and the hostagent stops the VM (`pkg/driver/wsl2/vm_windows.go` in Lima). Under vz and qemu, `boot.sh` runs in `lima-init.service`, and the driver never sees its exit code. `boot.sh` still writes `/run/lima-boot-done`, so the hostagent's last requirement passes, and the VM keeps running with `lima-init.service` failed. Round 1's text said "a failed script in the wsl.exe run". The rewrite dropped that qualifier, so a reader on macOS or Linux learns a behavior those VMs don't have.

The probe boots the embedded raw distro under vz with one provision script that exits 1; qemu rests on the same hostagent code, unmeasured. The other side of the claim, a WSL VM that stops, is in #1309's CI logs (`Driver stopped due to error`).

```bash repro

- location: embedded:///distro.raw.xz
```

## Suggestions

S1. **Test 139's `journalctl --boot` covers every run of the distro since WSL's kernel booted** — `rdd/bats/tests/32-app-controllers/engine-docker.bats:100-103` [Claude Opus 5.5]

```bash
    run -0 rdd limavm shell "${VM_NAME}" sudo journalctl --boot \
        --unit=rancher-desktop-provision.service --identifier=wsl-exec --output=cat
    run grep --count --fixed-strings "+ systemctl stop rancher-desktop.target" <<<"${output}"

```

All WSL distro runs share the kernel's boot ID, so `--boot` doesn't limit the journal to the current run. The Windows CI capture shows each new run replaying the earlier runs' provision lines. The test expects one `systemctl stop` line, and it gets one only because `local_setup_file` runs `rdd svc delete` and starts a fresh distro. A VM restart added before this test would make the count two. The PR body's "this boot's journal" overstates the scope for the same reason.

Fix: say in the test comment that the count relies on a freshly created distro, and write "the provision unit's journal" in the PR body.

**Outcome:** fixed in `9d1673963`. The test comment says that boots of a WSL distro share the kernel's boot ID, and that the count holds only because `rdd svc delete` unregisters the old distro and the new one has booted once. `dfbfab7c3` corrects the same claim in `bats-with-timeout.sh` and `load.bash`. The PR body edit is pending until the next push.

S1. **The new network-setup want is now the only thing that makes it read `/etc/sysconfig/rancher-desktop` before `boot.sh` writes it** — `rdd/overlay/manifest.yaml:229-233` (suggestion, gap)

```yaml

- path: /etc/systemd/system/multi-user.target.wants/network-setup.service
  type: symlink
  target: /usr/local/lib/systemd/system/network-setup.service
  profiles: [wsl]
```

- **What happens:** network-setup loads `EnvironmentFile=-/etc/sysconfig/rancher-desktop` when it starts. In the staged Windows job, it started at 06:25:48 (`guest-network-setup.log:1`). `boot.sh` copied the file at 06:26:02 (`lima-init.log:284`). On a new instance's first boot, `VM_SWITCH_LOG` and `NETWORK_SETUP_EXTRA_ARGS` therefore fall back to the unit's defaults, so vm-switch logs to the guest's `/var/log/vm-switch.log` instead of the host log directory.
- **Why it matters:** the merge-base had the same gap, through lima-init's `Requires=`. In this tree, line 230 and `network-setup.service:31` cause it on their own. Nothing else starts network-setup early: every other RD unit installs into `rancher-desktop.target`, and only the provision trap starts that target. The provision drop-in (`network-namespace.conf:3-4`) already has `Requires=`/`After=network-setup.service`.

Fix: drop lines 229-233 and restore `WantedBy=rancher-desktop.target`. Network-setup would then start when the provision unit pulls it in, after the file has been written. I could not check whether the later start delays the host-switch handshake, so this needs a Windows bats-app run. That run should show `vm-switch.log` in the host log directory on the first boot.

###### Acknowledged Limitations

- **Factory Reset Required for Existing VMs:** A VM created by an earlier build lacks `rancher-desktop-provision.service` in its overlay image, so provisioning steps will not run without a factory reset. This is noted in the PR description and commit message.
- **Ignored Unit Exit Code:** The Lima template executes `systemctl start rancher-desktop-provision.service || true` so that an upstream k3s download failure does not cause Lima to abort VM startup and terminate the container engine. Documented in `rdd/pkg/controllers/app/app/lima-template.yaml` (lines 97–100).
- **`RemainAfterExit=yes` Distro Lifespan:** `rancher-desktop-provision.service` uses `RemainAfterExit=yes`, relying on the invariant that every VM start begins from a terminated WSL distro (`wsl.exe --terminate`). Documented in `rdd/overlay/root/usr/local/lib/systemd/system/rancher-desktop-provision.service` (lines 1–4).
- **Log Repeats on WSL Distro Restarts:** Each WSL distro restart repeats earlier journal entries because WSL distro restarts share the Windows kernel boot ID; tracked separately in #1324.
- **Startup Ordering for WSL Networking Parameters:** `network-setup.service` starts at boot before `/etc/sysconfig/rancher-desktop` is updated, so `VM_SWITCH_LOG` and `NETWORK_SETUP_EXTRA_ARGS` take effect one boot late; pre-existing known gap documented in `network-setup.service`.
