Design Observations ¶

Concerns ¶

  • rdd-forwarder shows up as a command on Windows (future) Claude Opus 5.5. Round 1 listed it as a future design observation. linkBinaries links every file in resources\windows\bin into ~/.rd2/bin (rdd/pkg/binlinks/binlinks.go:99-104), and the MSI puts that directory on PATH (build/wix/main.wxs:91, :116), so typing rdd-forwarder prints Cannot open shim file. Staging the forwarder in resources/internal, as Claude proposed, would not remove the command, because #931's linkForwarders (at 80df05ba5) skips the forwarder in its per-tool loop but copies it into ~/.rd2/bin as the master every tool hardlinks to. A master name that PATHEXT does not match would hide it, and that is a decision for #931.
  • The arm64 build passes GNU flags to an MSVC toolchain (in-scope) Claude Opus 5.5 Codex GPT 6 Astra. The arm64 runner's clang++ targets MSVC and links with lld-link. The package log shows warning: argument unused during compilation: '-s' and lld-link: warning: ignoring unknown argument '--gc-sections', and -static has no effect there. The arm64 binary is static because clang defaults to libcmt for that target. A --target= per architecture, or a sentence in the Makefile comment, would make that visible to the next reader.

Unresolved Feedback ¶

  • "Looks like we are not actually building the binary" (@jandubois). Resolved: both Windows package jobs compile, sign and package the forwarder.
  • "Make sure we are building a static binary; we don't want to depend on any runtime library DLL" (@jandubois). Resolved for the compiler runtimes. The arm64 forwarder imports only KERNEL32.dll and SHELL32.dll. The x86_64 forwarder imports neither libstdc++ nor libgcc, but it does import the Universal CRT's api-ms-win-crt-* API sets. Windows 10 ships those, and RD2 supports only Windows 10 and later (packaging/electron-builder.yml:53). Whether the UCRT counts as a runtime library DLL here is the maintainer's call.

Review Process Notes ¶

Skill improvements ¶

  • Narrow the "What NOT to flag" rule on linter-catchable issues: it should exclude only issues the repository's lint gate passes. A change that turns a lint job red at the reviewed SHA is a finding, however cosmetic the edit, because the rule assumes the linter will stop it and a red non-required job does not stop a merge. Ask reviewers to run the repository's lint entry point on changed files before calling an edit formatting-only.
  • When reviewers disagree about a property of a built artifact (its imports, its architecture, its size), and CI builds that artifact, download it and inspect it before consolidating. Driver probes on the review host predict what a toolchain does; the artifact shows what the runner's toolchain did.

Repo context updates ¶

  • [repo] Lint TypeScript runs ESLint over the whole tree with --max-warnings=0 (scripts/lint-typescript.ts), so a warning-level rule such as @stylistic/key-spacing's value alignment fails the job. Treat any ESLint warning on a changed line as a CI failure, Important. The job is not one of main's required checks, so a PR can merge with it red, and every later PR then fails it.
  • [repo] On the Windows arm64 runners, C and C++ compile with the image's LLVM clang++, which targets aarch64-pc-windows-msvc and links with lld-link; x86_64 uses MinGW g++. GNU-only flags (-static, -s, -Wl,--gc-sections) do nothing or only warn on arm64, and clang's MSVC default links the static CRT (libcmt). Judge a native build flag per architecture, and confirm runtime linkage from the package artifact's import table.
