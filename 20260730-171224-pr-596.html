Executive Summary ¶

This merge brings RD1's i18n system, eight locale files, the i18n-report tool and the blog feed onto RD2's main. All 48 modify/delete conflicts were resolved correctly, and most of the 41 content conflicts hold both sides' intent. The misses all sit in the code connecting the two trees. A live General-page checkbox no longer works, a nav rename stranded six call sites, and several i18n hunks are half-applied.

I reviewed the conflict resolution, not the imported RD1 commits. The findings group into merge-authored glue that never connects (C1, I5, I6), hunks applied to one side of a pair (I1, I3, I4), and tooling the merge imported but left unrunnable (I2, S2). The PR already flags i18n and the blog feed as broken, so this report names only the defects that have a specific one-line fix.

Review Process Notes ¶

Skill improvements ¶

  • When the review target is a merge commit, derive the files to review by replaying the merge (git merge --no-commit --no-ff <other-parent> from the first parent) and classifying every conflict as take-one-side, hand-merged, or modify/delete. Take-one-side resolutions silently discard the other parent's change to that file, and hand-merged files are where a hunk gets half-applied. Tell agents to spend their budget there and to treat the rest of the merge-base diff as already-reviewed upstream work. Without this, the agents each re-review the whole import and converge on the same handful of shallow findings.
  • On a merge, classify each merged blob against both parents (identical to parent A, identical to parent B, or differs from both) and give agents the classification. A blob identical to a parent needs no review; only the third class is new work. This turns an unreviewable diff into a bounded file list.
  • The merge itself authored any rename or type change that appears in neither parent, so nothing upstream reviewed it. Flag such changes to agents as the highest-yield place to look for stranded call sites, because nothing outside the resolved file changed to match.
  • Before accepting a finding that traces a call chain to a defect, check that the chain's entry point can execute. A handler is latent when the only way in is a constant-false template branch, a commented-out block, or an unregistered route, and the severity must say so. Reviewers reconstruct chains bottom-up from the defect and routinely miss that the top of the chain is disabled two lines above the code they quoted.
  • When a reviewer proves a type error with a synthetic reproduction rather than the real declaration, re-run the check with the actual file imported through the project's own tsconfig, before repeating the claim. A hand-written stand-in can encode the union the reviewer expected instead of the one the code declares.
  • Where a change alters what a shared helper returns for a missing input (a placeholder string instead of undefined, an empty collection instead of null), grep every caller for ??, || and truthiness guards on that return. A caller written against the old contract keeps compiling and silently loses its fallback branch.

Repo context updates ¶

  • [repo] The check-spelling configuration under .github/actions/spelling/ is inert. The spelling job in .github/workflows/lint.yaml is commented out, and no spelling.yml workflow exists. A word missing from allow.txt or expect/*.txt cannot fail CI; it surfaces only through a manual make spelling. Rate such findings as suggestions, not CI breakage.
  • [repo] The Electron settings model in pkg/rancher-desktop/config/settings.ts and the daemon's App custom resource in rdd/pkg/apis/app/v1alpha1/app_types.go are separate schemas that must agree for a preference to round-trip. RdCheckbox's preference prop is typed against the generated @rdd-client AppSpec, so a setting present in defaultSettings but absent from ApplicationSpec cannot be written. Check both when you add or rename a preference. Note also that settings.ts retains RD1 field names in places (application.updater.enabled) where the daemon uses another (application.updates.enabled).
  • [repo] pkg/rancher-desktop/config/settingsImpl.ts is a stub with no updateTable and no migration function, so bumping CURRENT_SETTINGS_VERSION has no migration machinery behind it. Only settings.ts and store/diagnostics.ts read the constant. Do not flag a version bump for a missing migration entry.
  • [repo] pkg/rancher-desktop/typings/store.d.ts augments vuex's Dispatch and Commit, but declaration merging keeps the base (type: string, payload?: any) overload, so a wrong store action or getter name produces no type error and no test failure, only [vuex] unknown action type at runtime. When a change removes or renames a store member, grep every dispatch, mapActions, mapGetters and mapState consumer by hand.
  • [repo] The root bats/ tree holds tests/snapshots/ and tests/updater/ with no helpers/ directory, and no workflow runs it; .github/workflows/rdd-bats.yaml targets rdd/bats only. Suites there open with load '../helpers/load' and abort on line 1. Treat them as parked pending the RD2 harness.
  • [repo] yarn lint:typescript:nofix runs eslint, not tsc, and Playwright uses its own transpiler. Only the production package build type-checks bundled files. A type error in a .vue file that is statically imported still ships green through the lint and Jest jobs, so verify a type claim against the package build or a direct tsc run.
