## Important Issues

I1. **`trigger-obs` runs when every job it needs was skipped** — `.github/workflows/package.yaml:259` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]

```yaml
    if: ${{ !cancelled() && contains(needs.*.result, 'success') && !contains(needs.*.result, 'failure') }}
```

When GitHub evaluates a job's `if:`, `needs.*` covers every ancestor job, not only the three listed under `needs:` ([actions/runner#2346](https://github.com/actions/runner/issues/2346)). `package` and `check-paths` succeed on every pull request, so this condition is true even when `package-obs` and both uploads were skipped. The PR's Package runs at `2f041af18`, `9b2b487bf` and `97a51a25e` all ran this job; each failed in `read-vault-secrets` with `Unable to get ACTIONS_ID_TOKEN_REQUEST_URL`. The last force-push changed this condition, and the job still fails.

`package-obs` skips on every pull request, every tag push, a `workflow_dispatch` outside `main` and `release-*`, and every fork without `OBS_DEVEL_PROJECT`. Each of those Package runs now starts this job. On a tag push I expect the vault read to succeed and the job to post an empty `package=` to OBS, which I haven't tested.

S1. **`package-obs` downloads about 1 GB of zips it never reads** — `.github/workflows/package.yaml:152-156` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]

The job computes `package_name` from `GITHUB_REF_NAME` alone (lines 168-176) and never reads the zips. Both upload jobs download them again. In the fork's run (job 130257936176) this step fetched 554,828,997 and 499,744,327 bytes in 18 seconds.

S2. **A re-run of the Pages job will probably still find two `github-pages` artifacts** — `.github/workflows/package.yaml:250` [Claude Opus 5.5]

```yaml
      uses: actions/upload-artifact@cf430e030ddbb5b0abf93d22962f4752f3646cd9 # v7.0.2
      with:
        name: github-pages
        path: deploy.tar
        overwrite: true
```

`overwrite: true` deletes an earlier artifact only if upload-artifact can list it, and `deleteArtifactInternal` in `@actions/artifact` (read on actions/toolkit's default branch, not the copy that v7.0.2 bundles) lists by the current token's run and job backend IDs. Round 1's re-run (job 129580352369) suggests that those IDs don't reach an earlier attempt. Its attempt 2 uploaded the same name with `overwrite: false` without a conflict, and then `deploy-pages` found two artifacts. If so, a re-run uploads a second `github-pages` and fails the same way. Nobody has re-run this job since the change; the fork's first attempt deployed fine. This is the residual of round 1's S1.

Fix: name the artifact `github-pages-${{ github.run_attempt }}`, and pass the same name to `actions/deploy-pages` as `artifact_name`.

S3. **The warning that OBS fetches these exact S3 names is still gone** — `.github/workflows/linux-release.yaml:44-45` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]

## Review Process Notes

### Repo context updates

- [repo] In a GitHub Actions job-level `if:`, `needs.*` also covers ancestor jobs, not only the jobs listed under `needs:` (actions/runner#2346), while a step-level expression sees only the direct needs. In `package.yaml` the `package` and `check-paths` jobs succeed on every pull request, so a job condition built on `contains(needs.*.result, 'success')` is true there even when every direct need was skipped. Flag `needs.*` in a job-level `if:`, and name each need instead.

###### Findings

**Critical Issues**

C1. **`trigger-obs` runs inappropriately and fails on tags and PRs** — `.github/workflows/package.yaml:254-279`

```yaml
  trigger-obs:
    name: Trigger OBS build
    needs: [ package-obs, upload-obs-to-s3, upload-obs-to-pages ]
    # One of the needs: must have been skipped; so we can't rely on the default
    # `success()`, as that causes this to be skipped too.
    if: ${{ !cancelled() && contains(needs.*.result, 'success') && !contains(needs.*.result, 'failure') }}
```

The `if:` condition evaluates to `true` even when `package-obs` and both upload jobs are skipped. In GitHub Actions, `needs.*.result` returns an array of results from *all* dependency jobs in the workflow's dependency graph that ran, which includes the successful `package` matrix jobs, satisfying the `contains` check. 

Consequently, `trigger-obs` now runs on pushes to tags, PRs, and forks lacking `OBS_DEVEL_PROJECT`. This causes two failures:
1. On PRs from forks, `get-vault-secrets` runs (because the base repo owner evaluates to `rancher-sandbox`) but crashes with `Unable to get ACTIONS_ID_TOKEN_REQUEST_URL` because PRs lack `id-token: write` permissions.
2. On tags, `package_name` is empty (since `package-obs` was skipped), making the `curl` call to OBS fail with an empty `package=` parameter.

Fix: To run only when the OBS upload jobs actually executed, check their specific results instead of a wildcard.
```yaml
    if: ${{ !cancelled() && (needs.upload-obs-to-s3.result == 'success' || needs.upload-obs-to-pages.result == 'success') }}
```

###### Executive Summary

However, the newly restructured `trigger-obs` job evaluates `needs.*.result` across transitive ancestor jobs (actions/runner #2356), causing it to run and fail on every pull request, tag push, and fork without secrets (C1). `package-obs` also downloads 1 GB of unused artifacts (I1).

###### Findings

###### Critical Issues

C1. **`trigger-obs` runs on PRs, tags, and forks due to `needs.*` ancestor inclusion, breaking PR CI** — `.github/workflows/package.yaml:263` (critical, regression)

```yaml
  trigger-obs:
    name: Trigger OBS build
    needs: [ package-obs, upload-obs-to-s3, upload-obs-to-pages ]
    # One of the needs: must have been skipped; so we can't rely on the default
    # `success()`, as that causes this to be skipped too.
    if: ${{ !cancelled() && contains(needs.*.result, 'success') && !contains(needs.*.result, 'failure') }}
```

In GitHub Actions, job-level `if:` expressions evaluate `needs.*` over all transitive ancestor jobs (actions/runner #2356). Because `package-obs` depends on `package` (which succeeds), `needs.*.result` always contains `'success'`. When `package-obs`, `upload-obs-to-s3`, and `upload-obs-to-pages` are skipped (on pull requests, tag pushes, or in forks without `OBS_DEVEL_PROJECT`), `trigger-obs` runs unexpectedly. On PRs in `rancher-sandbox`, step `get-vault-secrets` (line 268) fails with `Unable to get ACTIONS_ID_TOKEN_REQUEST_URL env variable`, breaking PR CI (run 43125959930). In forks without secrets, step `Fall back to GitHub-hosted secrets` (line 276) fails. If secrets exist, it triggers OBS with an empty `package=` parameter (line 282) because `needs.package-obs.outputs.package_name` is unset.

Unproven: GitHub Actions evaluates job-level `if:` server-side during workflow scheduling, so the failure is confirmed by upstream CI PR run 43125959930 (`upstream-pr-trigger-obs-130888973704.log`) and documented in actions/runner issue #2356.

Fix:
```diff
   trigger-obs:
     name: Trigger OBS build
     needs: [ package-obs, upload-obs-to-s3, upload-obs-to-pages ]
-    # One of the needs: must have been skipped; so we can't rely on the default
-    # `success()`, as that causes this to be skipped too.
-    if: ${{ !cancelled() && contains(needs.*.result, 'success') && !contains(needs.*.result, 'failure') }}
+    if: ${{ !cancelled() && (needs.upload-obs-to-s3.result == 'success' || needs.upload-obs-to-pages.result == 'success') }}
```
