This happens on every platform, since Docker never finds plugins via PATH.   user's shell startup files on Unix (`.bash_profile`/`.bash_login`/`.profile`, `.bashrc`,
  `.zshrc`, `.cshrc`/`.tcshrc`, and fish's `config.fish`) and the user `Environment` in the
  registry on Windows. Valide values:
  - `unset`: nobody has picked a value yet. This is the **default**. rdd treats it exactly like
    `manual` (it leaves `PATH` alone); the GUI uses it to decide whether to open its first-run
    dialog. A CEL rule forbids changing the field back to `unset` once it holds another value (a
    patch that deletes the field gets `unset` back from defaulting, so that is rejected too), and
    `rdd set` replaces it with `manual` (see below).
  - `front`: prepend, so the bin directory takes precedence (`bin:$PATH`).
  - `back`: append, so existing `PATH` entries win (`$PATH:bin`).
  - `manual`: do not manage `PATH`; remove any lines a previous `front`/`back` added.

Design Observations ¶

Concerns ¶

  • rdd stop pins manual too (in-scope) Claude Opus 5.5: the pin is in setAction, which rdd start, rdd stop and rdd run all call (rdd/cmd/rdd/app.go:43, rdd/cmd/rdd/app.go:105, rdd/cmd/rdd/run.go:110). Issue #1052 covers instances started from the CLI. But rdd stop against a GUI-created App whose dialog was never answered also writes manual, and the dialog then never returns. Passing the pin as a setAction option that stopAction leaves off would make each command's behavior visible at its call site. Whether rdd stop should pin at all is a design decision, not a defect.

Strengths ¶

  • One predicate for every PATH decision (in-scope) Claude Opus 5.5 Codex GPT 6 Astra Gemini 3.5 Flash: IsAdding() replaces six comparisons. Two of them, the != manual tests in applyPosix and in the Settled check, would have treated unset like front.
  • The one-way rule holds in the API server (in-scope) Claude Opus 5.5 Codex GPT 6 Astra: the CEL rule binds every client, and it also rejects deleting the field or the whole application object, because defaulting brings unset back.

Testing Assessment ¶

  • I3 (required): decided by "How would a user see it?". Losing the existing-unset branch or the unset default produces a wrong result with no error, and each mutation passes all three new tests.
  • Executed by the consolidator:

  • An envtest probe against the committed CRD confirmed the CEL behavior. A create without addPath stores unset, and unset→front and front→manual are accepted. front→unset, front→null, front→application: null and manual→unset are rejected with the rule's message; front→"" is rejected by the enum.

The field doc and api_app.md describe unset, the CEL rule and the rdd set pin correctly. I2 covers the statements elsewhere that the new default falsified, and S2 the duplication inside api_app.md. The field doc's "The GUI sends "front" when the user opts in" still describes a GUI that does not write addPath yet. Issue #1051 asks for that sentence to be rewritten.

Acknowledged Limitations ¶

  • No path back to unset: nothing in the API returns an App to unset, so restoring the first-run state takes deleting the App or rdd svc delete, which RD2 requires between versions anyway. #1052 intends this; a future reviewer should not re-suggest a reset path.
  • rdd set --dry-run creates a real App: on a missing App the dry-run create is real, because the dry-run patch needs an object to validate against, and set.bats:190 pins that behavior. The created App keeps the default unset, since only the dry-run patch carries the manual pin. A future reviewer should not re-suggest DryRunAll on that create.

Review Process Notes ¶

Skill improvements ¶

  • When a change alters a default or adds a value to an enumerated setting, grep the whole repository for prose that states the old default or reasons over the old value set ("the default", "unless X is Y"): design docs, CLI help strings, and comments outside the diff. Each such sentence turns false without any of its lines appearing in the diff, so a check of the comments near the change misses it.
  • Enforce the no-services rule in the environment each external agent runs in, as well as in the prompt, for example by running the agent CLI under its own sandbox or with a PATH that lacks the container runtime and the project's service binary. A prompt rule that names the forbidden command has not stopped every model from running it, and such a run can rewrite the user's live configuration files before it fails.
