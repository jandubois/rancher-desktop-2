## Executive Summary

The PR shows a first-run dialog when the control plane or the App is missing, rebuilds it on shared Kubernetes-version and engine selectors, and adds JSON output to `rdd service status`. The selectors and the CLI change are sound, but the dialog's lifecycle is not. Quitting mid-dialog leaves a hidden process, an OK before the App exists drops the user's choices, the App created on open suppresses the dialog on later starts, and e2e escapes it only by a race.

## Important Issues

I1. **Quitting while the first-run dialog is open leaves a hidden process** — `pkg/rancher-desktop/pages/FirstRun.vue:65` [Claude Opus 5.5]

```ts
async function commitAndClose(event: Event) {
  event.preventDefault();
```

`commitAndClose` runs as the dialog's `beforeunload` listener (line 82), and `preventDefault()` there cancels the unload. Electron cancels `app.quit()` along with it, as the probe below shows against the pinned Electron.

On macOS the default menu's Quit works during first-run, because `buildApplicationMenu` runs after the dialog. Cmd-Q sets `ShuttingDown` (`background.ts:254`), the dialog cancels the quit, and once the commit finishes, `window.close()` closes the last window.

`window-all-closed` only hides the dock icon (`background.ts:261-263`), and `second-instance` and `activate` do nothing in `ShuttingDown`. The process keeps running with no window and no dock icon, and launching the app again does nothing.

The dialog also shows itself on mount (`dialog/ready`, line 92) while `onBeforeMount` still waits for the control plane and the App. On a fresh instance here, starting the control plane took 8.6 s (one sample), all of it before the App can exist. ## Suggestions

S1. **Every launch after a reboot now waits for the control plane before showing a window** — `pkg/rancher-desktop/main/rdd-ctl.ts:156-157` [Claude Opus 5.5, Gemini 3.5 Flash]

```ts

      ['ctl', 'get', 'app', '--output=name'], { stdio: ['ignore', 'pipe', console] });
```

On this Mac the call took about 2.1 s from a stopped control plane (three samples) and 0.1 s from a running one. ## Design Observations

### Concerns

- **The gate runs in the main process and spawns the `rdd` CLI** (in-scope) [Claude Opus 5.5, Gemini 3.5 Flash, Codex GPT 6 Astra]: `isFirstRunNeeded` runs up to two `rdd` processes before any window, while `gui.md` limits the GUI to one external process and keeps every other read on the API connection, which keeps a remote daemon possible. #1051 puts the gate in the renderer, in `ensureAppStarted`, and keys it on a field that the dialog writes. That design avoids I3's race, I4 and S1's delay together. Separately, the dialog needs explicit loading, saving and completed states; today mounting the dialog enables OK, creating the App suppresses it on later starts, and closing the window counts as completion.

### Strengths

- `cliflag.EnumValue` moves flag validation into pflag and simplifies `service paths` [Claude Opus 5.5, Gemini 3.5 Flash].
- The `LifetimeState` enum makes the `activate` and `second-instance` behaviour explicit for each startup phase [Claude Opus 5.5].
- `KubernetesVersionSelector` and the self-contained `EngineSelector` remove the duplicate selection logic between the Preferences and first-run dialogs [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash].
- JSON status goes to stdout apart from the log output, and the new BATS cases pin it across the service lifecycle [Codex GPT 6 Astra].

## Review Process Notes

### Skill improvements

- A reproducer run from the repository root inherits the root `package.json` module type, so a CommonJS probe saved as `.js` in an ES-module repo throws on its first `require` and, behind a filtered output, looks like a hang. Name each probe file for its module system (`.cjs` or `.mjs`), and run it from the repo root as the report tells the author to.
- When the prompt states an observed failure, agents echo it as a finding whether or not they explain it. Credit an agent for a prompt-supplied failure only when its mechanism checks out against the code, and count a wrong mechanism as a false positive.

### Repo context updates

- [repo] UPDATE: the Container Engine nav item is live; `window/preferenceConstants.ts` lists `container-engine` with its `general` tab, and only the WSL item and the remaining tabs stay commented out. Findings in `components/Preferences/ContainerEngineGeneral.vue` are live.

### [Claude Opus 5.5]

###### Executive Summary

PR #1086 adds JSON output to `rdd service status`, uses it with `rdd ctl get app` to decide whether the first-run dialog is needed, and rebuilds `FirstRun.vue` on the App spec with shared Kubernetes-version and engine selectors. ###### Important Issues

I1. **The dialog's `beforeunload` handler can cancel app quit and leave an invisible process** — `pkg/rancher-desktop/pages/FirstRun.vue:64-66` (important, regression)

```ts
async function commitAndClose(event: Event) {
  event.preventDefault();
  try {
    await store.dispatch('preferences/commit');
```

`commitAndClose` is registered as a `beforeunload` listener (line 82) and calls `preventDefault()`. The pinned Electron 44.7.2 documents that a window "cancels the quitting" from `beforeunload` (`electron.d.ts:1506-1508`). Picture Cmd-Q on macOS while the dialog is open (the default menu is still active, because `buildApplicationMenu` runs after first-run). `before-quit` sets `ShuttingDown` (`background.ts:254`), and the dialog then cancels the quit. When the commit finishes, `window.close()` (line 75) closes the last window. `window-all-closed` only hides the dock (`background.ts:261-263`), and `second-instance` and `activate` do nothing in `ShuttingDown` (lines 83-86, 274). The process keeps running with no window and no dock icon, and relaunching does nothing.

Unproven: the exact cancellation rules (`preventDefault` versus `returnValue`, and Chromium's sticky-activation gate) need a live Electron run, which this review may not do.

Fix: in `before-quit`, call `window.getWindow('FirstRun')?.destroy()`, which skips `beforeunload`, or drop `preventDefault()` on the unload path.

I2. **The first-run check is keyed on the App existing, but the dialog creates the App when it opens** — `pkg/rancher-desktop/main/rdd-ctl.ts:156-158` (important, gap)

```ts
    const { stdout } = await spawnFile(rddPath,
      ['ctl', 'get', 'app', '--output=name'], { stdio: ['ignore', 'pipe', console] });
    return !(stdout?.trim());
```

`FirstRun.vue:85` runs `rdd/ensureAppExists` in `onBeforeMount`, so the App exists while the dialog is still on screen. If the app is killed or quit mid-dialog, every later start finds the App and skips the dialog. The user never gets to choose, and the defaults apply silently. Issue #1051, the specification of record, requires the opposite: "The App stays `unset` only if the app is killed while the dialog is open, and the dialog then opens again on the next start." Any App created from the CLI (`rdd set …`) before the first GUI launch also suppresses the dialog.

The catch branch has a related problem. A transient `rdd ctl` failure, such as the discovery lag the e2e logs show, returns `false` for a created service with no App, which loses the dialog for good.

Fix: key the decision on a field the dialog itself writes (`spec.application.addPath` per #1051, or a marker field until #1049 lands), not on the App existing.

I3. **Clicking OK before the App exists silently drops the user's choices** — `pkg/rancher-desktop/pages/FirstRun.vue:67` (important, gap)

```ts
    await store.dispatch('preferences/commit');
```

The dialog shows itself on mount (`dialog/ready` at line 92, `window/index.ts:549`), before the async `onBeforeMount` finishes. On a true first run, `fetchConfig` has to create and start the control plane first, and only then does `ensureAppExists` create the App.

During that wait, `preferences` is `{}`: the Kubernetes box shows unchecked even though the default is enabled, and no engine is selected. If the user picks an engine and clicks OK in that window, `patchApp` finds no App, sets `appMissingStatus` and returns `false` (`store/preferences.ts:327-330`). `commit` resolves `false` rather than throwing, so the catch at line 68 never runs and the window closes with the choice discarded.

Fix: disable the OK button (and the selectors) until `rdd/app` has a `metadata.name`, and keep the dialog open when `commit` resolves `false`.

I4. **The e2e suite avoids the dialog only because of a discovery race** — `e2e/utils/TestUtils.ts:369-372` (important, gap)


I1. **`isFirstRunNeeded()` suppresses dialog on apiserver CRD discovery errors** — `pkg/rancher-desktop/main/rdd-ctl.ts:155-165` (important, regression)

I3. **`event.preventDefault()` in `beforeunload` does not prevent window close, dropping async commits** — `pkg/rancher-desktop/pages/FirstRun.vue:64-77` (important, regression)

```typescript

  event.preventDefault();
  try {
    await store.dispatch('preferences/commit');

    // we can display any following errors via the normal code path.  This
    // likely means there is something wrong with the back end.
    console.error(ex);
  } finally {
    window.removeEventListener('beforeunload', commitAndClose);
    window.close();
  }
}
```

Line 82 attaches `commitAndClose` to `beforeunload` to save default settings on window close. In Electron/Chromium, `event.preventDefault()` does not cancel window unloading; `event.returnValue = false` is required. Because unload is not suspended, Chromium tears down the renderer while `await store.dispatch('preferences/commit')` on line 67 is pending, dropping the HTTP patch mid-flight. Furthermore, closing the dialog via the titlebar close button resolves `openFirstRunDialog()` while `lifetimeState` remains `LifetimeState.FirstRun` (`background.ts:133`), causing `initUI()` to launch `openMain()` and start the VM despite the user attempting to dismiss the setup window.

Unproven: Asynchronous promise abortion during Chromium window destruction is documented by Electron and Chromium specs.

Fix: Cancel unload using `event.returnValue = false` before awaiting asynchronous persistence, or handle dialog cancellation by quitting the application.
