## Executive Summary

The containerd watcher mirrors namespaces, containers and images, and the `mirrorClient` extraction leaves the moby path unchanged. Every Important finding sits in the action path, where the host drives containerd directly while nerdctl owns state the host never touches: `start` and `restart` fail for `-t` containers; a stop leaves containerd's restart monitor free to undo it; deleting a never-started container leaks its nerdctl name; `deleteImage` uses the wrong digest; and `stopTask` reports a stop that never happened as succeeded.

Findings carry the agents that raised them. The two Gemini models share a family and converged on one issue, counted as a single opinion. I ran a reproducer for I1 and I5 against this tree; I2, I3 and I4 turn on upstream behavior no in-process test reaches, so each names its evidence.

## Important Issues

I1. **`startTask` drops the container's TTY setting, so `start` and `restart` fail for `-t` containers** — `rdd/pkg/controllers/app/engine/controllers/container_actions_containerd.go:186-195` [Claude Opus 5]

```go
	creator := cio.NullIO
	info, err := ctr.Info(nsCtx)
	if err != nil {
		return fmt.Errorf("failed to get container info: %w", err)
	}
	if raw := info.Labels["nerdctl/log-uri"]; raw != "" {
		if u, err := url.Parse(raw); err == nil {
			creator = cio.LogURI(u)
		}
	}
```

Both creators leave `Config.Terminal` false, so `NewTask` sends `Terminal=false`. The shim then skips `runc.NewTempConsoleSocket` (containerd v2.3.2 `cmd/containerd-shim-runc-v2/process/init.go:118-121`) while the bundle's `config.json` still has `process.terminal: true`, and runc refuses: `cannot allocate tty if runc will detach without setting console socket` (runc v1.2.3 `utils_linux.go:321`). Every `nerdctl run -dt` container records `lastAction.state=Failed`. nerdctl picks `cio.TerminalBinaryIO` for this case.

I2. **Neither `startTask` nor `stopTask` maintains the restart-monitor label, so containerd undoes a stop** — `rdd/pkg/controllers/app/engine/controllers/container_actions_containerd.go:201` [Codex GPT 5.6 Sol]

```go
	if err := task.Start(nsCtx); err != nil {
```

containerd's restart monitor restarts an `unless-stopped` container unless `containerd.io/restart.explicitly-stopped` is true (containerd v2.3.2 `core/runtime/restart/restart.go:136-140`). nerdctl sets it true on stop and false on start (`pkg/containerutil/containerutil.go:358` and `:302`). Neither path here touches it. A stop through the action annotation therefore records `lastAction.state=Succeeded` while the monitor brings the container back, and a start after a `nerdctl stop` leaves the container marked explicitly stopped, disabling its restart policy.

Unproven: observing the monitor act needs a live containerd. Codex reproduced it on a throwaway instance, reporting `running Succeeded` twenty seconds after the stop; I verified the label contract in the pinned sources above rather than re-running that probe.

Fix: set the label before signaling in `stopTask` and clear it after a successful `startTask`. The host can write it over the containerd API, so this needs no guest-side help.

**Outcome:** Deferred to its own PR with I3. A host-side fix was implemented and reverted after two verification passes each found a fresh failure mode; the ownership boundary is now documented in `api_containers.md`.
I3. **Deleting a never-started container leaks its nerdctl name** — `rdd/pkg/controllers/app/engine/controllers/container_actions_containerd.go:354` [Codex GPT 5.6 Sol]

```go
	if err := ctr.Delete(nsCtx, containerdclient.WithSnapshotCleanup); err != nil && !errdefs.IsNotFound(err) {
```

nerdctl reserves container names in a name store under its own state directory and releases them two ways: `nerdctl rm` calls the store directly (`pkg/cmd/container/remove.go:153-154`), and a running container's OCI `postStop` hook releases the name when the task is deleted (`pkg/ocihook/ocihook.go:663`). A container created but never started has no task, so `deleteContainer` removes the containerd record without either path running. The name stays reserved and `nerdctl create --name <same>` fails until someone repairs the store by hand, while the Kubernetes delete reports success.

Unproven: the name store lives inside the VM. Codex reproduced the collision on a live instance; I verified both release paths in the nerdctl source above.

Fix: this is the one finding the host cannot fix alone, since the name store is guest-local state. Either run nerdctl's removal inside the guest, or decide that engine-side names are nerdctl's to own and say so in `api_containers.md`.

**Outcome:** Deferred to its own PR with I2: the nerdctl name store is guest-local, so the fix needs a guest-exec path the engine controller does not have. Documented in `api_containers.md`.
I4. **`deleteImage` addresses a digest-named record by its manifest digest, so the delete silently no-ops** — `rdd/pkg/controllers/app/engine/controllers/container_actions_containerd.go:373-376` [Claude Opus 5]

```go
	// Dangling records are named by their digest.
	ref := img.Status.RepoTag
	if ref == "" {
		ref = img.Status.ID
	}
```

`status.id` is the *manifest* digest (`sync_images_containerd.go:105`), but containerd's CRI plugin names its digest record by the *config* digest: `imageID := configDesc.Digest.String()`, then `createOrUpdateImageReference(ctx, r, image.Target(), labels)` (containerd v2.3.2 `internal/cri/server/images/image_pull.go:199-207`). The two digests name different blobs. With Kubernetes enabled every k3s image in `k8s.io` gets such a record, and `digest.Parse` leaves its `repoTag` unset (`sync_images_containerd.go:134`). Deleting that mirror sends a digest matching no record; `NotFound` is swallowed, the finalizer comes off, and the mirror disappears while the containerd record survives to reappear on the next full sync.

Unproven: reaching a CRI-populated `k8s.io` namespace needs a live cluster, so the divergence rests on the containerd source cited above.

Fix: when `repoTag` is empty, scan the namespace and match on `img.Target().Digest`, the way `resolveContainer` scans at `container_actions_containerd.go:138-147`, or record the containerd record name on the mirror.

**Outcome:** Fixed, by matching the mirror name exactly rather than the target digest.
I5. **`stopTask` discards the error containerd reports, so a stop that never happened records Succeeded** — `rdd/pkg/controllers/app/engine/controllers/container_actions_containerd.go:242-244` [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]

```go
	select {
	case <-exitCh:
		return nil
	case <-time.After(stopTimeout(nsCtx, log, ctr)):
	}
```

`task.Wait` sends `ExitStatus{code: UnknownExitStatus, err: err}` and closes the channel whenever its RPC fails (containerd v2.3.2 `client/task.go:350-359`). A dropped containerd connection therefore satisfies `<-exitCh` at once, and `stopTask` returns nil for a container still running: `processContainerAction` writes `lastAction.state=Succeeded` while the mirror keeps reporting `running`. The second select at line 250 has the same shape, and `restartContainer` inherits the false success. nerdctl propagates this error (`pkg/containerutil/containerutil.go:496`).

Both Gemini models flagged these lines for blocking the reconciler until the grace period expires. That mechanism does not hold, for the same reason this one does: the wait channel fires on cancellation instead of going quiet.

## Suggestions

S1. **`stopTask` hardcodes SIGTERM and never resumes a paused task** — `rdd/pkg/controllers/app/engine/controllers/container_actions_containerd.go:239` [Claude Opus 5, Codex GPT 5.6 Sol]

```go
	if err := task.Kill(nsCtx, syscall.SIGTERM); err != nil {
```

containerd records an image's `STOPSIGNAL` in `containerdclient.StopSignalLabel`, and nerdctl's `getSignal` reads it before falling back to SIGTERM (`pkg/containerutil/containerutil.go:475-481`), as Docker does. A container built with `STOPSIGNAL SIGQUIT` gets SIGTERM here and is killed after the grace period. The status switch at line 228 also lets a `Paused` task through to the signal, where a frozen process cannot act on it.

Fix: resolve the signal from that label, and resume a paused task before signaling.

**Outcome:** Fixed, and the fix exposed a further defect: the signal name resolved against the host OS table, so a Linux guest received a different signal. It now resolves against an explicit Linux table.
S2. **`containerIDValidator` rejects mirror names containerd can produce** — `rdd/pkg/controllers/app/engine/controllers/container_passthrough.go:40` [Claude Opus 5]

```go
var containerIDValidator = regexp.MustCompile(`^(ctr-)?[0-9a-fA-F]+$`)
```

`containerdMirrorName` keeps any DNS1123-valid ID verbatim (`sync_containers_containerd.go:45-48`), so `ctr run --id my-app` yields the mirror name `my-app`, which this pattern rejects. `HandleLogs` answers 400 rather than the 501 the containerd backend means to return. The comment above the pattern describes two shapes where the code produces three.

Fix: validate with `validation.IsDNS1123Subdomain`, which is exactly the set of names the mirror layer emits.

**Outcome:** Fixed, by validating with `IsDNS1123Subdomain`.
S3. **A malformed `nerdctl/log-uri` silently downgrades to `NullIO`** — `rdd/pkg/controllers/app/engine/controllers/container_actions_containerd.go:192` [Claude Opus 5]

The parse error goes nowhere, so a container restarted through the action path keeps running but loses `nerdctl logs`, with nothing in the daemon log to explain it. The function already takes a `logr.Logger` and uses it at line 205.

**Outcome:** Fixed.
S4. **`w.starts` is pruned only on `ContainerDelete`** — `rdd/pkg/controllers/app/engine/controllers/containerd_watcher.go:47` [Claude Opus 5]

A watcher restart clears it, so this is one line rather than a redesign.

Fix: drop `starts` keys missing from `activeNames` at the end of `syncAllContainers`, under `startsMu`.

S5. **A live engine switch never swaps the watcher** — `rdd/pkg/controllers/app/engine/controllers/engine_reconciler.go:260` [Claude Opus 5]

S9. **The containerd full sync never prunes `Volume` mirrors** — `rdd/pkg/controllers/app/engine/controllers/containerd_watcher.go:301-309` [Codex GPT 5.6 Sol]

`fullSync` reconciles namespaces, containers and images. moby's `syncVolumes` prunes stale `Volume` mirrors on every full sync (`sync_volumes.go:62-75`); containerd has no equivalent, because it creates no volumes. **Outcome:** Fixed.

## Design Observations

### Concerns

- **Every CRI-pulled image produces three `Image` mirrors, one looking dangling** *(future)* [Claude Opus 5]. containerd's CRI plugin registers each image under its config digest, repo tag and repo digest (`internal/cri/server/images/image_pull.go:203`). `containerdImageMirrorName` hashes the record name, so all three become separate mirrors sharing one `status.id`, and the config-digest one gets no `repoTag`. With Kubernetes enabled the Images list triples. Grouping records by target digest and folding digest-named ones into `status.repoDigests`, as `imageStatusFromInspect` does, would also remove I4's ambiguity.
- **`ContainerNamespace` mirrors have no steady-state re-apply** *(future)* [Claude Opus 5, Codex GPT 5.6 Sol]. `Reconcile` never re-applies one: containerd writes it from `fullSync` and from create events only. Deleting the mirror leaves a permanent gap until the watcher restarts, which Codex confirmed on a live instance. This predates the PR: moby reaches `syncContainerNamespace` from `docker_watcher.go:513` alone, so both backends behave the same way and this is a gap rather than a regression. Codex rated it Important on the strength of the live repro; the pre-existing moby behavior is what holds it here.
- **Container mutations cross an ownership boundary** *(in-scope)* [Codex GPT 5.6 Sol]. I1, I2, I3 and S1 share one cause: the host controller drives containerd directly while nerdctl owns the labels, name store and state directories that make a container coherent. Each has a narrow fix, but the class does not close until something decides which side owns container lifecycle. I2 and S1 are cheap host-side label writes; I3 is not, since the name store is guest-local. That split is the design question the PR should answer, and `api_containers.md` is the place to record the answer.

### Strengths

- Subscribing before `fullSync` (`containerd_watcher.go:85-92`) is the right order, and the claim that nothing is lost holds: containerd's exchange queues for a slow subscriber through an unbounded `goevents.Queue` (`core/events/exchange/exchange.go:133`), even though the client-side channel is unbuffered. *(in-scope)* [Claude Opus 5]
- The LIFO defer sequence in `run` (`containerd_watcher.go:141-161`) is documented and correct, so the reconciler cannot observe a live watcher about to exit. *(in-scope)* [Claude Opus 5, Gemini 3.5 Flash]
- `containerdPorts` sorts port names and their bindings (`sync_containers_containerd.go:361-368`), matching the atomic-list SSA requirement, and the unit tests pin both orderings. *(in-scope)* [Claude Opus 5]
- Seeding `activeNames` before the apply (`sync_images_containerd.go:59-61`) keeps a transient failure from misclassifying a mirror as stale. *(in-scope)* [Claude Opus 5]
- `mirrorClient` is a true no-op extraction: the moved functions are identical modulo the receiver. *(in-scope)* [Claude Opus 5, Gemini 3.5 Flash]

## Review Process Notes

### Repo context updates

- [repo] When a finding concerns a `nerdctl/*` label on a containerd container record, check nerdctl's own write path before judging how the daemon reads it. nerdctl omits several labels rather than writing a zero or empty value, so a reader's fallback for the absent case may be unreachable rather than wrong. The module cache usually holds a nerdctl checkout even though the daemon does not depend on it.

### Skill improvements

- When a review lists a value-parsing fallback as a defect ("this rejects a legitimate zero/empty/negative input"), find the code that writes the value before accepting the finding. A fallback for an input the only writer never produces is unreachable, not wrong, and the writer is often a dependency in the module cache rather than the repo under review.
- When two agents from one model family report the same finding, treat their agreement as one opinion. Convergence between siblings measures shared priors, not independent confirmation, and a report that counts it twice overstates how well-attested the finding is.
- Reject a claim that a helper's inner assertion is lost to a nested test-harness capture only after running it. Whether the inner check still fires turns on which shell each half executes in, and a harness that captures in a subshell usually keeps an assertion and its own captured output together; what gets clobbered is the caller's copy. The probe is a two-case throwaway test file and settles the question in a minute.
- When an agent reports a finding it reproduced against live infrastructure the consolidator cannot rebuild, verify the mechanism in pinned source and record both: what the source establishes, and that the agent's run was not repeated. Dropping the finding for want of a rerun discards the class of defect that only a live system shows, and passing the run through unexamined reports someone else's output as verified.

### Defect found while verifying the fixes

Writing testing gap 5 first, as the fail-first gate requires, exposed a bug in
the S1 fix itself. `containerdclient.GetStopSignal` resolves a signal name
through `moby/sys/signal`, which maps against the **host** OS. The daemon runs
on macOS and Windows but signals a Linux guest, and the two disagree above
SIGTERM: macOS numbers SIGUSR1 30, Linux numbers it 10. A container built with
`STOPSIGNAL SIGUSR1` therefore received a different signal than it asked for.
SIGTERM, SIGQUIT, SIGHUP and SIGKILL share their numbers, which is why every
existing test passed and both verification passes missed it. The fix now
resolves signal names against an explicit Linux table, and `TestParseLinuxSignal`
pins the guest's numbers so the host constants cannot creep back.
