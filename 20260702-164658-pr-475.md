## Important Issues

I1. **Incompatible-server path and its JSONL parser have no tests** — `pkg/rancher-desktop/main/rdd-ctl.ts:99-111` [Claude Opus 4.8]

```ts
for (const line of stderr.split(/\r?\n/)) {
  try {
    const error: { 'exit-code'?: number; msg?: string } = JSON.parse(line);
    if (error?.['exit-code'] !== CodeIncompatibleServer) { continue; }
    if (typeof error?.msg === 'string' && error.msg && error.msg !== '<nil>') {
      message = error.msg; break;
    }
  } catch { /* ignore */ }
}
```

The parser regressed twice under review — the fallback first fired on multi-line JSON, then this loop was added to scan for the `exit-code:5` line — yet nothing exercises it. BATS asserts exit codes 3 and 4 (`rdd/bats/tests/20-service/6-timeout.bats`) but never 5; `rdd-ctl.ts` has no spec, and the cert-callback flow in `networking/index.ts` is untested. A regression that reverts the parser, or that returns the config before installing certificates, would ship green.

Fix: extract the "find the `exit-code:5` line, else fall back" logic into a pure helper and unit-test it against warn-level single-line, trace-level multi-line, empty-`msg`, and malformed input. Add a `run -5` BATS assertion if a version-mismatch fixture becomes feasible.

## Suggestions

S1. **stderr can be truncated when `spawnFile` rejects, hiding the version-specific message** — `pkg/rancher-desktop/main/rdd-ctl.ts:94` [Codex GPT 5.5, Claude Opus 4.8]

`spawnFile` rejects the instant the child's `exit` event fires; the stderr `end` promise sits in the same `Promise.all` and is abandoned on the first rejection. The `catch` then reads the `stderr` closure, which may still be missing the final chunk — the `exit-code:5` line that main.go logs immediately before exiting. When that line is absent, the parser falls back to the generic "Unsupported RDD service version" text. This is the fallback @mook-as observed (r3476447447); the loop fix addressed multi-line output, not this exit-versus-drain race.

```ts
promises.push(new Promise<void>((resolve, reject) => {
  child.on('exit', (code, signal) => {
    if (code === 0 && signal === null) { return resolve(); }
    reject(new SpawnError(...));   // fires before stderr 'end' resolves
  });
}));
await Promise.all(promises);
```

Fix: have `spawnFile` await stdio drain (listen for `close`, not `exit`) before rejecting, or parse only after an explicit stderr-complete signal. Touches shared infrastructure (`utils/childProcess.ts:277-288`), so weigh the blast radius.

S2. **Unbound `console.error` in `.catch` loses `this` and throws** — `pkg/rancher-desktop/main/networking/index.ts:68` [Codex GPT 5.5]

```ts
mainEvents.invoke('rdd/kube-config').catch(console.error);
```

`console` is `Logging.networking` (a `Log`), and `Log.error` calls `this.logWithDate` (`utils/logging.ts:129`). Passing `console.error` unbound drops `this`, so when `rdd/kube-config` rejects — which happens on the incompatible-server path — the catch handler itself throws a `TypeError` and buries the original failure in an unhandled rejection. A sibling utility already pairs the safe arrow form (`utils/backgroundProcess.ts:140`) with the same unbound bug (line 144).

Fix: `.catch(ex => console.error(ex))`.

S3. **JSON logging branch drops the nil-`Err` guard, emitting an empty-`msg` line** — `rdd/cmd/rdd/main.go:181` [Codex GPT 5.5, Claude Opus 4.8]

```go
if _, ok := logrus.StandardLogger().Formatter.(*logrus.JSONFormatter); ok {
    logrus.WithField("exit-code", exitErr.Code).Error(err)
} else if exitErr.Err != nil {
```

`(*cliexit.Error).Error()` returns `""` when `Err` is nil (`pkg/cli/exit/exit.go:35-40`), so a propagated child exit (`rdd run`, `run.go:177`) under `--log-format=json` now logs `{"exit-code":N,"level":"error","msg":""}`. The text branch keeps the guard that suppresses exactly this bare line. This PR's own `service config` path always carries a message, so the effect is cosmetic, but it reintroduces the noise the guard was written to prevent.

Fix: gate the JSON branch on `exitErr.Err != nil` too, adding the `exit-code` field only when a message exists.

S4. **`rdd --version=raw` is spawned fire-and-forget on every fetch** — `pkg/rancher-desktop/main/rdd-ctl.ts:88` [Claude Opus 4.8]

```ts
spawnFile(rddPath, ['--version=raw'], { stdio: ['ignore', 'pipe', console] })
  .then(({ stdout }) => console.log('RDD version:', stdout))
  .catch(err => console.error('Error fetching RDD version:', err));
```

Detached from the returned promise, the `'RDD version:'` line lands at a nondeterministic point in the startup log, and the inner `{ stdout }` shadows the outer `stdout` returned two lines later. The extra subprocess runs on every successful config fetch.

Fix: `await` the call so the version precedes the config in the log and rename the destructured variable; drop it if the daemon already logs its version at startup.

S5. **`stderrWritable.final()` is dead code** — `pkg/rancher-desktop/main/rdd-ctl.ts:53-63` [Claude Opus 4.8]

`spawnFile` forwards each `data` chunk to the sink but never calls `.end()` on it (`utils/childProcess.ts:264-270`), so `final()` never fires. The handler is harmless because logrus JSON lines are newline-terminated, but it cannot flush a trailing partial line and implies a flush path that does not exist.

Fix: drop `final()`, or flush `lastStderrLine` from the success and `catch` paths where the stream actually ends.

## Design Observations

### Concerns

- **The fatal quit trusts the numeric exit code, not a confirmed signal** *(future)* [Claude Opus 4.8] — `rdd-ctl.ts:95` quits on `err.code === CodeIncompatibleServer`, while `rdd run` (`run.go:177`) propagates arbitrary child exit codes including 5. This is safe today only because the TS spawns `rdd service config`, whose sole source of exit 5 is `checkSupportedVersion`. Gating the quit on a parsed `exit-code:5` record — which the loop already finds — would make the decision robust to future callers.
- **The Latch hangs silently if `rdd-ctl` is not imported before networking** *(in-scope)* [Claude Opus 4.8] — `await certificateCallback` resolves only once something emits `rdd/certificate-callback`. `background.ts:21` imports `@pkg/main/rdd-ctl` (registering the listener) before `setupNetworking` runs at line 90, so the order holds. A `setupNetworking` throw before the emit quits the app (`background.ts:93-97`), so this cannot wedge a running app either. The dependency is real but implicit — worth a one-line comment.

### Strengths

- **Callback-before-return guarantees certificates precede any config consumer** *(in-scope)* [Claude Opus 4.8] — `fetchConfigWithoutCache` invokes the cert callback before returning, and `fetchConfig` memoizes the promise, so every caller — including the renderer's independent `invoke('rdd/kube-config')` — receives a kubeconfig only after certificate handling is installed. This is safer than consuming the invoke return value directly, which would let the renderer race the cert setup.
- **Exit-code plumbing is correct end-to-end** *(in-scope)* [Codex GPT 5.5, Claude Opus 4.8] — `checkSupportedVersion` → `Wait` → `Classify` → `main.go` → `os.Exit(5)`; the JSON `exit-code`/`msg` field names match the TS parser exactly; `Wait` stops polling only on code 5 and keeps retrying transient errors; and no references to the removed `errorServerVersionUnsupported` type remain.

## Review Process Notes

### Skill improvements

- When an agent claims code fails to compile or type-check — a TypeScript overload mismatch, a missing symbol, a broken build — treat the claim as empirically verifiable. Run the compiler or type-checker on the exact construct, or confirm the project's build even type-checks that file, before rating it. Overload resolution and type assignability are easy to misread from signatures alone, and many build setups transpile without type-checking in development, so a hand-derived "this will not build" is often wrong. Rate such a claim only after the tool agrees.

- Flag callback arguments that pass an object method by bare reference — `.then(obj.method)`, `.catch(logger.error)`, `arr.forEach(this.handle)` — when the method body uses `this`. The detached call loses its receiver and throws at runtime, usually on an error path where the resulting `TypeError` buries the original failure. The safe form wraps the call in an arrow: `ex => logger.error(ex)`.

- When code reads a child process's stdout or stderr after the process rejects or exits, verify the read waits for stream drain (the `close` event), not just `exit`. A process can emit `exit` before its stdio pipes flush, so a post-exit read of a captured buffer can miss the final chunk — often the exact line the caller needs. Flag error-path parsing that reads a subprocess-output buffer filled by a drain path separate from the one that triggered the throw.

### Repo context updates

- [repo] `Lint TypeScript` in CI runs eslint (`scripts/lint-typescript.ts`), not `tsc`, and `yarn dev` builds with `transpileOnly: true` — only the production `package` build (`yarn package`, `transpileOnly: false`) type-checks bundled files. To verify a TypeScript type- or compile-error claim, run `tsc --noEmit` or check the `package` job, not the lint or dev output.

- [repo] The `Logging` module's `Log` methods (`Logging.<topic>.error`, `.log`, and siblings) are unbound and use `this` internally. Passing one by bare reference to a callback (`.catch(console.error)`) loses the receiver and throws a `TypeError`; the repo's safe idiom wraps it in an arrow (`ex => console.error(ex)`, see `utils/backgroundProcess.ts:140`). Flag bare-reference `Log`-method callbacks.

- [repo] `spawnFile` (`pkg/rancher-desktop/utils/childProcess.ts`) accepts a `stream.Writable` in the stdio tuple (the encoding path routes it to the child pipe), and it rejects on the child's `exit` event before the stdout/stderr `end` promises resolve. A caller that reads a stderr closure filled by that stream inside its `catch` can observe a truncated buffer missing the final line. Trace the drain-versus-reject ordering when reviewing subprocess error parsing here.

- [repo] UPDATE: the exit-codes context entry (`CodeRejected=3`, `CodeTimeout=4` in `pkg/cli/exit/exit.go`) should add `CodeIncompatibleServer=5` — the running daemon is incompatible with the client; documented in `cmd_app.md` and surfaced to the Electron UI as a fatal error dialog.

Detached from the returned promise, so `'RDD version:'` lands at a nondeterministic point in startup logs, and the inner `({ stdout })` reuses the name of the outer `stdout` (line 66) that is returned two lines later. Minor extra subprocess. If the daemon already logs its own version at startup this is redundant; otherwise consider `await`-ing it so the version precedes the config in the log, and rename the destructured variable.

**S3. `stderrWritable.final()` is dead code — `pkg/rancher-desktop/main/rdd-ctl.ts:53-63` (suggestion, enhancement)**

`spawnFile` writes chunks to the stream but never calls `.end()` on it (it only pipes `'data'` → `stdStreams[i].write(chunk)`, see `childProcess.ts:264-270`), so `final()` never fires. Harmless because logrus JSON lines are newline-terminated (the trailing split element is empty), but the handler cannot flush a trailing partial line and misleads readers into thinking it can. Consider dropping it, or flushing `lastStderrLine` from the `catch`/success path instead.

### Design Observations

**Concerns**

- **stderr may be truncated when `spawnFile` rejects (in-scope).** `spawnFile` rejects from `await Promise.all(promises)` the instant the child's `'exit'` fires (`childProcess.ts:277-288`); the stderr `'end'` promise is in the same array but abandoned on the first rejection. The `catch` at `rdd-ctl.ts:94` then reads the `stderr` closure, which may be missing chunks not yet delivered as `'data'`. For the small JSONL the daemon emits this is rare and the fallback message (`rdd-ctl.ts:99`) covers it, but it is exactly the failure mode mook flagged (`r3476447447`). A robust fix would have `spawnFile` await stream drain before rejecting; a local fix would attach an explicit `'finish'`/`'end'` signal before parsing. (Runtime-timing dependent — severity capped accordingly.)

- **The fatal quit trusts the numeric exit code, not a confirmed signal (future).** `rdd-ctl.ts:95` quits on `err.code === CodeIncompatibleServer`, while `rdd run` (`run.go:177`) propagates arbitrary child codes including 5. This is safe today only because the TS spawns `rdd service config`, whose sole source of exit 5 is `checkSupportedVersion`. Gating the quit on having actually parsed an `exit-code:5` record (which the loop already finds) would make the decision robust to future callers.

- **The Latch feature silently hangs if `rdd-ctl` is not imported first.** `await certificateCallback` never resolves unless something registers `rdd/certificate-callback` (via `rdd-ctl.ts:19`). Guaranteed today by `background.ts:21` importing `@pkg/main/rdd-ctl` before `setupNetworking` runs at `background.ts:90`, but it is an implicit ordering contract worth a one-line comment.

**Strengths**

- The callback-before-return design (`fetchConfigWithoutCache` invokes the cert callback at `rdd-ctl.ts:78` *before* returning, and `fetchConfig` memoizes the promise at line 136) guarantees certificate handling is installed before *any* caller receives the kubeconfig — including the renderer store's independent `invoke('rdd/kube-config')` (`store/rddConnection.ts:83`). This is materially safer than consuming the `invoke` return value directly, which would let the renderer race the cert setup. Keep this invariant during refactoring.
- Exit-code plumbing is correct end-to-end: `checkSupportedVersion` → `Wait` (`service.go:417-421`) → `Classify` → `main.go` → `os.Exit(5)`, with no dangling references to the removed `errorServerVersionUnsupported` type, and the JSON `exit-code`/`msg` field names match the TS parser exactly.
