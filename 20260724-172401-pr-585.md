## Executive Summary

Round 2 answers the round-1 memory crash with a hand-written Kubernetes Quantity parser. The parser fixes `2.5Gi` but still throws on other API-valid numerals. `rdd set virtualMachine.memory=5.Gi` stores a value the CRD accepts and the API server preserves verbatim; the renderer cannot parse it, so Preferences crashes. A non-string memory value throws too. Both reopen the failure class the round set out to close.

All four reviewers converged on the grammar gap, each reaching it through a different input. Codex and Claude both reproduced it by running the real parser, and Codex confirmed the value survives a Go round-trip. I verified the reachable case independently: the CRD pattern accepts a trailing dot, and `resource.ParseQuantity("5.Gi")` returns `5.Gi` unchanged rather than canonicalizing it as it does `2.5Gi` and `.5Gi`. Gemini 3.1 Pro alone noticed that the new files use BigInt literals their directory's tsconfig forbids. The display truncation both Gemini reviewers raised is deliberate, per Jan's PR comment, and moves to Acknowledged Limitations.

## Important Issues

I1. **Parser rejects Kubernetes-legal numerals with a leading or trailing dot, crashing the Preferences render** — `pkg/rancher-desktop/utils/parseQuantity.ts:59` [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]

```ts
  const [, sign, whole, fraction = '0'] = /^([+-]?)([0-9]+)?(?:\.([0-9]+))?$/.exec(numeral) ?? [];

  if (whole === undefined) {
    throw new Error(`Malformed quantity: ${ trimmed }`);
  }
```

The numeral regex demands digits before the dot and forbids a trailing dot, so `5.Gi` and `.5Gi` throw. Kubernetes accepts both. The CRD pattern (`rdd/pkg/controllers/app/app/crd.yaml:133`) admits them, `rdd set` forwards the string unchanged (`rdd/cmd/rdd/set.go:755`), and `resource.ParseQuantity("5.Gi")` returns `5.Gi` verbatim rather than canonicalizing, unlike `2.5Gi` which becomes `2560Mi`. So `rdd set virtualMachine.memory=5.Gi` reaches the renderer intact and the throw escapes an unguarded `computed`. This is prior I1's crash, one input class narrower.

Fix: allow an absent whole part and a bare trailing dot, rejecting only when both parts are empty.

```ts
const match = /^([+-]?)([0-9]*)(?:\.([0-9]*))?$/.exec(numeral);
```

I2. **A non-string `memory` value throws `TypeError` before parsing starts** — `pkg/rancher-desktop/utils/parseQuantity.ts:10` [Codex GPT 5.6 Sol, Claude Opus 5]

```ts
  const trimmed = value.trim();
```

The signature promises `string | undefined`, but the generated model types the field as `'memory'?: any` (`pkg/rdd-client/gen/models/IoRancherdesktopAppV1alpha1AppSpecVirtualMachine.ts:26`), so TypeScript checks nothing at the call site. The CRD is `x-kubernetes-int-or-string` with `anyOf: [integer, string]`, making a bare JSON integer schema-valid. Running the real function with `2147483648` yields `TypeError: value.trim is not a function`, another render crash. The `rdd` CLI always sends a string, so today the path opens only to a direct API writer.

Fix: coerce at the boundary, `String(value).trim()`, and widen the parameter to `string | number | undefined`.

I3. **New files use BigInt literals their tsconfig target forbids, adding 79 type errors** — `pkg/rancher-desktop/utils/parseQuantity.ts:22` [Gemini 3.1 Pro]

```ts
  let scale = 1n; // Negative scale means divide.
```

`pkg/rancher-desktop/tsconfig.json` sets `"target": "ES2018"`, and TypeScript resolves the nearest config, so every `1n` and `10n` raises `TS2737: BigInt literals are not available when targeting lower than ES2020`. Measured with the repo's own compiler: the merge-base reports 102 errors and zero TS2737; this SHA reports 181, the 79 new ones confined to `parseQuantity.ts` and its spec.

CI stays green, so this breaks no build: `Lint TypeScript` runs ESLint (`scripts/lint-typescript.ts:2`) and every `package` job passed at this SHA. The cost is that both new files light up red in any editor and in any `tsc -p` run over that directory.

Fix: raise the target to ES2020, or write `BigInt(1)` as `VirtualMachineHardware.vue:10` already does.

S7. **The parser accepts suffixes Kubernetes rejects, and the spec pins that leniency as the contract** — `pkg/rancher-desktop/utils/parseQuantity.ts:20` [Claude Opus 5, Gemini 3.1 Pro, Codex GPT 5.6 Sol]

```ts
  const suffix = rawSuffix?.replace(/B$/, '') ?? ''; // remove trailing B if present
```

Kubernetes accepts only `"" n u m k M G T P E Ki…Ei` plus an `e`/`E` exponent. Stripping a trailing `B`, mapping uppercase `K`, and adding `µ`/`μ` admits `1B`, `1MB`, `1KiB`, and `1K`, all of which `resource.ParseQuantity` rejects with "unable to parse quantity's suffix". The spec asserts several of them as correct, so a later reader takes the looser grammar as intended. The leniency only widens what is accepted and never computes a different value, so nothing is wrong today.

Fix: drop the `B` stripping, `K`, and the micro signs; add the cases from I1 that Kubernetes does accept.

S8. **Suffix lookup walks the prototype chain, turning a bad unit into a confusing `TypeError`** — `pkg/rancher-desktop/utils/parseQuantity.ts:45` [Orchestrator]

```ts

```

`in` consults inherited properties, so `constructor`, `toString`, `valueOf`, and `hasOwnProperty` all test true against the object literal. `scale` is then bound to a function, and the intended `Unknown units:` error never fires. Running the real parser on `1constructor` gives `TypeError: Cannot mix BigInt and other types, use explicit conversions`. The CRD pattern rejects these suffixes, so nothing reaches it through the App spec; this is robustness of a utility that presents itself as general.

Fix: `Object.hasOwn(scaleMapping, suffix)`, or hoist the map to a module-level null-prototype object.

## Design Observations

**Concerns**

- **A hand-rolled parser for a stable third-party grammar** (in-scope) [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.5 Flash] — `parseQuantity.ts` reimplements the `k8s.io/apimachinery` Quantity grammar, and three of this round's findings against it (I1, I2, S7) are grammar-fidelity bugs, the long tail the reference implementation already absorbed. No JS Quantity library is installed, so swapping one in is not free. The scope can shrink instead: the renderer only reads a byte count from `spec.virtualMachine.memory` and writes back `<int>Gi`. A `parseMemoryBytes` covering the binary suffixes plus a bare integer is a far smaller correctness surface than the full grammar. Keeping the general parser means owning the whole of `suffix.go`, and the tests should be generated against it rather than hand-picked.
- **Truncation compounds twice on the display path** (future) [Claude Opus 5] — `parseQuantity` truncates toward zero, then `memoryInGB` truncates again at `Number(bytes / gigaScale)`. Kubernetes' own `Quantity.Value()` rounds away from zero, so both layers disagree with the source of truth in the same direction: `1500m` gives `1n` here and `2` there. Measured against the shipped defaulter, every host whose reported RAM is under 24 GiB and not a multiple of 4 GiB gets a fractional default that displays low: 10 GiB gives `2560Mi` shown as 2, and 18 GiB gives `4608Mi` shown as 4. An 18 GB Apple silicon machine is a stock configuration. This is the facet Jan deferred; noted for the revisit he flagged.
- **`help.ts`'s exhaustive `satisfies` has a maintenance cliff** (future) [Claude Opus 5] — tightening `Partial<Record<TabKey, string>>` to `Record<TabKey, ...>` is the right direction, but it forces the mapping entries to be commented out in lockstep with the nav items. Re-enabling a nav item now means editing two files in one commit or the build breaks. That is the intended safety property, and it deserves a comment saying so before someone reads the commented block as dead code.

**Strengths**

- Deriving `TransientPreferencesState` from `preferencesNavDefaults` removes a hand-maintained mirror of the tab literals. Round 1's I2 was exactly the drift this prevents from here on. (in-scope) [Claude Opus 5, Gemini 3.1 Pro]
- Making the `help.ts` mapping exhaustive turns a silently missing doc URL into a compile error. (in-scope) [Claude Opus 5, Gemini 3.5 Flash]
- The mock `HostInfo` reconciler gives the e2e a deterministic hardware envelope, so the Playwright job does not depend on the CI runner's real RAM and core count. (in-scope) [all four reviewers]
- `watchResources`/`unwatchResources` on mount and unmount ref-counts the `HostInfo` watch, so it is not held open while the tab is closed. (in-scope) [Codex GPT 5.6 Sol, Claude Opus 5]

## Testing Assessment

CI is fully green at the review SHA: all four `package` jobs, `e2e-tests`, every BATS matrix job, and the lint jobs. Only signing and OBS are skipped. The gaps sit outside that coverage, ranked by risk:

1. **The daemon-side write is never asserted** (S1). No test at any layer confirms that moving a slider produces `spec.virtualMachine.memory == "8Gi"` on the App, and the dotted dispatch keys are untyped, so a typo ships green.
2. **`parseQuantity`'s spec has no case for the inputs it gets wrong** (I1, I2). The suite covers about 30 inputs and misses every leading- and trailing-dot form and every non-string value, which is exactly the class that still throws.
3. **`memoryInGB` and `availMemoryInGB` have no unit coverage.** The BigInt division, the `'2Gi'` fallback, and the absent-`hostInfo` fallback are reachable only through the e2e, which does not exercise them.
4. **Windows is asserted but not exercised.** The PR drops `test.skip(os.platform() === 'win32')` so the VM tab is always tested, but the Playwright workflow runs ubuntu-only, so the behavior the change enables is untested by construction.
5. **Out-of-range drags are silent.** `SystemPreferences.updatedVal` returns without emitting when `hasError` fires, and `VirtualMachineHardware.vue` binds neither `error` nor `warning`. Pre-existing, but wiring the component to live host data makes the range boundaries reachable for the first time.

Executed during consolidation, rather than reasoned: the parser was run over its real source against the leading-dot, trailing-dot, prototype-chain, and numeric inputs; `resource.ParseQuantity` and `NewQuantity` were run against the repo's pinned apimachinery to establish which forms canonicalize and which survive verbatim; `tsc` was run over the full `pkg/rancher-desktop` project at both the review SHA and the merge-base to produce the I3 error counts; and CI status was read from the API for the review SHA.

## Review Process Notes

**Skill improvements**

- Before stating that a defect breaks a named CI job, build step, or release gate, read that job's status at the review SHA and report what you found. ### Design Observations

**Concerns**

1. **A hand-rolled parser for a stable third-party grammar** *(in-scope)*. `parseQuantity.ts` reimplements `k8s.io/apimachinery/pkg/api/resource`'s grammar, and the two findings against it (I1, S1) are both grammar-fidelity bugs — the long tail the reference implementation already absorbed. The repo has no JS Quantity library installed, so replacing it is not free, but the *scope* can shrink: the renderer only ever reads a byte count from `spec.virtualMachine.memory` and writes back `<int>Gi`. A `parseMemoryBytes` that handles the binary suffixes plus a bare integer, and throws a UI-safe sentinel otherwise, is a much smaller correctness surface than "parse the Kubernetes Quantity grammar". If the general parser is kept, its contract is a wire-format parser and should be exercised against the exact set `suffix.go` defines rather than a hand-picked list.

2. **Truncation compounds twice on the display path** *(future)*. `parseQuantity` truncates toward zero (documented), then `memoryInGB` truncates again at `Number(bytes / gigaScale)`. Kubernetes' own `Quantity.Value()` rounds *away* from zero, so the two layers disagree with the source of truth in the same direction. Measured against the shipped defaulter (`app_defaulter.go:125`), every host whose RAM in GiB is not a multiple of 4 and is under 24 GiB gets a fractional default: 10 GiB → `2560Mi` displays `2`, 18 GiB → `4608Mi` displays `4`. 18 GB is a stock Apple silicon configuration. A single `Math.round(Number(bytes) / 2 ** 30)` at the display layer would show `2.5 → 3` instead of `2`, and nothing writes back unless the user moves the slider (`updatedVal` only fires on `@change`), so there is no silent-downgrade risk either way. This is the facet the author deferred; noted here for the future revisit he flagged.

3. **`help.ts`'s exhaustive `satisfies` has a maintenance cliff** *(future)*. Tightening `Partial<Record<TabKey, string>>` to `Record<TabKey, …>` (`help.ts:32`) is the right direction, but it forced eight mapping entries to be commented out in lockstep with the nav items. Re-enabling a nav item now requires editing two files in the same commit or the build breaks. That is the intended safety property, but it is worth a comment at `help.ts:21` saying so — otherwise the next person reads the commented block as dead code and deletes it.

**Strengths**

- Deriving `TransientPreferencesState` from `preferencesNavDefaults` removes a hand-maintained mirror of the tab literals; the prior I2 type error was exactly the drift that change prevents going forward.
- Making `help.ts`'s mapping exhaustive rather than `Partial` converts a silent missing-doc-URL into a compile error.
- The mock `HostInfo` reconciler is the right shape for the e2e: it gives the UI a deterministic hardware envelope without the Playwright job depending on the CI runner's real RAM and core count.
- `hostinfo_controller.go:81-96`'s `Start` correctly retries internally and returns `nil`, honouring the manager-Runnable contract; the mock's simpler create-or-update is fine because it runs from a watch, not a Runnable.

### Executive Summary

### Findings

#### Critical Issues

C1. **`parseQuantity` rejects valid fractional quantities** — `pkg/rancher-desktop/utils/parseQuantity.ts:59-63`

```typescript
  const [, sign, whole, fraction = '0'] = /^([+-]?)([0-9]+)?(?:\.([0-9]+))?$/.exec(numeral) ?? [];

  if (whole === undefined) {
    throw new Error(`Malformed quantity: ${ trimmed }`);
  }
```

The regex completely fails to match inputs ending in a dot (e.g., `1.`), returning `null`. For inputs beginning with a dot (e.g., `.5Gi`), the regex matches but fails to capture group 2, leaving `whole` as `undefined`.   if (!match || (!match[2] && !match[3])) throw new Error(`Malformed quantity: ${ trimmed }`);
```typescript
  const [, sign, whole = '0', rawFraction = '0'] = match;
```

### Executive Summary

This pull request restores the Virtual Machine memory and CPU hardware preferences tab in the user interface. While the new hand-written `parseQuantity` utility successfully resolves prior crashes on fractional inputs, a critical bigint integer division flooring bug in the UI logic causes fractional GiB selections to immediately snap back to floored values. Additionally, a rename of navigation test attributes has left three E2E page objects stale.

### Findings

#### Critical Issues

C1. **Memory value snap-back / floor-truncation on fractional GiB inputs** — `pkg/rancher-desktop/components/Preferences/VirtualMachineHardware.vue:18-24` (critical, regression)

```typescript
const memoryInGB = computed(() => {
  // quantityToScalar will return BigInts in our case; convert it to gigabytes,
  // at which point it should be reasonable for us.
  const memoryInBytes = parseQuantity(preferences.value?.virtualMachine?.memory ?? '2Gi');
  return Number(memoryInBytes / gigaScale);
});
```

In `VirtualMachineHardware.vue`, the `memoryInGB` computed getter at line 14 parses the memory string from preferences (line 17) and performs a floored bigint division at line 18: `Number(memoryInBytes / gigaScale)`. Because bigint division in JS always truncates the fraction, fractional values such as `2.5Gi` (parsed to `2684354560n` bytes) are floored to `2n` bytes (2 GB) before conversion.
When a user sets a fractional memory value (e.g. 2.5 GB) in the UI, `setMemory` at line 32 dispatches it as `"2.5Gi"`. During the subsequent re-render, the computed `memoryInGB` evaluates to `2` instead of `2.5`. This forces the slider/input (rendered at line 49) to snap back to 2 GB, making fractional selections impossible to persist or display in the UI.

Fix: Perform floating-point division by converting the bigints to numbers first, ensuring precise decimal calculations:

I1. **Hand-written Quantity parser throws on valid fractional-only numbers** — `pkg/rancher-desktop/utils/parseQuantity.ts:61-66` (important, regression)

```typescript
  if (whole === undefined) {
    throw new Error(`Malformed quantity: ${ trimmed }`);
  }

  const denom = 10n ** BigInt(fraction.length);
  const numer = (BigInt(whole) * denom + BigInt(fraction)) * (sign === '-' ? -1n : 1n);
```

In `parseQuantity.ts`, the second regex on line 59 `/^([+-]?)([0-9]+)?(?:\.([0-9]+))?$/` parses the numeric portion. If a valid Kubernetes Quantity with no whole-number part (such as `".5Gi"` or `".5"`) is supplied, the regex captures `whole` as `undefined` and `fraction` as `"5"`.
At line 61, the check `if (whole === undefined)` triggers, throwing a malformed quantity error. According to the Kubernetes Quantity specification, fractional-only coefficients like `".5"` are fully valid. This regression prevents custom-defined or manually configured sub-unit/fractional quantities from being parsed.

#### Suggestions

S1. **`applicable` platform-filter mechanism is half-built / lacks type-safety** — `pkg/rancher-desktop/window/preferenceConstants.ts:46-51` (suggestion, gap)

```typescript
type navItemResult<T extends readonly navItemEntry[]> = {
  [K in T[number]['name']]: Omit<Extract<T[number], { name: K }>, 'applicable' | 'name'> & { index: number };
};
```

The type mapping for filtered navigation items (`navItemResult<T>`) dynamically constructs keys from `T[number]['name']` without checking if `item.applicable?.()` evaluates to false at runtime. If an item is filtered out (as WSL would be on non-Windows hosts once active), its key will be present in the TypeScript definition but `undefined` at runtime.

Fix: Make the mapped keys in `navItemResult<T>` optional, or ensure type definitions are conditional on the platform structure:
```typescript
type navItemResult<T extends readonly navItemEntry[]> = {
  [K in T[number]['name']]?: Omit<Extract<T[number], { name: K }>, 'applicable' | 'name'> & { index: number };
};
```

S2. **Consolidate kebab-casing helper implementations** — `pkg/rancher-desktop/window/preferenceConstants.ts:58-61` (suggestion, gap)

```typescript
type KebabCase<T extends string> = T extends `${ infer Head }${ infer Tail }`
  ? `${ Head extends Alpha<Head> ? Lowercase<Head> : KebabCase<Tail> extends `-${ string }` ? '' : '-' }${ KebabCase<Tail> }`
  : T;
```

There are three separate and divergent implementations of kebab-casing used for preferences navigation: the type-level `KebabCase<T>` helper, lodash's `_.kebabCase` at runtime, and `toLowerCase().replace(/ /g, '-')` in `help.ts`. While they align for current items, a future top-level nav item name containing consecutive spaces or special characters could silently desynchronize their outputs and cause broken links.

Fix: Centralize runtime kebab-casing into a single shared utility function, and document the type-level `KebabCase` helper to align its exact parsing logic.

S3. **Document phantom `kubernetes: never` property** — `pkg/rancher-desktop/window/preferenceConstants.ts:67-70` (suggestion, gap)

```typescript
type PreferenceNavTabDefaults = {
  [K in keyof typeof preferencesNavItems as KebabCase<K>]:
  (typeof preferencesNavItems)[K] extends { tabs: readonly ([infer T, string])[] } ? T : never;
};
```

The `PreferenceNavTabDefaults` type-level mapping generates a phantom `'kubernetes': never` property for items without sub-tabs. Since it has no runtime counterpart in `preferencesNavDefaults`, a developer could easily find this confusing or try to remove it, which would break the `TabKey` and documentation mapping in `help.ts`.

Fix: Add a clear explaining comment above `PreferenceNavTabDefaults` detailing that keys with `never` values are load-bearing for the help-mapping type resolution in `help.ts`.

S4. **Add test cases for fractional-only quantity inputs** — `pkg/rancher-desktop/utils/__tests__/parseQuantity.spec.ts:1` (suggestion, gap)

The test suite for the new `parseQuantity` module lacks coverage for fractional-only numbers like `".5Gi"` and negative fractional quantities with negative scale mapping.

Fix: Add the following test cases in `parseQuantity.spec.ts`:
```typescript
  test('parses fractional-only quantities', () => {
    expect(parseQuantity('.5Gi')).toBe(536870912n);
    expect(parseQuantity('-.5Ki')).toBe(-512n);
  });
```

### Design Observations

#### Concerns
*   **Centralized Parsing Utility:** Creating custom parser algorithms for Kubernetes Quantities has a long tail of edge cases. While `parseQuantity.ts` successfully implements decimal SI/binary scaling (resolving `I1`), wrapping a fully featured third-party or official k8s parser package is generally preferred over custom-rolled string parsers if available in the ecosystem. *(in-scope)*

#### Strengths
*   **Mock HostInfo Reconciler implementation:** Integrating a full `hostInfoReconciler` (`rdd/pkg/controllers/mock/hostinfo_reconciler.go`) within the mock controller is beautifully executed. It enforces a deterministic mock environment (32 CPUs and 12 GiB memory) that directly facilitates robust, platform-independent E2E tests in CI.
