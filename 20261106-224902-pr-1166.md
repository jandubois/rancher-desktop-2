I2. **The new comment says size changes stop after 500 ms, but only Linux re-centering stops** — `pkg/rancher-desktop/window/index.ts:590` [Claude Opus 5.5]

```ts
    // Allow size changes for a short time after the initial open, in case
    // things need to be updated quickly.
    setTimeout(() => { hasInitialSize = true }, 500);
```

The flag decides one thing: whether the Linux branch calls `resizeWindow`, which centers the window on its parent (line 565). Once the timer fires, Linux still calls `setContentSize` at line 567, and the win32 and default branches never read the flag. So size changes continue for the life of the window, which round 1's I2 fix depends on, and only the re-centering stops. A reader who trusts the comment will expect a dialog to stop following its content after 500 ms. The probe runs the real `openDialog` on Linux with fake windows. If the comment held, the third event would call neither `resizeWindow` nor `setContentSize`.

## Suggestions

S1. **Shrinking or narrowing the window cuts off the buttons, and a corner drag snaps the width back** — `pkg/rancher-desktop/pages/FatalError.vue:101` [Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]

```scss
  .container {
    width: max-content;
    height: calc-size(max-content, max(size, 100vh - 2.5rem /* from .wrapper padding */));
    max-width: 52rem;
  }
```

The container's width never follows the window, and its height follows the window only above the content height. So shrinking the window below its content does not fire `preferred-size-changed`, and `body { overflow: hidden }` (`layouts/dialog.vue:62`) hides what no longer fits. Rendered on macOS, narrowing the 763x269 dialog by 200px left Close at x=725 in a 563px viewport, and shortening it by 100px left Close at y=250 in a 169px one. Growing it in both directions does change the preferred height, and the handler's `setContentSize(width, height)` then put the width back from 963 to 763. Round 1's S3 needed the details open; now any shrink does it. The final commit's message says the dialog deliberately omits size limits, and Escape or the title bar still closes it.

Fix: let the message and details boxes shrink with the window so the button bar stays in view, without window size limits.

S2. **A repeat call during load shows the dialog before it is ready** — `pkg/rancher-desktop/window/index.ts:676` [Codex GPT 6 Astra, Claude Opus 5.5, Gemini 3.5 Flash]

```ts
    existingWindow.webContents.send('dialog/populate', fatalErrorParams);
    restoreWindow(existingWindow);
```

`createWindow` registers the window as soon as it starts loading (`window/index.ts:103`), so a second call during load takes this branch. `restoreWindow` calls `show()` on any window without focus (lines 37-42), and a hidden window has none. The dialog therefore appears before the page sends `dialog/ready`, possibly still at its 100x100 creation size. A probe that runs the real `openFatalErrorDialog` and `restoreWindow` source counted one `show()` before `dialog/ready`. The latest-payload part of round 1's S1 works: the same probe saw the window's `dialog/load` handler send the newest message.

Fix: skip `restoreWindow` until the window has sent `dialog/ready`, for example with a flag that the dialog's `dialog/ready` handler sets.

S3. **An empty title or message still leaves the dialog blank** — `pkg/rancher-desktop/pages/FatalError.vue:86` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]

```ts
ipcRenderer.on('dialog/populate', (_event, { title, message, details }) => {
  titlePart.value = title;
  mainMessage.value = message;
  failureDetails.value = details ?? '';
});
```

Round 1's S2 is unaddressed. The window stays hidden until the first `dialog/populate` (`layouts/dialog.vue:47-51`), and this handler then replaces the placeholders from lines 75-76 with whatever arrives. #1167 passes the App condition's reason and message, so a condition without them shows an empty heading over an empty grey box. A probe spec that populates `{ title: '', message: '' }` gets `""` where it expects "Unknown Error".

Fix: fall back with `title || t.value('fatalError.titleUnknown')` and `message || t.value('fatalError.messageUnknown')`, and point the spec's first case at that fallback.

S4. **A caller that starts waiting in the same tick as a close and reopen waits for the new window too** — `pkg/rancher-desktop/window/index.ts:694` [Codex GPT 6 Astra]

```ts
  window.on('closed', () => fatalErrorClosed.resolve());
  fatalErrorClosed.reset();
  await fatalErrorClosed;
```

`await` calls the Latch's `then` a microtask later, and only then does `waitForSettled` read the latch's state (`utils/latch.ts:63-80`). If the dialog closes and a new one opens in the same tick as a caller's `await`, `reset()` runs first, and that caller also waits for the new window to close. A probe with the real `latch.ts` showed `await latch` still waiting after `resolve()` and `reset()`, while `await latch.then()` returned. Nothing closes and reopens the dialog in one tick today.

Fix: write `await fatalErrorClosed.then()` at lines 677 and 694, which reads the latch's state when the call runs.

S5. **`RD_OS` and `RD_ARCH` are still build-time variables in four files** — `pkg/rancher-desktop/vue.config.mjs:51` [Codex GPT 6 Astra, Claude Opus 5.5, Gemini 3.5 Flash]

```js
      'process.env.RD_OS':       JSON.stringify(process.env.RD_OS),
      'process.env.RD_ARCH':     JSON.stringify(process.env.RD_ARCH),
```

Round 1's S5 is unaddressed. The two variables exist only for the version line (`FatalError.vue:82-83`), and `scripts/build.ts`, `scripts/dev.ts` and `scripts/e2e.ts` each set them. Dialog windows run with `nodeIntegration: true` (`window/index.ts:542`), so the page can compute both values. All three entry points set them today, so nothing is broken; a fourth one would compile `undefined` into the version line.

Fix: call `artifactPlatform(process.platform)` and `artifactArch(process.arch)` in `FatalError.vue`, and drop the edits to the four build files.

S6. **The new spec lacks the SPDX header that its page gained** — `pkg/rancher-desktop/pages/__tests__/FatalError.spec.ts:1` [Codex GPT 6 Astra, Claude Opus 5.5, Gemini 3.1 Pro]

```ts
import { jest } from '@jest/globals';
```

This round added the header to `FatalError.vue:1-5` but not to its spec, which round 1's S7 also covered. Of the four page specs in this directory, only `Volumes.spec.ts` has one; commit `c6684bd2c` added it there for new test files.

Fix: prepend the three lines from `Volumes.spec.ts:1-3`.

S7. **The layout's header comment does not mention `data-auto-width`** — `pkg/rancher-desktop/layouts/dialog.vue:1` [Gemini 3.5 Flash, Codex GPT 6 Astra, Claude Opus 5.5]

```html
<!--
  - This layout is used by dialog boxes that do not want navigation.
  - With the help of .../pkg/rancher-desktop/window/index.ts, this also handles automatic sizing
  - of the dialog boxes, using the given events:
  - emit    'dialog/load':     the dialog has been mounted.
  - receive 'dialog/populate': any additional data for the dialog.
  - emit    'dialog/ready':    the dialog is ready to be displayed.

```

The comment lists what a dialog page can use, and this round removed its stale `data-flex` paragraph, which nothing at the merge-base read. When a page sets `data-auto-width` on its root element, as `FatalError.vue:10` does, the rule at lines 79-81 sizes the dialog to the page's unwrapped content. That page must then limit its own width, as `FatalError.vue:103` does with `max-width`. The comment says neither.

Fix: add a line to the comment for `data-auto-width` and the `max-width` that it needs.

## Design Observations

### Concerns

- **(future)** Nothing records that the user dismissed the dialog. Under #1167, each App status change while the `FatalError` condition holds calls `openFatalErrorDialog`, so a dialog that the user closed comes back with the next change. Raised in round 1 and still open. [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]
- **(future)** `Troubleshooting.vue:166` sends `show-logs`, which nothing in the main process handles, while the new handler listens on `error/show-logs` (`background.ts:308`). One channel would serve both pages once the Troubleshooting page returns to the nav. Raised in round 1 and still open. [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]

### Strengths

- **(in-scope)** The `data-auto-width` opt-in keeps the intrinsic width to FatalError. Rendered at the review SHA, DenyRoot measured 420x171 and UnmetPrerequisites 455x276, the same as at the merge-base. [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]
- **(in-scope)** `fatalErrorParams` and the shared `Latch` fix round 1's lost update and listener pile-up. A late `dialog/load` sends the newest message, each window adds one `closed` listener, and every waiter resolves when the dialog closes. [Codex GPT 6 Astra, Claude Opus 5.5, Gemini 3.5 Flash, Gemini 3.1 Pro]
- **(in-scope)** The page renders the backend's text with `v-text`, and uses `v-clean-html` only for the translated version line. [Codex GPT 6 Astra, Gemini 3.5 Flash]

## Acknowledged Limitations

- Nothing calls the dialog in this PR, as commit `86b5ae0b3` says, and #1167 adds the first caller. I1 and S1 through S4 become reachable only then.
- Do not re-suggest replacing `max(size, 100vh - 2.5rem)` with `min()` at `FatalError.vue:102`. `100vh` is the dialog window's own height, and `max` lets the container fill a window that the user has made taller.
- Do not re-suggest `overflow: auto` on `body` as the fix for S1. Rendered at the review SHA, it did not scroll. Each shrink fired two more `preferred-size-changed` events, and the window snapped back to its content size. I suspect a scrollbar appearing changes the preferred size, but I did not check that.
- The refocus in the existing-window branch is intended, as its comment says ("update it, and focus"). S2 asks only to defer it until the window is ready.

###### Design Observations

###### Concerns

- **(in-scope)** Auto-sizing and user resizing conflict: Dialog windows rely on `enablePreferredSizeMode` and continuous `preferred-size-changed` events while `.container` has `width: max-content` and a height coupled to `100vh`. Separating initial auto-fit sizing from subsequent user resizing (or using standard CSS flex layout where the container fills the window) would allow users to resize freely without snap-back or button clipping (I1).
- **(future)** Error dismissal tracking: Nothing tracks whether the user dismissed a fatal error dialog. When callers like draft PR #1167 trigger on every backend condition update, a dismissed dialog will reappear on the next status change.
- **(future)** Unified logs IPC channel: `Troubleshooting.vue:166` sends `'show-logs'` (currently unhandled in the main process), while `FatalError.vue` sends `'error/show-logs'`. Handling both channels in `background.ts:308` would restore functionality to Troubleshooting without extra IPC handlers.

###### Strengths

- **(in-scope)** XSS prevention: Error details, main messages, and titles are bound using `v-text` (`FatalError.vue:29, 33, 42`), restricting `v-clean-html` strictly to the version line to render `&mdash;`.
- **(in-scope)** Fallback log handling: `background.ts:311-325` gracefully handles failures from `shell.openPath` by logging the error and displaying a translated native message box directing the user to the log directory.
- **(in-scope)** Caller coordination: `openFatalErrorDialog` uses a centralized module-level `Latch` (`fatalErrorClosed`) and `fatalErrorParams`, avoiding duplicate window creation, consolidating concurrent callers, and eliminating listener accumulation.
