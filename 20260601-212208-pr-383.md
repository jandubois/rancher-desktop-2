## Important Issues

I1. **`IsOurProcess` is a Unix no-op, so a recycled on-disk PID can be SIGKILLed as a process group** — `pkg/util/process/process_unix.go:30-38` [Gemini 3.1 Pro]

```go
func IsOurProcess(_ int, _ ...string) bool {
	return true
}
```

The Windows guard rejects a recycled PID before acting on it; on Unix the function always returns true. `killOrphanedHostagent` and the force-stop paths read `HostAgentPID` from a previous service's `ha.pid`. After a crash or reboot, Lima's `ReadPIDFile` returns that PID whenever it is merely alive (a `Signal(0)` check, not identity), so a recycled PID passes. The path SIGINTs it, waits 30s for a stop that never comes, then `KillTree` (`process_unix.go:57-68`) SIGKILLs its process group.

I downgrade Gemini's Critical to Important: it predates this PR, which is deliberately Windows-scoped, and needs a stale PID file plus recycling. But the no-op's docstring claims PIDs "are not recycled within a daemon's lifetime" — false for an on-disk PID from a *previous* lifetime.

Fix: verify identity on Unix (`/proc/<pid>/exe`, `proc_pidpath`), or document the residual risk and why it is accepted.

## Suggestions

S1. **`PID()` removes the PID file on a transient identity-check failure, not only a true mismatch** — `pkg/service/cmd/service.go:167-174` [Claude Opus 4.8]

```go
if err == nil && !process.IsOurProcess(pid, "service", "serve") {
	err = fmt.Errorf("pid %d is not our control plane", pid)
}
if err != nil {
	_ = os.Remove(instance.PIDFile())
	return PIDNotFound
}
```

`IsOurProcess` returns false for any state it cannot positively confirm — `OpenProcess` denied, a short `ReadProcessMemory` on the PEB walk, or `os.Executable()` failing. On Windows this collapses "the control plane is gone" and "I could not inspect a live control plane this instant" into one outcome, and the next line deletes the PID file. A false negative then makes `Running()` report a live control plane as dead and orphans it. For a same-user process holding only `PROCESS_QUERY_LIMITED_INFORMATION|PROCESS_VM_READ` this is very unlikely, so severity is low; the `longPath` comment reasons only about short-path resolution, not these modes.

Fix: note in the `PID()` comment that an inaccessible-but-live control plane reads as not-running and loses its PID file, or distinguish `OpenProcess`-denied from a clean "process gone" before removing the file.

S2. **`processCommandLine` sizes the buffer from `Length/2` but reads `Length` bytes** — `pkg/util/process/process_windows.go:177-186` [Claude Opus 4.8]

```go
length := params.CommandLine.Length
buf := make([]uint16, length/2)
// later: readProcessMemory(..., &buf[0], uintptr(length))
```

`buf` holds `length/2` UTF-16 units, which is `length` bytes only when `length` is even. The read requests `uintptr(length)` bytes, so an odd `length` overflows `buf` by one byte. `NTUnicodeString.Length` counts bytes and is always even, so this cannot fire today — but the code reads `length` bytes into a buffer sized from `length/2` with no assertion of the relation.

Fix: reject an odd `length` with an error, or size the read as `len(buf)*2`, making the invariant explicit.

S3. **`Running()` runs a full PEB walk on every 100 ms poll during shutdown** — `pkg/service/cmd/service.go:445-446` [Claude Opus 4.8]

```go
case <-ticker.C:
	if !Running() {
```

`StopWithWait` polls `Running()` every 100 ms for up to 60s, and `Running()` → `PID()` now performs `OpenProcess` + `NtQueryInformationProcess` + three `ReadProcessMemory` calls per poll — up to ~600 cross-process PEB walks per stop. The cost is negligible and not worth restructuring, but a reader will not expect `Running()` to be this heavy.

Fix: add a one-line note on `PID()` that its Windows path inspects the target's command line, so future hot-loop callers know the cost.

## Design Observations

**Concerns**

- **Action-scoped process APIs would close the validate-then-use window** `(future)` [Codex GPT 5.5] — `IsOurProcess` opens a process handle, verifies identity, closes the handle, and returns a bool (`process_windows.go:63-73`); the caller then acts on the bare PID. Between the return and the `Interrupt`/`taskkill`, the verified process could exit and Windows could recycle the PID. Codex rated this Important; verification reduces it: the window is a function return to the next syscall with no death-trigger inside it, and the guard still removes the 30-second window Round 1 fixed, so it is not a regression. `InterruptIfOurProcess`/`KillTreeIfOurProcess`, holding the handle through the action, would encode the invariant in the API and remove the class.

- **Shutdown timeout budgets are uncoordinated** `(future)` [Codex GPT 5.5] — `shutdownAllHostagents` can spend `gracefulShutdownTimeout` (30s) + cleanup (30s) + post-kill wait (10s) per instance, sequentially, while `Run` abandons the manager after 45s (`service.go:863`) and the CLI kills the service after 60s (`service.go:429`). Codex rated this Important and cited the 60s CLI kill as binding; the service's own 45s abandon fires first. On Windows `procExited` closes promptly under force-kill, so the 30s wait is skipped and one instance reclaims in ~10s — within budget. A stuck hostagent (procExited never closes) or several instances could exceed 45s and abandon cleanup; the sequential loop is already TODO'd (`limavm_controller.go:540`).

**Strengths**

- The recycled-PID guard sits at all six force-stop sites (`limavm_lifecycle.go:210,547,618,679`, `limavm_controller.go:566`, `service.go:167`), and the copy-vs-mutate choice is correct at each: sites that reuse `inst` afterward copy into `forceInst`/`safeInst`, while `shutdownAllHostagents` mutates its loop-local value. [Claude Opus 4.8, Codex GPT 5.5]
- `hostAgentPIDFile` reconstructs the exact `--pidfile` path the hostagent was launched with (`limavm_lifecycle.go:367,651`), an unambiguous per-instance discriminator that closes the prefix-collision footgun from Round 1's S1. [Codex GPT 5.5, Claude Opus 4.8]
- `IsOurProcess` returns false, never an error, for any unconfirmable state, so callers treat "unknown" as "not ours." [Claude Opus 4.8, Gemini 3.1 Pro]
- `samePath`/`longPath` normalize 8.3 short paths before comparison, and the PEB command-line read avoids WMI and external tools. [Gemini 3.1 Pro, Claude Opus 4.8]

## Review Process Notes

**Skill improvement — Correctness dimension: platform no-op guard rationale.** When a cross-platform safety check is a no-op (or a weaker form) on some platform because "the hazard does not apply here," verify that justification against every caller. A guard whose no-op is safe for in-process state is often unsafe for callers acting on state persisted by a *previous* process — PID files, lock files, on-disk handles — because the "within one process lifetime" assumption that licenses the no-op breaks across a restart, crash, or reboot. Flag a no-op or weakened guard whose docstring asserts a safety property the caller's data source contradicts. Recognize the pattern when a function reads an identifier from disk and a same-named guard returns a constant on the current platform.

**Skill improvement — Correctness dimension: identify the binding deadline.** When a finding claims an operation can exceed a deadline — a cleanup outliving a stop, a wait outliving a budget — enumerate every timeout, abandon, and kill point along the path: the outer caller's wait, the callee's own self-abandon, and any per-iteration bound. Determine which fires first. The binding limit is often an inner self-timeout that exits before the outer caller's kill, so a finding citing only the outermost deadline can misattribute both the mechanism and the severity. Verify the worst-case sum against the smallest enclosing deadline, not the largest.

**[repo] Unix `ReadPIDFile` trusts an alive PID without identity.** On Unix, Lima's `ReadPIDFile` (`pkg/store/instance.go`) returns the stored PID whenever the process is merely alive — it checks `Signal(0)`, not identity — and removes the file only when the PID is dead. `process.IsOurProcess` is a no-op (returns true) on Unix. So an on-disk `HostAgentPID`/`DriverPID` recycled to an unrelated *live* process is trusted by the lima-controller's force-stop paths, which then `SIGINT` it and, after the graceful wait, `SIGKILL` its process group via `KillTree`. When reviewing lima-controller process-lifecycle code, treat a recycled-but-alive on-disk PID as reachable on Unix after a crash or reboot leaves a stale `ha.pid`, not only on Windows.

### [Gemini 3.1 Pro]

### Executive Summary

This PR successfully addresses the risk of PID recycling on Windows by verifying process identity via PEB introspection before signaling or forcefully killing orphaned instances. However, the decision to skip this identity verification on Unix introduces a critical regression: because `ha.pid` persists across daemon lifetimes and system reboots, a recycled PID on Unix will be blindly trusted and forcefully terminated via a process-group `SIGKILL`. 

### Findings

**Critical Issues**

C1. **`IsOurProcess` unconditionally returns `true` on Unix, permitting `SIGKILL` on unrelated processes** — `pkg/util/process/process_unix.go:30-39` (critical, gap)

```go
// IsOurProcess reports whether pid is a live process running this program's own
// executable. On Unix it is always true: PIDs are not recycled within a
// daemon's lifetime the way they are on Windows...
func IsOurProcess(_ int, _ ...string) bool {
	return true
}
```

The assumption that PIDs are not recycled "within a daemon's lifetime" ignores that `killOrphanedHostagent` retrieves `inst.HostAgentPID` from the on-disk `ha.pid` file left behind by a *previous* daemon run or a system crash. Over the hours or days since the crash, the OS may have recycled this PID to an unrelated user process (e.g., `bash`, `vim`, or a browser). Because `IsOurProcess` unconditionally blesses the stale PID, the controller will send `SIGINT` to the unrelated process. If the process does not exit, the graceful timeout expires and `stopInstanceForcibly` invokes `process.KillTree`, which sends `SIGKILL` to the unrelated process's entire process group.

**Fix**: Implement identity verification for Unix. On Linux, verify that `/proc/<pid>/exe` matches `os.Executable()` and `/proc/<pid>/cmdline` contains the expected substrings. On macOS, use `proc_pidpath` (or `sysctl` with `KERN_PROCARGS2`).

**Important Issues**

None.

**Suggestions**
