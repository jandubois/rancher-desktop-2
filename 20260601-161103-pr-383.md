## Executive Summary

PR #383 adds `process.IsOurProcess` to verify a Windows PID still runs rdd's own executable before signalling or taskkilling it, guards `service.PID()` against recycled PIDs, and makes `shutdownAllHostagents` reclaim leftover PID files and WSL2 distros after every graceful shutdown. The hardening is careful and thoroughly commented. The one gap: `killOrphanedHostagent` verifies identity before its 30-second graceful wait but not before the forceStop that follows — unlike its sibling `shutdownHostagent`, which re-checks.

Three cloud reviewers ran. Codex found nothing to fix; Claude raised robustness and documentation suggestions; Gemini surfaced the one Important gap (I1) and the underlying lifecycle design concern.

## Important Issues

I1. **Re-verify the hostagent PID before forceStop in `killOrphanedHostagent`** — `pkg/controllers/lima/limavm/controllers/limavm_lifecycle.go:601-617` [Gemini 3.1 Pro]

```go
if inst.HostAgentPID > 0 && process.IsOurProcess(inst.HostAgentPID, "hostagent", inst.Name) {
    if err := process.Interrupt(inst.HostAgentPID); err == nil {
        stopCtx, cancel := context.WithTimeout(ctx, gracefulShutdownTimeout) // 30s
        defer cancel()
        if waitForInstanceStopped(stopCtx, inst.Name) { return nil }
    }
} // else: forceInst.HostAgentPID = 0
stopInstanceForcibly(ctx, logger, &forceInst) // PID verified 30s ago, not re-checked
```

`IsOurProcess` runs once at line 601, before a wait of up to `gracefulShutdownTimeout` (30s, `limavm_controller.go:86`). On the timeout fall-through the code taskkills `forceInst.HostAgentPID` — the PID verified 30 seconds earlier. In the orphaned path no `os.Process` handle pins that PID, so once the signalled hostagent dies without the instance reaching `StatusStopped` (a WSL2 distro the keepAlive process keeps running), Windows can recycle the PID and the taskkill hits an unrelated process. `shutdownHostagent` re-checks `IsOurProcess` right before its forceStop (lines 546-550); its comment claims all force paths do, but this one does not. (important, gap)

Fix: drop the `else` and re-verify unconditionally before the forced stop, mirroring `shutdownHostagent`.

```diff
-	} else {
-		forceInst.HostAgentPID = 0
-	}
-
+	}
+	if forceInst.HostAgentPID > 0 && !process.IsOurProcess(forceInst.HostAgentPID, "hostagent", forceInst.Name) {
+		forceInst.HostAgentPID = 0
+	}
 	stopInstanceForcibly(ctx, logger, &forceInst)
```

## Suggestions

S1. **Anchor the instance-name discriminator passed to `IsOurProcess`** — `pkg/controllers/lima/limavm/controllers/limavm_lifecycle.go:210,547,601,666` and `limavm_controller.go:566` [Gemini 3.1 Pro, Claude Opus 4.8]

```go
process.IsOurProcess(inst.HostAgentPID, "hostagent", inst.Name)
```

Callers pass the raw `inst.Name` as the command-line discriminator, which `IsOurProcess` matches with `strings.Contains`. Its docstring warns that "vm" matches a hostagent for "vm2" and tells callers to "pass a name distinct enough" — but the callers pass the bare name. With concurrent prefix-named instances (dev/test only) plus PID recycling, the cleanup for "vm" could verify and taskkill "vm2"'s live hostagent. The hostagent command line ends with the name as its final argument, so a whole-token match closes the gap. (suggestion, gap)

Fix: pass `" "+inst.Name` (anchoring the leading space), or pass the per-instance pidfile path, which cannot collide.

S2. **`resolveLongPath` need not double the buffer** — `pkg/util/process/process_windows.go:120-129` [Gemini 3.1 Pro]

```go
for bufSize := uint32(1024); bufSize <= 32768; bufSize *= 2 {
    buf := make([]uint16, bufSize)
    n, err := windows.GetLongPathName(p16, &buf[0], bufSize)
    if n < bufSize { return windows.UTF16ToString(buf[:n]), nil }
    // n >= bufSize: the buffer was too small and n is the required size; grow.
}
```

`GetLongPathName` returns the exact required size in `n` when the buffer is too small, so the doubling loop issues extra syscalls for very long paths instead of allocating `n` directly. `processImagePath` must double because `QueryFullProcessImageName` does not report its needed size — but `resolveLongPath` has the size and can skip the loop. The code is correct as written; the parallel structure with `processImagePath` is deliberate, so this is optional. (suggestion, enhancement)

Fix: allocate 1024, and on `n >= len(buf)` reallocate to exactly `n` once.

S3. **`processCommandLine` reads the whole `RTL_USER_PROCESS_PARAMETERS`, not the prefix it uses** — `pkg/util/process/process_windows.go:171-187` [Claude Opus 4.8]

```go
var params windows.RTL_USER_PROCESS_PARAMETERS
if err := readProcessMemory(handle, uintptr(unsafe.Pointer(peb.ProcessParameters)),
    unsafe.Pointer(&params), unsafe.Sizeof(params)); err != nil {
    return "", err
}
```

`readProcessMemory` errors unless the full `unsafe.Sizeof(params)` range is read, yet the only field used (`CommandLine`) sits near the front of the struct. The read works in practice: ntdll allocates `ProcessParameters` as one block (the struct plus its string buffers plus the environment), so the trailing bytes are mapped, and `TestProcessCommandLineReadsOwnCommandLine` confirms it on CI. The cost is coupling to x/sys's full struct layout, not a live failure. (suggestion, enhancement)

Fix: read only through `CommandLine` (its offset plus size), or document why a full-struct read is safe on supported Windows.

## Design Observations

**Concerns**

- **`exec.CommandContext` hard-kills the hostagent before it can self-clean** `(future)` [Gemini 3.1 Pro] — `startInstance` spawns the hostagent with `exec.CommandContext(ctx, …)` and leaves `Cmd.Cancel`/`Cmd.WaitDelay` unset (`limavm_lifecycle.go:431`), so a manager-context cancel hard-kills it (`TerminateProcess` on Windows, `SIGKILL` on Unix) before it runs its own teardown. The PR compensates by reclaiming the leftovers externally — `stopInstanceForcibly` after the wait — which is sound. A cleaner structure sets `haCmd.Cancel` to send `process.Interrupt` and `haCmd.WaitDelay` to bound the grace period (Go 1.20+, and `go.mod` declares 1.25.7), letting the hostagent run its own shutdown (driver termination, distro cleanup, tmp removal) instead of relying on external reclaim.

- **The recycled-PID guard is copied at five sites** `(future)` [Claude Opus 4.8] — the pattern `safeInst := *inst; if safeInst.HostAgentPID > 0 && !process.IsOurProcess(…) { safeInst.HostAgentPID = 0 }; stopInstanceForcibly(…, &safeInst)` now appears at `limavm_lifecycle.go:209,546,600,665` and `limavm_controller.go:566`. I1 is the site that forgot the guard. A `stopInstanceForciblyVerified(ctx, logger, inst)` that clears a recycled `HostAgentPID` internally would make the guard impossible to omit at the next call site.

- **PID identity is validate-then-use** `(future)` [Codex GPT 5.5] — `IsOurProcess` validates a PID and a later call acts on it, leaving the validate-then-use race (I1) and the unchecked `DriverPID` the comments flag. Tracking hostagent and driver processes through a Windows Job Object rather than on-disk PID files would remove both, because the kernel terminates the job's members regardless of PID reuse. The code already names Job Objects as the proper fix.

**Strengths**

- The `procExited` gate (`hostagent_watcher.go:213-217`, `limavm_controller.go:519-523`) separates the in-memory `*exec.Cmd` paths — handle held, PID cannot recycle — from the on-disk-PID paths that need `IsOurProcess`. [Claude Opus 4.8]
- Extracting `forceStopForDeletion` deduplicates the force-stop logic and applies it to the previously-unguarded leftover-instance path (`limavm_controller.go:218`). [Claude Opus 4.8]
- `IsOurProcess` returns `false`, never an error, for any unconfirmable state, so callers safely treat "unknown" as "not ours." [Claude Opus 4.8, Codex GPT 5.5]
- The identity check lives in `pkg/util/process` with a Unix no-op that keeps the signature. [Codex GPT 5.5]
- The command line is read from the PEB natively, avoiding WMI or external tools, and long-path normalization handles 8.3 short-path launches. [Gemini 3.1 Pro]

## Review Process Notes

**Skill improvement — Correctness dimension: guard staleness across a wait.** When a destructive action (kill, delete, overwrite, unlock, free) is gated by an identity, ownership, or existence check, and a blocking wait or long-running call separates the check from the action, flag the absence of a re-check immediately before the action. The guarded entity can change identity during the wait — a recycled process ID, a replaced file, a released lock, an expired lease — so a check that passed before the wait need not hold after it. When one call path re-checks after the wait and a sibling path does not, the sibling is the likely bug. (This dimension would have surfaced the one Important finding, which only one of three reviewers caught.)

**[repo] Repo context — Windows force-stop guard placement.** On Windows, every force-stop path that taskkills an on-disk `HostAgentPID` must screen it with `process.IsOurProcess` immediately before the kill, because Windows recycles PIDs and a stale PID may resolve to an unrelated process. A check made only at an earlier signal decision is insufficient when a graceful wait separates it from the kill — re-screen after the wait. When reviewing a new or changed force-stop path, confirm the guard sits at the point of the taskkill, not just upstream.

### Executive Summary

This PR hardens Windows shutdown paths by verifying process identity before sending signals or trusting on-disk PIDs, preventing `CTRL_BREAK` or `taskkill` from escaping to recycled, unrelated processes. The implementation of `process.IsOurProcess` provides a robust defense against Windows' aggressive PID recycling. However, the core mechanism is undermined by a Time-Of-Check to Time-Of-Use (TOCTOU) gap during a wait timeout, and an architectural flaw where manager context cancellation instantly hard-kills the hostagent, bypassing the graceful teardown the PR relies upon entirely.

I1. **Stale PID verification before wait exposes recycled PIDs** — `pkg/controllers/lima/limavm/controllers/limavm_lifecycle.go:616` (important, gap)

```go
	} else {
		forceInst.HostAgentPID = 0
	}

	stopInstanceForcibly(ctx, logger, &forceInst)
	return nil
}
```

`killOrphanedHostagent` calls `process.IsOurProcess` before signalling the hostagent, then waits for it to exit via `waitForInstanceStopped`. If the wait times out (e.g., due to delayed Lima state updates), the function falls through to `stopInstanceForcibly` using the original `forceInst.HostAgentPID`. During the 10+ second wait, the hostagent may have actually exited and its PID been recycled. Because `IsOurProcess` is not re-checked after the wait, `stopInstanceForcibly` will taskkill the recycled PID, defeating the PR's core defense.

Fix: Re-verify the PID after the wait, mirroring the exact pattern used in `shutdownHostagent`:

```diff
 	} else {
 		forceInst.HostAgentPID = 0
 	}
 
+	if forceInst.HostAgentPID > 0 && !process.IsOurProcess(forceInst.HostAgentPID, "hostagent", forceInst.Name) {
+		forceInst.HostAgentPID = 0
+	}
 	stopInstanceForcibly(ctx, logger, &forceInst)
 	return nil
 }
```

I2. **Substring match in `IsOurProcess` allows cross-instance PID collision** — `pkg/controllers/lima/limavm/controllers/limavm_lifecycle.go:593` (important, gap)

```go
	if inst.HostAgentPID > 0 && process.IsOurProcess(inst.HostAgentPID, "hostagent", inst.Name) {
```

`IsOurProcess` uses `strings.Contains` for command-line verification and explicitly warns in its documentation that a substring like `"vm"` will loosely match a process named `"vm2"`. However, the callers in `limavm_lifecycle.go` simply pass the raw `inst.Name` as the discriminator. If a user creates multiple instances with overlapping names (e.g., `test` and `test2`) and `test`'s PID is recycled to `test2`'s hostagent, the cleanup routine for `test` will falsely verify and force-kill `test2`.

Fix: Safest approach is to retrieve the exact arguments using `windows.CommandLineToArgv` in `IsOurProcess`. Alternatively, anchor the discriminator so it cannot match substrings of other names:

```diff
-	if inst.HostAgentPID > 0 && process.IsOurProcess(inst.HostAgentPID, "hostagent", inst.Name) {
+	// Ensure the instance name is distinct in the command line
+	if inst.HostAgentPID > 0 && process.IsOurProcess(inst.HostAgentPID, "hostagent", " " + inst.Name) {
```

#### Suggestions

S1. **Unnecessary loop when fetching long path names** — `pkg/util/process/process_windows.go:120-129` (suggestion, enhancement)

```go
	for bufSize := uint32(1024); bufSize <= 32768; bufSize *= 2 {
		buf := make([]uint16, bufSize)
		n, err := windows.GetLongPathName(p16, &buf[0], bufSize)
        // ...
		// n >= bufSize: the buffer was too small and n is the required size; grow.
	}
```

When the buffer is too small, `windows.GetLongPathName` explicitly returns the required buffer size in `n` (including the null terminator). The loop that doubles `bufSize` on each iteration performs multiple unnecessary syscalls for very long paths. It can be simplified to allocate the exact required size immediately.

Fix: Remove the loop and perform a direct reallocation if the first attempt is too small:

```go
	buf := make([]uint16, 1024)
	n, err := windows.GetLongPathName(p16, &buf[0], uint32(len(buf)))
	if err != nil {
		return "", err
	}
	if n >= uint32(len(buf)) {
		buf = make([]uint16, n)
		if n, err = windows.GetLongPathName(p16, &buf[0], uint32(len(buf))); err != nil || n >= uint32(len(buf)) {
			return "", windows.ERROR_INSUFFICIENT_BUFFER
		}
	}
	return windows.UTF16ToString(buf[:n]), nil
```

### Design Observations

**Concerns**
- `exec.CommandContext` cancellation defeats graceful shutdown on all platforms `(in-scope)`
  `startInstance` spawns the hostagent using `exec.CommandContext(ctx, ...)`. When the daemon begins graceful shutdown, `waitForShutdown` waits for this exact context to be cancelled. As soon as the context cancels, Go's `exec` package immediately sends `SIGKILL` (Unix) or `TerminateProcess` (Windows) to the hostagent. Consequently, the `r.shutdownAllHostagents()` loop attempts to send a graceful `process.Interrupt` to an already-dead process. The hostagent never runs its teardown sequence on any platform. Unix hides this because `store.Inspect` auto-removes stale PID files, but the root cause remains. Consider uncoupling the hostagent from the manager context, or using Go 1.20's `haCmd.Cancel` and `haCmd.WaitDelay` to orchestrate a graceful signal before the hard kill.

**Strengths**
- The addition of `process.IsOurProcess` is cleanly implemented. Comparing the normalized long paths protects against edge-case 8.3 short-path launches, and querying the remote PEB natively without relying on WMI or external tools avoids significant overhead.
