## Executive Summary

The PR replaces the Windows `addPath: manual` position rule with a marker file. `front` and `back` write `~/.rd<n>/.path-managed`, and `manual` removes the bin directory only while the marker exists. The Go change is sound, and its unit tests pass on macOS and Windows CI. The new BATS file is broken on Windows, though. Two of its three tests fail and the third passes without checking anything. `Verify generated files` is red, and the design doc still describes the old rule.

I4. **`set_user_path` splices the saved Path into PowerShell code, so the restore fails** — `rdd/bats/tests/32-app-controllers/path-marker.bats:21-25` [Codex GPT 6 Astra] [Gemini 3.5 Flash] [Claude Opus 5.5]

```bash
# set_user_path overwrites the user Path. The value is passed as an argument, not
# interpolated into the script, so backslashes and spaces survive.
set_user_path() { # <value>
    powershell.exe -NoProfile -NonInteractive -Command \
        "[Environment]::SetEnvironmentVariable('Path', \$args[0], 'User')" "$1"
```

Windows PowerShell joins every argument after a `-Command` string into the command text: "all arguments following it are interpreted as part of the command to execute" ([about_PowerShell_exe](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_powershell_exe?view=powershell-5.1)). `$args` stays empty, and a Path such as `C:\a;C:\b` becomes `..., 'User') C:\a;C:\b`, a parse error. So the restore at line 84 fails, and the comment states the opposite. CI cannot show it, because `bats-exec-file` calls `teardown_file` under `||`, which suspends errexit.

Repairing the call is not enough. `[Environment]::GetEnvironmentVariable` expands `%VAR%` references, and `SetEnvironmentVariable` writes REG_SZ ([dotnet-framework-early-access#58](https://github.com/microsoft/dotnet-framework-early-access/issues/58)). That is the damage that `writeUserPath` guards against at `pathmanagement_windows.go:138-145`.

Unproven: needs a Windows host; the evidence is Microsoft's CLI reference and the .NET issue.

Fix: drop `set_user_path`, `ORIGINAL_PATH` and the restore; `rdd svc delete` already removes the entry. If I5's fix needs a setter, `reg.exe add HKCU\Environment /v Path /t REG_EXPAND_SZ /d <value> /f` takes the value as data and keeps the type.

## Suggestions

S1. **A failed marker delete skips the `WM_SETTINGCHANGE` broadcast for good** — `rdd/pkg/controllers/app/pathmanagement/controllers/pathmanagement_windows.go:157` [Codex GPT 6 Astra] [Claude Opus 5.5]

```go
	if !adding && removeExisting {
		if err := r.removePathMarker(); err != nil {
			return changed, err
		}
	}
```

After a successful registry write, a failed marker delete returns `(true, err)`, and `applyPath` (lines 93-96) returns on `err` before it broadcasts. The retry finds Path already edited, gets `changed=false`, and never broadcasts either, so Explorer hands new processes the old Path until the user logs off. The trigger needs `os.Remove` of an empty file to fail right after the registry write, and under `manual` the bin directory still exists, so the stale entry does no harm.

Fix: in `applyPath`, broadcast whenever `changed` is true, then return the error.

S2. **The marker path has no single owner** — `rdd/pkg/controllers/app/pathmanagement/controllers/pathmanagement_windows.go:53` [Codex GPT 6 Astra] [Claude Opus 5.5] [Gemini 3.5 Flash]

```go
	return filepath.Join(filepath.Dir(r.BinDir), pathMarkerName)
```

Go derives the marker from `filepath.Dir(r.BinDir)`, and the BATS file rebuilds it as `${RDD_SHORT_DIR}/.path-managed` (`path-marker.bats:76`). When two components build a path, repo convention gives it one owner, an `instance` accessor plus an `rdd svc paths` key. Renaming the file today breaks the BATS assertions without a compile error. The comments also call `~/.rd<n>` the "instance directory", while `instance.Dir()` is the data directory under `AppData\Local`.

Fix: add `instance.PathMarker()` and a `path_marker` key, set a reconciler field from it so the unit tests can still use a temp directory, and say "short directory" in the comments.

S3. **The BATS helpers break the suite's conventions, and one turns a tool failure into a pass** — `rdd/bats/tests/32-app-controllers/path-marker.bats:36-45` [Claude Opus 5.5] [Codex GPT 6 Astra] [Gemini 3.1 Pro] [Gemini 3.5 Flash]


- `user_path` pipes `powershell.exe` into `tr`, and lines 57 and 63 capture with `$(...)`. The suite uses `run -0` and a here-string.
- `local want have` declares two names on one line.
- Line 116 calls `run -0` without reading `${output}`.

## Design Observations

### Concerns

- (future) The marker records that rdd owns some copy of the bin directory, not which copy. If a user hand-adds a second copy while the marker exists, the next `manual` pass removes both. The field doc says "from any position", so the behaviour is documented; recording the exact entry `front`/`back` wrote would close the gap if anyone hits it. [Claude Opus 5.5]

### Strengths

- (in-scope) The marker is written before the registry edit and cleared after it, so a crash at either point leaves state that the next pass repairs. [Claude Opus 5.5] [Codex GPT 6 Astra] [Gemini 3.5 Flash]
- (in-scope) `computeWindowsPath` loses its anchor-index logic, and the fixed-point assertion in the table test still guards idempotence. [Claude Opus 5.5] [Gemini 3.5 Flash]
- (in-scope) The marker is under `ShortDir`, which `rdd svc delete` removes after `Unwind`, and the existing cross-process lock covers the marker and the registry edit together. [Claude Opus 5.5] [Codex GPT 6 Astra]

I2. **`set_user_path` trailing arguments not bound to `$args` in PowerShell `-Command`** — `rdd/bats/tests/32-app-controllers/path-marker.bats:23-26` (important, regression)

```bash
set_user_path() { # <value>
    powershell.exe -NoProfile -NonInteractive -Command \
        "[Environment]::SetEnvironmentVariable('Path', \$args[0], 'User')" "$1"
}
```

When `powershell.exe` is invoked from bash with `-Command "<string>" "$1"`, PowerShell concatenates all arguments following `-Command` with spaces into a single command string to execute. It does not bind trailing arguments to `$args` unless the command string is an inline script block invoked with the `&` call operator.

Instead, PowerShell parses `<value>` as trailing tokens following the method invocation. When `<value>` contains semicolons (as `PATH` entries do), PowerShell attempts to interpret subsequent segments as separate commands, leaving `$args[0]` null and failing with syntax/command-not-found errors. In `local_teardown_file` at line 84, `set_user_path "${ORIGINAL_PATH}"` fails to restore the user's `PATH`.

Unproven: Host environment lacks `powershell.exe`; behavior is defined by Windows PowerShell CLI parameter binding specifications.

Fix: Wrap the command string in an inline script block invoked with `&`:

```diff
 set_user_path() { # <value>
     powershell.exe -NoProfile -NonInteractive -Command \
-        "[Environment]::SetEnvironmentVariable('Path', \$args[0], 'User')" "$1"
+        "& { [Environment]::SetEnvironmentVariable('Path', \$args[0], 'User') }" "$1"
 }
```
