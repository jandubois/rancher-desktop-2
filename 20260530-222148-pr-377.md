## Executive Summary

The PR adds `process.IsOurProcess` — a Windows PEB-walk identity check, a no-op on Unix — and guards the graceful hostagent-shutdown paths against PID reuse before sending `CTRL_BREAK`. The fix is correct, well-documented, and resolves the CI failure it targets. The headline gap: the forced-stop fallback and the service's `StopWithWait` still signal unverified on-disk PIDs, so a recycled PID can still be killed — the class this PR set out to close.

All three reviewers agreed the implementation is sound and raised no surviving critical issues. The two Important findings are pre-existing gaps in the same hazard class, not regressions in this commit. Gemini's two criticals did not survive verification: one is the force-kill gap (real, but a gap and important, not a critical regression), and the other alleges a `procExited`/handle-release race whose stated mechanism the code rules out.

## Important Issues

I1. **Force-stop fallback still kills an unverified on-disk PID** — `pkg/controllers/lima/limavm/controllers/limavm_lifecycle.go:607-621` [Codex GPT 5.5, Gemini 3.1 Pro] (important, gap)

```go
if inst.HostAgentPID > 0 && process.IsOurProcess(inst.HostAgentPID, "hostagent", inst.Name) {
    // graceful interrupt + wait
}
stopInstanceForcibly(ctx, logger, inst)   // line 621
```

When `IsOurProcess` rejects a recycled `HostAgentPID` (line 607), the code skips the graceful signal but still calls `stopInstanceForcibly` with the unchanged PID (line 621). That helper runs `process.KillTree` on `inst.HostAgentPID` (line 659) — `taskkill /F /T /PID` on Windows (`process_windows.go:188`) — terminating whatever process now holds the recycled PID. `inst.DriverPID` shares this exposure and cannot use `IsOurProcess` (the driver is qemu/wsl, not rdd). The merge-base already fell through to `stopInstanceForcibly`, so this is pre-existing, not a regression. But the new comment calls the fallback "reuse-safe" (line 606); that holds only against console escape, not against killing the recycled process.

Fix: zero the rejected PID before the fallback (copy `inst` to avoid mutating the caller's value); guard `DriverPID` separately.

```diff
+	forceInst := *inst
 	if inst.HostAgentPID > 0 && process.IsOurProcess(inst.HostAgentPID, "hostagent", inst.Name) {
 		// graceful interrupt + wait (unchanged)
+	} else {
+		forceInst.HostAgentPID = 0 // rejected/absent: do not force-kill a recycled PID
 	}
-	stopInstanceForcibly(ctx, logger, inst)
+	stopInstanceForcibly(ctx, logger, &forceInst)
```

I2. **`StopWithWait` signals the service's unverified on-disk PID** — `pkg/service/cmd/service.go:407` [Claude Opus 4.8] (important, gap)

```go
pid := PID()                                    // on-disk PID file; existence-checked only
if err := process.Interrupt(pid); err != nil {  // CTRL_BREAK on Windows
    if err := process.Kill(pid); err != nil {
```

`PID()` reads the service PID from disk and, on Windows, confirms only that some process with that PID exists (`os.FindProcess`, line 148) — not that it is rdd. A stale PID file from a crashed service can be recycled, so `Running()` returns true and `StopWithWait` sends `CTRL_BREAK` (line 407), then `Kill` (line 408), to an unrelated process — the exact failure this PR fixes for hostagents. The service is spawned as `service serve` (line 274), so the new helper applies directly. Pre-existing and outside the diff, but in the class the PR targets, with the fix tool now in hand.

Fix: verify identity inside `PID()` so a recycled PID reads as not-running (cleaning the stale file at line 159), closing the class for both `Running()` and `StopWithWait` at once.

```diff
 		if runtime.GOOS != "windows" {
 			err = process.Signal(syscall.Signal(0))
+		} else if !process.IsOurProcess(pid, "service", "serve") {
+			err = fmt.Errorf("pid %d is not our service", pid)
 		}
```

## Suggestions

S1. **Commit/PR description overstates the guard mechanism** — `pkg/controllers/lima/limavm/controllers/hostagent_watcher.go:215`, `limavm_controller.go:520` [Claude Opus 4.8] (suggestion, doc)

The PR text says all three graceful paths are "guarded with `IsOurProcess`." In the code, only `killOrphanedHostagent` (line 607) calls `IsOurProcess`; `signalHostagent` and `shutdownAllHostagents` use a `procExited`-channel guard, because those paths hold the live `os.Process` handle (per the author's reply to @mook-as). The split is correct and intentional, but a future bisect that greps for three `IsOurProcess` call sites will not find them. Reword the commit body to describe the two-mechanism split — held-handle guard for the in-memory paths, identity check for the on-disk path.

S2. **`procExited` guard comment overstates the invariant** — `pkg/controllers/lima/limavm/controllers/hostagent_watcher.go:212-219` [Claude Opus 4.8] (suggestion)

```go
// While it is open the handle is held.
select {
case <-state.procExited:
    return false
default:
}
```

The comment claims the OS handle is held while `procExited` is open. The watcher closes `procExited` only after `cmd.Wait()` returns (`hostagent_watcher.go:85`), and `Wait()` releases the handle before it returns. Between release and close, `procExited` reads open while the PID is already reusable. The window spans a few instructions and needs a concurrent signaller plus an immediate PID reassignment, so practical risk sits far below the on-disk scenario — and the pre-PR code signalled unconditionally, so this remains a net improvement. Soften the comment to "the handle is normally still held." Same pattern at `limavm_controller.go:520-524`.

S3. **Identity check's rejection branch is untested** — `pkg/util/process/process_windows_test.go:40` [Claude Opus 4.8, Codex GPT 5.5] (suggestion, gap)

`TestIsOurProcess` covers the own-process match, the argv0 substring match, an absent substring, and a dead PID (`process_windows.go:61`, the `OpenProcess`-fails path). It never exercises the actual PID-reuse defense at `process_windows.go:67` — a live process running a different executable. Add a case that spawns a known system binary (e.g. `cmd.exe /c pause`), asserts `IsOurProcess(child.Pid, ...)` is false, then kills it. This is the branch the whole change exists to protect.

S4. **Hardening for the PEB command-line read** — `pkg/util/process/process_windows.go:90-93`, `111-113` [Claude Opus 4.8, Gemini 3.1 Pro] (suggestion, robustness)

Two robustness nits in the unsafe reads; both fail safe (a read error makes `IsOurProcess` return false and the caller forces stop). First, `buf := make([]uint16, length/2)` then reads `uintptr(length)` bytes (lines 90-93): an odd `length` would overrun the slice by one byte. `Length` is always even for a well-formed UTF-16 `NTUnicodeString`, so this cannot fire normally; reading `uintptr(len(buf)*2)` stays self-consistent. Second, `readProcessMemory(..., unsafe.Sizeof(params))` (line 111) requires the whole `RTL_USER_PROCESS_PARAMETERS` struct to be mapped, though only fields up to `CommandLine` are needed; reading just through that field reduces cross-page short-read fragility on older OS layouts.

S5. **`IsOurProcess` matches `inst.Name` as a substring** — `pkg/controllers/lima/limavm/controllers/limavm_lifecycle.go:607` [Consolidation] (suggestion)

`IsOurProcess(inst.HostAgentPID, "hostagent", inst.Name)` accepts the PID when the command line *contains* `inst.Name` (`process_windows.go:79`, `strings.Contains`). A live hostagent for instance `foobar` contains the substring `foo`, so an orphan check for instance `foo` would match it; a short or numeric name (e.g. `0`) matches almost any command line. Low probability in the single-user embedded context, but the discriminator is weak. Consider matching the instance name as a whole argument rather than a substring.

## Design Observations

### Concerns

- **One hazard, two guard mechanisms (in-scope)** [Claude Opus 4.8, Codex GPT 5.5] — the PR guards in-memory `*exec.Cmd` paths with the held-handle/`procExited` check and the on-disk path with `IsOurProcess`. The split is correct: `GenerateConsoleCtrlEvent` takes a PID, not a handle, so there is no handle-based `CTRL_BREAK`, and the in-memory paths genuinely hold the handle. The cost is that a reader must track two defenses for one risk, and one on-disk caller (`StopWithWait`, I2) was missed. A single helper that prefers the handle and falls back to identity would unify the model, but adds abstraction for two sites — not worth it now.
- **Forced stop trusts persisted PIDs (future)** [Gemini 3.1 Pro] — the structural root of I1: `stopInstanceForcibly` runs `KillTree` on `DriverPID` and `HostAgentPID` straight from on-disk state, across daemon restarts. A supervisor / Job-Object / pidfd ownership model would eliminate signalling unrelated PIDs entirely. Out of scope for this fix.

### Strengths

- Fail-closed contract: `IsOurProcess` returns `false` (never an error) on every uncertain path, and every caller treats `false` as "fall back to forced stop." [Codex GPT 5.5]
- The PEB walk is a clean, dependency-free way to read another process's command line on Windows. [Gemini 3.1 Pro]
- The Unix/Windows split with a documented no-op stub and a matching signature keeps the call sites platform-agnostic. [Claude Opus 4.8]

## Review Process Notes

### Skill improvements

- When a finding's severity depends on standard-library or language-runtime internals — goroutine scheduling and lifecycle ordering, signal-delivery semantics, OS handle-release timing, finalizer or GC timing — verify the claim against the runtime's documented contract or source before classifying, and record the runtime version. Downgrade any high-severity finding that rests on assumed runtime behavior without such a citation. Runtime internals routinely diverge from intuition: whether a subprocess's stdio is a file or a pipe, for example, decides whether a wait call blocks. If the worktree sandbox blocks the stdlib source needed to confirm, state the assumption explicitly and cap the severity rather than asserting the mechanism.

### Repo context updates

- [repo] The lima controller launches the hostagent as a child `rdd` process and sets its stdout/stderr to `*os.File` log handles from `logfile.Create` (not pipes). Go's `exec` passes those descriptors to the child directly and spawns no I/O-copy goroutine, so `cmd.Wait()` returns promptly once the process is reaped, and the watcher closes `procExited` immediately after. When evaluating claims that `cmd.Wait()` blocks on inherited pipes, or that `procExited` lags handle release by an exploitable margin on these paths, account for the no-pipe stdio: the residual window is a few instructions, not unbounded.
- [repo] On Windows, `process.IsOurProcess` guards only the graceful `CTRL_BREAK` (`process.Interrupt`) shutdown paths. The forced-stop path (`stopInstanceForcibly` → `process.KillTree` → `taskkill /F /T`) still runs on `inst.DriverPID` and `inst.HostAgentPID` read from on-disk Lima state, as does the service's own `StopWithWait`/`PID()` chain in `pkg/service/cmd/service.go`. These PIDs can be recycled across daemon restarts. When reviewing process-shutdown changes, check whether every force-kill or signal target carries an identity guard, not just the graceful path.

### [Codex] — Pass 1

### Executive Summary

The PR adds a Windows-only identity check before graceful `CTRL_BREAK` delivery and narrows active watcher shutdown to unreaped processes. One important issue remains: when the new orphan check rejects a stale hostagent PID, the same stale PID is still passed to the force path, which can terminate an unrelated process via `taskkill`.

### Findings

#### Critical Issues

None.

#### Important Issues

I1. **Rejected hostagent PIDs still flow into force kill** — `pkg/controllers/lima/limavm/controllers/limavm_lifecycle.go:607-621` (important, regression)

```go
if inst.HostAgentPID > 0 && process.IsOurProcess(inst.HostAgentPID, "hostagent", inst.Name) {
	if err := process.Interrupt(inst.HostAgentPID); err != nil {
		logger.V(1).Info("Could not signal orphaned hostagent", "pid", inst.HostAgentPID, "error", err)
	} else {
		// ...
	}
}

stopInstanceForcibly(ctx, logger, inst)
```

When `IsOurProcess` returns false at line 607, that is exactly the “PID is stale, inaccessible, or not ours” case. The code then falls through to line 621 with the original `inst`; `stopInstanceForcibly` still iterates `inst.HostAgentPID` at line 659, and Windows `KillTree` runs `taskkill /PID` at `pkg/util/process/process_windows.go:188`. That avoids `CTRL_BREAK` escaping, but it can still terminate the unrelated process that reused the stale hostagent PID.

Fix: do not pass an unverified hostagent PID to the force path.

```diff
-	if inst.HostAgentPID > 0 && process.IsOurProcess(inst.HostAgentPID, "hostagent", inst.Name) {
+	forceInst := *inst
+	if inst.HostAgentPID > 0 {
+		if !process.IsOurProcess(inst.HostAgentPID, "hostagent", inst.Name) {
+			forceInst.HostAgentPID = 0
+		} else {
 		if err := process.Interrupt(inst.HostAgentPID); err != nil {
 			logger.V(1).Info("Could not signal orphaned hostagent", "pid", inst.HostAgentPID, "error", err)
 		} else {
 			// ...
 		}
+		}
 	}
 
-	stopInstanceForcibly(ctx, logger, inst)
+	stopInstanceForcibly(ctx, logger, &forceInst)
```

### Design Observations

**Strengths**

The Windows helper uses a fail-closed contract: inaccessible or unverifiable process identity returns false, so callers can avoid `GenerateConsoleCtrlEvent` unless they positively identify the target.

Separating the active `os.Process` handle paths from the stale PID-file path keeps the common watcher shutdown path simple and aligns with the PR review discussion about handles preventing PID reuse while held.

### Testing Assessment

1. The highest-risk missing scenario is I1: a Windows stale `ha.pid` whose PID has been reused by a non-hostagent process. A regression test should verify that neither `CTRL_BREAK` nor `taskkill /PID <stale-hostagent-pid>` is issued for that PID.

2. The Windows tests cover the current process and a nonexistent PID, but not a same-executable process with a mismatching command line. That case is the real false-positive boundary for `IsOurProcess`.

Executed checks: `go test ./pkg/util/process`, `go test ./pkg/controllers/lima/limavm/controllers`, and Windows cross-compiles for both packages with `GOOS=windows GOARCH=amd64 go test -c`.

### [Gemini] — Pass 1

### Executive Summary

The PR introduces identity verification for recycled PIDs during graceful shutdown to prevent `CTRL_BREAK` from crashing the RDD service. However, it explicitly routes known-recycled PIDs into a forced shutdown path that executes `taskkill` unconditionally, silently assassinating arbitrary user processes. Additionally, the graceful paths suffer from a subtle race condition where Go's `Cmd.Wait()` closes the process handle before closing the `procExited` channel, reopening the exact PID-reuse window the PR aimed to fix.

### Findings

#### Critical Issues

**C1. Graceful paths race against Go's handle release** — `pkg/controllers/lima/limavm/controllers/limavm_controller.go:520-524` (critical, regression)

```go
		select {
		case <-state.procExited:
			continue
		default:
		}
```

The author intentionally omitted `IsOurProcess` here, reasoning that an open `procExited` implies the OS handle is still held and prevents PID reuse. This contradicts Go's `os/exec` model: `Cmd.Wait()` calls `Process.Wait()` (which closes the Windows handle, freeing the PID) *and then* blocks waiting for stdout/stderr copying goroutines to finish. If the hostagent spawns a child that keeps the pipes open, `Cmd.Wait()` blocks indefinitely. The handle is closed, the PID is recycled, but `procExited` remains open. The `select` takes the `default` branch and sends `CTRL_BREAK` to an unrelated process, crashing the RDD console.

Fix: Unconditionally guard the signal with `IsOurProcess`.

```diff
-		select {
-		case <-state.procExited:
-			continue
-		default:
-		}
+		if !process.IsOurProcess(state.cmd.Process.Pid, "hostagent", name) {
+			continue
+		}
 		_ = process.Interrupt(state.cmd.Process.Pid)
```

**C2. Known-recycled PIDs are forcefully murdered** — `pkg/controllers/lima/limavm/controllers/limavm_lifecycle.go:607-622` (critical, regression)

```go
	if inst.HostAgentPID > 0 && process.IsOurProcess(inst.HostAgentPID, "hostagent", inst.Name) {
        // ... graceful shutdown ...
	}

	stopInstanceForcibly(ctx, logger, inst)
```

When `IsOurProcess` detects that the on-disk `HostAgentPID` has been recycled to an unrelated user process, it safely skips graceful shutdown. However, it immediately falls through to `stopInstanceForcibly`, which unconditionally executes `process.KillTree` (`taskkill /F /T`) on the exact same recycled `HostAgentPID`. The PR explicitly routes known-unrelated PIDs into a destructive path, aggressively terminating innocent user applications (e.g., an IDE or background service) and their children. `taskkill` is only "reuse-safe" in that it spares the RDD console; it is fatal to the unrelated process.

Fix: Clear the recycled PID before falling through.

```diff
 	if inst.HostAgentPID > 0 && process.IsOurProcess(inst.HostAgentPID, "hostagent", inst.Name) {
 		if err := process.Interrupt(inst.HostAgentPID); err != nil {
 			logger.V(1).Info("Could not signal orphaned hostagent", "pid", inst.HostAgentPID, "error", err)
 		} else {
            // ... wait logic ...
 			logger.Info("Orphaned hostagent did not exit gracefully, forcing stop")
 		}
+	} else {
+		inst.HostAgentPID = 0
 	}
 
 	stopInstanceForcibly(ctx, logger, inst)
```

#### Important Issues

**I1. Buffer overflow in PEB command line read** — `pkg/util/process/process_windows.go:90-93` (important, gap)

```go
	buf := make([]uint16, length/2)
	if err := readProcessMemory(handle, uintptr(unsafe.Pointer(params.CommandLine.Buffer)),
		unsafe.Pointer(&buf[0]), uintptr(length)); err != nil {
```

`params.CommandLine.Length` counts bytes. If `length` is odd (due to memory corruption or an unexpected PEB state in the target process), `length/2` truncates the allocation size. The subsequent `readProcessMemory` call reads `uintptr(length)` bytes into `unsafe.Pointer(&buf[0])`. This reads one byte past the end of the allocated slice, corrupting the heap of the RDD process.

Fix: Read exactly the number of bytes allocated in the buffer.

```diff
 	// NTUnicodeString.Length counts bytes; the buffer holds UTF-16 code units.
 	buf := make([]uint16, length/2)
 	if err := readProcessMemory(handle, uintptr(unsafe.Pointer(params.CommandLine.Buffer)),
-		unsafe.Pointer(&buf[0]), uintptr(length)); err != nil {
+		unsafe.Pointer(&buf[0]), uintptr(len(buf)*2)); err != nil {
 		return "", err
 	}
```

**I2. DriverPID remains completely unprotected** — `pkg/controllers/lima/limavm/controllers/limavm_lifecycle.go:659` (important, gap)

```go
	for _, pid := range []int{inst.DriverPID, inst.HostAgentPID} {
```

While the PR protects `HostAgentPID` during graceful shutdown, `inst.DriverPID` remains completely unprotected. `stopInstanceForcibly` unconditionally runs `process.KillTree` on `inst.DriverPID`. Because this PID also comes from persistent on-disk state, it is equally susceptible to recycling. Since `IsOurProcess` strictly checks against `os.Executable()`, it cannot be used to verify the external driver (e.g., `qemu` or `wsl`).

Fix: Add a generic verification utility (e.g., `process.IsRunning(pid, "qemu")`) that queries the process image path, and use it to guard `inst.DriverPID` before calling `KillTree`.

**I3. Unix implementation ignores persistent state recycling** — `pkg/util/process/process_unix.go:37-39` (important, gap)

```go
func IsOurProcess(_ int, _ ...string) bool {
	return true
}
```

The Unix implementation unconditionally returns `true`, claiming that "PIDs are not recycled within a daemon's lifetime" and "SIGINT to a stale PID is a harmless no-op". However, `inst.HostAgentPID` is read from on-disk state persisted by a *previous* execution of the daemon. If the previous daemon crashed days ago, the PID can easily have wrapped around and been recycled by a new user process. Sending `SIGINT` to a recycled process is not a no-op; it terminates the innocent process.

Fix: Implement a proper identity check on Unix (e.g., reading `/proc/<pid>/cmdline` on Linux or using `proc_pidinfo` on macOS).

#### Suggestions

None.

### Design Observations

**Concerns**
- **Lifecycle tracking via files (in-scope):** Storing PIDs in persistent disk state and blindly trusting them across daemon restarts invites severe PID-recycling vulnerabilities across all platforms. Transitioning to an architecture where long-lived processes are managed via proper process supervisors or pidfd (where supported) would structurally eliminate the risk of signalling unrelated processes.

**Strengths**
- The PEB walk in `process_windows.go` is an elegant, dependency-free approach to reading an external process's command line on Windows.

### Testing Assessment

1. The race condition window where the OS handle is closed but `procExited` remains open is entirely untested. A test simulating an inherited pipe holding `Wait()` open is needed.
2. The fallback path to `stopInstanceForcibly` for a recycled `HostAgentPID` lacks test coverage to verify that unrelated mock processes are not violently terminated.

### Documentation Assessment

The doc comment on `process_unix.go:32` inaccurately models process lifetimes across daemon restarts, minimizing the risk of sending signals to recycled PIDs. It should be revised once the Unix `IsOurProcess` implementation is fortified.

### Acknowledged Limitations

- **PR comment**: @jandubois noted that the `IsOurProcess` check was intentionally reverted from `shutdownAllHostagents` and `signalHostagent` because the OS process handle was believed to remain open and prevent PID reuse. However, as detailed in C1, this rationale breaks down under Go's `os/exec` model, which closes the Windows handle before waiting for I/O copying to finish. Therefore, this issue has been promoted to a Critical finding (C1).
