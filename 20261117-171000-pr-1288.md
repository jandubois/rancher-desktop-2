## Executive Summary

The PR lets a developer-mode rdd running from a checkout publish the checkout's `resources/<goos>` tools and Docker CLI plugins, the way a packaged app does. The approach is sound, and the bats file passes on a live instance with and without an assembled checkout. Two things need fixing first. On Windows, a checkout without `rdd-forwarder.exe` now fails to publish anything, even rdd's own links. And a fixture comment claims developer-mode detection that the mock never triggers.

`resolveSrcDirs` picks the checkout path once both resource directories exist. On Windows, `LinkBundledBinaries` then calls `linkForwarders`, which returns a `locate forwarder` error before it writes anything.

See `rdd/pkg/binlinks/forwarders.go:60-63`. At the merge-base the same rdd took `ensureSelfLinks` and linked `rdd.exe`, `kubectl.exe` and `nerdctl.exe`.

`yarn`'s postinstall builds `rdd-forwarder.exe` (`scripts/dependencies/rdd.ts:14-16`). But `make clean` removes `rdd/bin` (`rdd/Makefile:426-427`), and the default goal and every bats target rebuild only `rdd.exe`. A fresh instance then ends up without a bin directory, and only the daemon log says why. CI is unaffected, because its checkouts lack `resources/windows`.

S1. **The checkout publish mirrors downloader leftovers that packaging excludes** — `rdd/pkg/binlinks/binlinks.go:214-218` [Codex GPT 6 Astra, Gemini 3.1 Pro]

Postinstall keeps `helm.tar.gz` beside `helm` on every platform (`scripts/lib/download.ts:265,277`), and a `<tool>.unsigned` copy beside each codesigned macOS tool (`download.ts:130,189-192`). `packaging/electron-builder.yml:14-18` keeps both out of the bundle, but the checkout path links whatever `srcDir` holds. A live developer-mode start from a `yarn`-assembled checkout published `docker.unsigned`, `docker-credential-osxkeychain.unsigned` and `helm.tar.gz` into the bin directory.

On Windows, `linkForwarders` (`forwarders.go:78-82`) turns `helm.tar.gz` into a forwarder copy. `removeStaleForwarders` maps its shim to `helm.tar.gz.exe` and deletes the shim on every start, so later cleanups cannot find the copy to remove it. The plugin directory stays clean, because buildx and compose download as bare binaries. Everything that worked before still works; developer-mode bin directories just collect clutter.

Fix: skip the names that packaging excludes when reading `srcDir`, in both `linkBinaries` and `linkForwarders`. On Windows, publishing only `.exe` entries also works, since only an executable can run through a forwarder.

## Design Observations

### Concerns

- **(in-scope)** The PR does not make the bats test that motivated #1285 find buildx. [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]
  - CI's bats workflow never runs `yarn`, and the repository does not track any file under `resources/<goos>/`, so in CI `resolveSrcDirs` returns `selfOnly` and behaviour stays as before.
  - Locally the publish happens, but `rdd/bats/tests/40-docker/build.bats` runs the docker on `PATH` (`rdd/bats/helpers/commands.bash:16-18`). That docker finds plugins only through `cliPluginsExtraDirs`, and `applyDockerPlugins` registers the instance's plugin directory only under `addPath` `front` or `back`. The default is `manual`, and the bats helpers leave it there.
  - So `build.bats` still skips unless the developer's own docker config supplies buildx. I reasoned this from the code and did not boot a VM to run `build.bats`.
  - The PR does deliver the issue's literal request, a developer-mode path that publishes the checkout's binaries. Its body could say what is left before `Fixes #1285` closes the motivating case.
- **(future)** `checkoutRoot` finds the repository three levels above the executable, independently of the marker that `developer.Mode` checks. [Claude Opus 5.5] With `RDD_DEVELOPER_MODE=1` forced on an rdd built elsewhere (`dlv --output /tmp/rdd`), only the `os.Stat` checks keep it from misfiring. Anchoring both on `rdd/cmd/rdd/main.go` would keep detection and layout in one definition.

### Strengths

- `resolveSrcDirs` checks `inAppBundle` before developer mode, so packaged builds take the old path, and the case "app bundle wins even in developer mode" pins that order. Passing `developerMode` in keeps the tests free of the memoized `developer.Mode()`. [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]
- `pathOptions` separates the source directories from `execPath`, so the link and forwarder code no longer assume rdd is in `srcDir`, and one loop gives both layouts their `rdd` link. [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]
- The `export RDD_DEVELOPER_MODE=0` in `local_setup` is needed. Without it, tests 3, 5 and 6 fail in a `yarn`-assembled checkout (the mutant run under Testing Assessment).

## Acknowledged Limitations

PR #1023's reviews settled these on the same code, and this PR leaves them as they were:

- `pluginTargets` treats every read error of the plugin directory as "no plugins". The checkout path stats that directory first, so this PR does not make it worse.
- The suite still passes when the production plugin-directory wiring is deleted.
- `7-binlinks.bats` builds the plugin destination path by hand and duplicates `assert_published`.
- A standalone start on macOS and Linux leaves dangling plugin symlinks, and docker skips a missing candidate. Do not re-suggest a symlink prune in `ensureSelfLinks`.

These predate the PR and are tracked for a separate fix. The `func link` comment still calls the cross-volume copy fallback deferred, `dropForwarder` logs the remove error instead of the rename error, and lines 15-18 of the `7-binlinks.bats` header say a stand-in forwarder is enough, while setup copies the real one. The PR rewrote the paragraph above those lines and left them.

Requiring both checkout directories before publishing is intentional. `TestResolveSrcDirs` pins it, and postinstall always creates both. Do not re-suggest publishing tools when only one exists.

### [Gemini 3.1 Pro]

###### Executive Summary

This change enables publishing Docker CLI plugins and third-party tools when running out of a developer checkout tree, matching the behavior of packaged app bundles. It introduces `pathOptions` and `resolveSrcDirs` to map the checkout's assembled resources to the `binlinks` package's source directories. While the design is elegant and unified, it inadvertently publishes non-executable development archives into the user's PATH and introduces an edge case where a missing forwarder binary completely breaks multicall linking on Windows.

###### Critical Issues

###### Important Issues

I1. **`linkBinaries` and `linkForwarders` publish development archives and unsigned binaries** — `rdd/pkg/binlinks/binlinks.go:214-220` (important, regression)

```go
	for _, entry := range entries {
		if entry.IsDir() {
			continue
		}
		name := entry.Name()
```

In a development checkout, `yarn postinstall` leaves verified archives (`.zip`, `.tar.gz`, `.tgz`) and unsigned originals (`.unsigned`) alongside the extracted binaries in `resources/<goos>/bin` and `resources/<goos>/docker-cli-plugins`. Because `linkBinaries`, `linkForwarders`, and `pluginTargets` iterate these checkout directories without filtering out non-executable extensions, they mirror all non-directory files into `~/.rd<instance>/bin` and `~/.rd<instance>/docker-cli-plugins`. This clutters the user's bin directory with archives and creates forwarders like `docker-buildx.zip.shim` which could inadvertently trigger archive handlers when executed.

Fix: Filter out known archive and `.unsigned` extensions when reading source directories. Extract a helper like `isArchiveOrUnsigned(name string)` checking for `.unsigned`, `.tar.gz`, `.tgz`, `.xz`, and `.zip` extensions, and add `|| isArchiveOrUnsigned(entry.Name())` to the `continue` conditions in `linkBinaries` (line 215), `linkForwarders` (line 79), and `pluginTargets` (line 156).

I2. **Missing forwarder aborts all binary linking in developer mode** — `rdd/pkg/binlinks/forwarders.go:60-64` (important, regression)

```go

	forwarderSrc := filepath.Join(filepath.Dir(paths.execPath), forwarderName)
	if _, err := os.Stat(forwarderSrc); err != nil {
		return fmt.Errorf("locate forwarder %q: %w", forwarderSrc, err)

```

When running from a checkout on Windows, if `rdd-forwarder.exe` is absent (e.g. after running `make clean` and `make build` without `make build-forwarder`), `linkForwarders` returns an error at `os.Stat(forwarderSrc)`. This aborts the entire `LinkBundledBinaries` process. Before this change, the standalone path `ensureSelfLinks` would still execute and publish hardlinks for `rdd`, `kubectl`, and `nerdctl`. Alternatively, require `rdd-forwarder.exe` to exist in `resolveSrcDirs` before setting `selfOnly = false` on Windows.

###### Concerns

- **Issue #1285 remains unresolved in CI BATS runs** `(future)`:
  Issue #1285 notes that `docker buildx` is missing during BATS tests on Windows. While PR #1288 adds the daemon mechanism to link checkout plugins when present, `.github/workflows/rdd-bats.yaml` only runs `make build-rdd` and `make build-forwarder`; it never runs `yarn postinstall`. Because `resources/windows/docker-cli-plugins` is gitignored and never populated in CI, `resolveSrcDirs` falls back to `selfOnly = true` on CI runners, and `tests/40-docker/build.bats` will continue to skip on Windows in CI. To solve the issue in CI, `rdd-bats.yaml` needs a step to stage or download Windows plugins.

- **All-or-nothing requirement for checkout binaries and plugins** `(in-scope)`:
  In `resolveSrcDirs` (`binlinks.go:107-111`), `selfOnly` remains `true` unless *both* `resources/<goos>/bin` and `resources/<goos>/docker-cli-plugins` exist. If a developer only staged tools in `bin` (or plugin downloads were skipped), `rdd` refuses to publish even `docker` and `helm`. Since `linkBinaries` and `linkForwarders` already handle a missing `pluginsSrcDir` by returning `nil` plugins, requiring both directories to exist unnecessarily suppresses binary publishing.

###### Strengths

- Consolidating link paths into the `pathOptions` struct eliminates repetitive argument threading between `LinkBundledBinaries`, `linkBinaries`, `linkForwarders`, and `ensureSelfLinks`.
- Prioritizing `inAppBundle` over `developerMode` ensures packaged application builds incur zero extra filesystem checks or divergence even if developer mode flags are present.
