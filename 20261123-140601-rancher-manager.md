## Executive Summary

The branch adds a macOS Cluster API infrastructure provider to rdd. For each LimaMachine that Rancher's Cluster API creates in the App's k3s cluster, rdd boots a node VM from the App's own distro image. The design holds up, and it keeps the registration token out of conditions and errors. One Important defect remains. When rdd's webhooks reject one LimaMachine's LimaVM, every pass aborts there, and the LimaMachines listed after it never get node VMs.

## Important Issues

I1. **A LimaVM that rdd rejects stalls every LimaMachine listed after it** — `rdd/pkg/controllers/app/capi/limamachine.go:100-103` [Codex GPT 6 Astra, Claude Opus 5.5]

```go
		reason, message, err := r.provisionLimaMachine(ctx, app, kubeSystem.UID, machine)
		if err != nil {
			return false, err
		}
```

The loop returns on the first LimaMachine whose provisioning fails. A LimaVM create that rdd's admission webhooks reject fails the same way on every pass, so the LimaMachines listed after it never get a node VM, status or deletion, and the rejected one never gets a Ready reason.

Two inputs trigger it. The CRD accepts a negative `memory` or `disk`, which Lima's template validation rejects. And the webhook rejects a name that any namespace uses (`rdd/pkg/controllers/lima/limavm/validation.go:23-45`), but `getOwned` looks for a same-named LimaVM only in `rancher-desktop`, so `NameConflict` misses one in `default`.

The rejected attempt also leaves its `-source` ConfigMap, which later passes reuse, so a corrected spec never takes effect.

## Suggestions

S1. **Node VMs of a replaced guest cluster outlive it while Cluster API is absent** — `rdd/pkg/controllers/app/capi/reconciler.go:160-164` [Codex GPT 6 Astra]

```go
	if _, err := r.crdClient.Get(ctx, machineCRDName, metav1.GetOptions{}); err != nil {
		if apierrors.IsNotFound(err) {
			// A k3s without Cluster API stays untouched.
			log.V(1).Info("Cluster API is not installed in the guest cluster")
			return ctrl.Result{RequeueAfter: requeueIdle}, nil
```

Only `collectGarbage` removes node VMs that belong to another guest cluster, and it runs after this check. So when the guest cluster's `kube-system` UID changes and the new cluster lacks Cluster API, `syncNodeVMsRunning` keeps starting the old node VMs with the App, and the LimaVM webhook rejects deleting them by hand. The design doc promises that cleanup (`rdd/docs/design/capi-provider.md:170`).

The path is latent today. The App controller never recreates the App VM, and the Troubleshooting page's Reset Kubernetes and Factory Reset buttons send `k8s-reset` and `factory-reset`, but the main process doesn't handle either message. Deleting the App removes node VMs through `DeleteOwnedResources`. Once Reset Kubernetes reaches rdd, this becomes Important.

Fix: read the `kube-system` UID before the Cluster API check and remove node objects labelled with another guest UID there. Keep the cleanup of missing LimaMachines behind a successful LimaMachine list.

**Outcome:** fixed in `850f9b85e` as the Fix proposes. Step c of `TestReconcile` covers a changed UID with Cluster API absent.

S2. **A dotted LimaMachine name gets a provider ID that never matches its Node** — `rdd/pkg/controllers/app/capi/template.go:118` [Claude Opus 5.5]

```go
	if hostname := "lima-" + name; len(hostname) > 63 {
```

`ValidateMachineName` accepts `.` and `_`, because Lima's instance names allow them. But Lima builds the guest's hostname with `hostname.FromInstName`, which turns both into `-`, and `rd-init` sets the hostname from that value (`rdd/src/rd-init/metadata.go:37`). For a LimaMachine `pool.a-1`, rdd writes `k3s://lima-pool.a-1` (`limamachine.go:240-241`) while k3s registers the Node `lima-pool-a-1`. Cluster API then never matches the Node, and the Machine stalls without an error. Whether Rancher lets a dot into a machine name is unverified.

Fix: reject `.` and `_` with `InvalidName`. Building the provider ID with `FromInstName` instead would let `a.b` and `a-b` share a Node name.

**Outcome:** fixed in `0dcdbd42f` as the Fix proposes, and `TestValidateMachineName` has a row with a dot.

S3. **A first boot longer than Lima's wait stays `BootstrapFailed` until the VM restarts** — `rdd/pkg/controllers/app/capi/limamachine.go:216-217` [Claude Opus 5.5]

```go
	probe, ok := r.probes[machine.UID]
	if !ok || probe.restartCount != vm.Status.RestartCount {
```

The design doc says Lima reports a VM running only after its boot scripts finish (`capi-provider.md:140`). That holds within Lima's wait of 200 polls 3 seconds apart (`pkg/hostagent/requirements.go:44-45` in the Lima fork). After that, the hostagent reports Running with `Degraded` set (`pkg/hostagent/hostagent.go:550`), and rdd's watcher ignores `Degraded` (`hostagent_watcher.go:101-104`). If the first boot takes longer, for example on a slow zypper install of openssl, the probe runs before the marker exists. Its result is cached for the whole boot, so the LimaMachine stays `BootstrapFailed` after the script succeeds.

Fix: don't cache a probe that lacks the marker, and qualify the doc's sentence.

**Outcome:** fixed in `65f08ae18`. rdd probes again on every pass until a probe finds the marker, and a failed probe keeps the boot's last result. `TestReconcileLimaMachines` covers both, and the design doc says Lima also reports a VM running when its wait for the boot scripts times out.

S4. **The LimaMachine spec accepts negative sizes** — `rdd/pkg/capi/v1alpha1/limamachine_types.go:29` [Claude Opus 5.5]

```go
	CPUs int `json:"cpus,omitempty"`
```

The CRD doesn't set a minimum for `cpus`, and its quantity pattern accepts a leading `-` for `memory` and `disk`. With I1's patch, a negative `memory` or `disk` shows up as `CreateFailed`. But `cpus: -1` passes Lima's validation, which rejects only 0 (`pkg/limayaml/validate.go:108` in the Lima fork), and fails only when the VM starts. Validation in the CRD would reject all three when the user applies the template.

Fix: add `+kubebuilder:validation:Minimum=1` to `cpus` and a CEL rule that requires positive `memory` and `disk`.

**Outcome:** fixed in `8174f7621`. CEL rules require positive `memory` and `disk`, as proposed. But `cpus` gets `Minimum=0`. A `cpus` of 0 means unset and gives the VM 2 vCPUs, so the review's `Minimum=1` would reject a valid spec.

S5. **The probe-failure branch builds its logger inline** — `rdd/pkg/controllers/app/capi/limamachine.go:222` [Gemini 3.1 Pro]

```go
			logf.FromContext(ctx).V(1).Info("Cannot probe the node VM", "limaVM", vmKey, "err", err)
```

The repo's controllers build their logger once at the top of a function and log through it, because an inline chain pushes its key/value pairs onto a continuation line where they are easy to miss. This is the only inline chain the branch adds.

Fix: declare `log := logf.FromContext(ctx)` at the top of `provisionLimaMachine`.

**Outcome:** fixed in `65f08ae18`. `provisionLimaMachine` declares `log` at the top.

S2. **A first boot slower than Lima's boot-script wait stays at `BootstrapFailed` until the VM restarts** — `rdd/pkg/controllers/app/capi/limamachine.go:216-235` (suggestion, new-feature)

```go

```

Design doc line 140 says Lima reports Running only after the boot scripts finish. That holds only inside Lima's wait of 200 × 3 s (the fork's `requirements.go:43-46`). ##### Design Observations

**Concerns**

- (future) `probeNodeOverSSH` runs synchronously in the single worker and can take up to 15 s per VM. When the App starts with N node VMs, one pass can take N × 15 s, which also delays deletions in that pass. A per-VM probe goroutine that writes into `r.probes` would bound the pass, at the cost of a lock.

- The registration token stays out of conditions and errors. The design also accounts for every place it lands, including base64 in the Lima template so that `text/template` never logs it.

```bash
    run_e -0 rdd limavm shell "${MACHINE}" ip -4 route show default dev lima0

```

In `assert_guest_to_guest_route`, assertions at lines 97, 101, 104, and 107 run in sequence without `|| return 1`. When evaluated where errexit is suspended (such as under `run`, `try`, or conditionals), a failure in `assert_output_lt` does not stop execution; subsequent passing checks reset the return status to 0, masking the earlier failure.

Fix: Append `|| return 1` to each assertion in `assert_guest_to_guest_route` so failures return immediately.

S2. **`LimaMachineTemplateResource` omits `metadata` field, causing user labels to be pruned** — `rdd/pkg/capi/v1alpha1/limamachinetemplate_types.go:32-35` (suggestion, new-feature)

```go
// LimaMachineTemplateResource defines the spec of a LimaMachine created from a
// template.
type LimaMachineTemplateResource struct {
	// spec is the desired state of the LimaMachine.
	Spec LimaMachineSpec `json:"spec"`
}
```

In Cluster API infrastructure templates, `spec.template` conventionally defines both `metadata` (labels and annotations to copy onto generated machines) and `spec`. Because `LimaMachineTemplateResource` only declares `Spec`, and `crds.yaml` does not preserve unknown fields under `spec.template`, any `metadata` supplied in a `LimaMachineTemplate` is pruned by the Kubernetes API server.

Fix: Add an optional `metadata` field with labels and annotations to `LimaMachineTemplateResource`.

S3. **`InstallScript` rejects bootstrap data formatted with CRLF line endings** — `rdd/pkg/controllers/app/capi/bootstrap.go:50-54` (suggestion, new-feature)

```go
func InstallScript(data []byte) ([]byte, error) {
	body, _ := bytes.CutPrefix(data, []byte("## template: jinja\n"))
	if !bytes.HasPrefix(body, []byte("#cloud-config\n")) {
		return nil, errors.New("bootstrap data does not start with a #cloud-config line")
	}
```

`InstallScript` checks for exact Unix newlines (`\n`) in `CutPrefix` and `HasPrefix`. If bootstrap data is created with CRLF (`\r\n`), `CutPrefix` fails to strip the jinja line and `HasPrefix` rejects the `#cloud-config` header.

Fix: Normalize `\r\n` to `\n` or support CRLF prefixes in `InstallScript`.

###### Design Observations

###### Concerns

1. **Guest cluster polling and token security (in-scope)**: Polling the guest cluster API without informers avoids storing guest tokens in controller informer caches, but means new `LimaCluster` and `LimaMachine` resources can wait up to 30 seconds (`requeueIdle`) before reconciliation begins. This is an acceptable security trade-off documented in `capi-provider.md:65`.

###### Strengths

- **Bootstrapping race prevention**: Ordering `lima-init.service` (`Before=sshd.service`) ensures that SSH probes can only execute after `guardScript` has run to completion, completely eliminating in-flight probe races.
- **Token isolation**: Base64 encoding the install script into a separate provisioning file (`install.sh.b64`) prevents Lima's `text/template` engine from attempting template substitution on shell scripts and logging sensitive tokens on failure.
- **Clean garbage collection**: The provider reconciles node VMs and input ConfigMaps using `machineUIDLabel` and `guestClusterUIDLabel`, properly pruning orphaned resources when a guest cluster is reset.

###### Testing Assessment

- I1: Required. Testing `crds.SplitYAML` with leading comments in a YAML document ensures valid multi-document streams are not dropped.
- I2: Optional. Testing `controlPlaneVersion` with custom namespaces or `apiVersion` in `controlPlaneRef`.
- S1: Optional. Testing `assert_guest_to_guest_route` assertion failure handling under `run`/`try`.
- S3: Optional. Testing `InstallScript` with CRLF bootstrap input.

###### Documentation Assessment

`rdd/docs/design/capi-provider.md` is well written, comprehensive, and accurately documents the provider architecture, token exposure model, condition transitions, and test suite. The typo flagged in S5 should be fixed in the CRD description.
