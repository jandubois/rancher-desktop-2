## Executive Summary

Moving the host-switch into the per-VM hostagent is the right ownership model: it deletes six teardown call sites, a mutex, and an `atomic.Bool`, and replaces them with OS reclamation that no future shutdown path can forget. Three issues survive verification, all in the seam between the new host and the moved code: a cancellation contract that never fires, lost error severity, and a doc guarantee the retry loop does not implement.

Gemini 3.1 Pro hit an exhausted quota and produced no output. The findings below come from Claude, Codex, and Gemini 3.5 Flash. I verified each one against the worktree at the review SHA.

## Important Issues

I1. **Host-switch context is never cancelled, so every clean-shutdown path is unreachable** — `rdd/pkg/hostagent/command.go:52` [Claude Opus 4.8, Codex GPT 5.6 Sol]

```go
	ctx := cmd.Context()
```

`main.go` reaches cobra through `cli.RunNoErrOutput` → `cmd.Execute()`, never `ExecuteContext`, and nothing calls `SetContext`. Cobra assigns `context.Background()`, so the `ctx` handed to `hostswitch.Run` at `command.go:192` is never cancelled and `ctx.Err()` is permanently nil.

Every branch keyed on cancellation is dead: the clean-stop check at `hostswitch_windows.go:136-141`, the `<-ctx.Done()` arm at lines 154-156, and the `Run` docstring's "returns nil on ctx cancellation". On a normal VM stop the vsock listener fails while `ctx.Err()` is still nil, so the loop logs "Host-switch exited unexpectedly; guest networking is down until it restarts" and schedules a retry. Process exit wins the race, but the log carries a misleading error on every clean shutdown.

`rdd/docs/design/networking.md:133-134` documents the same non-existent cancellation.

Fix: derive a cancellable context in `hostagentAction` and `defer` its cancel, so it fires when `ha.Run` returns:

```go
	hsCtx, hsCancel := context.WithCancel(ctx)
	defer hsCancel()
	// ... pass hsCtx to hostswitch.Run
```

I2. **The funcr adapter collapses `logger.Error` into `logrus.Info`** — `rdd/pkg/hostagent/command.go:184` [Codex GPT 5.6 Sol, Claude Opus 4.8]

```go
	hsLogger := funcr.New(func(prefix, args string) {
		if prefix != "" {
			logrus.Infof("%s: %s", prefix, args)
		} else {
			logrus.Info(args)
		}
	}, funcr.Options{Verbosity: hsVerbosity}).WithName("host-switch")
```

`funcr` routes `Info` and `Error` through one callback that cannot tell them apart, so every host-switch error lands as `level=info`: the bridge-died message at `hostswitch_windows.go:147`, the stalled-data-plane diagnostic at line 243, the unexpose failures at lines 349 and 365.

This compounds: RDD calls `hostagentevents.Watch(..., propagateStderr=false, ...)` at `hostagent_watcher.go:130`, so these lines never reach the daemon log at all. Combined with the removed `HostSwitchRestarted` event, a wedged bridge now leaves only an info-level line in a per-instance file.

Fix: implement a `logr.LogSink` over `funcr.Formatter` whose `Error` method calls `logrus.Errorf`, keeping the existing verbosity gate.

I3. **The design doc promises recovery for a data-plane wedge the retry loop never detects** — `rdd/docs/design/networking.md:141` [Codex GPT 5.6 Sol]

```markdown
If the bridge dies on its own while the VM keeps running (for example the vsock data plane wedges), the guest loses DHCP/DNS/NAT. `hostswitch.Run` detects the unexpected exit and restarts the bridge internally, rate-limited to one attempt per 15 seconds. The VM and hostagent keep running; the reconciler is not involved.
```

The named example is the one case not covered. `vn.AcceptStdio` errors are logged and the accept loop continues (`hostswitch_windows.go:225-251`); even the `relayDropWarnThreshold` escalation only emits diagnostics. `runOnce` returns solely on an `ln.Accept()` failure, so a wedged data plane behind a live listener never engages the supervisor.

Fix: narrow the doc to the setup and listener failures that actually escape `runOnce`, or add a watchdog that returns an error when the byte counters stay flat across consecutive short-lived connections.

## Suggestions

S1. **`store.Inspect` runs synchronously before boot and is fatal on every platform** — `rdd/pkg/hostagent/command.go:172` [Claude Opus 4.8]

```go
	inst, err := store.Inspect(ctx, instName)
	if err != nil {
		return fmt.Errorf("failed to inspect instance %q for host-switch: %w", instName, err)
	}
```

Its only consumer is the `VMType != WSL2` check inside `hostswitch.Run`, yet it blocks `ha.Run`. Because the hostagent already wrote its PID file at line 84, `Inspect` takes the `HostAgentPID != 0` branch and makes a 3s-capped HTTP round-trip to this process's own socket. On Windows `InspectStatus` also shells out to `wsl.exe --list --verbose` under a context that is never cancelled (see I1). On macOS and Linux the work is pure waste, since `Run` is a no-op there, yet a failure still aborts the hostagent.

The repo's own contract limits the blast radius: `store.Inspect` errors only on a missing `lima.yaml` or an invalid name, neither of which can happen at hostagent start. So the fatal path is close to unreachable, which is why this sits at Suggestion rather than Important.

Fix: move the inspect and its error handling inside the goroutine, so a lookup failure degrades only WSL2 networking.

S2. **The retry loop has no test seam** — `rdd/pkg/hostswitch/hostswitch_windows.go:133` [Claude Opus 4.8, Codex GPT 5.6 Sol]

The retry-and-backoff loop is the only new logic in the package, and `hostswitch_windows_test.go` still covers only `validateSubnet` and `newVirtualNetworkConfig`. Rate limiting, the `err == nil` hot-loop guard, and the cancellation arms cannot be exercised without a Windows VM.

Fix: extract `runLoop(ctx, logger, attempt func(context.Context) error) error` and have `Run` pass a closure over `runOnce`. The loop is then testable on every platform with a fake that fails on a schedule, including the assertion that a cancelled context ends it, which per I1 nothing currently proves.

S3. **Dead `else` branch in the log callback** — `rdd/pkg/hostagent/command.go:187` [Claude Opus 4.8]

```go
		} else {
			logrus.Info(args)
		}
```

`WithName("host-switch")` is applied at construction, so the formatter always carries a non-empty prefix and the fallback never runs. It reads as though unnamed lines are possible.

Fix: drop the conditional and keep the `Infof` form. If I2's sink replacement lands, the branch disappears with it.

S4. **Component label applied twice** — `rdd/pkg/hostswitch/hostswitch_windows.go:123` [Claude Opus 4.8]

```go
	logger = logger.WithValues("component", "host-switch")
```

The caller already names the logger `host-switch` (`command.go:190`), so every line carries the string twice: once as the funcr prefix, once as a key-value pair. Under the previous owner the reconciler's logger had no such name, so this was the only label.

Fix: drop this line, or drop `WithName` at the call site, but not both.

## Design Observations

### Concerns

1. **The Docker named pipe is still unscoped, and the socketbridge error is still swallowed** `(in-scope)` [Codex GPT 5.6 Sol, Gemini 3.5 Flash]

`socketbridge.NewDockerHostBridge` binds the well-known `\\.\pipe\docker_engine`, which Docker Desktop also owns, and the errgroup goroutine at `hostswitch_windows.go:202-208` logs the failure then returns nil, so the new supervisor never retries it. The engine controller dials the same path and accepts any successful ping, so Docker Desktop's daemon can be mirrored and its containers force-removed.

This code moved verbatim; the PR neither introduces nor worsens it, and `deep-review-context.md` already records it. Raising it here only because the move is the natural moment to scope the pipe to the instance.

2. **Bridge failure lost its structured signal** `(future)` [Claude Opus 4.8]

The old path emitted a `HostSwitchRestarted` Warning event and set a `failed` flag the reconciler could read. `networking.md:141` documents the new arrangement as deliberate, but a permanently wedged bridge is now invisible to `rdd ctl describe limavm` and to App-level readiness. The hostagent could emit a lima `events.Event` with `Status.Errors` on stdout, which `hostagent_watcher.go:97` already parses, letting the reconciler surface a condition without owning the restart.

3. **Restarts accumulate gvisor stacks** `(future)` [Claude Opus 4.8]

`virtualnetwork.VirtualNetwork` exposes no `Close` in gvisor-tap-vsock v0.8.9, so each pass through `runOnce` leaves the previous netstack and its goroutines behind. The old design had the same property at the same 15s rate, so this is a gap rather than a regression, but a hostagent surviving a long crash loop now accumulates them for the VM's whole life.

### Strengths

1. **The ownership model is the real win** [Claude Opus 4.8, Codex GPT 5.6 Sol, Gemini 3.5 Flash]

Tying the bridge to the hostagent deletes four `stopHostSwitch` call sites, an `atomic.Bool`, a second mutex, and a reconciler branch, replacing them with OS reclamation that a new shutdown path cannot forget.

2. **`fail(...)` became ordinary wrapped-error returns** [Claude Opus 4.8]

`runOnce` now has a single exit contract (`hostswitch_windows.go:169`, `176`, `186`), which is what makes the retry loop expressible at all.

3. **`unexposeAllForwards` kept its `defer` and got an honest comment** [Claude Opus 4.8]

The rewritten comment at lines 336-341 narrows the old claim to the internal-restart case. That is the right treatment of an invariant whose reason changed while its necessity did not.

## Testing Assessment

No test accompanies the move, and the retry loop is the one piece of new logic (S2). Beyond that seam, four gaps stand out:

1. **Clean-shutdown classification.** Nothing distinguishes a cancelled stop from a failure, which is exactly the distinction I1 shows is currently impossible to reach.
2. **The non-WSL2 early return.** `hostswitch_other.go:22` and the `VMType` guard at `hostswitch_windows.go:120-122` are the only protection against the host-switch firing on a vz/qemu instance; neither is asserted.

4. **Windows lifecycle.** Hostagent exit releasing the pipe, vsock, and forwarded ports is untested, as is the engine controller refusing a foreign Docker daemon.

BATS adds nothing here, and the Windows path is untestable in the current matrix. A non-Windows assertion that `rdd limavm` start/stop still works would at least cover the new pre-boot inspect on macOS and Linux.

## Review Process Notes

### Skill improvements

- [ ] When a finding depends on a context's cancellation semantics, trace the context to its origin before accepting or rejecting it. A `ctx` obtained from a framework accessor (`cmd.Context()`, a request context, an injected field) may be a background context that is never cancelled, which silently converts every `<-ctx.Done()` branch and every `ctx.Err()` check into dead code while the surrounding comments and design docs continue to describe cancellation as the shutdown path. Verify the entry point actually installs a cancellable context rather than assuming the accessor implies one.

- [ ] Treat a design document's own example as a claim to verify, not as context. When a doc names a specific failure mode as the one a recovery mechanism handles, trace that exact scenario through the code. Illustrative examples are written from intent and are the most likely part of a document to outrun the implementation, particularly when the mechanism recovers from a different, coarser class of failure than the example describes.

- [ ] When a PR moves code between processes or ownership domains, diff the logging path as carefully as the logic. An adapter inserted at the new boundary (a `logr` sink, a writer wrapper, a formatter callback) can silently drop severity, redirect a stream to a file nothing propagates, or change which log the operator actually reads. Verify that an error raised in the moved code still reaches an operator at error level, and name the file it lands in.

### Repo context updates

- [ ] [repo] The `rdd` CLI reaches cobra through `cli.RunNoErrOutput` (`k8s.io/component-base/cli`) → `cmd.Execute()`, never `ExecuteContext`, and nothing calls `SetContext`. So `cmd.Context()` inside any subcommand's `RunE` is `context.Background()` and is never cancelled, on any platform. Subcommands that need shutdown propagation must derive their own cancellable context and cancel it explicitly; on Windows the shutdown request arrives through the named interrupt event registered by `process.RegisterInterruptHandler`, not through a signal, so `signal.NotifyContext` alone is not sufficient. Reject findings that assume `cmd.Context()` cancels on SIGTERM, and flag new code whose cleanup depends on it.

- [ ] [repo] RDD calls lima's `hostagentevents.Watch` with `propagateStderr=false` (`rdd/pkg/controllers/lima/limavm/controllers/hostagent_watcher.go`), so anything the hostagent writes to stderr stays in that instance's `ha.stderr.log` and never reaches the daemon log. Only lima events on hostagent *stdout* drive reconciler behavior. When reviewing code that logs from inside the hostagent process, do not treat a log call as operator-visible in `rdd.stderr.log`, and check whether a failure needs a lima `events.Event` (which the watcher parses) rather than a log line.

- [ ] [repo] `store.Inspect` called from inside the hostagent process is not free and not equivalent to calling it from the reconciler. The hostagent writes its own PID file early, so `Inspect` takes the `HostAgentPID != 0` branch and makes a 3s-capped HTTP round-trip to the hostagent's own API socket; on Windows the WSL2 driver's `InspectStatus` also shells out to `wsl.exe --list --verbose`. Flag a synchronous `Inspect` on the hostagent's pre-boot path, especially under a context that is never cancelled.

- [ ] [repo] `virtualnetwork.VirtualNetwork` (gvisor-tap-vsock v0.8.9) exposes no `Close`, so every host-switch restart leaks the previous netstack and its goroutines. Treat "restart the bridge" designs as accumulating, and judge a restart loop by whether it bounds attempts or documents the leak, not by whether it tears the old network down.

## Deep Review — PR #578: Move host-switch from RDD controller to hostagent

### Executive Summary

The PR relocates the WSL2 host-switch (gvisor-tap-vsock bridge, vsock handshake, Docker socket bridge) from a reconciler-managed goroutine into the per-VM hostagent process, replacing reconciler-driven teardown and restart with process-lifetime reclamation and an internal rate-limited retry loop. The mechanics are sound and the reconciler simplifies substantially. The headline problem is that the context handed to `hostswitch.Run` is `context.Background()` — every cancellation path in the new loop, and the design doc's stop sequence, describe behavior that cannot occur.

**I1. Host-switch context is never cancelled; every clean-shutdown path in `Run` is unreachable — `rdd/pkg/hostagent/command.go:52,192`** (important, regression)

```go
func hostagentAction(cmd *cobra.Command, args []string) error {
	ctx := cmd.Context()
```

Neither `cmd/rdd/main.go` nor `cmd/lima-controller/main.go` calls `SetContext`; both reach cobra through a plain `Execute()`, which assigns `context.Background()` when `c.ctx == nil`. So the `ctx` passed to `hostswitch.Run` at line 192 is never cancelled, and `ctx.Err()` is permanently nil. Consequences in `hostswitch_windows.go`: the clean-stop branch at lines 136-141 and the `<-ctx.Done()` arm at lines 154-156 can never fire, so the docstring's "It returns nil on ctx cancellation" (line 116) is unreachable. When the VM stops and the bridge's peer disappears, `Run` must classify it as a failure, logging "Host-switch exited unexpectedly; guest networking is down until it restarts" (line 147) and relaunching a handshake loop on every normal stop. `networking.md:133-134` documents the same non-existent cancellation.

Fix: derive a cancellable context and cancel it both when `ha.Run` returns and on interrupt. `signal.NotifyContext` is not sufficient — on Windows the shutdown request arrives through the named event registered at lines 67-72, not a signal, so the closure must do the cancelling.

```diff

+	defer hsCancel()
 	releaseInterrupt, err := process.RegisterInterruptHandler(process.HostagentInterruptKey(instName), func() {
+		hsCancel()
 		select {
 		case signalCh <- os.Interrupt:
 		default:
 		}
 	})
```
(and pass `hsCtx` to `hostswitch.Run`; move the `WithCancel` above the handler registration).

```go
func (s logrusSink) WithValues(kv ...any) logr.LogSink  { s.AddValues(kv); return s }
```

## Design Observations

### Concerns

#### 1. **Docker named pipe collision handling is silent** `(in-scope)`
On Windows, RDD's Docker socket bridge attempts to bind to the well-known named pipe `\\.\pipe\docker_engine` (`rdd/pkg/socketbridge/host_windows.go`). If another process (such as Docker Desktop) already owns this named pipe, the call to `bridge.Run(gctx)` logs an error and returns `nil`. This is highly beneficial for robustness because it avoids stalling guest-side internet access (DHCP/DNS/NAT), but because it fails silently from the reconciler's perspective, users may not easily realize that the Docker socket bridge itself is non-functional.

### Strengths

#### 1. **Elegant resource reclamation**
Moving the host-switch into the hostagent process allows the host OS to automatically garbage-collect the vsock listeners, gvisor networking stack, and exposed ports when the process exits. This completely removes the risk of orphaned resources outliving the VM.

#### 2. **Self-contained bridge failure recovery**
By managing recovery internally with `hostswitch.Run`'s rate-limited retry loop (retrying once per 15 seconds), the VM remains running and unaffected by transient vsock connection drops, and the main controller is spared from dealing with network-level reconnections.

#### 3. **Observability and clean logging integration**
Using `funcr` to wrap the `logr.Logger` interface and redirect host-switch diagnostics to `logrus` stderr output successfully keeps verbose diagnostics out of the stdout stream, preventing pollution of the Lima event watcher.
