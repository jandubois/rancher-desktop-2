## Executive Summary

Round 2 landed most of round 1's fixes: the bulk requeue, the UID guard,
throttled progress writes, the AfterFunc leak, the namespace lock and the
BATS setup. Three Important defects remain: the coalescing fix left each
object's UID in the App key, so mirror bursts queue one reconcile per object;
the completion goroutine reads a shared error the pull goroutine writes
unsynchronised; and a test reads the state map without the lock, so
`go test -race` fails.

Four reviewers ran. Gemini 3.1 Pro's first launch hung silently after five
minutes and was relaunched once with a larger budget. Every Important finding
carries a reproducer run in the lead worktree, and every proposed fix was
re-run under the race detector. Three round-1 findings were declined by the
author in a PR comment and are recorded under Acknowledged Limitations rather

## Design Observations

### Concerns

**Completion state travels through a closure variable instead of the context cause that already carries it** `(in-scope)` [Claude Opus 5, Codex GPT 5.6 Sol]. `progressCtx` is cancelled with a cause on every terminal path, and `context.Cause` gives a race-free read with a guaranteed happens-before edge, but the comment at `image_pull_request_reconciler.go:236-237` explains why the code bypasses it: a `nil` cause reads back as `context.Canceled`. A success sentinel removes the closure variable and I2 with it, and leaves the `Done` branch with one input to inspect for every cancel reason: typed reason, `Deleted`, the UID-mismatch error, shutdown, or completion.

**The last defence against a wrong `Succeeded` is an API call that happens to fail** `(in-scope)` [Claude Opus 5, Gemini 3.1 Pro]. On manager shutdown the goroutine reaches `setImagePullRequestTerminalReasonFromError(imagePullRequest, nil)`, and the only reason the result is not persisted is that `Status().Update` at line 415 runs on the cancelled `pullContext`. The `r.Get` before it reads the informer cache, which ignores cancellation. An explicit `if pullContext.Err() != nil { return }` before line 264 makes the invariant local.

**`spec.namespace` is validated but never consumed** `(future)` [Claude Opus 5]. The webhook proves the named `ContainerNamespace` exists, but the reconciler hands the repo tag straight to the moby watcher; only the webhook reads the field. Today only `ContainerNamespace/moby` exists so the two agree by construction. When containerd mirroring lands, a request naming a containerd namespace will pull into moby with no error.

**Deleting `ContainerNamespace/moby` is allowed with a warning, and the new validator then rejects every pull request until fullSync recreates it** `(future)` [Codex GPT 5.6 Sol]. `container_namespace_webhooks.go:25-28` still carries the TODO that the moby namespace should not be deletable. Round 1 noted the same tension from the other side: the validator rejects a request whose namespace object does not exist, so the reconciler's "queue until the engine is up" path serves a case a client cannot reach. Unchanged this round.

### Strengths

**Namespace threaded as a parameter rather than locked at every read** [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.5 Flash]. `cleanupMirrorResources`, `waitMirrorResourcesGone`, `countMirrorResources`, `deleteAllOfType`, `reconcileContainerActions`, `processFinalizers` and the three `process*Finalizers` helpers take `namespace string`, which removes the shared-field read from the hot paths. Every remaining `r.apiNamespace` access (`container_passthrough.go:72`, `image_pull_request_reconciler.go:99`, `watch_reconciler.go:47,183`) is under `engineMu`, so `e53b824d9`'s commit body holds.

**Smallest non-zero `RequeueAfter` fold in the bulk path** [Claude Opus 5, Codex GPT 5.6 Sol]. Lines 116-127 fix round-1 I1 cleanly and correctly ignore the zero results terminal requests return.

**Ticker-decoupled progress writes** [Gemini 3.1 Pro, Gemini 3.5 Flash]. The 100 ms ticker with a changed flag caps status writes at ten per second per pull regardless of how fast moby streams, which settles round-1 I5.

## Acknowledged Limitations

### Declined in prior rounds

- **Round-1 I2, `Unauthorized` and `InvalidArgument` unreachable via the stream** — declined Round 1 by the author: "Ignored, but the other path is now covered." ## Review Process Notes

### Skill improvements

- [ ] When a change moves work out of a synchronous callback into a goroutine that also wakes on context cancellation, enumerate every source that can cancel that context and check that each one supplies the ordering guarantee the callback had. The callback's argument becomes shared state the moment it is stored for a goroutine to read, and only the path the fix was written for establishes the happens-before edge by construction.
- [ ] Before crediting an agent's reproducer, read its assertion against the failure it quotes. An assertion the finding's own premise satisfies (asserting that two keys differ, to show they are not deduplicated) cannot have produced the quoted failure; the block was written to satisfy the format, and the finding needs the consolidator's own probe.
- [ ] When an external agent's watchdog fires, read the timestamp of its last session record before choosing the retry budget. A session whose last record is minutes old with no output written is a hung API turn and retries cleanly at any budget; one still writing records at the deadline is a budget failure, where the retry needs a larger deadline and the scratch directory may already hold usable probes.

### Repo context updates

- [ ] [repo] CI's "RDD Unit tests" job runs `make test`, which is plain `go test ./...` without `-race`. A data race in a test or in the code under test ships green, so run `go test -race` on every Go package a PR touches and treat a failure as a regression against the verified baseline, not as a CI flake.
- [ ] [repo] `engineRequest`, the engine reconciler's workqueue key, is the whole struct: `Kind`, `NamespacedName` and `UID`. A handler that maps many objects onto the singleton App request must leave `UID` empty; a constant `NamespacedName` alone does not restore coalescing.
- [ ] [repo] controller-runtime's cached client ignores context cancellation on `Get`, which reads the informer store, while `Status().Update` and other writes fail immediately on a cancelled context. A goroutine that runs on past a cancelled context therefore reads a valid object and then logs a write failure; a guard that relies on the read failing is not a guard.

## Design Observations

### Concerns

- **Completion state travels through a closure variable rather than the context that already carries it** `(in-scope)`. `progressCtx` is cancelled with a cause on every terminal path, and `context.Cause` gives a race-free read with a guaranteed happens-before edge — but the code deliberately bypasses it (`image_pull_request_reconciler.go:236-238`: "context.Cause(progressCtx) returns Cancelled if the context is cancelled with nil; however, we want to distinguish that from a successful pull"). A one-line sentinel removes the closure variable and I1 with it: cancel with `errPullSucceeded` instead of `nil` inside `progressCancel`, then map that sentinel back to `nil` at the read site. The Done branch then has exactly one input — the cause — and every cancel reason (typed reason, `Deleted`, the UID-mismatch `errors.New`, `watcherCtx` shutdown, completion) is distinguishable by inspecting it, instead of the current mix of a state-map lookup, an `errors.AsType` check, and an unsynchronised variable.

- **The last defence against a wrong `Succeeded` is an API call that happens to fail** `(in-scope)`. On manager shutdown the goroutine reaches `setImagePullRequestTerminalReasonFromError(imagePullRequest, nil)` → `Succeeded`, and the only reason it is not persisted is that `r.Status().Update` at line 415 runs on the cancelled `pullContext`. The `r.Get` two lines earlier reads the informer cache, which ignores context cancellation entirely — so the guard is not the context check it looks like. An explicit `if pullContext.Err() != nil { return }` before line 281 makes the invariant local and legible.

- **`spec.namespace` is validated but never used** `(future)`. The webhook proves the named `ContainerNamespace` exists (`image_pull_request_webhooks.go:52-64`), but `reconcileSingleImagePullRequest` hands the repo tag straight to the moby watcher and ignores the field. Today only `ContainerNamespace/moby` exists so the two agree by construction; when containerd mirroring lands, a request naming a containerd namespace will be pulled into moby with no error. Worth a `// TODO` at the call site rather than a code change now.

### Strengths

- Threading `namespace string` through `cleanupMirrorResources`, `waitMirrorResourcesGone`, `countMirrorResources`, `deleteAllOfType`, `reconcileContainerActions` and the three `process*Finalizers` helpers (`watch_reconciler.go`) is the right shape: it removes the shared-field read from the hot paths entirely instead of sprinkling locks, and I verified every remaining `r.apiNamespace` access (`container_passthrough.go:72`, `image_pull_request_reconciler.go:99`, `watch_reconciler.go:47`, `:183`) is under `engineMu`.
- The bulk path's smallest-non-zero `RequeueAfter` fold (lines 116-127) is a clean fix for round-1 I1 and correctly ignores the zero results that terminal requests return.
- Splitting `watch_reconciler.go` out of the 900-line `engine_reconciler.go` leaves a dispatcher small enough to read in one screen.

##### I1. **Lost Workqueue Coalescing for Mirror Events** — `rdd/pkg/controllers/app/engine/controllers/engine_reconciler.go:226-233` (important, regression)

```go

	// enqueue a reconcile request for the App so the watcher can update.

		func(_ context.Context, obj client.Object) []engineRequest {

			}}
		})
```

The refactoring introduced the custom `engineRequest` type with a `UID` field. In `enqueueRequestsForApp`, assigning the individual child resource's `UID` (such as a `Container` or `Volume` UID) to the `AppKind` request makes each mapped request structurally unique. Since the workqueue deduplicates based on the entire `engineRequest` value, this prevents any coalescing of concurrent mirror resource events. On VM boot or bulk operations (e.g., 500 container updates), the queue depth reaches 500 instead of 1, resulting in 500 redundant, serialized reconcile loops that retrieve the single "app" object and execute identical watcher checks.
