Executive Summary ¶

The staging mechanism is correct and faithful to the investigation gist. The pinned SHA-256 matches AMD's release byte-for-byte, the .deb extraction handles the real archive's symlinks properly, and marker-last write ordering is crash-safe. The issues below are all variants of one theme — the guest can end up without the bridge, or with a stale one, while the API reports success.

Four Important findings: a spec.gpu.source change never reaches the guest, a failed stage is silent and unretried, the design doc's pod contract drops the hostPath type guards the gist proved, and the package is described as MIT when the staged library links a proprietary blob. I have grouped the findings by the failure they produce; several span more than one file.

Design Observations ¶

Concerns ¶

  • No status surface for GPU state (in-scope) Claude Opus 5 Codex GPT 5.6 Sol — App.Status gains nothing, so nothing can distinguish "installed" from "enabled but the download failed" from "enabled on macOS, where the toggle is inert". One GPUReady condition closes the observability half of I1 and I2 and gives a future preferences checkbox something to bind to.
  • Payload identity lives outside the template (in-scope) Codex GPT 5.6 Sol — the template holds a fixed path while the meaningful state is the mutable files behind it. A content-addressed manifest would make restart identity and App settlement derive from the same state, which is the shared root of I1 and I2.
  • spec.gpu.source is a daemon-host path in a resource a remote GUI may set (future) Claude Opus 5 — every other App spec field is host-independent. This cuts against the standing constraint that the GUI and daemon must work over the socket alone and may run on different machines. A pinned URL + digest pair travels; a path does not, and it would fold the air-gapped case into the verified-download path instead of a second unverified one.
  • Runtime acquisition versus shipping the bits (future) Codex GPT 5.6 Sol Claude Opus 5 — mook-as's proposal to build librocdxg and bundle it would delete the fetch path and with it I2, I4, S3, S9 and S16. Worth settling before this graduates from experimental, because that path is where nearly every finding clusters.

Strengths ¶

  • Marker-last write ordering is genuinely crash-safe (in-scope) Claude Opus 5 — two reviewers drafted a stale-marker finding here and both retracted it after tracing the windows. Every partial state across a version bump leaves the old marker, so the next run re-fetches. Worth preserving through any refactor.
  • The fetch is pinned properly (in-scope) Codex GPT 5.6 Sol Gemini 3.5 Flash — an immutable release-tag URL, a SHA-256 checked before any parsing, and the bump instruction in the comment. Extraction only ever touches verified bytes.
  • Enable/disable symmetry is carried end to end (in-scope) Claude Opus 5 — host Unstage, GPU_ENABLED: false, and guest rm -f, rather than leaving a manual cleanup step.
  • The guest contract matches the proven procedure exactly (in-scope) Codex GPT 5.6 Sol — paths, 0755/0644 modes, /dev/dxg, hostIPC, both env vars, and the native-KFD scope boundary all line up with the gist.
  • gpuWindowsHostSupported as a test seam (in-scope) Claude Opus 5 — lets the enabled path be tested on macOS/Linux CI, which is the only automated coverage this Windows-only feature can get.

Review Process Notes ¶

Skill improvements ¶

  • When a PR description links an external design document, gist, or investigation write-up, fetch it and inline it in the prompt as the specification of record, with an instruction to check the implementation against every concrete contract it states (paths, permissions, environment variables, version requirements) and against every negative result it records. Divergence between a proven manual procedure and the automation that replaces it is a defect class that reading the diff alone cannot surface, because both sides look internally consistent.
  • When a change ships both a reference document and a runnable example of the same contract, diff them against each other and against any source procedure. The document is what readers copy and the example is what was actually executed, so a guard present in one and absent in the other marks the document as the untested copy.
  • Before accepting a reviewer's claim that a shell command will fail on a given input, run that command against that input. Coreutils tools frequently succeed where a reviewer expects failure, and the difference between a loud failure and a silent wrong result inverts both the severity and the fix.

Repo context updates ¶

  • [repo] Test functions in this repo that mutate a package-level var test seam are correct without t.Parallel() even when sibling tests in the same file call it: Go runs the sequential portion of every top-level test before resuming any paused parallel one, so a non-parallel mutating test completes, including its t.Cleanup, before parallel siblings observe the variable. Do not report this as a data race without first running go test -race; report it as latent fragility only.
  • [repo] make verify-generate fails on main by rewriting comments in nine unrelated containers apply-configuration files. Treat a failure confined to those files as pre-existing drift, not a PR defect; only a diff touching the CRD or deepcopy files of the package under review is a real finding.
  • [repo] The App reconciler registers no MaxConcurrentReconciles and no periodic requeue in SetupWithManager, so it runs single-threaded and an error swallowed inside Reconcile is retried only on the next watch event or controller-runtime's 10-hour default resync. Any blocking I/O added to that path serialises the whole App loop, and any best-effort error swallow needs an explicit requeue to converge.
